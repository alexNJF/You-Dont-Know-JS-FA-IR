# Closure (بخش ۱)

بیایید اول closure را با چند عملیات ریاضی رایانه رایج تمرین کنیم: تعیین اینکه آیا مقداری اول است (هیچ مقسوم‌علی جز ۱ و خودش ندارد)، و تولید لیست عامل‌های اول (مقسوم‌علی‌ها) برای عدد داده‌شده.

مثلاً:

```js
isPrime(11);        // true
isPrime(12);        // false

factorize(11);      // [ 11 ]
factorize(12);      // [ 3, 2, 2 ] --> 3*2*2=12
```

این پیاده‌سازی `isPrime(..)` است، اقتباس‌شده از کتابخانه Math.js: [^MathJSisPrime]

```js
function isPrime(v) {
    if (v <= 3) {
        return v > 1;
    }
    if (v % 2 == 0 || v % 3 == 0) {
        return false;
    }
    var vSqrt = Math.sqrt(v);
    for (let i = 5; i <= vSqrt; i += 6) {
        if (v % i == 0 || v % (i + 2) == 0) {
            return false;
        }
    }
    return true;
}
```

و این پیاده‌سازی نسبتاً پایه `factorize(..)` است (با `factorial(..)` از فصل ۶ اشتباه نشود):

```js
function factorize(v) {
    if (!isPrime(v)) {
        let i = Math.floor(Math.sqrt(v));
        while (v % i != 0) {
            i--;
        }
        return [
            ...factorize(i),
            ...factorize(v / i)
        ];
    }
    return [v];
}
```

| نکته: |
| :--- |
| این را پایه می‌نامم چون برای عملکرد بهینه نشده. binary-recursive است (که tail-call optimizable نیست) و کپی‌های آرایه میانی زیادی ایجاد می‌کند. همچنین عامل‌های کشف‌شده را به هیچ ترتیبی مرتب نمی‌کند. الگوریتم‌های بسیار دیگری برای این کار هست، اما می‌خواستم چیزی کوتاه و تقریباً قابل فهم برای تمرینمان استفاده کنم. |

اگر `isPrime(4327)` را چندین بار در برنامه فراخوانی کنید، می‌بینید هر بار از همه ده‌ها مرحله مقایسه/محاسبه عبور می‌کند. اگر `factorize(..)` را در نظر بگیرید، هنگام محاسبه لیست عامل‌ها `isPrime(..)` را چندین بار فراخوانی می‌کند. و احتمال خوبی هست بیشتر آن فراخوانی‌ها تکراری باشند. کار هدررفته زیادی!

بخش اول این تمرین استفاده از closure برای پیاده‌سازی cache برای به یاد آوردن نتایج `isPrime(..)` است، تا اول بودن (`true` یا `false`) عدد داده‌شده فقط یک بار محاسبه شود. اشاره: این نوع کش را قبلاً در فصل ۶ با `factorial(..)` نشان دادیم.

اگر به `factorize(..)` نگاه کنید، با بازگشت پیاده‌سازی شده، یعنی بارها خودش را فراخوانی می‌کند. دوباره یعنی احتمالاً فراخوانی‌های هدررفته زیادی برای محاسبه عامل‌های اول همان عدد می‌بینیم. پس بخش دوم تمرین استفاده از همان تکنیک closure cache برای `factorize(..)` است.

از closureهای جدا برای کش کردن `isPrime(..)` و `factorize(..)` استفاده کنید، به جای قرار دادن آن‌ها در یک scope واحد.

خودتان تمرین را امتحان کنید، سپس راه‌حل پیشنهادی را در انتهای این پیوست ببینید.

### کلامی درباره حافظه

می‌خواهم نکته سریعی درباره این تکنیک closure cache و تأثیراتش بر عملکرد اپلیکیشن‌تان به اشتراک بگذارم.

می‌بینیم که با ذخیره فراخوانی‌های تکراری، سرعت محاسبه را بهبود می‌دهیم (در برخی موارد، به میزان چشمگیر). اما این استفاده از closure trade-off صریحی می‌کند که باید خیلی آگاه باشید.

Trade-off حافظه است. اساساً cacheمان را (در حافظه) به طور نامحدود رشد می‌دهیم. اگر توابع مورد نظر میلیون‌ها بار با عمدتاً ورودی‌های یکتا فراخوانی شوند، حافظه زیادی مصرف می‌کنیم. قطعاً می‌تواند ارزش هزینه را داشته باشد، اما فقط اگر فکر می‌کنیم احتمالاً تکرار ورودی‌های مشترک می‌بینیم تا از cache بهره ببریم.

اگر تقریباً هر فراخوانی ورودی یکتا داشته باشد و cache اساساً هرگز *استفاده* نشود تا سودی ببرد، این تکنیک نامناسبی برای استفاده است.

همچنین ممکن است ایده خوبی باشد رویکرد کش پیچیده‌تری داشته باشید، مثل cache LRU (least recently used)، که اندازه‌اش را محدود می‌کند؛ وقتی به حد می‌رسد، LRU مقادیری را که... خوب، کم‌ترین استفاده اخیر را داشتند evict می‌کند!

نکته منفی اینجا این است که LRU خودش کاملاً non-trivial است. می‌خواهید پیاده‌سازی بهینه‌شده و بررسی‌شده LRU استفاده کنید و به شدت از همه trade-offهای درگیر آگاه باشید.
