# ماژول چیست؟

ماژول مجموعه‌ای از داده و توابع مرتبط است (اغلب در این زمینه به عنوان متدها نامیده می‌شوند)، که با تقسیم‌بندی بین جزئیات *خصوصی* پنهان و جزئیات *عمومی* قابل دسترسی مشخص می‌شود، معمولاً «API عمومی» نامیده می‌شود.

ماژول همچنین stateful است: اطلاعاتی را در طول زمان نگه می‌دارد، همراه با قابلیت دسترسی و به‌روزرسانی آن اطلاعات.

| نکته: |
| :--- |
| نگرانی گسترده‌تر الگوی ماژول پذیرش کامل modularization در سطح سیستم از طریق loose-coupling و تکنیک‌های معماری برنامه دیگر است. آن موضوع پیچیده‌ای است که فراتر از محدوده بحث ماست، اما ارزش مطالعه بیشتر فراتر از این کتاب را دارد. |

برای درک بهتر ماژول، بیایید چند ویژگی ماژول را با الگوهای کد مفیدی که کاملاً ماژول نیستند مقایسه کنیم.

### Namespaceها (گروه‌بندی بدون حالت)

اگر مجموعه‌ای از توابع مرتبط را بدون داده با هم گروه کنید، واقعاً encapsulation مورد انتظار یک ماژول را ندارید. اصطلاح بهتر برای این گروه‌بندی توابع *بدون حالت* namespace است:

```js
// namespace, not module
var Utils = {
    cancelEvt(evt) {
        evt.preventDefault();
        evt.stopPropagation();
        evt.stopImmediatePropagation();
    },
    wait(ms) {
        return new Promise(function c(res){
            setTimeout(res,ms);
        });
    },
    isValidEmail(email) {
        return /[^@]+@[^@.]+\.[^@.]+/.test(email);
    }
};
```

`Utils` اینجا مجموعه مفیدی از ابزارهاست، اما همه توابع مستقل از حالت هستند. گردآوری قابلیت با هم به طور کلی تمرین خوبی است، اما این را ماژول نمی‌کند. بلکه یک namespace `Utils` تعریف کرده و توابع را زیر آن سازماندهی کرده‌ایم.

### ساختارهای داده (گروه‌بندی با حالت)

حتی اگر داده و توابع stateful را با هم بسته‌بندی کنید، اگر دیدپذیری هیچ‌کدام را محدود نکنید، از جنبه POLE encapsulation کوتاه می‌آیید؛ چندان مفید نیست که آن را ماژول بنامیم.

در نظر بگیرید:

```js
// data structure, not module
var Student = {
    records: [
        { id: 14, name: "Kyle", grade: 86 },
        { id: 73, name: "Suzy", grade: 87 },
        { id: 112, name: "Frank", grade: 75 },
        { id: 6, name: "Sarah", grade: 91 }
    ],
    getName(studentID) {
        var student = this.records.find(
            student => student.id == studentID
        );
        return student.name;
    }
};

Student.getName(73);
// Suzy
```

چون `records` داده عمومی قابل دسترسی است، نه پشت API عمومی پنهان، `Student` اینجا واقعاً ماژول نیست.

`Student` جنبه داده-و-قابلیت encapsulation را دارد، اما جنبه کنترل-دیدپذیری را ندارد. بهتر است این را نمونه‌ای از ساختار داده بنامیم.

### ماژول‌ها (کنترل دسترسی با حالت)

برای تجسم روح کامل الگوی ماژول، نه فقط به گروه‌بندی و حالت، بلکه به کنترل دسترسی از طریق دیدپذیری (خصوصی در مقابل عمومی) نیاز داریم.

بیایید `Student` از بخش قبلی را به ماژول تبدیل کنیم. با شکلی شروع می‌کنیم که آن را «ماژول کلاسیک» می‌نامم، که در اصل وقتی در اوایل دهه ۲۰۰۰ پدیدار شد «ماژول آشکارساز» نامیده می‌شد. در نظر بگیرید:

```js
var Student = (function defineStudent(){
    var records = [
        { id: 14, name: "Kyle", grade: 86 },
        { id: 73, name: "Suzy", grade: 87 },
        { id: 112, name: "Frank", grade: 75 },
        { id: 6, name: "Sarah", grade: 91 }
    ];

    var publicAPI = {
        getName
    };

    return publicAPI;

    // ************************

    function getName(studentID) {
        var student = records.find(
            student => student.id == studentID
        );
        return student.name;
    }
})();

Student.getName(73);   // Suzy
```

`Student` اکنون نمونه‌ای از ماژول است. دارای API عمومی با یک متد است: `getName(..)`. این متد می‌تواند به داده خصوصی پنهان `records` دسترسی پیدا کند.

| هشدار: |
| :--- |
| باید اشاره کنم که داده صریح دانش‌آموز که hard-code در تعریف این ماژول شده فقط برای اهداف توضیح ماست. یک ماژول معمولی در برنامه‌تان این داده را از منبع بیرونی دریافت می‌کند، معمولاً از دیتابیس‌ها، فایل‌های داده JSON، فراخوانی‌های Ajax و غیره بارگذاری می‌شود. داده سپس معمولاً از طریق متد(های) روی API عمومی ماژول به نمونه ماژول inject می‌شود. |

الگوی ماژول کلاسیک چطور کار می‌کند؟

توجه کنید که نمونه ماژول با اجرای IIFE `defineStudent()` ایجاد می‌شود. این IIFE یک object (به نام `publicAPI`) برمی‌گرداند که ویژگی روی آن دارد که به تابع درونی `getName(..)` ارجاع می‌دهد.

نامیدن object به `publicAPI` ترجیح سبکی من است. object می‌تواند هر نامی داشته باشد (JS اهمیت نمی‌دهد)، یا می‌توانید مستقیماً object را بدون انتساب به هیچ متغیر نام‌دار داخلی برگردانید. بیشتر درباره این انتخاب در پیوست الف.

از بیرون، `Student.getName(..)` این تابع درونی در معرض را فراخوانی می‌کند که از طریق closure به متغیر درونی `records` دسترسی دارد.

*نباید* حتماً object با تابع به عنوان یکی از ویژگی‌هایش برگردانید. می‌توانید مستقیماً یک تابع برگردانید، به جای object. آن همچنان همه اجزای اصلی ماژول کلاسیک را برآورده می‌کند.

به خاطر نحوه کار lexical scope، تعریف متغیرها و توابع داخل تابع تعریف ماژول بیرونی همه چیز را *به طور پیش‌فرض* خصوصی می‌کند. فقط ویژگی‌های اضافه‌شده به object API عمومی برگشتی از تابع برای استفاده عمومی خارجی export می‌شوند.

استفاده از IIFE دلالت می‌کند که برنامه ما فقط به یک نمونه مرکزی واحد از ماژول نیاز دارد، معمولاً «singleton» نامیده می‌شود. در واقع، این مثال خاص به اندازه کافی ساده است که دلیلی واضح برای نیاز به چیزی بیش از فقط یک نمونه ماژول `Student` نیست.

#### کارخانه ماژول (چند نمونه)

اما اگر می‌خواستیم ماژولی تعریف کنیم که چند نمونه در برنامه پشتیبانی کند، می‌توانیم کد را کمی تغییر دهیم:

```js
// factory function, not singleton IIFE
function defineStudent() {
    var records = [
        { id: 14, name: "Kyle", grade: 86 },
        { id: 73, name: "Suzy", grade: 87 },
        { id: 112, name: "Frank", grade: 75 },
        { id: 6, name: "Sarah", grade: 91 }
    ];

    var publicAPI = {
        getName
    };

    return publicAPI;

    // ************************

    function getName(studentID) {
        var student = records.find(
            student => student.id == studentID
        );
        return student.name;
    }
}

var fullTime = defineStudent();
fullTime.getName(73);            // Suzy
```

به جای مشخص کردن `defineStudent()` به عنوان IIFE، آن را به عنوان تابع مستقل عادی تعریف می‌کنیم، که معمولاً در این زمینه «تابع کارخانه ماژول» نامیده می‌شود.

سپس کارخانه ماژول را فراخوانی می‌کنیم و نمونه‌ای از ماژول تولید می‌کنیم که `fullTime` نام می‌بریم. این نمونه ماژول نمونه جدیدی از scope درونی را دلالت می‌کند، و بنابراین closure جدیدی که `getName(..)` روی `records` نگه می‌دارد. `fullTime.getName(..)` اکنون متد را روی آن نمونه خاص فراخوانی می‌کند.

#### تعریف ماژول کلاسیک

پس برای روشن کردن آنچه چیزی را ماژول کلاسیک می‌کند:

* باید scope بیرونی وجود داشته باشد، معمولاً از تابع کارخانه ماژول که حداقل یک بار اجرا می‌شود.

* scope درونی ماژول باید حداقل یک قطعه اطلاعات پنهان داشته باشد که حالت ماژول را نشان می‌دهد.

* ماژول باید روی API عمومی‌اش ارجاعی به حداقل یک تابع برگرداند که closure روی حالت پنهان ماژول دارد (تا این حالت واقعاً حفظ شود).

احتمالاً با گونه‌های دیگر این رویکرد ماژول کلاسیک برخورد می‌کنید که با جزئیات بیشتر در پیوست الف بررسی می‌کنیم.
