# ماژول‌های Node CommonJS

در فصل ۴، فرمت ماژول CommonJS استفاده‌شده توسط Node را معرفی کردیم. برخلاف فرمت ماژول کلاسیک توضیح‌داده‌شده قبلی، که می‌توانستید کارخانه ماژول یا IIFE را همراه با هر کد دیگری از جمله ماژول‌های دیگر بسته‌بندی کنید، ماژول‌های CommonJS مبتنی بر فایل هستند؛ یک ماژول در هر فایل.

بیایید مثال ماژولمان را برای پایبندی به آن فرمت تغییر دهیم:

```js
module.exports.getName = getName;

// ************************

var records = [
    { id: 14, name: "Kyle", grade: 86 },
    { id: 73, name: "Suzy", grade: 87 },
    { id: 112, name: "Frank", grade: 75 },
    { id: 6, name: "Sarah", grade: 91 }
];

function getName(studentID) {
    var student = records.find(
        student => student.id == studentID
    );
    return student.name;
}
```

شناسه‌های `records` و `getName` در scope سطح بالای این ماژول هستند، اما آن scope سراسری نیست (همان‌طور که در فصل ۴ توضیح داده شد). به همین دلیل، همه چیز اینجا *به طور پیش‌فرض* برای ماژول خصوصی است.

برای در معرض قرار دادن چیزی روی API عمومی ماژول CommonJS، ویژگی به object خالی ارائه‌شده به عنوان `module.exports` اضافه می‌کنید. در برخی کدهای legacy قدیمی‌تر، ممکن است به `exports` لخت برخورد کنید، اما برای وضوح کد همیشه آن ارجاع را با پیشوند `module.` به طور کامل مشخص کنید.

برای اهداف سبکی، دوست دارم «export»هایم را در بالا و پیاده‌سازی ماژول را در پایین بگذارم. اما این exportها می‌توانند هر کجا قرار گیرند. قویاً توصیه می‌کنم همه را با هم جمع کنید، یا در بالا یا پایین فایل.

برخی توسعه‌دهندگان عادت جایگزینی object export پیش‌فرض را دارند، مثل این:

```js
// defining a new object for the API
module.exports = {
    // ..exports..
};
```

چند quirk با این رویکرد هست، از جمله رفتار غیرمنتظره اگر چند ماژول از این نوع به طور دایره‌ای به هم وابسته باشند. به همین دلیل، توصیه می‌کنم object را جایگزین نکنید. اگر می‌خواهید چند export را یکجا انتساب دهید، با تعریف سبک object literal می‌توانید این کار را بکنید:

```js
Object.assign(module.exports,{
   // .. exports ..
});
```

آنچه اینجا اتفاق می‌افتد تعریف object literal `{ .. }` با API عمومی ماژول مشخص‌شده است، و سپس `Object.assign(..)` کپی سطحی همه آن ویژگی‌ها را روی object موجود `module.exports` انجام می‌دهد، به جای جایگزینی آن. این تعادل خوبی از راحتی و رفتار امن‌تر ماژول است.

برای گنجاندن نمونه ماژول دیگری در ماژول/برنامه‌تان، از متد `require(..)` Node استفاده کنید. با فرض اینکه این ماژول در «/path/to/student.js» قرار دارد، این‌طور می‌توانیم به آن دسترسی پیدا کنیم:

```js
var Student = require("/path/to/student.js");

Student.getName(73);
// Suzy
```

`Student` اکنون به API عمومی مثال ماژول ما ارجاع می‌دهد.

ماژول‌های CommonJS به عنوان نمونه‌های singleton رفتار می‌کنند، مشابه سبک تعریف ماژول IIFE ارائه‌شده قبل. مهم نیست چند بار همان ماژول را `require(..)` کنید، فقط ارجاع‌های اضافی به نمونه ماژول مشترک واحد می‌گیرید.

`require(..)` مکانیزم همه-یا-هیچ است؛ ارجاع کل API عمومی در معرض ماژول را شامل می‌کند. برای دسترسی مؤثر فقط به بخشی از API، رویکرد معمول این است:

```js
var getName = require("/path/to/student.js").getName;

// or alternately:

var { getName } = require("/path/to/student.js");
```

مشابه فرمت ماژول کلاسیک، متدهای export شده عمومی API ماژول CommonJS closure روی جزئیات داخلی ماژول نگه می‌دارند. این‌طور حالت singleton ماژول در طول عمر برنامه حفظ می‌شود.

| نکته: |
| :--- |
| در statementهای Node `require("student")`، مسیرهای غیرمطلق (`"student"`) پسوند فایل «.js» را فرض می‌کنند و «node_modules» را جستجو می‌کنند. |
