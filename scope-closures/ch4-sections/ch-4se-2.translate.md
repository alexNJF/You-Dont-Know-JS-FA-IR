# Scope سراسری دقیقاً کجاست؟

ممکن است واضح به نظر برسد که scope سراسری در بیرونی‌ترین بخش یک فایل قرار دارد؛ یعنی داخل هیچ تابع یا بلوک دیگری نیست. اما به آن سادگی نیست.

محیط‌های مختلف جاوااسکریپت scopeهای برنامه‌های شما، به‌خصوص scope سراسری، را متفاوت مدیریت می‌کنند. برای توسعه‌دهندگان جاوااسکریپت کاملاً رایج است که تصورات غلط داشته باشند بدون اینکه حتی متوجه شوند.

### «Window» مرورگر

با respect به برخورد با scope سراسری، *خالص*‌ترین محیطی که جاوااسکریپت می‌تواند در آن اجرا شود به‌عنوان فایل .js مستقل بارگذاری‌شده در محیط صفحهٔ وب در مرورگر است. منظورم «خالص» به معنای چیزی که خودکار اضافه نشود نیست—چیزهای زیادی ممکن است اضافه شوند!—بلکه از نظر حداقل دخالت در کد یا تداخل با رفتار scope سراسری مورد انتظارش.

این فایل .js را در نظر بگیرید:

```js
var studentName = "Kyle";

function hello() {
    console.log(`Hello, ${ studentName }!`);
}

hello();
// Hello, Kyle!
```

این کد ممکن است در محیط صفحهٔ وب با تگ `<script>` inline، تگ اسکریپت `<script src=..>` در markup، یا حتی المان DOM `<script>` ایجادشدهٔ پویا بارگذاری شود. در هر سه مورد، شناسه‌های `studentName` و `hello` در scope سراسری اعلان می‌شوند.

یعنی اگر به global object (معمولاً `window` در مرورگر) دسترسی یابید، propertyهای همان نام‌ها را آنجا پیدا می‌کنید:

```js
var studentName = "Kyle";

function hello() {
    console.log(`Hello, ${ window.studentName }!`);
}

window.hello();
// Hello, Kyle!
```

این رفتار پیش‌فرضی است که از خواندن مشخصات جاوااسکریپت انتظار می‌رود: scope بیرونی *همان* scope سراسری است و `studentName` به‌طور قانونی به‌عنوان متغیر سراسری ایجاد می‌شود.

منظورم از *خالص* این است. اما متأسفانه، این همیشه برای تمام محیط‌های جاوااسکریپتی که با آن‌ها برخورد می‌کنید درست نخواهد بود، و اغلب برای توسعه‌دهندگان جاوااسکریپت تعجب‌آور است.

#### Globals سایه‌اندازی Globals

بحث shadowing (و global unshadowing) از فصل ۳ را به یاد آورید، جایی که یک اعلان متغیر می‌تواند اعلان با همان نام از scope بیرونی را override و از دسترسی جلوگیری کند.

نتیجهٔ غیرمعمول تفاوت بین متغیر سراسری و property سراسری با همان نام این است که، در خود scope سراسری، یک property global object می‌تواند توسط متغیر سراسری سایه انداخته شود:

```js
window.something = 42;

let something = "Kyle";

console.log(something);
// Kyle

console.log(window.something);
// 42
```

اعلان `let` متغیر سراسری `something` را اضافه می‌کند اما property global object نه (فصل ۳ را ببینید). تأثیر آنگاه این است که شناسهٔ لغوی `something` property global object `something` را سایه می‌اندازد.

تقریباً قطعاً ایدهٔ بدی است که واگرایی بین global object و scope سراسری ایجاد کنید. خوانندگان کدتان تقریباً قطعاً گیر خواهند کرد.

راه ساده برای اجتناب از این دام با اعلان‌های سراسری: همیشه برای globals از `var` استفاده کنید. `let` و `const` را برای scopeهای بلوک رزرو کنید («Scoping with Blocks» در فصل ۶ را ببینید).

#### DOM Globals

ادعا کردم که محیط جاوااسکریپت میزبان مرورگر خالص‌ترین رفتار scope سراسری را دارد که خواهیم دید. با این حال، کاملاً *خالص* نیست.

یک رفتار تعجب‌آور در scope سراسری که ممکن است با برنامه‌های جاوااسکریپت مبتنی بر مرورگر برخورد کنید: المان DOM با attribute `id` به‌طور خودکار متغیر سراسری ایجاد می‌کند که به آن ارجاع می‌دهد.

این markup را در نظر بگیرید:

```text
<ul id="my-todo-list">
   <li id="first">Write a book</li>
   ..
</ul>
```

و جاوااسکریپت آن صفحه می‌تواند شامل باشد:

```js
first;
// <li id="first">..</li>

window["my-todo-list"];
// <ul id="my-todo-list">..</ul>
```

اگر مقدار `id` یک نام لغوی معتبر باشد (مثل `first`)، متغیر لغوی ایجاد می‌شود. اگر نه، تنها راه دسترسی به آن سراسری از طریق global object (`window[..]`) است.

ثبت خودکار تمام المان‌های DOM دارای `id` به‌عنوان متغیرهای سراسری رفتار legacy قدیمی مرورگر است که با این حال باید باقی بماند چون سایت‌های قدیمی زیادی هنوز به آن تکیه می‌کنند. توصیهٔ من این است هرگز از این متغیرهای سراسری استفاده نکنید، حتی اگر همیشه به‌طور بی‌صدا ایجاد شوند.

#### چه چیزی در یک نام (Window) است؟

عجیب‌بودن دیگر scope سراسری در جاوااسکریپت مبتنی بر مرورگر:

```js
var name = 42;

console.log(name, typeof name);
// "42" string
```

`window.name` یک «سراسری» از پیش تعریف‌شده در زمینهٔ مرورگر است؛ یک property روی global object است، پس به نظر مثل متغیر سراسری عادی می‌رسد (اما هر چیزی هست جز «عادی»).

از `var` برای اعلانمان استفاده کردیم، که property سراسری از پیش تعریف‌شدهٔ `name` را **سایه نمی‌اندازد**. یعنی، به‌طور مؤثر، اعلان `var` نادیده گرفته می‌شود، چون از قبل property شیء scope سراسری با آن نام وجود دارد. همانطور که قبلاً بحث کردیم، اگر `let name` استفاده کرده بودیم، `window.name` را با متغیر سراسری جداگانهٔ `name` سایه می‌انداختیم.

اما رفتار واقعاً تعجب‌آور این است که حتی با انتساب عدد `42` به `name` (و بنابراین `window.name`)، وقتی مقدارش را بازیابی می‌کنیم، رشتهٔ `"42"` است! در این مورد، عجیب بودن به این دلیل است که `name` در واقع یک getter/setter از پیش تعریف‌شده روی شیء `window` است، که اصرار دارد مقدارش رشته باشد. وای!

با استثنای برخی موارد نادر گوشه مثل ID المان‌های DOM و `window.name`، جاوااسکریپت در حال اجرا به‌عنوان فایل مستقل در صفحهٔ مرورگر برخی از خالص‌ترین رفتارهای scope سراسری را دارد که با آن برخورد خواهیم کرد.

### Web Workers

Web Workers یک افزونهٔ پلتفرم وب روی رفتار مرورگر-جاوااسکریپت است، که اجازه می‌دهد یک فایل جاوااسکریپت در thread کاملاً جداگانه (از نظر سیستم عامل) از threadی که برنامهٔ اصلی جاوااسکریپت را اجرا می‌کند اجرا شود.

چون این برنامه‌های Web Worker روی thread جداگانه اجرا می‌شوند، در ارتباط با thread اصلی برنامه محدود هستند، برای اجتناب/محدود کردن race conditionها و پیچیدگی‌های دیگر. کد Web Worker به DOM دسترسی ندارد، مثلاً. با این حال، برخی APIهای وب برای worker در دسترس هستند، مثل `navigator`.

چون Web Worker به‌عنوان برنامهٔ کاملاً جداگانه تلقی می‌شود، scope سراسری را با برنامهٔ اصلی جاوااسکریپت به اشتراک نمی‌گذارد. با این حال، موتور جاوااسکریپت مرورگر هنوز کد را اجرا می‌کند، پس می‌توانیم *خلوص* مشابهی از رفتار scope سراسری آن انتظار داشته باشیم. چون دسترسی DOM وجود ندارد، alias `window` برای scope سراسری وجود ندارد.

در Web Worker، مرجع global object معمولاً با `self` انجام می‌شود:

```js
var studentName = "Kyle";
let studentID = 42;

function hello() {
    console.log(`Hello, ${ self.studentName }!`);
}

self.hello();
// Hello, Kyle!

self.studentID;
// undefined
```

دقیقاً مثل برنامه‌های اصلی جاوااسکریپت، اعلان‌های `var` و `function` propertyهای آینه‌ای روی global object (یعنی `self`) ایجاد می‌کنند، جایی که اعلان‌های دیگر (`let` و غیره) نمی‌کنند.

پس باز هم، رفتار scope سراسری که اینجا می‌بینیم تقریباً به *خالص*‌ترین شکل برای اجرای برنامه‌های جاوااسکریپت است؛ شاید حتی *خالص*‌تر چون DOMی برای خراب کردن چیزها نیست!

### Developer Tools Console/REPL

از فصل ۱ در *شروع کنید* به یاد آورید که Developer Tools محیط جاوااسکریپت کاملاً adherent ایجاد نمی‌کنند. آن‌ها کد جاوااسکریپت را پردازش می‌کنند، اما همچنین به نفع تعامل UX که برای توسعه‌دهندگان دوستانه‌تر است (یعنی developer experience یا DX) تمایل دارند.

در برخی موارد، ترجیح DX هنگام تایپ قطعه‌کدهای کوتاه جاوااسکریپت، بر مراحل strict عادی مورد انتظار برای پردازش یک برنامهٔ کامل جاوااسکریپت، تفاوت‌های قابل مشاهده در رفتار کد بین برنامه‌ها و ابزارها تولید می‌کند. مثلاً، شرایط خطای خاصی که برای برنامهٔ جاوااسکریپت اعمال می‌شوند ممکن است هنگام وارد کردن کد در ابزار توسعه‌دهنده راحت‌تر و نمایش داده نشوند.

با respect به بحث‌های ما اینجا دربارهٔ scope، چنین تفاوت‌های قابل مشاهده در رفتار ممکن است شامل باشد:

* رفتار scope سراسری

* Hoisting (فصل ۵ را ببینید)

* declaratorهای block-scoping (`let` / `const`، فصل ۶ را ببینید) هنگام استفاده در scope بیرونی‌ترین

اگرچه ممکن است هنگام استفاده از console/REPL به نظر برسد که عبارت‌های واردشده در scope بیرونی‌ترین در scope سراسری واقعی پردازش می‌شوند، این کاملاً دقیق نیست. چنین ابزارهایی معمولاً موقعیت scope سراسری را تا حدی emulate می‌کنند؛ emulate است، نه adherence دقیق. این محیط‌های ابزار راحتی توسعه‌دهنده را اولویت می‌دهند، یعنی گاهی (مثل بحث‌های فعلی ما دربارهٔ scope) رفتار مشاهده‌شده ممکن است از مشخصات جاوااسکریپت منحرف شود.

نتیجه این است که Developer Tools، در حالی که برای انواع فعالیت‌های توسعه‌دهنده به راحتی و مفید بودن بهینه شده‌اند، **مناسب** محیط‌هایی برای تعیین یا تأیید رفتارهای صریح و ظریف یک زمینهٔ برنامهٔ جاوااسکریپت واقعی نیستند.

### ES Modules (ESM)

ES6 پشتیبانی درجهٔ اول برای الگوی ماژول معرفی کرد (فصل ۸ پوشش داده می‌شود). یکی از آشکارترین تأثیرات استفاده از ESM نحوهٔ تغییر رفتار scope سطح بالأ قابل مشاهده در یک فایل است.

این قطعهٔ کد را از قبل به یاد آورید (که با استفاده از کلمهٔ کلیدی `export` به فرمت ESM تنظیم می‌کنیم):

```js
var studentName = "Kyle";

function hello() {
    console.log(`Hello, ${ studentName }!`);
}

hello();
// Hello, Kyle!

export hello;
```

اگر آن کد در فایلی باشد که به‌عنوان ES module بارگذاری می‌شود، هنوز دقیقاً همان اجرا می‌شود. با این حال، تأثیرات قابل مشاهده، از نظر کلی برنامه، متفاوت خواهند بود.

علیرغم اعلان در سطح بالأ فایل (ماژول)، در scope آشکار بیرونی‌ترین، `studentName` و `hello` متغیرهای سراسری نیستند. در عوض، در سراسر ماژول هستند، یا اگر ترجیح می‌دهید، «module-global».

با این حال، در یک ماژول «شیء scope در سراسر ماژول» ضمنی برای اضافه شدن این اعلان‌های سطح بالا به‌عنوان property وجود ندارد، همانطور که وقتی اعلان‌ها در سطح بالای فایل‌های جاوااسکریپت غیرماژول ظاهر می‌شوند وجود دارد. این نیست که متغیرهای سراسری نمی‌توانند در چنین برنامه‌هایی وجود داشته یا دسترسی یابند. فقط این است که متغیرهای سراسری با اعلان متغیرها در scope سطح بالای ماژول *ایجاد* نمی‌شوند.

scope سطح بالای ماژول از scope سراسری نزول می‌کند، تقریباً انگار کل محتوای ماژول در یک تابع قرار گرفته باشد. بنابراین، تمام متغیرهایی که در scope سراسری وجود دارند (چه روی global object باشند چه نه!) به‌عنوان شناسه‌های لغوی از داخل scope ماژول در دسترس هستند.

ESM تشویق به حداقل کردن تکیه بر scope سراسری می‌کند، جایی که هر ماژولی که برای کار ماژول فعلی نیاز دارید import می‌کنید. به همین ترتیب، کمتر استفاده از scope سراسری یا global object آن را می‌بینید.

با این حال، همانطور که قبلاً ذکر شد، هنوز globals جاوااسکریپت و وب زیادی وجود دارند که به‌طور مداوم از scope سراسری دسترسی خواهید یافت، چه متوجه شوید چه نه!

### Node

یک جنبهٔ Node که اغلب توسعه‌دهندگان جاوااسکریپت را غافلگیر می‌کند این است که Node هر فایل .js واحدی که بارگذاری می‌کند، از جمله اصلی که فرآیند Node را با آن شروع می‌کنید، به‌عنوان *ماژول* (ES module یا CommonJS module، فصل ۸ را ببینید) تلقی می‌کند. تأثیر عملی این است که سطح بالای برنامه‌های Node شما **هرگز در واقع scope سراسری نیست**، همانطور که هنگام بارگذاری فایل غیرماژول در مرورگر است.

از زمان نگارش این متن، Node اخیراً پشتیبانی از ES modules را اضافه کرده. اما علاوه بر آن، Node از ابتدا فرمت ماژولی به نام «CommonJS» را پشتیبانی کرده، که اینطور به نظر می‌رسد:

```js
var studentName = "Kyle";

function hello() {
    console.log(`Hello, ${ studentName }!`);
}

hello();
// Hello, Kyle!

module.exports.hello = hello;
```

قبل از پردازش، Node اساساً چنین کدی را در یک تابع قرار می‌دهد، تا اعلان‌های `var` و `function` در scope آن تابع wrapper قرار گیرند، **نه** به‌عنوان متغیرهای سراسری تلقی شوند.

کد قبلی را اینطور تصور کنید که Node می‌بیند (توضیحی، نه واقعی):

```js
function Module(module,require,__dirname,...) {
    var studentName = "Kyle";

    function hello() {
        console.log(`Hello, ${ studentName }!`);
    }

    hello();
    // Hello, Kyle!

    module.exports.hello = hello;
}
```

Node سپس اساساً تابع اضافه‌شدهٔ `Module(..)` را برای اجرای ماژول شما فراخوانی می‌کند. می‌توانید به‌وضوح اینجا ببینید چرا شناسه‌های `studentName` و `hello` سراسری نیستند، بلکه در scope ماژول اعلان شده‌اند.

همانطور که قبلاً ذکر شد، Node چند «global» مثل `require()` تعریف می‌کند، اما آن‌ها در واقع شناسه در scope سراسری نیستند (و نه propertyهای global object). آن‌ها در scope هر ماژول inject می‌شوند، اساساً کمی مثل پارامترهای لیست‌شده در اعلان تابع `Module(..)`.

پس چطور متغیرهای سراسری واقعی را در Node تعریف می‌کنید؟ تنها راه این است که property به یکی دیگر از «globals»های خودکار ارائه‌شدهٔ Node اضافه کنید، که به طعنه `global` نامیده می‌شود. `global` مرجعی به شیء scope سراسری واقعی است، کمی مثل استفاده از `window` در محیط جاوااسکریپت مرورگر.

در نظر بگیرید:

```js
global.studentName = "Kyle";

function hello() {
    console.log(`Hello, ${ studentName }!`);
}

hello();
// Hello, Kyle!

module.exports.hello = hello;
```

اینجا `studentName` را به‌عنوان property روی شیء `global` اضافه می‌کنیم، و سپس در عبارت `console.log(..)` می‌توانیم به `studentName` به‌عنوان متغیر سراسری عادی دسترسی یابیم.

به یاد داشته باشید، شناسهٔ `global` توسط جاوااسکریپت تعریف نشده؛ به‌طور خاص توسط Node تعریف شده است.
