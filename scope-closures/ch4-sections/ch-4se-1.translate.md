# چرا Scope سراسری؟

احتمالاً برای خوانندگان تعجب‌آور نیست که اکثر برنامه‌ها از چند (گاهی خیلی!) فایل جاوااسکریپت جداگانه تشکیل شده‌اند. پس دقیقاً چطور تمام آن فایل‌های جدا با هم در یک زمینهٔ runtime واحد توسط موتور جاوااسکریپت دوخته می‌شوند؟

با respect به برنامه‌های اجراشده در مرورگر، سه راه اصلی وجود دارد.

اول، اگر مستقیماً از ES modules استفاده می‌کنید (بدون transpile به فرمت ماژول-بستهٔ دیگری)، این فایل‌ها به‌صورت جداگانه توسط محیط جاوااسکریپت بارگذاری می‌شوند. هر ماژول سپس `import` مرجع به هر ماژول دیگری که نیاز به دسترسی دارد می‌کند. فایل‌های ماژول جدا منحصراً از طریق این importهای مشترک با هم همکاری می‌کنند، بدون نیاز به هیچ scope بیرونی مشترکی.

دوم، اگر در فرآیند build از bundler استفاده می‌کنید، تمام فایل‌ها معمولاً قبل از تحویل به مرورگر و موتور جاوااسکریپت به هم الحاق می‌شوند، که سپس فقط یک فایل بزرگ پردازش می‌کند. حتی با قرارگیری تمام قطعات برنامه در یک فایل واحد، مکانیزمی لازم است تا هر قطعه یک *نام* برای ارجاع توسط قطعات دیگر ثبت کند، و همچنین امکانی برای وقوع آن دسترسی.

در برخی تنظیمات build، کل محتوای فایل در یک scope محصورکنندهٔ واحد، مثل تابع wrapper، ماژول جهانی (UMD—پیوست الف را ببینید)، و غیره قرار می‌گیرد. هر قطعه می‌تواند خود را از طریق متغیرهای محلی در آن scope مشترک برای دسترسی از قطعات دیگر ثبت کند. مثلاً:

```js
(function wrappingOuterScope(){
    var moduleOne = (function one(){
        // ..
    })();

    var moduleTwo = (function two(){
        // ..

        function callModuleOne() {
            moduleOne.someMethod();
        }

        // ..
    })();
})();
```

همانطور که نشان داده شد، متغیرهای محلی `moduleOne` و `moduleTwo` داخل scope تابع `wrappingOuterScope()` اعلان شده‌اند تا این ماژول‌ها بتوانند برای همکاری به یکدیگر دسترسی یابند.

در حالی که scope `wrappingOuterScope()` یک تابع است و scope سراسری کامل محیط نیست، به نوعی عمل می‌کند مثل «scope در سراسر برنامه»، سطلی که تمام شناسه‌های سطح بالا می‌توانند در آن ذخیره شوند، اگرچه در scope سراسری واقعی نیست. به نوعی جایگزین scope سراسری در آن respect است.

و در نهایت، راه سوم: چه از ابزار bundler برای برنامه استفاده شود، چه فایل‌های (غیر ES module) به‌سادگی در مرورگر جداگانه بارگذاری شوند (از طریق تگ‌های `<script>` یا بارگذاری پویای منبع جاوااسکریپت دیگر)، اگر هیچ scope محصورکنندهٔ واحدی که تمام این قطعات را در بر بگیرد نباشد، **scope سراسری** تنها راه همکاری آن‌ها با یکدیگر است:

فایل بسته‌شدهٔ این نوع اغلب شبیه این است:

```js
var moduleOne = (function one(){
    // ..
})();
var moduleTwo = (function two(){
    // ..

    function callModuleOne() {
        moduleOne.someMethod();
    }

    // ..
})();
```

اینجا، چون scope تابع محصورکننده‌ای وجود ندارد، این اعلان‌های `moduleOne` و `moduleTwo` به‌سادگی در scope سراسری قرار می‌گیرند. این به‌طور مؤثر همان است که اگر فایل‌ها الحاق نشده بودند، بلکه جداگانه بارگذاری می‌شدند:

module1.js:

```js
var moduleOne = (function one(){
    // ..
})();
```

module2.js:

```js
var moduleTwo = (function two(){
    // ..

    function callModuleOne() {
        moduleOne.someMethod();
    }

    // ..
})();
```

اگر این فایل‌ها به‌صورت جداگانه به‌عنوان فایل‌های .js مستقل عادی در محیط مرورگر بارگذاری شوند، هر اعلان متغیر سطح بالا به متغیر سراسری ختم می‌شود، چون scope سراسری تنها منبع مشترک بین این دو فایل جدا است—از نظر موتور جاوااسکریپت برنامه‌های مستقل هستند.

علاوه بر (احتمالاً) محاسبهٔ محل قرارگیری کد برنامه در حین runtime، و نحوهٔ دسترسی هر قطعه به قطعات دیگر برای همکاری، scope سراسری همچنین جایی است که:

* جاوااسکریپت built-inهایش را در معرض قرار می‌دهد:

    - primitives: `undefined`, `null`, `Infinity`, `NaN`
    - natives: `Date()`, `Object()`, `String()`, و غیره
    - توابع سراسری: `eval()`, `parseInt()`, و غیره
    - namespaceها: `Math`, `Atomics`, `JSON`
    - دوستان جاوااسکریپت: `Intl`, `WebAssembly`

* محیط میزبان موتور جاوااسکریپت built-inهای خودش را در معرض قرار می‌دهد:

    - `console` (و متدهایش)
    - DOM (`window`, `document`, و غیره)
    - تایمرها (`setTimeout(..)`, و غیره)
    - APIهای پلتفرم وب: `navigator`, `history`, geolocation, WebRTC, و غیره

این‌ها فقط برخی از *globals*های زیادی هستند که برنامه‌های شما با آن‌ها تعامل خواهند داشت.

| NOTE: |
| :--- |
| Node همچنین چند عنصر را «به‌صورت سراسری» در معرض قرار می‌دهد، اما از نظر فنی در scope `global` نیستند: `require()`, `__dirname`, `module`, `URL`, و غیره. |

اکثر توسعه‌دهندگان موافقند که scope سراسری نباید فقط محل تخلیهٔ هر متغیر در برنامهٔ شما باشد. این آشفتگی باگ‌هایی است که منتظر وقوع هستند. اما همچنین غیرقابل انکار است که scope سراسری *چسب* مهمی برای عملاً هر برنامهٔ جاوااسکریپت است.
