# Scopeبندی با بلوک‌ها

تا این نقطه باید با مزایای ایجاد scopeها برای محدود کردن مواجهه شناسه راحت باشید.

تا اینجا، این کار را از طریق scope `function` (یعنی IIFE) بررسی کردیم. اما حالا استفاده از اعلان‌های `let` با بلوک‌های تو در تو را در نظر بگیریم. به طور کلی، هر جفت آکولاد `{ .. }` که یک statement است به عنوان بلوک عمل می‌کند، اما **نه لزوماً** به عنوان scope.

یک بلوک فقط در صورت نیاز scope می‌شود، برای نگه داشتن اعلان‌های block-scoped (یعنی `let` یا `const`). در نظر بگیرید:

```js
{
    // not necessarily a scope (yet)

    // ..

    // now we know the block needs to be a scope
    let thisIsNowAScope = true;

    for (let i = 0; i < 5; i++) {
        // this is also a scope, activated each
        // iteration
        if (i % 2 == 0) {
            // this is just a block, not a scope
            console.log(i);
        }
    }
}
// 0 2 4
```

همه جفت‌های آکولاد `{ .. }` بلوک (و در نتیجه واجد تبدیل شدن به scope) ایجاد نمی‌کنند:

* Object literalها از جفت‌های آکولاد `{ .. }` برای محدود کردن لیست‌های کلید-مقدارشان استفاده می‌کنند، اما چنین مقادیر object **scope** نیستند.

* `class` از آکولادهای `{ .. }` دور تعریف بدنه‌اش استفاده می‌کند، اما این بلوک یا scope نیست.

* یک `function` از `{ .. }` دور بدنه‌اش استفاده می‌کند، اما این از نظر فنی بلوک نیست—یک statement واحد برای بدنه تابع است. با این حال، یک scope (تابع) *است*.

* جفت آکولاد `{ .. }` روی statement `switch` (دور مجموعه بندهای `case`) بلوک/scope تعریف نمی‌کند.

غیر از چنین مثال‌های غیربلوکی، یک جفت آکولاد `{ .. }` می‌تواند بلوکی متصل به یک statement (مثل `if` یا `for`) تعریف کند، یا به تنهایی بایستد—جفت آکولاد بیرونی `{ .. }` در قطعه قبلی را ببینید. یک بلوک صریح از این نوع—اگر اعلانی نداشته باشد، در واقع scope نیست—هیچ هدف عملیاتی ندارد، هرچند هنوز می‌تواند به عنوان سیگنال معنایی مفید باشد.

بلوک‌های صریح مستقل `{ .. }` همیشه نحو معتبر JS بوده‌اند، اما چون قبل از `let`/`const` ES6 نمی‌توانستند scope باشند، بسیار نادرند. با این حال، پس از ES6، کم‌کم رواج پیدا می‌کنند.

در بیشتر زبان‌هایی که block scoping را پشتیبانی می‌کنند، یک block scope صریح الگوی بسیار رایجی برای ایجاد برشی باریک از scope برای یک یا چند متغیر است. پس در پیروی از اصل POLE، باید این الگو را در JS هم گسترده‌تر بپذیریم؛ از block scoping (صریح) برای باریک کردن مواجهه شناسه‌ها به حداقل عملی استفاده کنید.

یک block scope صریح حتی داخل بلوک دیگری (چه بلوک بیرونی scope باشد یا نه) می‌تواند مفید باشد.

مثلاً:

```js
if (somethingHappened) {
    // this is a block, but not a scope

    {
        // this is both a block and an
        // explicit scope
        let msg = somethingHappened.message();
        notifyOthers(msg);
    }

    // ..

    recoverFromSomething();
}
```

اینجا، جفت آکولاد `{ .. }` **داخل** statement `if` یک block scope صریح درونی حتی کوچک‌تر برای `msg` است، چون آن متغیر برای کل بلوک `if` لازم نیست. بیشتر توسعه‌دهندگان فقط `msg` را به بلوک `if` block-scope می‌کنند و ادامه می‌دهند. و منصفانه بگویم، وقتی فقط چند خط در نظر است، قضاوت سخت است. اما با رشد کد، این مسائل مواجهه بیش از حد برجسته‌تر می‌شوند.

پس آیا اضافه کردن جفت `{ .. }` و سطح تورفتگی اضافی به اندازه کافی مهم است؟ فکر می‌کنم باید POLE را دنبال کنید و همیشه (در حد معقول!) کوچک‌ترین بلوک را برای هر متغیر تعریف کنید. پس استفاده از block scope صریح اضافی را همان‌طور که نشان داده شد توصیه می‌کنم.

بحث خطاهای TDZ را از «متغیرهای مقداردهی‌نشده (TDZ)» (فصل ۵) به یاد بیاورید. پیشنهاد من آنجا این بود: برای به حداقل رساندن خطر خطاهای TDZ با اعلان‌های `let`/`const`، همیشه آن اعلان‌ها را در بالای scopeشان قرار دهید.

اگر خودتان را در حال قرار دادن اعلان `let` در وسط یک scope یافتید، اول فکر کنید «اوه نه! هشدار TDZ!» اگر این اعلان `let` در نیمه اول آن بلوک لازم نیست، باید از block scope صریح درونی برای باریک‌تر کردن مواجهه آن استفاده کنید!

مثال دیگر با block scope صریح:

```js
function getNextMonthStart(dateStr) {
    var nextMonth, year;

    {
        let curMonth;
        [ , year, curMonth ] = dateStr.match(
                /(\d{4})-(\d{2})-\d{2}/
            ) || [];
        nextMonth = (Number(curMonth) % 12) + 1;
    }

    if (nextMonth == 1) {
        year++;
    }

    return `${ year }-${
            String(nextMonth).padStart(2,"0")
        }-01`;
}
getNextMonthStart("2019-12-25");   // 2020-01-01
```

اول scopeها و شناسه‌هایشان را مشخص کنیم:

۱. scope بیرونی/سراسری یک شناسه دارد، تابع `getNextMonthStart(..)`.

۲. scope تابع برای `getNextMonthStart(..)` سه تا دارد: `dateStr` (پارامتر)، `nextMonth` و `year`.

۳. جفت آکولاد `{ .. }` یک block scope درونی تعریف می‌کند که یک متغیر را شامل می‌شود: `curMonth`.

پس چرا `curMonth` را در block scope صریح قرار دهیم به جای کنار `nextMonth` و `year` در scope سطح بالای تابع؟ چون `curMonth` فقط برای آن دو statement اول لازم است؛ در سطح scope تابع مواجهه بیش از حد دارد.

این مثال کوچک است، پس خطرات مواجهه بیش از حد `curMonth` نسبتاً محدود است. اما مزایای اصل POLE وقتی بهتر حاصل می‌شوند که عادت به حداقل رساندن مواجهه scope به‌طور پیش‌فرض را به عنوان عادت بپذیرید. اگر اصل را حتی در موارد کوچک به‌طور مداوم دنبال کنید، با رشد برنامه‌هایتان بیشتر به شما خدمت می‌کند.

حالا به مثالی حتی قابل‌توجه‌تر نگاه کنیم:

```js
function sortNamesByLength(names) {
    var buckets = [];

    for (let firstName of names) {
        if (buckets[firstName.length] == null) {
            buckets[firstName.length] = [];
        }
        buckets[firstName.length].push(firstName);
    }

    // a block to narrow the scope
    {
        let sortedNames = [];

        for (let bucket of buckets) {
            if (bucket) {
                // sort each bucket alphanumerically
                bucket.sort();

                // append the sorted names to our
                // running list
                sortedNames = [
                    ...sortedNames,
                    ...bucket
                ];
            }
        }

        return sortedNames;
    }
}

sortNamesByLength([
    "Sally",
    "Suzy",
    "Frank",
    "John",
    "Jennifer",
    "Scott"
]);
// [ "John", "Suzy", "Frank", "Sally",
//   "Scott", "Jennifer" ]
```

شش شناسه در پنج scope مختلف اعلان شده‌اند. آیا همه این متغیرها می‌توانستند در scope بیرونی/سراسری واحد وجود داشته باشند؟ از نظر فنی بله، چون همه نام یکتا دارند و در نتیجه برخورد نام ندارند. اما این سازماندهی کد واقعاً ضعیفی می‌بود و احتمالاً به سردرگمی و باگ‌های آینده منجر می‌شد.

آن‌ها را در هر scope تو در تو درونی مناسب تقسیم کردیم. هر متغیر در درونی‌ترین scope ممکن برای عملکرد مطلوب برنامه تعریف شده است.

`sortedNames` می‌توانست در scope سطح بالای تابع تعریف شود، اما فقط برای نیمه دوم این تابع لازم است. برای اجتناب از مواجهه بیش از حد آن متغیر در scope بالاتر، دوباره POLE را دنبال می‌کنیم و آن را در block scope صریح درونی block-scope می‌کنیم.

### `var` *و* `let`

بعدی، درباره اعلان `var buckets` صحبت کنیم. آن متغیر در کل تابع استفاده می‌شود (به جز statement نهایی `return`). هر متغیری که در همه (یا حتی بیشتر) تابع لازم است باید طوری اعلان شود که چنین استفاده‌ای آشکار باشد.

| نکته: |
| :--- |
| پارامتر `names` در کل تابع استفاده نمی‌شود، اما راهی برای محدود کردن scope پارامتر نیست، پس صرف نظر از آن به عنوان اعلان در کل تابع رفتار می‌کند. |

پس چرا از `var` به جای `let` برای اعلان متغیر `buckets` استفاده کردیم؟ دلایل معنایی و فنی برای انتخاب `var` اینجا هست.

از نظر سبکی، `var` همیشه، از اولین روزهای JS، سیگنال «متغیری که به کل تابع تعلق دارد» بوده است. همان‌طور که در «Lexical Scope» (فصل ۱) گفتیم، `var` به نزدیک‌ترین scope تابع احاطه‌کننده متصل می‌شود، هر کجا ظاهر شود. حتی اگر `var` داخل بلوک ظاهر شود درست است:

```js
function diff(x,y) {
    if (x > y) {
        var tmp = x;    // `tmp` is function-scoped
        x = y;
        y = tmp;
    }

    return y - x;
}
```

حتی با اینکه `var` داخل بلوک است، اعلانش function-scoped است (به `diff(..)`)، نه block-scoped.

در حالی که می‌توانید `var` داخل بلوک اعلان کنید (و همچنان function-scoped باشد)، به جز چند مورد خاص (در پیوست الف بحث شده) این رویکرد را توصیه نمی‌کنم. در غیر این صورت، `var` باید برای استفاده در scope سطح بالای تابع رزرو شود.

چرا فقط `let` را در همان مکان استفاده نکنیم؟ چون `var` از نظر بصری با `let` متمایز است و بنابراین به وضوح سیگنال می‌دهد «این متغیر function-scoped است.» استفاده از `let` در scope سطح بالا، به‌ویژه اگر در چند خط اول تابع نباشد، و وقتی همه اعلان‌های دیگر در بلوک‌ها از `let` استفاده می‌کنند، توجه بصری به تفاوت با اعلان function-scoped جلب نمی‌کند.

به عبارت دیگر، احساس می‌کنم `var` بهتر از `let` function-scoped را منتقل می‌کند، و `let` هم block-scoping را منتقل می‌کند (و به آن دست می‌یابد!) جایی که `var` کافی نیست. تا زمانی که برنامه‌هایتان به هر دو متغیر function-scoped و block-scoped نیاز دارند، منطقی‌ترین و خواناترین رویکرد استفاده از هر دو `var` *و* `let` با هم است، هر کدام برای بهترین هدف خودشان.

دلایل معنایی و عملیاتی دیگری برای انتخاب `var` یا `let` در سناریوهای مختلف هست. مورد استفاده `var` *و* `let` را با جزئیات بیشتر در پیوست الف کاوش می‌کنیم.

| هشدار: |
| :--- |
| توصیه من برای استفاده از هر دو `var` *و* `let` به وضوح بحث‌برانگیز است و با اکثریت تناقض دارد. رایج‌تر است که ادعاهایی مثل «var خراب است، let آن را درست می‌کند» و «هرگز از var استفاده نکن، let جایگزین است» بشنوید. آن نظرات معتبرند، اما صرفاً نظرند، درست مثل نظر من. `var` از نظر واقعی خراب یا منسوخ نیست؛ از اوایل JS کار کرده و تا زمانی که JS هست ادامه خواهد داد. |

### کجا `let`؟

توصیه من برای رزرو کردن `var` برای (عمدتاً) فقط scope سطح بالای تابع یعنی بیشتر اعلان‌های دیگر باید از `let` استفاده کنند. اما شاید هنوز تعجب کنید چطور تصمیم بگیرید هر اعلان در برنامه‌تان کجا تعلق دارد؟

POLE از قبل شما را در آن تصمیمات راهنمایی می‌کند، اما بیایید صریحاً بیانش کنیم. نحوه تصمیم‌گیری بر اساس کلمه کلیدی که می‌خواهید استفاده کنید نیست. نحوه تصمیم‌گیری این است که بپرسید «کمترین مواجهه scope که برای این متغیر کافی است چیست؟»

وقتی به آن پاسخ دادید، می‌دانید متغیر به block scope تعلق دارد یا scope تابع. اگر در ابتدا تصمیم گرفتید متغیر باید block-scoped باشد، و بعد متوجه شدید باید به function-scoped ارتقا یابد، آن نه فقط مکان اعلان آن متغیر را تغییر می‌دهد، بلکه کلمه کلیدی اعلان‌کننده استفاده‌شده را هم. فرآیند تصمیم‌گیری واقعاً باید این‌طور پیش برود.

اگر اعلان به block scope تعلق دارد، از `let` استفاده کنید. اگر به scope تابع تعلق دارد، از `var` استفاده کنید (دوباره، فقط نظر من).

اما راه دیگر برای تجسم این تصمیم‌گیری در نظر گرفتن نسخه پیش از ES6 یک برنامه است. مثلاً، `diff(..)` قبلی را به یاد بیاورید:

```js
function diff(x,y) {
    var tmp;

    if (x > y) {
        tmp = x;
        x = y;
        y = tmp;
    }

    return y - x;
}
```

در این نسخه `diff(..)`، `tmp` به وضوح در scope تابع اعلان شده. آیا برای `tmp` مناسب است؟ استدلال می‌کنم نه. `tmp` فقط برای آن چند statement لازم است. برای statement `return` لازم نیست. پس باید block-scoped باشد.

قبل از ES6، `let` نداشتیم پس نمی‌توانستیم *واقعاً* آن را block-scope کنیم. اما می‌توانستیم بهترین کار بعدی را برای سیگنال قصدمان انجام دهیم:

```js
function diff(x,y) {
    if (x > y) {
        // `tmp` is still function-scoped, but
        // the placement here semantically
        // signals block-scoping
        var tmp = x;
        x = y;
        y = tmp;
    }

    return y - x;
}
```

قرار دادن اعلان `var` برای `tmp` داخل statement `if` به خواننده کد سیگنال می‌دهد که `tmp` به آن بلوک تعلق دارد. حتی با اینکه JS آن scopeبندی را اعمال نمی‌کند، سیگنال معنایی هنوز برای خواننده کدتان سودمند است.

با پیروی از این دیدگاه، می‌توانید هر `var` داخل بلوکی از این نوع را پیدا کنید و به `let` تغییر دهید تا سیگنال معنایی که قبلاً فرستاده شده اعمال شود. این استفاده صحیح از `let` به نظر من است.

مثال دیگر که از نظر تاریخی بر `var` بود اما اکنون تقریباً همیشه باید از `let` استفاده کند حلقه `for` است:

```js
for (var i = 0; i < 5; i++) {
    // do something
}
```

هر کجا چنین حلقه‌ای تعریف شود، `i` اساساً همیشه فقط داخل حلقه استفاده می‌شود، که در آن مورد POLE حکم می‌کند با `let` به جای `var` اعلان شود:

```js
for (let i = 0; i < 5; i++) {
    // do something
}
```

تقریباً تنها موردی که عوض کردن `var` به `let` به این شکل کدتان را «خراب» می‌کند اگر به دسترسی به iterator حلقه (`i`) بیرون/بعد از حلقه متکی بودید، مثل:

```js
for (var i = 0; i < 5; i++) {
    if (checkValue(i)) {
        break;
    }
}

if (i < 5) {
    console.log("The loop stopped early!");
}
```

این الگوی استفاده خیلی غیرمعمول نیست، اما بیشتر احساس می‌کنند بوی ساختار کد ضعیف می‌دهد. رویکرد ترجیحی استفاده از متغیر scope بیرونی دیگری برای آن هدف است:

```js
var lastI;

for (let i = 0; i < 5; i++) {
    lastI = i;
    if (checkValue(i)) {
        break;
    }
}

if (lastI < 5) {
    console.log("The loop stopped early!");
}
```

`lastI` در کل این scope لازم است، پس با `var` اعلان می‌شود. `i` فقط در (هر) تکرار حلقه لازم است، پس با `let` اعلان می‌شود.

### Catch چطور؟

تا اینجا گفتیم `var` و پارامترها function-scoped هستند، و `let`/`const` اعلان‌های block-scoped را سیگنال می‌دهند. یک استثنای کوچک برای ذکر هست: بند `catch`.

از معرفی `try..catch` در ES3 (۱۹۹۹)، بند `catch` از قابلیت اعلان block-scoping اضافی (کم‌شناخته) استفاده کرده:

```js
try {
    doesntExist();
}
catch (err) {
    console.log(err);
    // ReferenceError: 'doesntExist' is not defined
    // ^^^^ message printed from the caught exception

    let onlyHere = true;
    var outerVariable = true;
}

console.log(outerVariable);     // true

console.log(err);
// ReferenceError: 'err' is not defined
// ^^^^ this is another thrown (uncaught) exception
```

متغیر `err` اعلان‌شده توسط بند `catch` به آن بلوک block-scoped است. این بند `catch` می‌تواند اعلان‌های block-scoped دیگر را از طریق `let` نگه دارد. اما اعلان `var` داخل این بلوک همچنان به scope تابع/سراسری بیرونی متصل می‌شود.

ES2019 (اخیراً، در زمان نوشتن) بندهای `catch` را طوری تغییر داد که اعلانشان اختیاری است؛ اگر اعلان حذف شود، بلوک `catch` دیگر (به‌طور پیش‌فرض) scope نیست؛ هنوز بلوک است!

پس اگر باید به شرط *وقوع استثنا* واکنش نشان دهید (تا بتوانید به‌طور ظریف بازیابی کنید)، اما به خود مقدار خطا اهمیت نمی‌دهید، می‌توانید اعلان `catch` را حذف کنید:

```js
try {
    doOptionOne();
}
catch {   // catch-declaration omitted
    doOptionTwoInstead();
}
```

این ساده‌سازی کوچک اما دلپذیر نحو برای مورد استفاده نسبتاً رایج است، و ممکن است با حذف scope غیرضروری کمی کارآمدتر هم باشد!
