# اعلان‌های تابع در بلوک‌ها (FiB)

اکنون دیدیم که اعلان‌های با `let` یا `const` block-scoped هستند، و اعلان‌های `var` function-scoped هستند. پس اعلان‌های `function` که مستقیماً داخل بلوک‌ها ظاهر می‌شوند چطور؟ به عنوان یک ویژگی، این «FiB» نامیده می‌شود.

معمولاً اعلان‌های `function` را مثل معادل اعلان `var` در نظر می‌گیریم. پس آیا مثل `var` function-scoped هستند؟

نه و بله. می‌دانم... گیج‌کننده است. بیایید عمیق شویم:

```js
if (false) {
    function ask() {
        console.log("Does this run?");
    }
}
ask();
```

از این برنامه چه انتظاری دارید؟ سه نتیجه معقول:

۱. فراخوانی `ask()` ممکن است با استثنای `ReferenceError` شکست بخورد، چون شناسه `ask` به block scope بلوک `if` محدود است و بنابراین در scope بیرونی/سراسری در دسترس نیست.

۲. فراخوانی `ask()` ممکن است با استثنای `TypeError` شکست بخورد، چون شناسه `ask` وجود دارد، اما `undefined` است (چون statement `if` اجرا نمی‌شود) و بنابراین تابع قابل فراخوانی نیست.

۳. فراخوانی `ask()` ممکن است درست اجرا شود و پیام «Does it run?» را چاپ کند.

قسمت گیج‌کننده این است: بسته به اینکه آن قطعه کد را در کدام محیط JS امتحان کنید، ممکن است نتایج متفاوت بگیرید! این یکی از آن چند ناحیه عجیب است که رفتار میراثی موجود نتیجه قابل پیش‌بینی را خیانت می‌کند.

مشخصات JS می‌گوید اعلان‌های `function` داخل بلوک‌ها block-scoped هستند، پس جواب باید (۱) باشد. با این حال، بیشتر موتورهای JS مبتنی بر مرورگر (از جمله v8 که از Chrome می‌آید اما در Node هم استفاده می‌شود) مثل (۲) رفتار می‌کنند، یعنی شناسه به بلوک `if` محدود نیست اما مقدار تابع به‌طور خودکار مقداردهی اولیه نمی‌شود، پس `undefined` می‌ماند.

چرا به موتورهای JS مرورگر اجازه داده می‌شود بر خلاف مشخصات رفتار کنند؟ چون این موتورها از قبل رفتارهای خاصی حول FiB قبل از معرفی block scoping در ES6 داشتند، و نگرانی بود که تغییر برای پایبندی به مشخصات ممکن است کد JS وب‌سایت موجود را خراب کند. به همین دلیل، استثنایی در پیوست ب مشخصات JS گذاشته شد، که انحرافات خاصی را برای موتورهای JS مرورگر (فقط!) مجاز می‌کند.

| نکته: |
| :--- |
| معمولاً Node را به عنوان محیط JS مرورگر دسته‌بندی نمی‌کنید، چون معمولاً روی سرور اجرا می‌شود. اما موتور v8 Node با مرورگرهای Chrome (و Edge) مشترک است. چون v8 اول موتور JS مرورگر است، این استثنای پیوست ب را می‌پذیرد، که یعنی استثناهای مرورگر به Node گسترش می‌یابند. |

یکی از رایج‌ترین موارد استفاده برای قرار دادن اعلان `function` در بلوک تعریف شرطی تابع به یک شکل یا شکل دیگر (مثل statement `if..else`) بسته به وضعیت محیط است. مثلاً:

```js
if (typeof Array.isArray != "undefined") {
    function isArray(a) {
        return Array.isArray(a);
    }
}
else {
    function isArray(a) {
        return Object.prototype.toString.call(a)
            == "[object Array]";
    }
}
```

وسوسه‌انگیز است کد را به این شکل برای دلایل عملکرد ساختار دهید، چون بررسی `typeof Array.isArray` فقط یک بار انجام می‌شود، در مقابل تعریف فقط یک `isArray(..)` و قرار دادن statement `if` داخلش—بررسی آنگاه در هر فراخوانی به‌طور غیرضروری اجرا می‌شد.

| هشدار: |
| :--- |
| علاوه بر خطرات انحرافات FiB، مشکل دیگر تعریف شرطی توابع این است که اشکال‌زدایی چنین برنامه‌ای سخت‌تر است. اگر در تابع `isArray(..)` به باگی برخوردید، اول باید بفهمید *کدام* پیاده‌سازی `isArray(..)` واقعاً در حال اجراست! گاهی باگ این است که نسخه اشتباه اعمال شد چون بررسی شرطی نادرست بود! اگر چند نسخه از یک تابع تعریف کنید، آن برنامه همیشه سخت‌تر برای استدلال و نگهداری است. |

علاوه بر قطعات قبلی، چند مورد گوشه FiB دیگر کمین کرده‌اند؛ چنین رفتارهایی در مرورگرهای مختلف و محیط‌های JS غیرمرورگر (موتورهای JS که مبتنی بر مرورگر نیستند) احتمالاً متفاوت خواهند بود. مثلاً:

```js
if (true) {
    function ask() {
        console.log("Am I called?");
    }
}

if (true) {
    function ask() {
        console.log("Or what about me?");
    }
}

for (let i = 0; i < 5; i++) {
    function ask() {
        console.log("Or is it one of these?");
    }
}

ask();

function ask() {
    console.log("Wait, maybe, it's this one?");
}
```

به یاد بیاورید که function hoisting همان‌طور که در «چه زمانی می‌توانم از یک متغیر استفاده کنم؟» (فصل ۵) توضیح داده شد ممکن است پیشنهاد دهد که `ask()` نهایی در این قطعه، با «Wait, maybe...» به عنوان پیامش، بالای فراخوانی `ask()` hoist شود. چون آخرین function declaration با آن نام است، باید «برنده» شود، درست؟ متأسفانه نه.

قصد من مستند کردن همه این موارد گوشه عجیب نیست، و نه توضیح چرایی رفتار هر کدام به شکلی خاص. آن اطلاعات، به نظر من، اطلاعات میراثی مبهم است.

نگرانی واقعی من با FiB این است: چه توصیه‌ای می‌توانم بدهم تا کدتان در همه شرایط قابل پیش‌بینی رفتار کند؟

تا جایی که به من مربوط است، تنها جواب عملی برای اجتناب از نوسانات FiB این است که به سادگی از FiB کاملاً اجتناب کنید. به عبارت دیگر، هرگز اعلان `function` را مستقیماً داخل هیچ بلوکی قرار ندهید. همیشه اعلان‌های `function` را هر کجا در scope سطح بالای تابع (یا در scope سراسری) قرار دهید.

پس برای مثال `if..else` قبلی، پیشنهاد من اجتناب از تعریف شرطی توابع در حد امکان است. بله، ممکن است کمی کمتر کارآمد باشد، اما این رویکرد کلی بهتر است:

```js
function isArray(a) {
    if (typeof Array.isArray != "undefined") {
        return Array.isArray(a);
    }
    else {
        return Object.prototype.toString.call(a)
            == "[object Array]";
    }
}
```

اگر آن ضربه عملکرد به مسیر بحرانی برنامه‌تان تبدیل شد، این رویکرد را پیشنهاد می‌کنم:

```js
var isArray = function isArray(a) {
    return Array.isArray(a);
};

// override the definition, if you must
if (typeof Array.isArray == "undefined") {
    isArray = function isArray(a) {
        return Object.prototype.toString.call(a)
            == "[object Array]";
    };
}
```

مهم است توجه کنید که اینجا function **expression** قرار می‌دهم، نه declaration، داخل statement `if`. برای function expressionها ظاهر شدن داخل بلوک‌ها کاملاً درست و معتبر است. بحث ما درباره FiB اجتناب از function **declaration**ها در بلوک‌هاست.

حتی اگر برنامه‌تان را تست کنید و درست کار کند، سود کوچکی که ممکن است از استفاده سبک FiB در کدتان ببرید با خطرات بالقوه آینده برای سردرگمی توسعه‌دهندگان دیگر، یا تفاوت‌ها در نحوه اجرای کدتان در محیط‌های JS دیگر، بسیار کمتر است.

FiB ارزشش را ندارد و باید از آن اجتناب شود.
