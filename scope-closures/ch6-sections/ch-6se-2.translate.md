# پنهان‌سازی در scope (تابع) آشکار

اکنون باید روشن باشد چرا پنهان کردن اعلان‌های متغیر و تابع در پایین‌ترین (عمیق‌ترین تو در تو) scopeهای ممکن مهم است. اما چطور این کار را انجام می‌دهیم؟

قبلاً کلمات کلیدی `let` و `const` را دیده‌ایم که اعلان‌کننده‌های block-scoped هستند؛ به زودی با جزئیات بیشتر به آن‌ها برمی‌گردیم. اما اول، پنهان کردن اعلان‌های `var` یا `function` در scopeها چطور؟ این کار به راحتی با قرار دادن یک scope تابع دور یک اعلان انجام می‌شود.

مثالی را در نظر بگیریم که scopeبندی تابع می‌تواند مفید باشد.

عملیات ریاضی «فاکتوریل» (نماد «۶!») ضرب یک عدد صحیح داده‌شده در همه اعداد صحیح متوالی پایین‌تر تا `1` است—در واقع می‌توانید در `2` متوقف شوید چون ضرب در `1` کاری نمی‌کند. به عبارت دیگر، «۶!» همان «۶ * ۵!» است، که همان «۶ * ۵ * ۴!» است، و همین‌طور ادامه دارد. به خاطر ماهیت ریاضیات درگیر، وقتی فاکتوریل هر عدد صحیح داده‌شده (مثل «۴!») محاسبه شد، نباید آن کار را دوباره انجام دهیم، چون همیشه همان جواب خواهد بود.

پس اگر ساده‌لوحانه فاکتوریل `6` را محاسبه کنید، و بعد بخواهید فاکتوریل `7` را محاسبه کنید، ممکن است به‌طور غیرضروری فاکتوریل‌های همه اعداد صحیح از ۲ تا ۶ را دوباره محاسبه کنید. اگر مایلید حافظه را با سرعت عوض کنید، می‌توانید آن محاسبه هدررفته را با کش کردن فاکتوریل هر عدد صحیح هنگام محاسبه حل کنید:

```js
var cache = {};

function factorial(x) {
    if (x < 2) return 1;
    if (!(x in cache)) {
        cache[x] = x * factorial(x - 1);
    }
    return cache[x];
}

factorial(6);
// 720

cache;
// {
//     "2": 2,
//     "3": 6,
//     "4": 24,
//     "5": 120,
//     "6": 720
// }

factorial(7);
// 5040
```

همه فاکتوریل‌های محاسبه‌شده را در `cache` ذخیره می‌کنیم تا در چندین فراخوانی `factorial(..)`، محاسبات قبلی باقی بمانند. اما متغیر `cache` به وضوح جزئی *خصوصی* نحوه کار `factorial(..)` است، نه چیزی که باید در scope بیرونی—به‌ویژه scope سراسری—در معرض قرار گیرد.

| نکته: |
| :--- |
| `factorial(..)` اینجا بازگشتی است—فراخوانی به خودش از داخل انجام می‌شود—اما فقط برای اختصار کد است؛ پیاده‌سازی غیربازگشتی همان تحلیل scope را نسبت به `cache` می‌دهد. |

با این حال، رفع این مشکل مواجهه بیش از حد به سادگی پنهان کردن متغیر `cache` داخل `factorial(..)` نیست، آن‌طور که به نظر می‌رسد. چون به `cache` برای زنده ماندن در چندین فراخوانی نیاز داریم، باید در scope بیرون از آن تابع قرار گیرد. پس چه کار می‌توانیم بکنیم؟

یک scope میانی دیگر (بین scope بیرونی/سراسری و داخل `factorial(..)`) برای قرار گرفتن `cache` تعریف کنیم:

```js
// outer/global scope

function hideTheCache() {
    // "middle scope", where we hide `cache`
    var cache = {};

    return factorial;

    // **********************

    function factorial(x) {
        // inner scope
        if (x < 2) return 1;
        if (!(x in cache)) {
            cache[x] = x * factorial(x - 1);
        }
        return cache[x];
    }
}

var factorial = hideTheCache();

factorial(6);
// 720

factorial(7);
// 5040
```

تابع `hideTheCache()` هیچ هدف دیگری جز ایجاد scope برای ماندگاری `cache` در چندین فراخوانی `factorial(..)` ندارد. اما برای اینکه `factorial(..)` به `cache` دسترسی داشته باشد، باید `factorial(..)` را داخل همان scope تعریف کنیم. سپس ارجاع تابع را به عنوان مقداری از `hideTheCache()` برمی‌گردانیم و در متغیر scope بیرونی، با همین نام `factorial` ذخیره می‌کنیم. اکنون با فراخوانی `factorial(..)` (چندین بار!)، `cache` پایدارش پنهان می‌ماند اما فقط برای `factorial(..)` قابل دسترسی است!

خوب، اما... تعریف (و نام‌گذاری!) یک scope تابع `hideTheCache(..)` هر بار که چنین نیازی برای پنهان‌سازی متغیر/تابع پیش می‌آید خسته‌کننده خواهد بود، به‌ویژه چون احتمالاً می‌خواهیم با دادن نام یکتا به هر رخداد از برخورد نام با این تابع اجتناب کنیم. اوه.

| نکته: |
| :--- |
| تکنیک نشان‌داده‌شده—کش کردن خروجی محاسبه‌شده یک تابع برای بهینه‌سازی عملکرد وقتی فراخوانی‌های تکراری همان ورودی‌ها انتظار می‌رود—در دنیای برنامه‌نویسی تابعی (FP) کاملاً رایج است، که به‌طور متعارف «memoization» نامیده می‌شود؛ این کش به closure متکی است (فصل ۷ را ببینید). همچنین، نگرانی‌های استفاده از حافظه وجود دارد (در «کلامی درباره حافظه» در پیوست ب مورد بحث قرار گرفته). کتابخانه‌های FP معمولاً یک ابزار بهینه‌شده و بررسی‌شده برای memoization توابع ارائه می‌دهند، که جایگزین `hideTheCache(..)` اینجا می‌شود. Memoization فراتر از *scope* (جناس در نظر گرفته شده!) بحث ماست، اما کتاب *Functional-Light JavaScript* من را برای اطلاعات بیشتر ببینید. |

به جای تعریف یک تابع جدید و با نام یکتا هر بار که یکی از آن موقعیت‌های فقط-scope-برای-پنهان‌سازی-یک-متغیر رخ می‌دهد، شاید راه‌حل بهتری استفاده از یک function expression باشد:

```js
var factorial = (function hideTheCache() {
    var cache = {};

    function factorial(x) {
        if (x < 2) return 1;
        if (!(x in cache)) {
            cache[x] = x * factorial(x - 1);
        }
        return cache[x];
    }

    return factorial;
})();

factorial(6);
// 720

factorial(7);
// 5040
```

صبر کنید! این هنوز از یک تابع برای ایجاد scope پنهان‌سازی `cache` استفاده می‌کند، و در این مورد تابع هنوز `hideTheCache` نام دارد، پس چطور چیزی را حل می‌کند؟

از «Function Name Scope» (فصل ۳) به یاد بیاورید چه اتفاقی برای شناسه نام از یک function expression می‌افتد. چون `hideTheCache(..)` به عنوان function expression به جای function declaration تعریف شده، نامش در scope خودش است—اساساً همان scope که `cache`—نه در scope بیرونی/سراسری.

یعنی می‌توانیم هر رخداد از چنین function expression را دقیقاً همان نام بدهیم و هرگز برخوردی نداشته باشیم. مناسب‌تر، می‌توانیم هر رخداد را بر اساس هرچه سعی در پنهان کردنش داریم معنایی نام‌گذاری کنیم، و نگران نباشیم که هر نامی که انتخاب می‌کنیم با هر scope function expression دیگری در برنامه برخورد کند.

در واقع، می‌توانستیم اصلاً نام را حذف کنیم—و به جای آن یک «anonymous function expression» تعریف کنیم. اما پیوست الف اهمیت نام‌ها حتی برای چنین توابع فقط-scope را بحث خواهد کرد.

### فراخوانی فوری Function Expressionها

یک نکته مهم دیگر در برنامه بازگشتی فاکتوریل قبلی هست که به راحتی از دست می‌رود: خط انتهای function expression که شامل `})();` است.

توجه کنید که کل function expression را در یک جفت `( .. )` قرار دادیم، و بعد در انتها آن جفت دوم `()` را اضافه کردیم؛ در واقع function expression تازه تعریف‌شده را فراخوانی می‌کند. علاوه بر این، در این مورد، جفت اول `( .. )` دور function expression به‌طور سخت‌گیرانه لازم نیست (بعداً بیشتر)، اما برای خوانایی به هر حال استفاده کردیم.

پس به عبارت دیگر، یک function expression تعریف می‌کنیم که بلافاصله فراخوانی می‌شود. این الگوی رایج نامی (بسیار خلاقانه!) دارد: Immediately Invoked Function Expression (IIFE).

یک IIFE وقتی مفید است که بخواهیم scope ایجاد کنیم تا متغیرها/توابع را پنهان کنیم. چون یک expression است، می‌تواند در **هر** جایی در برنامه JS که expression مجاز است استفاده شود. یک IIFE می‌تواند نام‌دار باشد، مثل `hideTheCache()`، یا (خیلی رایج‌تر!) بدون نام/anonymous. و می‌تواند مستقل باشد یا، مثل قبل، بخشی از عبارت دیگری—`hideTheCache()` ارجاع تابع `factorial()` را برمی‌گرداند که بعد با `=` به متغیر `factorial` انتساب داده می‌شود.

برای مقایسه، اینجا مثالی از یک IIFE مستقل است:

```js
// outer scope

(function(){
    // inner hidden scope
})();

// more outer scope
```

برخلاف قبلاً با `hideTheCache()`، که `(..)` بیرونی دور آن به عنوان انتخاب سبکی اختیاری ذکر شد، برای یک IIFE مستقل **الزامی** است؛ تابع را به عنوان expression متمایز می‌کنند، نه statement. با این حال، برای یکنواختی، همیشه function یک IIFE را با `( .. )` احاطه کنید.

| نکته: |
| :--- |
| از نظر فنی، `( .. )` احاطه‌کننده تنها راه نحوی برای اطمینان از اینکه function در یک IIFE توسط parser جاوااسکریپت به عنوان function expression تلقی شود نیست. گزینه‌های دیگری در پیوست الف بررسی می‌کنیم. |

#### مرزهای تابع

هشدار که استفاده از IIFE برای تعریف scope می‌تواند عواقب ناخواسته‌ای داشته باشد، بسته به کد اطرافش. چون IIFE یک تابع کامل است، مرز تابع رفتار برخی statementها/سازه‌ها را تغییر می‌دهد.

مثلاً، یک statement `return` در بخشی از کد معنایش عوض می‌شود اگر IIFE دورش پیچیده شود، چون حالا `return` به تابع IIFE اشاره می‌کند. IIFEهای تابع غیر-arrow همچنین binding کلمه کلیدی `this` را تغییر می‌دهند—بیشتر در کتاب *Objects & Classes*. و statementهایی مثل `break` و `continue` از مرز تابع IIFE عبور نمی‌کنند تا حلقه یا بلوک بیرونی را کنترل کنند.

پس اگر کدی که باید scope دورش بپیچید `return`، `this`، `break` یا `continue` دارد، IIFE احتمالاً بهترین رویکرد نیست. در آن مورد، ممکن است به جای تابع با بلوک scope ایجاد کنید.
