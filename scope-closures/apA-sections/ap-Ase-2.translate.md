# توابع گمنام در مقابل نام‌دار

همان‌طور که در فصل ۳ بحث شد، توابع می‌توانند به شکل نام‌دار یا گمنام بیان شوند. استفاده از شکل گمنام بسیار رایج‌تر است، اما آیا ایده خوبی است؟

وقتی نام‌گذاری توابع را در نظر می‌گیرید، این موارد را در نظر بگیرید:

* استنتاج نام ناقص است
* نام‌های lexical اجازه self-reference می‌دهند
* نام‌ها توضیحات مفیدی هستند
* توابع arrow نام lexical ندارند
* IIFEها هم به نام نیاز دارند

### نام صریح یا استنتاج‌شده؟

هر تابع در برنامه‌تان هدفی دارد. اگر هدفی ندارد، حذفش کنید، چون فقط فضا هدر می‌دهید. اگر *هدف* دارد، *نامی* برای آن هدف وجود دارد.

تا اینجا بسیاری خوانندگان احتمالاً با من موافقند. اما آیا یعنی همیشه باید آن نام را در کد بگذاریم؟ اینجا چند ابرو بالا می‌رود. می‌گویم، بدون ابهام، بله!

اول از همه، ظاهر شدن «anonymous» در stack traceها برای اشکال‌زدایی چندان مفید نیست:

```js
btn.addEventListener("click",function(){
    setTimeout(function(){
        ["a",42].map(function(v){
            console.log(v.toUpperCase());
        });
    },100);
});
// Uncaught TypeError: v.toUpperCase is not a function
//     at myProgram.js:4
//     at Array.map (<anonymous>)
//     at myProgram.js:3
```

اوه. با آنچه گزارش می‌شود اگر به توابع نام بدهم مقایسه کنید:

```js
btn.addEventListener("click",function onClick(){
    setTimeout(function waitAMoment(){
        ["a",42].map(function allUpper(v){
            console.log(v.toUpperCase());
        });
    },100);
});
// Uncaught TypeError: v.toUpperCase is not a function
//     at allUpper (myProgram.js:4)
//     at Array.map (<anonymous>)
//     at waitAMoment (myProgram.js:3)
```

ببینید نام‌های `waitAMoment` و `allUpper` ظاهر می‌شوند و اطلاعات/زمینه مفیدتری به stack trace برای اشکال‌زدایی می‌دهند؟ برنامه اگر برای همه توابع نام‌های معقول استفاده کنیم قابل اشکال‌زدایی‌تر است.

| نکته: |
| :--- |
| «&lt;anonymous>» بدبختانه که هنوز نشان داده می‌شود به این واقعیت اشاره دارد که پیاده‌سازی `Array.map(..)` در برنامه ما حضور ندارد، بلکه در موتور JS ساخته شده. از هیچ سردرگمی که برنامه ما با میانبرهای خوانایی معرفی می‌کند نیست. |

به هر حال، مطمئن شویم درباره تابع نام‌دار در یک صفحه هستیم:

```js
function thisIsNamed() {
    // ..
}

ajax("some.url",function thisIsAlsoNamed(){
   // ..
});

var notNamed = function(){
    // ..
};

makeRequest({
    data: 42,
    cb /* also not a name */: function(){
        // ..
    }
});

var stillNotNamed = function butThisIs(){
    // ..
};
```

«اما صبر کنید!»، می‌گویید. برخی از آن‌ها *نام‌دار* هستند، درست!؟

```js
var notNamed = function(){
    // ..
};

var config = {
    cb: function(){
        // ..
    }
};

notNamed.name;
// notNamed

config.cb.name;
// cb
```

این‌ها *inferred* name نامیده می‌شوند. نام‌های استنتاج‌شده خوبند، اما واقعاً نگرانی کامل من را برطرف نمی‌کنند.

### نام‌های گم‌شده؟

بله، این نام‌های استنتاج‌شده ممکن است در stack traceها ظاهر شوند، که قطعاً بهتر از ظاهر شدن «anonymous» است. اما...

```js
function ajax(url,cb) {
    console.log(cb.name);
}

ajax("some.url",function(){
    // ..
});
// ""
```

اوپس. function expressionهای گمنام `function` که به عنوان callback فرستاده می‌شوند قادر به دریافت نام استنتاج‌شده نیستند، پس `cb.name` فقط رشته خالی `""` نگه می‌دارد. اکثریت قاطع همه function expressionها، به‌ویژه گمنام‌ها، به عنوان آرگومان callback استفاده می‌شوند؛ هیچ‌کدام نام نمی‌گیرند. پس تکیه بر استنتاج نام در بهترین حالت ناقص است.

و فقط callbackها نیستند که با استنتاج کوتاه می‌آیند:

```js
var config = {};

config.cb = function(){
    // ..
};

config.cb.name;
// ""

var [ noName ] = [ function(){} ];
noName.name
// ""
```

هر انتساب function expression که *انتساب ساده* نباشد هم در استنتاج نام شکست می‌خورد. پس به عبارت دیگر، مگر اینکه دقیق و عمدی باشید، اساساً تقریباً همه function expressionهای گمنام در برنامه‌تان در واقع اصلاً نامی ندارند.

استنتاج نام فقط... کافی نیست.

و حتی اگر function expression *نام* استنتاج‌شده بگیرد، هنوز به عنوان تابع نام‌دار کامل به حساب نمی‌آید.

### من کیستم؟

بدون شناسه نام lexical، تابع راه داخلی برای ارجاع به خودش ندارد. Self-reference برای چیزهایی مثل بازگشت و مدیریت رویداد مهم است:

```js
// broken
runOperation(function(num){
    if (num <= 1) return 1;
    return num * oopsNoNameToCall(num - 1);
});

// also broken
btn.addEventListener("click",function(){
   console.log("should only respond to one click!");
   btn.removeEventListener("click",oopsNoNameHere);
});
```

حذف نام lexical از callback ارجاع خودکار قابل اعتماد به تابع را سخت‌تر می‌کند. *می‌توانستید* متغیری در scope احاطه‌کننده اعلان کنید که به تابع ارجاع دهد، اما آن متغیر *کنترل* scope احاطه‌کننده است—می‌تواند انتساب مجدد شود و غیره—پس به اندازه تابعی که ارجاع خودکار داخلی دارد قابل اعتماد نیست.

### نام‌ها توصیف‌کننده‌اند

در آخر، و فکر می‌کنم از همه مهم‌تر، حذف نام از تابع فهمیدن هدف تابع را برای خواننده در نگاه سریع سخت‌تر می‌کند. باید بیشتر کد را بخوانند، از جمله کد داخل تابع و کد اطراف بیرون تابع، تا بفهمند.

در نظر بگیرید:

```js
[ 1, 2, 3, 4, 5 ].filter(function(v){
    return v % 2 == 1;
});
// [ 1, 3, 5 ]

[ 1, 2, 3, 4, 5 ].filter(function keepOnlyOdds(v){
    return v % 2 == 1;
});
// [ 1, 3, 5 ]
```

هیچ استدلال معقولی برای **حذف** نام `keepOnlyOdds` از callback اول برای انتقال مؤثرتر هدف این callback به خواننده وجود ندارد. ۱۳ کاراکتر صرفه‌جویی کردید، اما اطلاعات خوانایی مهم را از دست دادید. نام `keepOnlyOdds` به وضوح به خواننده در نگاه اول می‌گوید چه اتفاقی می‌افتد.

موتور JS به نام اهمیت نمی‌دهد. اما خوانندگان انسانی کدتان قطعاً اهمیت می‌دهند.

آیا خواننده می‌تواند `v % 2 == 1` را ببیند و بفهمد چه می‌کند؟ حتماً. اما باید هدف (و نام) را با اجرای ذهنی کد استنتاج کنند. حتی مکث کوتاه برای این کار خواندن کد را کند می‌کند. یک نام توصیفی خوب این فرآیند را تقریباً بدون تلاش و فوری می‌کند.

این‌طور فکر کنید: چند بار نویسنده این کد باید هدف تابع را قبل از اضافه کردن نام به کد بفهمد؟ حدود یک بار. شاید دو یا سه بار اگر نیاز به تنظیم نام داشته باشد. اما چند بار خوانندگان این کد باید نام/هدف را بفهمند؟ هر بار که این خط خوانده می‌شود. صدها بار؟ هزاران؟ بیشتر؟

صرف نظر از طول یا پیچیدگی تابع، ادعای من این است که نویسنده باید نام توصیفی خوبی پیدا کند و به کد اضافه کند. حتی توابع یک‌خطی در statementهای `map(..)` و `then(..)` باید نام داشته باشند:

```js
lookupTheRecords(someData)
.then(function extractSalesRecords(resp){
   return resp.allSales;
})
.then(storeRecords);
```

نام `extractSalesRecords` هدف این handler `then(..)` را *بهتر* از استنتاج آن هدف با اجرای ذهنی `return resp.allSales` به خواننده می‌گوید.

تنها بهانه برای شامل نکردن نام روی تابع یا تنبلی است (نمی‌خواهید چند کاراکتر اضافی تایپ کنید) یا عدم خلاقیت (نمی‌توانید نام خوبی پیدا کنید). اگر نمی‌توانید نام خوبی پیدا کنید، احتمالاً هنوز تابع و هدفش را نمی‌فهمید. تابع شاید ضعیف طراحی شده، یا کارهای زیادی انجام می‌دهد، و باید بازطراحی شود. وقتی تابعی با طراحی خوب و تک‌هدف دارید، نام مناسبش آشکار می‌شود.

ترفندی که استفاده می‌کنم: هنگام نوشتن اولیه تابع، اگر هدفش را کاملاً نمی‌فهمم و نمی‌توانم نام خوبی پیدا کنم، فقط از `TODO` به عنوان نام استفاده می‌کنم. به این شکل، بعداً هنگام بازبینی کدم، احتمالاً آن placeholderهای نام را پیدا می‌کنم و تمایل بیشتری (و آماده‌تر!) برای برگشتن و پیدا کردن نام بهتر دارم تا اینکه آن را به عنوان `TODO` بگذارم.

همه توابع به نام نیاز دارند. هر کدام. بدون استثنا. هر نامی که حذف کنید برنامه را سخت‌تر برای خواندن، اشکال‌زدایی، گسترش و نگهداری بعداً می‌کند.

### توابع Arrow

توابع arrow **همیشه** گمنام هستند، حتی اگر (به ندرت) به شکلی استفاده شوند که نام استنتاج‌شده بگیرند. چند صفحه توضیح دادم چرا توابع گمنام ایده بدی هستند، پس احتمالاً حدس می‌زنید درباره توابع arrow چه فکر می‌کنم.

آن‌ها را به عنوان جایگزین عمومی توابع عادی استفاده نکنید. بله، مختصرترند، اما آن اختصار به بهای حذف جداکننده‌های بصری کلیدی که به مغزمان کمک می‌کنند سریع آنچه می‌خوانیم parse کنیم می‌آید. و به نکته این بحث، آن‌ها گمنام هستند که از آن زاویه هم برای خوانایی بدتر می‌کنند.

توابع arrow هدفی دارند، اما آن هدف صرفه‌جویی در ضربه‌های کلید نیست. توابع arrow رفتار *lexical this* دارند که تا حدی فراتر از محدوده بحث ما در این کتاب است.

به طور خلاصه: توابع arrow اصلاً شناسه کلمه کلیدی `this` تعریف نمی‌کنند. اگر داخل تابع arrow از `this` استفاده کنید، دقیقاً مثل هر ارجاع متغیر دیگر رفتار می‌کند، یعنی scope chain برای یافتن scope تابع (تابع غیر-arrow) جایی که *تعریف* شده مشورت می‌شود و از آن استفاده می‌شود.

به عبارت دیگر، توابع arrow با `this` مثل هر متغیر lexical دیگر برخورد می‌کنند.

اگر به hackهایی مثل `var self = this` عادت دارید، یا ترجیح می‌دهید `.bind(this)` روی function expressionهای درونی بزنید، فقط برای مجبور کردن آن‌ها به ارث بردن `this` از تابع بیرونی مثل یک متغیر lexical، پس توابع arrow `=>` قطعاً گزینه بهتری هستند. آن‌ها دقیقاً برای حل آن مشکل طراحی شده‌اند.

پس در موارد نادری که به *lexical this* نیاز دارید، از تابع arrow استفاده کنید. بهترین ابزار برای آن کار است. اما فقط آگاه باشید که با این کار هزینه خوانایی تابع گمنام را می‌پذیرید. باید تلاش اضافی برای کاهش *هزینه* خوانایی انجام دهید، مثل نام‌های متغیر توصیفی‌تر و کامنت‌های کد.

### گونه‌های IIFE

همه توابع باید نام داشته باشند. چند بار گفتم، درست!؟ از جمله IIFEها.

```js
(function(){
    // don't do this!
})();

(function doThisInstead(){
    // ..
})();
```

چطور برای IIFE نام پیدا کنیم؟ مشخص کنید IIFE برای چیست. چرا در آن نقطه به scope نیاز دارید؟ آیا متغیر cache برای سوابق دانش‌آموزی پنهان می‌کنید؟

```js
var getStudents = (function StoreStudentRecords(){
    var studentRecords = [];

    return function getStudents() {
        // ..
    }
})();
```

IIFE را `StoreStudentRecords` نامیدم چون آن کار را می‌کند: ذخیره سوابق دانش‌آموزی. هر IIFE باید نام داشته باشد. بدون استثنا.

IIFEها معمولاً با قرار دادن `( .. )` دور function expression تعریف می‌شوند، همان‌طور که در آن قطعات قبلی نشان داده شد. اما این تنها راه تعریف IIFE نیست. از نظر فنی، تنها دلیل استفاده از آن جفت اول `( .. )` احاطه‌کننده فقط این است که کلمه کلیدی `function` در موقعیتی نباشد که به عنوان function declaration توسط parser JS واجد شرایط شود. اما راه‌های نحوی دیگری برای اجتناب از parse شدن به عنوان declaration هست:

```js
!function thisIsAnIIFE(){
    // ..
}();

+function soIsThisOne(){
    // ..
}();

~function andThisOneToo(){
    // ..
}();
```

عملگرهای `!`، `+`، `~` و چند unary operator دیگر (عملگرهای با یک عملوند) همگی می‌توانند جلوی `function` قرار گیرند تا آن را به expression تبدیل کنند. سپس فراخوانی نهایی `()` معتبر است، که آن را IIFE می‌کند.

در واقع وقتی IIFE مستقل تعریف می‌کنم استفاده از unary operator `void` را دوست دارم:

```js
void function yepItsAnIIFE() {
    // ..
}();
```

سود `void` این است که در ابتدای تابع به وضوح منتقل می‌کند که این IIFE هیچ مقداری برنمی‌گرداند.

هر طور IIFEهایتان را تعریف کنید، با دادن نام به آن‌ها عشق نشان دهید.
