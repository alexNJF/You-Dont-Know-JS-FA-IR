# مورد استفاده `var`

از *variable hoisting* که حرف زدیم، بیایید کمی صحبت واقعی درباره `var` داشته باشیم، villain مورد علاقه devها که دوست دارند بسیاری از مشکلات توسعه JS را مقصر بدانند. در فصل ۵، `let`/`const` را کاوش کردیم و وعده دادیم جایی که `var` در کل ترکیب قرار می‌گیرد بازمی‌گردیم.

همان‌طور که مورد را می‌گذارم، از دست ندهید:

* `var` هرگز خراب نبود
* `let` دوست شماست
* `const` کاربرد محدودی دارد
* بهترین هر دو دنیا: `var` *و* `let`

### `var` را دور نیندازید

`var` خوب است و خوب کار می‌کند. ۲۵ سال است که هست و ۲۵ سال یا بیشتر دیگر هم خواهد بود و مفید و کاربردی. ادعاهای اینکه `var` خراب، منسوخ، قدیمی، خطرناک یا بدطراحی است bandwagoning بی‌اساس است.

آیا یعنی `var` اعلان‌کننده درست برای هر اعلان در برنامه‌تان است؟ قطعاً نه. اما هنوز جایگاهی در برنامه‌هایتان دارد. امتناع از استفاده به خاطر اینکه کسی در تیم linter opinion تهاجمی انتخاب کرده که روی `var` خفه می‌شود cutting off your nose to spite your face است.

خوب، حالا که واقعاً عصبانی‌تان کردم، بگذارید سعی کنم موضعم را توضیح دهم.

برای ثبت، طرفدار `let` هستم، برای اعلان‌های block-scoped. واقعاً TDZ را دوست ندارم و فکر می‌کنم اشتباه بود. اما خود `let` عالی است. اغلب استفاده می‌کنم. در واقع، احتمالاً به اندازه یا بیشتر از `var` استفاده می‌کنم.

### `const` گیج‌کننده

`const` از طرف دیگر، به اندازه استفاده نمی‌کنم. قرار نیست به همه دلایل بپردازم، اما به این خلاصه می‌شود که `const` *وزن خودش را حمل نمی‌کند*. یعنی در حالی که سود کوچکی از `const` در برخی موارد هست، آن سود با تاریخ طولانی مشکلات حول سردرگمی `const` در زبان‌های مختلف، مدتها قبل از ظهورش در JS، کمتر می‌شود.

`const` وانمود می‌کند مقادیری ایجاد می‌کند که نمی‌توان mutate کرد—سوءتفاهمی که در جوامع توسعه‌دهندگان در بسیاری زبان‌ها بسیار رایج است—در حالی که واقعاً از انتساب مجدد جلوگیری می‌کند.

```js
const studentIDs = [ 14, 73, 112 ];

// later

studentIDs.push(6);   // whoa, wait... what!?
```

استفاده از `const` با مقدار mutable (مثل آرایه یا object) دعوت توسعه‌دهنده آینده (یا خواننده کدتان) به افتادن در تله‌ای است که گذاشتید، که یا نمی‌دانستند یا فراموش کرده بودند که *immutability مقدار* اصلاً همان *immutability انتساب* نیست.

فقط فکر نمی‌کنم باید آن تله‌ها را بگذاریم. تنها زمانی که از `const` استفاده می‌کنم وقتی مقدار از قبل immutable انتساب می‌دهم (مثل `42` یا `"Hello, friends!"`) و وقتی به وضوح «ثابت» به معنای placeholder نام‌دار برای مقدار literal است، برای اهداف معنایی. این بهترین استفاده از `const` است. در کدم نسبتاً نادر است.

اگر انتساب مجدد متغیر مسئله بزرگی بود، `const` مفیدتر می‌بود. اما انتساب مجدد متغیر در ایجاد باگ چندان بزرگ نیست. لیست طولانی چیزهایی که به باگ در برنامه‌ها منجر می‌شوند هست، اما «انتساب مجدد تصادفی» خیلی خیلی پایین آن لیست است.

آن را با این واقعیت ترکیب کنید که `const` (و `let`) قرار است در بلوک‌ها استفاده شوند و بلوک‌ها قرار است کوتاه باشند، و ناحیه واقعاً کوچکی از کدتان دارید که اعلان `const` حتی قابل اعمال است. یک `const` در خط ۱ بلوک ده‌خطی فقط درباره نه خط بعدی به شما می‌گوید. و چیزی که می‌گوید با نگاه به آن نه خط قبلاً واضح است: متغیر هرگز سمت چپ `=` نیست؛ انتساب مجدد نمی‌شود.

همین، این همه کاری است که `const` واقعاً می‌کند. غیر از آن، خیلی مفید نیست. در مقابل سردرگمی قابل توجه immutability مقدار در مقابل انتساب، `const` خیلی از درخششش را از دست می‌دهد.

یک `let` (یا `var`!) که هرگز انتساب مجدد نمی‌شود از نظر رفتاری قبلاً «ثابت» است، حتی اگر تضمین کامپایلر را ندارد. در بیشتر موارد کافی است.

### `var` *و* `let`

به نظر من، `const` نسبتاً به ندرت مفید است، پس این فقط مسابقه دو اسب بین `let` و `var` است. اما واقعاً مسابقه هم نیست، چون نباید فقط یک برنده باشد. هر دو می‌توانند برنده شوند... مسابقه‌های مختلف.

واقعیت این است که باید هم `var` و هم `let` را در برنامه‌هایتان استفاده کنید. قابل تعویض نیستند: نباید `var` جایی که `let` لازم است استفاده کنید، اما نباید `let` جایی که `var` مناسب‌تر است استفاده کنید.

پس کجا هنوز باید از `var` استفاده کنیم؟ در چه شرایطی انتخاب بهتری از `let` است؟

برای یکی، همیشه در scope سطح بالای هر تابع از `var` استفاده می‌کنم، صرف نظر از اینکه در ابتدا، وسط یا انتهای تابع باشد. همچنین در scope سراسری از `var` استفاده می‌کنم، هرچند سعی می‌کنم استفاده از scope سراسری را به حداقل برسانم.

چرا برای function scoping از `var` استفاده کنیم؟ چون دقیقاً کاری است که `var` می‌کند. تحت‌اللفظی ابزار بهتری برای کار scopeبندی function یک اعلان از اعلان‌کننده‌ای که ۲۵ سال دقیقاً آن کار را کرده نیست.

*می‌توانستید* در این scope سطح بالا از `let` استفاده کنید، اما بهترین ابزار برای آن کار نیست. همچنین می‌بینم که اگر همه جا از `let` استفاده کنید، کمتر واضح است کدام اعلان‌ها برای localized طراحی شده‌اند و کدام‌ها برای استفاده در کل تابع.

در مقابل، به ندرت داخل بلوک از `var` استفاده می‌کنم. آن کار `let` است. بهترین ابزار را برای کار استفاده کنید. اگر `let` ببینید، می‌گوید با اعلان localized سروکار دارید. اگر `var` ببینید، می‌گوید با اعلان در کل تابع سروکار دارید. به همین سادگی.

```js
function getStudents(data) {
    var studentRecords = [];

    for (let record of data.records) {
        let id = `student-${ record.id }`;
        studentRecords.push({
            id,
            record.name
        });
    }

    return studentRecords;
}
```

متغیر `studentRecords` برای استفاده در کل تابع در نظر گرفته شده. `var` بهترین اعلان‌کننده برای گفتن این به خواننده است. در مقابل، `record` و `id` فقط برای استفاده در scope باریک‌تر تکرار حلقه در نظر گرفته شده‌اند، پس `let` بهترین ابزار برای آن کار است.

علاوه بر این استدلال معنایی *بهترین ابزار*، `var` چند ویژگی دیگر دارد که در شرایط محدود خاص آن را قدرتمندتر می‌کند.

یک مثال وقتی است که حلقه انحصاراً از متغیری استفاده می‌کند، اما بند شرطی نمی‌تواند اعلان‌های block-scoped داخل تکرار را ببیند:

```js
function commitAction() {
    do {
        let result = commit();
        var done = result && result.code == 1;
    } while (!done);
}
```

اینجا، `result` به وضوح فقط داخل بلوک استفاده می‌شود، پس از `let` استفاده می‌کنیم. اما `done` کمی متفاوت است. فقط برای حلقه مفید است، اما بند `while` نمی‌تواند اعلان‌های `let` داخل حلقه را ببیند. پس مصالحه می‌کنیم و از `var` استفاده می‌کنیم تا `done` به scope بیرونی جایی که دیده می‌شود hoist شود.

جایگزین—اعلان `done` بیرون حلقه—آن را از جایی که اولین بار استفاده می‌شود جدا می‌کند و یا نیاز به انتخاب مقدار پیش‌فرض برای انتساب دارد، یا بدتر، آن را بدون انتساب می‌گذارد و بنابراین برای خواننده مبهم به نظر می‌رسد. فکر می‌کنم `var` داخل حلقه اینجا ترجیح دارد.

ویژگی مفید دیگر `var` با اعلان‌ها داخل بلوک‌های ناخواسته دیده می‌شود. بلوک‌های ناخواسته بلوک‌هایی هستند که چون نحو بلوک می‌خواهد ایجاد می‌شوند، اما جایی که قصد توسعه‌دهنده واقعاً ایجاد scope localized نیست. بهترین تصویر scope ناخواسته statement `try..catch` است:

```js
function getStudents() {
    try {
        // not really a block scope
        var records = fromCache("students");
    }
    catch (err) {
        // oops, fall back to a default
        var records = [];
    }
    // ..
}
```

راه‌های دیگری برای ساختار دادن این کد هست، بله. اما فکر می‌کنم با توجه به trade-offهای مختلف این *بهترین* راه است.

نمی‌خواهم `records` را (با `var` یا `let`) بیرون بلوک `try` اعلان کنم و بعد در یک یا هر دو بلوک به آن انتساب دهم. ترجیح می‌دهم اعلان‌های اولیه همیشه تا حد امکان نزدیک (ایده‌آل، همان خط) به اولین استفاده از متغیر باشند. در این مثال ساده فقط چند خط فاصله می‌شد، اما در کد واقعی می‌تواند به خطوط بیشتری رشد کند. هرچه فاصله بزرگ‌تر، فهمیدن به کدام متغیر از کدام scope انتساب می‌دهید سخت‌تر. `var` در انتساب واقعی کمتر مبهم می‌کند.

همچنین توجه کنید در هر دو بلوک `try` و `catch` از `var` استفاده کردم. چون می‌خواهم به خواننده سیگنال دهم که صرف نظر از مسیر، `records` همیشه اعلان می‌شود. از نظر فنی کار می‌کند چون `var` یک بار به scope تابع hoist می‌شود. اما هنوز سیگنال معنایی خوبی برای یادآوری به خواننده آنچه هر `var` تضمین می‌کند است. اگر `var` فقط در یکی از بلوک‌ها استفاده می‌شد و فقط بلوک دیگر را می‌خواندید، به راحتی نمی‌فهمیدید `records` از کجا می‌آید.

این به نظر من یک superpower کوچک `var` است. نه فقط می‌تواند از بلوک‌های `try..catch` ناخواسته فرار کند، بلکه اجازه ظاهر شدن چند بار در scope تابع را دارد. با `let` نمی‌توانید این کار را بکنید. بد نیست، در واقع ویژگی کمکی کوچکی است. به `var` بیشتر مثل annotation اعلانی فکر کنید که هر استفاده به شما یادآوری می‌کند متغیر از کجا می‌آید. «آها، درست، به کل تابع تعلق دارد.»

این superpower annotation تکراری در موارد دیگر مفید است:

```js
function getStudents() {
    var data = [];

    // do something with data
    // .. 50 more lines of code ..

    // purely an annotation to remind us
    var data;

    // use data again
    // ..
}
```

دومین `var data` `data` را دوباره اعلان نمی‌کند، فقط برای سود خوانندگان annotate می‌کند که `data` اعلان در کل تابع است. به این شکل خواننده نیازی به scroll کردن ۵۰+ خط کد برای پیدا کردن اعلان اولیه ندارد.

کاملاً با استفاده مجدد از متغیرها برای اهداف متعدد در سراسر scope تابع راحتم. همچنین کاملاً با داشتن دو استفاده از متغیر جدا شده با چند خط کد راحتم. در هر دو مورد، توانایی «اعلان مجدد» (annotate) امن با `var` کمک می‌کند مطمئن شوم می‌توانم بگویم `data` از کجا می‌آید، هر کجا در تابع باشم.

دوباره، متأسفانه، `let` نمی‌تواند این کار را بکند.

ظرافت‌ها و سناریوهای دیگری هست وقتی `var` کمک می‌کند، اما بیشتر به نقطه نمی‌پردازم. نتیجه این است که `var` می‌تواند در برنامه‌هایمان همراه با `let` (و گاه `const`) مفید باشد. آیا مایلید خلاقانه از ابزارهای ارائه‌شده زبان JS برای گفتن داستان غنی‌تر به خوانندگان استفاده کنید؟

فقط ابزار مفیدی مثل `var` را به خاطر شرمنده شدن توسط کسی که فکر می‌کرد دیگر cool نیست دور نیندازید. از `var` به خاطر یک بار گیج شدن سال‌ها پیش اجتناب نکنید. این ابزارها را یاد بگیرید و هر کدام را برای بهترین کارش استفاده کنید.
