# گونه‌های ماژول کلاسیک

فصل ۸ الگوی ماژول کلاسیک را توضیح داد که می‌تواند این‌طور به نظر برسد:

```js
var StudentList = (function defineModule(Student){
    var elems = [];

    var publicAPI = {
        renderList() {
            // ..
        }
    };

    return publicAPI;

})(Student);
```

توجه کنید که `Student` (نمونه ماژول دیگر) را به عنوان وابستگی می‌فرستیم. اما گونه‌های مفید زیادی روی این شکل ماژول وجود دارد که ممکن است برخورد کنید. چند اشاره برای تشخیص این گونه‌ها:

* آیا ماژول API خودش را می‌شناسد؟
* حتی اگر از module loader فancy استفاده کنیم، فقط ماژول کلاسیک است
* برخی ماژول‌ها باید به طور جهانی کار کنند

### API من کجاست؟

اول، بیشتر ماژول‌های کلاسیک `publicAPI` را آن‌طور که در این کد نشان دادم تعریف و استفاده نمی‌کنند. به جای آن، معمولاً این‌طور به نظر می‌رسند:

```js
var StudentList = (function defineModule(Student){
    var elems = [];

    return {
        renderList() {
            // ..
        }
    };

})(Student);
```

تنها تفاوت اینجا برگرداندن مستقیم objectی است که به عنوان API عمومی ماژول خدمت می‌کند، در مقابل اول ذخیره آن در متغیر درونی `publicAPI`. این به مراتب نحوه تعریف بیشتر ماژول‌های کلاسیک است.

اما قویاً ترجیح می‌دهم و همیشه خودم از شکل قبلی `publicAPI` استفاده می‌کنم. دو دلیل:

* `publicAPI` توصیف‌کننده معنایی است که با واضح‌تر کردن هدف object خوانایی را کمک می‌کند.

* ذخیره متغیر درونی `publicAPI` که به همان object API عمومی خارجی برگشتی ارجاع می‌دهد، می‌تواند مفید باشد اگر نیاز به دسترسی یا تغییر API در طول عمر ماژول دارید.

    مثلاً، ممکن است بخواهید یکی از توابع در معرض عمومی را از داخل ماژول فراخوانی کنید. یا ممکن است بسته به شرایط خاص متدها را اضافه یا حذف کنید، یا مقدار ویژگی در معرض را به‌روزرسانی کنید.

    هر موردی که باشد، به نظر من کمی احمقانه است که *ارجاعی برای دسترسی به API خودمان* نگه نداریم. درست؟

### Asynchronous Module Definition (AMD)

گونه دیگر روی شکل ماژول کلاسیک ماژول‌های سبک AMD است (چند سال پیش محبوب)، مثل آن‌هایی که توسط ابزار RequireJS پشتیبانی می‌شوند:

```js
define([ "./Student" ],function StudentList(Student){
    var elems = [];

    return {
        renderList() {
            // ..
        }
    };
});
```

اگر به `StudentList(..)` دقیق نگاه کنید، تابع کارخانه ماژول کلاسیک است. داخل ماشین‌آلات `define(..)` (ارائه‌شده توسط RequireJS)، تابع `StudentList(..)` اجرا می‌شود و نمونه‌های ماژول دیگر اعلان‌شده به عنوان وابستگی به آن فرستاده می‌شوند. مقدار برگشتی objectی است که API عمومی ماژول را نشان می‌دهد.

این بر اساس دقیقاً همان اصول (از جمله نحوه کار closure!) است که با ماژول‌های کلاسیک کاوش کردیم.

### ماژول‌های Universal (UMD)

گونه نهایی که می‌بینیم UMD است که کمتر یک فرمت خاص و دقیق و بیشتر مجموعه‌ای از فرمت‌های بسیار مشابه است. برای ایجاد interop بهتر (بدون تبدیل build-tool) برای ماژول‌هایی طراحی شد که ممکن است در مرورگرها، توسط loaderهای سبک AMD، یا در Node بارگذاری شوند. شخصاً هنوز بسیاری کتابخانه‌های ابزاریام را با شکلی از UMD منتشر می‌کنم.

ساختار معمول UMD:

```js
(function UMD(name,context,definition){
    // loaded by an AMD-style loader?
    if (
        typeof define === "function" &&
        define.amd
    ) {
        define(definition);
    }
    // in Node?
    else if (
        typeof module !== "undefined" &&
        module.exports
    ) {
        module.exports = definition(name,context);
    }
    // assume standalone browser script
    else {
        context[name] = definition(name,context);
    }
})("StudentList",this,function DEF(name,context){

    var elems = [];

    return {
        renderList() {
            // ..
        }
    };

});
```

هرچند ممکن است کمی غیرمعمول به نظر برسد، UMD واقعاً فقط یک IIFE است.

تفاوت این است که بخش اصلی function expression (در بالا) IIFE شامل سری statementهای `if..else if` برای تشخیص کدام یک از سه محیط پشتیبانی‌شده ماژول در آن بارگذاری می‌شود.

`()` نهایی که معمولاً IIFE را فراخوانی می‌کند سه آرگومان فرستاده می‌شود: `"StudentsList"`، `this` و function expression دیگر. اگر آن آرگومان‌ها را با پارامترهایشان مطابقت دهید، می‌بینید به ترتیب هستند: `name`، `context` و `definition`. `"StudentList"` (`name`) برچسب نام برای ماژول است، عمدتاً در صورت تعریف به عنوان متغیر سراسری. `this` (`context`) عموماً `window` (یعنی global object؛ فصل ۴ را ببینید) برای تعریف ماژول با نامش است.

`definition(..)` برای بازیابی واقعی تعریف ماژول فراخوانی می‌شود و متوجه می‌شوید که، بله، آن فقط شکل ماژول کلاسیک است!

شکی نیست که در زمان نوشتن، ESM (ES Modules) به سرعت محبوب و گسترده می‌شوند. اما با میلیون‌ها ماژول نوشته‌شده در ۲۰ سال گذشته، همه با گونه‌ای از ماژول‌های کلاسیک pre-ESM، هنوز خیلی مهمند که وقتی برخورد می‌کنید بتوانید بخوانید و بفهمید.
