# TDZ چه مشکلی دارد؟

TDZ (temporal dead zone) در فصل ۵ توضیح داده شد. نحوه وقوعش را نشان دادیم، اما از توضیح *چرا* در اصل لازم بود معرفی شود گذشتیم. بیایید به طور خلاصه انگیزه‌های TDZ را ببینیم.

برخی breadcrumbها در داستان منشأ TDZ:

* `const`ها هرگز نباید تغییر کنند
* همه چیز درباره زمان است
* آیا `let` باید بیشتر مثل `const` یا `var` رفتار کند؟

### از کجا شروع شد

TDZ در واقع از `const` می‌آید.

در طول کار توسعه اولیه ES6، TC39 باید تصمیم می‌گرفت آیا `const` (و `let`) به بالای بلوک‌هایشان hoist می‌شوند. تصمیم گرفتند این اعلان‌ها hoist شوند، مشابه `var`. اگر اینطور نبود، فکر می‌کنم بخشی از ترس سردرگمی با shadowing وسط scope بود، مثل:

```js
let greeting = "Hi!";

{
    // what should print here?
    console.log(greeting);

    // .. a bunch of lines of code ..

    // now shadowing the `greeting` variable
    let greeting = "Hello, friends!";

    // ..
}
```

با آن statement `console.log(..)` چه کنیم؟ آیا برای devهای JS معنا داشت «Hi!» چاپ کند؟ به نظر می‌رسد می‌تواند gotcha باشد که shadowing فقط برای نیمه دوم بلوک اعمال شود، نه نیمه اول. رفتار بسیار شهودی و JS-like نیست. پس `let` و `const` باید به بالای بلوک hoist شوند، در سراسر قابل مشاهده.

اما اگر `let` و `const` به بالای بلوک hoist شوند (مثل hoist شدن `var` به بالای تابع)، چرا `let` و `const` مقداردهی اولیه خودکار (به `undefined`) مثل `var` نمی‌کنند؟ این نگرانی اصلی بود:

```js
{
    // what should print here?
    console.log(studentName);

    // later

    const studentName = "Frank";

    // ..
}
```

تصور کنیم `studentName` نه فقط به بالای این بلوک hoist شد، بلکه به `undefined` هم مقداردهی اولیه خودکار شد. برای نیمه اول بلوک، `studentName` می‌توانست با مقدار `undefined` مشاهده شود، مثل statement `console.log(..)` ما. وقتی به statement `const studentName = ..` رسیدیم، حالا `studentName` مقدار `"Frank"` انتساب داده شد. از آن نقطه به بعد، `studentName` هرگز نمی‌تواند انتساب مجدد شود.

اما آیا عجیب یا غافل‌گیرکننده است که یک ثابت به طور قابل مشاهده دو مقدار مختلف دارد، اول `undefined`، بعد `"Frank"`؟ به نظر می‌رسد بر خلاف آنچه فکر می‌کنیم یک `const`ant یعنی؛ فقط باید با یک مقدار قابل مشاهده باشد.

پس... الان مشکل داریم. نمی‌توانیم `studentName` را به `undefined` (یا هر مقدار دیگر) مقداردهی اولیه خودکار کنیم. اما متغیر باید در کل scope وجود داشته باشد. با دوره زمانی از وقتی اولین بار وجود دارد (ابتدای scope) تا وقتی مقدارش انتساب می‌شود چه کنیم؟

این دوره زمانی را «منطقه مرده» می‌نامیم، یعنی «temporal dead zone» (TDZ). برای جلوگیری از سردرگمی، تعیین شد که هر نوع دسترسی به متغیر در حین TDZ غیرقانونی است و باید به خطای TDZ منجر شود.

خوب، آن خط استدلال معنا می‌دهد، باید اعتراف کنم.

### چه کسی TDZ را برای `let` بیرون داد؟

اما آن فقط `const` بود. `let` چطور؟

خوب، TC39 تصمیم گرفت: چون به TDZ برای `var` نیاز داریم، بهتر است برای `let` هم TDZ داشته باشیم. *در واقع، اگر برای let TDZ بگذاریم، آن variable hoisting زشت مردم را دلسرد می‌کنیم.* پس دیدگاه یکنواختی بود و شاید کمی مهندسی اجتماعی برای تغییر رفتار توسعه‌دهندگان.

استدلال متقابل من این است: اگر به یکنواختی favor می‌دهید، با `var` به جای `const` یکنواخت باشید؛ `let` قطعاً بیشتر شبیه `var` است تا `const`. به‌ویژه چون قبلاً برای کل موضوع hoist-به-بالای-scope با `var` یکنواختی انتخاب کرده بودند. بگذارید `const` deal منحصربه‌فرد خودش را با TDZ داشته باشد، و جواب TDZ purely این باشد: فقط با همیشه اعلان ثابت‌هایتان در بالای scope از TDZ اجتناب کنید. فکر می‌کنم این معقول‌تر می‌بود.

اما افسوس، این‌طور نشد. `let` TDZ دارد چون `const` به TDZ نیاز دارد، چون `let` و `const` در hoist به بالای scope (بلوک) از `var` تقلید می‌کنند. همین. خیلی دایره‌ای؟ چند بار دوباره بخوانید.
