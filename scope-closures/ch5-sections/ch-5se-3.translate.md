# اعلان مجدد؟

فکر می‌کنید وقتی متغیری بیش از یک بار در همان scope اعلان می‌شود چه اتفاقی می‌افتد؟ در نظر بگیرید:

```js
var studentName = "Frank";
console.log(studentName);
// Frank

var studentName;
console.log(studentName);   // ???
```

انتظار دارید برای آن پیام دوم چه چاپ شود؟ بسیاری معتقدند دومین `var studentName` متغیر را اعلان مجدد کرده (و بنابراین آن را «reset» کرده)، پس انتظار چاپ `undefined` را دارند.

اما آیا چیزی به نام «اعلان مجدد» متغیر در همان scope وجود دارد؟ نه.

اگر این برنامه را از نظر استعارهٔ hoisting در نظر بگیرید، کد برای اهداف اجرا اینطور بازچینش می‌شد:

```js
var studentName;
var studentName;    // clearly a pointless no-op!

studentName = "Frank";
console.log(studentName);
// Frank

console.log(studentName);
// Frank
```

چون hoisting در واقع دربارهٔ ثبت متغیر در ابتدای scope است، در وسط scope جایی که برنامهٔ اصلی در واقع عبارت دوم `var studentName` را داشت کاری برای انجام نیست. فقط یک no-op(eration)، عبارت بی‌فایده است.

| TIP: |
| :--- |
| به سبک روایت گفتگو از فصل ۲، *Compiler* عبارت اعلان دوم `var` را پیدا می‌کرد و از *Scope Manager* می‌پرسید آیا قبلاً شناسهٔ `studentName` را دیده؛ چون دیده بود، کار دیگری نبود. |

همچنین مهم است اشاره کنیم که `var studentName;` به معنای `var studentName = undefined;` نیست، همانطور که اکثر فرض می‌کنند. بیایید با در نظر گرفتن این variant برنامه ثابت کنیم متفاوت هستند:

```js
var studentName = "Frank";
console.log(studentName);   // Frank

var studentName;
console.log(studentName);   // Frank <--- still!

// let's add the initialization explicitly
var studentName = undefined;
console.log(studentName);   // undefined <--- see!?
```

ببینید مقداردهی اولیهٔ صریح `= undefined` نتیجهٔ متفاوتی از فرض وقوع ضمنی هنگام حذف تولید می‌کند؟ در بخش بعد، این موضوع مقداردهی اولیهٔ متغیرها از اعلان‌هایشان را مرور می‌کنیم.

اعلان `var` تکراری همان نام شناسه در یک scope به‌طور مؤثر عملیات هیچ‌کاری نیست. تصویر دیگری، این بار در یک تابع با همان نام:

```js
var greeting;

function greeting() {
    console.log("Hello!");
}

// basically, a no-op
var greeting;

typeof greeting;        // "function"

var greeting = "Hello!";

typeof greeting;        // "string"
```

اولین اعلان `greeting` شناسه را در scope ثبت می‌کند، و چون `var` است مقداردهی اولیهٔ خودکار `undefined` خواهد بود. اعلان `function` نیازی به ثبت مجدد شناسه ندارد، اما به خاطر *function hoisting* مقداردهی اولیهٔ خودکار را override می‌کند تا از مرجع تابع استفاده کند. دومین `var greeting` به تنهایی کاری نمی‌کند چون `greeting` از قبل شناسه است و *function hoisting* از قبل برای مقداردهی اولیهٔ خودکار اولویت گرفت.

در واقع انتساب `"Hello!"` به `greeting` مقدارش را از تابع اولیهٔ `greeting()` به رشته تغییر می‌دهد؛ خود `var` هیچ تأثیری ندارد.

اعلان مجدد در یک scope با `let` یا `const` چطور؟

```js
let studentName = "Frank";

console.log(studentName);

let studentName = "Suzy";
```

این برنامه اجرا نمی‌شود، بلکه فوراً `SyntaxError` پرتاب می‌کند. بسته به محیط جاوااسکریپت شما، پیام خطا چیزی مثل این نشان می‌دهد: «studentName has already been declared.» به عبارت دیگر، این موردی است که «اعلان مجدد» تلاش‌شده صریحاً مجاز نیست!

فقط این نیست که دو اعلان شامل `let` این خطا را پرتاب می‌کنند. اگر هر اعلان از `let` استفاده کند، دیگری می‌تواند `let` یا `var` باشد، و خطا هنوز اتفاق می‌افتد، همانطور که با این دو variant نشان داده شد:

```js
var studentName = "Frank";

let studentName = "Suzy";
```

و:

```js
let studentName = "Frank";

var studentName = "Suzy";
```

در هر دو مورد، `SyntaxError` روی اعلان *دوم* پرتاب می‌شود. به عبارت دیگر، تنها راه «اعلان مجدد» متغیر استفاده از `var` برای تمام (دو یا بیشتر) اعلان‌هایش است.

اما چرا ممنوع است؟ دلیل خطا به خودی خود فنی نیست، چون «اعلان مجدد» `var` همیشه مجاز بوده؛ واضح است، همان اجازه می‌توانست برای `let` هم داده شود.

واقعاً بیشتر موضوع «مهندسی اجتماعی» است. «اعلان مجدد» متغیرها توسط برخی، از جمله بسیاری در بدنهٔ TC39، عادت بدی دیده می‌شود که می‌تواند منجر به باگ برنامه شود. پس وقتی ES6 `let` را معرفی کرد، تصمیم گرفتند «اعلان مجدد» را با خطا جلوگیری کنند.

| NOTE: |
| :--- |
| این البته نظر سبکی است، نه واقعاً استدلال فنی. بسیاری از توسعه‌دهندگان با این موضع موافقند، و احتمالاً بخشی از دلیل اینکه TC39 خطا را (و همچنین تطابق `let` با `const`) شامل شد همین است. اما می‌شد استدلال معقولی کرد که ثابت ماندن با سابقهٔ `var` محتاطانه‌تر بود، و چنین اعمال نظر بهترین کار به linterهای opt-in واگذار می‌شد. در پیوست الف، کاوش می‌کنیم آیا `var` (و رفتار مرتبطش، مثل «اعلان مجدد») هنوز در جاوااسکریپت مدرن مفید است. |

وقتی *Compiler* از *Scope Manager* دربارهٔ اعلان می‌پرسد، اگر آن شناسه از قبل اعلان شده، و اگر یک یا هر دو اعلان با `let` انجام شده باشد، خطا پرتاب می‌شود. سیگنال مورد نظر به توسعه‌دهنده «تکیه بر اعلان مجدد شل را متوقف کن!» است.

### ثابت‌ها؟

کلمهٔ کلیدی `const` محدودتر از `let` است. مثل `let`، `const` نمی‌تواند با همان شناسه در همان scope تکرار شود. اما در واقع دلیل فنی غالب وجود دارد که چرا آن نوع «اعلان مجدد» ممنوع است، برخلاف `let` که «اعلان مجدد» را عمدتاً به دلایل سبکی ممنوع می‌کند.

کلمهٔ کلیدی `const` نیاز دارد متغیر مقداردهی اولیه شود، پس حذف انتساب از اعلان منجر به `SyntaxError` می‌شود:

```js
const empty;   // SyntaxError
```

اعلان‌های `const` متغیرهایی ایجاد می‌کنند که نمی‌توان انتساب مجدد داد:

```js
const studentName = "Frank";
console.log(studentName);
// Frank

studentName = "Suzy";   // TypeError
```

متغیر `studentName` نمی‌تواند انتساب مجدد شود چون با `const` اعلان شده است.

| WARNING: |
| :--- |
| خطای پرتاب‌شده هنگام انتساب مجدد `studentName` `TypeError` است، نه `SyntaxError`. تمایز ظریف اینجا در واقع خیلی مهم است، اما متأسفانه خیلی راحت از دست می‌رود. خطاهای نحو نقص‌های برنامه را نشان می‌دهند که حتی از شروع اجرا جلوگیری می‌کنند. خطاهای نوع نقص‌هایی را نشان می‌دهند که در حین اجرای برنامه به وجود می‌آیند. در قطعهٔ قبلی، `"Frank"` قبل از پردازش انتساب مجدد `studentName` چاپ می‌شود، که سپس خطا پرتاب می‌کند. |

پس اگر اعلان‌های `const` نمی‌توانند انتساب مجدد شوند، و اعلان‌های `const` همیشه نیاز به انتساب دارند، پس دلیل فنی واضحی داریم که چرا `const` باید هر «اعلان مجدد» را ممنوع کند: هر «اعلان مجدد» `const` لزوماً انتساب مجدد `const` هم خواهد بود، که نمی‌توان مجاز کرد!

```js
const studentName = "Frank";

// obviously this must be an error
const studentName = "Suzy";
```

چون «اعلان مجدد» `const` باید ممنوع شود (بر آن مبانی فنی)، TC39 اساساً احساس کرد «اعلان مجدد» `let` هم باید ممنوع شود، برای یکنواختی. قابل بحث است اگر این بهترین انتخاب بود، اما حداقل استدلال پشت تصمیم را داریم.

### حلقه‌ها

پس از بحث قبلی واضح است که جاوااسکریپت واقعاً نمی‌خواهد متغیرهایمان را در همان scope «اعلان مجدد» کنیم. احتمالاً نصیحت ساده‌ای به نظر می‌رسد، تا زمانی که در نظر بگیرید برای اجرای تکراری عبارت‌های اعلان در حلقه‌ها چه معنایی دارد. در نظر بگیرید:

```js
var keepGoing = true;
while (keepGoing) {
    let value = Math.random();
    if (value > 0.5) {
        keepGoing = false;
    }
}
```

آیا `value` به‌طور مکرر در این برنامه «اعلان مجدد» می‌شود؟ آیا خطا پرتاب می‌شود؟ نه.

تمام قوانین scope (از جمله «اعلان مجدد» متغیرهای ایجادشده با `let`) *به ازای هر نمونه scope* اعمال می‌شوند. به عبارت دیگر، هر بار که scope در حین اجرا وارد می‌شود، همه چیز reset می‌شود.

هر تکرار حلقه نمونهٔ scope جدید خودش است، و در هر نمونه scope، `value` فقط یک بار اعلان می‌شود. پس «اعلان مجدد» تلاش‌شده‌ای نیست، و بنابراین خطایی نیست. قبل از در نظر گرفتن اشکال دیگر حلقه، اگر اعلان `value` در قطعهٔ قبلی به `var` تغییر می‌کرد چه؟

```js
var keepGoing = true;
while (keepGoing) {
    var value = Math.random();
    if (value > 0.5) {
        keepGoing = false;
    }
}
```

آیا `value` اینجا «اعلان مجدد» می‌شود، به‌خصوص چون می‌دانیم `var` اجازه می‌دهد؟ نه. چون `var` به‌عنوان اعلان block-scoping تلقی نمی‌شود (فصل ۶ را ببینید)، خود را به scope سراسری متصل می‌کند. پس فقط یک متغیر `value` وجود دارد، در همان scope با `keepGoing` (scope سراسری، در این مورد). «اعلان مجدد» اینجا هم نیست!

یک راه برای نگه داشتن همهٔ این‌ها درست به یاد آوردن این است که کلمات کلیدی `var`، `let` و `const` به‌طور مؤثر تا زمان شروع اجرا *حذف* می‌شوند. آن‌ها کاملاً توسط کامپایلر مدیریت می‌شوند.

اگر ذهنی کلمات کلیدی declarator را پاک کنید و سپس سعی کنید کد را پردازش کنید، باید به شما کمک کند تصمیم بگیرید آیا و چه زمانی (اعلان) مجدد ممکن است اتفاق بیفتد.

«اعلان مجدد» با اشکال دیگر حلقه، مثل حلقه‌های `for` چطور؟

```js
for (let i = 0; i < 3; i++) {
    let value = i * 10;
    console.log(`${ i }: ${ value }`);
}
// 0: 0
// 1: 10
// 2: 20
```

باید واضح باشد که فقط یک `value` به ازای هر نمونه scope اعلان می‌شود. اما `i` چطور؟ آیا «اعلان مجدد» می‌شود؟

برای پاسخ، scope `i` را در نظر بگیرید. ممکن است به نظر برسد در scope بیرونی (در این مورد، سراسری) باشد، اما نیست. در scope بدنهٔ حلقهٔ `for` است، دقیقاً مثل `value`. در واقع، می‌توانستید آن حلقه را در این شکل معادل پرحرف‌تر فکر کنید:

```js
{
    // a fictional variable for illustration
    let $$i = 0;

    for ( /* nothing */; $$i < 3; $$i++) {
        // here's our actual loop `i`!
        let i = $$i;

        let value = i * 10;
        console.log(`${ i }: ${ value }`);
    }
    // 0: 0
    // 1: 10
    // 2: 20
}
```

اکنون باید واضح باشد: متغیرهای `i` و `value` هر دو دقیقاً یک بار **به ازای هر نمونه scope** اعلان می‌شوند. «اعلان مجدد» اینجا نیست.

اشکال دیگر حلقهٔ `for` چطور؟

```js
for (let index in students) {
    // this is fine
}

for (let student of students) {
    // so is this
}
```

همین با حلقه‌های `for..in` و `for..of`: متغیر اعلان‌شده به‌عنوان *داخل* بدنهٔ حلقه تلقی می‌شود، و بنابراین به ازای هر تکرار (یعنی هر نمونه scope) مدیریت می‌شود. «اعلان مجدد» نیست.

خوب، می‌دانم در این مرحله مثل صفحهٔ شکسته به نظر می‌رسم. اما بیایید ببینیم `const` چگونه این ساختارهای حلقه را تحت تأثیر قرار می‌دهد. در نظر بگیرید:

```js
var keepGoing = true;
while (keepGoing) {
    // ooo, a shiny constant!
    const value = Math.random();
    if (value > 0.5) {
        keepGoing = false;
    }
}
```

دقیقاً مثل variant `let` این برنامه که قبلاً دیدیم، `const` دقیقاً یک بار در هر تکرار حلقه اجرا می‌شود، پس از مشکلات «اعلان مجدد» امن است. اما وقتی دربارهٔ حلقه‌های `for` حرف می‌زنیم چیزها پیچیده‌تر می‌شوند.

`for..in` و `for..of` با `const` خوب هستند:

```js
for (const index in students) {
    // this is fine
}

for (const student of students) {
    // this is also fine
}
```

اما حلقهٔ `for` عمومی نه:

```js
for (const i = 0; i < 3; i++) {
    // oops, this is going to fail with
    // a Type Error after the first iteration
}
```

اینجا چه اشکالی است؟ می‌توانستیم `let` را در این ساختار خوب استفاده کنیم، و ادعا کردیم که برای هر scope تکرار حلقه `i` جدید ایجاد می‌کند، پس حتی به نظر «اعلان مجدد» هم نمی‌رسد.

بیایید ذهنی آن حلقه را مثل قبل «بسط» دهیم:

```js
{
    // a fictional variable for illustration
    const $$i = 0;

    for ( ; $$i < 3; $$i++) {
        // here's our actual loop `i`!
        const i = $$i;
        // ..
    }
}
```

مشکل را می‌بینید؟ `i` ما در واقع فقط یک بار داخل حلقه ایجاد می‌شود. مشکل آن نیست. مشکل `$$i` مفهومی است که هر بار باید با عبارت `$$i++` افزایش یابد. آن **انتساب مجدد** است (نه «اعلان مجدد»)، که برای ثابت‌ها مجاز نیست.

به یاد داشته باشید، این شکل «بسط‌شده» فقط یک مدل مفهومی برای کمک به شهود منبع مشکل است. ممکن است تعجب کنید آیا جاوااسکریپت می‌توانست به‌طور مؤثر `const $$i = 0` را به `let $ii = 0` تبدیل کند، که آنگاه اجازه می‌داد `const` با حلقهٔ `for` کلاسیک ما کار کند؟ ممکن است، اما آنگاه می‌توانست استثناهای احتمالاً تعجب‌آور به معناشناسی حلقهٔ `for` معرفی کند.

مثلاً، استثنای ظریف نسبتاً دلخواه (و احتمالاً گیج‌کننده) می‌بود که اجازه دهد `i++` در هدر حلقهٔ `for` از سخت‌گیری انتساب `const` فرار کند، اما انتساب‌های مجدد دیگر `i` داخل تکرار حلقه را مجاز نکند، همانطور که گاهی مفید است.

پاسخ ساده این است: `const` نمی‌تواند با شکل کلاسیک حلقهٔ `for` استفاده شود به خاطر انتساب مجدد الزامی.

جالبی اینکه، اگر انتساب مجدد نکنید، آنگاه معتبر است:

```js
var keepGoing = true;

for (const i = 0; keepGoing; /* nothing here */ ) {
    keepGoing = (Math.random() > 0.5);
    // ..
}
```

این کار می‌کند، اما بی‌فایده است. دلیلی برای اعلان `i` در آن موقعیت با `const` نیست، چون کل هدف چنین متغیری در آن موقعیت **استفاده برای شمارش تکرارها** است. فقط از شکل حلقهٔ متفاوت استفاده کنید، مثل حلقهٔ `while`، یا از `let`!
