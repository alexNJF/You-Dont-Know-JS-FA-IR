# متغیرهای مقداردهی‌نشده (یعنی TDZ)

با اعلان‌های `var`، متغیر به بالای scopeاش «hoist» می‌شود. اما همچنین به‌طور خودکار به مقدار `undefined` مقداردهی اولیه می‌شود، تا متغیر در کل scope قابل استفاده باشد.

با این حال، اعلان‌های `let` و `const` در این respect کاملاً یکسان نیستند.

در نظر بگیرید:

```js
console.log(studentName);
// ReferenceError

let studentName = "Suzy";
```

نتیجهٔ این برنامه این است که `ReferenceError` در خط اول پرتاب می‌شود. بسته به محیط جاوااسکریپت شما، پیام خطا ممکن است چیزی مثل این بگوید: «Cannot access studentName before initialization.»

| NOTE: |
| :--- |
| پیام خطا همانطور که اینجا دیده می‌شود قبلاً خیلی مبهم یا گمراه‌کننده بود. خوشبختانه، چند نفر از ما در جامعه با موفقیت توانستیم برای بهبود این پیام خطا توسط موتورهای جاوااسکریپت لابی کنیم تا دقیق‌تر به شما بگوید چه اشکالی است! |

آن پیام خطا کاملاً نشان‌دهندهٔ اشکال است: `studentName` در خط ۱ وجود دارد، اما مقداردهی اولیه نشده، پس هنوز نمی‌تواند استفاده شود. بیایید این را امتحان کنیم:

```js
studentName = "Suzy";   // let's try to initialize it!
// ReferenceError

console.log(studentName);

let studentName;
```

اوه. هنوز `ReferenceError` می‌گیریم، اما این بار در خط اول که داریم سعی می‌کنیم به این متغیر «مقداردهی‌نشده» به اصطلاح `studentName` انتساب دهیم (یعنی مقداردهی اولیه!). چه خبر!

سوال واقعی این است، چطور متغیر مقداردهی‌نشده را مقداردهی اولیه می‌کنیم؟ برای `let`/`const`، **تنها راه** استفاده از انتسابی است که به عبارت اعلان متصل است. انتساب به تنهایی کافی نیست! در نظر بگیرید:

```js
let studentName = "Suzy";
console.log(studentName);   // Suzy
```

اینجا، `studentName` را (در این مورد، به `"Suzy"` به‌جای `undefined`) از طریق شکل عبارت اعلان `let` که با انتساب جفت شده مقداردهی اولیه می‌کنیم.

یا:

```js
// ..

let studentName;
// or:
// let studentName = undefined;

// ..

studentName = "Suzy";

console.log(studentName);
// Suzy
```

| NOTE: |
| :--- |
| جذاب است! از قبل به یاد آورید، گفتیم `var studentName;` *همان* `var studentName = undefined;` نیست، اما اینجا با `let`، یکسان رفتار می‌کنند. تفاوت به این واقعیت برمی‌گردد که `var studentName` به‌طور خودکار در بالای scope مقداردهی اولیه می‌شود، جایی که `let studentName` نمی‌کند. |

به یاد داشته باشید که چند بار ادعا کردیم *Compiler* در نهایت هر declarator `var`/`let`/`const` را حذف می‌کند، آن‌ها را با دستورالعمل‌های بالای هر scope برای ثبت شناسه‌های مناسب جایگزین می‌کند.

پس اگر تحلیل کنیم اینجا چه اتفاقی می‌افتد، می‌بینیم که ظرافت اضافی این است که *Compiler* همچنین دستورالعملی در وسط برنامه، در نقطهٔ اعلان متغیر `studentName`، اضافه می‌کند تا مقداردهی اولیهٔ خودکار آن اعلان را مدیریت کند. نمی‌توانیم متغیر را در هیچ نقطه‌ای قبل از وقوع آن مقداردهی اولیه استفاده کنیم. همین برای `const` مثل `let` است.

اصطلاح ابداع‌شده توسط TC39 برای اشاره به این *دورهٔ زمانی* از ورود به scope تا جایی که مقداردهی اولیهٔ خودکار متغیر اتفاق می‌افتد: Temporal Dead Zone (TDZ).

TDZ پنجرهٔ زمانی است که متغیر وجود دارد اما هنوز مقداردهی اولیه نشده، و بنابراین به هیچ شکلی قابل دسترسی نیست. فقط اجرای دستورالعمل‌های باقی‌مانده توسط *Compiler* در نقطهٔ اعلان اصلی می‌تواند آن مقداردهی اولیه را انجام دهد. بعد از آن لحظه، TDZ تمام می‌شود، و متغیر برای بقیهٔ scope آزاد است استفاده شود.

یک `var` از نظر فنی TDZ هم دارد، اما طولش صفر است و بنابراین برای برنامه‌هایمان قابل مشاهده نیست! فقط `let` و `const` TDZ قابل مشاهده دارند.

به هر حال، «temporal» در TDZ واقعاً به *زمان* اشاره دارد نه *موقعیت در کد*. در نظر بگیرید:

```js
askQuestion();
// ReferenceError

let studentName = "Suzy";

function askQuestion() {
    console.log(`${ studentName }, do you know?`);
}
```

حتی با اینکه از نظر موقعیتی `console.log(..)` ارجاع‌دهنده به `studentName` *بعد از* اعلان `let studentName` می‌آید، از نظر زمان‌بندی تابع `askQuestion()` *قبل از* برخورد عبارت `let` فراخوانی می‌شود، در حالی که `studentName` هنوز در TDZاش است! از این رو خطا.

یک تصور غلط رایج این است که TDZ یعنی `let` و `const` hoist نمی‌شوند. این ادعای نادقیق، یا حداقل کمی گمراه‌کننده است. قطعاً hoist می‌شوند.

تفاوت واقعی این است که اعلان‌های `let`/`const` به‌طور خودکار در ابتدای scope مقداردهی اولیه نمی‌شوند، همانطور که `var` می‌کند. *بحث* آنگاه این است که آیا مقداردهی اولیهٔ خودکار *بخشی از* hoisting است یا نه؟ فکر می‌کنم ثبت خودکار متغیر در بالای scope (یعنی آنچه «hoisting» می‌نامم) و مقداردهی اولیهٔ خودکار در بالای scope (به `undefined`) عملیات‌های مجزا هستند و نباید تحت اصطلاح واحد «hoisting» lump شوند.

قبلاً دیدیم که `let` و `const` در بالای scope مقداردهی اولیهٔ خودکار نمی‌شوند. اما بیایید ثابت کنیم که `let` و `const` *do* hoist می‌کنند (ثبت خودکار در بالای scope)، به لطف دوستمان shadowing («Shadowing» در فصل ۳ را ببینید):

```js
var studentName = "Kyle";

{
    console.log(studentName);
    // ???

    // ..

    let studentName = "Suzy";

    console.log(studentName);
    // Suzy
}
```

با اولین عبارت `console.log(..)` چه اتفاقی می‌افتد؟ اگر `let studentName` به بالای scope hoist نمی‌شد، آنگاه اولین `console.log(..)` *باید* `"Kyle"` چاپ می‌کرد، درست؟ در آن لحظه، به نظر می‌رسید، فقط `studentName` بیرونی وجود دارد، پس آن متغیری است که `console.log(..)` باید دسترسی یابد و چاپ کند.

اما در عوض، اولین `console.log(..)` خطای TDZ پرتاب می‌کند، چون در واقع، `studentName` scope داخلی **hoist شده بود** (ثبت خودکار در بالای scope). آنچه **اتفاق نیفتاد** (هنوز!) مقداردهی اولیهٔ خودکار آن `studentName` داخلی بود؛ در آن لحظه هنوز مقداردهی اولیه نشده، از این رو نقض TDZ!

پس برای خلاصه، خطاهای TDZ اتفاق می‌افتند چون اعلان‌های `let`/`const` *do* اعلان‌هایشان را به بالای scopeهایشان hoist می‌کنند، اما برخلاف `var`، مقداردهی اولیهٔ خودکار متغیرهایشان را تا لحظهٔ در ترتیب کد که اعلان اصلی ظاهر شد به تعویق می‌اندازند. این پنجرهٔ زمانی (نکته: temporal)، هر طولی که باشد، TDZ است.

چطور می‌توانید از خطاهای TDZ اجتناب کنید؟

توصیهٔ من: همیشه اعلان‌های `let` و `const` را در بالای هر scope قرار دهید. پنجرهٔ TDZ را به طول صفر (یا نزدیک صفر) کوچک کنید، و آنگاه بی‌اهمیت می‌شود.

اما چرا TDZ اصلاً وجود دارد؟ چرا TC39 دستور نداد که `let`/`const` مثل `var` مقداردهی اولیهٔ خودکار کنند؟ صبور باشید، در پیوست الف با جزئیات بیشتر به *چرا* TDZ برمی‌گردیم.
