# Values as Types

در JavaScript، متغیرها type ندارند — **مقادیر type دارند**. متغیرها می‌توانند در هر زمان هر مقداری را نگه دارند.

نگاه دیگر به typeهای JS این است که JS «type enforcement» ندارد؛ یعنی موتور اصرار نمی‌کند که یک *متغیر* همیشه مقادیر *همان type اولیه*ای را نگه دارد که با آن شروع کرده. یک متغیر می‌تواند در یک عبارت انتساب `string` داشته باشد و در عبارت بعدی `number`، و غیره.

*مقدار* `42` یک type ذاتی به‌نام `number` دارد و *type* آن قابل تغییر نیست. مقدار دیگر، مثل `"42"` با type `string`، می‌تواند *از* مقدار `number` یعنی `42` از طریق فرایندی به نام **coercion** ساخته شود (فصل ۴ را ببینید).

اگر `typeof` را روی یک متغیر به کار ببرید، این نیست که بپرسد «type متغیر چیست؟» آن‌طور که به نظر می‌رسد، چون متغیرهای JS type ندارند. بلکه می‌پرسد «type مقدار *داخل* متغیر چیست؟»

```js
var a = 42;
typeof a; // "number"

a = true;
typeof a; // "boolean"
```

عملگر `typeof` همیشه یک رشته برمی‌گرداند. پس:

```js
typeof typeof 42; // "string"
```

اولین `typeof 42` مقدار `"number"` را برمی‌گرداند، و `typeof "number"` برابر است با `"string"`.

### `undefined` در مقابل «undeclared»

متغیرهایی که *در حال حاضر* مقداری ندارند، در واقع مقدار `undefined` را دارند. فراخوانی `typeof` روی چنین متغیرهایی `"undefined"` برمی‌گرداند:

```js
var a;

typeof a; // "undefined"

var b = 42;
var c;

// later
b = c;

typeof b; // "undefined"
typeof c; // "undefined"
```

برای بیشتر توسعه‌دهندگان وسوسه‌انگیز است که «undefined» را مترادف «undeclared» بدانند. اما در JS این دو مفهوم کاملاً متفاوت‌اند.

یک متغیر «undefined» متغیری است که در scope در دسترس اعلان شده اما *در این لحظه* مقدار دیگری در آن نیست. در مقابل، یک متغیر «undeclared» متغیری است که به‌طور رسمی در scope در دسترس اعلان نشده است.

در نظر بگیرید:

```js
var a;

a; // undefined
b; // ReferenceError: b is not defined
```

پیام خطایی که مرورگرها به این وضعیت می‌دهند گیج‌کننده است. همان‌طور که می‌بینید، پیام «b is not defined» است که البته به‌راحتی و به‌حق با «b is undefined» اشتباه گرفته می‌شود. باز هم «undefined» و «is not defined» دو چیز خیلی متفاوت‌اند. خوب بود اگر مرورگرها چیزی مثل «b is not found» یا «b is not declared» می‌گفتند تا کمتر گیج شود!

همچنین رفتار خاصی برای `typeof` در رابطه با متغیرهای undeclared وجود دارد که این گیجی را بیشتر می‌کند. در نظر بگیرید:

```js
var a;

typeof a; // "undefined"

typeof b; // "undefined"
```

عملگر `typeof` حتی برای متغیرهای «undeclared» (یا «not defined») هم `"undefined"` برمی‌گرداند. توجه کنید که وقتی `typeof b` را اجرا کردیم خطایی پرتاب نشد، با وجود اینکه `b` متغیر undeclared است. این یک safety guard خاص در رفتار `typeof` است.

مشابه بالا، خوب بود اگر `typeof` در مورد متغیر undeclared به‌جای یکی کردن مقدار نتیجه با حالت متفاوت «undefined»، مقدار "undeclared" برمی‌گرداند.

### `typeof` و Undeclared

با این حال، این safety guard هنگام کار با JavaScript در مرورگر، جایی که چند فایل اسکریپت می‌توانند متغیرها را در فضای نام سراسری مشترک بار کنند، ویژگی سودمندی است.

**توجه:** بسیاری از توسعه‌دهندگان معتقدند نباید هیچ متغیری در فضای نام سراسری باشد و همه چیز باید در ماژول‌ها و فضای نام‌های خصوصی/جدا قرار گیرد. از نظر تئوری عالی است اما در عمل تقریباً غیرممکن است؛ با این حال هدف خوبی برای تلاش است! خوشبختانه ES6 پشتیبانی درجهٔ اول از ماژول‌ها را اضافه کرد که در نهایت این را خیلی عملی‌تر می‌کند.

به‌عنوان مثال ساده، تصور کنید در برنامه‌تان یک «حالت اشکال‌زدایی» دارید که با یک متغیر سراسری (پرچم) به‌نام `DEBUG` کنترل می‌شود. می‌خواهید قبل از انجام کاری مثل لاگ کردن پیام در کنسول بررسی کنید که آن متغیر اعلان شده باشد. اعلان سراسری سطح بالا `var DEBUG = true` فقط در فایل «debug.js» قرار می‌گیرد که فقط وقتی در حالت توسعه/تست هستید در مرورگر بار می‌کنید، نه در production.

اما باید در نحوهٔ بررسی متغیر سراسری `DEBUG` در بقیهٔ کد برنامه دقت کنید تا `ReferenceError` پرتاب نکنید. در این مورد safety guard روی `typeof` دوست ماست.

```js
// oops, this would throw an error!
if (DEBUG) {
	console.log( "Debugging is starting" );
}

// this is a safe existence check
if (typeof DEBUG !== "undefined") {
	console.log( "Debugging is starting" );
}
```

این نوع بررسی حتی وقتی با متغیرهای تعریف‌شده توسط کاربر (مثل `DEBUG`) سروکار ندارید هم سودمند است. اگر برای یک API از پیش‌تعریف‌شده بررسی ویژگی می‌کنید، بررسی بدون پرتاب خطا هم می‌تواند کمک‌کننده باشد:

```js
if (typeof atob === "undefined") {
	atob = function() { /*..*/ };
}
```

**توجه:** اگر برای ویژگیی که هنوز وجود ندارد «polyfill» تعریف می‌کنید، احتمالاً بهتر است از `var` برای اعلان `atob` استفاده نکنید. اگر داخل دستور `if` بنویسید `var atob`، این اعلان (به *Scope & Closures* این مجموعه مراجعه کنید) به بالای scope منتقل (hoisted) می‌شود، حتی اگر شرط `if` برقرار نباشد (چون `atob` سراسری از قبل وجود دارد!). در بعضی مرورگرها و برای بعضی نوع‌های خاص متغیرهای سراسری built-in (که اغلب «host objects» نامیده می‌شوند)، این اعلان تکراری ممکن است خطا پرتاب کند. حذف `var` از این اعلان منتقل‌شده جلوگیری می‌کند.

روش دیگر برای این بررسی‌ها روی متغیرهای سراسری بدون استفاده از قابلیت safety guard در `typeof` این است که توجه کنیم همهٔ متغیرهای سراسری propertyهای شیء سراسری هم هستند، که در مرورگر اساساً شیء `window` است. پس بررسی‌های بالا می‌توانستند (به‌طور کاملاً امن) این‌طور انجام شوند:

```js
if (window.DEBUG) {
	// ..
}

if (!window.atob) {
	// ..
}
```

برخلاف ارجاع به متغیرهای undeclared، اگر به property یک شیء (حتی روی شیء سراسری `window`) که وجود ندارد دسترسی بجویید، `ReferenceError` پرتاب نمی‌شود.

از طرف دیگر، ارجاع دستی به متغیر سراسری با ارجاع `window` چیزی است که بعضی توسعه‌دهندگان ترجیح می‌دهند از آن پرهیز کنند، به‌ویژه اگر کدتان باید در چند محیط JS (نه فقط مرورگر، بلکه مثلاً node.js سمت سرور) اجرا شود، جایی که شیء سراسری ممکن است همیشه `window` نامیده نشود.

از نظر فنی، این safety guard روی `typeof` حتی وقتی از متغیرهای سراسری استفاده نمی‌کنید هم سودمند است، هرچند این شرایط کمتر رایج است و بعضی توسعه‌دهندگان ممکن است این رویکرد طراحی را کمتر مطلوب بدانند. تصور کنید یک تابع کمکی دارید که می‌خواهید دیگران در برنامه یا ماژول‌هایشان کپی-پیست کنند، و می‌خواهید بررسی کنید برنامهٔ شامل آیا متغیر معینی را تعریف کرده (تا بتوانید استفاده کنید) یا نه:

```js
function doSomethingCool() {
	var helper =
		(typeof FeatureXYZ !== "undefined") ?
		FeatureXYZ :
		function() { /*.. default feature ..*/ };

	var val = helper();
	// ..
}
```

`doSomethingCool()` متغیری به‌نام `FeatureXYZ` را بررسی می‌کند و اگر پیدا شد از آن استفاده می‌کند، وگرنه از خودش. حالا اگر کسی این کمکی را در ماژول/برنامه‌اش قرار دهد، به‌طور امن بررسی می‌شود که آیا `FeatureXYZ` را تعریف کرده یا نه:

```js
// an IIFE (see "Immediately Invoked Function Expressions"
// discussion in the *Scope & Closures* title of this series)
(function(){
	function FeatureXYZ() { /*.. my XYZ feature ..*/ }

	// include `doSomethingCool(..)`
	function doSomethingCool() {
		var helper =
			(typeof FeatureXYZ !== "undefined") ?
			FeatureXYZ :
			function() { /*.. default feature ..*/ };

		var val = helper();
		// ..
	}

	doSomethingCool();
})();
```

اینجا `FeatureXYZ` اصلاً متغیر سراسری نیست، اما هنوز از safety guard مربوط به `typeof` استفاده می‌کنیم تا بررسی را امن کنیم. و مهم این که اینجا *هیچ* شیءی برای بررسی نداریم (مثل `window.___` برای متغیرهای سراسری)، پس `typeof` خیلی کمک‌کننده است.

توسعه‌دهندگان دیگر الگوی طراحی به‌نام «dependency injection» را ترجیح می‌دهند؛ به‌جای اینکه `doSomethingCool()` به‌طور ضمنی بررسی کند که `FeatureXYZ` بیرون/اطراف آن تعریف شده باشد، وابستگی باید صریحاً به آن پاس داده شود، مثلاً:

```js
function doSomethingCool(FeatureXYZ) {
	var helper = FeatureXYZ ||
		function() { /*.. default feature ..*/ };

	var val = helper();
	// ..
}
```

برای طراحی چنین قابلیتی گزینه‌های زیادی وجود دارد. هیچ الگویی اینجا «درست» یا «غلط» نیست — هر رویکرد معاوضه‌های خودش را دارد. اما در کل خوب است که safety guard مربوط به undeclared در `typeof` گزینه‌های بیشتری به ما می‌دهد.
