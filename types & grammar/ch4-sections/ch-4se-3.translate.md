# Explicit Coercion

*Explicit* coercion به تبدیل‌های type اشاره دارد که واضح و صریح هستند. طیف گسترده‌ای از کاربرد تبدیل type وجود دارد که برای بیشتر توسعه‌دهندگان به‌وضوح در دستهٔ *explicit* coercion قرار می‌گیرد.

هدف اینجا شناسایی الگوها در کدمان است که بتوانیم واضح و روشن کنیم داریم مقدار را از یک type به type دیگر تبدیل می‌کنیم، تا چاله برای توسعه‌دهندگان بعدی نگذاریم که در آن بیفتند. هرچه صریح‌تر باشیم، احتمال بیشتری هست که کسی بعداً بتواند کدمان را بخواند و بدون تلاش اضافی منظورمان را بفهمد.

سخت است اختلاف نظر مهمی با *explicit* coercion پیدا کنیم، چون بیشتر از همه با نحوهٔ کار تبدیل type در زبان‌های با type ایستا هم‌خوان است. بنابراین (فعلاً) فرض می‌گیریم که می‌توان بر سر اینکه *explicit* coercion شر یا بحث‌برانگیز نیست توافق کرد. البته بعداً به آن برمی‌گردیم.

### صریح: Stringها <--> Numberها

با ساده‌ترین و شاید رایج‌ترین عملیات coercion شروع می‌کنیم: coercion مقدارها بین نمایش `string` و `number`.

برای coercion بین `string`ها و `number`ها از توابع داخلی `String(..)` و `Number(..)` استفاده می‌کنیم (که در فصل ۳ آن‌ها را «سازنده‌های native» نامیدیم)، اما **خیلی مهم است** که از کلمهٔ کلیدی `new` جلوی آن‌ها استفاده نکنیم. بنابراین object wrapper نمی‌سازیم.

در عوض، واقعاً *صریحاً* بین آن دو type coerce می‌کنیم:

```js
var a = 42;
var b = String( a );

var c = "3.14";
var d = Number( c );

b; // "42"
d; // 3.14
```

`String(..)` از هر مقدار دیگر به مقدار primitive نوع `string` با قوانین عملیات `ToString` که قبلاً گفتیم coerce می‌کند. `Number(..)` از هر مقدار دیگر به مقدار primitive نوع `number` با قوانین عملیات `ToNumber` که قبلاً گفتیم coerce می‌کند.

این را *explicit* coercion می‌نامم چون به‌طور کلی برای بیشتر توسعه‌دهندگان کاملاً واضح است که نتیجهٔ نهایی این عملیات تبدیل type مربوطه است.

در واقع، این کاربرد خیلی شبیه برخی زبان‌های با type ایستای دیگر به‌نظر می‌رسد.

مثلاً در C/C++ می‌توانید `(int)x` یا `int(x)` بگویید و هر دو مقدار در `x` را به integer تبدیل می‌کنند. هر دو شکل معتبرند، اما بسیاری دومی را ترجیح می‌دهند که کمی شبیه فراخوانی تابع به‌نظر می‌رسد. در JavaScript وقتی `Number(x)` می‌گویید، خیلی شبیه است. آیا مهم است که در JS *واقعاً* فراخوانی تابع است؟ نه واقعاً.

علاوه بر `String(..)` و `Number(..)` راه‌های دیگری هم برای «صریح» تبدیل این مقدارها بین `string` و `number` هست:

```js
var a = 42;
var b = a.toString();

var c = "3.14";
var d = +c;

b; // "42"
d; // 3.14
```

فراخوانی `a.toString()` به‌ظاهر صریح است (کاملاً روشن است که «toString» یعنی «به string»)، اما اینجا یک implicitness پنهان هست. نمی‌توان `toString()` را روی مقدار *primitive* مثل `42` فراخوانی کرد. پس JS به‌طور خودکار `42` را در یک object wrapper «box» می‌کند (فصل ۳ را ببینید) تا بتوان `toString()` را روی آن object فراخوانی کرد. به‌عبارت دیگر، شاید آن را «صریحاً ضمنی» بنامید.

`+c` اینجا شکل *unary operator* (عملگری با فقط یک عملوند) عملگر `+` را نشان می‌دهد. به‌جای انجام جمع ریاضی (یا الحاق رشته — پایین را ببینید)، unary `+` صریحاً عملوندش (`c`) را به مقدار `number` coerce می‌کند.

آیا `+c` *explicit* coercion است؟ بستگی به تجربه و نگاه شما دارد. اگر بدانید (که الان می‌دانید!) که unary `+` صریحاً برای coercion به `number` منظور شده، پس کاملاً صریح و واضح است. اما اگر هرگز ندیده باشید، می‌تواند خیلی گیج‌کننده، ضمنی، با اثرات جانبی پنهان و غیره به‌نظر برسد.

**توجه:** نگاه پذیرفته‌شدهٔ کلی در جامعهٔ open-source JS این است که unary `+` شکلی پذیرفته‌شده از *explicit* coercion است.

حتی اگر واقعاً فرم `+c` را دوست دارید، قطعاً جاهایی هست که می‌تواند خیلی گیج‌کننده به‌نظر برسد. در نظر بگیرید:

```js
var c = "3.14";
var d = 5+ +c;

d; // 8.14
```

عملگر unary `-` هم مثل `+` coerce می‌کند، اما علامت عدد را هم برمی‌گرداند. با این حال نمی‌توانید دو `--` را کنار هم بگذارید تا علامت را برگردانید، چون به‌عنوان عملگر decrement parse می‌شود. در عوض باید این کار را بکنید: `- -"3.14"` با فاصله بین آن‌ها، که به coercion به `3.14` منجر می‌شود.

احتمالاً می‌توانید انواع ترکیب‌های زشت عملگرهای دودویی (مثل `+` برای جمع) کنار شکل unary یک عملگر تصور کنید. یک مثال دیوانه‌وار دیگر:

```js
1 + - + + + - + 1;	// 2
```

به‌شدت در نظر بگیرید از unary `+` (یا `-`) برای coercion وقتی بلافاصله کنار عملگرهای دیگر است اجتناب کنید. با وجود اینکه بالا کار می‌کند، تقریباً به‌طور جهانی ایدهٔ بدی تلقی می‌شود. حتی `d = +c` (یا `d =+ c`!) خیلی راحت با `d += c` اشتباه گرفته می‌شود که کاملاً متفاوت است!

**توجه:** جای دیگر بسیار گیج‌کننده برای استفادهٔ unary `+` کنار عملگر دیگر عملگرهای افزایش `++` و کاهش `--` هستند. مثلاً: `a +++b`، `a + ++b` و `a + + +b`. برای بیشتر دربارهٔ `++` بخش «Expression Side-Effects» فصل ۵ را ببینید.

یادتان باشد، داریم سعی می‌کنیم صریح باشیم و **سردرگمی را کم** کنیم، نه خیلی بدترش کنیم!

#### `Date` به `number`

کاربرد رایج دیگر عملگر unary `+` coercion یک object نوع `Date` به `number` است، چون نتیجه نمایش unix timestamp (میلی‌ثانیه‌های سپری‌شده از ۱ ژانویه ۱۹۷۰ ۰۰:۰۰:۰۰ UTC) مقدار تاریخ/زمان است:

```js
var d = new Date( "Mon, 18 Aug 2014 08:53:06 CDT" );

+d; // 1408369986000
```

رایج‌ترین کاربرد این اصطلاح گرفتن لحظهٔ *now* فعلی به‌صورت timestamp است، مثل:

```js
var timestamp = +new Date();
```

**توجه:** بعضی توسعه‌دهندگان از یک «ترفند» نحوی عجیب در JavaScript آگاهند: اینکه `()` در فراخوانی constructor (تابعی که با `new` فراخوانی می‌شود) *اختیاری* است اگر آرگومانی برای دادن نباشد. پس ممکن است به فرم `var timestamp = +new Date;` برخورد کنید. با این حال، همهٔ توسعه‌دهندگان موافق نیستند که حذف `()` خوانایی را بهتر می‌کند، چون یک استثنای نحوی غیرمعمول است که فقط برای فرم فراخوانی `new fn()` اعمال می‌شود نه فرم فراخوانی معمولی `fn()`.

اما coercion تنها راه گرفتن timestamp از یک object نوع `Date` نیست. رویکرد غیر-coercion شاید حتی ترجیح‌پذیرتر باشد، چون حتی صریح‌تر است:

```js
var timestamp = new Date().getTime();
// var timestamp = (new Date()).getTime();
// var timestamp = (new Date).getTime();
```

اما گزینهٔ *حتی* ترجیح‌پذیرتر غیر-coercion استفاده از تابع استاتیک `Date.now()` اضافه‌شده در ES5 است:

```js
var timestamp = Date.now();
```

و اگر می‌خواهید `Date.now()` را در مرورگرهای قدیمی‌تر polyfill کنید، خیلی ساده است:

```js
if (!Date.now) {
	Date.now = function() {
		return +new Date();
	};
}
```

توصیه می‌کنم از فرم‌های coercion مربوط به تاریخ صرف‌نظر کنید. برای timestampهای *now* فعلی از `Date.now()` استفاده کنید و برای گرفتن timestamp یک تاریخ/زمان *غیر-now* مشخص از `new Date( .. ).getTime()` استفاده کنید.

#### مورد عجیب `~`

یک عملگر coercive JS که اغلب نادیده گرفته می‌شود و معمولاً خیلی گیج‌کننده است عملگر tilde `~` (با نام «bitwise NOT») است. بسیاری از کسانی که حتی می‌فهمند چه می‌کند اغلب باز هم می‌خواهند از آن اجتناب کنند. اما در روح رویکرد این کتاب و مجموعه، بیایید عمیق شویم و ببینیم آیا `~` چیز مفیدی برای ما دارد.

در بخش «۳۲-bit (Signed) Integers» فصل ۲ گفتیم عملگرهای bitwise در JS فقط برای عملیات ۳۲-bit تعریف شده‌اند، یعنی عملوندها را مجبور می‌کنند به نمایش مقدار ۳۲-bit conform شوند. قوانین چگونگی این اتفاق توسط عملیات انتزاعی `ToInt32` (مشخصات ES5، بخش ۹.۵) کنترل می‌شود.

`ToInt32` ابتدا یک coercion به `ToNumber` انجام می‌دهد، یعنی اگر مقدار `"123"` باشد ابتدا `123` می‌شود قبل از اعمال قوانین `ToInt32`.

با اینکه *از نظر فنی* خود coercion نیست (چون type عوض نمی‌شود!)، استفاده از عملگرهای bitwise (مثل `|` یا `~`) با مقدارهای خاص `number` اثری coercive دارد که به مقدار `number` متفاوتی منجر می‌شود.

مثلاً ابتدا عملگر `|` «bitwise OR» را در اصطلاح no-op دیگر یعنی `0 | x` در نظر بگیریم که (همان‌طور که فصل ۲ نشان داد) اساساً فقط تبدیل `ToInt32` را انجام می‌دهد:

```js
0 | -0;			// 0
0 | NaN;		// 0
0 | Infinity;	// 0
0 | -Infinity;	// 0
```

این عددهای خاص قابل نمایش ۳۲-bit نیستند (چون از استاندارد ۶۴-bit IEEE 754 می‌آیند — فصل ۲ را ببینید)، پس `ToInt32` فقط `0` را به‌عنوان نتیجه از این مقدارها مشخص می‌کند.

قابل بحث است که آیا `0 | __` شکلی *explicit* از این عملیات coercive یعنی `ToInt32` است یا *implicit*‌تر. از نظر مشخصات، قطعاً *explicit* است، اما اگر در این سطح عملیات bitwise را نفهمید، می‌تواند کمی *ضمنی* جادویی به‌نظر برسد. با این حال، هم‌خوان با سایر ادعاهای این فصل، آن را *explicit* می‌خوانیم.

پس توجه را به `~` برگردانیم. عملگر `~` ابتدا به مقدار `number` ۳۲-bit «coerce» می‌کند و سپس negation bitwise (برگرداندن parity هر bit) را انجام می‌دهد.

**توجه:** این خیلی شبیه نحوهٔ `!` است که نه‌فقط مقدارش را به `boolean` coerce می‌کند بلکه parity آن را هم برمی‌گرداند (بحث «unary `!`» بعد را ببینید).

اما... چی!؟ چرا به برگرداندن bitها اهمیت می‌دهیم؟ چیز تخصصی و ظریفی است. برای توسعه‌دهندگان JS نادر است که لازم باشد دربارهٔ تک‌تک bitها استدلال کنند.

نگاه دیگر به تعریف `~` از علوم رایانه/ریاضیات گسسته قدیمی می‌آید: `~` two's-complement انجام می‌دهد. عالی، ممنون، کاملاً روشن‌تر شد!

دوباره امتحان کنیم: `~x` تقریباً همان `-(x+1)` است. عجیب است، اما کمی راحت‌تر برای استدلال. پس:

```js
~42;	// -(42+1) ==> -43
```

احتمالاً هنوز می‌پرسید همهٔ این `~` اصلاً دربارهٔ چیست، یا چرا برای بحث coercion واقعاً مهم است. سریع به اصل مطلب برسیم.

`-(x+1)` را در نظر بگیرید. تنها مقداری که می‌توانید این عملیات را روی آن انجام دهید و نتیجهٔ `0` (یا از نظر فنی `-0`!) بدهد چیست؟ `-1`. به‌عبارت دیگر، `~` با محدودهٔ مقدارهای `number` برای مقدار ورودی `-1` مقدار falsy (به‌راحتی قابل coercion به `false`) یعنی `0` می‌دهد و برای هر `number` truthy دیگر مقدار دیگر.

چرا مرتبط است؟

`-1` معمولاً «sentinel value» نامیده می‌شود، که اساساً یعنی مقداری که معنای معنایی دلخواهی در مجموعهٔ بزرگتر مقدارهای هم‌type خود (`number`ها) به آن داده شده. زبان C از sentinel valueهای `-1` برای بسیاری از توابعی استفاده می‌کند که برای «موفقیت» مقدارهای `>= 0` و برای «شکست» `-1` برمی‌گردانند.

JavaScript این سابقه را هنگام تعریف عملیات `string` یعنی `indexOf(..)` پذیرفت، که زیررشته را جستجو می‌کند و اگر پیدا شد index موقعیت بر اساس صفر را برمی‌گرداند، یا اگر پیدا نشد `-1`.

خیلی رایج است که از `indexOf(..)` نه فقط به‌عنوان عملیات گرفتن موقعیت، بلکه به‌عنوان بررسی `boolean` حضور/عدم حضور زیررشته در `string` دیگر استفاده شود. نحوهٔ معمول توسعه‌دهندگان برای چنین بررسی‌هایی:

```js
var a = "Hello World";

if (a.indexOf( "lo" ) >= 0) {	// true
	// found it!
}
if (a.indexOf( "lo" ) != -1) {	// true
	// found it
}

if (a.indexOf( "ol" ) < 0) {	// true
	// not found!
}
if (a.indexOf( "ol" ) == -1) {	// true
	// not found!
}
```

به‌نظر من کمی زشت است `>= 0` یا `== -1` را ببینم. اساساً یک «abstraction نشت‌کننده» است، چون رفتار پیاده‌سازی زیرین — استفاده از sentinel `-1` برای «شکست» — را به کدم نشت می‌دهد. ترجیح می‌دهم چنین جزئیاتی را پنهان کنم.

و حالا بالاخره می‌بینیم چرا `~` می‌تواند کمک کند! استفاده از `~` با `indexOf()` مقدار را «coerce» می‌کند (در واقع فقط transform می‌کند) **تا به‌درستی قابل coercion به `boolean` باشد**:

```js
var a = "Hello World";

~a.indexOf( "lo" );			// -4   <-- truthy!

if (~a.indexOf( "lo" )) {	// true
	// found it!
}

~a.indexOf( "ol" );			// 0    <-- falsy!
!~a.indexOf( "ol" );		// true

if (!~a.indexOf( "ol" )) {	// true
	// not found!
}
```

`~` مقدار برگشتی `indexOf(..)` را transform می‌کند: برای «شکست» یعنی `-1` falsy یعنی `0` می‌گیریم و هر مقدار دیگر truthy است.

**توجه:** الگوریتم شبه `-(x+1)` برای `~` دلالت می‌کند که `~-1` برابر `-0` است، اما در واقع `0` تولید می‌کند چون عملیات زیرین در واقع bitwise است نه ریاضی.

از نظر فنی، `if (~a.indexOf(..))` هنوز به coercion *implicit* نتیجهٔ `0` به `false` یا غیرصفر به `true` وابسته است. اما در کل، `~` هنوز برای من بیشتر مثل مکانیزم *explicit* coercion به‌نظر می‌رسد، تا وقتی بدانید در این اصطلاح قرار است چه کند.

به‌نظر من این کد تمیزتر از شلوغی قبلی `>= 0` / `== -1` است.

##### Truncating Bits

یک جای دیگر که `~` ممکن است در کدی که می‌بینید ظاهر شود: بعضی توسعه‌دهندگان از double tilde یعنی `~~` برای قطع بخش اعشاری یک `number` استفاده می‌کنند (یعنی «coerce» آن به عدد صحیح «integer»). معمولاً (اگرچه به‌اشتباه) گفته می‌شود نتیجه همان فراخوانی `Math.floor(..)` است.

نحوهٔ کار `~~` این است که اولین `~` «coercion» یعنی `ToInt32` را اعمال می‌کند و برگرداندن bitwise را انجام می‌دهد، و سپس دومین `~` برگرداندن bitwise دیگری انجام می‌دهد و همهٔ bitها را به حالت اولیه برمی‌گرداند. نتیجهٔ نهایی فقط «coercion» یعنی `ToInt32` است (با نام truncation).

**توجه:** double-flip bitwise یعنی `~~` خیلی شبیه رفتار parity double-negate یعنی `!!` است که در بخش «Explicitly: * --> Boolean» بعد توضیح داده می‌شود.

با این حال، `~~` نیاز به احتیاط/وضوح دارد. اول، فقط روی مقدارهای ۳۲-bit قابل اعتماد کار می‌کند. اما مهم‌تر، روی عددهای منفی مثل `Math.floor(..)` کار نمی‌کند!

```js
Math.floor( -49.6 );	// -50
~~-49.6;				// -49
```

با کنار گذاشتن تفاوت `Math.floor(..)`، `~~x` می‌تواند به (۳۲-bit) integer قطع کند. اما `x | 0` هم همین کار را می‌کند و به‌نظر با (کمی) *کمتر تلاش*.

پس چرا ممکن است `~~x` را به‌جای `x | 0` انتخاب کنید؟ اولویت عملگر (فصل ۵ را ببینید):

```js
~~1E20 / 10;		// 166199296

1E20 | 0 / 10;		// 1661992960
(1E20 | 0) / 10;	// 166199296
```

همان‌طور که با همهٔ توصیه‌های دیگر اینجا، از `~` و `~~` فقط به‌عنوان مکانیزم‌های صریح برای «coercion» و transform مقدار استفاده کنید اگر همهٔ کسانی که چنین کدی را می‌خوانند/می‌نویسند به‌درستی از نحوهٔ کار این عملگرها آگاه باشند!

### صریح: Parsing Numeric Strings

نتیجه‌ای مشابه coercion یک `string` به `number` را می‌توان با parse کردن یک `number` از محتوای کاراکتری یک `string` به‌دست آورد. با این حال، تفاوت‌های مشخصی بین این parsing و تبدیل type که بالا بررسی کردیم وجود دارد.

در نظر بگیرید:

```js
var a = "42";
var b = "42px";

Number( a );	// 42
parseInt( a );	// 42

Number( b );	// NaN
parseInt( b );	// 42
```

Parse کردن مقدار عددی از یک string به کاراکترهای غیرعددی *تحمل* می‌کند — فقط وقتی به آن برخورد کند از چپ به راست parse را متوقف می‌کند — در حالی که coercion *تحمل* نمی‌کند و ناموفق شده و به مقدار `NaN` منجر می‌شود.

Parsing نباید جایگزین coercion دیده شود. این دو کار، هرچند مشابه، هدف‌های متفاوتی دارند. وقتی نمی‌دانید/اهمیت نمی‌دهید چه کاراکترهای غیرعددی دیگری ممکن است سمت راست باشد یک `string` را به‌عنوان `number` parse کنید. وقتی تنها مقدارهای قابل قبول عددی هستند و چیزی مثل `"42px"` باید به‌عنوان `number` رد شود یک `string` را (به `number`) coerce کنید.

**نکته:** `parseInt(..)` یک جفت دارد، `parseFloat(..)`، که (همان‌طور که از نامش پیداست) عدد اعشاری را از یک string بیرون می‌کشد.

فراموش نکنید که `parseInt(..)` روی مقدارهای `string` عمل می‌کند. دادن مقدار `number` به `parseInt(..)` اصلاً معنی ندارد. دادن هر type دیگر مثل `true`، `function(){..}` یا `[1,2,3]` هم معنی ندارد.

اگر غیر-`string` بدهید، مقداری که می‌دهید ابتدا به‌طور خودکار به `string` coerce می‌شود (بخش «`ToString`» قبلی را ببینید)، که واضحاً نوعی coercion *implicit* پنهان خواهد بود. اتکا به چنین رفتاری در برنامه واقعاً ایدهٔ بدی است، پس هرگز `parseInt(..)` را با مقدار غیر-`string` استفاده نکنید.

قبل از ES5، gotcha دیگری با `parseInt(..)` وجود داشت که منبع باگ بسیاری از برنامه‌های JS بود. اگر آرگومان دوم را برای مشخص کردن مبنای عددی (با نام radix) برای تفسیر محتوای `string` عددی نمی‌دادید، `parseInt(..)` به کاراکتر(های) ابتدا نگاه می‌کرد تا حدس بزند.

اگر دو کاراکتر اول `"0x"` یا `"0X"` بودند، حدس (طبق قرارداد) این بود که می‌خواهید `string` را به‌عنوان عدد هگزادسیمال (مبنای ۱۶) تفسیر کنید. در غیر این صورت، اگر کاراکتر اول `"0"` بود، حدس (باز طبق قرارداد) این بود که می‌خواهید `string` را به‌عنوان عدد اکتال (مبنای ۸) تفسیر کنید.

`string`های هگزادسیمال (با `0x` یا `0X` پیشرو) به‌راحتی قابل اشتباه گرفتن نیستند. اما حدس عدد اکتال به‌طور شیطانی رایج بود. مثلاً:

```js
var hour = parseInt( selectedHour.value );
var minute = parseInt( selectedMinute.value );

console.log( "The time you selected was: " + hour + ":" + minute);
```

بی‌ضرر به‌نظر می‌رسد، درست؟ سعی کنید `08` را برای ساعت و `09` را برای دقیقه انتخاب کنید. `0:0` می‌گیرید. چرا؟ چون نه `8` و نه `9` کاراکتر معتبر در مبنای اکتال ۸ نیستند.

اصلاح پیش از ES5 ساده بود، اما به‌راحتی فراموش می‌شد: **همیشه `10` را به‌عنوان آرگومان دوم بدهید**. کاملاً امن بود:

```js
var hour = parseInt( selectedHour.value, 10 );
var minute = parseInt( selectedMiniute.value, 10 );
```

از ES5 به بعد، `parseInt(..)` دیگر اکتال حدس نمی‌زند. مگر خلافش را بگویید، مبنای ۱۰ (یا مبنای ۱۶ برای پیشوندهای `"0x"`) فرض می‌کند. خیلی بهتر است. فقط مراقب باشید اگر کدتان باید در محیط‌های پیش از ES5 اجرا شود، که در آن صورت هنوز باید برای radix مقدار `10` را بدهید.

#### Parsing Non-Strings

یک مثال تا حدی بدنام از رفتار `parseInt(..)` در یک پست شوخی طعنه‌آمیز چند سال پیش برجسته شده که به این رفتار JS می‌خندید:

```js
parseInt( 1/0, 19 ); // 18
```

ادعای فرضی (اما کاملاً نامعتبر) این بود: «اگر Infinity بدهم و یک integer از آن parse کنم، باید Infinity برگردانم، نه ۱۸.» حتماً JS برای این نتیجه دیوانه است، درست؟

هرچند این مثال واضحاً ساختگی و غیرواقعی است، یک لحظه دیوانگی را تحمل کنیم و بررسی کنیم آیا JS واقعاً آن‌قدر دیوانه است.

اول، واضح‌ترین گناه اینجا دادن غیر-`string` به `parseInt(..)` است. این کار ممنوع است. انجامش دهید و دردسر می‌خواهید. اما حتی اگر بکنید، JS مودبانه چیزی که می‌دهید را به `string`ی coerce می‌کند که بتواند سعی کند parse کند.

بعضی استدلال می‌کنند این رفتار نامعقول است و `parseInt(..)` باید از عمل روی مقدار غیر-`string` خودداری کند. شاید باید خطا پرتاب کند؟ صادقانه بگویم، خیلی شبیه Java می‌شد. از فکر اینکه JS شروع کند همه‌جا خطا پرتاب کند تا `try..catch` دور تقریباً هر خط لازم شود به لرزه می‌افتم.

آیا باید `NaN` برگرداند؟ شاید. اما... این چطور:

```js
parseInt( new String( "42") );
```

آیا آن هم باید ناموفق شود؟ مقدار غیر-`string` است. اگر می‌خواهید آن object wrapper نوع `String` به `"42"` unbox شود، پس آیا واقعاً غیرمعمول است که `42` ابتدا `"42"` شود تا `42` دوباره parse شود؟

استدلال می‌کنم این coercion نیمه-*explicit* و نیمه-*implicit* که می‌تواند رخ دهد اغلب می‌تواند خیلی مفید باشد. مثلاً:

```js
var a = {
	num: 21,
	toString: function() { return String( this.num * 2 ); }
};

parseInt( a ); // 42
```

این واقعیت که `parseInt(..)` به‌زور مقدارش را به `string` coerce می‌کند تا parse روی آن انجام دهد کاملاً معقول است. اگر آشغال بدهید و آشغال پس بگیرید، سطل زباله را مقصر ندانید — فقط وظیفه‌اش را درست انجام داد.

پس اگر مقداری مثل `Infinity` (نتیجهٔ واضح `1 / 0`) بدهید، چه نوع نمایش `string` برای coercion آن معقول‌ترین است؟ فقط دو انتخاب معقول به ذهن می‌رسد: `"Infinity"` و `"∞"`. JS `"Infinity"` را انتخاب کرد. خوشحالم که کرد.

فکر می‌کنم خوب است که **همهٔ مقدارها** در JS نوعی نمایش پیش‌فرض `string` داشته باشند، تا جعبهٔ سیاه مرموزی نباشند که نتوانیم debug و استدلال کنیم.

حالا مبنای ۱۹ چطور؟ واضحاً کاملاً ساختگی و دروغین. هیچ برنامهٔ JS واقعی از مبنای ۱۹ استفاده نمی‌کند. پوچ است. اما باز هم پوچی را تحمل کنیم. در مبنای ۱۹، کاراکترهای عددی معتبر `0` تا `9` و `a` تا `i` هستند (بدون توجه به حروف بزرگ/کوچک).

پس برگردیم به مثال `parseInt( 1/0, 19 )`. اساساً `parseInt( "Infinity", 19 )` است. چطور parse می‌کند؟ کاراکتر اول `"I"` است که در مبنای مسخرهٔ ۱۹ مقدار `18` است. کاراکتر دوم `"n"` در مجموعهٔ معتبر کاراکترهای عددی نیست و بنابراین parse فقط مودبانه متوقف می‌شود، درست مثل وقتی به `"p"` در `"42px"` برخورد کرد.

نتیجه؟ `18`. دقیقاً همان‌طور که معقول است. رفتارهای درگیر برای رسیدن به آن، و نه به خطا یا خود `Infinity`، **خیلی مهم** برای JS هستند و نباید به‌این راحتی کنار گذاشته شوند.

مثال‌های دیگر این رفتار با `parseInt(..)` که ممکن است غافل‌گیرکننده اما کاملاً معقول باشند:

```js
parseInt( 0.000008 );		// 0   ("0" from "0.000008")
parseInt( 0.0000008 );		// 8   ("8" from "8e-7")
parseInt( false, 16 );		// 250 ("fa" from "false")
parseInt( parseInt, 16 );	// 15  ("f" from "function..")

parseInt( "0x10" );			// 16
parseInt( "103", 2 );		// 2
```

`parseInt(..)` در واقع در رفتارش کاملاً قابل پیش‌بینی و یکنواخت است. اگر درست استفاده کنید، نتایج معقول می‌گیرید. اگر غلط استفاده کنید، نتایج دیوانه‌ای که می‌گیرید تقصیر JavaScript نیست.

### صریح: * --> Boolean

حالا coercion از هر مقدار غیر-`boolean` به `boolean` را بررسی می‌کنیم.

درست مثل `String(..)` و `Number(..)` بالا، `Boolean(..)` (بدون `new` البته!) راه صریح اجبار coercion به `ToBoolean` است:

```js
var a = "0";
var b = [];
var c = {};

var d = "";
var e = 0;
var f = null;
var g;

Boolean( a ); // true
Boolean( b ); // true
Boolean( c ); // true

Boolean( d ); // false
Boolean( e ); // false
Boolean( f ); // false
Boolean( g ); // false
```

با اینکه `Boolean(..)` واضحاً صریح است، اصلاً رایج یا اصطلاحی نیست.

درست مثل عملگر unary `+` که مقدار را به `number` coerce می‌کند (بالا را ببینید)، عملگر نفی unary `!` صریحاً مقدار را به `boolean` coerce می‌کند. *مشکل* این است که مقدار را هم از truthy به falsy یا برعکس برمی‌گرداند. پس رایج‌ترین نحوهٔ coercion صریح توسعه‌دهندگان JS به `boolean` استفاده از عملگر double-negate یعنی `!!` است، چون دومین `!` parity را به حالت اولیه برمی‌گرداند:

```js
var a = "0";
var b = [];
var c = {};

var d = "";
var e = 0;
var f = null;
var g;

!!a;	// true
!!b;	// true
!!c;	// true

!!d;	// false
!!e;	// false
!!f;	// false
!!g;	// false
```

هرکدام از این coercionهای `ToBoolean` *به‌طور ضمنی* بدون `Boolean(..)` یا `!!` رخ می‌داد اگر در زمینهٔ `boolean` مثل دستور `if (..) ..` استفاده می‌شد. اما هدف اینجا صریحاً مجبور کردن مقدار به `boolean` است تا روشن‌تر شود که coercion به `ToBoolean` منظور است.

مثال استفادهٔ دیگر برای coercion صریح به `ToBoolean` اگر بخواهید coercion مقدار `true`/`false` را در سریال‌سازی JSON یک ساختار داده اعمال کنید:

```js
var a = [
	1,
	function(){ /*..*/ },
	2,
	function(){ /*..*/ }
];

JSON.stringify( a ); // "[1,null,2,null]"

JSON.stringify( a, function(key,val){
	if (typeof val == "function") {
		// force `ToBoolean` coercion of the function
		return !!val;
	}
	else {
		return val;
	}
} );
// "[1,true,2,true]"
```

اگر از Java به JavaScript آمده‌اید، شاید این اصطلاح را بشناسید:

```js
var a = 42;

var b = a ? true : false;
```

عملگر سه‌تایی `? :` مقدار `a` را برای truthiness تست می‌کند و بر اساس آن تست یا `true` یا `false` را به `b` نسبت می‌دهد.

در ظاهر، این اصطلاح شبیه شکلی از coercion نوع *explicit* به `ToBoolean` به‌نظر می‌رسد، چون واضح است که فقط یا `true` یا `false` از عملیات بیرون می‌آید.

با این حال، یک coercion *implicit* پنهان هست، چون عبارت `a` باید ابتدا به `boolean` coerce شود تا تست truthiness انجام شود. این اصطلاح را «صریحاً ضمنی» می‌خوانم. علاوه بر این، پیشنهاد می‌کنم **این اصطلاح را در JavaScript کاملاً اجتناب کنید**. مزیت واقعی ندارد و بدتر، خودش را به‌عنوان چیزی که نیست جا می‌زند.

`Boolean(a)` و `!!a` گزینه‌های *explicit* coercion به‌مراتب به‌ترند.
