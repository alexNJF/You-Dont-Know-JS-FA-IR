# Loose Equals در مقابل Strict Equals

Loose equals همان عملگر `==` است و strict equals همان عملگر `===` است. هر دو عملگر برای مقایسهٔ دو مقدار از نظر «برابری» استفاده می‌شوند، اما «loose» در مقابل «strict» تفاوت **خیلی مهمی** در رفتار بین آن دو را نشان می‌دهد، به‌طور مشخص در نحوهٔ تصمیم‌گیری دربارهٔ «برابری».

یک تصور غلط بسیار رایج دربارهٔ این دو عملگر این است: «`==` مقدارها را برای برابری بررسی می‌کند و `===` هم مقدارها و هم typeها را بررسی می‌کند.» هرچند خوب و معقول به‌نظر می‌رسد، نادرست است. کتاب‌ها و وبلاگ‌های جاوااسکریپت معتبر بی‌شمار دقیقاً همین را گفته‌اند، اما متأسفانه همگی *غلط* هستند.

توصیف درست این است: «`==` در مقایسهٔ برابری coercion را اجازه می‌دهد و `===` coercion را اجازه نمی‌دهد.»

### عملکرد برابری

بایستید و به تفاوت بین توضیح اول (نادرست) و این دوم (درست) فکر کنید.

در توضیح اول، به‌نظر واضح است که `===` *کار بیشتری* از `==` می‌کند، چون باید *هم* type را بررسی کند. در توضیح دوم، `==` است که *کار بیشتری* می‌کند چون اگر typeها متفاوت باشند باید مراحل coercion را دنبال کند.

اما در دام نیفتید، مثل بسیاری، که فکر کنید به عملکرد ربطی دارد، انگار `==` به‌نحوی مرتبط کندتر از `===` باشد. هرچند قابل اندازه‌گیری است که coercion *کمی* زمان پردازش می‌برد، فقط میکروثانیه است (بله، یعنی میلیونم ثانیه!).

اگر دو مقدار با type یکسان را مقایسه می‌کنید، `==` و `===` الگوریتم یکسان استفاده می‌کنند و بنابراین جز تفاوت‌های جزئی در پیاده‌سازی موتور، باید همان کار را بکنند.

اگر دو مقدار با type متفاوت مقایسه می‌کنید، عملکرد عامل مهم نیست. سؤالی که باید از خود بپرسید این است: وقتی این دو مقدار را مقایسه می‌کنم، coercion می‌خواهم یا نه؟

اگر coercion می‌خواهید، از برابری loose یعنی `==` استفاده کنید، اما اگر coercion نمی‌خواهید از برابری strict یعنی `===` استفاده کنید.

**توجه:** دلالت اینجا پس این است که هر دو `==` و `===` type عملوندهایشان را بررسی می‌کنند. تفاوت در واکنش آن‌هاست اگر typeها مطابقت نکنند.

### Abstract Equality

رفتار عملگر `==` در بخش ۱۱.۹.۳ مشخصات ES5 به‌عنوان «الگوریتم مقایسهٔ Abstract Equality» تعریف شده. آنچه آنجا فهرست شده الگوریتمی جامع اما ساده است که صریحاً هر ترکیب ممکن typeها و نحوهٔ رخ دادن coercionها (در صورت لازم) را برای هر ترکیب مشخص می‌کند.

**هشدار:** وقتی (*implicit*) coercion به‌عنوان بیش از حد پیچیده و پرنقص برای اینکه *بخش مفید خوب* باشد محکوم می‌شود، این قوانین «abstract equality» هستند که محکوم می‌شوند. معمولاً گفته می‌شود برای توسعه‌دهندگان بیش از حد پیچیده و غیرشهودی برای یادگیری و استفادهٔ عملی هستند و بیشتر مستعد ایجاد باگ در برنامه‌های JS هستند تا امکان خوانایی بیشتر کد. به‌نظر من این فرضی غلط است — که شما خوانندگان توسعه‌دهندگان competent هستید که همهٔ روز الگوریتم (یعنی کد) می‌نویسید (و می‌خوانید و می‌فهمید!). پس آنچه می‌آید توضیح سادهٔ «abstract equality» به زبان ساده است. اما از شما می‌خواهم بخش ۱۱.۹.۳ مشخصات ES5 را هم بخوانید. فکر می‌کنم از معقول بودنش متعجب می‌شوید.

اساساً، بند اول (۱۱.۹.۳.۱) می‌گوید اگر دو مقدار مقایسه‌شده از type یکسان باشند، به‌سادگی و طبیعی طبق Identity مقایسه می‌شوند آن‌طور که انتظار دارید. مثلاً `42` فقط با `42` برابر است و `"abc"` فقط با `"abc"`.

چند استثنای جزئی نسبت به انتظار معمولی که باید بدانید:

* `NaN` هرگز با خودش برابر نیست (فصل ۲ را ببینید)
* `+0` و `-0` با هم برابرند (فصل ۲ را ببینید)

مقررات نهایی در بند ۱۱.۹.۳.۱ برای مقایسهٔ برابری loose یعنی `==` با `object`ها (شامل `function`ها و `array`ها) است. دو چنین مقداری فقط *برابر* هستند اگر هر دو ارجاع به *دقیقاً همان مقدار* باشند. اینجا coercion رخ نمی‌دهد.

**توجه:** مقایسهٔ برابری strict یعنی `===` عیناً مثل ۱۱.۹.۳.۱ تعریف شده، از جمله مقررات دربارهٔ دو مقدار `object`. واقعیت بسیار کم‌شناخته‌شده این است که **`==` و `===` در مورد مقایسهٔ دو `object` یکسان رفتار می‌کنند!**

بقیهٔ الگوریتم در ۱۱.۹.۳ مشخص می‌کند که اگر از برابری loose یعنی `==` برای مقایسهٔ دو مقدار با type متفاوت استفاده کنید، یکی یا هر دو مقدار باید *به‌طور ضمنی* coerce شوند. این coercion طوری رخ می‌دهد که هر دو مقدار در نهایت به همان type برسند، که بعد می‌توان مستقیماً با Identity مقدار ساده برای برابری مقایسه کرد.

**توجه:** عملیات loose not-equality یعنی `!=` دقیقاً آن‌طور که انتظار دارید تعریف شده: یعنی مقایسهٔ عملیات `==` به‌طور کامل انجام می‌شود و بعد نفی نتیجه. همین‌طور برای عملیات strict not-equality یعنی `!==`.

#### مقایسه: `string`ها با `number`ها

برای illustration coercion در `==`، ابتدا از مثال‌های `string` و `number` قبلی این فصل استفاده می‌کنیم:

```js
var a = 42;
var b = "42";

a === b;	// false
a == b;		// true
```

همان‌طور که انتظار داریم، `a === b` ناموفق است چون coercion مجاز نیست و واقعاً مقدارهای `42` و `"42"` متفاوت‌اند.

با این حال، مقایسهٔ دوم یعنی `a == b` از برابری loose استفاده می‌کند که یعنی اگر typeها متفاوت باشند الگوریتم مقایسه *implicit* coercion روی یکی یا هر دو مقدار انجام می‌دهد.

اما دقیقاً چه نوع coercion اینجا رخ می‌دهد؟ آیا مقدار `a` یعنی `42` به `string` می‌شود، یا مقدار `b` یعنی `"42"` به `number`؟

در مشخصات ES5، بندهای ۱۱.۹.۳.۴–۵ می‌گویند:

> 4. If Type(x) is Number and Type(y) is String,
>    return the result of the comparison x == ToNumber(y).
> 5. If Type(x) is String and Type(y) is Number,
>    return the result of the comparison ToNumber(x) == y.

**هشدار:** مشخصات از `Number` و `String` به‌عنوان نام‌های رسمی typeها استفاده می‌کند، در حالی که این کتاب `number` و `string` را برای typeهای primitive ترجیح می‌دهد. اجازه ندهید حروف بزرگ `Number` در مشخصات شما را با تابع native یعنی `Number()` اشتباه بگیرد. برای منظور ما، حروف بزرگ نام type بی‌اهمیت است — اساساً همان معنی را دارند.

واضح است که مشخصات می‌گوید مقدار `"42"` برای مقایسه به `number` coerce می‌شود. *چگونگی* آن coercion قبلاً پوشش داده شده، به‌طور مشخص با عملیات انتزاعی `ToNumber`. در این مورد پس کاملاً واضح است که دو مقدار `42` حاصل برابرند.

#### مقایسه: هر چیزی با `boolean`

یکی از بزرگ‌ترین gotchaهای *implicit* coercion در برابری loose یعنی `==` وقتی ظاهر می‌شود که سعی می‌کنید مقداری را مستقیماً با `true` یا `false` مقایسه کنید.

در نظر بگیرید:

```js
var a = "42";
var b = true;

a == b;	// false
```

صبر کنید، اینجا چه شد!؟ می‌دانیم که `"42"` مقدار truthy است (قبلی این فصل را ببینید). پس چطور با `true` برابری loose یعنی `==` ندارد؟

دلیل هم ساده است و هم فریبنده trick. به‌راحتی قابل سوءتفاهم است و بسیاری از توسعه‌دهندگان JS هرگز به‌اندازهٔ کافی توجه نمی‌کنند تا کامل درکش کنند.

باز از مشخصات نقل می‌کنیم، بندهای ۱۱.۹.۳.۶–۷:

> 6. If Type(x) is Boolean,
>    return the result of the comparison ToNumber(x) == y.
> 7. If Type(y) is Boolean,
>    return the result of the comparison x == ToNumber(y).

شکستنش می‌دهیم. اول:

```js
var x = true;
var y = "42";

x == y; // false
```

`Type(x)` واقعاً `Boolean` است، پس `ToNumber(x)` را انجام می‌دهد که `true` را به `1` coerce می‌کند. حالا `1 == "42"` ارزیابی می‌شود. typeها هنوز متفاوت‌اند، پس (اساساً بازگشتی) دوباره الگوریتم را مراجعه می‌کنیم که مثل بالا `"42"` را به `42` coerce می‌کند و `1 == 42` واضحاً `false` است.

برعکسش کنیم، باز همان نتیجه را می‌گیریم:

```js
var x = "42";
var y = false;

x == y; // false
```

این بار `Type(y)` برابر `Boolean` است، پس `ToNumber(y)` مقدار `0` می‌دهد. `"42" == 0` بازگشتی می‌شود به `42 == 0` که البته `false` است.

به‌عبارت دیگر، **مقدار `"42"` نه با `== true` و نه با `== false` برابر است.** در نگاه اول، آن جمله شاید دیوانه به‌نظر برسد. چطور می‌تواند مقداری نه truthy و نه falsy باشد؟

اما مشکل همین است! سؤال اشتباه می‌پرسید، کلاً. تقصیر شما نیست. مغزتان شما را فریب می‌دهد.

`"42"` واقعاً truthy است، اما `"42" == true` **اصلاً تست/coercion به boolean انجام نمی‌دهد**، هرچه مغزتان بگوید. `"42"` *به* `boolean` (`true`) coerce *نمی‌شود*، بلکه `true` به `1` coerce می‌شود و بعد `"42"` به `42` coerce می‌شود.

خواه بخواهیم نخواهیم، `ToBoolean` اصلاً اینجا دخیل نیست، پس truthiness یا falsiness مقدار `"42"` به عملیات `==` نامرتبط است!

آنچه *مرتبط* است این است که بفهمیم الگوریتم مقایسهٔ `==` با همهٔ ترکیب‌های مختلف type چطور رفتار می‌کند. در مورد مقدار `boolean` در هر طرف `==`، یک `boolean` همیشه *ابتدا* به `number` coerce می‌شود.

اگر عجیب به‌نظرتان رسید، تنها نیستید. به‌نظر شخصی من توصیه می‌کنم هرگز، تحت هیچ شرایطی، از `== true` یا `== false` استفاده نکنید. هرگز.

اما یادتان باشد، فقط دربارهٔ `==` حرف می‌زنم. `=== true` و `=== false` coercion را اجازه نمی‌دهند، پس از این coercion پنهان `ToNumber` در امان‌اند.

در نظر بگیرید:

```js
var a = "42";

// bad (will fail!):
if (a == true) {
	// ..
}

// also bad (will fail!):
if (a === true) {
	// ..
}

// good enough (works implicitly):
if (a) {
	// ..
}

// better (works explicitly):
if (!!a) {
	// ..
}

// also great (works explicitly):
if (Boolean( a )) {
	// ..
}
```

اگر هرگز در کدتان از `== true` یا `== false` (یعنی برابری loose با `boolean`ها) استفاده نکنید، هرگز نگران این gotcha ذهنی truthiness/falsiness نخواهید بود.

#### مقایسه: `null`ها با `undefined`ها

مثال دیگر *implicit* coercion را می‌توان در برابری loose یعنی `==` بین مقدارهای `null` و `undefined` دید. باز از مشخصات ES5 نقل می‌کنیم، بندهای ۱۱.۹.۳.۲–۳:

> 2. If x is null and y is undefined, return true.
> 3. If x is undefined and y is null, return true.

`null` و `undefined` وقتی با برابری loose یعنی `==` مقایسه می‌شوند با هم (و واضحاً با خودشان) برابر می‌شوند (یعنی به هم coerce می‌شوند)، و با هیچ مقدار دیگر در کل زبان.

یعنی `null` و `undefined` را می‌توان برای منظور مقایسه غیرقابل تشخیص در نظر گرفت، اگر از عملگر برابری loose یعنی `==` برای اجازهٔ *implicit* coercion متقابل آن‌ها استفاده کنید.

```js
var a = null;
var b;

a == b;		// true
a == null;	// true
b == null;	// true

a == false;	// false
b == false;	// false
a == "";	// false
b == "";	// false
a == 0;		// false
b == 0;		// false
```

Coercion بین `null` و `undefined` امن و قابل پیش‌بینی است و هیچ مقدار دیگری نمی‌تواند در چنین بررسی false positive بدهد. توصیه می‌کنم از این coercion استفاده کنید تا `null` و `undefined` غیرقابل تشخیص و بنابراین مثل یک مقدار تلقی شوند.

مثلاً:

```js
var a = doSomething();

if (a == null) {
	// ..
}
```

بررسی `a == null` فقط وقتی موفق می‌شود که `doSomething()` یا `null` یا `undefined` برگرداند، و با هر مقدار دیگر ناموفق می‌شود، حتی سایر مقدارهای falsy مثل `0`، `false` و `""`.

فرم *explicit* این بررسی که هر coercion از این دست را اجازه نمی‌دهد به‌نظر من به‌طور غیرضروری زشت‌تر است (و شاید کمی کمتر performant!):

```js
var a = doSomething();

if (a === undefined || a === null) {
	// ..
}
```

به‌نظر من فرم `a == null` نمونهٔ دیگری است که *implicit* coercion خوانایی کد را بهتر می‌کند، اما به‌صورتی قابل اعتماد امن.

#### مقایسه: `object`ها با غیر-`object`ها

اگر یک `object`/`function`/`array` با primitive اسکالر ساده (`string`، `number` یا `boolean`) مقایسه شود، مشخصات ES5 در بندهای ۱۱.۹.۳.۸–۹ می‌گوید:

> 8. If Type(x) is either String or Number and Type(y) is Object,
>    return the result of the comparison x == ToPrimitive(y).
> 9. If Type(x) is Object and Type(y) is either String or Number,
>    return the result of the comparison ToPrimitive(x) == y.

**توجه:** ممکن است متوجه شوید این بندها فقط `String` و `Number` را ذکر می‌کنند، نه `Boolean`. چون همان‌طور که قبلاً نقل شد، بندهای ۱۱.۹.۳.۶–۷ هر عملوند `Boolean` ارائه‌شده را ابتدا به `Number` coerce می‌کنند.

در نظر بگیرید:

```js
var a = 42;
var b = [ 42 ];

a == b;	// true
```

مقدار `[ 42 ]` عملیات انتزاعی `ToPrimitive` رویش فراخوانی می‌شود (بخش «Abstract Value Operations» قبلی را ببینید) که به مقدار `"42"` منجر می‌شود. از آنجا فقط `42 == "42"` است که همان‌طور که پوشش دادیم می‌شود `42 == 42`، پس `a` و `b` از نظر coercive برابر یافت می‌شوند.

**نکته:** همهٔ quirkهای عملیات انتزاعی `ToPrimitive` که قبلاً در این فصل گفتیم (`toString()`، `valueOf()`) اینجا آن‌طور که انتظار دارید اعمال می‌شوند. اگر ساختار دادهٔ پیچیده‌ای دارید که می‌خواهید متد سفارشی `valueOf()` روی آن تعریف کنید تا مقدار ساده برای منظور مقایسهٔ برابری بدهد می‌تواند خیلی مفید باشد.

در فصل ۳ «unboxing» را پوشش دادیم، جایی که object wrapper دور یک مقدار primitive (مثلاً از `new String("abc")`) باز می‌شود و مقدار primitive زیرین (`"abc"`) برگردانده می‌شود. این رفتار به coercion یعنی `ToPrimitive` در الگوریتم `==` مربوط است:

```js
var a = "abc";
var b = Object( a );	// same as `new String( a )`

a === b;				// false
a == b;					// true
```

`a == b` برابر `true` است چون `b` از طریق `ToPrimitive` coerce (یعنی «unbox»، unwrap) می‌شود به مقدار primitive اسکالر زیرین یعنی `"abc"` که با مقدار در `a` یکی است.

با این حال مقدارهایی هست که این‌طور نیست، به‌خاطر قوانین بازنویسی‌شدهٔ دیگر در الگوریتم `==`. در نظر بگیرید:

```js
var a = null;
var b = Object( a );	// same as `Object()`
a == b;					// false

var c = undefined;
var d = Object( c );	// same as `Object()`
c == d;					// false

var e = NaN;
var f = Object( e );	// same as `new Number( e )`
e == f;					// false
```

مقدارهای `null` و `undefined` قابل boxing نیستند — معادل object wrapper ندارند — پس `Object(null)` مثل `Object()` است و هر دو فقط یک object معمولی تولید می‌کنند.

`NaN` را می‌توان در معادل object wrapper نوع `Number` boxing کرد، اما وقتی `==` باعث unboxing می‌شود مقایسهٔ `NaN == NaN` ناموفق است چون `NaN` هرگز با خودش برابر نیست (فصل ۲ را ببینید).

### Edge Cases

حالا که *implicit* coercion برابری loose یعنی `==` را (هم به‌صورت معقول و هم غافل‌گیرکننده) کامل بررسی کردیم، بیایید بدترین و دیوانه‌وارترین corner caseها را برجسته کنیم تا ببینیم برای گزیده نشدن با باگ coercion از چه چیزهایی باید اجتناب کنیم.

اول، ببینیم تغییر prototypeهای native داخلی چطور می‌تواند نتایج دیوانه تولید کند:

#### A Number By Any Other Value Would...

```js
Number.prototype.valueOf = function() {
	return 3;
};

new Number( 2 ) == 3;	// true
```

**هشدار:** `2 == 3` در این دام نمی‌افتاد، چون نه `2` و نه `3` متد داخلی `Number.prototype.valueOf()` را فراخوانی نمی‌کردند چون هر دو از قبل مقدار primitive نوع `number` هستند و می‌توان مستقیماً مقایسه کرد. با این حال، `new Number(2)` باید از coercion یعنی `ToPrimitive` بگذرد و بنابراین `valueOf()` را فراخوانی می‌کند.

شر، درست است؟ البته. هیچ‌کس نباید چنین کاری بکند. این واقعیت که *می‌توانید* چنین کاری بکنید گاهی برای انتقاد از coercion و `==` استفاده می‌شود. اما آن ناراحتی جهت اشتباه دارد. JavaScript *بد* نیست چون می‌توانید چنین کارهایی بکنید؛ یک توسعه‌دهنده *بد* است **اگر چنین کارهایی بکند**. در دام مغالطهٔ «زبان برنامه‌نویسی من باید از خودم محافظتم کند» نیفتید.

بعد، مثال trick دیگر را در نظر بگیریم که شر مثال قبلی را به سطح دیگری می‌برد:

```js
if (a == 2 && a == 3) {
	// ..
}
```

شاید فکر کنید غیرممکن است، چون `a` هرگز نمی‌تواند *هم‌زمان* با هر دو `2` و `3` برابر باشد. اما «هم‌زمان» نادرست است، چون عبارت اول یعنی `a == 2` به‌طور دقیق *قبل از* `a == 3` رخ می‌دهد.

پس چه می‌شود اگر `a.valueOf()` هر بار که فراخوانی می‌شود side effect داشته باشد، طوری که بار اول `2` برگرداند و بار دوم `3`؟ خیلی آسان:

```js
var i = 2;

Number.prototype.valueOf = function() {
	return i++;
};

var a = new Number( 42 );

if (a == 2 && a == 3) {
	console.log( "Yep, this happened." );
}
```

باز هم، این‌ها ترفندهای شر هستند. انجام ندهید. اما همچنین از آن‌ها به‌عنوان شکایت علیه coercion استفاده نکنید. سوءاستفاده‌های احتمالی یک مکانیزم دلیل کافی برای محکوم کردن آن مکانیزم نیست. فقط از این ترفندهای دیوانه اجتناب کنید و فقط به استفادهٔ معتبر و درست از coercion پایبند باشید.

#### False-y Comparisons

رایج‌ترین شکایت علیه *implicit* coercion در مقایسه‌های `==` از نحوهٔ رفتار غافل‌گیرکنندهٔ مقدارهای falsy وقتی با هم مقایسه می‌شوند می‌آید.

برای illustration، به فهرستی از corner-caseهای اطراف مقایسهٔ مقدار falsy نگاه می‌کنیم تا ببینیم کدام‌ها معقول و کدام‌ها مشکل‌سازند:

```js
"0" == null;			// false
"0" == undefined;		// false
"0" == false;			// true -- UH OH!
"0" == NaN;				// false
"0" == 0;				// true
"0" == "";				// false

false == null;			// false
false == undefined;		// false
false == NaN;			// false
false == 0;				// true -- UH OH!
false == "";			// true -- UH OH!
false == [];			// true -- UH OH!
false == {};			// false

"" == null;				// false
"" == undefined;		// false
"" == NaN;				// false
"" == 0;				// true -- UH OH!
"" == [];				// true -- UH OH!
"" == {};				// false

0 == null;				// false
0 == undefined;			// false
0 == NaN;				// false
0 == [];				// true -- UH OH!
0 == {};				// false
```

در این فهرست ۲۴ مقایسه، ۱۷ تای آن‌ها کاملاً معقول و قابل پیش‌بینی‌اند. مثلاً می‌دانیم `""` و `NaN` اصلاً مقدارهای قابل برابری نیستند و واقعاً به loose equals coerce نمی‌شوند، در حالی که `"0"` و `0` به‌طور معقول قابل برابری‌اند و *به‌عنوان* loose equals coerce می‌شوند.

با این حال، هفت مقایسه با «UH OH!» علامت خورده‌اند چون به‌عنوان false positive احتمال بیشتری دارد gotcha باشند که شما را گیر بیندازند. `""` و `0` قطعاً مقدارهای متمایز هستند و نادر است بخواهید آن‌ها را قابل برابری تلقی کنید، پس coercion متقابل آن‌ها مشکل‌ساز است. توجه کنید اینجا false negative نداریم.

#### The Crazy Ones

نباید همانجا بایستیم. می‌توانیم به دنبال coercionهای حتی مشکل‌سازتر بگردیم:

```js
[] == ![];		// true
```

اوه، به‌نظر یک سطح بالاتر دیوانگی است، درست!؟ مغزتان احتمالاً شما را فریب می‌دهد که دارید truthy را با falsy مقایسه می‌کنید، پس نتیجهٔ `true` غافل‌گیرکننده است چون *می‌دانیم* یک مقدار هرگز نمی‌تواند هم truthy و هم falsy باشد!

اما آنچه واقعاً اتفاق می‌افتد این نیست. شکستنش می‌دهیم. دربارهٔ عملگر unary `!` چه می‌دانیم؟ صریحاً با قوانین `ToBoolean` به `boolean` coerce می‌کند (و parity را هم برمی‌گرداند). پس قبل از اینکه `[] == ![]` حتی پردازش شود، در واقع قبلاً به `[] == false` ترجمه شده. آن فرم را قبلاً در فهرست بالا دیدیم (`false == []`)، پس نتیجهٔ غافل‌گیرکننده‌اش *برایمان تازه* نیست.

corner caseهای دیگر چطور؟

```js
2 == [2];		// true
"" == [null];	// true
```

همان‌طور که قبلاً در بحث `ToNumber` گفتیم، مقدارهای سمت راست یعنی `[2]` و `[null]` از coercion یعنی `ToPrimitive` می‌گذرند تا راحت‌تر با primitiveهای ساده (`2` و `""` به‌ترتیب) سمت چپ مقایسه شوند. چون `valueOf()` برای مقدارهای `array` فقط خود `array` را برمی‌گرداند، coercion به stringify کردن `array` می‌رسد.

`[2]` می‌شود `"2"` که بعد برای مقدار سمت راست در مقایسهٔ اول با `ToNumber` coerce می‌شود به `2`. `[null]` مستقیم می‌شود `""`.

پس `2 == 2` و `"" == ""` کاملاً قابل فهم‌اند.

اگر غریزه‌تان هنوز این نتایج را دوست ندارد، ناراحتیتان در واقع با coercion نیست آن‌طور که احتمالاً فکر می‌کنید. در واقع شکایتی علیه رفتار پیش‌فرض مقدارهای `array` در coercion به `ToPrimitive` به مقدار `string` است. احتمالاً فقط آرزو می‌کنید `[2].toString()` برنگرداند `"2"` یا `[null].toString()` برنگرداند `""`.

اما دقیقاً *باید* این coercionهای `string` به چه نتیجه‌ای برسند؟ به‌جز شاید `"[2]"` — که در زمینه‌های دیگر می‌تواند خیلی عجیب باشد! — coercion مناسب دیگر `string` برای `[2]` به ذهنم نمی‌رسد.

می‌توانید به‌درستی استدلال کنید که چون `String(null)` می‌شود `"null"`، پس `String([null])` هم باید بشود `"null"`. ادعای معقولی است. پس مقصر واقعی همان است.

*Implicit* coercion خودش اینجا شر نیست. حتی *explicit* coercion یعنی `[null]` به `string` به `""` منجر می‌شود. آنچه در تناقض است این است که آیا اصلاً معقول است مقدارهای `array` به معادل محتوایشان stringify شوند و دقیقاً چطور. پس ناراحتیتان را به قوانین `String( [..] )` معطوف کنید، چون منشأ دیوانگی آنجاست. شاید اصلاً نباید stringification coercion برای `array`ها باشد؟ اما آن downsides زیادی در بخش‌های دیگر زبان دارد.

gotcha معروف دیگر:

```js
0 == "\n";		// true
```

همان‌طور که قبلاً با `""` خالی گفتیم، `"\n"` (یا `" "` یا هر ترکیب whitespace دیگر) از طریق `ToNumber` coerce می‌شود و نتیجه `0` است. چه مقدار `number` دیگری برای whitespace انتظار دارید coerce شود؟ آیا اذیت می‌کند که *explicit* یعنی `Number(" ")` مقدار `0` بدهد؟

واقعاً تنها مقدار `number` معقول دیگر که stringهای خالی یا stringهای whitespace می‌توانستند به آن coerce شوند `NaN` است. اما آیا *واقعاً* بهتر بود؟ مقایسهٔ `" " == NaN` البته ناموفق می‌شد، اما روشن نیست که واقعاً *هیچ* از نگرانی‌های زیرین را حل کرده باشیم.

احتمال اینکه یک برنامهٔ JS واقعی به‌خاطر `0 == "\n"` ناموفق شود به‌شدت نادر است و چنین corner caseهایی به‌راحتی قابل اجتناب‌اند.

تبدیل type **همیشه** corner case دارد، در هر زبانی — چیزی خاص coercion نیست. مسائل اینجا دربارهٔ زیر سؤال بردن مجموعهٔ خاصی از corner caseهاست (و شاید به‌حق!؟)، اما آن استدلال برجسته‌ای علیه کل مکانیزم coercion نیست.

نتیجهٔ کلام: تقریباً هر coercion دیوانه بین *مقدارهای معمولی* که احتمالاً به آن برخورد می‌کنید (جز ترفندهای عمدی `valueOf()` یا `toString()` مثل قبل) به فهرست هفت‌موردی gotchaهای coercion که شناسایی کردیم خلاصه می‌شود.

برای مقایسه با این ۲۴ مورد مشکوک به gotchaهای coercion، فهرست دیگری مثل این در نظر بگیرید:

```js
42 == "43";							// false
"foo" == 42;						// false
"true" == true;						// false

42 == "42";							// true
"foo" == [ "foo" ];					// true
```

در این موارد غیرfalsy و غیرcorner (و به‌راستی تعداد بی‌نهایت مقایسه می‌توانیم در این فهرست بگذاریم)، نتایج coercion کاملاً امن، معقول و قابل توضیح‌اند.

#### Sanity Check

خب، قطعاً وقتی عمیق به *implicit* coercion نگاه کردیم چیزهای دیوانه پیدا کردیم. عجیب نیست که بیشتر توسعه‌دهندگان ادعا می‌کنند coercion شر است و باید اجتناب شود، درست!؟

اما یک قدم عقب برویم و sanity check کنیم.

از نظر مقیاس مقایسه، *یک فهرست* از هفت coercion مشکل‌ساز داریم، اما *فهرست دیگری* از (حداقل ۱۷، اما در واقع بی‌نهایت) coercion داریم که کاملاً سالمه و قابل توضیح‌اند.

اگر به دنبال مثال کتاب درسی «دور ریختن بچه با آب حمام» هستید، این است: دور ریختن کل coercion (فهرست بی‌نهایت بزرگ رفتارهای امن و مفید) به‌خاطر فهرستی به‌راستی فقط هفت gotcha.

واکنش محتاطانه‌تر این است که بپرسیم: «چطور می‌توانم از بخش‌های *خوب* بی‌شمار coercion استفاده کنم، اما از چند بخش *بد* اجتناب کنم؟»

دوباره به فهرست *بد* نگاه کنیم:

```js
"0" == false;			// true -- UH OH!
false == 0;				// true -- UH OH!
false == "";			// true -- UH OH!
false == [];			// true -- UH OH!
"" == 0;				// true -- UH OH!
"" == [];				// true -- UH OH!
0 == [];				// true -- UH OH!
```

چهار مورد از هفت مورد این فهرست مقایسهٔ `== false` را شامل می‌شوند که قبلاً گفتیم **همیشه، همیشه** باید اجتناب کنید. قانون به‌راحتی قابل یادآوری است.

حالا فهرست به سه تا رسید.

```js
"" == 0;				// true -- UH OH!
"" == [];				// true -- UH OH!
0 == [];				// true -- UH OH!
```

آیا این coercionهای معقولی هستند که در یک برنامهٔ جاوااسکریپت معمولی انجام می‌دهید؟ تحت چه شرایطی واقعاً اتفاق می‌افتند؟

فکر نمی‌کنم احتمال زیادی داشته باشد که واقعاً در برنامه‌تان در یک تست boolean از `== []` استفاده کنید، حداقل اگر بدانید چه می‌کنید. احتمالاً به‌جای آن `== ""` یا `== 0` می‌کنید، مثل:

```js
function doSomething(a) {
	if (a == "") {
		// ..
	}
}
```

اگر تصادفاً `doSomething(0)` یا `doSomething([])` فراخوانی کنید oops دارید. سناریوی دیگر:

```js
function doSomething(a,b) {
	if (a == b) {
		// ..
	}
}
```

باز هم می‌تواند بشکند اگر مثلاً `doSomething("",0)` یا `doSomething([],"")` بکنید.

پس با وجود اینکه موقعیت‌هایی *می‌توانند* وجود داشته باشند که این coercionها شما را بگزند و می‌خواهید دور آن‌ها مراقب باشید، احتمالاً روی کل پایگاه کدتان خیلی رایج نیستند.

#### استفادهٔ امن از Implicit Coercion

مهم‌ترین توصیه‌ای که می‌توانم بدهم: برنامه‌تان را بررسی کنید و استدلال کنید چه مقدارهایی می‌توانند در هر طرف مقایسهٔ `==` ظاهر شوند. برای اجتناب مؤثر از مسائل چنین مقایسه‌هایی، چند قانون اکتشافی برای دنبال کردن:

۱. اگر هر طرف مقایسه می‌تواند مقدارهای `true` یا `false` داشته باشد، هرگز، هرگز از `==` استفاده نکنید.
۲. اگر هر طرف مقایسه می‌تواند مقدارهای `[]`، `""` یا `0` داشته باشد، جداً در نظر بگیرید از `==` استفاده نکنید.

در این سناریوها، تقریباً قطعاً بهتر است به‌جای `==` از `===` استفاده کنید تا از coercion ناخواسته اجتناب شود. آن دو قانون ساده را دنبال کنید و تقریباً همهٔ gotchaهای coercion که می‌توانند منطقاً به شما آسیب بزنند مؤثراً اجتناب می‌شوند.

**صریح‌تر/پرگویی‌تر بودن در این موارد از سردردهای زیاد جلوگیری می‌کند.**

سؤال `==` در مقابل `===` واقعاً به‌درستی این‌طور مطرح می‌شود: آیا باید برای یک مقایسه coercion اجازه دهید یا نه؟

موارد زیادی هست که چنین coercion می‌تواند مفید باشد و به شما اجازه دهد برخی منطق مقایسه را خلاصه‌تر بیان کنید (مثل با `null` و `undefined`).

در کل طرح، نسبتاً کم هستند مواردی که *implicit* coercion واقعاً خطرناک است. اما در آن جاها، برای امنیت حتماً از `===` استفاده کنید.

**نکته:** جای دیگر که coercion تضمین شده *نمی‌زند* با عملگر `typeof` است. `typeof` همیشه یکی از هفت string برمی‌گرداند (فصل ۱ را ببینید) و هیچ‌کدام string خالی `""` نیست. بنابراین هیچ موردی نیست که بررسی type یک مقدار به *implicit* coercion برخورد کند. `typeof x == "function"` صددرصد به‌اندازهٔ `typeof x === "function"` امن و قابل اعتماد است. به‌راستی، مشخصات می‌گوید الگوریتم در این وضعیت یکسان خواهد بود. پس فقط کورکورانه همه‌جا `===` استفاده نکنید فقط چون ابزارهای کدتان می‌گویند، یا (بدتر از همه) چون در کتابی به شما گفته شده **فکر نکنید**. شما مالک کیفیت کدتان هستید.

آیا *implicit* coercion شر و خطرناک است؟ در چند مورد بله، اما به‌طور کلی نه.

توسعه‌دهندهٔ مسئول و بالغ باشید. بیاموزید چطور از قدرت coercion (هم *explicit* و هم *implicit*) به‌طور مؤثر و امن استفاده کنید. و به اطرافیانتان هم همین را بیاموزانید.
