# Implicit Coercion

*Implicit* coercion به تبدیل‌های type اشاره دارد که پنهان هستند، با اثرات جانبی کمتر واضحی که به‌طور ضمنی از عمل‌های دیگر رخ می‌دهند. به‌عبارت دیگر، *implicit coercion*ها هر تبدیل type هستند که (برای شما) واضح نیستند.

در حالی که هدف *explicit* coercion روشن است (صریح و خواناتر کردن کد)، شاید *خیلی* واضح باشد که *implicit* coercion هدف مخالف دارد: سخت‌تر کردن درک کد.

در ظاهر، فکر می‌کنم منشأ بخش زیادی از خشم نسبت به coercion همین‌جاست. اکثر شکایت‌ها دربارهٔ «coercion جاوااسکریپت» در واقع (خواه بدانند یا نه) به *implicit* coercion معطوف است.

**توجه:** Douglas Crockford، نویسندهٔ *"JavaScript: The Good Parts"*، در بسیاری از سخنرانی‌ها و نوشته‌های کنفرانس ادعا کرده که coercion جاوااسکریپت باید اجتناب شود. اما به‌نظر می‌رسد منظورش این است که *implicit* coercion بد است (به نظر او). با این حال، اگر کد خودش را بخوانید، مثال‌های زیادی از coercion پیدا می‌کنید، هم *implicit* و هم *explicit*! در واقع، به‌نظر می‌رسد ناراحتی او عمدتاً متوجه عملیات `==` است، اما همان‌طور که در این فصل خواهید دید، آن فقط بخشی از مکانیزم coercion است.

پس **آیا implicit coercion** شر است؟ خطرناک است؟ نقص در طراحی JavaScript است؟ باید به هر قیمتی از آن اجتناب کنیم؟

شرط می‌بندم بیشتر شما خوانندگان مایلید با اشتیاق فریاد بزنید: «بله!»

**این‌قدر سریع نه.** حرفم را بشنوید.

نگاه دیگری به *implicit* coercion و آنچه می‌تواند باشد بیندازیم، نه فقط اینکه «مخالف نوع خوب explicit coercion است». آن خیلی محدود است و یک nuance مهم را از دست می‌دهد.

هدف *implicit* coercion را این‌طور تعریف کنیم: کاهش پرگویی، boilerplate و/یا جزئیات پیاده‌سازی غیرضروری که کدمان را با نوفه‌ای شلوغ می‌کند که از منظور مهم‌تر منحرف می‌کند.

### ساده‌سازی به‌طور ضمنی

قبل از رسیدن به JavaScript، اجازه دهید چیزی شبه‌کد از یک زبان با type قوی فرضی پیشنهاد کنم برای illustration:

```js
SomeType x = SomeType( AnotherType( y ) )
```

در این مثال، یک مقدار با type دلخواه در `y` دارم که می‌خواهم به type یعنی `SomeType` تبدیل کنم. مشکل این است که این زبان نمی‌تواند مستقیم از هرچه الان `y` است به `SomeType` برود. به یک مرحلهٔ میانی نیاز دارد که ابتدا به `AnotherType` تبدیل کند و بعد از `AnotherType` به `SomeType`.

حالا اگر آن زبان (یا تعریفی که خودتان با زبان می‌توانید بسازید) *فقط* به شما اجازه می‌داد بگویید:

```js
SomeType x = SomeType( y )
```

آیا به‌طور کلی موافق نیستید که تبدیل type اینجا را ساده کردیم تا «نوفه» غیرضروری مرحلهٔ تبدیل میانی را کم کنیم؟ یعنی آیا *واقعاً* این‌قدر مهم است، دقیقاً اینجا در این نقطهٔ کد، ببینیم و با این واقعیت که `y` ابتدا به `AnotherType` می‌رود و بعد به `SomeType` سر و کار داشته باشیم؟

بعضی استدلال می‌کنند، حداقل در بعضی شرایط، بله. اما فکر می‌کنم استدلالی برابر می‌توان برای بسیاری شرایط دیگر کرد که اینجا ساده‌سازی **در واقع به خوانایی کد کمک می‌کند** با انتزاع یا پنهان کردن چنین جزئیاتی، یا در خود زبان یا در انتزاع‌های خودمان.

بدون شک، پشت صحنه، جایی، مرحلهٔ تبدیل میانی هنوز اتفاق می‌افتد. اما اگر آن جزئیات از دید اینجا پنهان باشد، می‌توانیم فقط به رساندن `y` به type یعنی `SomeType` به‌عنوان عملیات کلی فکر کنیم و جزئیات شلوغ را پنهان کنیم.

هرچند قیاس کاملی نیست، آنچه در بقیهٔ این فصل استدلال می‌کنم این است که *implicit* coercion در JS را می‌توان مشابه کمکی مشابه برای کدتان در نظر گرفت.

اما **و این خیلی مهم است**، این یک ادعای نامحدود و مطلق نیست. قطعاً شرهای زیادی در *implicit* coercion کمین کرده‌اند که به کدتان بیشتر از هر بهبود خوانایی احتمالی آسیب می‌زنند. واضح است که باید بیاموزیم چگونه از چنین ساختارهایی اجتناب کنیم تا کدمان را با انواع باگ مسموم نکنیم.

بسیاری از توسعه‌دهندگان معتقدند اگر یک مکانیزم بتواند کار مفید **A** را بکند اما همچنین بتوان سوءاستفاده یا استفادهٔ غلط کرد و کار وحشتناک **Z** را انجام داد، باید آن مکانیزم را یک‌جا دور بریزیم، فقط برای امنیت.

تشویق من به شما: به آن راضی نشوید. «با آب حمام بچه را هم دور نریزید.» فرض نکنید *implicit* coercion همه‌اش بد است چون فکر می‌کنید هرچه دیده‌اید «بخش‌های بد» آن بوده. فکر می‌کنم اینجا «بخش‌های خوب» هم هست و می‌خواهم به بیشترتان کمک و الهام دهم تا آن‌ها را پیدا و بپذیرید!

### ضمنی: Stringها <--> Numberها

قبل‌تر در این فصل *صریح* coercion بین مقدارهای `string` و `number` را بررسی کردیم. حالا همان کار را با رویکردهای *implicit* coercion بررسی می‌کنیم. اما قبل از آن باید به nuanceهای عملیاتی بپردازیم که *به‌طور ضمنی* coercion را اعمال می‌کنند.

عملگر `+` overload شده تا هم جمع `number` و هم الحاق `string` را انجام دهد. پس JS چطور می‌فهمد کدام نوع عملیات را می‌خواهید؟ در نظر بگیرید:

```js
var a = "42";
var b = "0";

var c = 42;
var d = 0;

a + b; // "420"
c + d; // 42
```

چه تفاوتی باعث `"420"` در مقابل `42` می‌شود؟ تصور غلط رایج این است که تفاوت این است که آیا یکی یا هر دو عملوند `string` است، چون یعنی `+` الحاق `string` فرض می‌کند. هرچند تا حدی درست است، پیچیده‌تر از آن است.

در نظر بگیرید:

```js
var a = [1,2];
var b = [3,4];

a + b; // "1,23,4"
```

هیچ‌کدام از این عملوندها `string` نیست، اما واضح است که هر دو به `string` coerce شدند و بعد الحاق `string` شروع شد. پس واقعاً چه اتفاقی می‌افتد؟

(**هشدار:** صحبت عمیق مشخصات می‌آید، پس دو پاراگراف بعد را اگر ترسناک است رد کنید!)

-----

طبق بخش ۱۱.۶.۱ مشخصات ES5، الگوریتم `+` (وقتی مقدار `object` عملوند است) الحاق می‌کند اگر یا عملوند از قبل `string` باشد، یا اگر مراحل بعد نمایش `string` تولید کنند. پس وقتی `+` برای هر عملوند یک `object` (شامل `array`) می‌گیرد، ابتدا عملیات انتزاعی `ToPrimitive` (بخش ۹.۱) را روی مقدار فراخوانی می‌کند، که سپس الگوریتم `[[DefaultValue]]` (بخش ۸.۱۲.۸) را با hint زمینهٔ `number` فراخوانی می‌کند.

اگر دقیق توجه کنید، متوجه می‌شوید این عملیات الان با نحوهٔ برخورد عملیات انتزاعی `ToNumber` با `object`ها یکسان است (بخش «`ToNumber`» قبلی را ببینید). عملیات `valueOf()` روی `array` نمی‌تواند primitive ساده تولید کند، پس به نمایش `toString()` می‌رسد. پس آن دو `array` به‌ترتیب می‌شوند `"1,2"` و `"3,4"`. حالا `+` آن دو `string` را مثل معمول الحاق می‌کند: `"1,23,4"`.

-----

آن جزئیات شلوغ را کنار بگذاریم و به توضیح ساده‌شدهٔ قبلی برگردیم: اگر هر عملوند `+` یک `string` باشد (یا با مراحل بالا بشود!)، عملیات الحاق `string` خواهد بود. در غیر این صورت همیشه جمع عددی است.

**توجه:** یک coercion gotcha معمولاً نقل‌شده `[] + {}` در مقابل `{} + []` است، چون آن دو عبارت به‌ترتیب به `"[object Object]"` و `0` منجر می‌شوند. با این حال بیشتر دارد و آن جزئیات را در بخش «Blocks» فصل ۵ پوشش می‌دهیم.

این برای *implicit* coercion چه معنایی دارد؟

می‌توانید یک `number` را به `string` به‌سادگی با «جمع» کردن آن `number` و `string` خالی `""` coerce کنید:

```js
var a = 42;
var b = a + "";

b; // "42"
```

**نکته:** جمع عددی با عملگر `+` جابه‌جایی‌پذیر است، یعنی `2 + 3` همان `3 + 2` است. الحاق `string` با `+` واضحاً به‌طور کلی جابه‌جایی‌پذیر نیست، **اما** در مورد خاص `""` عملاً جابه‌جایی‌پذیر است، چون `a + ""` و `"" + a` نتیجهٔ یکسان می‌دهند.

خیلی رایج/اصطلاحی است که با عملیات `+ ""` (به‌طور *ضمنی*) `number` را به `string` coerce کنیم. در واقع، جالب است که حتی بعضی از منتقدان صریح *implicit* coercion باز هم این رویکرد را در کد خودشان استفاده می‌کنند، به‌جای یکی از جایگزین‌های *explicit* آن.

**فکر می‌کنم این مثال خوبی** از یک فرم مفید در *implicit* coercion است، با وجود اینکه چقدر این مکانیزم مورد انتقاد قرار می‌گیرد!

در مقایسهٔ این *implicit* coercion یعنی `a + ""` با مثال قبلیمان یعنی `String(a)` *explicit* coercion، یک quirk اضافی هست که باید بدانید. به‌خاطر نحوهٔ کار عملیات انتزاعی `ToPrimitive`، `a + ""` روی مقدار `a` یعنی `valueOf()` را فراخوانی می‌کند که مقدار برگشتی آن در نهایت از طریق عملیات داخلی `ToString` به `string` تبدیل می‌شود. اما `String(a)` فقط مستقیماً `toString()` را فراخوانی می‌کند.

هر دو رویکرد در نهایت به `string` منجر می‌شوند، اما اگر به‌جای مقدار primitive معمولی `number` از `object` استفاده کنید، ممکن است لزوماً *همان* مقدار `string` را نگیرید!

در نظر بگیرید:

```js
var a = {
	valueOf: function() { return 42; },
	toString: function() { return 4; }
};

a + "";			// "42"

String( a );	// "4"
```

به‌طور کلی این نوع gotcha شما را نمی‌گزد مگر واقعاً بخواهید ساختارهای داده و عملیات گیج‌کننده بسازید، اما اگر برای یک `object` هم `valueOf()` و هم `toString()` خودتان را تعریف می‌کنید مراقب باشید، چون نحوهٔ coercion مقدار می‌تواند روی نتیجه اثر بگذارد.

جهت دیگر چطور؟ چطور می‌توانیم *به‌طور ضمنی* از `string` به `number` coerce کنیم؟

```js
var a = "3.14";
var b = a - 0;

b; // 3.14
```

عملگر `-` فقط برای تفریق عددی تعریف شده، پس `a - 0` مقدار `a` را مجبور می‌کند به `number` coerce شود. هرچند به‌مراتب کمتر رایج، `a * 1` یا `a / 1` هم همان نتیجه را می‌داد، چون آن عملگرها هم فقط برای عملیات عددی تعریف شده‌اند.

مقدارهای `object` با عملگر `-` چطور؟ داستان مشابه `+` بالا:

```js
var a = [3];
var b = [1];

a - b; // 2
```

هر دو مقدار `array` باید `number` شوند، اما ابتدا به `string` coerce می‌شوند (با سریال‌سازی مورد انتظار `toString()`)، و بعد به `number` coerce می‌شوند تا تفریق `-` روی آن‌ها انجام شود.

پس آیا *implicit* coercion مقدارهای `string` و `number` شر زشتی است که همیشه داستان‌های وحشت دربارهٔ آن شنیده‌اید؟ به‌نظر شخصی من نه.

`b = String(a)` (*explicit*) را با `b = a + ""` (*implicit*) مقایسه کنید. فکر می‌کنم می‌توان برای هر دو رویکرد استدلال کرد که در کدتان مفیدند. قطعاً `b = a + ""` در برنامه‌های JS به‌مراتب رایج‌تر است و utility خودش را ثابت می‌کند صرف‌نظر از *احساسات* دربارهٔ مزایا یا خطرات *implicit* coercion به‌طور کلی.

### ضمنی: Booleanها --> Numberها

فکر می‌کنم موردی که *implicit* coercion واقعاً می‌درخشد ساده‌سازی انواع خاصی از منطق `boolean` پیچیده به جمع عددی ساده است. البته این تکنیک همه‌کاره نیست، بلکه راه‌حل خاص برای موارد خاص است.

در نظر بگیرید:

```js
function onlyOne(a,b,c) {
	return !!((a && !b && !c) ||
		(!a && b && !c) || (!a && !b && c));
}

var a = true;
var b = false;

onlyOne( a, b, b );	// true
onlyOne( b, a, b );	// true

onlyOne( a, b, a );	// false
```

این ابزار `onlyOne(..)` فقط وقتی باید `true` برگرداند که دقیقاً یکی از آرگومان‌ها `true`/truthy باشد. از *implicit* coercion برای بررسی‌های truthy و *explicit* coercion برای بقیه از جمله مقدار برگشتی نهایی استفاده می‌کند.

اما اگر لازم بود آن ابزار بتواند چهار، پنج یا بیست پرچم را به همان شکل handle کند چطور؟ تصور پیاده‌سازی کدی که همهٔ آن ترکیب‌های مقایسه را handle کند خیلی سخت است.

اما اینجاست که coercion مقدارهای `boolean` به `number`ها (`0` یا `1`، واضحاً) می‌تواند خیلی کمک کند:

```js
function onlyOne() {
	var sum = 0;
	for (var i=0; i < arguments.length; i++) {
		// skip falsy values. same as treating
		// them as 0's, but avoids NaN's.
		if (arguments[i]) {
			sum += arguments[i];
		}
	}
	return sum == 1;
}

var a = true;
var b = false;

onlyOne( b, a );		// true
onlyOne( b, a, b, b, b );	// true

onlyOne( b, b );		// false
onlyOne( b, a, b, b, b, a );	// false
```

**توجه:** البته به‌جای حلقهٔ `for` در `onlyOne(..)` می‌توانستید از ابزار `reduce(..)` در ES5 به‌صورت خلاصه‌تر استفاده کنید، اما نمی‌خواستم مفاهیم را مخفی کنم.

اینجا به coercionهای `1` برای true/truthy اتکا می‌کنیم و همه را عددی جمع می‌کنیم. `sum += arguments[i]` از *implicit* coercion استفاده می‌کند تا این اتفاق بیفتد. اگر یک و فقط یک مقدار در فهرست `arguments` برابر `true` باشد، جمع عددی `1` می‌شود، در غیر این صورت جمع `1` نمی‌شود و بنابراین شرط مطلوب برقرار نیست.

البته می‌توانستیم این را با *explicit* coercion هم انجام دهیم:

```js
function onlyOne() {
	var sum = 0;
	for (var i=0; i < arguments.length; i++) {
		sum += Number( !!arguments[i] );
	}
	return sum === 1;
}
```

ابتدا از `!!arguments[i]` برای اجبار coercion مقدار به `true` یا `false` استفاده می‌کنیم. برای اینکه بتوانید مقدارهای غیر-`boolean` هم بدهید، مثل `onlyOne( "42", 0 )`، و باز هم درست کار کند (وگرنه به الحاق `string` می‌رسیدید و منطق غلط می‌شد).

وقتی مطمئن شدیم `boolean` است، coercion *explicit* دیگری با `Number(..)` می‌کنیم تا مطمئن شویم مقدار `0` یا `1` است.

آیا فرم *explicit* coercion این ابزار «به‌تر» است؟ از دام `NaN` که در توضیحات کد گفته شد اجتناب می‌کند. اما در نهایت بستگی به نیازتان دارد. به‌نظر شخصی من نسخهٔ قبلی با اتکا به *implicit* coercion ظریف‌تر است (اگر `undefined` یا `NaN` نمی‌دهید)، و نسخهٔ *explicit* به‌طور غیرضروری پرگویی‌تر است.

اما مثل تقریباً همهٔ آنچه اینجا بحث می‌کنیم، قضاوت است.

**توجه:** صرف‌نظر از رویکرد *implicit* یا *explicit*، به‌راحتی می‌توانید انواع `onlyTwo(..)` یا `onlyFive(..)` بسازید با فقط عوض کردن مقایسهٔ نهایی از `1` به `2` یا `5`. این به‌مراتب راحت‌تر از اضافه کردن یک دسته عبارت `&&` و `||` است. پس به‌طور کلی coercion در این مورد خیلی مفید است.

### ضمنی: * --> Boolean

حالا به *implicit* coercion به مقدارهای `boolean` می‌پردازیم، چون به‌مراتب رایج‌ترین و همچنین به‌مراتب بالقوه مشکل‌سازترین است.

یادتان باشد، *implicit* coercion وقتی فعال می‌شود که مقداری را طوری استفاده کنید که مجبورش می‌کند تبدیل شود. برای عملیات عددی و `string` نسبتاً آسان است ببینیم coercionها چطور می‌توانند رخ دهند.

اما چه نوع عملیات عبارتی نیاز/اجبار (*به‌طور ضمنی*) coercion به `boolean` می‌کند؟

۱. عبارت تست در دستور `if (..)`.
۲. عبارت تست (بند دوم) در هدر `for ( .. ; .. ; .. )`.
۳. عبارت تست در حلقه‌های `while (..)` و `do..while(..)`.
۴. عبارت تست (بند اول) در عبارت‌های سه‌تایی `? :`.
۵. عملوند سمت چپ (که به‌عنوان عبارت تست عمل می‌کند — پایین را ببینید!) عملگرهای `||` («logical or») و `&&` («logical and»).

هر مقداری که در این زمینه‌ها استفاده شود و از قبل `boolean` نباشد با قوانین عملیات انتزاعی `ToBoolean` که قبلاً در این فصل گفتیم *به‌طور ضمنی* به `boolean` coerce می‌شود.

چند مثال ببینیم:

```js
var a = 42;
var b = "abc";
var c;
var d = null;

if (a) {
	console.log( "yep" );		// yep
}

while (c) {
	console.log( "nope, never runs" );
}

c = d ? a : b;
c;					// "abc"

if ((a && d) || c) {
	console.log( "yep" );		// yep
}
```

در همهٔ این زمینه‌ها، مقدارهای غیر-`boolean` *به‌طور ضمنی* به معادل `boolean`شان coerce می‌شوند تا تصمیم‌های تست گرفته شود.

### عملگرهای `||` و `&&`

احتمالاً عملگرهای `||` («logical or») و `&&` («logical and») را در بیشتر یا همهٔ زبان‌های دیگری که استفاده کرده‌اید دیده‌اید. پس طبیعی است فرض کنید در JavaScript هم اساساً مثل زبان‌های مشابه کار می‌کنند.

اینجا nuance بسیار کم‌شناخته‌شده اما خیلی مهمی هست.

در واقع استدلال می‌کنم این عملگرها را حتی نباید «عملگرهای logical ___» نامید، چون آن نام در توصیف کاری که می‌کنند ناقص است. اگر نام دقیق‌تر (اگر شاید دست‌وپاگیرتر) می‌دادم، آن‌ها را «عملگرهای selector» یا کامل‌تر «عملگرهای operand selector» می‌نامیدم.

چرا؟ چون در JavaScript در واقع به مقدار *logic* (یعنی `boolean`) منجر نمی‌شوند، برخلاف بعضی زبان‌های دیگر.

پس *چی* برمی‌گردانند؟ مقدار یکی (و فقط یکی) از دو عملوندشان را برمی‌گردانند. به‌عبارت دیگر، **یکی از مقدارهای دو عملوند را انتخاب می‌کنند**.

از بخش ۱۱.۱۱ مشخصات ES5 نقل می‌کنم:

> The value produced by a && or || operator is not necessarily of type Boolean. The value produced will always be the value of one of the two operand expressions.

Illustration می‌کنیم:

```js
var a = 42;
var b = "abc";
var c = null;

a || b;		// 42
a && b;		// "abc"

c || b;		// "abc"
c && b;		// null
```

**صبر کنید، چی!؟** به آن فکر کنید. در زبان‌هایی مثل C و PHP آن عبارت‌ها `true` یا `false` برمی‌گردانند، اما در JS (و Python و Ruby!) نتیجه از خود مقدارها می‌آید.

هر دو عملگر `||` و `&&` یک تست `boolean` روی **عملوند اول** (`a` یا `c`) انجام می‌دهند. اگر عملوند از قبل `boolean` نباشد (اینجا نیست)، یک coercion معمولی به `ToBoolean` رخ می‌دهد تا تست انجام شود.

برای عملگر `||`، اگر تست `true` باشد، عبارت `||` به مقدار عملوند *اول* (`a` یا `c`) منجر می‌شود. اگر تست `false` باشد، عبارت `||` به مقدار عملوند *دوم* (`b`) منجر می‌شود.

برعکس، برای عملگر `&&`، اگر تست `true` باشد، عبارت `&&` به مقدار عملوند *دوم* (`b`) منجر می‌شود. اگر تست `false` باشد، عبارت `&&` به مقدار عملوند *اول* (`a` یا `c`) منجر می‌شود.

نتیجهٔ عبارت `||` یا `&&` همیشه مقدار زیرین یکی از عملوندهاست، **نه** (احتمالاً coerced شده) نتیجهٔ تست. در `c && b`، `c` برابر `null` است و بنابراین falsy. اما خود عبارت `&&` به `null` (مقدار در `c`) منجر می‌شود، نه به `false` coerced شدهٔ استفاده‌شده در تست.

حالا می‌بینید این عملگرها چطور مثل «operand selector» عمل می‌کنند؟

نگاه دیگر به این عملگرها:

```js
a || b;
// roughly equivalent to:
a ? a : b;

a && b;
// roughly equivalent to:
a ? b : a;
```

**توجه:** `a || b` را «تقریباً معادل» با `a ? a : b` می‌خوانم چون نتیجه یکسان است، اما تفاوت ظریفی هست. در `a ? a : b` اگر `a` عبارت پیچیده‌تری بود (مثلاً با side effect مثل فراخوانی `function` و غیره)، آن عبارت `a` احتمالاً دو بار ارزیابی می‌شد (اگر ارزیابی اول truthy بود). در مقابل، برای `a || b` عبارت `a` فقط یک بار ارزیابی می‌شود و آن مقدار هم برای تست coercive و هم برای مقدار نتیجه (در صورت مناسب) استفاده می‌شود. همان nuance برای عبارت‌های `a && b` و `a ? b : a` هم اعمال می‌شود.

یک کاربرد بسیار رایج و مفید این رفتار، که احتمال خوبی هست قبلاً استفاده کرده و کاملاً نفهمیده باشید:

```js
function foo(a,b) {
	a = a || "hello";
	b = b || "world";

	console.log( a + " " + b );
}

foo();					// "hello world"
foo( "yeah", "yeah!" );	// "yeah yeah!"
```

اصطلاح `a = a || "hello"` (گاهی نسخهٔ JavaScript از عملگر «null coalescing» در C# نامیده می‌شود) `a` را تست می‌کند و اگر مقداری نداشته باشد (یا فقط مقدار falsy نامطلوب)، مقدار پیش‌فرض پشتیبان (`"hello"`) را می‌دهد.

**مراقب باشید**، اما!

```js
foo( "That's it!", "" ); // "That's it! world" <-- Oops!
```

مشکل را دیدید؟ `""` به‌عنوان آرگومان دوم مقدار falsy است (بخش `ToBoolean` قبلی این فصل را ببینید)، پس تست `b = b || "world"` ناموفق می‌شود و مقدار پیش‌فرض `"world"` جایگزین می‌شود، حتی اگر احتمالاً منظور این بود که `""` صریحاً داده‌شده به `b` نسبت داده شود.

این اصطلاح `||` خیلی رایج و خیلی مفید است، اما فقط در مواردی استفاده کنید که *همهٔ مقدارهای falsy* باید رد شوند. در غیر این صورت باید در تستتان صریح‌تر باشید و احتمالاً به‌جای آن از سه‌تایی `? :` استفاده کنید.

این اصطلاح *default value assignment* آن‌قدر رایج (و مفید!) است که حتی کسانی که علناً و با شدت coercion جاوااسکریپت را محکوم می‌کنند در کد خودشان از آن استفاده می‌کنند!

`&&` چطور؟

اصطلاح دیگری هست که به‌مراتب کمتر معمولاً دستی نوشته می‌شود، اما minifierهای JS اغلب استفاده می‌کنند. عملگر `&&` عملوند دوم را «انتخاب» می‌کند فقط و فقط اگر عملوند اول به‌عنوان truthy تست شود، و این کاربرد گاهی «guard operator» نامیده می‌شود (همچنین بخش «Short Circuited» فصل ۵ را ببینید) — تست عبارت اول از عبارت دوم «محافظت» می‌کند:

```js
function foo() {
	console.log( a );
}

var a = 42;

a && foo(); // 42
```

`foo()` فقط فراخوانی می‌شود چون `a` به‌عنوان truthy تست می‌شود. اگر آن تست ناموفق می‌شد، این عبارت دستوری `a && foo()` فقط ساکت متوقف می‌شد — که «short circuiting» نامیده می‌شود — و هرگز `foo()` را فراخوانی نمی‌کرد.

باز هم، مردم به‌اندازهٔ کافی چنین چیزی نمی‌نویسند. معمولاً به‌جای آن `if (a) { foo(); }` می‌کنند. اما minifierهای JS `a && foo()` را انتخاب می‌کنند چون خیلی کوتاه‌تر است. پس حالا اگر مجبور شدید چنین کدی را decipher کنید، می‌دانید چه می‌کند و چرا.

خب، پس `||` و `&&` چند ترفند در آستین دارند، تا وقتی که بخواهید *implicit* coercion را در ترکیب بپذیرید.

**توجه:** هر دو اصطلاح `a = b || "something"` و `a && b()` به رفتار short circuiting وابسته‌اند که با جزئیات بیشتر در فصل ۵ پوشش می‌دهیم.

این واقعیت که این عملگرها در واقع `true` و `false` برنمی‌گردانند شاید الان کمی سرتان را به هم ریخته. احتمالاً می‌پرسید همهٔ دستورهای `if` و حلقه‌های `for` چطور کار کرده‌اند اگر عبارت‌های منطقی مرکب مثل `a && (b || c)` داشته‌اند.

نگران نباشید! آسمان نمی‌افتد. کدتان (احتمالاً) درست است. فقط احتمالاً قبلاً متوجه نشده بودید که *implicit* coercion به `boolean` **بعد از** ارزیابی عبارت مرکب در جریان بوده.

در نظر بگیرید:

```js
var a = 42;
var b = null;
var c = "foo";

if (a && (b || c)) {
	console.log( "yep" );
}
```

این کد هنوز همان‌طور که همیشه فکر می‌کردید کار می‌کند، با یک جزئیات ظریف اضافی. عبارت `a && (b || c)` *در واقع* به `"foo"` منجر می‌شود، نه `true`. پس دستور `if` *بعد* مقدار `"foo"` را مجبور می‌کند به `boolean` coerce شود که البته `true` می‌شود.

دیدید؟ دلیلی برای وحشت نیست. کدتان احتمالاً هنوز امن است. اما حالا بیشتر می‌دانید چطور کار می‌کند.

و حالا همچنین متوجه شده‌اید چنین کدی از *implicit* coercion استفاده می‌کند. اگر هنوز در «اردوگاه اجتناب از (implicit) coercion» هستید، باید برگردید و همهٔ آن تست‌ها را *explicit* کنید:

```js
if (!!a && (!!b || !!c)) {
	console.log( "yep" );
}
```

موفق باشید! ... شوخی می‌کنم.

### Symbol Coercion

تا اینجا تقریباً هیچ تفاوت نتیجهٔ قابل مشاهده‌ای بین *explicit* و *implicit* coercion نبوده — فقط خوانایی کد در میان بوده.

اما Symbolهای ES6 یک gotcha به سیستم coercion معرفی می‌کنند که باید مختصر بحث کنیم. به دلایلی که فراتر از محدودهٔ آنچه در این کتاب بحث می‌کنیم است، *explicit* coercion یک `symbol` به `string` مجاز است، اما *implicit* coercion همان مجاز نیست و خطا پرتاب می‌کند.

در نظر بگیرید:

```js
var s1 = Symbol( "cool" );
String( s1 );					// "Symbol(cool)"

var s2 = Symbol( "not cool" );
s2 + "";						// TypeError
```

مقدارهای `symbol` اصلاً نمی‌توانند به `number` coerce شوند (هر دو طرف خطا پرتاب می‌کنند)، اما عجیب است که هم *explicit* و هم *implicit* می‌توانند به `boolean` coerce شوند (همیشه `true`).

یکنواختی همیشه یادگیری را آسان‌تر می‌کند و استثناها هرگز سرگرم‌کننده نیست، اما فقط باید دور مقدارهای `symbol` جدید ES6 و نحوهٔ coercion آن‌ها مراقب باشیم.

خبر خوب: احتمالاً به‌شدت نادر است که لازم شود مقدار `symbol` را coerce کنید. نحوهٔ معمول استفادهٔ آن‌ها (فصل ۳ را ببینید) احتمالاً به‌طور عادی coercion نمی‌طلبد.
