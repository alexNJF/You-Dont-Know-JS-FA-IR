# عملیات‌های انتزاعی روی مقدارها

پیش از آنکه *explicit* و *implicit* coercion را بررسی کنیم، باید قوانین پایه‌ای را بیاموزیم که تعیین می‌کنند مقدارها چطور به `string`، `number` یا `boolean` *تبدیل* می‌شوند. مشخصات ES5 در بخش ۹ چند «عملیات انتزاعی» (اصطلاح فنی مشخصات برای «عملیات صرفاً داخلی») با قوانین تبدیل مقدار تعریف کرده است. به‌طور مشخص به این‌ها توجه خواهیم کرد: `ToString`، `ToNumber` و `ToBoolean`، و در درجهٔ کمتری به `ToPrimitive`.

### `ToString`

وقتی هر مقدار غیر از `string` به نمایش `string` coerce شود، تبدیل توسط عملیات انتزاعی `ToString` در بخش ۹.۸ مشخصات انجام می‌شود.

مقدارهای primitive داخلی stringification طبیعی دارند: `null` می‌شود `"null"`، `undefined` می‌شود `"undefined"` و `true` می‌شود `"true"`. مقدارهای `number` معمولاً به‌صورت طبیعی که انتظار دارید بیان می‌شوند، اما همان‌طور که در فصل ۲ گفتیم، عددهای خیلی کوچک یا خیلی بزرگ به‌صورت نمایی نمایش داده می‌شوند:

```js
// multiplying `1.07` by `1000`, seven times over
var a = 1.07 * 1000 * 1000 * 1000 * 1000 * 1000 * 1000 * 1000;

// seven times three digits => 21 digits
a.toString(); // "1.07e21"
```

برای objectهای معمولی، مگر اینکه خودتان مشخص کنید، پیش‌فرض `toString()` (موجود در `Object.prototype.toString()`) *`[[Class]]` داخلی* را برمی‌گرداند (فصل ۳ را ببینید)، مثلاً `"[object Object]"`.

اما همان‌طور که قبلاً نشان دادیم، اگر object متد `toString()` خودش را داشته باشد و آن object را به‌صورت شبیه `string` استفاده کنید، `toString()` آن به‌طور خودکار فراخوانی می‌شود و نتیجهٔ `string` آن فراخوانی به‌جای آن استفاده می‌شود.

**توجه:** از نظر فنی نحوهٔ coercion یک object به `string` از عملیات انتزاعی `ToPrimitive` (مشخصات ES5، بخش ۹.۱) می‌گذرد، اما آن جزئیات ظریف در بخش `ToNumber` همین فصل با جزئیات بیشتر پوشش داده شده‌اند، پس اینجا از آن‌ها می‌گذریم.

آرایه‌ها یک `toString()` پیش‌فرض بازنویسی‌شده دارند که به‌صورت الحاق (string) همهٔ مقدارهایش (هر کدام خود stringify شده‌اند) با `","` بین هر مقدار، stringify می‌کند:

```js
var a = [1,2,3];

a.toString(); // "1,2,3"
```

باز هم، `toString()` یا می‌تواند صریحاً فراخوانی شود، یا اگر یک غیر-`string` در زمینهٔ `string` استفاده شود به‌طور خودکار فراخوانی می‌شود.

#### JSON Stringification

کار دیگری که به‌نظر خیلی به `ToString` مربوط است وقتی است که از ابزار `JSON.stringify(..)` برای سریال‌سازی یک مقدار به مقدار `string` سازگار با JSON استفاده می‌کنید.

مهم است بدانید این stringification دقیقاً همان coercion نیست. اما چون به قوانین `ToString` بالا مربوط است، کمی منحرف می‌شویم و رفتارهای stringification مربوط به JSON را اینجا پوشش می‌دهیم.

برای بیشتر مقدارهای ساده، JSON stringification اساساً مثل تبدیل‌های `toString()` عمل می‌کند، با این تفاوت که نتیجهٔ سریال‌سازی *همیشه یک `string`* است:

```js
JSON.stringify( 42 );	// "42"
JSON.stringify( "42" );	// ""42"" (a string with a quoted string value in it)
JSON.stringify( null );	// "null"
JSON.stringify( true );	// "true"
```

هر مقدار *JSON-safe* را می‌توان با `JSON.stringify(..)` stringify کرد. اما *JSON-safe* چیست؟ هر مقداری که بتواند به‌درستی در نمایش JSON نمایش داده شود.

شاید راحت‌تر باشد مقدارهایی را در نظر بگیریم که **نه** JSON-safe هستند. چند مثال: `undefined`ها، `function`ها، (ES6+) `symbol`ها، و `object`هایی با ارجاع دایره‌ای (جایی که ارجاع‌های property در ساختار object یک چرخهٔ بی‌پایان بین یکدیگر ایجاد می‌کنند). این‌ها همگی مقدارهای نامعتبر برای ساختار استاندارد JSON هستند، عمدتاً چون به زبان‌های دیگری که مقدارهای JSON را مصرف می‌کنند قابل انتقال نیستند.

ابزار `JSON.stringify(..)` به‌طور خودکار مقدارهای `undefined`، `function` و `symbol` را وقتی به آن‌ها برخورد کند حذف می‌کند. اگر چنین مقداری در یک `array` پیدا شود، آن مقدار با `null` جایگزین می‌شود (تا اطلاعات موقعیت آرایه تغییر نکند). اگر به‌عنوان property یک `object` پیدا شود، آن property به‌سادگی حذف می‌شود.

در نظر بگیرید:

```js
JSON.stringify( undefined );					// undefined
JSON.stringify( function(){} );					// undefined

JSON.stringify( [1,undefined,function(){},4] );	// "[1,null,null,4]"
JSON.stringify( { a:2, b:function(){} } );		// "{"a":2}"
```

اما اگر سعی کنید یک `object` دارای ارجاع دایره‌ای را با `JSON.stringify(..)` stringify کنید، خطا پرتاب می‌شود.

JSON stringification رفتار خاصی دارد: اگر مقدار یک `object` متد `toJSON()` تعریف‌شده داشته باشد، این متد ابتدا فراخوانی می‌شود تا مقداری برای سریال‌سازی به‌دست آید.

اگر قصد دارید objectی را JSON stringify کنید که ممکن است مقدارهای نامعتبر JSON داشته باشد، یا اگر فقط مقدارهایی در `object` دارید که برای سریال‌سازی مناسب نیستند، باید یک متد `toJSON()` برای آن تعریف کنید که نسخهٔ *JSON-safe* آن `object` را برمی‌گرداند.

مثلاً:

```js
var o = { };

var a = {
	b: 42,
	c: o,
	d: function(){}
};

// create a circular reference inside `a`
o.e = a;

// would throw an error on the circular reference
// JSON.stringify( a );

// define a custom JSON value serialization
a.toJSON = function() {
	// only include the `b` property for serialization
	return { b: this.b };
};

JSON.stringify( a ); // "{"b":42}"
```

یک تصور غلط بسیار رایج این است که `toJSON()` باید نمایش stringification مربوط به JSON را برگرداند. احتمالاً نادرست است، مگر اینکه واقعاً بخواهید خود `string` را stringify کنید (معمولاً نه!). `toJSON()` باید مقدار واقعی معمولی (از هر type که باشد) مناسب را برگرداند، و خود `JSON.stringify(..)` stringification را انجام می‌دهد.

به‌عبارت دیگر، `toJSON()` باید «به مقدار JSON-safe مناسب برای stringification» تفسیر شود، نه «به رشتهٔ JSON» آن‌طور که بسیاری از توسعه‌دهندگان به‌اشتباه فرض می‌کنند.

در نظر بگیرید:

```js
var a = {
	val: [1,2,3],

	// probably correct!
	toJSON: function(){
		return this.val.slice( 1 );
	}
};

var b = {
	val: [1,2,3],

	// probably incorrect!
	toJSON: function(){
		return "[" +
			this.val.slice( 1 ).join() +
		"]";
	}
};

JSON.stringify( a ); // "[2,3]"

JSON.stringify( b ); // ""[2,3]""
```

در فراخوانی دوم، `string` برگشتی را stringify کردیم نه خود `array` را، که احتمالاً منظورمان نبود.

در حین صحبت از `JSON.stringify(..)`، چند قابلیت کمتر شناخته‌شده را هم بررسی می‌کنیم که همچنان می‌توانند بسیار مفید باشند.

می‌توان آرگومان دوم اختیاری به `JSON.stringify(..)` داد که *replacer* نامیده می‌شود. این آرگومان می‌تواند یک `array` یا یک `function` باشد. برای سفارشی‌سازی سریال‌سازی بازگشتی یک `object` با ارائهٔ مکانیزم فیلتر برای اینکه کدام propertyها باید شامل شوند و کدام نه استفاده می‌شود، مشابه نحوهٔ آماده‌سازی مقدار برای سریال‌سازی توسط `toJSON()`.

اگر *replacer* یک `array` باشد، باید آرایه‌ای از `string`ها باشد که هر کدام نام property مجاز برای گنجاندن در سریال‌سازی آن `object` را مشخص می‌کنند. اگر propertyای وجود داشته باشد که در این فهرست نیست، رد می‌شود.

اگر *replacer* یک `function` باشد، یک بار برای خود `object` و سپس یک بار برای هر property در آن `object` فراخوانی می‌شود، و هر بار دو آرگومان *key* و *value* به آن داده می‌شود. برای رد کردن یک *key* در سریال‌سازی، `undefined` برگردانید. در غیر این صورت، *value* داده‌شده را برگردانید.

```js
var a = {
	b: 42,
	c: "42",
	d: [1,2,3]
};

JSON.stringify( a, ["b","c"] ); // "{"b":42,"c":"42"}"

JSON.stringify( a, function(k,v){
	if (k !== "c") return v;
} );
// "{"b":42,"d":[1,2,3]}"
```

**توجه:** در حالت *replacer* به‌صورت `function`، آرگومان key یعنی `k` در فراخوانی اول `undefined` است (جایی که خود object `a` داده می‌شود). دستور `if` property با نام `"c"` را **فیلتر می‌کند**. Stringification بازگشتی است، پس آرایهٔ `[1,2,3]` هر یک از مقدارهایش (`1`، `2` و `3`) را به‌عنوان `v` به *replacer* می‌دهد، با indexهای (`0`، `1` و `2`) به‌عنوان `k`.

همچنین می‌توان آرگومان سوم اختیاری به `JSON.stringify(..)` داد به نام *space* که برای تورفتگی خروجی خواناتر و دوست‌دار انسان استفاده می‌شود. *space* می‌تواند یک عدد صحیح مثبت باشد که مشخص کند در هر سطح تورفتگی چند کاراکتر فاصله استفاده شود. یا *space* می‌تواند یک `string` باشد که در آن صورت تا ده کاراکتر اول مقدارش برای هر سطح تورفتگی استفاده می‌شود.

```js
var a = {
	b: 42,
	c: "42",
	d: [1,2,3]
};

JSON.stringify( a, null, 3 );
// "{
//    "b": 42,
//    "c": "42",
//    "d": [
//       1,
//       2,
//       3
//    ]
// }"

JSON.stringify( a, null, "-----" );
// "{
// -----"b": 42,
// -----"c": "42",
// -----"d": [
// ----------1,
// ----------2,
// ----------3
// -----]
// }"
```

یادتان باشد، `JSON.stringify(..)` به‌طور مستقیم شکلی از coercion نیست. اما آن را اینجا پوشش دادیم به دو دلیل که رفتارش را به coercion مربوط به `ToString` ربط می‌دهد:

۱. مقدارهای `string`، `number`، `boolean` و `null` همگی برای JSON اساساً مثل coerce شدن به مقدارهای `string` طبق قوانین عملیات انتزاعی `ToString` stringify می‌شوند.
۲. اگر مقدار `object` به `JSON.stringify(..)` بدهید و آن `object` متد `toJSON()` روی خودش داشته باشد، `toJSON()` به‌طور خودکار فراخوانی می‌شود تا (به‌نوعی) مقدار را قبل از stringification *JSON-safe* «coerce» کند.

### `ToNumber`

اگر هر مقدار غیر از `number` به‌گونه‌ای استفاده شود که لازم باشد `number` باشد، مثلاً در یک عملیات ریاضی، مشخصات ES5 عملیات انتزاعی `ToNumber` را در بخش ۹.۳ تعریف می‌کند.

مثلاً `true` می‌شود `1` و `false` می‌شود `0`. `undefined` می‌شود `NaN`، اما (عجیب است که) `null` می‌شود `0`.

`ToNumber` برای مقدار `string` اساساً مثل قوانین/نحو literalهای عددی کار می‌کند (فصل ۳ را ببینید). اگر ناموفق باشد، نتیجه `NaN` است (به‌جای خطای نحو مثل literalهای `number`). یک تفاوت مثال این است که عددهای اکتال با پیشوند `0` در این عملیات مثل اکتال عمل نمی‌کنند (فقط مثل اعشار مبنای ۱۰ معمولی)، هرچند چنین اکتال‌هایی به‌عنوان literalهای `number` معتبرند (فصل ۲ را ببینید).

**توجه:** تفاوت‌های نحو literalهای `number` و `ToNumber` روی مقدار `string` ظریف و بسیار دقیق هستند و بنابراین اینجا بیشتر پوشش داده نمی‌شوند. برای اطلاعات بیشتر به بخش ۹.۳.۱ مشخصات ES5 مراجعه کنید.

Objectها (و آرایه‌ها) ابتدا به معادل مقدار primitive خود تبدیل می‌شوند، و مقدار حاصل (اگر primitive باشد اما هنوز `number` نباشد) طبق قوانین `ToNumber` که همین الان گفتیم به `number` coerce می‌شود.

برای تبدیل به این معادل مقدار primitive، عملیات انتزاعی `ToPrimitive` (مشخصات ES5، بخش ۹.۱) از مقدار (با استفاده از عملیات داخلی `DefaultValue` — مشخصات ES5، بخش ۸.۱۲.۸) سؤال می‌کند که آیا متد `valueOf()` دارد یا نه. اگر `valueOf()` موجود باشد و مقدار primitive برگرداند، *همان* مقدار برای coercion استفاده می‌شود. اگر نه، اما `toString()` موجود باشد، مقدار را برای coercion فراهم می‌کند.

اگر هیچ‌کدام از این عملیات نتوانند مقدار primitive بدهند، `TypeError` پرتاب می‌شود.

از ES5 به بعد، می‌توانید چنین object غیرقابل‌coerce — بدون `valueOf()` و `toString()` — بسازید اگر مقدار `null` برای `[[Prototype]]` خود داشته باشد، که معمولاً با `Object.create(null)` ساخته می‌شود. برای اطلاعات بیشتر دربارهٔ `[[Prototype]]`ها عنوان *this & Object Prototypes* این مجموعه را ببینید.

**توجه:** نحوهٔ coercion به `number`ها را بعدتر در این فصل با جزئیات پوشش می‌دهیم، اما برای قطعه کد بعدی، فقط فرض کنید تابع `Number(..)` این کار را می‌کند.

در نظر بگیرید:

```js
var a = {
	valueOf: function(){
		return "42";
	}
};

var b = {
	toString: function(){
		return "42";
	}
};

var c = [4,2];
c.toString = function(){
	return this.join( "" );	// "42"
};

Number( a );			// 42
Number( b );			// 42
Number( c );			// 42
Number( "" );			// 0
Number( [] );			// 0
Number( [ "abc" ] );	// NaN
```

### `ToBoolean`

حالا کمی دربارهٔ نحوهٔ رفتار `boolean`ها در JS صحبت کنیم. **سردرگمی و تصور غلط زیادی** دربارهٔ این موضوع وجود دارد، پس دقیق توجه کنید!

اول و مهم‌تر، JS کلمات کلیدی واقعی `true` و `false` دارد و دقیقاً مثل `boolean`هایی که انتظار دارید رفتار می‌کنند. تصور غلط رایج این است که مقدارهای `1` و `0` با `true`/`false` یکسان‌اند. هرچند در زبان‌های دیگر ممکن است درست باشد، در JS مقدارهای `number`، `number` هستند و `boolean`ها، `boolean`. می‌توانید `1` را به `true` coerce کنید (و برعکس) یا `0` را به `false` (و برعکس). اما یکی نیستند.

#### مقدارهای Falsy

اما داستان همین‌جا تمام نمی‌شود. باید بگوییم مقدارهای غیر از آن دو `boolean` وقتی *به* معادل `boolean`شان coerce می‌شوند چطور رفتار می‌کنند.

همهٔ مقدارهای JavaScript را می‌توان به دو دسته تقسیم کرد:

۱. مقدارهایی که اگر به `boolean` coerce شوند می‌شوند `false`
۲. بقیه (که واضح است می‌شوند `true`)

شوخی نمی‌کنم. مشخصات JS فهرست مشخص و محدودی از مقدارها تعریف می‌کند که وقتی به مقدار `boolean` coerce شوند به `false` coerce می‌شوند.

چطور می‌دانیم فهرست چیست؟ در مشخصات ES5، بخش ۹.۲ عملیات انتزاعی `ToBoolean` را تعریف می‌کند که دقیقاً می‌گوید برای همهٔ مقدارهای ممکن وقتی سعی می‌کنید آن‌ها را «به boolean» coerce کنید چه اتفاقی می‌افتد.

از آن جدول، این‌ها را به‌عنوان فهرست به‌اصطلاح «falsy» می‌گیریم:

* `undefined`
* `null`
* `false`
* `+0`، `-0` و `NaN`
* `""`

همین. اگر مقداری در آن فهرست باشد، مقدار «falsy» است و اگر coercion به `boolean` را روی آن اعمال کنید به `false` coerce می‌شود.

با نتیجهٔ منطقی، اگر مقداری *در آن فهرست نباشد*، باید در *فهرست دیگری* باشد که آن را فهرست مقدارهای «truthy» می‌نامیم. اما JS واقعاً فهرست «truthy» به‌خودی‌خود تعریف نکرده. چند مثال می‌زند، مثلاً صریح می‌گوید همهٔ objectها truthy هستند، اما عمدتاً مشخصات فقط دلالت می‌کند: **هر چیزی که صریحاً در فهرست falsy نباشد پس truthy است.**

#### Falsy Objectها

یک لحظه، حتی عنوان این بخش متناقض به‌نظر می‌رسد. همین الان گفتم مشخصات همهٔ objectها را truthy می‌خواند، درست است؟ نباید چیزی به نام «falsy object» وجود داشته باشد.

این اصلاً چه معنایی می‌تواند داشته باشد؟

شاید وسوسه شوید فکر کنید یعنی object wrapper (فصل ۳ را ببینید) دور یک مقدار falsy (مثل `""`، `0` یا `false`). اما در آن *دام* نیفتید.

**توجه:** این یک شوخی ظریف مشخصات است که شاید بعضی‌تان متوجه شوید.

در نظر بگیرید:

```js
var a = new Boolean( false );
var b = new Number( 0 );
var c = new String( "" );
```

می‌دانیم هر سه مقدار اینجا object هستند (فصل ۳ را ببینید) که دور مقدارهای آشکاراً falsy پیچیده شده‌اند. اما آیا این objectها مثل `true` رفتار می‌کنند یا مثل `false`؟ پاسخ آسان است:

```js
var d = Boolean( a && b && c );

d; // true
```

پس هر سه مثل `true` رفتار می‌کنند، چون تنها راهی است که `d` می‌تواند `true` شود.

**نکته:** به `Boolean( .. )` دور عبارت `a && b && c` توجه کنید — شاید بپرسید چرا آنجاست. بعدتر در این فصل به آن برمی‌گردیم، پس یادداشت ذهنی کنید. برای پیش‌نمایش (از نظر جزئیات)، خودتان امتحان کنید اگر فقط `d = a && b && c` را بدون فراخوانی `Boolean( .. )` بنویسید `d` چه می‌شود!

پس اگر «falsy object»ها **فقط objectهای پیچیده‌شده دور مقدارهای falsy نیستند**، پس اصلاً چی هستند؟

قسمت trick این است که می‌توانند در برنامهٔ JS شما ظاهر شوند، اما در واقع بخشی از خود JavaScript نیستند.

**چی!؟**

مواردی هست که مرورگرها نوعی رفتار *exotic* برای مقدارها ساخته‌اند، یعنی همین ایدهٔ «falsy object»ها، روی معناشناسی معمولی JS.

یک «falsy object» مقداری است که شبیه و مثل یک object معمولی به‌نظر می‌رسد و عمل می‌کند (propertyها و غیره)، اما وقتی آن را به `boolean` coerce می‌کنید به مقدار `false` coerce می‌شود.

**چرا!؟**

معروف‌ترین مورد `document.all` است: یک (object) شبیه آرایه که *توسط DOM* (نه خود موتور JS) به برنامهٔ JS شما داده می‌شود و المان‌های صفحه را به برنامهٔ JS شما در معرض قرار می‌دهد. *قبلاً* مثل یک object معمولی رفتار می‌کرد — truthy عمل می‌کرد. اما دیگر نه.

خود `document.all` هرگز واقعاً «استاندارد» نبود و مدتهاست منسوخ/کنار گذاشته شده.

«پس نمی‌توانند آن را حذف کنند؟» متأسفانه، تلاش خوبی بود. کاش می‌توانستند. اما پایگاه‌های کد JS legacy زیادی وجود دارند که به استفاده از آن وابسته‌اند.

پس چرا آن را falsy کنند؟ چون coercionهای `document.all` به `boolean` (مثل در دستورهای `if`) تقریباً همیشه برای تشخیص IE قدیمی و غیراستاندارد استفاده می‌شد.

IE مدتهاست به رعایت استاندارد رسیده و در بسیاری موارد به‌اندازهٔ یا بیشتر از هر مرورگر دیگری وب را پیش می‌برد. اما همهٔ آن کد قدیمی `if (document.all) { /* it's IE */ }` هنوز آنجاست و احتمالاً بخش زیادی از آن هرگز از بین نمی‌رود. همهٔ این کد legacy هنوز فرض می‌کند در IE ده‌سال پیش اجرا می‌شود، که فقط به تجربهٔ مرور بد برای کاربران IE منجر می‌شود.

پس نمی‌توانیم `document.all` را کاملاً حذف کنیم، اما IE نمی‌خواهد کد `if (document.all) { .. }` دیگر کار کند تا کاربران IE مدرن منطق کد استاندارد-سازگار جدید را بگیرند.

«چه کار کنیم؟» **«فهمیدم! بیایید سیستم type جاوااسکریپت را خراب کنیم و وانمود کنیم `document.all` falsy است!»**

اوه. بد است. یک gotcha دیوانه‌وار که بیشتر توسعه‌دهندگان JS درکش نمی‌کنند. اما گزینهٔ دیگر (هیچ کاری دربارهٔ آن مشکلات بدون‌برنده نکردن) *فقط کمی* بدتر است.

پس... این داریم: «falsy object»های دیوانه و غیراستاندارد که مرورگرها به JavaScript اضافه کرده‌اند. هورا!

#### مقدارهای Truthy

برگردیم به فهرست truthy. مقدارهای truthy دقیقاً چه هستند؟ یادتان باشد: **یک مقدار truthy است اگر در فهرست falsy نباشد.**

در نظر بگیرید:

```js
var a = "false";
var b = "0";
var c = "''";

var d = Boolean( a && b && c );

d;
```

انتظار دارید `d` اینجا چه مقداری داشته باشد؟ باید یا `true` باشد یا `false`.

`true` است. چرا؟ چون با وجود اینکه محتوای آن مقدارهای `string` شبیه مقدارهای falsy به‌نظر می‌رسد، خود مقدارهای `string` همگی truthy هستند، چون `""` تنها مقدار `string` در فهرست falsy است.

این‌ها چطور؟

```js
var a = [];				// empty array -- truthy or falsy?
var b = {};				// empty object -- truthy or falsy?
var c = function(){};	// empty function -- truthy or falsy?

var d = Boolean( a && b && c );

d;
```

بله، حدس زدید، `d` اینجا هنوز `true` است. چرا؟ همان دلیل قبلی. با وجود آنچه به‌نظر می‌رسد، `[]`، `{}` و `function(){}` در فهرست falsy نیستند و بنابراین مقدارهای truthy هستند.

به‌عبارت دیگر، فهرست truthy بی‌نهایت طولانی است. ساختن چنین فهرستی غیرممکن است. فقط می‌توانید یک فهرست falsy متناهی بسازید و *آن* را مراجعه کنید.

پنج دقیقه وقت بگذارید، فهرست falsy را روی یک یادداشت برای مانیتورتان بنویسید، یا اگر ترجیح می‌دهید حفظش کنید. به‌هرحال، هر وقت لازم داشتید به‌راحتی می‌توانید فهرست truthy مجازی را با پرسیدن اینکه در فهرست falsy هست یا نه بسازید.

اهمیت truthy و falsy در درک نحوهٔ رفتار یک مقدار است اگر آن را (صریح یا ضمنی) به مقدار `boolean` coerce کنید. حالا که آن دو فهرست را در ذهن دارید، می‌توانیم سراغ خود مثال‌های coercion برویم.
