# Automatic Semicolons

ASI (Automatic Semicolon Insertion) وقتی است که جاوااسکریپت در جاهای معینی از برنامهٔ JS شما یک `;` فرض می‌کند حتی اگر خودتان نگذاشته باشید.

چرا چنین می‌کند؟ چون اگر حتی یک `;` الزامی را حذف کنید برنامه‌تان شکست می‌خورد. چندان بخشش‌کننده نیست. ASI به JS اجازه می‌دهد در جاهای معینی که معمولاً فکر نمی‌کنند `;` لازم است تحمل داشته باشد.

مهم است توجه کنید که ASI فقط در حضور یک newline (یعنی شکست خط) اثر می‌گذارد. Semicolonها در وسط خط درج نمی‌شوند.

اساساً، اگر parser جاوااسکریپت خطی را parse کند که در آن خطای parser رخ می‌دهد (یک `;` مورد انتظار گم‌شده)، و بتواند معقولانه یکی درج کند، این کار را می‌کند. درج معقول چیست؟ فقط اگر بین انتهای یک statement و newline/شکست خط آن خط چیزی جز فاصله‌خالی و/یا کامنت نباشد.

در نظر بگیرید:

```js
var a = 42, b
c;
```

آیا JS باید `c` در خط بعد را بخشی از statement `var` بداند؟ قطعاً اگر یک `,` هر جا (حتی خط دیگر) بین `b` و `c` می‌آمد می‌دانست. اما چون نیست، JS به‌جایش فرض می‌کند که یک `;` ضمنی (در newline) بعد از `b` وجود دارد. پس، `c;` به‌عنوان یک expression statement مستقل می‌ماند.

به‌همین‌ترتیب:

```js
var a = 42, b = "foo";

a
b	// "foo"
```

این هنوز برنامهٔ معتبر بدون خطاست، چون expression statementها هم ASI می‌پذیرند.

جاهای معینی هست که ASI مفید است، مثلاً:

```js
var a = 42;

do {
	// ..
} while (a)	// <-- ; اینجا انتظار می‌رود!
a;
```

grammar بعد از حلقهٔ `do..while` به `;` نیاز دارد، اما بعد از حلقه‌های `while` یا `for` نه. اما بیشتر توسعه‌دهندگان یادشان نیست! پس ASI کمک می‌کند و یکی درج می‌کند.

همان‌طور که قبلاً در فصل گفتیم، بلوک‌های statement به خاتمهٔ `;` نیاز ندارند، پس ASI لازم نیست:

```js
var a = 42;

while (a) {
	// ..
} // <-- ; اینجا انتظار نمی‌رود
a;
```

مورد اصلی دیگر که ASI وارد عمل می‌شود با کلمات کلیدی `break`، `continue`، `return` و (در ES6) `yield` است:

```js
function foo(a) {
	if (!a) return
	a *= 2;
	// ..
}
```

statement `return` از newline به expression `a *= 2` کشیده نمی‌شود، چون ASI `;` خاتمه‌دهندهٔ statement `return` را فرض می‌کند. البته، statementهای `return` *می‌توانند* به‌راحتی چند خط را در بر بگیرند، فقط نه وقتی بعد از `return` چیزی جز newline/شکست خط نیست.

```js
function foo(a) {
	return (
		a * 2 + 3 / 12
	);
}
```

همان استدلال برای `break`، `continue` و `yield` هم اعمال می‌شود.

### Error Correction

یکی از جنگ‌های *مذهبی* داغ‌بحث در جامعهٔ JS ( besides تب در مقابل فاصله) این است که آیا باید شدیداً/انحصاراً به ASI تکیه کرد یا نه.

بیشتر، اما نه همه، semicolonها اختیاری‌اند، اما آن دو `;` در هدر حلقهٔ `for ( .. ) ..` الزامی‌اند.

در طرف موافق این بحث، بسیاری از توسعه‌دهندگان باور دارند ASI مکانیسم مفیدی است که به آن‌ها اجازه می‌دهد با حذف همهٔ `;`ها به‌جز آن‌هایی که strictly الزامی‌اند (که خیلی کم‌اند) کد مختصرتر (و «زیباتر») بنویسند. اغلب ادعا می‌شود ASI بسیاری از `;`ها را اختیاری می‌کند، پس برنامهٔ درست نوشته‌شده *بدون آن‌ها* با برنامهٔ درست نوشته‌شده *با آن‌ها* فرقی ندارد.

در طرف مخالف بحث، بسیاری از توسعه‌دهندگان دیگر ادعا می‌کنند *خیلی* جاها می‌تواند gotcha تصادفی باشد، به‌ویژه برای توسعه‌دهندگان تازه‌کار و کم‌تجربه، جایی که `;`های ناخواستهٔ به‌طور جادویی درج‌شده معنی را عوض می‌کنند. به‌همین‌ترتیب، بعضی استدلال می‌کنند اگر semicolon را حذف کنند، یک اشتباه آشکار است، و می‌خواهند ابزارهایشان (linterها و غیره) قبل از اینکه موتور JS اشتباه را زیر پرده *اصلاح* کند آن را بگیرند.

فقط نظر خودم را می‌گویم. خوانش سخت مشخصات یعنی ASI یک روال «اصلاح خطا» است. چه نوع خطایی، ممکن است بپرسید؟ به‌طور خاص، یک **خطای parser**. به عبارت دیگر، در تلاش برای کمتر شکست خوردن parser، ASI به آن اجازه می‌دهد تحمل‌کننده‌تر باشد.

اما تحمل چه چیزی؟ به نظر من، تنها راه رخ دادن یک **خطای parser** این است که برنامهٔ نادرست/خطادار برای parse به آن داده شود. پس، در حالی که ASI به‌طور سخت خطاهای parser را اصلاح می‌کند، تنها راه گرفتن چنین خطاهایی این است که اول خطاهای نگارش برنامه — حذف semicolonها جایی که قواعد grammar آن‌ها را می‌خواهند — وجود داشته باشد.

پس، صریح‌تر بگویم، وقتی می‌شنوم کسی ادعا می‌کند می‌خواهد «semicolonهای اختیاری» را حذف کند، مغزم آن ادعا را به «می‌خواهم پارس‌شکن‌ترین برنامه‌ای را بنویسم که هنوز کار کند» ترجمه می‌کند.

این را موضعی مضحک برای گرفتن می‌دانم و استدلال‌های ذخیرهٔ ضربه‌های کلید و داشتن کد «زیباتر» را در بهترین حالت ضعیف می‌دانم.

علاوه بر این، موافق نیستم این همان بحث فاصله در مقابل تب باشد — که کاملاً cosmetic است — بلکه معتقدم مسئلهٔ اساسی نوشتن کدی است که به الزامات grammar پایبند باشد در مقابل کدی که به استثناهای grammar تکیه کند تا به‌زور رد شود.

نگاه دیگر این است که تکیه بر ASI اساساً newlineها را فاصله‌خالی «معنادار» در نظر گرفتن است. زبان‌های دیگر مثل Python فاصله‌خالی معنادار واقعی دارند. اما آیا واقعاً مناسب است جاوااسکریپت را در وضع فعلی دارای newline معنادار بدانیم؟
