# Operator Precedence

همان‌طور که در فصل ۴ پوشش دادیم، نسخهٔ جاوااسکریپت از `&&` و `||` از این نظر جالب است که یکی از عملوندهایشان را انتخاب و برمی‌گردانند، نه فقط به `true` یا `false` نتیجه دادن. اگر فقط دو عملوند و یک operator باشد استدلال درباره‌اش آسان است.

```js
var a = 42;
var b = "foo";

a && b;	// "foo"
a || b;	// 42
```

اما وقتی دو operator و سه عملوند در کار باشد چه؟

```js
var a = 42;
var b = "foo";
var c = [1,2,3];

a && b || c; // ???
a || b && c; // ???
```

برای فهمیدن اینکه آن expressionها به چه نتیجه می‌رسند، باید بفهمیم چه قواعدی نحوهٔ پردازش operatorها را وقتی بیش از یکی در یک expression حاضر است حکم می‌کنند.

این قواعد «operator precedence» نامیده می‌شوند.

شرط می‌بندم بیشتر خوانندگان فکر می‌کنند درک مناسبی از operator precedence دارند. اما مثل بقیهٔ چیزهایی که در این مجموعهٔ کتاب پوشش داده‌ایم، می‌خواهیم آن درک را زیر و رو کنیم ببینیم چقدر محکم است، و امیدواریم چند چیز جدید هم یاد بگیریم.

مثال بالا را به یاد بیاورید:

```js
var a = 42, b;
b = ( a++, a );

a;	// 43
b;	// 43
```

اما اگر `( )` را حذف کنیم چه می‌شود؟

```js
var a = 42, b;
b = a++, a;

a;	// 43
b;	// 42
```

صبر کنید! چرا مقدار انتساب‌شده به `b` عوض شد؟

چون operator `,` اولویت کمتری از operator `=` دارد. پس، `b = a++, a` به صورت `(b = a++), a` تفسیر می‌شود. چون (همان‌طور که قبلاً توضیح دادیم) `a++` *side effect بعدی* دارد، مقدار انتساب‌شده به `b` مقدار `42` قبل از تغییر `a` توسط `++` است.

این فقط مسئلهٔ سادهٔ نیاز به فهم operator precedence است. اگر می‌خواهید از `,` به‌عنوان operator سری statement استفاده کنید، مهم است بدانید که در واقع کمترین اولویت را دارد. هر operator دیگر محکم‌تر از `,` bind می‌شود.

حالا این مثال بالا را به یاد بیاورید:

```js
if (str && (matches = str.match( /[aeiou]/g ))) {
	// ..
}
```

گفتیم `( )` دور انتساب الزامی است، اما چرا؟ چون `&&` اولویت بالاتری از `=` دارد، پس بدون `( )` برای تحمیل binding، expression به‌جایش به صورت `(str && matches) = str.match..` رفتار می‌شد. اما این خطا می‌داد، چون نتیجهٔ `(str && matches)` قرار نیست یک متغیر باشد، بلکه یک مقدار است (در این مورد `undefined`)، و پس نمی‌تواند سمت چپ انتساب `=` باشد!

خب، پس احتمالاً فکر می‌کنید operator precedence را فهمیده‌اید.

بریم سراغ یک مثال پیچیده‌تر (که در چند بخش بعدی این فصل با خود حمل می‌کنیم) تا درکتان را *واقعاً* بیازماییم:

```js
var a = 42;
var b = "foo";
var c = false;

var d = a && b || c ? c || b ? a : c && b : a;

d;		// ??
```

خب، شیطانی است، قبول دارم. هیچ‌کس چنین رشته‌ای از expressionها نمی‌نویسد، درست؟ *احتمالاً* نه، اما از آن برای بررسی مسائل مختلف دربارهٔ زنجیر کردن چند operator استفاده می‌کنیم، که *واقعاً* کار بسیار رایجی است.

نتیجهٔ بالا `42` است. اما چطور می‌توانیم بدون اینکه فقط در برنامهٔ JS بگذاریم و بگذاریم جاوااسکریپت حلش کند به آن جواب برسیم به همان اندازه جالب است.

بیایید عمیق شویم.

سؤال اول — شاید اصلاً به ذهنتان نرسیده باشد — این است که آیا بخش اول (`a && b || c`) مثل `(a && b) || c` رفتار می‌کند یا مثل `a && (b || c)`؟ مطمئنید؟ آیا می‌توانید خودتان را متقاعد کنید که واقعاً متفاوت‌اند؟

```js
(false && true) || true;	// true
false && (true || true);	// false
```

پس ثابت شد متفاوت‌اند. اما باز هم، `false && true || true` چطور رفتار می‌کند؟ جواب:

```js
false && true || true;		// true
(false && true) || true;	// true
```

پس جواب را داریم. operator `&&` اول ارزیابی می‌شود و operator `||` دوم.

اما آیا فقط به‌خاطر پردازش چپ-به-راست است؟ ترتیب operatorها را برعکس کنیم:

```js
true || false && false;		// true

(true || false) && false;	// false -- نه
true || (false && false);	// true -- برنده!
```

حالا ثابت کردیم که `&&` اول و بعد `||` ارزیابی می‌شود، و در این مورد در واقع خلاف پردازش معمول چپ-به-راست بود.

پس چه چیزی باعث رفتار شد؟ **Operator precedence**.

هر زبان فهرست اولویت operator خودش را تعریف می‌کند. با این حال، نگران‌کننده است که چقدر کم پیش می‌آید توسعه‌دهندگان JS فهرست JS را خوانده باشند.

اگر خوب می‌دانستید، مثال‌های بالا اصلاً شما را نمی‌گرفتند، چون از قبل می‌دانستید که `&&` مقدم‌تر از `||` است. اما شرط می‌بندم تعداد قابل‌توجهی از خوانندگان مجبور شدند کمی فکر کنند.

| NOTE: |
| :--- |
| متأسفانه، مشخصات JS فهرست اولویت operator را در یک محل مناسب و واحد واقعاً ندارد. باید همهٔ قواعد grammar را parse کنید و بفهمید. پس سعی می‌کنیم بخش‌های رایج‌تر و مفیدتر را اینجا به شکل مناسب‌تری ارائه دهیم. برای فهرست کامل اولویت operator، «Operator Precedence» در سایت MDN را ببینید (* https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/Operator_Precedence). |

### Short Circuited

در فصل ۴، در یک یادداشت فرعی به ماهیت «short circuiting» operatorهایی مثل `&&` و `||` اشاره کردیم. حالا با جزئیات بیشتر به آن برگردیم.

برای هر دو operator `&&` و `||`، عملوند سمت راست **ارزیابی نمی‌شود** اگر عملوند سمت چپ برای تعیین نتیجهٔ عملیات کافی باشد. از این رو نام «short circuited» (یعنی در صورت امکان زود shortcut می‌زند).

مثلاً، با `a && b`، اگر `a` falsy باشد `b` ارزیابی نمی‌شود، چون نتیجهٔ عملوند `&&` از قبل قطعی است، پس دلیلی برای بررسی `b` نیست. به‌همین‌ترتیب، با `a || b`، اگر `a` truthy باشد نتیجهٔ عملوند از قبل قطعی است، پس دلیلی برای بررسی `b` نیست.

این short circuiting می‌تواند خیلی مفید باشد و معمولاً استفاده می‌شود:

```js
function doSomething(opts) {
	if (opts && opts.cool) {
		// ..
	}
}
```

بخش `opts` از تست `opts && opts.cool` نوعی guard عمل می‌کند، چون اگر `opts` تنظیم نشده باشد (یا `object` نباشد)، expression `opts.cool` خطا پرتاب می‌کند. شکست تست `opts` به‌علاوهٔ short circuiting یعنی `opts.cool` اصلاً ارزیابی نمی‌شود، پس خطا نیست!

به‌همین‌ترتیب می‌توانید از short circuiting با `||` استفاده کنید:

```js
function doSomething(opts) {
	if (opts.cache || primeCache()) {
		// ..
	}
}
```

اینجا اول `opts.cache` را بررسی می‌کنیم، و اگر وجود داشت، تابع `primeCache()` را فراخوانی نمی‌کنیم، و از کار احتمالی غیرضروری جلوگیری می‌کنیم.

### Tighter Binding

اما برگردیم به آن مثال statement پیچیدهٔ قبلی با همهٔ operatorهای زنجیره‌ای، به‌طور خاص بخش‌های operator سه‌گانهٔ `? :`. آیا operator `? :` اولویت بیشتر یا کمتری از operatorهای `&&` و `||` دارد؟

```js
a && b || c ? c || b ? a : c && b : a
```

آیا بیشتر شبیه این است:

```js
a && b || (c ? c || (b ? a : c) && b : a)
```

یا این؟

```js
(a && b || c) ? (c || b) ? a : (c && b) : a
```

جواب دومی است. اما چرا؟

چون `&&` مقدم‌تر از `||` است، و `||` مقدم‌تر از `? :`.

پس، expression `(a && b || c)` *اول* قبل از `? :`ای که در آن شرکت می‌کند ارزیابی می‌شود. توضیح رایج دیگر این است که `&&` و `||` «محکم‌تر bind می‌کنند» از `? :`. اگر برعکس بود، آنگاه `c ? c...` محکم‌تر bind می‌شد، و (مثل گزینهٔ اول) مثل `a && b || (c ? c..)` رفتار می‌کرد.

### Associativity

پس، operatorهای `&&` و `||` اول bind می‌شوند، بعد operator `? :`. اما در مورد چند operator با همان اولویت چه؟ آیا همیشه چپ-به-راست یا راست-به-چپ پردازش می‌کنند؟

به‌طور کلی، operatorها یا چپ-تداعی یا راست-تداعی‌اند، که به این اشاره دارد که **grouping از چپ اتفاق می‌افتد یا از راست**.

مهم است توجه کنید associativity *همان* پردازش چپ-به-راست یا راست-به-چپ نیست.

اما چرا مهم است پردازش چپ-به-راست یا راست-به-چپ باشد؟ چون expressionها می‌توانند side effect داشته باشند، مثلاً با فراخوانی تابع:

```js
var a = foo() && bar();
```

اینجا، `foo()` اول ارزیابی می‌شود، و بعد احتمالاً `bar()` بسته به نتیجهٔ expression `foo()`. این قطعاً می‌توانست رفتار برنامهٔ متفاوتی از وقتی که `bar()` قبل از `foo()` فراخوانی می‌شد نتیجه دهد.

اما این رفتار *فقط* پردازش چپ-به-راست است (رفتار پیش‌فرض در جاوااسکریپت!) — ربطی به associativity `&&` ندارد. در آن مثال، چون فقط یک `&&` هست و پس grouping مرتبط اینجا نیست، associativity اصلاً وارد بازی نمی‌شود.

اما با expressionی مثل `a && b && c`، grouping *ضمنی* اتفاق می‌افتد، یعنی یا `a && b` یا `b && c` اول ارزیابی می‌شود.

از نظر فنی، `a && b && c` به صورت `(a && b) && c` handle می‌شود، چون `&&` چپ-تداعی است (`||` هم همین‌طور). با این حال، جایگزین راست-تداعی یعنی `a && (b && c)` از نظر مشاهده‌پذیر همان‌طور رفتار می‌کند. برای همان مقدارها، همان expressionها به همان ترتیب ارزیابی می‌شوند.

| NOTE: |
| :--- |
| اگر فرضاً `&&` راست-تداعی بود، مثل وقتی که دستی از `( )` برای ایجاد grouping مثل `a && (b && c)` استفاده می‌کردید پردازش می‌شد. اما این هنوز **یعنی** نیست که `c` قبل از `b` پردازش می‌شد. راست-تداعی **یعنی** ارزیابی راست-به-چپ نیست، یعنی **grouping** راست-به-چپ. در هر صورت، صرف‌نظر از grouping/associativity، ترتیب سخت ارزیابی `a`، بعد `b`، بعد `c` خواهد بود (یعنی چپ-به-راست). |

پس خیلی مهم نیست که `&&` و `||` چپ-تداعی‌اند، جز برای دقیق بودن در نحوهٔ بحث از تعریف‌شان.

اما همیشه این‌طور نیست. بعضی operatorها بسته به چپ-تداعی در مقابل راست-تداعی خیلی متفاوت رفتار می‌کنند.

operator `? :` («ternary» یا «conditional») را در نظر بگیرید:

```js
a ? b : c ? d : e;
```

`? :` راست-تداعی است، پس کدام grouping نحوهٔ پردازش را نشان می‌دهد؟

* `a ? b : (c ? d : e)`
* `(a ? b : c) ? d : e`

جواب `a ? b : (c ? d : e)` است. برخلاف `&&` و `||` بالا، راست-تداعی اینجا واقعاً مهم است، چون `(a ? b : c) ? d : e` برای بعضی (اما نه همه!) ترکیب مقدارها *واقعاً* متفاوت رفتار می‌کند.

یک مثال:

```js
true ? false : true ? true : true;		// false

true ? false : (true ? true : true);	// false
(true ? false : true) ? true : true;	// true
```

حتی تفاوت‌های ظریف‌تر با ترکیب مقدارهای دیگر نهفته‌اند، حتی اگر نتیجهٔ نهایی یکی باشد. در نظر بگیرید:

```js
true ? false : true ? true : false;		// false

true ? false : (true ? true : false);	// false
(true ? false : true) ? true : false;	// false
```

از آن سناریو، همان نتیجهٔ نهایی یعنی grouping بی‌اثر است. با این حال:

```js
var a = true, b = false, c = true, d = true, e = false;

a ? b : (c ? d : e); // false, evaluates only `a` and `b`
(a ? b : c) ? d : e; // false, evaluates `a`, `b` AND `e`
```

پس، واضح ثابت کردیم که `? :` راست-تداعی است، و با respect به نحوهٔ رفتار operator وقتی با خودش زنجیره شود واقعاً مهم است.

مثال دیگر راست-تداعی (grouping) operator `=` است. مثال انتساب زنجیره‌ای قبلی این فصل را به یاد بیاورید:

```js
var a, b, c;

a = b = c = 42;
```

قبلاً گفتیم که `a = b = c = 42` با ارزیابی اول انتساب `c = 42`، بعد `b = ..`، و در نهایت `a = ..` پردازش می‌شود. چرا؟ به‌خاطر راست-تداعی، که در واقع statement را این‌طور رفتار می‌کند: `a = (b = (c = 42))`.

مثال expression انتساب پیچیدهٔ در حال اجرایمان از اوایل این فصل را به یاد دارید؟

```js
var a = 42;
var b = "foo";
var c = false;

var d = a && b || c ? c || b ? a : c && b : a;

d;		// 42
```

با دانش precedence و associativity، حالا باید بتوانیم کد را به رفتار grouping‌اش این‌طور تجزیه کنیم:

```js
((a && b) || c) ? ((c || b) ? a : (c && b)) : a
```

یا، اگر با تورفتگی ارائه دهیم راحت‌تر فهمیده شود:

```js
(
  (a && b)
    ||
  c
)
  ?
(
  (c || b)
    ?
  a
    :
  (c && b)
)
  :
a
```

حالا حلش کنیم:

1. `(a && b)` برابر `"foo"` است.
2. `"foo" || c` برابر `"foo"` است.
3. برای تست اول `?`، `"foo"` truthy است.
4. `(c || b)` برابر `"foo"` است.
5. برای تست دوم `?`، `"foo"` truthy است.
6. `a` برابر `42` است.

همین، تمام! جواب `42` است، همان‌طور که قبلاً دیدیم. واقعاً سخت نبود، نه؟

### Disambiguation

حالا باید درک خیلی بهتری از operator precedence (و associativity) داشته باشید و در فهم رفتار کد با چند operator زنجیره‌ای راحت‌تر باشید.

اما یک سؤال مهم باقی می‌ماند: آیا باید همهٔ ما کدی بنویسیم که همهٔ قواعد operator precedence/associativity را بفهمیم و کاملاً به آن‌ها تکیه کنیم؟ آیا فقط وقتی لازم است binding/ترتیب پردازش متفاوتی تحمیل کنیم از grouping دستی `( )` استفاده کنیم؟

یا، از طرف دیگر، آیا باید تشخیص دهیم که حتی اگر چنین قواعدی *واقعاً* قابل یادگیری‌اند، gotchaهای کافی هست که نادیده گرفتن precedence/associativity خودکار را توجیه کند؟ اگر چنین است، آیا پس باید همیشه از grouping دستی `( )` استفاده کنیم و همهٔ تکیه بر این رفتارهای خودکار را حذف کنیم؟

این بحث بسیار ذهنی است، و به‌شدت متقارن با بحث فصل ۴ دربارهٔ coercion *ضمنی* است. بیشتر توسعه‌دهندگان دربارهٔ هر دو بحث همین احساس را دارند: یا هر دو رفتار را می‌پذیرند و با انتظار از آن‌ها کد می‌زنند، یا هر دو را دور می‌ریزند و به idiomهای دستی/صریح می‌چسبند.

البته، نمی‌توانم این سؤال را قطعاً برای خواننده اینجا جواب دهم، همان‌طور که در فصل ۴ نتوانستم. اما مزایا و معایب را ارائه دادم، و امیدوارم درک عمیق‌تر کافی تشویق کرده باشم که بتوانید تصمیم‌های آگاهانه به‌جای hype-driven بگیرید.

به نظر من، یک حد وسط مهم وجود دارد. باید هم operator precedence/associativity و هم grouping دستی `( )` را در برنامه‌هایمان ترکیب کنیم — همان‌طور که در فصل ۴ برای استفادهٔ سالم/ایمن از coercion *ضمنی* استدلال می‌کنم، اما قطعاً آن را به‌طور انحصاری بدون حد توصیه نمی‌کنم.

مثلاً، `if (a && b && c) ..` برای من کاملاً OK است، و `if ((a && b) && c) ..` نمی‌نویسم فقط برای صریح کردن associativity، چون فکر می‌کنم بیش از حد verbose است.

از طرف دیگر، اگر لازم بود دو operator شرطی `? :` را با هم زنجیره کنم، قطعاً از grouping دستی `( )` استفاده می‌کردم تا منطق مورد نظرم کاملاً روشن شود.

پس، توصیهٔ من اینجا مشابه فصل ۴ است: **جایی که به کد کوتاه‌تر و تمیزتر منجر می‌شود از operator precedence/associativity استفاده کنید، اما در جاهایی که به وضوح و کاهش سردرگمی کمک می‌کند از grouping دستی `( )` استفاده کنید.**
