# Statements و Expressions

برای توسعه‌دهندگان نسبتاً رایج است که فرض کنند اصطلاحات «statement» و «expression» تقریباً معادل‌اند. اما اینجا باید بین این دو تمایز قائل شویم، چون در برنامه‌های JS ما تفاوت‌های بسیار مهمی وجود دارد.

برای ترسیم این تمایز، از اصطلاحاتی که شاید بیشتر با آن‌ها آشنا هستید وام می‌گیریم: زبان انگلیسی.

یک «جمله» (sentence) یک تشکیل کامل از کلمات است که فکری را بیان می‌کند. از یک یا چند «عبارت» (phrase) تشکیل شده که هر کدام می‌توانند با علائم نقطه‌گذاری یا کلمات ربط («و»، «یا» و غیره) به هم وصل شوند. یک عبارت خودش می‌تواند از عبارت‌های کوچک‌تر ساخته شود. بعضی عبارت‌ها ناقص‌اند و به تنهایی کار چندانی انجام نمی‌دهند، در حالی که بعضی دیگر می‌توانند مستقل بایستند. این قواعد در مجموع *grammar* زبان انگلیسی نامیده می‌شوند.

و در grammar جاوااسکریپت هم همین‌طور است. statementها جملات‌اند، expressionها عبارات‌اند، و operatorها ربط/نقطه‌گذاری‌اند.

هر expression در JS را می‌توان تا یک نتیجهٔ مقدار واحد و مشخص ارزیابی کرد. مثلاً:

```js
var a = 3 * 6;
var b = a;
b;
```

در این قطعه، `3 * 6` یک expression است (که به مقدار `18` ارزیابی می‌شود). اما `a` در خط دوم هم یک expression است، و `b` در خط سوم هم. expressionهای `a` و `b` هر دو به مقادیر ذخیره‌شده در آن متغیرها در آن لحظه ارزیابی می‌شوند، که اتفاقاً `18` است.

علاوه بر این، هر یک از سه خط یک statement است که expressionها را در بر می‌گیرد. `var a = 3 * 6` و `var b = a` «declaration statement» نامیده می‌شوند چون هر کدام یک متغیر اعلام می‌کنند (و اختیاراً مقداری به آن نسبت می‌دهند). انتساب‌های `a = 3 * 6` و `b = a` (بدون `var`) expressionهای انتساب نامیده می‌شوند.

خط سوم فقط expression `b` را در بر می‌گیرد، اما خودش هم یک statement است (هرچند چندان جالب نیست!). این به‌طور کلی «expression statement» نامیده می‌شود.

### Statement Completion Values

نکتهٔ نسبتاً کم‌شناخته این است که همهٔ statementها مقدار تکمیل (completion value) دارند (حتی اگر آن مقدار فقط `undefined` باشد).

چطور می‌توانید مقدار تکمیل یک statement را ببینید؟

بدیهی‌ترین جواب این است که statement را در کنسول توسعه‌دهندهٔ مرورگرتان تایپ کنید، چون وقتی آن را اجرا می‌کنید، کنسول به‌طور پیش‌فرض مقدار تکمیل آخرین statement اجراشده را گزارش می‌کند.

بیایید `var b = a` را در نظر بگیریم. مقدار تکمیل آن statement چیست؟

expression انتساب `b = a` به مقداری که انتساب داده شد (`18` در بالا) نتیجه می‌دهد، اما خود statement `var` به `undefined` نتیجه می‌دهد. چرا؟ چون statementهای `var` در مشخصات این‌طور تعریف شده‌اند. اگر `var a = 42;` را در کنسول بگذارید، به‌جای `42` مقدار `undefined` گزارش می‌شود.

| NOTE: |
| :--- |
| از نظر فنی کمی پیچیده‌تر است. در مشخصات ES5، بخش ۱۲.۲ «Variable Statement»، الگوریتم VariableDeclaration در واقع مقداری برمی‌گرداند (یک `string` شامل نام متغیر اعلام‌شده — عجیبه، نه!؟)، اما آن مقدار اساساً بلعیده می‌شود (به‌جز برای استفاده توسط حلقهٔ `for..in`) توسط الگوریتم VariableStatement، که یک مقدار تکمیل خالی (یعنی `undefined`) را تحمیل می‌کند. |

در واقع، اگر در کنسول (یا در محیط REPL جاوااسکریپت — ابزار read/evaluate/print/loop) زیاد آزمایش کرده باشید، احتمالاً دیده‌اید که بعد از statementهای مختلف `undefined` گزارش شده، و شاید هرگز نفهمیده‌اید چرا یا آن چیست. به‌سادگی، کنسول فقط مقدار تکمیل statement را گزارش می‌کند.

اما آنچه کنسول برای مقدار تکمیل چاپ می‌کند چیزی نیست که بتوانیم در برنامه‌مان استفاده کنیم. پس چطور می‌توانیم مقدار تکمیل را ضبط کنیم؟

این کار بسیار پیچیده‌تر است. قبل از توضیح *چطور*، بیایید *چرا* می‌خواهید این کار را بکنید بررسی کنیم.

باید نوع‌های دیگر مقدار تکمیل statement را در نظر بگیریم. مثلاً، هر بلوک معمولی `{ .. }` مقدار تکمیلش برابر مقدار تکمیل آخرین statement/expression موجود در آن است.

در نظر بگیرید:

```js
var b;

if (true) {
	b = 4 + 38;
}
```

اگر این را در کنسول/REPL تایپ کنید، احتمالاً `42` را می‌بینید، چون `42` مقدار تکمیل بلوک `if` است، که مقدار تکمیل آخرین expression statement انتسابی خودش یعنی `b = 4 + 38` را گرفته.

به عبارت دیگر، مقدار تکمیل یک بلوک مثل یک *implicit return* مقدار آخرین statement در بلوک است.

| NOTE: |
| :--- |
| از نظر مفهومی این در زبان‌هایی مثل CoffeeScript آشناست، که از `function`ها مقدار `return` ضمنی دارند که همان مقدار آخرین statement در تابع است. |

اما یک مشکل واضح وجود دارد. این نوع کد کار نمی‌کند:

```js
var a, b;

a = if (true) {
	b = 4 + 38;
};
```

نمی‌توانیم مقدار تکمیل یک statement را به‌صورت نحوی/دستوری آسان در متغیر دیگری انتساب دهیم (حداقل هنوز نه!).

پس چه کار می‌توانیم بکنیم؟

| WARNING: |
| :--- |
| فقط برای نمایش — در کد واقعی‌تان این کار را نکنید! |

می‌توانیم از تابع بدنام `eval(..)` (گاهی «evil» تلفظ می‌شود) استفاده کنیم تا این مقدار تکمیل را ضبط کنیم.

```js
var a, b;

a = eval( "if (true) { b = 4 + 38; }" );

a;	// 42
```

آره. خیلی زشت است. اما کار می‌کند! و نشان می‌دهد که مقدارهای تکمیل statement چیز واقعی‌اند که می‌توان نه فقط در کنسولمان بلکه در برنامه‌مان ضبط کرد.

یک پیشنهاد برای ES7 به نام «do expression» وجود دارد. ممکن است این‌طور کار کند:

```js
var a, b;

a = do {
	if (true) {
		b = 4 + 38;
	}
};

a;	// 42
```

expression `do { .. }` یک بلوک را اجرا می‌کند (با یک یا چند statement در آن)، و مقدار تکمیل آخرین statement داخل بلوک به مقدار تکمیل *خود* expression `do` تبدیل می‌شود، که بعد می‌توان آن را همان‌طور که نشان داده شد به `a` انتساب داد.

ایدهٔ کلی این است که بتوان statementها را مثل expression رفتار کرد — می‌توانند داخل statementهای دیگر ظاهر شوند — بدون نیاز به پیچیدن آن‌ها در یک function expression درون‌خطی و انجام یک `return ..` صریح.

فعلاً، مقدارهای تکمیل statement چیزی بیش از اطلاعات عمومی نیستند. اما احتمالاً با تکامل JS اهمیت بیشتری پیدا می‌کنند، و امیدواریم expressionهای `do { .. }` وسوسهٔ استفاده از چیزهایی مثل `eval(..)` را کم کنند.

| WARNING: |
| :--- |
| تکرار هشدار قبلی: از `eval(..)` دوری کنید. جدی. برای توضیح بیشتر به عنوان *Scope & Closures* این مجموعه مراجعه کنید. |

### Expression Side Effects

بیشتر expressionها side effect ندارند. مثلاً:

```js
var a = 2;
var b = a + 3;
```

expression `a + 3` خودش side effect نداشت، مثلاً تغییر `a`. نتیجه‌ای داشت که `5` است، و آن نتیجه در statement `b = a + 3` به `b` انتساب داده شد.

رایج‌ترین مثال یک expression با (احتمالی) side effect، expression فراخوانی تابع است:

```js
function foo() {
	a = a + 1;
}

var a = 1;
foo();		// result: `undefined`, side effect: changed `a`
```

expressionهای با side effect دیگر هم هست. مثلاً:

```js
var a = 42;
var b = a++;
```

expression `a++` دو رفتار جداگانه دارد. *اول*، مقدار فعلی `a` را برمی‌گرداند که `42` است (که بعد به `b` انتساب داده می‌شود). اما *بعد*، خود مقدار `a` را تغییر می‌دهد و آن را یکی زیاد می‌کند.

```js
var a = 42;
var b = a++;

a;	// 43
b;	// 42
```

بسیاری از توسعه‌دهندگان اشتباهاً باور می‌کنند که `b` مثل `a` مقدار `43` دارد. اما سردرگمی از در نظر نگرفتن کامل *زمان* side effectهای operator `++` است.

operator افزایش `++` و operator کاهش `--` هر دو unary operator هستند (فصل ۴ را ببینید)، که می‌توانند در موقعیت postfix («بعد») یا prefix («قبل») به کار روند.

```js
var a = 42;

a++;	// 42
a;		// 43

++a;	// 44
a;		// 44
```

وقتی `++` در موقعیت prefix به صورت `++a` به کار می‌رود، side effect آن (افزایش `a`) *قبل* از برگرداندن مقدار از expression رخ می‌دهد، نه *بعد* مثل `a++`.

| NOTE: |
| :--- |
| فکر می‌کنید `++a++` سینتکس قانونی باشد؟ اگر امتحان کنید، خطای `ReferenceError` می‌گیرید، اما چرا؟ چون operatorهای با side effect **به یک ارجاع متغیر** نیاز دارند تا side effectهایشان را روی آن اعمال کنند. برای `++a++`، بخش `a++` اول ارزیابی می‌شود (به‌خاطر اولویت operator — پایین‌تر ببینید)، که مقدار `a` را *قبل* از افزایش برمی‌گرداند. اما بعد سعی می‌کند `++42` را ارزیابی کند، که (اگر امتحان کنید) همان خطای `ReferenceError` را می‌دهد، چون `++` نمی‌تواند مستقیماً روی مقداری مثل `42` side effect داشته باشد. |

گاهی اشتباهاً فکر می‌شود می‌توان side effect *بعدی* `a++` را با پیچیدن آن در یک جفت `( )` کپسوله کرد، مثل:

```js
var a = 42;
var b = (a++);

a;	// 43
b;	// 42
```

متأسفانه، خود `( )` یک expression جدید پیچیده‌شده تعریف نمی‌کند که *بعد* از *side effect بعدی* expression `a++` ارزیابی شود، آن‌طور که امید داشتیم. در واقع، حتی اگر می‌کرد، `a++` اول `42` را برمی‌گرداند، و مگر expression دیگری داشته باشید که بعد از side effect `++` دوباره `a` را ارزیابی کند، از آن expression `43` نمی‌گیرید، پس به `b` مقدار `43` انتساب داده نمی‌شود.

یک گزینه هست: operator کامای سری statement، `,`. این operator به شما اجازه می‌دهد چند expression statement مستقل را در یک statement به هم وصل کنید:

```js
var a = 42, b;
b = ( a++, a );

a;	// 43
b;	// 43
```

| NOTE: |
| :--- |
| `( .. )` دور `a++, a` اینجا الزامی است. دلیلش اولویت operator است که بعداً در این فصل پوشش می‌دهیم. |

expression `a++, a` یعنی expression statement دوم `a` *بعد* از *side effectهای بعدی* expression statement اول `a++` ارزیابی می‌شود، یعنی مقدار `43` را برای انتساب به `b` برمی‌گرداند.

مثال دیگر operator با side effect، `delete` است. همان‌طور که در فصل ۲ نشان دادیم، `delete` برای حذف یک property از `object` یا یک slot از `array` به کار می‌رود. اما معمولاً فقط به‌صورت یک statement مستقل فراخوانی می‌شود:

```js
var obj = {
	a: 42
};

obj.a;			// 42
delete obj.a;	// true
obj.a;			// undefined
```

مقدار نتیجهٔ operator `delete` اگر عملیات درخواستی معتبر/مجاز باشد `true` است، وگرنه `false`. اما side effect operator این است که property (یا slot آرایه) را حذف می‌کند.

| NOTE: |
| :--- |
| معتبر/مجاز یعنی چه؟ propertyهای ناموجود، یا propertyهایی که وجود دارند و configurable هستند (فصل ۳ عنوان *this & Object Prototypes* این مجموعه را ببینید) از operator `delete` مقدار `true` برمی‌گردانند. وگرنه نتیجه `false` یا خطا خواهد بود. |

یک مثال آخر operator با side effect، که ممکن است هم واضح و هم غیرواضح باشد، operator انتساب `=` است.

در نظر بگیرید:

```js
var a;

a = 42;		// 42
a;			// 42
```

شاید به نظر نرسد که `=` در `a = 42` یک operator با side effect برای expression باشد. اما اگر مقدار نتیجهٔ statement `a = 42` را بررسی کنیم، همان مقداری است که تازه انتساب داده شد (`42`)، پس انتساب همان مقدار به `a` اساساً یک side effect است.

| TIP: |
| :--- |
| همان استدلال دربارهٔ side effect برای operatorهای انتساب مرکب مثل `+=`، `-=` و غیره هم برقرار است. مثلاً، `a = b += 2` اول به صورت `b += 2` (یعنی `b = b + 2`) پردازش می‌شود، و نتیجهٔ *همان* انتساب `=` بعد به `a` انتساب داده می‌شود. |

این رفتار که یک expression (یا statement) انتساب به مقدار انتساب‌شده نتیجه می‌دهد عمدتاً برای انتساب‌های زنجیره‌ای مفید است، مثل:

```js
var a, b, c;

a = b = c = 42;
```

اینجا، `c = 42` به `42` ارزیابی می‌شود (با side effect انتساب `42` به `c`)، بعد `b = 42` به `42` ارزیابی می‌شود (با side effect انتساب `42` به `b`)، و در نهایت `a = 42` ارزیابی می‌شود (با side effect انتساب `42` به `a`).

| WARNING: |
| :--- |
| اشتباه رایج توسعه‌دهندگان با انتساب زنجیره‌ای چیزی مثل `var a = b = 42` است. هرچند به نظر همان است، نیست. اگر آن statement بدون وجود یک `var b` جدا (جایی در scope) برای اعلام رسمی `b` رخ دهد، آنگاه `var a = b = 42` مستقیماً `b` را اعلام نمی‌کند. بسته به حالت `strict`، یا خطا پرتاب می‌شود یا یک global تصادفی ساخته می‌شود (عنوان *Scope & Closures* این مجموعه را ببینید). |

سناریوی دیگر برای در نظر گرفتن:

```js
function vowels(str) {
	var matches;

	if (str) {
		// pull out all the vowels
		matches = str.match( /[aeiou]/g );

		if (matches) {
			return matches;
		}
	}
}

vowels( "Hello World" ); // ["e","o","o"]
```

این کار می‌کند، و بسیاری از توسعه‌دهندگان چنین را ترجیح می‌دهند. اما با استفاده از یک اصطلاح که از side effect انتساب بهره می‌بریم، می‌توانیم با ترکیب دو statement `if` در یکی ساده‌تر کنیم:

```js
function vowels(str) {
	var matches;

	// pull out all the vowels
	if (str && (matches = str.match( /[aeiou]/g ))) {
		return matches;
	}
}

vowels( "Hello World" ); // ["e","o","o"]
```

| NOTE: |
| :--- |
| `( .. )` دور `matches = str.match..` الزامی است. دلیلش اولویت operator است که بعداً در بخش «Operator Precedence» این فصل پوشش می‌دهیم. |

من این سبک کوتاه‌تر را ترجیح می‌دهم، چون فکر می‌کنم روشن‌تر می‌کند که دو شرط در واقع به هم مربوط‌اند نه جدا. اما مثل بیشتر انتخاب‌های سبکی در JS، اینکه کدام *بهتر* است کاملاً نظر شخصی است.

### Contextual Rules

در قواعد grammar جاوااسکریپت جاهای زیادی هست که همان syntax بسته به محل/نحوهٔ استفاده معانی مختلف دارد. این نوع چیز می‌تواند به‌تنهایی سردرگمی قابل‌توجهی ایجاد کند.

اینجا همهٔ این موارد را فهرست نمی‌کنیم، فقط چند مورد رایج را برمی‌شماریم.

#### آکولادهای `{ .. }`

دو جای اصلی (و با تکامل JS بیشتر می‌شود!) وجود دارد که یک جفت آکولاد `{ .. }` در کدتان ظاهر می‌شود. هر کدام را ببینیم.

##### Object Literals

اول، به‌عنوان `object` literal:

```js
// assume there's a `bar()` function defined

var a = {
	foo: bar()
};
```

چطور می‌دانیم این یک `object` literal است؟ چون جفت `{ .. }` مقداری است که به `a` انتساب داده می‌شود.

| NOTE: |
| :--- |
| ارجاع `a` «l-value» (یعنی مقدار دست چپ) نامیده می‌شود چون هدف انتساب است. جفت `{ .. }` یک «r-value» (یعنی مقدار دست راست) است چون *فقط* به‌عنوان مقدار استفاده می‌شود (در این مورد به‌عنوان مبدأ انتساب). |

##### Labels

اگر بخش `var a =` قطعهٔ بالا را حذف کنیم چه می‌شود؟

```js
// assume there's a `bar()` function defined

{
	foo: bar()
}
```

بسیاری از توسعه‌دهندگان فرض می‌کنند جفت `{ .. }` فقط یک `object` literal مستقل است که جایی انتساب نمی‌شود. اما در واقع کاملاً متفاوت است.

اینجا، `{ .. }` فقط یک بلوک کد معمولی است. داشتن یک بلوک مستقل `{ .. }` مثل این در جاوااسکریپت خیلی idiom نیست (در زبان‌های دیگر بیشتر!), اما grammar معتبر JS است. به‌ویژه وقتی با اعلام‌های block-scoping با `let` ترکیب شود می‌تواند مفید باشد (عنوان *Scope & Closures* این مجموعه را ببینید).

بلوک کد `{ .. }` اینجا از نظر عملکردی تقریباً با بلوک کد متصل به یک statement مثل حلقهٔ `for`/`while`، شرط `if` و غیره یکسان است.

اما اگر بلوک معمولی کد است، آن syntax عجیب `foo: bar()` چیست و چطور قانونی است؟

به‌خاطر یک ویژگی کم‌شناخته (و صادقانه بگوییم، منع‌شده) در جاوااسکریپت به نام «labeled statements». `foo` یک label برای statement `bar()` است (که `;` پایانی آن حذف شده — بخش «Automatic Semicolons» بعداً در این فصل را ببینید). اما هدف labeled statement چیست؟

اگر جاوااسکریپت statement `goto` داشت، از نظر تئوری می‌توانستید بگویید `goto foo` و اجرا به آن محل در کد بپرد. معمولاً `goto`ها idiomهای وحشتناک کدنویسی دانسته می‌شوند چون کد را خیلی سخت‌تر فهم می‌کنند («spaghetti code»)، پس *خیلی خوب* است که جاوااسکریپت یک `goto` کلی ندارد.

با این حال، JS *از* یک شکل محدود و خاص `goto` پشتیبانی می‌کند: پرش‌های دارای label. هر دو statement `continue` و `break` می‌توانند اختیاراً یک label مشخص بپذیرند، که در آن صورت جریان برنامه نوعی مثل `goto` «می‌پرد». در نظر بگیرید:

```js
// `foo` labeled-loop
foo: for (var i=0; i<4; i++) {
	for (var j=0; j<4; j++) {
		// whenever the loops meet, continue outer loop
		if (j == i) {
			// jump to the next iteration of
			// the `foo` labeled-loop
			continue foo;
		}

		// skip odd multiples
		if ((j * i) % 2 == 1) {
			// normal (non-labeled) `continue` of inner loop
			continue;
		}

		console.log( i, j );
	}
}
// 1 0
// 2 0
// 2 1
// 3 0
// 3 2
```

| NOTE: |
| :--- |
| `continue foo` یعنی «برو به موقعیت دارای label 'foo' برای ادامه» نیست، بلکه یعنی «حلقه‌ای که label 'foo' دارد را با تکرار بعدی آن ادامه بده.» پس *واقعاً* یک `goto` دلخواه نیست. |

همان‌طور که می‌بینید، تکرار مضرب فرد `3 1` را رد کردیم، اما پرش حلقهٔ دارای label تکرارهای `1 1` و `2 2` را هم رد کرد.

شاید شکل کمی مفیدتر پرش دارای label با `break __` از داخل یک حلقهٔ درونی باشد که می‌خواهید از حلقهٔ بیرونی خارج شوید. بدون `break` دارای label، همین منطق گاهی می‌توانست نسبتاً awkward نوشته شود:

```js
// `foo` labeled-loop
foo: for (var i=0; i<4; i++) {
	for (var j=0; j<4; j++) {
		if ((i * j) >= 3) {
			console.log( "stopping!", i, j );
			// break out of the `foo` labeled loop
			break foo;
		}

		console.log( i, j );
	}
}
// 0 0
// 0 1
// 0 2
// 0 3
// 1 0
// 1 1
// 1 2
// stopping! 1 3
```

| NOTE: |
| :--- |
| `break foo` یعنی «برو به موقعیت دارای label 'foo' برای ادامه» نیست، بلکه یعنی «از حلقه/بلوکی که label 'foo' دارد خارج شو و *بعد* از آن ادامه بده.» دقیقاً یک `goto` به معنای سنتی نیست، نه؟ |

جایگزین `break` بدون label برای بالا احتمالاً باید یک یا چند تابع، دسترسی متغیر scope مشترک و غیره را درگیر کند. احتمالاً از `break` دارای label گیج‌کننده‌تر می‌شد، پس اینجا استفاده از `break` دارای label شاید گزینهٔ بهتری است.

یک label می‌تواند به یک بلوک غیرحلقه اعمال شود، اما فقط `break` می‌تواند به چنین label غیرحلقه‌ای ارجاع دهد. می‌توانید یک `break ___` دارای label از هر بلوک دارای label انجام دهید، اما نمی‌توانید یک label غیرحلقه را `continue ___` کنید، و نمی‌توانید یک `break` بدون label از یک بلوک انجام دهید.

```js
function foo() {
	// `bar` labeled-block
	bar: {
		console.log( "Hello" );
		break bar;
		console.log( "never runs" );
	}
	console.log( "World" );
}

foo();
// Hello
// World
```

حلقه/بلوک‌های دارای label بسیار غیررایج‌اند و اغلب مورد پسند نیستند. در صورت امکان بهتر است از آن‌ها دوری کنید؛ مثلاً به‌جای پرش‌های حلقه از فراخوانی تابع استفاده کنید. اما شاید موارد محدودی باشد که مفید باشند. اگر می‌خواهید از پرش دارای label استفاده کنید، حتماً با کامنت زیاد توضیح دهید چه می‌کنید!

باور بسیار رایج این است که JSON زیرمجموعهٔ درست JS است، پس یک رشتهٔ JSON (مثل `{"a":42}` — به نقل‌قول‌های دور نام property توجه کنید که JSON الزامی می‌کند!) برنامهٔ جاوااسکریپت معتبر فرض می‌شود. **درست نیست!** سعی کنید `{"a":42}` را در کنسول JS بگذارید، خطا می‌گیرید.

چون labelهای statement نمی‌توانند نقل‌قول دورشان داشته باشند، پس `"a"` یک label معتبر نیست، و بنابراین `:` نمی‌تواند درست بعد از آن بیاید.

پس JSON از نظر syntax زیرمجموعهٔ واقعی JS است، اما JSON به‌تنهایی grammar معتبر JS نیست.

یک تصور نادرست بسیار رایج در این راستا این است که اگر فایل JS را در تگ `<script src=..>` لود کنید که فقط محتوای JSON دارد (مثل از فراخوانی API)، داده به‌عنوان جاوااسکریپت معتبر خوانده می‌شود اما فقط برای برنامه در دسترس نیست. معمولاً گفته می‌شود JSON-P (عمل پیچیدن دادهٔ JSON در فراخوانی تابع، مثل `foo({"a":42})`) این عدم دسترسی را با فرستادن مقدار به یکی از توابع برنامه‌تان حل می‌کند.

**درست نیست!** مقدار کاملاً معتبر JSON یعنی `{"a":42}` به‌تنهایی در واقع خطای JS پرتاب می‌کند چون به‌عنوان بلوک statement با label نامعتبر تفسیر می‌شود. اما `foo({"a":42})` JS معتبر است چون در آن، `{"a":42}` یک مقدار `object` literal است که به `foo(..)` پاس داده می‌شود. پس به‌درستی گفته می‌شود **JSON-P باعث می‌شود JSON grammar معتبر JS شود!**

##### Blocks

یک gotcha رایج دیگر JS (مربوط به coercion — فصل ۴ را ببینید) این است:

```js
[] + {}; // "[object Object]"
{} + []; // 0
```

به نظر می‌رسد operator `+` بسته به اینکه عملوند اول `[]` باشد یا `{}` نتیجهٔ متفاوت می‌دهد. اما در واقع ربطی به آن ندارد!

در خط اول، `{}` در expression operator `+` ظاهر می‌شود، و بنابراین به‌عنوان یک مقدار واقعی (یک `object` خالی) تفسیر می‌شود. فصل ۴ توضیح داد که `[]` به `""` coercion می‌شود و بنابراین `{}` هم به مقدار `string` coercion می‌شود: `"[object Object]"`.

اما در خط دوم، `{}` به‌عنوان یک بلوک خالی مستقل `{}` (که کاری نمی‌کند) تفسیر می‌شود. بلوک‌ها به semicolon برای خاتمه نیاز ندارند، پس نبودش اینجا مشکلی نیست. در نهایت، `+ []` expressionی است که `[]` را *صریحاً* به `number` coercion می‌کند (فصل ۴ را ببینید)، که مقدار `0` است.

##### Object Destructuring

از ES6 به بعد، جای دیگر دیدن جفت‌های `{ .. }` در «destructuring assignments» است (عنوان *ES6 & Beyond* این مجموعه را برای اطلاعات بیشتر ببینید)، به‌طور خاص destructuring `object`. در نظر بگیرید:

```js
function getData() {
	// ..
	return {
		a: 42,
		b: "foo"
	};
}

var { a, b } = getData();

console.log( a, b ); // 42 "foo"
```

همان‌طور که احتمالاً می‌فهمید، `var { a , b } = ..` شکلی از انتساب destructuring در ES6 است، که تقریباً معادل است با:

```js
var res = getData();
var a = res.a;
var b = res.b;
```

| NOTE: |
| :--- |
| `{ a, b }` در واقع مخفف destructuring در ES6 برای `{ a: a, b: b }` است، پس هر دو کار می‌کنند، اما انتظار می‌رود شکل کوتاه‌تر `{ a, b }` شکل ترجیحی شود. |

Object destructuring با جفت `{ .. }` می‌تواند برای آرگومان‌های نام‌دار تابع هم به کار رود، که sugar برای همین نوع انتساب ضمنی property شیء است:

```js
function foo({ a, b, c }) {
	// no need for:
	// var a = obj.a, b = obj.b, c = obj.c
	console.log( a, b, c );
}

foo( {
	c: [1,2,3],
	a: 42,
	b: "foo"
} );	// 42 "foo" [1, 2, 3]
```

پس، contextی که جفت‌های `{ .. }` را در آن به کار می‌بریم کاملاً تعیین می‌کند معنی‌شان چیست، که تفاوت syntax و grammar را نشان می‌دهد. درک این ظرافت‌ها برای جلوگیری از تفسیرهای غیرمنتظره توسط موتور JS بسیار مهم است.

#### `else if` و بلوک‌های اختیاری

تصور نادرست رایج این است که جاوااسکریپت بند `else if` دارد، چون می‌توانید بکنید:

```js
if (a) {
	// ..
}
else if (b) {
	// ..
}
else {
	// ..
}
```

اما یک ویژگی پنهان grammar JS اینجاست: `else if` وجود ندارد. اما به statementهای `if` و `else` اجازه داده می‌شود اگر فقط یک statement داشته باشند `{ }` دور بلوک متصل‌شان را حذف کنند. قبلاً بارها دیده‌اید، بدون شک:

```js
if (a) doSomething( a );
```

بسیاری از راهنمای سبک JS اصرار می‌کنند همیشه دور یک بلوک تک‌statement از `{ }` استفاده کنید، مثل:

```js
if (a) { doSomething( a ); }
```

با این حال، همان قانون grammar دقیقاً برای بند `else` هم اعمال می‌شود، پس شکل `else if` که احتمالاً همیشه کد زده‌اید *در واقع* این‌طور parse می‌شود:

```js
if (a) {
	// ..
}
else {
	if (b) {
		// ..
	}
	else {
		// ..
	}
}
```

`if (b) { .. } else { .. }` یک statement واحد است که بعد از `else` می‌آید، پس می‌توانید یا `{ }` دورش را بگذارید یا نگذارید. به عبارت دیگر، وقتی از `else if` استفاده می‌کنید، از نظر فنی آن قانون رایج راهنمای سبک را می‌شکنید و فقط `else` خود را با یک statement `if` تعریف می‌کنید.

البته، اصطلاح `else if` بسیار رایج است و یک سطح تورفتگی کمتر نتیجه می‌دهد، پس جذاب است. هر طور که انجامش می‌دهید، فقط در راهنمای سبک/قواعد خودتان صریحاً ذکر کنید و فرض نکنید چیزهایی مثل `else if` قواعد grammar مستقیم‌اند.
