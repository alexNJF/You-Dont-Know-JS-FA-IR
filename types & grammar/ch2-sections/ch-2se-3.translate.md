# Numbers

JavaScript فقط یک نوع عددی دارد: `number`. این type هم مقدارهای «عدد صحیح» و هم اعداد اعشاری را شامل می‌شود. «عدد صحیح» را در گیومه گفتم چون مدت‌هاست که به JS انتقاد می‌شود که اعداد صحیح واقعی مثل زبان‌های دیگر ندارد. شاید روزی عوض شود، اما الان فقط `number` برای همه چیز داریم.

پس در JS، یک «عدد صحیح» فقط مقداری است که بخش اعشاری ندارد. یعنی `42.0` به‌اندازهٔ `42` «عدد صحیح» است.

مثل بیشتر زبان‌های مدرن، از جمله تقریباً همهٔ زبان‌های اسکریپتی، پیاده‌سازی `number`های JavaScript بر اساس استاندارد «IEEE 754» است که اغلب «floating-point» نامیده می‌شود. JavaScript به‌طور مشخص از فرمت «double precision» (یعنی «۶۴-بیتی باینری») این استاندارد استفاده می‌کند.

در وب مطالب خوب زیادی دربارهٔ جزئیات ذخیرهٔ اعداد اعشاری باینری در حافظه و نتیجهٔ آن انتخاب‌ها هست. چون درک الگوهای بیتی در حافظه برای استفادهٔ درست از `number`ها در JS ضروری نیست، جزئیات IEEE 754 را به خوانندهٔ علاقه‌مند واگذار می‌کنیم.

### Numeric Syntax

لیترال‌های عددی در JavaScript معمولاً به‌صورت اعشاری مبنای ۱۰ نوشته می‌شوند. مثلاً:

```js
var a = 42;
var b = 42.3;
```

قسمت جلوی مقدار اعشاری، اگر `0` باشد، اختیاری است:

```js
var a = 0.42;
var b = .42;
```

به‌طور مشابه، قسمت بعد از `.` (اعشاری)، اگر `0` باشد، اختیاری است:

```js
var a = 42.0;
var b = 42.;
```

**هشدار:** `42.` کم‌استفاده است و اگر می‌خواهید خوانندگان کدتان گیج نشوند احتمالاً ایدهٔ خوبی نیست. با این حال معتبر است.

به‌طور پیش‌فرض، بیشتر `number`ها به‌صورت اعشاری مبنای ۱۰ خروجی می‌شوند و صفرهای اعشاری انتها حذف می‌شوند. پس:

```js
var a = 42.300;
var b = 42.0;

a; // 42.3
b; // 42
```

عددهای خیلی بزرگ یا خیلی کوچک به‌طور پیش‌فرض به‌صورت نمادی (exponent) خروجی می‌شوند، مثل خروجی متد `toExponential()`:

```js
var a = 5E10;
a;					// 50000000000
a.toExponential();	// "5e+10"

var b = a * a;
b;					// 2.5e+21

var c = 1 / a;
c;					// 2e-11
```

چون مقدارهای `number` می‌توانند با wrapper شیء `Number` boxing شوند (فصل ۳ را ببینید)، مقدارهای `number` می‌توانند به متدهای `Number.prototype` (فصل ۳) دسترسی داشته باشند. مثلاً متد `toFixed(..)` اجازه می‌دهد مشخص کنید می‌خواهید مقدار با چند رقم اعشار نمایش داده شود:

```js
var a = 42.59;

a.toFixed( 0 ); // "43"
a.toFixed( 1 ); // "42.6"
a.toFixed( 2 ); // "42.59"
a.toFixed( 3 ); // "42.590"
a.toFixed( 4 ); // "42.5900"
```

توجه کنید خروجی در واقع نمایش `string` از `number` است و اگر بیشتر از رقم‌های مقدار بخواهید، سمت راست با `0` پر می‌شود.

`toPrecision(..)` شبیه است، اما مشخص می‌کند چند *رقم معنادار* برای نمایش مقدار به کار رود:

```js
var a = 42.59;

a.toPrecision( 1 ); // "4e+1"
a.toPrecision( 2 ); // "43"
a.toPrecision( 3 ); // "42.6"
a.toPrecision( 4 ); // "42.59"
a.toPrecision( 5 ); // "42.590"
a.toPrecision( 6 ); // "42.5900"
```

برای دسترسی به این متدها لازم نیست حتماً از متغیر استفاده کنید؛ می‌توانید مستقیم روی لیترال `number` فراخوانی کنید. اما با عملگر `.` باید دقت کنید. چون `.` کاراکتر عددی معتبر است، در صورت امکان اول به‌عنوان بخشی از لیترال `number` تفسیر می‌شود، نه به‌عنوان دسترسی به property.

```js
// invalid syntax:
42.toFixed( 3 );	// SyntaxError

// these are all valid:
(42).toFixed( 3 );	// "42.000"
0.42.toFixed( 3 );	// "0.420"
42..toFixed( 3 );	// "42.000"
```

`42.toFixed(3)` سینتکس نامعتبر است، چون `.` جزوی از لیترال `42.` بلعیده می‌شود (که معتبر است — بالا را ببینید!) و بعد دیگر عملگر property `.` برای دسترسی `.toFixed` وجود ندارد.

`42..toFixed(3)` کار می‌کند چون اولین `.` جزو `number` است و دومی عملگر property. اما احتمالاً عجیب به نظر می‌رسد و در کد واقعی JavaScript خیلی کم دیده می‌شود. در واقع فراخوانی مستقیم متد روی مقدارهای primitive چندان رایج نیست. رایج نبودن به معنی *بد* یا *غلط* نیست.

**توجه:** کتابخانه‌هایی هستند که `Number.prototype` از پیش‌تعریف‌شده را (فصل ۳) گسترش می‌دهند تا عملیات اضافه روی `number`ها ارائه دهند؛ در آن موارد استفاده از چیزی مثل `10..makeItRain()` برای اجرای انیمیشن باران پول ۱۰ ثانیه‌ای یا چیزهای مشابه کاملاً معتبر است.

این هم از نظر فنی معتبر است (به فاصله توجه کنید):

```js
42 .toFixed(3); // "42.000"
```

با این حال، به‌طور خاص برای لیترال `number` **این سبک کدنویسی به‌ویژه گیج‌کننده است** و فقط دیگر توسعه‌دهندگان (و خود آینده‌تان) را گیج می‌کند. از آن پرهیز کنید.

`number`ها را می‌توان به‌صورت نمادی (exponent) هم نوشت، که برای نمایش عددهای بزرگتر رایج است:

```js
var onethousand = 1E3;						// means 1 * 10^3
var onemilliononehundredthousand = 1.1E6;	// means 1.1 * 10^6
```

لیترال‌های `number` را می‌توان در مبنای دیگر هم نوشت، مثل باینری، اکتال و هگزادسیمال.

این فرمت‌ها در نسخه‌های فعلی JavaScript کار می‌کنند:

```js
0xf3; // hexadecimal for: 243
0Xf3; // ditto

0363; // octal for: 243
```

**توجه:** از ES6 به بعد در حالت `strict`، فرم `0363` برای لیترال اکتال دیگر مجاز نیست (فرم جدید را پایین ببینید). فرم `0363` در حالت غیر-`strict` هنوز مجاز است، اما بهتر است دیگر استفاده نکنید تا با آینده سازگار بمانید (و چون الان باید از حالت `strict` استفاده کنید!).

از ES6 به بعد این فرم‌های جدید هم معتبرند:

```js
0o363;		// octal for: 243
0O363;		// ditto

0b11110011;	// binary for: 243
0B11110011; // ditto
```

لطفاً به همکارانتان لطف کنید: هرگز از فرم `0O363` استفاده نکنید. `0` کنار `O` بزرگ فقط دعوت به گیجی است. همیشه پیشوندهای کوچک `0x`، `0b` و `0o` را به کار ببرید.

### Small Decimal Values

معروف‌ترین (یا بدنام‌ترین) اثر جانبی اعداد اعشاری باینری (که یادتان باشد در **همه** زبان‌هایی که از IEEE 754 استفاده می‌کنند هست — نه *فقط* JavaScript آن‌طور که خیلی‌ها فرض می‌کنند) این است:

```js
0.1 + 0.2 === 0.3; // false
```

از نظر ریاضی می‌دانیم آن عبارت باید `true` باشد. چرا `false` است؟

به‌طور خلاصه، نمایش `0.1` و `0.2` در اعشاری باینری دقیق نیست، پس وقتی جمع می‌شوند نتیجه دقیقاً `0.3` نیست. **خیلی** نزدیک است: `0.30000000000000004`، اما اگر مقایسه‌تان شکست بخورد، «نزدیک» مهم نیست.

**توجه:** آیا JavaScript باید به پیاده‌سازی دیگری برای `number` برود که نمایش دقیق برای همهٔ مقادیر داشته باشد؟ بعضی چنین فکر می‌کنند. سال‌ها گزینه‌های زیادی پیشنهاد شده. هنوز هیچ‌کدام پذیرفته نشده و شاید هرگز نشوند. به‌رغم اینکه به نظر ساده می‌رسد بگوییم «همین باگ را درست کنید!»، به آن سادگی نیست. اگر بود، قطعاً مدتها پیش عوض شده بود.

حالا سؤال این است: اگر به بعضی `number`ها نمی‌توان برای دقیق بودن *اعتماد* کرد، آیا یعنی اصلاً نباید از `number` استفاده کنیم؟ **البته که نه.**

برنامه‌هایی هستند که باید دقیق‌تر باشید، به‌ویژه با مقدارهای اعشاری. خیلی (شاید بیشتر؟) برنامه‌ها فقط با عددهای صحیح سروکار دارند و آن هم حداکثر در حد میلیون یا تریلیون. این برنامه‌ها بوده‌اند و خواهند بود که استفاده از عملیات عددی در JS در آن‌ها **کاملاً امن** است.

اگر *واقعاً* لازم بود دو `number` را مقایسه کنیم، مثلاً `0.1 + 0.2` با `0.3`، با علم به اینکه آزمون برابری ساده شکست می‌خورد؟

پذیرفته‌شده‌ترین روش استفاده از یک مقدار خیلی کوچک «خطای گرد کردن» به‌عنوان *تلرانس* مقایسه است. این مقدار کوچک اغلب «machine epsilon» نامیده می‌شود که برای نوع `number`های JavaScript معمولاً `2^-52` (`2.220446049250313e-16`) است.

از ES6 به بعد، `Number.EPSILON` با این مقدار تلرانس از پیش تعریف شده؛ پس بهتر است از آن استفاده کنید، اما می‌توانید برای قبل از ES6 به‌طور امن polyfill بنویسید:

```js
if (!Number.EPSILON) {
	Number.EPSILON = Math.pow(2,-52);
}
```

می‌توانیم از این `Number.EPSILON` برای مقایسهٔ دو `number` از نظر «برابری» (در حد تلرانس خطای گرد کردن) استفاده کنیم:

```js
function numbersCloseEnoughToEqual(n1,n2) {
	return Math.abs( n1 - n2 ) < Number.EPSILON;
}

var a = 0.1 + 0.2;
var b = 0.3;

numbersCloseEnoughToEqual( a, b );					// true
numbersCloseEnoughToEqual( 0.0000001, 0.0000002 );	// false
```

بیشترین مقدار floating-point قابل نمایش تقریباً `1.798e+308` است (که واقعاً خیلی بزرگ است!) و به‌صورت `Number.MAX_VALUE` از پیش تعریف شده. در طرف کوچک، `Number.MIN_VALUE` تقریباً `5e-324` است که منفی نیست اما خیلی به صفر نزدیک است!

### Safe Integer Ranges

به‌خاطر نحوهٔ نمایش `number`ها، محدودهٔ مقادیر «ایمن» برای «عدد صحیح»های `number` وجود دارد و به‌طور قابل توجهی کمتر از `Number.MAX_VALUE` است.

بیشترین عدد صحیحی که می‌توان «به‌طور ایمن» نمایش داد (یعنی تضمین می‌شود مقدار درخواستی واقعاً به‌طور یکتا قابل نمایش است) برابر است با `2^53 - 1`، یعنی `9007199254740991`. با جداکنندهٔ هزارگان می‌بینید کمی بیش از ۹ کوادریلیون است. پس برای محدودهٔ `number`ها خیلی بزرگ است.

این مقدار در ES6 به‌صورت خودکار تعریف شده: `Number.MAX_SAFE_INTEGER`. تعجبی ندارد که یک مقدار کمینه هم هست، `-9007199254740991`، که در ES6 به‌نام `Number.MIN_SAFE_INTEGER` تعریف شده.

اصلی‌ترین جایی که برنامه‌های JS با چنین عددهای بزرگی روبه‌رو می‌شوند، کار با شناسه‌های ۶۴-بیتی از پایگاه داده و غیره است. عددهای ۶۴-بیتی را نمی‌توان با type `number` به‌درستی نمایش داد، پس باید با نمایش `string` در JavaScript ذخیره (و ارسال/دریافت) شوند.

عملیات عددی روی چنین مقدارهای عددی بزرگ (جز مقایسه که با `string` درست کار می‌کند) خوشبختانه چندان رایج نیست. اما اگر *واقعاً* لازم است روی این مقدارهای خیلی بزرگ محاسبه کنید، فعلاً باید از ابزار *big number* استفاده کنید. ممکن است در نسخهٔ آیندهٔ JavaScript پشتیبانی رسمی برای اعداد بزرگ اضافه شود.

### Testing for Integers

برای تست اینکه یک مقدار عدد صحیح است یا نه، می‌توانید از `Number.isInteger(..)` تعریف‌شده در ES6 استفاده کنید:

```js
Number.isInteger( 42 );		// true
Number.isInteger( 42.000 );	// true
Number.isInteger( 42.3 );	// false
```

برای polyfill کردن `Number.isInteger(..)` قبل از ES6:

```js
if (!Number.isInteger) {
	Number.isInteger = function(num) {
		return typeof num == "number" && num % 1 == 0;
	};
}
```

برای تست اینکه یک مقدار *safe integer* است یا نه، از `Number.isSafeInteger(..)` تعریف‌شده در ES6 استفاده کنید:

```js
Number.isSafeInteger( Number.MAX_SAFE_INTEGER );	// true
Number.isSafeInteger( Math.pow( 2, 53 ) );			// false
Number.isSafeInteger( Math.pow( 2, 53 ) - 1 );		// true
```

برای polyfill کردن `Number.isSafeInteger(..)` در مرورگرهای قبل از ES6:

```js
if (!Number.isSafeInteger) {
	Number.isSafeInteger = function(num) {
		return Number.isInteger( num ) &&
			Math.abs( num ) <= Number.MAX_SAFE_INTEGER;
	};
}
```

### 32-bit (Signed) Integers

هرچند عددهای صحیح می‌توانند تا حدود ۹ کوادریلیون (۵۳ بیت) به‌طور ایمن باشند، بعضی عملیات عددی (مثل عملگرهای بیتی) فقط برای `number`های ۳۲-بیتی تعریف شده‌اند، پس «محدودهٔ ایمن» برای `number`هایی که آن‌طور استفاده می‌شوند باید خیلی کوچک‌تر باشد.

محدوده پس از آن از `Math.pow(-2,31)` (`-2147483648`، حدود ۲٫۱ میلیارد منفی) تا `Math.pow(2,31)-1` (`2147483647`، حدود ۲٫۱ میلیارد مثبت) است.

برای اجبار مقدار `number` در `a` به مقدار عدد صحیح علامت‌دار ۳۲-بیتی، از `a | 0` استفاده کنید. این کار می‌کند چون عملگر بیتی `|` فقط برای مقدارهای عدد صحیح ۳۲-بیتی کار می‌کند (یعنی فقط به ۳۲ بیت توجه می‌کند و بقیهٔ بیت‌ها از دست می‌روند). بعد، «or» کردن با صفر در عمل هیچ تغییری در بیت‌ها نمی‌دهد.

**توجه:** بعضی مقدارهای خاص (که در بخش بعد پوشش می‌دهیم) مثل `NaN` و `Infinity` «۳۲-بیتی ایمن» نیستند؛ وقتی این مقدارها به عملگر بیتی داده شوند از عملیات انتزاعی `ToInt32` (فصل ۴) عبور می‌کنند و برای آن عملیات بیتی صرفاً به مقدار `+0` تبدیل می‌شوند.
