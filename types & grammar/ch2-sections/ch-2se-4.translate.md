# Special Values

چند مقدار خاص در typeهای مختلف پراکنده‌اند که توسعه‌دهندهٔ *هوشیار* JS باید آن‌ها را بشناسد و درست به کار ببرد.

### The Non-value Values

برای type `undefined` فقط یک مقدار وجود دارد: `undefined`. برای type `null` فقط یک مقدار: `null`. پس برای هر دو، برچسب هم type و هم مقدار است.

هم `undefined` و هم `null` اغلب به‌جای هم به‌عنوان مقدار «خالی» یا «غیر» به کار می‌روند. بعضی توسعه‌دهندگان ترجیح می‌دهند با ظرافت بین آن‌ها فرق بگذارند. مثلاً:

* `null` مقدار خالی است
* `undefined` مقدار غایب است

یا:

* `undefined` هنوز مقدار نداشته
* `null` قبلاً مقدار داشت و الان ندارد

صرف‌نظر از اینکه چطور این دو مقدار را «تعریف» و استفاده می‌کنید، `null` یک کلیدواژهٔ خاص است، نه شناسه، و بنابراین نمی‌توانید آن را مثل متغیر انتساب دهید (اصلاً چرا!). اما `undefined` (متأسفانه) یک شناسه است. وای.

### Undefined

در حالت غیر-`strict`، در واقع می‌شود (هرچند به‌شدت نامناسب!) به شناسهٔ سراسری `undefined` مقدار داد:

```js
function foo() {
	undefined = 2; // really bad idea!
}

foo();
```

```js
function foo() {
	"use strict";
	undefined = 2; // TypeError!
}

foo();
```

در هر دو حالت غیر-`strict` و `strict` می‌توانید متغیر محلی به‌نام `undefined` بسازید. اما باز هم ایدهٔ وحشتناکی است!

```js
function foo() {
	"use strict";
	var undefined = 2;
	console.log( undefined ); // 2
}

foo();
```

**دوستان اجازه نمی‌دهند دوستان `undefined` را override کنند.** هرگز.

#### عملگر `void`

در حالی که `undefined` یک شناسهٔ از پیش‌تعریف‌شده است که (مگر تغییر کرده باشد — بالا را ببینید!) مقدار از پیش‌تعریف‌شدهٔ `undefined` را نگه می‌دارد، راه دیگر گرفتن این مقدار عملگر `void` است.

عبارت `void ___` هر مقداری را «void» می‌کند، طوری که نتیجهٔ عبارت همیشه مقدار `undefined` است. مقدار موجود را عوض نمی‌کند؛ فقط تضمین می‌کند که از عبارت عملگر هیچ مقداری برنگردد.

```js
var a = 42;

console.log( void a, a ); // undefined 42
```

طبق قرارداد (عمدتاً از برنامه‌نویسی C)، برای نمایش مقدار `undefined` به‌تنهایی با `void` از `void 0` استفاده می‌کنند (هرچند واضح است که `void true` یا هر عبارت `void` دیگر هم همین کار را می‌کند). بین `void 0`، `void 1` و `undefined` تفاوت عملی نیست.

اما عملگر `void` در چند مورد دیگر هم می‌تواند مفید باشد، اگر لازم است تضمین کنید یک عبارت نتیجه‌ای ندارد (حتی اگر اثر جانبی داشته باشد).

مثلاً:

```js
function doSomething() {
	// note: `APP.ready` is provided by our application
	if (!APP.ready) {
		// try again later
		return void setTimeout( doSomething, 100 );
	}

	var result;

	// do some other stuff
	return result;
}

// were we able to do it right away?
if (doSomething()) {
	// handle next tasks right away
}
```

اینجا تابع `setTimeout(..)` یک مقدار عددی برمی‌گرداند (شناسهٔ یکتای بازهٔ تایمر، اگر بخواهید لغوش کنید)، اما می‌خواهیم آن را `void` کنیم تا مقدار برگشتی تابعمان با دستور `if` false-positive ندهد.

خیلی از توسعه‌دهندگان ترجیح می‌دهند این کارها را جدا انجام دهند، که همان نتیجه را می‌دهد اما از عملگر `void` استفاده نمی‌کند:

```js
if (!APP.ready) {
	// try again later
	setTimeout( doSomething, 100 );
	return;
}
```

به‌طور کلی، هر جا مقداری (از یک عبارت) وجود دارد و برایتان مفید است که به‌جایش `undefined` باشد، از عملگر `void` استفاده کنید. احتمالاً در برنامه‌هایتان خیلی پیش نمی‌آید، اما در موارد نادری که لازم دارید، می‌تواند خیلی کمک‌کننده باشد.

### Special Numbers

type `number` چند مقدار خاص دارد. هر کدام را جدا بررسی می‌کنیم.

#### The Not Number, Number

هر عملیات ریاضی که بدون اینکه هر دو عملوند `number` باشند (یا مقادیری که بتوان به‌عنوان `number` معمولی در مبنای ۱۰ یا ۱۶ تفسیر کرد) انجام دهید، به شکست در تولید یک `number` معتبر منجر می‌شود و در آن صورت مقدار `NaN` را می‌گیرید.

`NaN` به‌معنای تحت‌اللفظی «not a number» است، هرچند این برچسب/توضیح خیلی ضعیف و گمراه‌کننده است، همان‌طور که به‌زودی می‌بینیم. دقیق‌تر این است که `NaN` را «عدد نامعتبر»، «عدد ناموفق» یا حتی «عدد بد» بدانیم تا «نه یک عدد».

مثلاً:

```js
var a = 2 / "foo";		// NaN

typeof a === "number";	// true
```

به عبارت دیگر: «type نه-یک-عدد برابر است با 'number'!» عجب نام و معناشناسی گیج‌کننده.

`NaN` نوعی «مقدار sentinel» است (مقداری در غیر این صورت عادی که معنای خاصی به آن داده شده) که نشان‌دهندهٔ نوع خاصی از وضعیت خطا در مجموعهٔ `number` است. وضعیت خطا در اصل این است: «سعی کردم عملیات ریاضی انجام دهم اما شکست خورد، پس اینجا نتیجهٔ `number` ناموفق است.»

پس اگر در متغیری مقداری دارید و می‌خواهید تست کنید که آیا این `NaN` خاص است یا نه، شاید فکر کنید می‌توانید مستقیم با خود `NaN` مقایسه کنید، مثل هر مقدار دیگر مثل `null` یا `undefined`. نه.

```js
var a = 2 / "foo";

a == NaN;	// false
a === NaN;	// false
```

`NaN` مقدار خیلی خاصی است به این معنا که هرگز با مقدار `NaN` دیگر برابر نیست (یعنی هرگز با خودش برابر نیست). در واقع تنها مقداری است که reflexive نیست (ویژگی هویت `x === x` را ندارد). پس `NaN !== NaN`. کمی عجیب است، نه؟

پس چطور تستش می‌کنیم، اگر نمی‌توانیم با `NaN` مقایسه کنیم (چون آن مقایسه همیشه شکست می‌خورد)?

```js
var a = 2 / "foo";

isNaN( a ); // true
```

به‌اندازهٔ کافی ساده است؟ از ابزار سراسری از پیش‌تعریف‌شدهٔ `isNaN(..)` استفاده می‌کنیم و به ما می‌گوید مقدار `NaN` است یا نه. مشکل حل شد!

نه این‌قدر زود.

ابزار `isNaN(..)` یک نقص جدی دارد. به نظر می‌رسد معنای `NaN` («Not a Number») را خیلی تحت‌اللفظی گرفته — که کارش در اصل این است: «تست کن که آیا چیز پاس‌داده‌شده یا `number` نیست یا هست.» اما این دقیق نیست.

```js
var a = 2 / "foo";
var b = "foo";

a; // NaN
b; // "foo"

window.isNaN( a ); // true
window.isNaN( b ); // true -- ouch!
```

واضح است که `"foo"` به‌معنای تحت‌اللفظی *نه یک `number`* است، اما قطعاً مقدار `NaN` هم نیست! این باگ از همان اول در JS بوده (بیش از ۱۹ سال *اوچ*).

از ES6 به بعد، بالاخره جایگزینی ارائه شده: `Number.isNaN(..)`. یک polyfill ساده برای آن تا بتوانید *الان* حتی در مرورگرهای قبل از ES6 به‌طور امن مقدارهای `NaN` را بررسی کنید:

```js
if (!Number.isNaN) {
	Number.isNaN = function(n) {
		return (
			typeof n === "number" &&
			window.isNaN( n )
		);
	};
}

var a = 2 / "foo";
var b = "foo";

Number.isNaN( a ); // true
Number.isNaN( b ); // false -- phew!
```

در واقع می‌توانیم polyfill برای `Number.isNaN(..)` را با استفاده از این واقعیت عجیب که `NaN` با خودش برابر نیست راحت‌تر پیاده کنیم. `NaN` *تنها* مقداری در کل زبان است که این‌طور است؛ هر مقدار دیگر همیشه **با خودش برابر** است.

پس:

```js
if (!Number.isNaN) {
	Number.isNaN = function(n) {
		return n !== n;
	};
}
```

عجیب است، نه؟ اما جواب می‌دهد!

`NaN`ها احتمالاً در خیلی از برنامه‌های واقعی JS وجود دارند، عمدی یا تصادفی. ایدهٔ خیلی خوبی است که از تست قابل اطمینان مثل `Number.isNaN(..)` (ارائه‌شده یا polyfill شده) برای تشخیص درست آن‌ها استفاده کنید.

اگر الان در برنامه فقط از `isNaN(..)` استفاده می‌کنید، واقعیت غم‌انگیز این است که برنامه‌تان *باگ دارد*، حتی اگر هنوز گازش را نخورده باشید!

#### Infinities

توسعه‌دهندگان زبان‌های کامپایل‌شدهٔ سنتی مثل C احتمالاً عادت دارند برای عملیاتی مثل این یا خطای کامپایلر یا استثنای زمان اجرا ببینند، مثلاً «تقسیم بر صفر»:

```js
var a = 1 / 0;
```

اما در JS این عملیات به‌خوبی تعریف شده و به مقدار `Infinity` (یعنی `Number.POSITIVE_INFINITY`) منجر می‌شود. تعجبی ندارد:

```js
var a = 1 / 0;	// Infinity
var b = -1 / 0;	// -Infinity
```

همان‌طور که می‌بینید، `-Infinity` (یعنی `Number.NEGATIVE_INFINITY`) از تقسیم بر صفر وقتی حاصل می‌شود که یکی (اما نه هر دو!) از عملوندهای تقسیم منفی باشد.

JS از نمایش عددی متناهی استفاده می‌کند (IEEE 754 floating-point که قبلاً پوشش دادیم)، پس برخلاف ریاضیات محض، به نظر می‌رسد *می‌شود* حتی با عملیاتی مثل جمع یا تفریق overflow کرد، و در آن صورت `Infinity` یا `-Infinity` می‌گیرید.

مثلاً:

```js
var a = Number.MAX_VALUE;	// 1.7976931348623157e+308
a + a;						// Infinity
a + Math.pow( 2, 970 );		// Infinity
a + Math.pow( 2, 969 );		// 1.7976931348623157e+308
```

طبق مشخصات، اگر عملیاتی مثل جمع به مقداری منجر شود که برای نمایش خیلی بزرگ است، حالت «round-to-nearest» در IEEE 754 مشخص می‌کند نتیجه چه باشد. پس به‌طور تقریبی، `Number.MAX_VALUE + Math.pow( 2, 969 )` به `Number.MAX_VALUE` نزدیک‌تر است تا به `Infinity`، پس «به پایین گرد می‌شود»، در حالی که `Number.MAX_VALUE + Math.pow( 2, 970 )` به `Infinity` نزدیک‌تر است پس «به بالا گرد می‌شود».

اگر زیاد به این فکر کنید سرتان درد می‌گیرد. پس نکنید. جدی، بس کنید!

اما وقتی به یکی از *بی‌نهایت*ها overflow کردید، راه برگشتی نیست. به عبارت دیگر، به‌شکلی تقریباً شاعرانه، می‌توانید از متناهی به نامتناهی بروید اما نه از نامتناهی برگردید به متناهی.

تقریباً فلسفی است بپرسیم: «بی‌نهایت تقسیم بر بی‌نهایت چیست». ذهن ساده‌مان احتمالاً می‌گوید «۱» یا شاید «بی‌نهایت». معلوم می‌شود هیچ‌کدام درست نیست. هم از نظر ریاضی و هم در JavaScript، `Infinity / Infinity` عملیات تعریف‌شده نیست. در JS نتیجه `NaN` است.

اما هر `number` متناهی مثبت تقسیم بر `Infinity` چطور؟ ساده است! `0`. و `number` متناهی منفی تقسیم بر `Infinity`؟ ادامه بدهید!

#### Zeros

هرچند ممکن است خوانندهٔ ریاضی‌اندیش را گیج کند، JavaScript هم صفر معمولی `0` (که صفر مثبت `+0` هم نامیده می‌شود) و هم صفر منفی `-0` دارد. قبل از توضیح دلیل وجود `-0`، باید ببینیم JS چطور با آن برخورد می‌کند، چون می‌تواند گیج‌کننده باشد.

علاوه بر اینکه به‌صورت تحت‌اللفظی `-0` نوشته شود، صفر منفی از بعضی عملیات ریاضی هم حاصل می‌شود. مثلاً:

```js
var a = 0 / -3; // -0
var b = 0 * -3; // -0
```

جمع و تفریق نمی‌توانند به صفر منفی منجر شوند.

صفر منفی وقتی در کنسول توسعه‌دهنده بررسی شود معمولاً `-0` نشان می‌دهد، هرچند تا همین اواخر معمول نبود، پس ممکن است بعضی مرورگرهای قدیمی‌تر هنوز آن را `0` گزارش کنند.

با این حال، اگر بخواهید مقدار صفر منفی را به رشته تبدیل کنید، طبق مشخصات همیشه به‌صورت `"0"` گزارش می‌شود.

```js
var a = 0 / -3;

// (some browser) consoles at least get it right
a;							// -0

// but the spec insists on lying to you!
a.toString();				// "0"
a + "";						// "0"
String( a );				// "0"

// strangely, even JSON gets in on the deception
JSON.stringify( a );		// "0"
```

جالب این که عملیات معکوس (از `string` به `number`) دروغ نمی‌گویند:

```js
+"-0";				// -0
Number( "-0" );		// -0
JSON.parse( "-0" );	// -0
```

**هشدار:** رفتار `JSON.stringify( -0 )` به‌صورت `"0"` به‌ویژه عجیب است وقتی ببینید با معکوس ناسازگار است: `JSON.parse( "-0" )` همان‌طور که درست انتظار دارید `-0` گزارش می‌دهد.

علاوه بر اینکه stringify کردن صفر منفی فریبنده است و مقدار واقعی را پنهان می‌کند، عملگرهای مقایسه هم (عمداً) طوری پیکربندی شده‌اند که *دروغ* بگویند.

```js
var a = 0;
var b = 0 / -3;

a == b;		// true
-0 == 0;	// true

a === b;	// true
-0 === 0;	// true

0 > -0;		// false
a > b;		// false
```

واضح است که اگر می‌خواهید در کدتان `-0` را از `0` تشخیص دهید، نمی‌توانید فقط به خروجی کنسول توسعه‌دهنده تکیه کنید، پس باید کمی زیرک‌تر باشید:

```js
function isNegZero(n) {
	n = Number( n );
	return (n === 0) && (1 / n === -Infinity);
}

isNegZero( -0 );		// true
isNegZero( 0 / -3 );	// true
isNegZero( 0 );			// false
```

حالا چرا به صفر منفی نیاز داریم، جز به‌عنوان اطلاعات عمومی؟

برنامه‌هایی هستند که توسعه‌دهندگان در آن‌ها بزرگی مقدار را برای نمایش یک بخش اطلاعات (مثل سرعت حرکت در هر فریم انیمیشن) و علامت آن `number` را برای بخش دیگر (مثل جهت آن حرکت) به کار می‌برند.

در آن برنامه‌ها، به‌عنوان یک مثال، اگر متغیری به صفر برسد و علامتش را از دست بدهد، اطلاعات جهت حرکت قبل از رسیدن به صفر از دست می‌رود. حفظ علامت صفر از از دست رفتن ناخواستهٔ اطلاعات جلوگیری می‌کند.

### Special Equality

همان‌طور که بالا دیدیم، مقدارهای `NaN` و `-0` در مقایسهٔ برابری رفتار خاص دارند. `NaN` هرگز با خودش برابر نیست، پس باید از `Number.isNaN(..)` در ES6 (یا polyfill) استفاده کنید. به‌طور مشابه، `-0` دروغ می‌گوید و وانمود می‌کند با صفر مثبت معمولی برابر است (حتی `===` strict equal — فصل ۴ را ببینید)، پس باید از تابع کمکی تا حدی hackish یعنی `isNegZero(..)` که پیشنهاد کردیم استفاده کنید.

از ES6 به بعد، ابزار جدیدی برای تست برابری مطلق دو مقدار، بدون این استثناها، وجود دارد. نامش `Object.is(..)` است:

```js
var a = 2 / "foo";
var b = -3 * 0;

Object.is( a, NaN );	// true
Object.is( b, -0 );		// true

Object.is( b, 0 );		// false
```

یک polyfill نسبتاً ساده برای `Object.is(..)` در محیط‌های قبل از ES6:

```js
if (!Object.is) {
	Object.is = function(v1, v2) {
		// test for `-0`
		if (v1 === 0 && v2 === 0) {
			return 1 / v1 === 1 / v2;
		}
		// test for `NaN`
		if (v1 !== v1) {
			return v2 !== v2;
		}
		// everything else
		return v1 === v2;
	};
}
```

احتمالاً نباید از `Object.is(..)` در مواردی استفاده کنید که `==` یا `===` *ایمن* شناخته شده‌اند (فصل ۴ «Coercion» را ببینید)، چون عملگرها احتمالاً کارآمدترند و قطعاً رایج‌تر/idiomatic‌ترند. `Object.is(..)` بیشتر برای همین موارد خاص برابری است.
