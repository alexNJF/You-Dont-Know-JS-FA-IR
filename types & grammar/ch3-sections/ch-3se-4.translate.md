# Natives as Constructors

برای مقدارهای `array`، `object`، `function` و عبارت باقاعده، تقریباً همه‌جا شکل literal برای ساختن مقدارها ترجیح داده می‌شود، اما شکل literal همان نوع object را می‌سازد که شکل constructor (یعنی مقدار غیر-wrapped وجود ندارد).

همان‌طور که با بقیهٔ natives بالا دیدیم، این شکل‌های constructor را به‌طور کلی باید پرهیز کرد، مگر واقعاً بدانید لازم دارید، عمدتاً چون استثناها و نکات مهمی معرفی می‌کنند که احتمالاً *نمی‌خواهید* با آن‌ها سروکار داشته باشید.

### `Array(..)`

```js
var a = new Array( 1, 2, 3 );
a; // [1, 2, 3]

var b = [1, 2, 3];
b; // [1, 2, 3]
```

**توجه:** constructor یعنی `Array(..)` به کلیدواژهٔ `new` جلوی خود نیاز ندارد. اگر حذفش کنید، طوری رفتار می‌کند که انگار استفاده کرده‌اید. پس `Array(1,2,3)` همان نتیجهٔ `new Array(1,2,3)` است.

constructor یعنی `Array` یک شکل خاص دارد: اگر فقط یک آرگومان `number` فرستاده شود، به‌جای اینکه آن مقدار به‌عنوان *محتوای* آرایه باشد، به‌عنوان طول برای «از پیش اندازه دادن آرایه» گرفته می‌شود (خب، تقریباً).

این ایدهٔ وحشتناکی است. اول این که می‌توانید تصادفی به آن شکل برخورد کنید، چون فراموش کردنش راحت است.

اما مهم‌تر این که چیزی به‌نام واقعاً از پیش اندازه دادن آرایه وجود ندارد. به‌جایش، آنچه می‌سازید یک آرایهٔ در غیر این صورت خالی است، با این که property به‌نام `length` آرایه روی مقدار عددی مشخص‌شده تنظیم می‌شود.

آرایه‌ای که در خانه‌هایش مقدار صریح ندارد اما property به‌نام `length` دارد که *دلالت* می‌کند خانه‌ها وجود دارند، یک نوع ساختار دادهٔ عجیب و exotic در JS با رفتاری بسیار عجیب و گیج‌کننده است. قابلیت ساختن چنین مقداری صرفاً از قابلیت‌های قدیمی، منسوخ و تاریخی می‌آید («شیءهای شبیه آرایه» مثل شیء `arguments`).

**توجه:** آرایه‌ای که حداقل یک «خانهٔ خالی» دارد اغلب «sparse array» نامیده می‌شود.

کمک نمی‌کند که این هم نمونهٔ دیگری است که کنسولهای توسعه‌دهندهٔ مرورگرها در نمایش چنین شیءی فرق می‌کنند، که گیجی بیشتر ایجاد می‌کند.

مثلاً:

```js
var a = new Array( 3 );

a.length; // 3
a;
```

سریال‌سازی `a` در Chrome (در زمان نگارش): `[ undefined x 3 ]`. **واقعاً بدشانسی است.** دلالت می‌کند که سه مقدار `undefined` در خانه‌های این آرایه هست، در حالی که در واقع خانه‌ها وجود ندارند (به‌اصطلاح «خانه‌های خالی» — اسم بدی هم هست!).

برای دیدن تفاوت، این را امتحان کنید:

```js
var a = new Array( 3 );
var b = [ undefined, undefined, undefined ];
var c = [];
c.length = 3;

a;
b;
c;
```

**توجه:** همان‌طور که با `c` در این مثال می‌بینید، خانه‌های خالی در آرایه می‌توانند بعد از ساختن آرایه پیش بیایند. با تغییر `length` آرایه به فراتر از تعداد واقعی خانه‌های تعریف‌شده، به‌طور ضمنی خانه‌های خالی معرفی می‌کنید. در واقع حتی می‌توانید در قطعهٔ بالا `delete b[1]` فراخوانی کنید و یک خانهٔ خالی وسط `b` ایجاد شود.

برای `b` (در Chrome، فعلاً) سریال‌سازی را `[ undefined, undefined, undefined ]` می‌بینید، در مقابل `[ undefined x 3 ]` برای `a` و `c`. گیج شدید؟ بله، بقیه هم همین‌طور.

بدتر از آن، در زمان نگارش Firefox برای `a` و `c` مقدار `[ , , , ]` گزارش می‌دهد. فهمیدید چرا این‌قدر گیج‌کننده است؟ دقیق نگاه کنید. سه کاما دلالت بر چهار خانه می‌کند، نه سه خانه آن‌طور که انتظار داریم.

**چی!?** Firefox یک `,` اضافه در انتهای سریال‌سازی‌شان می‌گذارد چون از ES5 به بعد، کامای انتهایی در لیست‌ها (مقدارهای آرایه، لیست propertyها و غیره) مجازند (و بنابراین حذف و نادیده گرفته می‌شوند). پس اگر مقدار `[ , , , ]` را در برنامه یا کنسول تایپ کنید، در واقع مقدار زیرینی شبیه `[ , , ]` می‌گیرید (یعنی آرایه‌ای با سه خانهٔ خالی). این انتخاب، هرچند در خواندن کنسول توسعه‌دهنده گیج‌کننده است، با این استدلال دفاع می‌شود که رفتار کپی-پیست را درست می‌کند.

اگر دارید با سر تکان می‌دهید یا چشمتان را می‌چرخانید، تنها نیستید! شانه بالا انداختن.

متأسفانه بدتر می‌شود. بیش از خروجی گیج‌کنندهٔ کنسول، `a` و `b` از قطعهٔ کد بالا در بعضی موارد **یکسان** رفتار می‌کنند اما **در بقیه متفاوت**:

```js
a.join( "-" ); // "--"
b.join( "-" ); // "--"

a.map(function(v,i){ return i; }); // [ undefined x 3 ]
b.map(function(v,i){ return i; }); // [ 0, 1, 2 ]
```

**اه.**

فراخوانی `a.map(..)` *شکست* می‌خورد چون خانه‌ها در واقع وجود ندارند، پس `map(..)` چیزی برای پیمایش ندارد. `join(..)` متفاوت کار می‌کند. در اصل می‌توانیم فکر کنیم تقریباً این‌طور پیاده شده:

```js
function fakeJoin(arr,connector) {
	var str = "";
	for (var i = 0; i < arr.length; i++) {
		if (i > 0) {
			str += connector;
		}
		if (arr[i] !== undefined) {
			str += arr[i];
		}
	}
	return str;
}

var a = new Array( 3 );
fakeJoin( a, "-" ); // "--"
```

همان‌طور که می‌بینید، `join(..)` با *فرض* وجود خانه‌ها و حلقه تا مقدار `length` کار می‌کند. هرچه `map(..)` درونش می‌کند، (ظاهراً) چنین فرضی نمی‌کند، پس نتیجه از آرایهٔ عجیب «خانه‌های خالی» غیرمنتظره است و احتمالاً به شکست می‌انجامد.

پس اگر می‌خواستید *واقعاً* آرایه‌ای از مقدارهای واقعی `undefined` (نه فقط «خانه‌های خالی») بسازید، چطور می‌کردید (جز دستی)?

```js
var a = Array.apply( null, { length: 3 } );
a; // [ undefined, undefined, undefined ]
```

گیج شدید؟ بله. تقریباً این‌طور کار می‌کند.

`apply(..)` ابزاری است برای همهٔ توابع که تابعی که روی آن به کار رفته را به‌شیوهٔ خاصی فراخوانی می‌کند.

آرگومان اول binding شیء `this` است (در عنوان *this & Object Prototypes* این مجموعه پوشش داده شده)، که اینجا به آن کاری نداریم، پس `null` می‌گذاریم. آرگومان دوم قرار است یک آرایه (یا چیزی *شبیه* آرایه — یعنی «شیء شبیه آرایه») باشد. محتوای این «آرایه» به‌عنوان آرگومان‌های تابع مورد نظر «پخش» می‌شوند.

پس `Array.apply(..)` تابع `Array(..)` را فراخوانی می‌کند و مقدارها (شیء `{ length: 3 }`) را به‌عنوان آرگومان‌هایش پخش می‌کند.

داخل `apply(..)` می‌توان تصور کرد یک حلقهٔ `for` دیگر هست (تقریباً مثل `join(..)` بالا) که از `0` تا قبل از `length` (`3` در مورد ما) می‌رود.

برای هر اندیس، آن کلید را از شیء می‌گیرد. پس اگر پارامتر شیء-آرایه داخل `apply(..)` مثلاً `arr` نام داشت، دسترسی به property در عمل می‌شد `arr[0]`، `arr[1]` و `arr[2]`. البته هیچ‌کدام از آن propertyها روی مقدار شیء `{ length: 3 }` وجود ندارند، پس هر سهٔ آن دسترسی‌ها مقدار `undefined` برمی‌گردانند.

به عبارت دیگر، در نهایت `Array(..)` را تقریباً این‌طور فراخوانی می‌کند: `Array(undefined,undefined,undefined)`، و این‌طور به آرایه‌ای پر از مقدارهای `undefined` می‌رسیم، نه فقط آن خانه‌های (دیوانه‌وار) خالی.

هرچند `Array.apply( null, { length: 3 } )` روش عجیب و طولانی برای ساختن آرایه‌ای پر از مقدارهای `undefined` است، **به‌مراتب** بهتر و قابل اطمینان‌تر از نتیجهٔ footgun یعنی `Array(3)` با خانه‌های خالی است.

نتیجهٔ نهایی: **هرگز، تحت هیچ شرایطی** نباید عمداً این آرایه‌های exotic با خانهٔ خالی را بسازید و استفاده کنید. فقط نکنید. دیوانه‌اند.

### `Object(..)`، `Function(..)` و `RegExp(..)`

constructorهای `Object(..)` / `Function(..)` / `RegExp(..)` هم به‌طور کلی اختیاری‌اند (و پس معمولاً باید پرهیز شوند مگر صریحاً خواسته شود):

```js
var c = new Object();
c.foo = "bar";
c; // { foo: "bar" }

var d = { foo: "bar" };
d; // { foo: "bar" }

var e = new Function( "a", "return a * 2;" );
var f = function(a) { return a * 2; };
function g(a) { return a * 2; }

var h = new RegExp( "^a*b+", "g" );
var i = /^a*b+/g;
```

عملاً دلیلی برای استفاده از شکل constructor یعنی `new Object()` نیست، به‌ویژه که مجبورتان می‌کند propertyها را یکی‌یکی اضافه کنید به‌جای چندتایی یکجا در شکل literal شیء.

constructor یعنی `Function` فقط در نادرترین موارد مفید است، جایی که باید پارامترها و/یا بدنهٔ تابع را به‌طور پویا تعریف کنید. **فقط `Function(..)` را به‌عنوان شکل جایگزین `eval(..)` در نظر نگیرید.** تقریباً هرگز به تعریف پویای تابع به این شکل نیاز ندارید.

عبارت‌های باقاعدهٔ تعریف‌شده به شکل literal (`/^a*b+/g`) به‌شدت ترجیح داده می‌شوند، نه فقط برای سادگی سینتکس بلکه به‌خاطر کارایی — موتور JS آن‌ها را قبل از اجرای کد پیش‌کامپایل و cache می‌کند. برخلاف شکل‌های constructor دیگری که تا الان دیدیم، `RegExp(..)` کاربرد معقولی دارد: تعریف پویای الگوی عبارت باقاعده.

```js
var name = "Kyle";
var namePattern = new RegExp( "\\b(?:" + name + ")+\\b", "ig" );

var matches = someText.match( namePattern );
```

این نوع سناریو هر از گاهی در برنامه‌های JS به‌طور مشروع پیش می‌آید، پس باید از شکل `new RegExp("pattern","flags")` استفاده کنید.

### `Date(..)` و `Error(..)`

native constructorهای `Date(..)` و `Error(..)` از بقیهٔ natives بسیار مفیدترند، چون برای هیچ‌کدام شکل literal وجود ندارد.

برای ساختن مقدار شیء تاریخ، باید از `new Date()` استفاده کنید. constructor یعنی `Date(..)` آرگومان‌های اختیاری برای مشخص کردن تاریخ/زمان می‌پذیرد، اما اگر حذف شوند، تاریخ/زمان فعلی فرض می‌شود.

دورترین دلیل رایج برای ساختن شیء تاریخ گرفتن مقدار timestamp فعلی است (عدد صحیح علامت‌دار میلی‌ثانیه از ۱ ژانویه ۱۹۷۰). می‌توانید با فراخوانی `getTime()` روی نمونهٔ شیء تاریخ این کار را بکنید.

اما راه حتی راحت‌تر فقط فراخوانی تابع کمکی استاتیک تعریف‌شده از ES5 است: `Date.now()`. و polyfill کردن آن برای قبل از ES5 نسبتاً ساده است:

```js
if (!Date.now) {
	Date.now = function(){
		return (new Date()).getTime();
	};
}
```

**توجه:** اگر `Date()` را بدون `new` فراخوانی کنید، نمایش رشتهٔ تاریخ/زمان در آن لحظه را می‌گیرید. شکل دقیق این نمایش در مشخصات زبان تعریف نشده، هرچند مرورگرها معمولاً روی چیزی نزدیک به این توافق دارند: `"Fri Jul 18 2014 00:31:02 GMT-0500 (CDT)"`.

constructor یعنی `Error(..)` (مثل `Array()` بالا) با وجود یا نبود کلیدواژهٔ `new` یکسان رفتار می‌کند.

دلیل اصلی ساختن شیء خطا این است که context پشتهٔ اجرای فعلی را در شیء ضبط می‌کند (در بیشتر موتورهای JS، بعد از ساخته شدن به‌صورت property فقط-خواندنی به‌نام `.stack` آشکار می‌شود). این context پشته شامل call-stack توابع و شمارهٔ خطی است که شیء خطا در آن ساخته شده، که اشکال‌زدایی آن خطا را خیلی راحت‌تر می‌کند.

معمولاً چنین شیء خطایی را با عملگر `throw` به کار می‌برید:

```js
function foo(x) {
	if (!x) {
		throw new Error( "x wasn't provided" );
	}
	// ..
}
```

نمونه‌های شیء خطا معمولاً حداقل یک property به‌نام `message` دارند، و گاهی propertyهای دیگر (که باید فقط-خواندنی در نظر بگیرید) مثل `type`. با این حال، جز بررسی property به‌نام `stack` که گفته شد، معمولاً بهترین کار فراخوانی `toString()` روی شیء خطا است (یا صریح یا به‌طور ضمنی از طریق coercion — فصل ۴ را ببینید) تا پیام خطای با فرمت دوستانه بگیرید.

**نکته:** از نظر فنی، علاوه بر native کلی یعنی `Error(..)`، چند native نوع خطای خاص دیگر هست: `EvalError(..)`، `RangeError(..)`، `ReferenceError(..)`، `SyntaxError(..)`، `TypeError(..)` و `URIError(..)`. اما استفادهٔ دستی از این nativeهای خطای خاص خیلی نادر است. اگر برنامه‌تان واقعاً دچار استثنای واقعی شود (مثل ارجاع به متغیر undeclared و گرفتن خطای `ReferenceError`) به‌طور خودکار استفاده می‌شوند.

### `Symbol(..)`

جدید از ES6، یک type مقدار primitive اضافه به‌نام «Symbol» اضافه شده است. Symbolها مقدارهای «یکتا» (به‌طور قطع تضمین‌نشده!) خاصی هستند که می‌توانند به‌عنوان property روی شیءها با ترس کم از برخورد به کار روند. عمدتاً برای رفتارهای built-in خاص سازه‌های ES6 طراحی شده‌اند، اما می‌توانید symbolهای خودتان را هم تعریف کنید.

Symbolها می‌توانند به‌عنوان نام property به کار روند، اما نمی‌توانید مقدار واقعی یک symbol را از برنامه یا کنسول توسعه‌دهنده ببینید یا به آن دسترسی داشته باشید. اگر symbol را در کنسول توسعه‌دهنده ارزیابی کنید، چیزی شبیه `Symbol(Symbol.create)` نشان داده می‌شود.

چند symbol از پیش‌تعریف‌شده در ES6 وجود دارد که به‌عنوان propertyهای استاتیک شیء تابع `Symbol` در دسترس‌اند، مثل `Symbol.create`، `Symbol.iterator` و غیره. برای استفاده، کاری مثل این بکنید:

```js
obj[Symbol.iterator] = function(){ /*..*/ };
```

برای تعریف symbolهای سفارشی خودتان، از native یعنی `Symbol(..)` استفاده کنید. native «constructor» یعنی `Symbol(..)` از این نظر یکتا است که اجازهٔ استفاده از `new` با آن را ندارید؛ این کار خطا پرتاب می‌کند.

```js
var mysym = Symbol( "my own symbol" );
mysym;				// Symbol(my own symbol)
mysym.toString();	// "Symbol(my own symbol)"
typeof mysym; 		// "symbol"

var a = { };
a[mysym] = "foobar";

Object.getOwnPropertySymbols( a );
// [ Symbol(my own symbol) ]
```

هرچند symbolها در واقع خصوصی نیستند (`Object.getOwnPropertySymbols(..)` روی شیء reflect می‌کند و symbolها را کاملاً عمومی آشکار می‌کند)، استفاده از آن‌ها برای propertyهای خصوصی یا خاص احتمالاً کاربرد اصلی‌شان است. برای بیشتر توسعه‌دهندگان، ممکن است جای نام propertyهای با پیشوند `_` را بگیرند که طبق قرارداد تقریباً همیشه سیگنال «این property خصوصی/خاص/داخلی است، پس دست نزن!» هستند.

**توجه:** `Symbol`ها *نه* `object` هستند، بلکه scalar primitiveهای ساده‌اند.

### Native Prototypes

هر کدام از native constructorهای از پیش‌تعریف‌شده شیء `.prototype` خودش را دارد — `Array.prototype`، `String.prototype` و غیره.

این شیءها شامل رفتار یکتا برای subtype شیء خاص خودشان هستند.

مثلاً همهٔ شیءهای رشته، و به‌طور گسترده (از طریق boxing) primitiveهای `string`، به رفتار پیش‌فرض به‌صورت متدهای تعریف‌شده روی شیء `String.prototype` دسترسی دارند.

**توجه:** طبق قرارداد مستندات، `String.prototype.XYZ` به `String#XYZ` کوتاه می‌شود، و همین‌طور برای بقیهٔ `.prototype`ها.

* `String#indexOf(..)`: پیدا کردن موقعیت زیررشتهٔ دیگر در رشته
* `String#charAt(..)`: دسترسی به کاراکتر در یک موقعیت در رشته
* `String#substr(..)`، `String#substring(..)` و `String#slice(..)`: استخراج بخشی از رشته به‌صورت رشتهٔ جدید
* `String#toUpperCase()` و `String#toLowerCase()`: ساختن رشتهٔ جدید که به حروف بزرگ یا کوچک تبدیل شده
* `String#trim()`: ساختن رشتهٔ جدید بدون فاصلهٔ انتهایی یا ابتدایی

هیچ‌کدام از متدها رشته را *درجا* تغییر نمی‌دهند. تغییرها (مثل تبدیل حروف یا trim) از مقدار موجود مقدار جدید می‌سازند.

به‌واسطهٔ delegation از طریق prototype (عنوان *this & Object Prototypes* این مجموعه را ببینید)، هر مقدار رشته می‌تواند به این متدها دسترسی داشته باشد:

```js
var a = " abc ";

a.indexOf( "c" ); // 3
a.toUpperCase(); // " ABC "
a.trim(); // "abc"
```

prototypeهای constructorهای دیگر شامل رفتار مناسب typeشان هستند، مثل `Number#toFixed(..)` (رشته‌سازی عدد با تعداد ثابت رقم اعشار) و `Array#concat(..)` (ادغام آرایه‌ها). همهٔ توابع به `apply(..)`، `call(..)` و `bind(..)` دسترسی دارند چون `Function.prototype` آن‌ها را تعریف می‌کند.

اما بعضی از native prototypeها *فقط* شیء ساده نیستند:

```js
typeof Function.prototype;			// "function"
Function.prototype();				// it's an empty function!

RegExp.prototype.toString();		// "/(?:)/" -- empty regex
"abc".match( RegExp.prototype );	// [""]
```

یک ایدهٔ به‌ویژه بد این است که حتی می‌توانید این native prototypeها را تغییر دهید (نه فقط اضافه کردن property که احتمالاً با آن آشنا هستید):

```js
Array.isArray( Array.prototype );	// true
Array.prototype.push( 1, 2, 3 );	// 3
Array.prototype;					// [1,2,3]

// don't leave it that way, though, or expect weirdness!
// reset the `Array.prototype` to empty
Array.prototype.length = 0;
```

همان‌طور که می‌بینید، `Function.prototype` یک تابع است، `RegExp.prototype` یک عبارت باقاعده است و `Array.prototype` یک آرایه. جالب و باحال است، نه؟

#### Prototypes As Defaults

این که `Function.prototype` یک تابع خالی است، `RegExp.prototype` یک regex «خالی» (مثلاً بدون تطابق) و `Array.prototype` یک آرایهٔ خالی، همهٔ آن‌ها را به مقدار «پیش‌فرض» خوبی برای انتساب به متغیرها تبدیل می‌کند اگر آن متغیرها از قبل مقدار با type مناسب نداشته باشند.

مثلاً:

```js
function isThisCool(vals,fn,rx) {
	vals = vals || Array.prototype;
	fn = fn || Function.prototype;
	rx = rx || RegExp.prototype;

	return rx.test(
		vals.map( fn ).join( "" )
	);
}

isThisCool();		// true

isThisCool(
	["a","b","c"],
	function(v){ return v.toUpperCase(); },
	/D/
);					// false
```

**توجه:** از ES6 به بعد لازم نیست از ترفند سینتکس مقدار پیش‌فرض یعنی `vals = vals || ..` استفاده کنیم (فصل ۴ را ببینید)، چون می‌توان مقدارهای پیش‌فرض را برای پارامترها با سینتکس native در اعلان تابع تنظیم کرد (فصل ۵ را ببینید).

یک فایدهٔ جانبی کوچک این رویکرد این است که `.prototype`ها از قبل ساخته و built-in هستند، پس *فقط یک بار* ساخته می‌شوند. در مقابل، استفاده از خود مقدارهای `[]`، `function(){}` و `/(?:)/` برای آن پیش‌فرض‌ها (بسته به پیاده‌سازی موتور) احتمالاً آن مقدارها را برای *هر فراخوانی* `isThisCool(..)` دوباره می‌سازد (و بعد احتمالاً garbage-collect می‌کند). این می‌تواند اتلاف حافظه/CPU باشد.

همچنین خیلی مراقب باشید که از `Array.prototype` به‌عنوان مقدار پیش‌فرض **که بعداً تغییر کند** استفاده نکنید. در این مثال، `vals` فقط-خواندنی استفاده می‌شود، اما اگر به‌جایش تغییر درجا در `vals` بدهید، در واقع خود `Array.prototype` را تغییر می‌دهید که به نکات مهمی که قبلاً گفتیم می‌انجامد!

**توجه:** در حالی که این native prototypeها و کمی سودمندی‌شان را اشاره می‌کنیم، در تکیه کردن به آن‌ها محتاط باشید و حتی بیشتر از تغییر دادن آن‌ها به هر شکل برحذر باشید. برای بحث بیشتر به پیوست الف «Native Prototypes» مراجعه کنید.
