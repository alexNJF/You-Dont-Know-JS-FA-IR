# Native Prototypes

یکی از قطعات کلاسیک و بسیار شناخته‌شدهٔ *بهترین روش* جاوااسکریپت این است: **هرگز prototypeهای native را گسترش ندهید**.

هر نام متد یا property که برای افزودن به `Array.prototype` به ذهنتان برسد که (هنوز) وجود ندارد، اگر افزودنی مفید و خوب طراحی‌شده و درست نام‌گذاری‌شده باشد، احتمال قوی هست که *سرانجام* به مشخصات اضافه شود — که در آن صورت گسترش شما الان در تعارض است.

یک مثال واقعی که واقعاً برایم پیش آمد و این نکته را خوب نشان می‌دهد:

ویجت قابل‌تعبیه‌ای برای سایت‌های دیگر می‌ساختم، و ویجتم به jQuery تکیه داشت (هرچند تقریباً هر فریم‌ورکی از این gotcha رنج می‌برد). تقریباً روی هر سایتی کار می‌کرد، اما به یکی رسیدیم که کاملاً خراب بود.

بعد از تقریباً یک هفته تحلیل/دیباگ، فهمیدم سایت مورد نظر در اعماق یکی از فایل‌های legacyاش کدی داشت که این‌طور به نظر می‌رسید:

```js
// Netscape 4 doesn't have Array.push
Array.prototype.push = function(item) {
	this[this.length] = item;
};
```

گذشته از کامنت دیوانه (کی به Netscape 4 اهمیت می‌دهد!؟)، معقول به نظر می‌رسد، نه؟

مشکل این است که `Array.prototype.push` مدتی بعد از دوران کدنویسی Netscape 4 به مشخصات اضافه شد، اما آنچه اضافه شد با این کد سازگار نیست. `push(..)` استاندارد اجازه می‌دهد چند آیتم یکجا push شوند. این هک شده فقط آیتم بعدی را نادیده می‌گیرد.

اساساً همهٔ فریم‌ورک‌های JS کدی دارند که به `push(..)` با چند المان تکیه می‌کند. در مورد من، کد اطراف موتور انتخابگر CSS کاملاً خراب بود. اما دهها جای دیگر هم می‌توانست آسیب‌پذیر باشد.

توسعه‌دهنده‌ای که آن هک `push(..)` را نوشت غریزهٔ درستی داشت که آن را `push` بنامد، اما push کردن چند المان را پیش‌بینی نکرد. قطعاً با حسن نیت عمل می‌کرد، اما مینی ساخت که تا تقریباً ۱۰ سال بعد وقتی من ناخواسته رسیدم منفجر نشد.

درس‌های زیادی از هر طرف گرفته می‌شود.

اول، nativeها را گسترش ندهید مگر کاملاً مطمئن باشید کدتان تنها کدی است که در آن محیط اجرا می‌شود. اگر نمی‌توانید ۱۰۰٪ بگویید، گسترش nativeها خطرناک است. باید ریسک را بسنجید.

بعد، گسترش‌ها را بدون شرط تعریف نکنید (چون می‌توانید تصادفی nativeها را بازنویسی کنید). در این مثال خاص، اگر کد این را می‌گفت:

```js
if (!Array.prototype.push) {
	// Netscape 4 doesn't have Array.push
	Array.prototype.push = function(item) {
		this[this.length] = item;
	};
}
```

شرط `if` فقط این `push()` هک‌شده را برای محیط‌های JS که وجود نداشت تعریف می‌کرد. در مورد من، احتمالاً OK می‌بود. اما حتی این رویکرد بدون ریسک نیست:

1. اگر کد سایت (به دلیلی دیوانه!) به `push(..)`ی تکیه می‌کرد که چند آیتم را نادیده می‌گرفت، آن کد سال‌ها پیش وقتی `push(..)` استاندارد عرضه شد خراب می‌شد.
2. اگر کتابخانهٔ دیگری جلوتر از این شرط `if` یک `push(..)` هک‌شده می‌آورد و به‌صورت ناسازگار انجامش می‌داد، سایت در آن زمان خراب می‌شد.

آنچه برجسته می‌کند سؤال جالبی است که صادقانه توجه کافی از توسعه‌دهندگان JS نمی‌گیرد: **آیا هرگز باید به رفتار built-in native تکیه کنید** اگر کدتان در محیطی اجرا می‌شود که تنها کد حاضر نیست؟

جواب سخت **نه** است، اما خیلی غیرعملی است. کدتان معمولاً نمی‌تواند نسخه‌های خصوصی لمس‌نشدنی خودش از همهٔ رفتار built-in مورد تکیه را بازتعریف کند. حتی اگر *می‌توانست*، خیلی اتلاف است.

پس، آیا باید برای رفتار built-in هم feature-test و هم compliance-test کنید که آنچه انتظار دارید را انجام می‌دهد؟ و اگر آن تست شکست خورد — آیا کدتان باید فقط از اجرا امتناع کند؟

```js
// don't trust Array.prototype.push
(function(){
	if (Array.prototype.push) {
		var a = [];
		a.push(1,2);
		if (a[0] === 1 && a[1] === 2) {
			// tests passed, safe to use!
			return;
		}
	}

	throw Error(
		"Array#push() is missing/broken!"
	);
})();
```

از نظر تئوری معقول به نظر می‌رسد، اما طراحی تست برای هر متد built-in هم خیلی غیرعملی است.

پس چه کار کنیم؟ آیا باید *اعتماد کنیم اما تأیید کنیم* (feature- و compliance-test) **همه‌چیز**؟ آیا فقط فرض کنیم وجود یعنی سازگاری و بگذاریم خرابی (ناشی از دیگران) هرچه باشد بالا بیاید؟

جواب عالی نیست. تنها واقعیت قابل مشاهده این است که گسترش prototypeهای native تنها راهی است که این چیزها گاز می‌گیرند.

اگر نکنید، و هیچ‌کس دیگر در کد اپلیکیشنتان نکند، در امانید. وگرنه، باید حداقل کمی شک، بدبینی و انتظار خرابی احتمالی بسازید.

داشتن مجموعهٔ کامل تست واحد/رجوعی از کدتان که در همهٔ محیط‌های شناخته‌شده اجرا می‌شود یک راه برای نمایان کردن زودتر بعضی از این مسائل است، اما برای محافظت واقعی از این تعارض‌ها کاری نمی‌کند.

### Shims/Polyfills

معمولاً گفته می‌شود تنها جای امن گسترش یک native محیط قدیمی‌تر (غیرسازگار با مشخصات) است، چون بعید است هرگز عوض شود — مرورگرهای جدید با ویژگی‌های مشخصات جدید مرورگرهای قدیمی را جایگزین می‌کنند نه اصلاح.

اگر می‌توانستید آینده را ببینید و مطمئن بدانید استاندارد آینده چه خواهد بود، مثلاً برای `Array.prototype.foobar`، کاملاً امن بود نسخهٔ سازگار خودتان را برای استفادهٔ الان بسازید، درست؟

```js
if (!Array.prototype.foobar) {
	// silly, silly
	Array.prototype.foobar = function() {
		this.push( "foo", "bar" );
	};
}
```

اگر از قبل مشخصات `Array.prototype.foobar` هست و رفتار مشخص‌شده با این منطق برابر است، در تعریف چنین قطعه‌ای نسبتاً امنید، و در آن صورت معمولاً «polyfill» (یا «shim») نامیده می‌شود.

چنین کدی **خیلی** برای گنجاندن در پایهٔ کدتان برای «پچ» کردن محیط‌های مرورگر قدیمی که به جدیدترین مشخصات به‌روز نشده‌اند مفید است. استفاده از polyfill راه خوبی برای ساختن کد قابل‌پیش‌بینی در همهٔ محیط‌های پشتیبانی‌شده است.

| TIP: |
| :--- |
| ES5-Shim (https://github.com/es-shims/es5-shim) مجموعهٔ جامعی از shim/polyfillها برای رساندن یک پروژه به خط پایهٔ ES5 است، و به‌همین‌ترتیب ES6-Shim (https://github.com/es-shims/es6-shim) shim برای APIهای جدید اضافه‌شده از ES6 ارائه می‌دهد. در حالی که APIها را می‌توان shim/polyfill کرد، syntax جدید معمولاً نه. برای پل زدن شکاف نحوی، یک transpiler ES6-to-ES5 مثل Traceur (https://github.com/google/traceur-compiler/wiki/Getting-Started) هم می‌خواهید. |

اگر احتمالاً استانداردی در راه است و بیشتر بحث‌ها موافقند نام و نحوهٔ کارش چه خواهد بود، ساختن polyfill از قبل برای سازگاری با استانداردهای آینده‌نگر «prollyfill» (probably-fill) نامیده می‌شود.

گیر واقعی این است که اگر بعضی رفتار استاندارد جدید نتواند (کاملاً) polyfill/prollyfill شود.

در جامعه بحث است که آیا polyfill جزئی برای موارد رایج قابل قبول است (با مستند کردن بخش‌هایی که قابل polyfill نیستند)، یا اگر نمی‌تواند ۱۰۰٪ با مشخصات سازگار باشد باید از polyfill دوری کرد.

بسیاری از توسعه‌دهندگان حداقل بعضی polyfillهای جزئی رایج را می‌پذیرند (مثلاً برای `Object.create(..)`)، چون بخش‌هایی که پوشش داده نمی‌شوند بخش‌هایی نیست که قصد استفاده دارند.

بعضی باور دارند شرط `if` دور یک polyfill/shim باید نوعی تست سازگاری داشته باشد، و متد موجود را یا اگر غایب است یا تست‌ها را fail می‌کند جایگزین کند. این لایهٔ اضافی compliance testing گاهی برای تمایز «shim» (تست‌شدهٔ سازگاری) از «polyfill» (بررسی وجود) استفاده می‌شود.

تنها نتیجهٔ مطلق این است که جواب مطلق *درست* اینجا وجود ندارد. گسترش nativeها، حتی وقتی در محیط‌های قدیمی‌تر «به‌طور امن» انجام شود، ۱۰۰٪ امن نیست. همین‌طور تکیه بر nativeهای (احتمالاً گسترش‌یافته) در حضور کد دیگران.

هر دو باید همیشه با احتیاط، کد دفاعی و مستندات واضح زیاد دربارهٔ ریسک‌ها انجام شوند.
