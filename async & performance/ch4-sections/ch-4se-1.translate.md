# شکستن Run-to-Completion

در فصل ۱ توضیح دادیم یک انتظار مهم وجود دارد که تقریباً همه‌ی توسعه‌دهنده‌های JS در کدشان به آن تکیه می‌کنند: وقتی یک تابع شروع به اجرا می‌کند، تا پایان اجرا می‌رود و هیچ کد دیگری نمی‌تواند وسط آن وارد شود.

هرچقدر هم عجیب به نظر برسد، ES6 نوع جدیدی از تابع معرفی می‌کند که این رفتار run-to-completion را ندارد. اسم این نوع تابع «generator» است.

برای درک اثرش، این مثال را ببینید:

```js
var x = 1;

function foo() {
	x++;
	bar();				// <-- what about this line?
	console.log( "x:", x );
}

function bar() {
	x++;
}

foo();					// x: 3
```

در این مثال با قطعیت می‌دانیم `bar()` بین `x++` و `console.log(x)` اجرا می‌شود. اما اگر `bar()` نبود چه؟ واضح است خروجی به‌جای `3` می‌شد `2`.

حالا کمی ذهنتان را بپیچانیم: اگر `bar()` اصلاً وجود نداشت، اما هنوز somehow می‌توانست بین `x++` و `console.log(x)` اجرا شود چه؟ چنین چیزی چطور ممکن است؟

در زبان‌های **preemptive** چندریسمانی، در اصل ممکن است `bar()` دقیقاً در همان لحظه‌ی مناسب بین آن دو statement «interrupt» کند. اما JS نه preemptive است و نه (فعلاً) چندریسمانی. با این حال، یک شکل **cooperative** از همین «وقفه» (concurrency) ممکن است، اگر خود `foo()` بتواند somehow در آن نقطه «pause» اعلام کند.

**نکته:** من واژه‌ی "cooperative" را هم به‌خاطر پیوندش با اصطلاح کلاسیک concurrency (فصل ۱) استفاده می‌کنم، هم چون همان‌طور که در کد بعد می‌بینید، syntax مربوط به نقطه‌ی pause در ES6 کلمه‌ی `yield` است -- که حس «واگذاری کنترل به‌صورت مؤدبانه و همکاری‌محور» می‌دهد.

کد ES6 برای این نوع concurrency همکاری‌محور:

```js
var x = 1;

function *foo() {
	x++;
	yield; // pause!
	console.log( "x:", x );
}

function bar() {
	x++;
}
```

**نکته:** احتمالاً در بیشتر مستندات/کدهای JS، تعریف generator را به‌شکل `function* foo() { .. }` می‌بینید، نه فرمی که من اینجا نوشتم (`function *foo() { .. }`). تنها تفاوت، جای‌گذاری ظاهری `*` است. هر دو (و حتی `function*foo() { .. }`) از نظر نحوی/عملکردی یکسان‌اند. برای هر دو سبک استدلال‌هایی هست، ولی من `function *foo..` را ترجیح می‌دهم چون وقتی در متن با `*foo()` اشاره می‌کنم، از `foo()` معمولی قابل‌تفکیک‌تر است. این صرفاً ترجیح نگارشی است.

حالا چطور می‌توانیم کد بالا را طوری اجرا کنیم که `bar()` دقیقاً در نقطه‌ی `yield` داخل `*foo()` اجرا شود؟

```js
// construct an iterator `it` to control the generator
var it = foo();

// start `foo()` here!
it.next();
x;						// 2
bar();
x;						// 3
it.next();				// x: 3
```

خب، در این دو snippet چیزهای جدید و بالقوه گیج‌کننده زیاد است. ولی قبل از ورود به syntax/mechanics ژنراتورهای ES6، اول رفتار اجرایی را قدم‌به‌قدم مرور کنیم:

1. عبارت `it = foo()` هنوز generator `*foo()` را اجرا نمی‌کند؛ فقط یک *iterator* می‌سازد که اجرای آن را کنترل می‌کند.
2. اولین `it.next()` generator `*foo()` را شروع می‌کند و `x++` خط اول را اجرا می‌کند.
3. `*foo()` روی `yield` pause می‌شود؛ همان‌جا اولین `it.next()` تمام می‌شود. در این لحظه `*foo()` هنوز active هست، اما در وضعیت paused.
4. مقدار `x` را چک می‌کنیم؛ حالا `2` است.
5. `bar()` را صدا می‌زنیم که دوباره با `x++` مقدار را زیاد می‌کند.
6. دوباره `x` را چک می‌کنیم؛ حالا `3` است.
7. `it.next()` نهایی، generator `*foo()` را از همان نقطه‌ی pause شده ادامه می‌دهد و `console.log(..)` اجرا می‌شود که مقدار فعلی `x` یعنی `3` را چاپ می‌کند.

پس `*foo()` شروع شد، اما run-to-completion نداشت -- روی `yield` pause کرد. بعداً آن را resume کردیم و گذاشتیم تمام شود، ولی حتی همان هم اجباری نبود.

در نتیجه، generator نوع خاصی از تابع است که می‌تواند یک یا چند بار شروع/توقف شود و حتی لزوماً هیچ‌وقت تمام نشود. شاید هنوز واضح نباشد چرا این خیلی قدرتمند است، ولی در ادامه‌ی فصل می‌بینیم این یکی از بلوک‌های بنیادی برای ساخت الگوی generators-as-async-flow-control است.

### ورودی و خروجی

تابع generator یک تابع خاص با مدل پردازشی جدید است. اما هنوز «تابع» است؛ یعنی اصول پایه‌ی تابع بودنش حفظ می‌شود -- یعنی همچنان آرگومان می‌گیرد (input) و همچنان مقدار برمی‌گرداند (output):

```js
function *foo(x,y) {
	return x * y;
}

var it = foo( 6, 7 );

var res = it.next();

res.value;		// 42
```

آرگومان‌های `6` و `7` را به `*foo(..)` می‌دهیم (به‌ترتیب `x` و `y`). و `*foo(..)` مقدار `42` را برمی‌گرداند.

اینجا تفاوت مهمی با فراخوانی تابع عادی می‌بینیم. `foo(6,7)` ظاهراً آشناست، اما برخلاف تابع عادی، generator `*foo(..)` همان لحظه اجرا نشده است.

در عوض، فقط یک شیء *iterator* می‌سازیم (در `it`) که کنترل `*foo(..)` را به‌عهده دارد. بعد `it.next()` را می‌زنیم تا generator از موقعیت فعلی‌اش جلو برود و یا روی `yield` بعدی بایستد یا به انتها برسد.

خروجی `next(..)` شیئی است که پراپرتی `value` دارد و مقدار برگشتی `*foo(..)` (اگر باشد) را نگه می‌دارد. به زبان دیگر، `yield` می‌تواند وسط اجرای generator یک مقدار بیرون بفرستد؛ مثل یک `return` میانی.

هنوز مشخص نیست چرا این شیء غیرمستقیمِ *iterator* لازم است تا generator را کنترل کنیم. جلوتر کاملاً روشن می‌شود، *قول می‌دهم*.

#### پیام‌رسانی Iteration

علاوه بر آرگومان ورودی و مقدار خروجی، generatorها یک قابلیت پیام‌رسانی ورودی/خروجی خیلی قوی‌تر هم دارند که با `yield` و `next(..)` ساخته می‌شود.

```js
function *foo(x) {
	var y = x * (yield);
	return y;
}

var it = foo( 6 );

// start `foo(..)`
it.next();

var res = it.next( 7 );

res.value;		// 42
```

اول `6` را به‌عنوان `x` می‌دهیم. بعد `it.next()` می‌زنیم تا `*foo(..)` شروع شود.

داخل `*foo(..)` عبارت `var y = x ..` شروع به اجرا می‌کند، اما به expression `yield` می‌رسد. همان‌جا `*foo(..)` pause می‌شود (وسط همان statement انتساب!) و عملاً از کد فراخواننده می‌خواهد نتیجه‌ی expression `yield` را بدهد. سپس `it.next(7)` را صدا می‌زنیم تا `7` همان نتیجه‌ی `yield` متوقف‌شده شود.

پس حالا statement انتساب عملاً می‌شود `var y = 6 * 7`. بعد `return y` مقدار `42` را به‌عنوان نتیجه‌ی `it.next(7)` برمی‌گرداند.

یک نکته‌ی بسیار مهم (و در عین حال گیج‌کننده حتی برای برنامه‌نویس‌های باتجربه‌ی JS): بسته به زاویه‌ی نگاه، بین `yield` و `next(..)` یک mismatch دیده می‌شود. به‌طور کلی تعداد `next(..)` معمولاً یکی بیشتر از تعداد `yield` است -- در snippet بالا یک `yield` داریم و دو `next(..)`.

چرا mismatch؟

چون اولین `next(..)` همیشه generator را شروع می‌کند و تا اولین `yield` جلو می‌برد. اما این `next(..)` دوم است که اولین `yield` pause‌شده را «پاسخ» می‌دهد؛ `next(..)` سوم هم `yield` دوم را پاسخ می‌دهد و همین‌طور ادامه.

##### داستان دو سؤال

در واقع، اینکه mismatch حس کنید یا نه، بستگی دارد تمرکز ذهنی‌تان روی کدام سمت کد باشد.

فقط کد generator را ببینید:

```js
var y = x * (yield);
return y;
```

این `yield` **اول** در اصل یک *سؤال* می‌پرسد: «اینجا چه مقداری جای‌گذاری کنم؟»

چه کسی جواب می‌دهد؟ `next()` **اول** قبلاً اجرا شده تا generator به این نقطه برسد، پس واضح است که همان نمی‌تواند پاسخ دهد. بنابراین `next(..)` **دوم** باید به سؤال مطرح‌شده توسط `yield` **اول** پاسخ بدهد.

دیدید mismatch دوم-به-اول؟

حالا زاویه دید را برعکس کنیم: از نگاه iterator.

برای نمایش درست این زاویه باید روشن کنیم پیام‌ها دوطرفه‌اند -- expression `yield ..` می‌تواند در پاسخ به `next(..)` پیام بیرون بدهد، و `next(..)` هم می‌تواند به `yield` متوقف‌شده مقدار وارد کند:

```js
function *foo(x) {
	var y = x * (yield "Hello");	// <-- yield a value!
	return y;
}

var it = foo( 6 );

var res = it.next();	// first `next()`, don't pass anything
res.value;				// "Hello"

res = it.next( 7 );		// pass `7` to waiting `yield`
res.value;				// 42
```

`yield ..` و `next(..)` در حین اجرای generator یک سیستم پیام‌رسانی **دوطرفه** می‌سازند.

پس اگر فقط کد *iterator* را ببینیم:

```js
var res = it.next();	// first `next()`, don't pass anything
res.value;				// "Hello"

res = it.next( 7 );		// pass `7` to waiting `yield`
res.value;				// 42
```

**نکته:** عمداً به اولین `next()` مقداری پاس نمی‌دهیم. فقط `yield` pause‌شده می‌تواند مقدار `next(..)` را بپذیرد، و در شروع generator (اولین `next()`) هنوز **هیچ `yield` pause‌شده‌ای وجود ندارد**. specification و مرورگرهای سازگار هر مقداری که به اولین `next()` بدهید را بی‌صدا **discard** می‌کنند. با این حال کار بدی است چون کد مبهم و «ظاهراً موفق ولی عملاً بی‌اثر» می‌سازد. پس همیشه generator را با `next()` بدون آرگومان شروع کنید.

اولین `next()` (بدون آرگومان) در اصل یک *سؤال* است: «مقدار *بعدی* که generator `*foo(..)` برای من دارد چیست؟» و چه کسی جواب می‌دهد؟ expression اول `yield "Hello"`.

اینجا دیگر mismatch نداریم.

بسته به اینکه *چه کسی* را سؤال‌کننده بدانید، یا mismatch بین `yield` و `next(..)` می‌بینید یا نمی‌بینید.

اما صبر کنید! هنوز تعداد `next()` یکی بیشتر از `yield`هاست. پس `it.next(7)` آخر دوباره دارد می‌پرسد مقدار *بعدی* generator چیست. ولی دیگر `yield`ای نمانده که پاسخ دهد. پس چه کسی جواب می‌دهد؟

`return` جواب می‌دهد!

و اگر در generator **اصلاً `return` نداشته باشید** -- همان‌طور که در تابع عادی هم اجباری نیست -- همیشه یک `return;` ضمنی (یعنی `return undefined;`) وجود دارد که پاسخ پیش‌فرض سؤال آخرِ `it.next(7)` می‌شود.

این سؤال‌وجواب‌ها -- همان پیام‌رسانی دوطرفه‌ی `yield` و `next(..)` -- خیلی قدرتمندند، اما هنوز واضح نیست چطور به async flow-control وصل می‌شوند. داریم نزدیک می‌شویم!

### چند Iterator

ممکن است از ظاهر syntax چنین برداشت شود که وقتی از *iterator* برای کنترل generator استفاده می‌کنید، در حال کنترل خود generator function تعریف‌شده‌اید. اما یک ظرافت مهم هست: هر بار که یک *iterator* می‌سازید، در واقع یک instance جدید از همان generator ساخته می‌شود که آن iterator کنترلش می‌کند.

می‌توانید چند instance از یک generator را هم‌زمان اجرا کنید؛ حتی می‌توانند با هم تعامل داشته باشند:

```js
function *foo() {
	var x = yield 2;
	z++;
	var y = yield (x * z);
	console.log( x, y, z );
}

var z = 1;

var it1 = foo();
var it2 = foo();

var val1 = it1.next().value;			// 2 <-- yield 2
var val2 = it2.next().value;			// 2 <-- yield 2

val1 = it1.next( val2 * 10 ).value;		// 40  <-- x:20,  z:2
val2 = it2.next( val1 * 5 ).value;		// 600 <-- x:200, z:3

it1.next( val2 / 2 );					// y:300
										// 20 300 3
it2.next( val1 / 4 );					// y:10
										// 200 10 3
```

**هشدار:** رایج‌ترین کاربرد اجرای هم‌زمان چند instance از یک generator معمولاً این تعامل‌های درهم نیست، بلکه وقتی generator بدون ورودی، خودش مقدار تولید می‌کند (مثلاً از یک منبع مستقل). در بخش بعد بیشتر درباره‌ی value production حرف می‌زنیم.

بیایید خیلی کوتاه روند اجرای مثال را مرور کنیم:

1. هر دو instance از `*foo()` شروع می‌شوند و هر دو `next()` مقدار `2` را از `yield 2` بیرون می‌دهند.
2. `val2 * 10` یعنی `2 * 10` به instance اول (`it1`) فرستاده می‌شود؛ پس `x` می‌شود `20`. `z` از `1` به `2` افزایش می‌یابد و `20 * 2` yield می‌شود، پس `val1 = 40`.
3. `val1 * 5` یعنی `40 * 5` به instance دوم (`it2`) می‌رود؛ پس `x = 200`. `z` دوباره از `2` به `3` افزایش می‌یابد و `200 * 3` yield می‌شود، پس `val2 = 600`.
4. `val2 / 2` یعنی `600 / 2` به instance اول (`it1`) می‌رود؛ `y = 300` می‌شود و سپس `20 300 3` چاپ می‌شود.
5. `val1 / 4` یعنی `40 / 4` به instance دوم (`it2`) می‌رود؛ `y = 10` می‌شود و سپس `200 10 3` چاپ می‌شود.

این یک مثال «سرگرم‌کننده» برای اجرای ذهنی است. توانستید همه‌چیز را دقیق دنبال کنید؟

#### Interleaving

سناریوی زیر را از بخش "Run-to-completion" در فصل ۱ یادتان هست:

```js
var a = 1;
var b = 2;

function foo() {
	a++;
	b = b * a;
	a = b + 3;
}

function bar() {
	b--;
	a = 8 + b;
	b = a * 2;
}
```

با توابع عادی JS، یا `foo()` کامل اول اجرا می‌شود یا `bar()` کامل اول اجرا می‌شود؛ اما statementهای `foo()` نمی‌توانند با `bar()` interleave شوند. پس فقط دو خروجی ممکن داریم.

اما با generator، interleaving (حتی وسط statementها!) ممکن است:

```js
var a = 1;
var b = 2;

function *foo() {
	a++;
	yield;
	b = b * a;
	a = (yield b) + 3;
}

function *bar() {
	b--;
	yield;
	a = (yield 8) + b;
	b = a * (yield 2);
}
```

بسته به اینکه iteratorهای کنترل‌کننده‌ی `*foo()` و `*bar()` با چه ترتیبی صدا زده شوند، برنامه‌ی بالا می‌تواند چند نتیجه‌ی مختلف تولید کند. یعنی می‌توانیم (در یک شکل نسبتاً ساختگی) همان وضعیت «threaded race conditions» فصل ۱ را با interleave کردن iterationهای دو generator روی متغیرهای shared نشان دهیم.

اول یک helper به اسم `step(..)` بسازیم که یک *iterator* را کنترل می‌کند:

```js
function step(gen) {
	var it = gen();
	var last;

	return function() {
		// whatever is `yield`ed out, just
		// send it right back in the next time!
		last = it.next( last ).value;
	};
}
```

`step(..)` ابتدا generator را initialize می‌کند و `it` iteratorش را می‌سازد، سپس تابعی برمی‌گرداند که با هر فراخوانی یک گام iterator را جلو می‌برد. علاوه بر آن، مقداری که قبلاً yield شده بود در *next* بعدی دوباره به داخل فرستاده می‌شود. پس `yield 8` همان `8` می‌شود و `yield b` هم همان `b` (با مقدار لحظه‌ای‌اش).

حالا صرفاً برای سرگرمی، اثر interleaving تکه‌های مختلف `*foo()` و `*bar()` را امتحان کنیم. از حالت پایه‌ی ساده شروع می‌کنیم: بگذاریم `*foo()` کامل تمام شود و بعد `*bar()` (دقیقاً مثل فصل ۱):

```js
// make sure to reset `a` and `b`
a = 1;
b = 2;

var s1 = step( foo );
var s2 = step( bar );

// run `*foo()` completely first
s1();
s1();
s1();

// now run `*bar()`
s2();
s2();
s2();
s2();

console.log( a, b );	// 11 22
```

نتیجه نهایی `11` و `22` است؛ همان نتیجه‌ی نسخه‌ی فصل ۱. حالا ترتیب interleave را عوض کنیم و ببینیم مقدارهای نهایی `a` و `b` چطور تغییر می‌کنند:

```js
// make sure to reset `a` and `b`
a = 1;
b = 2;

var s1 = step( foo );
var s2 = step( bar );

s2();		// b--;
s2();		// yield 8
s1();		// a++;
s2();		// a = 8 + b;
			// yield 2
s1();		// b = b * a;
			// yield b
s1();		// a = b + 3;
s2();		// b = a * 2;
```

قبل از اینکه نتیجه را بگویم، می‌توانید حدس بزنید بعد از اجرای کد بالا `a` و `b` چه می‌شوند؟ بدون تقلب!

```js
console.log( a, b );	// 12 18
```

**نکته:** به‌عنوان تمرین، سعی کنید با جابه‌جایی ترتیب `s1()` و `s2()` ببینید چند ترکیب خروجی دیگر می‌شود گرفت. یادتان باشد همیشه به سه `s1()` و چهار `s2()` نیاز دارید. بحث قبلی درباره‌ی تطبیق `next()` با `yield` را برای دلیلش به خاطر بیاورید.

تقریباً قطعاً نمی‌خواهید عمداً چنین سطحی از interleavingِ گیج‌کننده بسازید، چون کد را خیلی سخت‌فهم می‌کند. اما این تمرین برای فهم اجرای concurrent چند generator در scope مشترک آموزنده است؛ چون جاهایی هست که همین قابلیت واقعاً کاربردی می‌شود.

در انتهای همین فصل، concurrency مربوط به generator را دقیق‌تر بررسی می‌کنیم.
