# Jobها

از ES6 به بعد، مفهومی جدید روی صف event loop اضافه شده به نام «Job queue». احتمالاً جایی که بیشتر با آن برخورد می‌کنید رفتار async مربوط به Promiseهاست (فصل ۳).

متاسفانه فعلاً این سازوکار API عمومی مستقیمی ندارد، پس نمایش عملی‌اش کمی پیچیده‌تر است. بنابراین فعلاً مفهومی توضیحش می‌دهیم تا وقتی در فصل ۳ رفتار async Promiseها را دیدیم، بدانید عملیات چطور زمان‌بندی و پردازش می‌شوند.

بهترین مدل ذهنی این است: «Job queue» صفی است که به انتهای هر tick از event loop وصل شده. بعضی رفتارهای async که ممکن است در یک tick رخ دهند، به‌جای اینکه یک رویداد جدید در صف event loop بگذارند، یک آیتم (Job) به انتهای Job queue همان tick فعلی اضافه می‌کنند.

انگار می‌گویید: «این کار دیگر را *بعدتر* انجام بده، ولی حتماً قبل از اینکه چیز دیگری رخ بدهد، همین الانِ بعدی انجام شود.»

یا با استعاره: event loop مثل صف یک وسیله‌ی شهربازی است که بعد از تمام‌شدن دور باید بروید ته صف. اما Job queue مثل این است که از وسیله پیاده شوید و مستقیم دوباره جلو صف بپرید.

یک Job می‌تواند Jobهای بیشتری هم به همین صف اضافه کند. بنابراین از نظر تئوری ممکن است یک «حلقه‌ی Job» (Jobی که دائم Job جدید اضافه کند) بی‌نهایت بچرخد و برنامه را از رفتن به tick بعدی event loop محروم کند. این از نظر مفهومی تقریباً مثل همان حلقه‌ی طولانی/بی‌نهایت (`while (true) ..`) است.

Jobها تا حدی روح هک `setTimeout(..0)` را دارند، اما با ترتیبی دقیق‌تر و تضمین‌شده‌تر: **بعدتر، اما در سریع‌ترین زمان ممکن**.

فرض کنیم یک API فرضی برای زمان‌بندی Job داریم و اسمش `schedule(..)` باشد:

```js
console.log( "A" );

setTimeout( function(){
	console.log( "B" );
}, 0 );

// theoretical "Job API"
schedule( function(){
	console.log( "C" );

	schedule( function(){
		console.log( "D" );
	} );
} );
```

شاید انتظار خروجی `A B C D` داشته باشید، اما خروجی `A C D B` می‌شود؛ چون Jobها در انتهای tick فعلی اجرا می‌شوند، ولی تایمر برای tick *بعدی* زمان‌بندی می‌شود (اگر نوبتش برسد).

در فصل ۳ می‌بینیم رفتار async Promiseها بر پایه‌ی Jobهاست؛ پس مهم است نسبت آن با event loop را دقیق بفهمیم.
