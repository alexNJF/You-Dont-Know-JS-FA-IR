# برنامه‌ای تکه‌تکه

ممکن است برنامه‌ی JS خودتان را در یک فایل *.js* بنویسید، اما تقریباً قطعی است که برنامه از چند «تکه» تشکیل شده که فقط یکی از آن‌ها *اکنون* اجرا می‌شود و بقیه *بعدتر* اجرا خواهند شد. رایج‌ترین واحد یک *chunk* همان `function` است.

مشکل رایج برای کسانی که تازه JS یاد می‌گیرند این است که *بعدتر* دقیقاً و بلافاصله بعد از *اکنون* اتفاق نمی‌افتد. به عبارت دیگر، کارهایی که *اکنون* کامل نمی‌شوند، طبق تعریف به‌صورت async کامل می‌شوند؛ پس رفتار blocking آن چیزی نیست که شاید شهودی انتظار دارید.

مثال:

```js
// ajax(..) is some arbitrary Ajax function given by a library
var data = ajax( "http://some.url.1" );

console.log( data );
// Oops! `data` generally won't have the Ajax results
```

احتمالاً می‌دانید درخواست Ajax معمولی sync کامل نمی‌شود؛ یعنی `ajax(..)` هنوز مقداری ندارد که برگرداند و در `data` ذخیره شود. اگر `ajax(..)` می‌توانست تا رسیدن پاسخ block کند، انتساب `data = ..` درست کار می‌کرد.

اما Ajax را این‌طور استفاده نمی‌کنیم. درخواست async را *اکنون* می‌فرستیم و نتیجه را *بعدتر* می‌گیریم.

ساده‌ترین (ولی نه تنها راه، و لزوماً هم بهترین راه) برای «صبر» از *اکنون* تا *بعدتر* استفاده از تابعی است که معمولاً callback نام دارد:

```js
// ajax(..) is some arbitrary Ajax function given by a library
ajax( "http://some.url.1", function myCallbackFunction(data){

	console.log( data ); // Yay, I gots me some `data`!

} );
```

**هشدار:** شاید شنیده باشید می‌شود Ajax را به شکل synchronous هم زد. هرچند از نظر فنی درست است، اما تحت هیچ شرایطی نباید این کار را بکنید، چون UI مرورگر (دکمه، منو، اسکرول و...) قفل می‌شود و تعامل کاربر از کار می‌افتد. این ایده بسیار بد است و باید همیشه از آن اجتناب کرد.

قبل از این‌که مخالفت کنید: نه، این‌که از شلوغی callback خوشتان نمی‌آید توجیهی برای Ajax sync و blocking نیست.

مثال دیگر:

```js
function now() {
	return 21;
}

function later() {
	answer = answer * 2;
	console.log( "Meaning of life:", answer );
}

var answer = now();

setTimeout( later, 1000 ); // Meaning of life: 42
```

این برنامه دو تکه دارد: چیزهایی که *اکنون* اجرا می‌شوند و چیزهایی که *بعدتر* اجرا می‌شوند. واضح است این دو کدام‌اند، اما شفاف‌ترش کنیم:

Now:
```js
function now() {
	return 21;
}

function later() { .. }

var answer = now();

setTimeout( later, 1000 );
```

Later:
```js
answer = answer * 2;
console.log( "Meaning of life:", answer );
```

تکه‌ی *اکنون* بلافاصله بعد از اجرای برنامه اجرا می‌شود. اما `setTimeout(..)` رویدادی (timeout) را برای *بعدتر* تنظیم می‌کند، پس محتوای `later()` در زمان بعدی اجرا خواهد شد (۱۰۰۰ میلی‌ثانیه بعد).

هر وقت بخشی از کد را داخل `function` قرار می‌دهید و مشخص می‌کنید در واکنش به رویدادی (تایمر، کلیک، پاسخ Ajax و...) اجرا شود، عملاً یک تکه‌ی *بعدتر* ساخته‌اید و ناهمگامی را وارد برنامه کرده‌اید.

### کنسول async

هیچ specification یا الزام رسمی‌ای برای نحوه‌ی کار `console.*` وجود ندارد -- این متدها جزو رسمی JavaScript نیستند، بلکه توسط *محیط میزبان* به JS اضافه می‌شوند (کتاب *Types & Grammar* این مجموعه).

پس مرورگرها و محیط‌های مختلف JS می‌توانند هر طور بخواهند رفتار کنند، و گاهی این باعث رفتار گیج‌کننده می‌شود.

به‌خصوص در بعضی مرورگرها و شرایط، `console.log(..)` الزاماً همان لحظه خروجی نمی‌دهد. دلیل اصلی این است که I/O در خیلی از برنامه‌ها (نه فقط JS) کند و blocking است. بنابراین ممکن است برای عملکرد بهتر صفحه/UI، مرورگر I/O مربوط به console را در پس‌زمینه و به‌صورت async انجام دهد، حتی بدون اینکه متوجه شوید.

سناریوی نه‌چندان رایج اما ممکن:

```js
var a = {
	index: 1
};

// later
console.log( a ); // ??

// even later
a.index++;
```

معمولاً انتظار داریم آبجکت `a` در همان لحظه‌ی `console.log(..)` snapshot شود و چیزی مثل `{ index: 1 }` چاپ شود؛ یعنی وقتی در خط بعد `a.index++` اجرا می‌شود، دارد چیزی را تغییر می‌دهد که جدا از خروجی قبلی است یا بعد از آن رخ می‌دهد.

در بیشتر مواقع، همین کد در ابزار توسعه‌ی مرورگر همان چیزی را نشان می‌دهد که انتظار دارید. اما ممکن است مرورگر تصمیم بگیرد I/O کنسول را عقب بیندازد؛ در این حالت ممکن است تا زمان نمایش آبجکت در کنسول، `a.index++` قبلاً انجام شده باشد و خروجی `{ index: 2 }` ببینید.

دقیقاً چه زمانی `console` defer می‌شود یا قابل‌مشاهده هست/نیست، ثابت نیست. فقط این ناهمگامی ممکن در I/O را بدانید تا اگر در دیباگ دیدید آبجکت بعد از `console.log(..)` تغییر کرده اما خروجی همان تغییر را نشان می‌دهد، غافلگیر نشوید.

**نکته:** اگر با این سناریوی نادر برخورد کردید، بهترین راه استفاده از breakpoint در debugger است نه تکیه بر `console` output. گزینه‌ی بعدی این است که با serialize کردن آبجکت به `string` (مثل `JSON.stringify(..)`) یک snapshot اجباری بگیرید.
