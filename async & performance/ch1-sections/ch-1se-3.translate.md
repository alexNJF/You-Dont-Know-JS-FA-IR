# Threading موازی

خیلی رایج است که واژه‌های «async» و «parallel» با هم قاطی شوند، درحالی‌که واقعاً فرق دارند. یادتان باشد async درباره‌ی شکاف بین *اکنون* و *بعدتر* است. اما parallel درباره‌ی رخداد هم‌زمان چیزهاست.

ابزارهای رایج محاسبات موازی process و thread هستند. processها و threadها مستقل اجرا می‌شوند و می‌توانند هم‌زمان اجرا شوند: روی پردازنده‌های جدا یا حتی رایانه‌های جدا. ضمن اینکه چند thread می‌توانند حافظه‌ی یک process واحد را به اشتراک بگذارند.

در مقابل، event loop کار را به taskهای کوچک می‌شکند و آن‌ها را سریالی اجرا می‌کند؛ بنابراین دسترسی و تغییر موازی روی حافظه‌ی مشترک را اجازه نمی‌دهد. البته parallelism و serialism می‌توانند به‌صورت event loopهای همکار در threadهای جدا کنار هم باشند.

Interleave شدن threadهای موازی با interleave شدن رویدادهای async در دو سطح دانه‌بندی کاملاً متفاوت رخ می‌دهد.

مثال:

```js
function later() {
	answer = answer * 2;
	console.log( "Meaning of life:", answer );
}
```

در event loop کل محتوای `later()` یک ورودی صف محسوب می‌شود. اما اگر از دید thread نگاه کنید، همین کد شاید از حدود یک دوجین عملیات low-level تشکیل شده. مثلاً `answer = answer * 2` یعنی ابتدا مقدار فعلی `answer` خوانده شود، بعد `2` جایی قرار بگیرد، ضرب انجام شود، و نتیجه دوباره در `answer` ذخیره شود.

در محیط single-threaded این جزئیات low-level مهم نیست چون چیزی thread را قطع نمی‌کند. اما در سیستم موازی که دو thread در یک برنامه کار می‌کنند، احتمال رفتار پیش‌بینی‌ناپذیر بالا می‌رود.

مثال:

```js
var a = 20;

function foo() {
	a = a + 1;
}

function bar() {
	a = a * 2;
}

// ajax(..) is some arbitrary Ajax function given by a library
ajax( "http://some.url.1", foo );
ajax( "http://some.url.2", bar );
```

در رفتار تک‌ریسمانی JavaScript، اگر `foo()` قبل از `bar()` اجرا شود نتیجه‌ی `a` می‌شود `42`، ولی اگر `bar()` اول اجرا شود نتیجه می‌شود `41`.

اما اگر رویدادهای JS با داده‌ی مشترک واقعاً موازی اجرا می‌شدند، مشکل خیلی ظریف‌تر می‌شد. به دو لیست زیر (شبه‌کد عملیات threadها برای `foo()` و `bar()`) نگاه کنید و فرض کنید دقیقاً هم‌زمان اجرا می‌شوند:

Thread 1 (`X` و `Y` حافظه‌های موقت‌اند):
```
foo():
  a. load value of `a` in `X`
  b. store `1` in `Y`
  c. add `X` and `Y`, store result in `X`
  d. store value of `X` in `a`
```

Thread 2 (`X` و `Y` حافظه‌های موقت‌اند):
```
bar():
  a. load value of `a` in `X`
  b. store `2` in `Y`
  c. multiply `X` and `Y`, store result in `X`
  d. store value of `X` in `a`
```

اگر دو thread واقعاً موازی باشند، مشکل دیده می‌شود: از حافظه‌ی موقت مشترک `X` و `Y` استفاده می‌کنند.

اگر ترتیب رخداد گام‌ها این باشد، نتیجه‌ی نهایی `a` چیست؟

```
1a  (load value of `a` in `X`   ==> `20`)
2a  (load value of `a` in `X`   ==> `20`)
1b  (store `1` in `Y`   ==> `1`)
2b  (store `2` in `Y`   ==> `2`)
1c  (add `X` and `Y`, store result in `X`   ==> `22`)
1d  (store value of `X` in `a`   ==> `22`)
2c  (multiply `X` and `Y`, store result in `X`   ==> `44`)
2d  (store value of `X` in `a`   ==> `44`)
```

نتیجه‌ی `a` می‌شود `44`. حالا اگر ترتیب این باشد:

```
1a  (load value of `a` in `X`   ==> `20`)
2a  (load value of `a` in `X`   ==> `20`)
2b  (store `2` in `Y`   ==> `2`)
1b  (store `1` in `Y`   ==> `1`)
2c  (multiply `X` and `Y`, store result in `X`   ==> `20`)
1c  (add `X` and `Y`, store result in `X`   ==> `21`)
1d  (store value of `X` in `a`   ==> `21`)
2d  (store value of `X` in `a`   ==> `21`)
```

نتیجه‌ی `a` می‌شود `21`.

پس برنامه‌نویسی threadی سخت است: اگر تمهیدات خاص برای جلوگیری از این نوع قطع/درهم‌رفتگی نگذارید، رفتار غیردترمینیست و غافلگیرکننده می‌گیرید که معمولاً دردسرساز است.

JavaScript داده را بین threadها share نمی‌کند، پس *آن* سطح از غیردترمینیسم مسئله نیست. اما این یعنی JS همیشه deterministic است؟ نه. یادتان هست ترتیب `foo()` و `bar()` دو نتیجه‌ی مختلف (`41` یا `42`) می‌داد؟

**نکته:** شاید فعلاً واضح نباشد، اما هر غیردترمینیسمی بد نیست. گاهی بی‌اهمیت است و گاهی عمدی. جلوتر نمونه‌های بیشتری می‌بینیم.

### اجرا تا اتمام (Run-to-Completion)

به‌خاطر single-thread بودن JavaScript، کد داخل `foo()` (و `bar()`) اتمیک است؛ یعنی وقتی `foo()` شروع شود، کل کدش تمام می‌شود قبل از اینکه حتی یک خط از `bar()` اجرا شود، یا برعکس. این رفتار را «run-to-completion» می‌گویند.

این معنا وقتی `foo()` و `bar()` بزرگ‌تر باشند واضح‌تر است:

```js
var a = 1;
var b = 2;

function foo() {
	a++;
	b = b * a;
	a = b + 3;
}

function bar() {
	b--;
	a = 8 + b;
	b = a * 2;
}

// ajax(..) is some arbitrary Ajax function given by a library
ajax( "http://some.url.1", foo );
ajax( "http://some.url.2", bar );
```

چون `foo()` توسط `bar()` قطع نمی‌شود و برعکس، این برنامه فقط دو خروجی ممکن دارد، بسته به اینکه کدام اول شروع شود. اگر threading واقعی بود و statementها می‌توانستند interleave شوند، تعداد خروجی‌های ممکن خیلی بیشتر می‌شد.

Chunk 1 همگام است (*اکنون*)، اما Chunkهای 2 و 3 ناهمگام‌اند (*بعدتر*)؛ پس اجرای آن‌ها با فاصله‌ی زمانی از هم جدا می‌شود.

Chunk 1:
```js
var a = 1;
var b = 2;
```

Chunk 2 (`foo()`):
```js
a++;
b = b * a;
a = b + 3;
```

Chunk 3 (`bar()`):
```js
b--;
a = 8 + b;
b = a * 2;
```

Chunkهای 2 و 3 می‌توانند با هر ترتیب «اولی» رخ دهند، پس دو خروجی ممکن داریم:

Outcome 1:
```js
var a = 1;
var b = 2;

// foo()
a++;
b = b * a;
a = b + 3;

// bar()
b--;
a = 8 + b;
b = a * 2;

a; // 11
b; // 22
```

Outcome 2:
```js
var a = 1;
var b = 2;

// bar()
b--;
a = 8 + b;
b = a * 2;

// foo()
a++;
b = b * a;
a = b + 3;

a; // 183
b; // 180
```

دو خروجی از یک کد یعنی هنوز غیردترمینیسم داریم. اما این غیردترمینیسم در سطح ترتیب اجرای تابع (رویداد) است، نه سطح statement یا حتی operation، مثل threadها. یعنی نسبت به threading *دترمینیست‌تر* است.

در زمینه‌ی JS، این غیردترمینیسمِ ترتیب تابعی همان چیزی است که معمولاً «race condition» می‌گویند؛ چون `foo()` و `bar()` مسابقه می‌دهند کدام زودتر اجرا شود. مشخصاً «race condition» است چون قابل پیش‌بینی قطعی نیست `a` و `b` چه مقادیری بگیرند.

**نکته:** اگر در JS تابعی وجود داشت که run-to-completion نداشت، خروجی‌های ممکن خیلی بیشتر نمی‌شد؟ جالب اینکه ES6 چیزی از این دست معرفی می‌کند (فصل ۴ «Generatorها»). فعلاً نگرانش نباشید، جلوتر برمی‌گردیم.
