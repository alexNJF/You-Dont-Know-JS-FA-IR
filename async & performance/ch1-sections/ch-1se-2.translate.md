# Event Loop

بیایید یک ادعای (شاید شوکه‌کننده) مطرح کنیم: با وجود اینکه JS به‌وضوح اجازه‌ی کد async می‌دهد (مثل همان timeout)، خود JavaScript تا همین اواخر (ES6) عملاً هیچ مفهوم مستقیمی از ناهمگامی داخل خودش نداشت.

**چی؟!** عجیب به نظر می‌رسد، اما درست است. موتور JS به‌تنهایی هیچ کاری جز اجرای یک تکه از برنامه در هر لحظه انجام نمی‌دهد، آن‌هم وقتی از او خواسته شود.

«خواسته شود». توسط چه کسی؟ این بخش مهم ماجراست.

موتور JS در خلأ اجرا نمی‌شود. داخل یک *محیط میزبان* اجرا می‌شود که برای بیشتر توسعه‌دهنده‌ها همان مرورگر وب است. در چند سال اخیر (و نه فقط آن)، JS بیرون از مرورگر هم رفته؛ مثل سرورها با Node.js. حتی امروز JavaScript در انواع دستگاه‌ها از ربات تا لامپ هوشمند embed می‌شود.

اما نخ مشترک همه‌ی این محیط‌ها این است که مکانیزمی دارند برای اجرای چند تکه از برنامه *در طول زمان*؛ مکانیزمی که هر بار موتور JS را فراخوانی می‌کند و به آن «event loop» می‌گوییم.

به بیان دیگر، موتور JS ذاتاً درکی از *زمان* نداشته، بلکه محیطی برای اجرای on-demand تکه‌های دلخواه JS بوده است. این محیط اطراف است که همیشه «رویدادها» (اجرای کد JS) را *زمان‌بندی* می‌کند.

پس مثلاً وقتی برنامه‌ی JS یک درخواست Ajax برای گرفتن داده از سرور می‌فرستد، کد «پاسخ» را داخل یک تابع می‌گذارید (معمولاً callback)، و موتور JS به محیط میزبان می‌گوید: «فعلاً اجرای من را متوقف می‌کنم، اما هر وقت درخواست شبکه تمام شد و داده داشتی، لطفاً این تابع را *call back* کن.»

مرورگر هم منتظر پاسخ شبکه می‌ماند و وقتی چیزی برای تحویل دارد، اجرای callback را با قرار دادن آن در *event loop* زمان‌بندی می‌کند.

پس *event loop* چیست؟

اول با یک شبه‌کد تقریبی تصورش کنیم:

```js
// `eventLoop` is an array that acts as a queue (first-in, first-out)
var eventLoop = [ ];
var event;

// keep going "forever"
while (true) {
	// perform a "tick"
	if (eventLoop.length > 0) {
		// get the next event in the queue
		event = eventLoop.shift();

		// now, execute the next event
		try {
			event();
		}
		catch (err) {
			reportError(err);
		}
	}
}
```

این قطعاً pseudocode ساده‌شده‌ای است، اما برای فهم مفهوم کافی است.

همان‌طور که می‌بینید، یک حلقه‌ی همیشگی داریم (`while`) که هر دورش یک «tick» است. در هر tick اگر رویدادی در صف باشد، برداشته می‌شود و اجرا می‌گردد. این رویدادها همان callbackهای تابعی شما هستند.

نکته‌ی مهم: `setTimeout(..)` callback شما را مستقیم داخل صف event loop نمی‌گذارد. کاری که می‌کند تنظیم تایمر است؛ وقتی تایمر منقضی شد، محیط callback را داخل event loop قرار می‌دهد تا در یکی از tickهای آینده اجرا شود.

اگر همان لحظه ۲۰ مورد دیگر در صف باشد چه؟ callback شما صبر می‌کند و پشت بقیه در صف می‌ایستد. معمولاً راهی برای پریدن از صف و اجرای فوری نیست. همین توضیح می‌دهد چرا تایمرهای `setTimeout(..)` همیشه با دقت زمانی کامل fire نمی‌شوند. به‌صورت تقریبی تضمین دارید callback *زودتر* از بازه‌ی تعیین‌شده اجرا نمی‌شود، اما ممکن است همان لحظه یا دیرتر اجرا شود، بسته به وضعیت صف رویداد.

پس برنامه‌ی شما معمولاً به تکه‌های کوچکی تقسیم می‌شود که در صف event loop یکی‌یکی اجرا می‌شوند. و از نظر فنی، رویدادهای دیگرِ غیرمستقیم مرتبط با برنامه‌ی شما هم می‌توانند بینشان interleave شوند.

**نکته:** گفتیم «تا همین اواخر» چون ES6 در محل مدیریت صف event loop کمی تغییر ایجاد کرد. بیشتر یک نکته‌ی فنی رسمی است، اما ES6 حالا نحوه‌ی کار event loop را مشخص می‌کند؛ یعنی از نظر فنی این موضوع در قلمرو موتور JS می‌آید نه فقط *محیط میزبان*. یکی از دلایل اصلی این تغییر معرفی Promiseهای ES6 است (فصل ۳) چون به کنترل مستقیم و ریزدانه روی زمان‌بندی عملیات در صف event loop نیاز دارند (بحث `setTimeout(..0)` در بخش «Cooperation»).
