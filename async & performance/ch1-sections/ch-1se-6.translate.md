# ترتیب Statementها

ترتیبی که statementها را در کد می‌نویسیم الزاماً همان ترتیبی نیست که موتور JS آن‌ها را اجرا می‌کند. شاید این ادعا عجیب باشد، پس کوتاه بررسی‌اش می‌کنیم.

اما قبلش یک نکته را خیلی روشن کنیم: قواعد/گرامر زبان (کتاب *Types & Grammar*) از دید برنامه رفتار بسیار قابل‌پیش‌بینی و قابل‌اعتماد برای ترتیب statementها تعریف می‌کنند. پس آنچه این‌جا می‌گوییم چیزهایی نیست که **اصولاً باید بتوانید در برنامه مشاهده کنید**.

**هشدار:** اگر زمانی توانستید reordering مربوط به کامپایلر را واقعاً *مشاهده* کنید، این نقض مشخصات است و قطعاً bug موتور JS است که باید گزارش و اصلاح شود. اما خیلی رایج‌تر این است که فکر کنید موتور JS «یک کار عجیب» کرده، در حالی که ایراد از کد خودتان است (احتمالاً race condition). پس اول و چندباره کد خودتان را بررسی کنید. debugger با breakpoint و step-by-step قدرتمندترین ابزار شماست.

مثال:

```js
var a, b;

a = 10;
b = 30;

a = a + 1;
b = b + 1;

console.log( a + b ); // 42
```

این کد async مشخصی ندارد (جز حالت نادر I/O async در `console` که گفتیم)، پس فرض طبیعی این است که خط‌به‌خط از بالا به پایین اجرا شود.

اما *ممکن* است موتور JS بعد از کامپایل (بله JS کامپایل می‌شود -- کتاب *Scope & Closures*) فرصت‌هایی برای اجرای سریع‌تر پیدا کند و ترتیب statementها را (به‌صورت امن) جابه‌جا کند. تا وقتی reordering قابل مشاهده نباشد، از نظر موتور مجاز است.

مثلاً ممکن است موتور این‌طور اجرا کند:

```js
var a, b;

a = 10;
a++;

b = 30;
b++;

console.log( a + b ); // 42
```

یا این‌طور:

```js
var a, b;

a = 11;
b = 31;

console.log( a + b ); // 42
```

یا حتی:

```js
// because `a` and `b` aren't used anymore, we can
// inline and don't even need them!
console.log( 42 ); // 42
```

در همه‌ی این حالت‌ها، موتور در زمان کامپایل بهینه‌سازی امن انجام می‌دهد، چون نتیجه‌ی *قابل مشاهده* یکی می‌ماند.

اما سناریوی زیر برای این بهینه‌سازی‌های خاص ناامن است و نباید مجاز باشد (هرچند ممکن است بهینه‌سازی‌های دیگری انجام شود):

```js
var a, b;

a = 10;
b = 30;

// we need `a` and `b` in their preincremented state!
console.log( a * b ); // 300

a = a + 1;
b = b + 1;

console.log( a + b ); // 42
```

نمونه‌های دیگری که reordering می‌تواند اثر جانبی قابل مشاهده بسازد (و پس باید منع شود) شامل هر فراخوانی تابع با side effect است (خصوصاً getterها)، یا آبجکت‌های Proxy در ES6 (کتاب *ES6 & Beyond*).

مثال:

```js
function foo() {
	console.log( b );
	return 1;
}

var a, b, c;

// ES5.1 getter literal syntax
c = {
	get bar() {
		console.log( a );
		return 1;
	}
};

a = 10;
b = 30;

a += foo();				// 30
b += c.bar;				// 11

console.log( a + b );	// 42
```

اگر `console.log(..)`ها در این مثال نبودند (که صرفاً برای نمایش side effect گذاشته‌ایم)، موتور احتمالاً می‌توانست (اگر می‌خواست) کد را این‌گونه بازچینی کند:

```js
// ...

a = 10 + foo();
b = 30 + c.bar;

// ...
```

خوشبختانه معناشناسی JS ما را از کابوس‌های *قابل مشاهده* ناشی از reordering کامپایلر حفظ می‌کند. اما همچنان مهم است بدانیم فاصله‌ی بین ترتیب نگارش کد (بالا به پایین) و ترتیب اجرای واقعی پس از کامپایل چقدر می‌تواند ظریف باشد.

reordering کامپایلر تا حدی یک «خرده‌استعاره» برای concurrency و interaction است. همین آگاهی مفهومی می‌تواند در فهم بهتر جریان async در JS کمک زیادی بکند.
