# مسئله‌ی اعتماد

ناهماهنگی بین برنامه‌ریزی ترتیبی مغز و کد async مبتنی بر callback فقط بخشی از مشکل callbackهاست. یک نگرانی عمیق‌تر هم وجود دارد.

دوباره به ایده‌ی callback function به‌عنوان continuation (نیمه‌ی دوم برنامه) برگردیم:

```js
// A
ajax( "..", function(..){
	// C
} );
// B
```

`// A` و `// B` *اکنون* رخ می‌دهند و کنترل مستقیمشان دست برنامه‌ی اصلی JS است. اما `// C` به *بعدتر* موکول می‌شود و کنترلش دست طرف دیگری است -- اینجا تابع `ajax(..)`. در نگاه پایه، این hand-off کنترل معمولاً خیلی هم دردسرساز به نظر نمی‌رسد.

اما فریب کم‌رخداد بودنش را نخورید. این تغییر کنترل در واقع یکی از بدترین (و در عین حال ظریف‌ترین) مشکلات طراحی callbackمحور است. مسئله حول این است که گاهی `ajax(..)` (یعنی همان «طرفی» که continuation را به او می‌سپارید) تابعی نیست که خودتان نوشته باشید یا مستقیم کنترلش کنید. خیلی وقت‌ها utilityای از یک طرف سوم است.

به این می‌گوییم "inversion of control": وقتی بخشی از برنامه را برمی‌دارید و کنترل اجرای آن را به یک طرف سوم می‌دهید. بین کد شما و utility طرف سوم یک «قرارداد نانوشته» شکل می‌گیرد -- مجموعه‌ای از چیزهایی که انتظار دارید رعایت شوند.

### داستان پنج callback

شاید بلافاصله واضح نباشد چرا این موضوع این‌قدر مهم است. یک سناریوی کمی اغراق‌آمیز می‌سازم تا خطر اعتماد بهتر دیده شود.

فرض کنید توسعه‌دهنده‌ای هستید که باید checkout یک سایت فروش تلویزیون‌های گران‌قیمت را بسازد. همه‌ی صفحه‌های checkout درست کار می‌کنند. در صفحه‌ی آخر، وقتی کاربر «تایید خرید» می‌زند، باید یک تابع طرف سوم (مثلاً شرکت analytics) صدا بزنید تا خرید track شود.

می‌بینید utilityای داده‌اند که ظاهراً async است (احتمالاً برای performance)، یعنی باید callback بدهید. داخل continuationای که پاس می‌دهید، کد نهایی شارژ کارت اعتباری و نمایش صفحه‌ی تشکر را می‌گذارید.

کد:

```js
analytics.trackPurchase( purchaseData, function(){
	chargeCreditCard();
	displayThankyouPage();
} );
```

ساده است، نه؟ کد را می‌نویسید، تست می‌کنید، همه‌چیز خوب است و deploy می‌کنید. همه خوشحال!

شش ماه می‌گذرد و مشکلی نیست. تقریباً یادتان می‌رود چنین کدی نوشته بودید. یک صبح در کافه قبل کار، وسط لاته، رئیس با اضطراب زنگ می‌زند که فوری بیا شرکت.

وقتی می‌رسید می‌فهمید کارت اعتباری یک مشتری مهم برای همان تلویزیون ۵ بار شارژ شده و طبیعی است عصبانی باشد. پشتیبانی عذرخواهی کرده و refund داده، اما رئیس می‌خواهد بداند این چطور ممکن شده. «مگه برای این چیزها تست نداریم؟»

خودتان هم کد را یادتان نیست. لاگ‌ها را می‌گردید و به این نتیجه می‌رسید تنها توضیح این است که utility analytics به‌دلیلی callback شما را به‌جای یک بار، پنج بار صدا زده. در مستنداتشان هم حرفی از این رفتار نیست.

عصبانی با پشتیبانی آن شرکت تماس می‌گیرید. آن‌ها هم شگفت‌زده می‌شوند، مسئله را به تیم توسعه escalation می‌دهند و می‌گویند خبر می‌دهند. روز بعد ایمیل مفصلی می‌آید و شما فوراً برای رئیس forward می‌کنید.

ظاهراً توسعه‌دهنده‌های analytics روی کد آزمایشی کار می‌کردند که تحت شرایطی callback پاس‌داده‌شده را هر ثانیه یک‌بار، تا ۵ ثانیه retry می‌کرد و بعد timeout می‌داد. قصد deploy نداشتند، اما somehow وارد production شده، و خیلی هم معذرت‌خواه‌اند. کلی هم درباره‌ی علت و پیشگیری بعدی توضیح می‌دهند.

بعد چه؟

با رئیس صحبت می‌کنید، اما او اصلاً راحت نیست. اصرار می‌کند (و شما با اکراه می‌پذیرید) که دیگر نمی‌شود به *آن‌ها* اعتماد کرد و باید checkout را در برابر چنین آسیب‌پذیری محافظت کنید.

بعد از کمی دستکاری، کد ad hoc ساده‌ای می‌نویسید که تیم ظاهراً با آن راضی است:

```js
var tracked = false;

analytics.trackPurchase( purchaseData, function(){
	if (!tracked) {
		tracked = true;
		chargeCreditCard();
		displayThankyouPage();
	}
} );
```

**نکته:** باید از فصل ۱ آشنا باشد، چون عملاً داریم latch می‌سازیم تا اگر callback چندبار هم‌زمان صدا شد، فقط یک بار عبور کند.

اما بعد یکی از QAها می‌پرسد: «اگر callback را اصلاً صدا نزنند چی؟» اوه! هیچ‌کدام به این فکر نکرده بودید.

حالا وارد سوراخ خرگوش می‌شوید و به همه‌ی حالت‌های خراب‌کاری احتمالی در callback فکر می‌کنید. تقریباً این فهرست درمی‌آید:

* callback را خیلی زود صدا بزند (قبل از track شدن)
* callback را خیلی دیر صدا بزند (یا اصلاً نزند)
* callback را کمتر یا بیشتر از انتظار صدا بزند (مثل مشکلی که خوردید)
* محیط/پارامترهای لازم را به callback پاس ندهد
* خطا/استثنای رخ‌داده را قورت بدهد
* ...

این فهرست باید نگران‌کننده باشد، چون واقعاً هست. کم‌کم می‌فهمید باید برای **تک‌تک callback**هایی که به utility غیرقابل‌اعتماد می‌دهید، حجم زیادی منطق ad hoc بنویسید.

الآن دقیق‌تر می‌فهمید callback hell چقدر جهنمی است.

### فقط کد دیگران نیست

شاید بعضی‌ها هنوز شک داشته باشند که موضوع آن‌قدر مهم است که من می‌گویم. شاید اصلاً زیاد با utility واقعاً طرف‌سوم کار نمی‌کنید. شاید API نسخه‌دار دارید یا کتابخانه‌ها را self-host می‌کنید تا رفتارشان زیر پایتان عوض نشود.

پس این را در نظر بگیرید: آیا واقعاً می‌توانیم به utilityهایی که ظاهراً خودمان کنترل می‌کنیم هم *کاملاً* اعتماد کنیم؟

این‌طور نگاه کنید: بیشتر ما قبول داریم باید برای پارامترهای ورودی تابع‌های داخلی خودمان هم تا حدی defensive check بگذاریم تا خطاهای غیرمنتظره کم شود.

اعتماد بیش از حد به ورودی:
```js
function addNumbers(x,y) {
	// + is overloaded with coercion to also be
	// string concatenation, so this operation
	// isn't strictly safe depending on what's
	// passed in.
	return x + y;
}

addNumbers( 21, 21 );	// 42
addNumbers( 21, "21" );	// "2121"
```

دفاع در برابر ورودی غیرقابل‌اعتماد:
```js
function addNumbers(x,y) {
	// ensure numerical input
	if (typeof x != "number" || typeof y != "number") {
		throw Error( "Bad parameters" );
	}

	// if we get here, + will safely do numeric addition
	return x + y;
}

addNumbers( 21, 21 );	// 42
addNumbers( 21, "21" );	// Error: "Bad parameters"
```

یا نسخه‌ی امن‌تر و کاربرپسندتر:
```js
function addNumbers(x,y) {
	// ensure numerical input
	x = Number( x );
	y = Number( y );

	// + will safely do numeric addition
	return x + y;
}

addNumbers( 21, 21 );	// 42
addNumbers( 21, "21" );	// 42
```

به هر روشی، این نوع check/normalization روی ورودی تابع بسیار رایج است، حتی درباره‌ی کدی که «فکر می‌کنیم» کاملاً قابل اعتماد است. یک جور نسخه‌ی برنامه‌نویسیِ اصل سیاسی «اعتماد کن، اما راستی‌آزمایی کن».

پس منطقی نیست همین کار را برای callbackهای async هم انجام دهیم؟ نه فقط کد خارجی، حتی کدی که «زیر کنترل خودمان» است؟ **قطعاً باید انجام دهیم.**

اما callback کمک خاصی نمی‌کند. باید تمام این سازوکار را خودمان بسازیم و معمولاً نتیجه‌اش boilerplate/overhead تکراری برای هر callback است.

آزاردهنده‌ترین مشکل callback همان *inversion of control* است که در امتداد خط‌های اعتماد، فروپاشی کامل ایجاد می‌کند.

اگر کدی دارید که callback استفاده می‌کند -- مخصوصاً (نه فقط) با utilityهای طرف‌سوم -- و برای این مسائل اعتمادِ ناشی از inversion of control هیچ mitigationی نگذاشته‌اید، کد شما *الآن* bug دارد، حتی اگر هنوز به شما نخورده. bug نهفته هم bug است.

جهنم، واقعاً.
