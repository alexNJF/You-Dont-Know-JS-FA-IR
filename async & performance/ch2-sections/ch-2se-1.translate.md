# Continuationها

بیایید به مثال callback async که فصل ۱ با آن شروع کردیم برگردیم، اما کمی تغییرش می‌دهم تا نکته‌ای را نشان دهم:

```js
// A
ajax( "..", function(..){
	// C
} );
// B
```

`// A` و `// B` نیمه‌ی اول برنامه را نشان می‌دهند (یا همان *now*)، و `// C` نیمه‌ی دوم را (یا همان *later*). نیمه‌ی اول فوراً اجرا می‌شود و بعد یک «مکث» با طول نامعین داریم. در آینده، اگر فراخوانی Ajax کامل شود، برنامه از همان‌جایی که مانده ادامه می‌دهد و با نیمه‌ی دوم *continue* می‌کند.

به بیان دیگر، callback function ادامه‌ی برنامه را wrap/encapsulate می‌کند.

کد را حتی ساده‌تر کنیم:

```js
// A
setTimeout( function(){
	// C
}, 1000 );
// B
```

یک لحظه مکث کنید و از خودتان بپرسید این برنامه را چطور برای کسی که درباره‌ی JS کمتر می‌داند توضیح می‌دهید. با صدای بلند امتحان کنید؛ تمرین خوبی است و نکته‌های بعدی را ملموس‌تر می‌کند.

بیشتر خواننده‌ها احتمالاً چیزی شبیه این گفتند/فکر کردند: «A را انجام بده، بعد timeout بگذار ۱۰۰۰ میلی‌ثانیه صبر کند، بعد وقتی timeout fire شد C را انجام بده.» چقدر به توضیح شما نزدیک بود؟

شاید خودتان را اصلاح کرده باشید: «A را انجام بده، timeout ۱۰۰۰ میلی‌ثانیه‌ای را تنظیم کن، بعد B را انجام بده، بعد از fire شدن timeout برو C.» این از اولی دقیق‌تر است. تفاوت را می‌بینید؟

با اینکه نسخه‌ی دوم دقیق‌تر است، هر دو توضیح هنوز در نگاشت درست بین مغز ما و کد، و بین کد و موتور JS ناقص‌اند. این disconnect هم ظریف است و هم بنیادی، و درست در قلب فهم محدودیت callback به‌عنوان ابزار بیان/مدیریت async قرار دارد.

به‌محض اینکه یک continuation (یا ده‌ها continuation مثل خیلی برنامه‌ها) را به شکل callback function وارد می‌کنیم، شکافی بین نحوه‌ی کار مغز ما و نحوه‌ی اجرای کد شکل می‌گیرد. هرجا این دو از هم دور شوند (و این تنها موردش نیست)، نتیجه ناگزیر این است که فهم، استدلال، دیباگ و نگهداری کد سخت‌تر می‌شود.
