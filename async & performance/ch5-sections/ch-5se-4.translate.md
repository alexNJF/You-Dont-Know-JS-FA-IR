# مرور

چهار فصل اول این کتاب بر این فرض بنا شد که الگوهای کدنویسی async به شما امکان می‌دهند کد performantتری بنویسید، که معمولاً پیشرفت خیلی مهمی است. اما رفتار async تا حدی پیش می‌رود، چون هنوز در نهایت به یک thread مربوط به event loop محدود است.

پس در این فصل چند مکانیزم سطح‌برنامه را پوشش دادیم که کارایی را باز هم بالاتر می‌برند.

Web Workerها اجازه می‌دهند یک فایل JS (یعنی برنامه) را روی thread جدا اجرا کنید و با eventهای async بین threadها پیام ردوبدل کنید. برای offload کردن کارهای طولانی یا resource-intensive به thread دیگر عالی‌اند تا thread اصلی UI responsiveتر بماند.

SIMD پیشنهاد می‌دهد عملیات ریاضی موازی در سطح CPU به APIهای JavaScript map شود تا عملیات data-parallel پرفورمنس‌بالا (مثل پردازش عددی روی داده‌های بزرگ) ممکن شود.

در نهایت، asm.js یک زیرمجموعه‌ی کوچک از JavaScript را توصیف می‌کند که بخش‌های سخت‌بهینه‌سازی JS (مثل garbage collection و coercion) را دور می‌زند و به JS engine اجازه می‌دهد چنین کدی را با بهینه‌سازی تهاجمی اجرا کند. asm.js را می‌شود دستی نوشت، اما بسیار خسته‌کننده و خطاپذیر است، شبیه نوشتن دستی assembly (اسمش هم از همین می‌آید). هدف اصلی این است که asm.js مقصد خوبی برای cross-compilation از زبان‌های بسیار بهینه‌شده‌ی دیگر باشد -- مثلاً تبدیل C/C++ به JavaScript با Emscripten.

هرچند در این فصل صریح پوشش ندادیم، ایده‌های رادیکال‌تری هم در مراحل خیلی اولیه‌ی بحث برای JavaScript وجود دارد، از جمله تقریب‌هایی از قابلیت threading مستقیم (نه فقط پشت APIهای ساختار داده). چه این اتفاق صریح بیفتد، چه صرفاً parallelism بیشتری پشت‌صحنه وارد JS شود، آینده‌ی کارایی سطح‌برنامه در JS واقعاً *امیدبخش* به نظر می‌رسد.
