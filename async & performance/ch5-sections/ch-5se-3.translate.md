# asm.js

`asm.js` برچسبی است برای یک زیرمجموعه‌ی بسیار قابل‌بهینه‌سازی از زبان JavaScript. با پرهیز دقیق از بعضی مکانیزم‌ها و الگوهایی که بهینه‌سازی‌شان *سخت* است (مثل garbage collection، coercion و...)، کد سبک asm.js می‌تواند توسط JS engine تشخیص داده شود و با بهینه‌سازی‌های low-level تهاجمی اجرا شود.

برخلاف مکانیزم‌های دیگر کارایی که در این فصل گفتیم، asm.js لزوماً چیزی نیست که باید وارد specification رسمی زبان JS شود. برای asm.js یک specification هم وجود دارد، اما بیشتر برای ثبت مجموعه‌ای توافقی از سرنخ‌های بهینه‌سازی است، نه مجموعه‌ای از الزام‌های موتورهای JS.

فعلاً syntax جدیدی پیشنهاد نشده. در عوض asm.js می‌گوید چطور syntax استاندارد موجود JS را که با قواعد asm.js سازگار است تشخیص دهیم تا engineها بتوانند بهینه‌سازی‌های خودشان را اعمال کنند.

بین vendorهای مرورگر اختلاف نظرهایی بود که asm.js دقیقاً چطور باید فعال شود. نسخه‌های اولیه نیاز به pragma مثل `"use asm";` داشتند (شبیه `"use strict";`) تا سرنخی برای engine باشد که دنبال فرصت‌های asm.js بگردد. برخی دیگر معتقد بودند asm.js باید صرفاً مجموعه‌ای heuristic باشد که engine خودکار تشخیص دهد، بدون اقدام اضافی از طرف نویسنده؛ یعنی برنامه‌های موجود هم شاید بدون تغییر خاص از این بهینه‌سازی‌ها بهره ببرند.

### بهینه‌سازی با asm.js چگونه است؟

اولین نکته‌ی مهم در بهینه‌سازی asm.js مربوط به typeها و coercion است (کتاب *Types & Grammar*). اگر JS engine مجبور باشد در طول عملیات مختلف چند نوع متفاوت مقدار را برای یک متغیر track کند تا coercion لازم را هندل کند، این کار اضافه‌ی زیادی است و بهینه‌سازی را suboptimal نگه می‌دارد.

**نکته:** اینجا برای نمایش از کد سبک asm.js استفاده می‌کنیم، اما معمولاً انتظار نمی‌رود با دست چنین کدی بنویسید. asm.js بیشتر هدف compile شدن از ابزارهای دیگر است، مثل Emscripten. نوشتن دستی asm.js ممکن است، ولی اغلب ایده‌ی بدی است چون کد خیلی low-level می‌شود و نگهداری‌اش زمان‌بر و خطاپذیر است. با این حال ممکن است جاهایی بخواهید دستی برای بهینه‌سازی asm.js tweak انجام دهید.

چند «ترفند» هست که به JS engine آگاه به asm.js سرنخ نوع متغیر/عملیات را می‌دهد تا مراحل track کردن coercion را رد کند.

مثلاً:

```js
var a = 42;

// ..

var b = a;
```

در این برنامه، انتساب `b = a` مسیر واگرایی نوع را باز می‌گذارد. اما می‌توان به این شکل نوشت:

```js
var a = 42;

// ..

var b = a | 0;
```

اینجا با `|` (OR بیتی) و مقدار `0` کاری کرده‌ایم که مقدار تغییری نکند جز اینکه ۳۲بیتیِ صحیح شود. این کد در JS معمولی هم درست کار می‌کند، ولی در engine آگاه به asm.js *می‌تواند* سیگنال بدهد `b` همیشه ۳۲بیتی صحیح در نظر گرفته شود، پس track coercion لازم نیست.

به‌همین شکل، جمع بین دو متغیر را می‌توان به جمع صحیح performant‌تر محدود کرد (به‌جای اعشاری):

```js
(a + b) | 0
```

باز هم engine آگاه به asm.js این hint را می‌بیند و نتیجه می‌گیرد `+` باید جمع صحیح ۳۲بیتی باشد، چون خروجی کل expression در هر صورت به ۳۲بیتی constrain می‌شود.

### ماژول‌های asm.js

یکی از مهم‌ترین ضربه‌زننده‌ها به کارایی در JS، allocation حافظه، garbage collection و دسترسی scope است. asm.js پیشنهاد می‌دهد برای دورزدن این مسائل، یک «ماژول» asm.js رسمی‌تر تعریف شود -- با ES6 module اشتباه نگیرید (کتاب *ES6 & Beyond*).

برای یک ماژول asm.js باید namespaceای با شکل دقیق را صریح پاس بدهید -- در spec به آن `stdlib` می‌گویند چون نماینده‌ی کتابخانه‌های استاندارد موردنیاز است -- تا symbolها import شوند، به‌جای اینکه مستقیم globalهای lexical scope استفاده شوند. در حالت پایه، شیء `window` می‌تواند `stdlib` باشد، ولی می‌توانید (و شاید بهتر است) نسخه‌ی محدودتر خودتان را بسازید.

همچنین باید یک "heap" تعریف و پاس بدهید -- اصطلاح fancy برای فضای رزروشده‌ی حافظه که متغیرها بدون درخواست حافظه‌ی جدید یا آزادسازی پی‌درپی در آن استفاده شوند -- تا ماژول asm.js کاری نکند که memory churn ایجاد کند؛ فقط از فضای از قبل رزروشده استفاده کند.

یک "heap" معمولاً `ArrayBuffer` نوع‌دار است، مثلاً:

```js
var heap = new ArrayBuffer( 0x10000 );	// 64k heap
```

با این ۶۴KB رزروشده، ماژول asm.js می‌تواند مقدارها را بدون جریمه‌ی allocation/GC ذخیره و بازیابی کند. مثلاً این buffer می‌تواند پشتوانه‌ی آرایه‌ای از `float` ۶۴بیتی باشد:

```js
var arr = new Float64Array( heap );
```

حالا یک مثال سریع و ساده از ماژول سبک asm.js بسازیم تا قطعات کنار هم دیده شوند. تابع `foo(..)` بازه‌ی صحیح شروع (`x`) تا پایان (`y`) می‌گیرد، حاصل‌ضرب‌های جفت‌های مجاور در بازه را حساب می‌کند و در پایان میانگین‌شان را برمی‌گرداند:

```js
function fooASM(stdlib,foreign,heap) {
	"use asm";

	var arr = new stdlib.Int32Array( heap );

	function foo(x,y) {
		x = x | 0;
		y = y | 0;

		var i = 0;
		var p = 0;
		var sum = 0;
		var count = ((y|0) - (x|0)) | 0;

		// calculate all the inner adjacent multiplications
		for (i = x | 0;
			(i | 0) < (y | 0);
			p = (p + 8) | 0, i = (i + 1) | 0
		) {
			// store result
			arr[ p >> 3 ] = (i * (i + 1)) | 0;
		}

		// calculate average of all intermediate values
		for (i = 0, p = 0;
			(i | 0) < (count | 0);
			p = (p + 8) | 0, i = (i + 1) | 0
		) {
			sum = (sum + arr[ p >> 3 ]) | 0;
		}

		return +(sum / count);
	}

	return {
		foo: foo
	};
}

var heap = new ArrayBuffer( 0x1000 );
var foo = fooASM( window, null, heap ).foo;

foo( 10, 20 );		// 233
```

**نکته:** این مثال asm.js دستی برای نمایش نوشته شده، پس دقیقاً همان کدی نیست که ابزار compile به asm.js تولید می‌کند. اما ماهیت رایج کد asm.js را خوب نشان می‌دهد، مخصوصاً hintهای نوع و استفاده از buffer مربوط به `heap` برای ذخیره‌ی متغیر موقت.

اولین فراخوانی `fooASM(..)` ماژول asm.js را با heap allocation آماده می‌کند. خروجی، تابع `foo(..)` است که هرچند بار لازم باشد صدا می‌زنیم. این فراخوانی‌ها در JS engine آگاه به asm.js باید بهینه‌سازی ویژه بگیرند. مهم اینکه کل کد بالا JS استاندارد است و در engine بدون asm.js هم درست کار می‌کند (فقط بدون آن سطح بهینه‌سازی).

واضح است محدودیت‌هایی که کد asm.js را قابل‌بهینه‌سازی می‌کند، دامنه‌ی استفاده‌ی آن را هم محدود می‌کند. asm.js الزاماً ابزار بهینه‌سازی عمومی برای هر برنامه‌ی JS نیست. هدفش بیشتر ارائه‌ی مسیر بهینه برای taskهای تخصصی مثل ریاضیات سنگین (مثلاً پردازش گرافیکی بازی) است.
