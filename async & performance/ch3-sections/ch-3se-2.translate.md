# Duck Typing برای Thenable

در دنیای Promise یک جزئیات مهم این است که چطور مطمئن شویم یک مقدار واقعاً Promise هست یا نه. دقیق‌تر: آیا مقداری است که مثل Promise رفتار می‌کند؟

چون Promise با `new Promise(..)` ساخته می‌شود، شاید فکر کنید `p instanceof Promise` کافی است. اما متاسفانه چند دلیل هست که این چک کامل نیست.

مهم‌ترینش: ممکن است Promise را از پنجره/iframe دیگری بگیرید که implementation جداگانه‌ی Promise خودش را دارد. در این حالت check بالا ممکن است Promise را تشخیص ندهد.

علاوه بر این، یک کتابخانه/فریم‌ورک ممکن است Promise خودش را بدهد و از Promise بومی ES6 استفاده نکند. حتی ممکن است در مرورگرهای قدیمی بدون Promise بومی، از Promiseهای کتابخانه‌ای استفاده کنید.

وقتی جلوتر درباره‌ی resolution Promise حرف بزنیم، روشن‌تر می‌شود چرا تشخیص یک مقدار Promise-like (حتی اگر Promise واقعی نباشد) حیاتی است. فعلاً همین‌قدر بپذیرید که قطعه‌ی مهمی از پازل است.

به همین دلیل تصمیم گرفته شد هر آبجکت/تابعی که متد `then(..)` دارد «thenable» تلقی شود. فرض بر این است که چنین مقداری با Promise سازگار است.

به این نوع «type check» که از روی شکل مقدار (وجود پراپرتی‌ها) درباره‌ی نوعش نتیجه می‌گیرد، می‌گویند "duck typing": «اگر مثل اردک به نظر می‌آید و مثل اردک صدا می‌دهد، پس اردک است» (کتاب *Types & Grammar*). پس چک duck typing برای thenable تقریباً این است:

```js
if (
	p !== null &&
	(
		typeof p === "object" ||
		typeof p === "function"
	) &&
	typeof p.then === "function"
) {
	// assume it's a thenable!
}
else {
	// not a thenable
}
```

افتضاح! جدا از زشتی پیاده‌سازی، مشکل عمیق‌تری هم هست.

اگر Promise را با هر آبجکت/تابعی fulfill کنید که اتفاقی `then(..)` داشته باشد ولی قصد نداشتید Promise/thenable رفتار کند، بدشانسی آورده‌اید؛ خودکار thenable تشخیص داده می‌شود و با قوانین خاص Promise رفتار می‌گیرد.

این حتی وقتی خودتان ندانید آن مقدار `then(..)` دارد هم صادق است. مثال:

```js
var o = { then: function(){} };

// make `v` be `[[Prototype]]`-linked to `o`
var v = Object.create( o );

v.someStuff = "cool";
v.otherStuff = "not so cool";

v.hasOwnProperty( "then" );		// false
```

`v` اصلاً شبیه Promise یا thenable نیست؛ یک آبجکت معمولی با چند پراپرتی است و احتمالاً می‌خواهید مثل آبجکت عادی پاسش بدهید.

اما بی‌خبر از شما، `v` به `o` لینک `[[Prototype]]` دارد (کتاب *this & Object Prototypes*) و `o` متد `then(..)` دارد. پس چک thenable فرض می‌کند `v` thenable است. اوه اوه.

لازم نیست این‌قدر هم عمدی باشد:

```js
Object.prototype.then = function(){};
Array.prototype.then = function(){};

var v1 = { hello: "world" };
var v2 = [ "Hello", "World" ];
```

هم `v1` و هم `v2` thenable فرض می‌شوند. شما نمی‌توانید کنترل کنید کد دیگری عمداً یا تصادفی `then(..)` به `Object.prototype` یا `Array.prototype` و ... اضافه نکند. و اگر این `then` هیچ‌کدام از callback پارامترها را صدا نزند، Promiseای که با چنین مقداری resolve شود ممکن است برای همیشه بی‌صدا hang کند!

بعید به نظر می‌رسد؟ شاید.

اما یادتان باشد قبل از ES6 چند کتابخانه‌ی معروفِ غیر-Promise در جامعه وجود داشتند که از قبل متدی به نام `then(..)` داشتند. بعضی‌شان مجبور شدند rename کنند تا collision نشود (خیلی بد!). بعضی دیگر هم عملاً به وضعیت «ناسازگار با Promise-based coding» تبعید شدند چون امکان تغییر نداشتند.

تصمیم استاندارد برای رزرو نام پراپرتی عمومی و قبلاً آزادِ `then` یعنی هیچ مقداری (یا delegateهایش)، گذشته/حال/آینده، نباید `then(..)` داشته باشد -- چه عمدی چه تصادفی -- وگرنه در سیستم Promise با thenable اشتباه می‌شود و احتمالاً bugهای سخت‌ردیابی می‌سازد.

**هشدار:** من شخصاً از اینکه تشخیص Promise با duck typingِ thenable انجام شد راضی نیستم. گزینه‌های دیگری مثل branding یا anti-branding هم وجود داشت؛ چیزی که گرفتیم شبیه بدترین سازش بود. البته کاملاً هم تاریک نیست: duck typing thenable می‌تواند مفید هم باشد (جلوتر می‌بینیم). فقط حواستان باشد تشخیص اشتباه thenable می‌تواند خطرناک باشد.
