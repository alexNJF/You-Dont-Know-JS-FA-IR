# Tail Call Optimization (TCO)

همان‌طور که کمی قبل گفتیم، ES6 یک الزام مشخص دارد که وارد قلمرو performance می‌شود. این الزام به نوع خاصی از بهینه‌سازی فراخوانی تابع مربوط است: *Tail Call Optimization*.

خلاصه اینکه «tail call» فراخوانی تابعی است که در «دم» تابع دیگر رخ می‌دهد؛ یعنی بعد از تمام شدن آن فراخوانی، دیگر کاری باقی نمی‌ماند (جز احتمالاً return کردن نتیجه‌اش).

مثال غیر بازگشتی با tail call:

```js
function foo(x) {
	return x;
}

function bar(y) {
	return foo( y + 1 );	// tail call
}

function baz() {
	return 1 + bar( 40 );	// not tail call
}

baz();						// 42
```

`foo(y+1)` در `bar(..)` یک tail call است چون بعد از پایان `foo(..)`، `bar(..)` هم جز return نتیجه‌ی همان call کار دیگری ندارد. اما `bar(40)` در `baz()` tail call نیست چون بعد از completion آن، هنوز باید نتیجه با `1` جمع شود تا `baz()` return کند.

بدون ورود به جزئیات خیلی ریز، فراخوانی تابع جدید حافظه‌ی رزرو اضافی برای call stack می‌خواهد که به آن "stack frame" می‌گویند. بنابراین snippet بالا معمولاً هم‌زمان به stack frame برای `baz()`, `bar(..)` و `foo(..)` نیاز دارد.

اما اگر engine دارای TCO تشخیص دهد call مربوط به `foo(y+1)` در *tail position* است (یعنی `bar(..)` عملاً تمام شده)، هنگام call به `foo(..)` لازم نیست stack frame جدید بسازد؛ می‌تواند frame فعلی `bar(..)` را reuse کند. این هم سریع‌تر است و هم حافظه‌ی کمتری مصرف می‌کند.

این optimize در snippet ساده خیلی بزرگ نیست، اما در recursion *خیلی مهم* می‌شود، مخصوصاً وقتی recursion ممکن است صدها یا هزاران stack frame می‌خواست. با TCO، engine می‌تواند تمام این callها را با یک stack frame انجام دهد!

recursion در JS موضوع حساسی است چون بدون TCO، engineها مجبور بوده‌اند حد دلخواه (و متفاوت) برای عمق stack recursion بگذارند تا حافظه تمام نشود. با TCO، تابع بازگشتی‌ای که callهای *tail position* دارد عملاً می‌تواند بدون مرز اجرا شود، چون مصرف حافظه‌ی اضافی ندارد!

مثال factorial قبلی را این‌بار به شکل TCO-friendly بازنویسی کنیم:

```js
function factorial(n) {
	function fact(n,res) {
		if (n < 2) return res;

		return fact( n - 1, n * res );
	}

	return fact( n, 1 );
}

factorial( 5 );		// 120
```

این نسخه هنوز بازگشتی است، اما با TCO هم قابل optimize است، چون هر دو فراخوانی داخلی `fact(..)` در *tail position* قرار دارند.

**نکته:** مهم است دقت کنیم TCO فقط وقتی اعمال می‌شود که واقعاً tail call داشته باشید. اگر تابع بازگشتی بدون tail call بنویسید، performance به allocation عادی stack frame برمی‌گردد و محدودیت عمق stack engine همچنان برقرار است. خیلی از توابع بازگشتی را می‌شود مثل همین `factorial(..)` بازنویسی کرد، اما به دقت بالا نیاز دارد.

یکی از دلایلی که ES6 پیاده‌سازی TCO را الزام کرد (نه اختیاری) این است که *نبود TCO* عملاً احتمال پیاده‌سازی بعضی الگوریتم‌ها با recursion در JS را کم می‌کند، چون توسعه‌دهنده از محدودیت stack می‌ترسد.

اگر نبود TCO فقط باعث افت performance می‌شد و در همه‌جا graceful degrade داشت، احتمالاً لازم نبود ES6 آن را *الزام* کند. اما چون نبود TCO می‌تواند بعضی برنامه‌ها را عملاً غیرعملی کند، این بیشتر یک ویژگی مهم زبانی است تا جزئیات پنهان پیاده‌سازی.

ES6 از این به بعد تضمین می‌دهد توسعه‌دهنده‌ی JS بتواند روی این optimize در همه‌ی مرورگرهای سازگار ES6+ حساب کند. این یک برد برای performance جاوااسکریپت است!
