# Microperformance

خب، تا اینجا دور مسائل مختلف microperformance چرخیدیم و عموماً نگاه انتقادی به وسواس روی آن‌ها داشتیم. می‌خواهم یک لحظه مستقیم خود موضوع را هدف بگیرم.

اولین چیزی که باید در benchmark کردن performance کد با آن راحت‌تر شوید این است که کدی که شما می‌نویسید همیشه همان کدی نیست که engine واقعاً اجرا می‌کند. در فصل ۱ وقتی درباره‌ی reorder شدن statementها توسط compiler حرف زدیم اشاره کردیم، ولی اینجا می‌خواهیم بگوییم compiler گاهی ممکن است کدی *مختلف از نظر ماهیت* اجرا کند، نه فقط با ترتیب متفاوت.

این قطعه کد را ببینید:

```js
var foo = 41;

(function(){
	(function(){
		(function(baz){
			var bar = foo + baz;
			// ..
		})(1);
	})();
})();
```

ممکن است reference مربوط به `foo` در تابع درونی را lookup سه‌سطحی scope در نظر بگیرید. در کتاب *Scope & Closures* گفتیم lexical scope چطور کار می‌کند و اینکه compiler معمولاً چنین lookupهایی را cache می‌کند تا ارجاع به `foo` از scopeهای مختلف عملاً هزینه‌ی اضافی محسوسی نداشته باشد.

اما نکته‌ی عمیق‌تری هست. اگر compiler بفهمد `foo` جز همان یک نقطه هیچ‌جا استفاده نشده و مقدارش هم هیچ‌وقت چیزی غیر از `41` نیست چه؟

کاملاً ممکن و قابل‌قبول نیست که JS compiler تصمیم بگیرد متغیر `foo` را حذف کند و مقدار را inline کند، مثل:

```js
(function(){
	(function(){
		(function(baz){
			var bar = 41 + baz;
			// ..
		})(1);
	})();
})();
```

**نکته:** طبیعتاً compiler احتمالاً می‌تواند برای `baz` هم تحلیل مشابه انجام دهد.

وقتی شروع می‌کنید کد JS خود را به‌عنوان یک hint/suggestion به engine ببینید، نه یک الزام لفظ‌به‌لفظ، می‌فهمید بخش بزرگی از وسواس روی ریزه‌کاری‌های syntax احتمالاً بی‌پایه است.

مثال دیگر:

```js
function factorial(n) {
	if (n < 2) return 1;
	return n * factorial( n - 1 );
}

factorial( 5 );		// 120
```

الگوریتم کلاسیک factorial! شاید فرض کنید JS engine تقریباً همین را همان‌طور اجرا می‌کند. راستش ممکن است -- من دقیق نمی‌دانم.

اما به‌عنوان anecdote، همین کد اگر در C نوشته شود و با optimize پیشرفته compile شود، compiler ممکن است بفهمد `factorial(5)` را می‌شود مستقیم با ثابت `120` جایگزین کرد و کل تابع/فراخوانی را حذف کرد!

علاوه بر این، بعضی engineها کاری به نام "unrolling recursion" دارند: ممکن است تشخیص دهند recursion شما را می‌شود با loop ساده‌تر/بهینه‌تر اجرا کرد. ممکن است کد بالا در JS engine به این شکل *بازنویسی* شود:

```js
function factorial(n) {
	if (n < 2) return 1;

	var res = 1;
	for (var i=n; i>1; i--) {
		res *= i;
	}
	return res;
}

factorial( 5 );		// 120
```

حالا تصور کنید در snippet قبلی نگران بودید `n * factorial(n-1)` سریع‌تر است یا `n *= factorial(--n)` و حتی benchmark هم زده‌اید. ولی نکته‌ی اصلی را از دست می‌دهید: در context بزرگ‌تر، engine ممکن است هیچ‌کدام را اجرا نکند چون recursion را unroll می‌کند!

حرف از `--` شد: `--n` در برابر `n--` هم زیاد به‌عنوان نقطه‌ی optimize مطرح می‌شود، با این توجیه که در سطح assembly شاید `--n` کم‌هزینه‌تر باشد.

این نوع وسواس در JavaScript مدرن عملاً بی‌معناست. این چیزی است که باید بگذارید engine مدیریت کند. شما باید کدی بنویسید که معنادارتر است. این سه حلقه‌ی `for` را ببینید:

```js
// Option 1
for (var i=0; i<10; i++) {
	console.log( i );
}

// Option 2
for (var i=0; i<10; ++i) {
	console.log( i );
}

// Option 3
for (var i=-1; ++i<10; ) {
	console.log( i );
}
```

حتی اگر تئوری‌ای داشته باشید که گزینه‌ی دوم یا سوم ذره‌ای سریع‌تر از اول است -- که خودش هم محل تردید است -- گزینه‌ی سوم گیج‌کننده‌تر است چون باید `i` را از `-1` شروع کنید تا pre-increment `++i` جبران شود. و تفاوت بین گزینه‌ی اول و دوم عملاً بی‌اهمیت است.

کاملاً ممکن است JS engine جایی که `i++` دیده، تشخیص دهد با خیال راحت `++i` جایگزین کند. یعنی زمانی که برای انتخاب بینشان گذاشته‌اید کاملاً هدر رفته.

یک مثال رایج دیگر از وسواس microperformance:

```js
var x = [ .. ];

// Option 1
for (var i=0; i < x.length; i++) {
	// ..
}

// Option 2
for (var i=0, len = x.length; i < len; i++) {
	// ..
}
```

تئوری این است که طول آرایه (`x.length`) را در `len` cache کنید چون ظاهراً تغییر نمی‌کند، تا هزینه‌ی خواندن `x.length` در هر iteration را حذف کنید.

اگر benchmark مربوط به `x.length` مستقیم را با حالت cache در `len` مقایسه کنید، می‌بینید با اینکه تئوری قشنگ است، در عمل تفاوت‌های اندازه‌گیری‌شده غالباً از نظر آماری بی‌ربط‌اند.

حتی در بعضی engineها مثل v8 نشان داده شده که پیش‌cache کردن length ممکن است کمی اوضاع را بدتر کند نسبت به اینکه engine خودش تشخیص دهد. سعی نکنید JavaScript engine را گول بزنید؛ در performance غالباً شما بازنده می‌شوید.

### همه‌ی Engineها شبیه هم نیستند

engineهای مختلف JS در مرورگرهای مختلف می‌توانند همگی spec-compliant باشند ولی روش‌های کاملاً متفاوتی برای اجرای کد داشته باشند. specification مربوط به JS الزام performance خاصی نمی‌گذارد -- به‌جز "Tail Call Optimization" در ES6 که جلوتر می‌بینیم.

engineها آزادند تصمیم بگیرند کدام عملیات را بیشتر optimize کنند و شاید عملیات دیگر را کمی قربانی کنند. پیدا کردن روشی که در *همه* مرورگرها همیشه سریع‌تر باشد خیلی شکننده است.

در جامعه‌ی JS (خصوصاً Node.js) جریانی وجود دارد که جزئیات پیاده‌سازی داخلی engine v8 را تحلیل می‌کند و کد JS را متناسب با v8 می‌نویسد. با این روش‌ها واقعاً می‌شود به optimizeهای قابل‌توجه رسید و بازده تلاش بالا باشد.

چند مثال معروف برای v8:

* متغیر `arguments` را از یک تابع به تابع دیگر پاس ندهید؛ این «نشت» پیاده‌سازی تابع را کند می‌کند.
* `try..catch` را در تابع جدا ایزوله کنید. مرورگرها در optimize کردن تابعی که داخلش `try..catch` است مشکل دارند، پس جداکردنش، آسیب de-optimize را محدود می‌کند و اطرافش قابل optimize می‌ماند.

اما به‌جای تمرکز روی همین نکته‌ها، بیایید رویکرد «optimize مخصوص v8» را کلی‌تر sanity check کنیم.

آیا واقعاً کدی می‌نویسید که فقط باید روی یک JS engine اجرا شود؟ حتی اگر الآن کل کد مخصوص Node.js باشد، آیا تضمین دارید v8 *همیشه* engine آن باقی می‌ماند؟ ممکن نیست چند سال بعد پلتفرم server-side دیگری را انتخاب کنید؟ اگر آن‌وقت optimize قبلی شما روی engine جدید کندتر باشد چه؟

یا اگر کدتان همیشه روی v8 بماند، اما v8 در آینده روش اجرای بعضی عملیات را عوض کند و آنچه قبلاً سریع بود حالا کند شود (یا برعکس) چه؟

این سناریوها فقط فرضی نیستند. زمانی stringها را این‌طور concatenate می‌کردند که در آرایه بریزند و `join("")` بزنند، چون از `+` مستقیم سریع‌تر بود. دلیل تاریخی‌اش ظریف است و به نحوه‌ی مدیریت string در حافظه برمی‌گردد.

در نتیجه، آن زمان توصیه‌ی «best practice» در صنعت پخش شد که همیشه از `join(..)` استفاده کنید؛ و خیلی‌ها همین کار را کردند.

اما در ادامه، JS engineها روش داخلی مدیریت string را تغییر دادند و optimize جدی برای الحاق با `+` گذاشتند. لزوماً `join(..)` را کندتر نکردند، ولی روی `+` سرمایه‌گذاری بیشتری کردند چون رایج‌تر بود.

**نکته:** استانداردسازی/بهینه‌سازی یک رویکرد بر مبنای استفاده‌ی گسترده‌ی موجود را استعاره‌ای "paving the cowpath" می‌نامند.

وقتی این رویکرد جدید جا افتاد، متاسفانه کل کدهای بیرون که برای concatenation از `join(..)` استفاده می‌کردند، sub-optimal شدند.

مثال دیگر: زمانی Opera با مرورگرهای دیگر در نحوه‌ی boxing/unboxing آبجکت wrapperِ primitiveها تفاوت داشت (کتاب *Types & Grammar*). بنابراین توصیه‌ی Opera این بود که اگر به `length` یا `charAt(..)` نیاز دارید از آبجکت `String` به‌جای primitive `string` استفاده کنید. شاید آن زمان برای Opera درست بود، اما برای مرورگرهای اصلی دیگر دقیقاً برعکس بود چون روی primitive `string` optimize داشتند نه wrapper object آن.

من فکر می‌کنم این‌جور gotchaها امروز هم حداقل ممکن‌اند، اگر نگوییم محتمل. برای همین نسبت به optimize وسیع در JS صرفاً بر اساس جزئیات یک engine **به‌شدت محتاطم، مخصوصاً وقتی فقط برای یک engine صدق کند**.

حالت برعکس هم خطرناک است: لزوماً نباید کد را طوری تغییر دهید که فقط ضعف یک engine در اجرای performant یک قطعه را دور بزند.

از نظر تاریخی IE مملو از چنین دردسرهایی بود؛ در نسخه‌های قدیمی IE سناریوهای زیادی بود که در performance مشکل داشت و مرورگرهای هم‌دوره کمتر داشتند. بحث concatenation string بالا در عصر IE6/IE7 مثال واقعی بود که گاهی `join(..)` بهتر از `+` می‌داد.

اما سخت است بگوییم چون یک مرورگر مشکل performance دارد، باید رویکردی را انتخاب کنیم که احتمالاً در بقیه مرورگرها sub-optimal است. حتی اگر آن مرورگر سهم بزرگی از کاربران شما داشته باشد، ممکن است عملی‌تر باشد کد صحیح را بنویسید و بگذارید مرورگر با updateهای بعدی خودش optimize شود.

«هیچ چیز ماندگارتر از یک هک موقتی نیست.» احتمالاً کدی که امروز برای دور زدن یک bug کارایی می‌نویسید، از خود آن bug در مرورگر بیشتر عمر می‌کند.

وقتی مرورگرها هر پنج سال یک‌بار آپدیت می‌شدند، تصمیم سخت‌تری بود. اما حالا مرورگرها با فاصله‌ی بسیار کوتاه‌تر آپدیت می‌شوند (هرچند دنیای موبایل هنوز عقب‌تر است)، و همه در حال رقابت برای optimize بهتر قابلیت‌های وب هستند.

اگر به موردی رسیدید که یک مرورگر خاص مشکل کارایی دارد و بقیه ندارند، حتماً از مسیر موجود گزارش bug بدهید. بیشتر مرورگرها bug tracker عمومی باز دارند.

**نکته:** من فقط وقتی workaround کارایی در مرورگر را توصیه می‌کنم که واقعاً show-stopper شدید باشد، نه صرفاً آزاردهنده. و خیلی دقیق باید چک کنید hack کارایی در مرورگر دیگر اثر منفی محسوس ایجاد نکند.

### تصویر بزرگ

به‌جای نگرانی درباره‌ی این ریزه‌کاری‌های microperformance، باید سراغ optimizeهای big-picture برویم.

چطور بفهمید چیزی big-picture هست یا نه؟ اول باید بفهمید کدتان روی critical path هست یا نه. اگر نیست، احتمالاً optimize شما ارزش زیادی ندارد.

حتماً جمله‌ی «این premature optimizationه!» را شنیده‌اید. از نقل‌قول معروف Donald Knuth می‌آید: "premature optimization is the root of all evil." خیلی‌ها این را طوری نقل می‌کنند که انگار بیشتر optimizeها زودهنگام و هدررفت‌اند. واقعیت مثل همیشه nuancedتر است.

نقل‌قول کامل در context:

> Programmers waste enormous amounts of time thinking about, or worrying about, the speed of **noncritical** parts of their programs, and these attempts at efficiency actually have a strong negative impact when debugging and maintenance are considered. We should forget about small efficiencies, say about 97% of the time: premature optimization is the root of all evil. Yet we should not pass up our opportunities in that **critical** 3%. [emphasis added]

برداشت منصفانه‌اش به نظر من این است که منظور Knuth این بوده: «optimize کردن مسیر غیر بحرانی، ریشه‌ی همه بدی‌هاست.» پس کلید کار این است که بفهمید کدتان روی critical path هست -- باید optimize شود -- یا نه.

حتی یک قدم جلوتر می‌گویم: هیچ مقدار زمانی که برای optimize مسیرهای بحرانی بگذارید هدر نیست، حتی اگر صرفه‌جویی کم باشد؛ اما هیچ مقدار optimize روی مسیرهای غیر بحرانی توجیه‌پذیر نیست، حتی اگر صرفه‌جویی زیاد باشد.

اگر کدتان روی critical path است، مثلاً "hot" بوده و بارها اجرا می‌شود، یا در UX حساس است مثل animation loop یا به‌روزرسانی سبک CSS که کاربر متوجه می‌شود، باید نهایت تلاش را برای optimize مرتبط و اندازه‌پذیر بگذارید.

مثلاً یک animation loop بحرانی را در نظر بگیرید که باید مقدار string را به number coercion کند. راه‌های مختلفی دارد (کتاب *Types & Grammar*)، اما کدام سریع‌تر است؟

```js
var x = "42";	// need number `42`

// Option 1: let implicit coercion automatically happen
var y = x / 2;

// Option 2: use `parseInt(..)`
var y = parseInt( x, 0 ) / 2;

// Option 3: use `Number(..)`
var y = Number( x ) / 2;

// Option 4: use `+` unary operator
var y = +x / 2;

// Option 5: use `|` unary operator
var y = (x | 0) / 2;
```

**نکته:** اگر دوست دارید تفاوت‌های بسیار ریز performance بین این گزینه‌ها را بررسی کنید، طراحی تست را به‌عنوان تمرین می‌گذارم.

وقتی این گزینه‌ها را می‌بینید، به قول معروف «یکی از این‌ها مثل بقیه نیست». `parseInt(..)` کار را انجام می‌دهد، اما کار بیشتری هم انجام می‌دهد -- parse می‌کند نه صرف coercion. احتمالاً درست حدس می‌زنید که `parseInt(..)` کندتر است و بهتر است از آن پرهیز کنید.

البته اگر `x` ممکن است مقداری باشد که **واقعاً نیاز به parse** دارد، مثل `"42px"` (مثلاً از CSS)، آن‌وقت `parseInt(..)` تنها گزینه‌ی درست است!

`Number(..)` هم یک function call است. از نظر رفتاری با گزینه‌ی `+` unary یکسان است، اما ممکن است کمی کندتر باشد چون machinery اجرای تابع را می‌خواهد. البته ممکن هم هست JS engine این تقارن رفتاری را تشخیص دهد و رفتار `Number(..)` (عملاً `+x`) را برایتان inline کند.

اما یادتان بماند، وسواس روی `+x` در برابر `x | 0` در بیشتر موارد هدررفت است. این یک موضوع microperformance است و نباید بگذارید readability برنامه را دیکته یا تخریب کند.

هرچند performance در مسیرهای بحرانی برنامه خیلی مهم است، تنها فاکتور نیست. بین چند گزینه که performance نزدیک دارند، readability هم باید یک نگرانی مهم باشد.
