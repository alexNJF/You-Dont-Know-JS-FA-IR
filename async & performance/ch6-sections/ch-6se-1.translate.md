# Benchmarking

خب، وقتش رسیده چند سوءبرداشت را کنار بزنیم. شرط می‌بندم اکثریت توسعه‌دهنده‌های JS اگر ازشان بخواهید سرعت (زمان اجرا) یک عملیات را benchmark کنند، اول چیزی شبیه این انجام می‌دهند:

```js
var start = (new Date()).getTime();	// or `Date.now()`

// do some operation

var end = (new Date()).getTime();

console.log( "Duration:", (end - start) );
```

اگر این تقریباً همان چیزی بود که به ذهن‌تان آمد دست‌تان بالا! بله، قابل حدس بود. این رویکرد ایرادهای زیادی دارد، ولی ناراحت نشوید؛ **همه‌ی ما از همین‌جا شروع کرده‌ایم.**

این اندازه‌گیری دقیقاً چه چیزی به شما گفت؟ فهمیدن اینکه چه می‌گوید و چه نمی‌گوید، کلید یادگیری benchmark درست performance در JavaScript است.

اگر مدت گزارش‌شده `0` باشد، شاید فکر کنید کمتر از یک میلی‌ثانیه طول کشیده. اما خیلی دقیق نیست. بعضی پلتفرم‌ها دقت تک‌میلی‌ثانیه‌ای ندارند و timer را در بازه‌های بزرگ‌تر آپدیت می‌کنند. مثلاً نسخه‌های قدیمی ویندوز (و در نتیجه IE) فقط دقت 15ms داشتند؛ یعنی عملیات باید حداقل آن‌قدر طول بکشد تا چیزی غیر از `0` ببینید!

علاوه بر این، هر عددی هم که گزارش شود، تنها چیزی که واقعاً می‌دانید این است که عملیات در همان یک اجرای خاص تقریباً این‌قدر طول کشیده. تقریباً هیچ اطمینانی ندارید که همیشه همین سرعت را خواهد داشت. نمی‌دانید آن لحظه engine یا سیستم چه مداخله‌ای داشته و شاید دفعات دیگر سریع‌تر اجرا شود.

اگر عدد گزارش‌شده `4` باشد، آیا مطمئن‌ترید که حدود چهار میلی‌ثانیه طول کشیده؟ نه. ممکن است کمتر بوده باشد و تاخیر از جای دیگری آمده باشد، مثلاً در گرفتن timestamp شروع یا پایان.

نگران‌کننده‌تر اینکه اصلاً نمی‌دانید شرایط این تست بیش‌ازحد خوش‌بینانه نبوده باشد. ممکن است JS engine راهی برای optimize کردن همین تست ایزوله پیدا کرده باشد، ولی در برنامه‌ی واقعی چنین optimizeای ضعیف یا غیرممکن باشد و عملیات کندتر اجرا شود.

پس چه می‌دانیم؟ متاسفانه با این واقعیت‌ها **خیلی کم می‌دانیم.** چیزی با این سطح اطمینان آن‌قدر قابل اتکا نیست که مبنای تصمیم شود. این «benchmark» عملاً بی‌استفاده است. بدتر از آن، خطرناک است چون حس اطمینان کاذب می‌دهد؛ هم به شما، هم به دیگرانی که شرایط پشت نتیجه را نقادانه بررسی نمی‌کنند.

### تکرار

حالا می‌گویید: «باشه، دورش loop می‌گذاریم تا کل تست طولانی‌تر شود.» اگر عملیات را 100 بار تکرار کنید و مجموعاً 137ms طول بکشد، می‌شود تقسیم بر 100 و میانگین 1.37ms برای هر عملیات، درست؟

نه دقیقاً.

میانگین ریاضی خام به‌تنهایی برای قضاوت performance که قرار است به کل برنامه تعمیم دهید کافی نیست. با 100 iteration، فقط چند outlier (خیلی بالا یا پایین) می‌تواند میانگین را منحرف کند، و بعد وقتی نتیجه را بارها اعمال می‌کنید، همین انحراف بزرگ‌تر هم می‌شود.

به‌جای تعداد iteration ثابت، می‌توانید تست را تا گذشت مقدار معینی زمان اجرا کنید. این شاید مطمئن‌تر باشد، اما طول اجرا را چطور تعیین می‌کنید؟ شاید حدس بزنید باید ضریبی از زمان اجرای تک‌عملیات باشد. اشتباه.

در واقع مدت تکرار باید بر اساس دقت timer انتخاب شود، تا احتمال خطا کمینه شود. هرچه timer کم‌دقت‌تر باشد، باید بیشتر اجرا کنید تا درصد خطا پایین بیاید. timer با دقت 15ms برای benchmark دقیق بد است؛ برای رساندن عدم‌قطعیت آن به کمتر از 1% باید هر چرخه‌ی تست را 750ms اجرا کنید. timer با دقت 1ms برای همان اطمینان فقط به چرخه‌ی 50ms نیاز دارد.

اما این هنوز فقط یک نمونه است. برای حذف انحراف، نمونه‌های زیاد می‌خواهید تا روی آن‌ها میانگین بگیرید. همچنین باید بفهمید بدترین نمونه چقدر کند است، بهترین چقدر سریع، فاصله‌ی بهترین و بدترین چقدر است و... . نه‌فقط یک عدد سرعت، بلکه یک معیار کمی از میزان اعتمادپذیری همان عدد لازم دارید.

همچنین احتمالاً می‌خواهید این روش‌ها (و روش‌های دیگر) را ترکیب کنید تا بهترین تعادل ممکن را بگیرید.

این‌ها تازه حداقل‌های شروع کار است. اگر تا حالا با روشی ساده‌تر از این benchmark می‌کردید، خب... «you don't know: proper benchmarking».

### Benchmark.js

هر benchmark قابل‌اتکا باید بر مبنای روش‌های آماری درست باشد. اینجا نمی‌خواهم فصل آمار بنویسم، پس فقط اشاره می‌کنم: standard deviation، variance، margin of error. اگر دقیق نمی‌دانید این‌ها یعنی چه -- من خودم هم با اینکه کلاس آمار گذرانده‌ام هنوز روی بعضی‌اش مطمئن نیستم -- عملاً صلاحیت نوشتن benchmark logic اختصاصی را ندارید.

خوشبختانه آدم‌های باهوشی مثل John-David Dalton و Mathias Bynens این مفاهیم را می‌دانند و ابزار آماری معتبری به نام Benchmark.js ساخته‌اند. پس تعلیق را تمام کنم: «فقط از همان ابزار استفاده کنید.»

من مستندات کامل Benchmark.js را تکرار نمی‌کنم؛ خودشان API Docs عالی دارند که باید بخوانید. همچنین چند نوشته‌ی خوب درباره‌ی جزئیات و روش‌شناسی وجود دارد.

اما برای نمایش سریع، این‌طور می‌شود با Benchmark.js یک تست performance ساده اجرا کرد:

```js
function foo() {
	// operation(s) to test
}

var bench = new Benchmark(
	"foo test",				// test name
	foo,					// function to test (just contents)
	{
		// ..				// optional extra options (see docs)
	}
);

bench.hz;					// number of operations per second
bench.stats.moe;			// margin of error
bench.stats.variance;		// variance across samples
// ..
```

غیر از این نگاه سریع، درباره‌ی Benchmark.js خیلی چیزهای بیشتری برای یادگیری هست. نکته این است که پیچیدگی‌های برقراری یک benchmark منصفانه، قابل‌اعتماد و معتبر برای تکه‌کد JS را خودش مدیریت می‌کند. اگر می‌خواهید واقعاً کدتان را تست و benchmark کنید، این کتابخانه اولین جایی است که باید سراغش بروید.

اینجا تست یک عملیات تکی X را نشان دادیم، اما خیلی وقت‌ها می‌خواهید X را با Y مقایسه کنید. ساده است: دو تست مختلف در یک "Suite" (قابلیت سازمان‌دهی Benchmark.js) تعریف می‌کنید، head-to-head اجرا می‌کنید، و آمار را مقایسه می‌کنید تا ببینید X سریع‌تر است یا Y.

Benchmark.js فقط برای مرورگر نیست؛ در محیط‌های غیرمرورگری (Node.js و...) هم اجرا می‌شود.

یکی از کاربردهای کمتر استفاده‌شده‌ی Benchmark.js این است که در محیط Dev/QA از آن برای تست regression کارایی روی مسیرهای بحرانی کد JS اپلیکیشن استفاده کنید. همان‌طور که قبل از deploy تست واحد می‌زنید، می‌توانید performance را هم با benchmarkهای قبلی مقایسه کنید تا بفهمید بهتر شده یا افت کرده.

#### Setup/Teardown

در snippet قبلی از شیء گزینه‌های اضافه `{ .. }` گذشتیم. اما دو گزینه مهم داریم: `setup` و `teardown`.

این دو امکان می‌دهند تابعی تعریف کنید که قبل و بعد اجرای تست case فراخوانی شود.

نکته‌ی خیلی مهم: کد `setup` و `teardown` **برای هر iteration تست اجرا نمی‌شود**. بهترین مدل ذهنی این است که یک loop بیرونی دارید (تکرار cycleها) و یک loop درونی (تکرار iterationهای تست). `setup`/`teardown` اول و آخر هر iteration مربوط به loop *بیرونی* اجرا می‌شوند، نه داخل loop درونی.

چرا مهم است؟ فرض کنید test case شما این است:

```js
a = a + "w";
b = a.charAt( 1 );
```

و `setup` را این‌طور گذاشته‌اید:

```js
var a = "x";
```

احتمالاً وسوسه می‌شوید فکر کنید `a` در هر iteration از `"x"` شروع می‌شود.

اما این‌طور نیست! `a` در هر cycle از `"x"` شروع می‌شود و سپس `+ "w"`های تکراری باعث می‌شوند `a` بزرگ و بزرگ‌تر شود، هرچند شما فقط کاراکتر جایگاه `1` یعنی `"w"` را می‌خوانید.

جایی که این بیشتر ضربه می‌زند وقتی است که side effect روی DOM انجام می‌دهید، مثل append کردن child. فکر می‌کنید parent هر بار خالی است، اما واقعاً هی element اضافه می‌شود، و این می‌تواند نتایج تست را شدیداً منحرف کند.
