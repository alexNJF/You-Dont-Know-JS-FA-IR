# jsPerf.com

هرچند Benchmark.js برای تست performance کد در هر محیط JS مفید است، باید تاکید کرد اگر می‌خواهید به نتیجه‌ی قابل‌اتکا برسید، باید نتایج را از محیط‌های مختلف زیاد (مرورگر دسکتاپ، موبایل و...) جمع‌آوری کنید.

مثلاً Chrome روی دسکتاپ رده‌بالا احتمالاً اصلاً شبیه Chrome موبایل روی گوشی اجرا نمی‌شود. حتی یک گوشی با باتری کامل هم احتمالاً شبیه همان گوشی روی 2% باتری نیست، وقتی دستگاه شروع می‌کند radio و پردازنده را کم‌مصرف کند.

اگر می‌خواهید گزاره‌هایی مثل «X از Y سریع‌تر است» را در معنای معقولی فراتر از یک محیط بگویید، باید تا حد ممکن همین محیط‌های واقعی را تست کنید. اینکه Chrome در یک عملیات خاص X را سریع‌تر از Y اجرا کند، یعنی همه‌ی مرورگرها همین‌طورند؟ نه. ضمن اینکه معمولاً باید نتایج چند مرورگر را با دموگرافی کاربران واقعی‌تان هم cross-reference کنید.

برای همین یک وب‌سایت عالی وجود دارد: [jsPerf](http://jsperf.com). این سرویس از Benchmark.js (که قبلاً گفتیم) استفاده می‌کند تا تست‌های آماری دقیق و قابل‌اعتماد اجرا کند، و تست را روی URL عمومی قابل‌اشتراک می‌گذارد.

هر بار تست اجرا شود، نتیجه جمع‌آوری و همراه همان تست ذخیره می‌شود، و نتایج تجمعی روی صفحه برای همه نمودار می‌شود.

وقتی تست می‌سازید، ابتدا دو test case دارید، اما می‌توانید هرچندتا لازم دارید اضافه کنید. همچنین می‌توانید کد `setup` (ابتدای هر cycle تست) و `teardown` (انتهای هر cycle) تعریف کنید.

**نکته:** یک ترفند برای داشتن فقط یک test case (وقتی head-to-head نمی‌خواهید): موقع ساخت اولیه، باکس تست دوم را با متن placeholder پر کنید؛ بعد تست را edit کنید و case دوم را خالی بگذارید تا حذف شود. بعداً همیشه می‌توانید test case جدید اضافه کنید.

می‌توانید setup اولیه‌ی صفحه را تعریف کنید (import کتابخانه‌ها، تعریف helperها، declaration متغیرها و...). همچنین اگر لازم بود رفتار setup/teardown جدا هم دارید -- بخش "Setup/Teardown" در بحث Benchmark.js بالا را ببینید.

### Sanity Check

jsPerf منبع فوق‌العاده‌ای است، اما تعداد زیادی تست منتشرشده وقتی دقیق نگاه کنید معیوب یا نامعتبرند، به دلایل مختلفی که تا اینجای فصل گفتیم.

مثال:

```js
// Case 1
var x = [];
for (var i=0; i<10; i++) {
	x[i] = "x";
}

// Case 2
var x = [];
for (var i=0; i<10; i++) {
	x[x.length] = "x";
}

// Case 3
var x = [];
for (var i=0; i<10; i++) {
	x.push( "x" );
}
```

چند نکته برای فکر کردن در این سناریو:

* خیلی رایج است که devها loop خودشان را داخل test case می‌گذارند و فراموش می‌کنند Benchmark.js خودش تمام تکرار لازم را انجام می‌دهد. احتمال زیادی هست `for`های اینجا فقط نویز اضافه باشند.
* declaration و initialization مربوط به `x` داخل هر test case است، شاید بی‌دلیل. یادتان هست اگر `x = []` را در setup بگذارید، قبل از هر iteration اجرا نمی‌شود، بلکه ابتدای هر cycle اجرا می‌شود. یعنی `x` مدام بزرگ و بزرگ‌تر می‌شود، نه فقط اندازه‌ی `10` که `for` القا می‌کند.

پس هدف چیست؟ اینکه تست فقط رفتار engine را برای آرایه‌های خیلی کوچک (اندازه `10`) بسنجد؟ ممکن است قصد همین باشد، اما باید ببینید این یعنی تمرکز بیش‌ازحد روی جزئیات داخلی بسیار ریز نیست؟

از طرف دیگر، شاید قصد تست این است که context رشد بزرگ آرایه را بپذیرد. آیا رفتار engine روی آرایه‌های بزرگ برای کاربرد واقعی مدنظر شما relevant و دقیق هست؟

* آیا هدف این است که هزینه‌ی اضافه‌ی `x.length` یا `x.push(..)` نسبت به append به آرایه سنجیده شود؟ این می‌تواند تست معتبری باشد. اما `push(..)` یک function call است، پس طبیعی است از دسترسی `[..]` کندتر باشد. از این نظر شاید caseهای 1 و 2 نسبت به case 3 منصفانه‌ترند.

یک مثال دیگر از خطای رایج apples-to-oranges:

```js
// Case 1
var x = ["John","Albert","Sue","Frank","Bob"];
x.sort();

// Case 2
var x = ["John","Albert","Sue","Frank","Bob"];
x.sort( function mySort(a,b){
	if (a < b) return -1;
	if (a > b) return 1;
	return 0;
} );
```

اینجا قصد واضح این است که comparator سفارشی `mySort(..)` چقدر از comparator پیش‌فرض کندتر است. اما چون `mySort(..)` را inline function expression نوشته‌اید، تست ناعادلانه/نامعتبر شده. در case دوم نه‌فقط comparator سفارشی تست می‌شود، **بلکه ساخت function expression جدید در هر iteration هم تست می‌شود.**

تعجب می‌کنید اگر بفهمید در تست مشابهی که صرفاً ساخت inline function expression را در برابر function از پیش‌تعریف‌شده جدا کند، ساخت inline می‌تواند حدود 2% تا 20% کندتر باشد؟

مگر اینکه قصد تست *دقیقاً* همین هزینه‌ی inline function باشد، تست بهتر/منصفانه‌تر این است که declaration `mySort(..)` را در page setup بگذارید -- نه test setup چون هر cycle بی‌خود redeclare می‌شود -- و داخل test case فقط با نام استفاده کنید: `x.sort(mySort)`.

ادامه‌ی همین مثال، یک دام دیگر: ناخواسته «کار اضافه» را به یکی از caseها اضافه/کم می‌کنید و apples-to-oranges می‌سازید:

```js
// Case 1
var x = [12,-14,0,3,18,0,2.9];
x.sort();

// Case 2
var x = [12,-14,0,3,18,0,2.9];
x.sort( function mySort(a,b){
	return a - b;
} );
```

فارغ از مشکل inline function قبلی، `mySort(..)` در case دوم چون ورودی عددی دارد درست کار می‌کند، ولی روی رشته fail می‌کرد. case اول خطا نمی‌دهد، اما رفتارش متفاوت و نتیجه‌اش فرق دارد! باید روشن باشد: **وقتی خروجی دو test case متفاوت باشد، تقریباً قطعاً کل تست نامعتبر می‌شود.**

علاوه بر تفاوت خروجی، اینجا comparator داخلی `sort(..)` عملاً «کار اضافه»ای می‌کند که `mySort()` نمی‌کند: مقادیر را به رشته coercion می‌کند و lexicographic compare انجام می‌دهد. خروجی snippet اول می‌شود `[-14, 0, 0, 12, 18, 2.9, 3]` اما دومی (احتمالاً نزدیک‌تر به قصد واقعی) می‌شود `[-14, 0, 0, 2.9, 3, 12, 18]`.

پس این تست ناعادلانه است چون caseها در اصل یک کار واحد انجام نمی‌دهند. هر نتیجه‌ای بگیرید نامعتبر است.

این دام‌ها حتی می‌توانند خیلی ظریف‌تر باشند:

```js
// Case 1
var x = false;
var y = x ? 1 : 2;

// Case 2
var x;
var y = x ? 1 : 2;
```

اینجا شاید قصد این باشد که هزینه‌ی coercion به Boolean در عملگر `? :` سنجیده شود اگر expression `x` از قبل Boolean نباشد (کتاب *Types & Grammar*). پس ظاهراً قبول کرده‌اید case دوم کار اضافه‌ی coercion دارد.

مشکل ظریف؟ در case اول مقدار `x` را set کرده‌اید ولی در case دوم نه؛ یعنی کاری در case اول انجام می‌دهید که در case دوم انجام نمی‌شود. برای حذف این skew کوچک اما ممکن، بهتر است:

```js
// Case 1
var x = false;
var y = x ? 1 : 2;

// Case 2
var x = undefined;
var y = x ? 1 : 2;
```

حالا هر دو case assignment دارند، پس احتمالاً چیزی که می‌خواستید تست کنید -- coercion مربوط به `x` یا نبود آن -- دقیق‌تر isolate شده است.
