# Transpiling

با سرعت بالای تکامل قابلیت‌ها، یک مشکل جدی‌تر برای توسعه‌دهندگان JS به‌وجود می‌آید: از یک سو شدیداً می‌خواهند از قابلیت‌های جدید استفاده کنند، اما از سوی دیگر با این واقعیت روبه‌رو هستند که سایت/اپ آن‌ها ممکن است مجبور باشد مرورگرهای قدیمیِ فاقد این پشتیبانی را هم پوشش دهد.

الگویی که ES5 در صنعت طی کرد این بود که معمولاً code baseها صبر می‌کردند تا بیشتر (یا همهٔ) محیط‌های پیشا-ES5 از محدودهٔ پشتیبانی خارج شوند، بعد ES5 را بپذیرند. نتیجه اینکه خیلی‌ها تازه همین اواخر (در زمان نگارش این متن) شروع به استفاده از مواردی مثل `strict` mode کرده‌اند؛ قابلیتی که بیش از پنج سال قبل در ES5 آمده بود.

به‌طور گسترده این رویکرد برای آیندهٔ اکوسیستم JS مضر دانسته می‌شود؛ اینکه سال‌ها از specification عقب بمانیم. همهٔ کسانی که مسئول تکامل زبان هستند می‌خواهند توسعه‌دهندگان هرچه زودتر، وقتی قابلیت‌های جدید در specification به ثبات رسیدند و مرورگرها فرصت پیاده‌سازی پیدا کردند، code خود را بر پایهٔ آن‌ها و الگوهای جدید بنا کنند.

پس این تناقض ظاهری را چطور حل کنیم؟ پاسخ، tooling است؛ مشخصاً تکنیکی به نام *transpiling* (transformation + compiling). به‌طور کلی ایده این است که از ابزار ویژه‌ای استفاده کنید تا code مربوط به ES6 شما را به معادل‌هایی (یا نزدیک به معادل!) تبدیل کند که در محیط‌های ES5 اجرا شوند.

برای مثال، تعریف shorthand برای propertyها را در نظر بگیرید (بخش «Object Literal Extensions» در فصل ۲). شکل ES6 آن:

```js
var foo = [1,2,3];

var obj = {
	foo		// means `foo: foo`
};

obj.foo;	// [1,2,3]
```

اما (تقریباً) به این شکل transpile می‌شود:

```js
var foo = [1,2,3];

var obj = {
	foo: foo
};

obj.foo;	// [1,2,3]
```

این یک transformation کوچک اما خوشایند است که اجازه می‌دهد عبارت `foo: foo` را در تعریف object literal، وقتی نام‌ها یکسان‌اند، فقط به `foo` کوتاه کنیم.

transpilerها این transformationها را برای شما انجام می‌دهند؛ معمولاً در یک مرحله از build workflow شبیه همان‌جا که linting، minification و عملیات مشابه را انجام می‌دهید.

### Shims/Polyfills

همهٔ قابلیت‌های جدید ES6 به transpiler نیاز ندارند. Polyfillها (یا shimها) الگویی برای تعریف رفتار معادل از یک محیط جدیدتر در یک محیط قدیمی‌تر هستند، هرجا که ممکن باشد. syntax قابل polyfill نیست، اما APIها اغلب هستند.

برای مثال، `Object.is(..)` یک utility جدید برای بررسی strict equality بین دو value است، اما بدون استثناهای ظریفی که `===` برای `NaN` و `-0` دارد. polyfill مربوط به `Object.is(..)` نسبتاً ساده است:

```js
if (!Object.is) {
	Object.is = function(v1, v2) {
		// test for `-0`
		if (v1 === 0 && v2 === 0) {
			return 1 / v1 === 1 / v2;
		}
		// test for `NaN`
		if (v1 !== v1) {
			return v2 !== v2;
		}
		// everything else
		return v1 === v2;
	};
}
```

**نکته:** به guard مربوط به `if` بیرونی که دور polyfill قرار گرفته دقت کنید. این جزئیات مهم است؛ یعنی این snippet فقط در محیط‌های قدیمی که API مورد نظر از قبل تعریف نشده، رفتار fallback را تعریف می‌کند. به‌ندرت پیش می‌آید که بخواهید یک API موجود را overwrite کنید.

یک مجموعهٔ بسیار خوب از shimهای ES6 با نام "ES6 Shim" (https://github.com/paulmillr/es6-shim/) وجود دارد که بهتر است قطعاً آن را به بخشی استاندارد از هر پروژهٔ جدید JS تبدیل کنید.

فرض بر این است که JS پیوسته تکامل پیدا می‌کند و مرورگرها به‌جای بسته‌های بزرگ، قابلیت‌ها را مداوم عرضه می‌کنند. پس بهترین راه برای همگام ماندن با این تکامل، این است که همین حالا polyfill shimها را وارد code base خود کنید و مرحلهٔ transpiler را به build workflow بیفزایید و به این واقعیت جدید عادت کنید.

اگر ترجیح بدهید وضع موجود را نگه دارید و صبر کنید تا همهٔ مرورگرهای فاقد پشتیبانی یک قابلیت از بین بروند و بعد از آن قابلیت استفاده کنید، همیشه عقب خواهید بود. متأسفانه در این حالت نوآوری‌هایی را از دست می‌دهید که برای مؤثرتر، کارآمدتر و مقاوم‌تر کردن توسعه با JavaScript طراحی شده‌اند.
