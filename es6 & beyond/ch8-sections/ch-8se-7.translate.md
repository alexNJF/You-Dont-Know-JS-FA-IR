# WebAssembly (WASM)

برندن آیک نزدیک پایان ویرایش اول این کتاب اعلامیه‌ای مهم مطرح کرد که می‌تواند مسیر آینده‌ی JavaScript را به‌شکل جدی تحت‌تاثیر قرار دهد: WebAssembly (WASM). در زمان نگارش این متن، WASM خیلی ابتدایی بود، پس این‌جا وارد جزئیات عمیقش نمی‌شویم؛ اما کتاب بدون اشاره به آن ناقص می‌ماند.

یکی از فشارهای مهم روی تغییرات اخیر (و آینده‌ی نزدیک) زبان JS این بوده که مقصد مناسب‌تری برای transpilation/cross-compilation از زبان‌های دیگر (مثل C/C++، ClojureScript و ...) شود. طبیعتاً عملکرد کدی که به‌صورت JavaScript اجرا می‌شود، دغدغه‌ی اصلی بوده است.

همان‌طور که در کتاب *Async & Performance* گفتیم، چند سال قبل گروهی در Mozilla ایده‌ای به نام ASM.js معرفی کردند. ASM.js زیرمجموعه‌ای از JS معتبر است که برخی رفتارها را محدود می‌کند تا بهینه‌سازی برای موتور JS آسان‌تر شود. نتیجه این است که کد سازگار با ASM.js در موتور ASM-aware می‌تواند بسیار سریع‌تر اجرا شود، نزدیک به کد C بهینه‌ی native. خیلی‌ها ASM.js را ستون اصلی اپلیکیشن‌های performance-heavy در JavaScript می‌دیدند.

به بیان دیگر، تمام راه‌های اجرای کد در مرورگر *از JavaScript عبور می‌کردند*.

تا قبل از اعلام WASM. WASM مسیر جایگزینی می‌دهد تا زبان‌های دیگر بدون عبور اولیه از JavaScript، محیط runtime مرورگر را هدف بگیرند. اگر WASM جا بیفتد، موتور JS یک قابلیت اضافه برای اجرای کد باینری خواهد داشت که تا حدی شبیه bytecode (مثل JVM) است.

WASM فرمتی برای نمایش باینری از AST بسیار فشرده‌ی کد پیشنهاد می‌کند، که می‌تواند مستقیماً به موتور JS و لایه‌های زیرینش دستور بدهد، بدون نیاز به parse شدن توسط JS یا حتی تبعیت کامل از قواعد JS. زبان‌هایی مثل C/C++ می‌توانند مستقیم به WASM کامپایل شوند (به‌جای ASM.js) و از حذف هزینه‌ی parse مربوط به JS، مزیت سرعت بیشتری بگیرند.

هدف کوتاه‌مدت WASM رسیدن به parity با ASM.js و JS بود. اما انتظار می‌رود در بلندمدت توانایی‌هایی فراتر از JS اضافه کند. مثلاً فشار برای اضافه‌شدن قابلیت‌های رادیکالی مثل thread در JS -- که می‌تواند شوک بزرگی به اکوسیستم JS بدهد -- شاید در قالب افزونه‌های آینده‌ی WASM راه بهتری داشته باشد و فشار تغییر مستقیم JS را کم کند.

در واقع این نقشه‌ی راه جدید، مسیرهای بیشتری برای زبان‌های مختلف جهت هدف‌گیری runtime وب باز می‌کند. این برای آینده‌ی پلتفرم وب هیجان‌انگیز است.

برای JS چه معنایی دارد؟ آیا JS بی‌ربط می‌شود یا «می‌میرد»؟ قطعاً نه. احتمالاً ASM.js در چند سال آینده اهمیت قبلی‌اش را از دست می‌دهد، اما بخش عمده‌ی JS همچنان محکم در داستان پلتفرم وب باقی می‌ماند.

حامیان WASM می‌گویند موفقیت آن باعث می‌شود طراحی JS از فشارهایی که ممکن بود تا مرزهای غیرمنطقی بکشاندش محافظت شود. پیش‌بینی می‌شود WASM به مقصد ترجیحی بخش‌های high-performance برنامه‌ها تبدیل شود، با کدنویسی در زبان‌های مختلف.

جالب این‌که JavaScript احتمالاً یکی از زبان‌هایی است که کمتر از بقیه مستقیماً WASM را هدف می‌گیرد. شاید در آینده زیرمجموعه‌هایی از JS برای این هدف شکل بگیرند، اما فعلاً اولویت بالایی ندارد.

هرچند JS لزوماً «قیف» اصلی WASM نمی‌شود، کد JS و کد WASM می‌توانند به‌صورت معناداری با هم interoperable باشند، تقریباً مثل تعامل ماژول‌ها امروز. می‌توانید تابع JS مثل `foo()` را صدا بزنید و در عمل تابع WASM هم‌نامی اجرا شود که بیرون از محدودیت‌های معمول JS قدرت بیشتری دارد.

چیزهایی که الان با JS نوشته می‌شوند احتمالاً در آینده‌ی قابل‌پیش‌بینی هم همچنان با JS نوشته می‌شوند. چیزهایی که به JS ترنسپایل می‌شوند احتمالاً کم‌کم WASM را هم به‌عنوان مقصد جدی بررسی می‌کنند. و برای کارهایی که بیشترین کارایی را با کمترین لایه‌ی انتزاع می‌خواهند، احتمالاً زبان غیر-JS مناسب + هدف‌گیری WASM انتخاب اصلی می‌شود.

احتمال زیاد این گذار آهسته و چندساله خواهد بود. حضور WASM در همه‌ی مرورگرهای اصلی هم بهترین حالت چند سال زمان می‌برد. در این فاصله، پروژه‌ی WASM (https://github.com/WebAssembly) یک polyfill اولیه برای اثبات مفهوم اصول پایه داشت.

اما با گذشت زمان و اضافه‌شدن ترفندهای غیر-JS به WASM، بعید نیست بخشی از چیزهای فعلاً نوشته‌شده با JS به زبان قابل‌هدف‌گیری WASM بازنویسی شوند. مثلاً بخش‌های حساس به عملکرد در فریم‌ورک‌ها، game engineها و ابزارهای پرمصرف می‌توانند از این تغییر بهره ببرند. توسعه‌دهنده‌ای که از این ابزارها استفاده می‌کند شاید تفاوت زیادی در API و integration حس نکند، اما خودکار از کارایی و قابلیت‌های بیشتر بهره می‌برد.

چیزی که قطعی است: هرچه WASM واقعی‌تر شود، تاثیرش بر مسیر و طراحی JavaScript بیشتر می‌شود. شاید یکی از مهم‌ترین موضوعات «فراتر از ES6» باشد که توسعه‌دهنده‌ها باید زیر نظر داشته باشند.
