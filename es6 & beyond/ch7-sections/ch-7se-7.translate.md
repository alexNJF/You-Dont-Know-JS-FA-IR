# بهینه‌سازی Tail Call (TCO)

به‌طور معمول، وقتی یک تابع از داخل تابع دیگری فراخوانی می‌شود، یک *stack frame* جدید برای مدیریت متغیرها/وضعیت فراخوانی جدید تخصیص می‌یابد. این کار هم زمان پردازشی هزینه دارد، هم حافظه‌ی بیشتری مصرف می‌کند.

در بیشتر برنامه‌ها زنجیره‌ی call stack معمولاً ۱۰ تا ۱۵ پرش بین تابع‌هاست و مصرف حافظه‌ی این سطح معمولاً مسئله‌ی عملی جدی نیست.

اما در برنامه‌نویسی بازگشتی (تابعی که خودش را تکراری صدا می‌زند) یا بازگشت متقابل (چند تابع که همدیگر را صدا می‌زنند)، عمق stack می‌تواند به‌راحتی صدها یا هزاران لایه شود. در این حالت اگر مصرف حافظه بی‌مهار رشد کند، مشکل‌ساز می‌شود.

به همین دلیل موتورهای JavaScript حدی دلخواه می‌گذارند تا برنامه با تمام‌کردن حافظه مرورگر/دستگاه کرش نکند. به‌همین خاطر خطای آزاردهنده‌ی `"RangeError: Maximum call stack size exceeded"` را می‌بینیم.

**هشدار:** حد عمق call stack در مشخصات کنترل نمی‌شود. وابسته به پیاده‌سازی است و بین مرورگرها/دستگاه‌ها فرق می‌کند. هیچ‌وقت با فرض محکم روی حد دقیق قابل مشاهده کدنویسی نکنید.

بعضی الگوهای فراخوانی تابع که به آن‌ها *tail call* می‌گویند، قابل بهینه‌سازی هستند تا از تخصیص frame اضافه جلوگیری شود. اگر تخصیص اضافی حذف شود، دلیلی برای محدودیت دلخواه عمق stack نمی‌ماند و موتور می‌تواند آن‌ها را بدون حد اجرا کند.

tail call یعنی دستور `return`ی که داخلش فراخوانی تابع است و بعد از آن فراخوانی هیچ کاری جز برگرداندن مقدارش انجام نمی‌شود.

این بهینه‌سازی فقط در `strict` mode اعمال می‌شود. یک دلیل دیگر برای این‌که کد را همیشه strict بنویسید.

نمونه‌ی فراخوانی‌ای که tail position نیست:

```js
"use strict";

function foo(x) {
	return x * 2;
}

function bar(x) {
	// not a tail call
	return 1 + foo( x );
}

bar( 10 );				// 21
```

اینجا بعد از `foo(x)` باید `1 + ..` انجام شود، پس وضعیت فراخوانی `bar(..)` باید حفظ شود.

اما در مثال بعد، هم فراخوانی `foo(..)` و هم `bar(..)` در tail position هستند چون آخرین کار مسیر اجرایی‌اند (جز خود `return`):

```js
"use strict";

function foo(x) {
	return x * 2;
}

function bar(x) {
	x = x + 1;
	if (x > 10) {
		return foo( x );
	}
	else {
		return bar( x + 1 );
	}
}

bar( 5 );				// 24
bar( 15 );				// 32
```

در این برنامه، `bar(..)` بازگشتی است، ولی `foo(..)` یک فراخوانی عادی است. هر دو در *proper tail position* هستند. `x + 1` قبل از فراخوانی `bar(..)` محاسبه می‌شود و بعد از پایان فراخوانی فقط `return` باقی می‌ماند.

Proper Tail Callها (PTC) در این فرم‌ها می‌توانند بهینه شوند -- همان tail call optimization یا TCO -- طوری که تخصیص frame اضافه لازم نباشد. به‌جای ساخت frame جدید، موتور همان frame فعلی را reuse می‌کند. چون بعد از PTC دیگر نیازی به حفظ state فعلی نیست.

TCO عملاً یعنی محدودیت عمق stack تقریباً از بین می‌رود. این ترفند کمی فراخوانی‌های عادی را هم بهتر می‌کند، اما مهم‌تر این است که راه استفاده‌ی واقعی از recursion را باز می‌کند، حتی اگر عمق فراخوانی ده‌ها هزار باشد.

یعنی recursion دیگر فقط ابزار نظری حل مسئله نیست و می‌تواند در برنامه‌های واقعی JavaScript استفاده شود.

از ES6 به بعد، همه‌ی PTCها باید قابل بهینه‌سازی باشند (چه recursive باشند چه نباشند).

### بازنویسی برای Tail Call

نکته این است که فقط PTCها قابل بهینه‌سازی‌اند؛ non-PTCها همچنان کار می‌کنند، اما مثل قبل frame اضافه می‌گیرند. پس اگر انتظار دارید optimization فعال شود باید ساختار توابع را با دقت در PTC نگه دارید.

اگر تابعی PTC-محور نوشته نشده باشد، ممکن است لازم شود دستی آن را بازچینی کنید تا واجد شرایط TCO شود.

مثال:

```js
"use strict";

function foo(x) {
	if (x <= 1) return 1;
	return (x / 2) + foo( x - 1 );
}

foo( 123456 );			// RangeError
```

فراخوانی `foo(x-1)` این‌جا PTC نیست چون خروجی‌اش باید قبل از `return` با `(x / 2)` جمع شود.

برای TCO در موتور ES6 می‌توانیم بازنویسی کنیم:

```js
"use strict";

var foo = (function(){
	function _foo(acc,x) {
		if (x <= 1) return acc;
		return _foo( (x / 2) + acc, x - 1 );
	}

	return function(x) {
		return _foo( 1, x );
	};
})();

foo( 123456 );			// 3810376848.5
```

اگر این کد را در موتور ES6 دارای TCO اجرا کنید، مقدار `3810376848.5` می‌گیرید. در موتورهای بدون TCO همچنان `RangeError` می‌خورید.

### بهینه‌سازی‌های غیر-TCO

راه‌های دیگری هم برای بازنویسی وجود دارد تا call stack با هر فراخوانی رشد نکند.

یکی از آن‌ها *trampolining* است: هر نتیجه‌ی جزئی را به‌صورت تابعی نمایش می‌دهید که یا تابع نتیجه‌ی جزئی بعدی را برگرداند یا نتیجه‌ی نهایی را. بعد در حلقه اجرا می‌کنید تا دیگر تابع دریافت نشود:

```js
"use strict";

function trampoline( res ) {
	while (typeof res == "function") {
		res = res();
	}
	return res;
}

var foo = (function(){
	function _foo(acc,x) {
		if (x <= 1) return acc;
		return function partial(){
			return _foo( (x / 2) + acc, x - 1 );
		};
	}

	return function(x) {
		return trampoline( _foo( 1, x ) );
	};
})();

foo( 123456 );			// 3810376848.5
```

این بازنویسی با تغییرات کم recursion را به حلقه‌ی `trampoline(..)` منتقل کرد:

1. خط `return _foo ..` را داخل `return partial() { ..` پیچیدیم.
2. فراخوانی `_foo(1,x)` را داخل `trampoline(..)` گذاشتیم.

چرا این روش به محدودیت stack نمی‌خورد؟ چون هر `partial(..)` فقط به حلقه‌ی `while` در `trampoline(..)` برگردانده می‌شود و حلقه آن را اجرا می‌کند. یعنی `partial(..)` خودش را recursive صدا نمی‌زند، فقط تابع بعدی را برمی‌گرداند. عمق stack ثابت می‌ماند.

در این بیان، trampoline از closure تابع درونی `partial()` روی `x` و `acc` استفاده می‌کند تا state بین تکرارها حفظ شود. مزیتش این است که منطق حلقه داخل utility قابل‌استفاده‌ی مجدد `trampoline(..)` بیرون کشیده می‌شود (نسخه‌هایی از آن در کتابخانه‌ها هم هست) و می‌توانید برای الگوریتم‌های مختلف reuse کنید.

البته اگر هدف بهینه‌سازی عمیق باشد (و reusability مهم نباشد)، می‌توانید state closure را حذف کنید و ردگیری state را در scope یک تابع با یک حلقه in-line کنید. این روش را معمولاً *recursion unrolling* می‌گویند:

```js
"use strict";

function foo(x) {
	var acc = 1;
	while (x > 1) {
		acc = (x / 2) + acc;
		x = x - 1;
	}
	return acc;
}

foo( 123456 );			// 3810376848.5
```

این نسخه ساده‌تر خوانده می‌شود و احتمالاً از نظر اجرای خام، بین فرم‌هایی که دیدیم بهترین کارایی را دارد. شاید به نظر برنده‌ی قطعی بیاید و بپرسید چرا اصلاً سراغ روش‌های دیگر برویم.

دلایلی هست که همیشه unroll دستی نخواهید:

* به‌جای بیرون‌کشیدن منطق trampoline برای reuse، آن را inline کردیم. برای یک مثال عالی است، اما وقتی چندین مورد در برنامه داشته باشید، reuse برای کوتاهی و مدیریت بهتر مهم می‌شود.
* مثال این‌جا عمداً ساده است. در عمل recursionها پیچیده‌ترند، مثل mutual recursion (بیش از یک تابع که همدیگر را صدا می‌زنند).

   هرچه جلوتر بروید، بهینه‌سازی دستیِ unrolling پیچیده‌تر و ریزه‌کارانه‌تر می‌شود و ارزش خوانایی خیلی زود از دست می‌رود. مزیت اصلی recursion (حتی در فرم PTC) حفظ خوانایی الگوریتم و سپردن بهینه‌سازی عملکرد به موتور است.

اگر الگوریتم را با PTC بنویسید، موتور ES6 با TCO کد را با عمق ثابت stack اجرا می‌کند (با reuse frameها). یعنی خوانایی recursion را با بیشتر مزایای کارایی و بدون محدودیت طول اجرا می‌گیرید.

### Meta؟

TCO چه ربطی به متاپروگرمینگ دارد؟

همان‌طور که در بخش «Feature Testing» گفتیم، می‌توانید در runtime بفهمید موتور از چه قابلیت‌هایی پشتیبانی می‌کند. این شامل TCO هم می‌شود، هرچند تشخیصش کمی brute-force است:

```js
"use strict";

try {
	(function foo(x){
		if (x < 5E5) return foo( x + 1 );
	})( 1 );

	TCO_ENABLED = true;
}
catch (err) {
	TCO_ENABLED = false;
}
```

در موتور بدون TCO حلقه‌ی بازگشتی نهایتاً fail می‌شود و `try..catch` آن را می‌گیرد. در موتور دارای TCO حلقه به‌راحتی کامل می‌شود.

زشت است، نه؟

اما متاپروگرمینگ حول وجود/عدم وجود TCO چه فایده‌ای دارد؟ پاسخ ساده: می‌توانید بر اساس نتیجه، نسخه‌ای از برنامه را لود کنید که recursion استفاده می‌کند، یا نسخه‌ی جایگزین تبدیل/ترنسپایل‌شده‌ای که recursion نیاز ندارد.

#### کد خودتنظیم (Self-Adjusting)

یک نگاه دیگر:

```js
"use strict";

function foo(x) {
	function _foo() {
		if (x > 1) {
			acc = acc + (x / 2);
			x = x - 1;
			return _foo();
		}
	}

	var acc = 1;

	while (x > 1) {
		try {
			_foo();
		}
		catch (err) { }
	}

	return acc;
}

foo( 123456 );			// 3810376848.5
```

این الگوریتم تلاش می‌کند تا جای ممکن کار را بازگشتی انجام دهد، اما پیشرفت را با متغیرهای scopeی `x` و `acc` نگه می‌دارد. اگر کل مسئله بدون خطا بازگشتی حل شد، عالی. اگر موتور وسط کار recursion را قطع کرد، با `try..catch` می‌گیریم و دوباره از همان نقطه ادامه می‌دهیم.

این هم نوعی متاپروگرمینگ است: در runtime توانایی موتور برای تکمیل کامل کار به‌صورت بازگشتی را probe می‌کنید و محدودیت موتورهای بدون TCO را دور می‌زنید.

در نگاه اول (حتی دوم) احتمالاً این کد نسبت به نسخه‌های قبلی خیلی زشت‌تر به نظر می‌رسد. روی اجرای بزرگ در محیط بدون TCO هم کمی کندتر است.

مزیت اصلی‌اش -- جز این‌که در موتور بدون TCO هم هر اندازه مسئله را تمام می‌کند -- این است که این «راه‌حل» نسبت به trampolining یا unrolling دستی انعطاف‌پذیرتر است.

عملاً `_foo()` در این حالت می‌تواند stand-in تقریباً هر کار بازگشتی (حتی mutual recursion) باشد. باقی کد هم boilerplateای است که برای بیشتر الگوریتم‌ها جواب می‌دهد.

تنها نکته این است که برای resume کردن پس از برخورد به حد recursion، state باید در متغیرهای scopeی بیرون از تابع(های) بازگشتی باشد. ما همین کار را کردیم و `x` و `acc` را بیرون `_foo()` نگه داشتیم، نه مثل قبل به‌عنوان آرگومان پاس بدهیم.

تقریباً هر الگوریتم بازگشتی را می‌توان به این فرم تطبیق داد. یعنی این روش با کمترین بازنویسی، فراگیرترین راه بهره‌گیری از TCO همراه recursion در برنامه است.

این رویکرد همچنان PTC دارد؛ بنابراین در مرورگر قدیمی به‌صورت *progressive enhancement* با batchهای recursion داخل حلقه اجرا می‌شود، و در محیط ES6+ می‌تواند کاملاً از recursion مبتنی بر TCO بهره ببرد. خیلی جذاب است.
