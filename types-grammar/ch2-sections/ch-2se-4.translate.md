## رفتارهای عددی

اعداد برای انواع کارها در برنامه‌هایمان استفاده می‌شوند، اما عمدتاً برای محاسبات ریاضی. به نحوهٔ رفتار اعداد JS دقت کنید تا نتایج مطابق انتظار باشند.

### عدم دقت نقطه‌شناور

باید بحث IEEE-754 از فصل ۱ را دوباره بررسی کنیم.

یکی از gotchaهای کلاسیک هر سیستم عددی IEEE-754 در هر زبان برنامه‌نویسی — نه منحصراً JS! — این است که همهٔ عملیات و مقادیر نمی‌توانند به‌راحتی در نمایش‌های IEEE-754 جا بگیرند.

رایج‌ترین مثال:

```js
point3a = 0.1 + 0.2;
point3b = 0.3;

point3a;                        // 0.30000000000000004
point3b;                        // 0.3

point3a === point3b;            // false <-- oops!
```

عملیات `0.1 + 0.2` در نهایت خطای نقطه‌شناور (drift) ایجاد می‌کند، جایی که مقدار ذخیره‌شده در واقع `0.30000000000000004` است.

نمایش‌های بیتی مربوطه:

```
// 0.30000000000000004
00111111110100110011001100110011
00110011001100110011001100110100

// 0.3
00111111110100110011001100110011
00110011001100110011001100110011
```

اگر به آن الگوهای بیتی دقیق نگاه کنید، فقط ۲ بیت آخر متفاوت هستند، از `00` به `11`. اما برای نابرابر بودن آن دو عدد کافی است!

دوباره تأکید: این رفتار **به هیچ وجه** منحصر به JS نیست. دقیقاً نحوهٔ کار هر زبان برنامه‌نویسی مطابق IEEE-754 در همین سناریو است. همان‌طور که بالا ادعا کردم، اکثر زبان‌های برنامه‌نویسی از IEEE-754 استفاده می‌کنند و بنابراین همین سرنوشت را خواهند داشت.

وسوسهٔ مسخره کردن JS برای `0.1 + 0.2 !== 0.3` قوی است، می‌دانم. اما اینجا کاملاً بی‌اساس است.

| NOTE: |
| :--- |
| تقریباً همهٔ برنامه‌نویسان باید از IEEE-754 آگاه باشند و مطمئن شوند دربارهٔ این نوع gotchaها محتاط هستند. به‌طرز ناامیدکننده‌ای شگفت‌انگیز است که چند نفر از آن‌ها ایده‌ای از نحوهٔ کار IEEE-754 دارند. اگر وقت گذاشته و این مفاهیم را تا الان خوانده و فهمیده‌اید، الان در آن درصد کوچک نادری هستید که واقعاً تلاش کرده‌اند اعداد در برنامه‌هایشان را بفهمند! |

#### آستانهٔ Epsilon

یک توصیهٔ رایج برای دور زدن چنین عدم دقت نقطه‌شناور از این مقدار `number` *بسیار کوچک* تعریف‌شده توسط JS استفاده می‌کند:

```js
Number.EPSILON;                 // 2.220446049250313e-16
```

*Epsilon* کوچک‌ترین تفاوتی است که JS می‌تواند بین `1` و مقدار بعدی بزرگ‌تر از `1` نمایش دهد. اگرچه این مقدار از نظر فنی وابسته به پیاده‌سازی/پلتفرم است، عموماً حدود `2.2E-16` یا `2^-52` است.

برای کسانی که به جزئیات اینجا دقت کافی نمی‌کنند — از جمله خود گذشتهٔ من! — عموماً فرض می‌شود که هر انحراف در دقت نقطه‌شناور از یک عملیات تکی هرگز نباید بزرگ‌تر از `Number.EPSILON` باشد. بنابراین، از نظر نظری، می‌توانیم از `Number.EPSILON` به‌عنوان مقدار تحمل *بسیار کوچک* استفاده کنیم تا مقایسه‌های برابری عددی *امن* باشند:

```js
function safeNumberEquals(a,b) {
    return Math.abs(a - b) < Number.EPSILON;
}

point3a = 0.1 + 0.2;
point3b = 0.3;

// are these safely "equal"?
safeNumberEquals(point3a,point3b);      // true
```

| WARNING: |
| :--- |
| در ویرایش اول کتاب «Types & Grammar»، دقیقاً این رویکرد را توصیه کردم. اشتباه بود. باید موضوع را دقیق‌تر تحقیق می‌کردم. |

اما معلوم می‌شود این رویکرد اصلاً امن نیست:

```js
point3a = 10.1 + 0.2;
point3b = 10.3;

safeNumberEquals(point3a,point3b);      // false :(
```

خب... بدشانسی!

متأسفانه، `Number.EPSILON` فقط برای اعداد/عملیات کوچک خاص به‌عنوان آستانهٔ خطای «امن برابر» کار می‌کند، و در موارد دیگر خیلی کوچک است و false negative می‌دهد.

می‌توانید `Number.EPSILON` را با عاملی مقیاس کنید تا آستانهٔ بزرگ‌تری تولید کنید که از false negative اجتناب کند اما همچنان همهٔ انحراف نقطه‌شناور در برنامه را فیلتر کند. اما چه عاملی استفاده شود کاملاً قضاوت دستی بر اساس بزرگی مقادیر و عملیات روی آن‌هاست که برنامه شامل می‌شود. راه خودکاری برای محاسبهٔ آستانهٔ قابل اعتماد و جهانی وجود ندارد.

مگر واقعاً بدانید چه می‌کنید، اصلاً نباید از این رویکرد آستانهٔ `Number.EPSILON` استفاده کنید.

| TIP: |
| :--- |
| اگر می‌خواهید جزئیات و توصیهٔ محکم‌تری دربارهٔ این موضوع بخوانید، به‌شدت این پست را توصیه می‌کنم. [^EpsilonBad] اما اگر نمی‌توانیم از `Number.EPSILON` برای اجتناب از خطرات انحراف نقطه‌شناور استفاده کنیم، چه کنیم؟ اگر می‌توانید با مقیاس‌بندی همهٔ اعدادتان به‌طور کامل از نقطه‌شناور اجتناب کنید تا همهٔ آن‌ها integerهای عدد صحیح (یا bigint) باشند هنگام انجام ریاضی، این کار را بکنید. فقط وقتی مجبورید مقدار نهایی را بعد از اتمام همهٔ ریاضیات خروجی/نمایش دهید با مقادیر اعشاری سروکار داشته باشید. اگر ممکن/عملی نیست، از کتابخانهٔ شبیه‌سازی اعشار دقت دلخواه استفاده کنید و کاملاً از مقادیر `number` اجتناب کنید. یا ریاضیات را در محیط برنامه‌نویسی خارجی دیگری که بر IEEE-754 مبتنی نیست انجام دهید. |

### مقایسهٔ عددی

مثل رشته‌ها، مقادیر عددی را می‌توان با همان عملگرها مقایسه کرد (هم برای برابری و هم ترتیب رابطه‌ای).

به یاد داشته باشید مهم نیست مقدار عددی هنگام مشخص‌شدن به‌عنوان literal چه شکلی داشته باشد (پایهٔ ۱۰، هشت‌تایی، هگزادسیمال، نمادی و غیره)، مقدار زیربنایی ذخیره‌شده همان است که مقایسه می‌شود. همچنین مسائل عدم دقت نقطه‌شناور بحث‌شده در بخش قبلی را به یاد داشته باشید، چون مقایسه‌ها به محتوای دودویی دقیق حساس هستند.

#### برابری عددی

درست مثل رشته‌ها، مقایسهٔ برابری برای اعداد از عملگرهای `==` / `===` یا `Object.is(..)` استفاده می‌کند. همچنین به یاد داشته باشید اگر نوع هر دو عملوند یکسان باشد، `==` دقیقاً مثل `===` عمل می‌کند.

```js
42 == 42;                   // true
42 === 42;                  // true

42 == 43;                   // false
42 === 43;                  // false

Object.is(42,42);           // true
Object.is(42,43);           // false
```

برای برابری اجباری `==` (وقتی نوع عملوندها مطابقت نکنند)، اگر هر عملوندی مقدار رشته نباشد، `==` بررسی برابری عددی را ترجیح می‌دهد (یعنی هر دو عملوند به عدد اجبار می‌شوند).

```js
// numeric (not string!) comparison
42 == "42";                 // true
```

در این قطعه، برابری اجباری `"42"` را به `42` اجبار می‌کند، نه برعکس (`42` به `"42"`). وقتی هر دو نوع `number` شدند، مقادیرشان برای برابری دقیق مقایسه می‌شوند، مثل `===`.

به یاد داشته باشید JS بین مقادیری مثل `42`، `42.0` و `42.000000` تمایز قائل نمی‌شود؛ در زیر، همه یکی هستند. تعجب‌آور نیست، بررسی‌های برابری `==` و `===` آن را تأیید می‌کنند:

```js
42 == 42.0;                 // true
42.0 == 42.00000;           // true
42.00 === 42.000;           // true
```

شهود شما احتمالاً این است که اگر دو عدد دقیقاً یکی باشند، برابرند. و JS همین‌طور تفسیر می‌کند. اما `0.3` دقیقاً با نتیجهٔ `0.1 + 0.2` یکی نیست، چون (همان‌طور که قبلاً دیدیم) دومی مقداری زیربنایی تولید می‌کند که *خیلی نزدیک* به `0.3` است اما دقیقاً یکسان نیست.

جالبه که دو مقدار *آنقدر* نزدیک هستند که تفاوتشان کمتر از آستانهٔ `Number.EPSILON` است، پس JS در واقع نمی‌تواند آن تفاوت را *دقیق* نمایش دهد.

شاید فکر کنید، حداقل غیررسمی، که چنین اعداد JS باید «برابر» باشند، چون تفاوت بین آن‌ها برای نمایش خیلی کوچک است. اما توجه کنید: JS *می‌تواند* نمایش دهد که تفاوت *وجود دارد*، به‌همین دلیل آن `4` را در انتهای اعشار می‌بینید وقتی JS مقدار `0.1 + 0.2` را ارزیابی می‌کند. و می‌توانستید عدد literal `0.00000000000000004` (یعنی `4e-17`) را تایپ کنید، که تفاوت بین `0.3` و `0.1 + 0.2` است.

آنچه JS با اعداد نقطه‌شناور IEEE-754 نمی‌تواند انجام دهد، نمایش عددی *دقیق* به اندازهٔ کافی است که عملیات روی آن نتایج مورد انتظار تولید کند. برای نمایش کامل و صحیح در نوع `number` که JS ارائه می‌دهد خیلی کوچک است.

پس `0.1 + 0.2 == 0.3` به `false` حل می‌شود، چون تفاوتی بین دو مقدار وجود دارد، حتی اگر JS نتواند تفاوتی به آن کوچکی را دقیق نمایش دهد یا با آن کاری کند.

همچنین مثل رشته‌ها، عملگرهای `!=` (coercive not-equal) و `!==` (strict-not-equal) با اعداد کار می‌کنند. `x != y` اساساً `!(x == y)` است و `x !== y` اساساً `!(x === y)` است.

دو استثنای ناامیدکننده در برابری عددی وجود دارد (چه از `==` یا `===` استفاده کنید):

```js
NaN === NaN;                // false -- ugh!
-0 === 0;                   // true -- ugh!
```

`NaN` هرگز با خودش برابر نیست (حتی با `===`)، و `-0` همیشه با `0` برابر است (حتی با `===`). گاهی تعجب‌برانگیز است که حتی `===` این دو استثنا را دارد.

با این حال، بررسی برابری `Object.is(..)` هیچ یک از این استثناها را ندارد، پس برای مقایسهٔ برابری با `NaN` و `-0`، از عملگرهای `==` / `===` اجتناب کنید و از `Object.is(..)` استفاده کنید — یا برای `NaN` به‌طور خاص، `Number.isNaN(..)`.

#### مقایسه‌های رابطه‌ای عددی

درست مثل مقادیر رشته، عملگرهای رابطه‌ای JS (`<`، `<=`، `>` و `>=`) با اعداد عمل می‌کنند. عملیات `<` (کمتر از) و `>` (بیشتر از) باید نسبتاً خودتوضیح باشند:

```js
41 < 42;                    // true

0.1 + 0.2 > 0.3;            // true (ugh, IEEE-754)
```

به یاد داشته باشید: مثل `==`، عملگرهای `<` و `>` هم اجباری هستند، یعنی هر مقدار غیرعددی به عدد اجبار می‌شود — مگر هر دو عملوند از قبل رشته باشند، همان‌طور که قبلاً دیدیم. عملگرهای مقایسهٔ رابطه‌ای strict وجود ندارند.

اگر مقایسهٔ رابطه‌ای بین اعداد انجام می‌دهید، تنها راه اجتناب از coercion اطمینان از این است که مقایسه‌ها همیشه دو عدد داشته باشند. در غیر این صورت، این عملگرها مقایسه‌های *رابطه‌ای اجباری* انجام می‌دهند شبیه نحوهٔ انجام مقایسه‌های *برابری اجباری* توسط `==`.

### عملگرهای ریاضی

همان‌طور که قبلاً ادعا کردم، دلیل اصلی داشتن اعداد در زبان برنامه‌نویسی انجام عملیات ریاضی با آن‌هاست. پس بیایید دربارهٔ نحوهٔ انجام آن صحبت کنیم.

عملگرهای حسابی پایه `+` (جمع)، `-` (تفریق)، `*` (ضرب) و `/` (تقسیم) هستند. عملگرهای `**` (توان) و `%` (modulo، یعنی *باقی‌ماندهٔ تقسیم*) هم در دسترس هستند. اشکال `+=`، `-=`، `*=`، `/=`، `**=` و `%=` عملگرها هم وجود دارند که علاوه بر آن نتیجه را به عملوند چپ — که باید هدف انتساب معتبر مثل متغیر یا ویژگی باشد، نه فقط مقدار literal — اختصاص می‌دهند.

| NOTE: |
| :--- |
| همان‌طور که قبلاً دیدیم، عملگر `+` overload شده تا هم با اعداد و هم رشته‌ها کار کند. وقتی یک یا هر دو عملوند رشته باشد، نتیجه الحاق رشته است (از جمله اجبار هر عملوند به رشته در صورت نیاز). اما اگر هیچ عملوندی رشته نباشد، نتیجه جمع عددی است، همان‌طور که انتظار می‌رود. |

همهٔ این عملگرهای ریاضی *دودویی* هستند، یعنی دو عملوند مقدار انتظار دارند، یکی در هر طرف عملگر؛ همه انتظار دارند عملوندها مقادیر عددی باشند. اگر یک یا هر دو عملوند غیرعدد باشند، عملوند(های) غیرعددی به عدد اجبار می‌شوند تا عملیات انجام شود. coercion را در فصل بعدی به‌تفصیل پوشش می‌دهیم.

در نظر بگیرید:

```js
40 + 2;                 // 42
44 - 2;                 // 42
21 * 2;                 // 42
84 / 2;                 // 42
7 ** 2;                 // 49
49 % 2;                 // 1

40 + "2";               // "402" (string concatenation)
44 - "2";               // 42 (because "2" is coerced to 2)
21 * "2";               // 42 (..ditto..)
84 / "2";               // 42 (..ditto..)
"7" ** "2";             // 49 (both operands are coerced to numbers)
"49" % "2";             // 1 (..ditto..)
```

عملگرهای `+` و `-` به شکل *یکانی* هم می‌آیند، یعنی فقط یک عملوند دارند؛ دوباره، عملوند انتظار می‌رود عدد باشد و اگر نباشد به عدد اجبار می‌شود:

```js
+42;                    // 42
-42;                    // -42

+"42";                  // 42
-"42";                  // -42
```

شاید متوجه شده باشید `-42` به‌نظر فقط literal عددی «منفی چهل‌ودو» است. کاملاً درست نیست. ظرافت نحو JS این است که literalهای عددی منفی را تشخیص نمی‌دهد. در عوض، JS این را به‌عنوان literal عددی مثبت `42` که قبلش یکانی `-` در جلویش قرار دارد و نفی می‌شود رفتار می‌کند.

تا حدی غافل‌گیرکننده:

```js
-42;                    // -42
- 42;                   // -42
-
    42;                 // -42
```

همان‌طور که می‌بینید، فاصلهٔ خالی (و حتی خطوط جدید) بین عملگر یکانی `-` و عملوندش مجاز است؛ در واقع، این برای همهٔ عملگرها و عملوندها صادق است.

#### افزایش و کاهش

دو عملگر عددی یکانی دیگر وجود دارد: `++` (افزایش) و `--` (کاهش). هر دو عملیات مربوطه را انجام می‌دهند و سپس نتیجه را به عملوند — که باید هدف انتساب معتبر مثل متغیر یا ویژگی باشد — دوباره انتساب می‌دهند.

ممکن است `++` را معادل `+= 1` و `--` را معادل `-= 1` فکر کنید:

```js
myAge = 42;

myAge++;
myAge;                  // 43

numberOfHeadHairs--;
```

با این حال، این عملگرهای ویژه‌ای هستند چون می‌توانند در موقعیت postfix (بعد از عملوند) یا prefix (قبل از عملوند) ظاهر شوند:

```js
myAge = 42;

++myAge;
myAge;                  // 43

--numberofHeadHairs;
```

شاید عجیب به‌نظر برسد که موقعیت‌های prefix و postfix در چنین مثال‌هایی به‌نظر نتیجهٔ یکسان می‌دهند (افزایش یا کاهش). تفاوت ظریف است و به نتیجهٔ انتساب نهایی مربوط نیست. این عملگرهای خاص را در فصل بعدی برای بررسی تفاوت‌های موقعیتی دوباره بررسی می‌کنیم.

### عملگرهای بیتی

JS چند عملگر بیتی برای انجام عملیات سطح بیتی روی مقادیر عددی ارائه می‌دهد.

با این حال، این عملیات بیتی روی الگوی بیتی بسته‌شدهٔ اعداد IEEE-754 (ببینید فصل ۱) انجام نمی‌شوند. در عوض، عدد عملوند ابتدا به *integer* علامت‌دار ۳۲ بیتی تبدیل می‌شود، عملیات بیتی انجام می‌شود و سپس نتیجه دوباره به عدد IEEE-754 تبدیل می‌شود.

به یاد داشته باشید، مثل هر عملگر اولیهٔ دیگر، این‌ها فقط مقادیر جدید محاسبه می‌کنند، نه واقعاً تغییر مقدار در جا.

* `&` (bitwise AND): عملیات AND با هر بیت متناظر از دو عملوند؛ `42 & 36 === 32`

* `|` (bitwise OR): عملیات OR با هر بیت متناظر از دو عملوند؛ `42 | 36 === 46`

* `^` (bitwise XOR): عملیات XOR با هر بیت متناظر از دو عملوند؛ `42 ^ 36 === 14`

* `~` (bitwise NOT): عملیات NOT روی بیت‌های یک عملوند تکی؛ `~42 === -43`

* `<<` (left shift): شیفت چپ بیت‌های عملوند چپ به تعداد بیت مشخص‌شده توسط عملوند راست؛ `42 << 3 == 336`

* `>>` (right shift): شیفت راست با انتشار علامت بیت‌های عملوند چپ؛ `42 >> 3 === 5`

* `>>>` (zero-fill right shift): همان شیفت راست مثل `>>` اما `0` بیت‌های شیفت‌خورده از چپ را پر می‌کند؛ `42 >>> 3 === 5` اما `-43 >>> 3 === 536870906`

* `&=`، `|=`، `<<=`، `>>=` و `>>>=`: عملگرهای بیتی با انتساب

صادقانه، عملیات بیتی در JS خیلی رایج نیستند. اما گاهی ممکن است عبارتی مثل این ببینید:

```js
myGPA = 3.54;

myGPA | 0;              // 3
```

چون عملگرهای بیتی فقط روی integerهای ۳۲ بیتی عمل می‌کنند، عملیات `| 0` هر مقدار اعشاری را قطع می‌کند (یعنی `Math.trunc(..)`)، و فقط integer را باقی می‌گذارد.

| WARNING: |
| :--- |
| تصور نادرست رایج این است که `| 0` مثل *floor* (یعنی `Math.floor(..)`) است. نتیجهٔ `| 0` روی اعداد مثبت با `Math.floor(..)` موافق است، اما روی اعداد منفی متفاوت است، چون طبق تعریف استاندارد، *floor* عملیاتی است که به سمت `-Infinity` گرد می‌کند. `| 0` صرفاً بیت‌های اعشاری را دور می‌ریزد، که در واقع truncation است. |

### متدهای مقدار عددی

مقادیر عددی متدهای زیر (به‌عنوان ویژگی) برای عملیات خاص عدد ارائه می‌دهند:

* `toExponential(..)`: نمایش رشتهٔ عدد با نماد علمی تولید می‌کند (مثلاً `"4.2e+1"`)

* `toFixed(..)`: نمایش رشتهٔ غیرنمادی عدد با تعداد مشخص‌شدهٔ ارقام اعشاری تولید می‌کند

* `toPrecision(..)`: مثل `toFixed(..)`، جز اینکه آرگومان عددی را به‌عنوان تعداد ارقام معنادار (یعنی دقت) اعمال می‌کند

* `toLocaleString(..)`: نمایش رشتهٔ عدد طبق locale فعلی تولید می‌کند

```js
myAge = 42;

myAge.toExponential(3);         // "4.200e+1"
```

یک ظرافت خاص نحو JS این است که `.` هنگام سروکار با literalهای عددی و دسترسی ویژگی/متد می‌تواند مبهم باشد.

اگر `.` بلافاصله (بدون فاصلهٔ خالی) بعد از رقم literal عددی بیاید و قبلاً `.` اعشاری در مقدار عدد نباشد، `.` فرض می‌شود شروع بخش اعشاری عدد است. اما اگر موقعیت `.` به‌طور غیرمبهم *بخشی* از literal عددی نباشد، همیشه به‌عنوان دسترسی ویژگی رفتار می‌شود.

```js
42 .toExponential(3);           // "4.200e+1"
```

اینجا، فاصلهٔ خالی `.` را روشن می‌کند و آن را به‌عنوان دسترسی ویژگی/متد مشخص می‌کند. شاید رایج‌تر/ترجیح‌داده‌شده‌تر استفاده از `(..)` به‌جای فاصلهٔ خالی برای چنین روشن‌سازی باشد:

```js
(42).toExponential(3);          // "4.200e+1"
```

اثر غیرمعمول‌به‌نظر این قانون دستور تجزیهٔ JS:

```js
42..toExponential(3);           // "4.200e+1"
```

به‌اصطلاح اصطلاح «double-dot»، اولین `.` در این عبارت اعشار است و بنابراین دومین `.` به‌طور غیرمبهم *اعشار نیست*، بلکه دسترسی ویژگی/متد است.

همچنین توجه کنید بعد از اولین `.` رقم نیست؛ کاملاً نحو قانونی است `.` دنباله‌دار روی literal عددی بگذارید:

```js
myAge = 41. + 1.;

myAge;                          // 42
```

مقادیر نوع `bigint` نمی‌توانند اعشار داشته باشند، پس تجزیه غیرمبهم است که `.` بعد از literal (با `n` دنباله‌دار) همیشه دسترسی ویژگی است:

```js
42n.toString();                 // 42
```

### ویژگی‌های استاتیک `Number`

* `Number.EPSILON`: کوچک‌ترین مقدار ممکن بین `1` و عدد بعدی بالاتر

* `Number.NaN`: همان نماد سراسری `NaN`، عدد نامعتبر ویژه

* `Number.MIN_SAFE_INTEGER` / `Number.MAX_SAFE_INTEGER`: integerهای مثبت و منفی با بزرگ‌ترین مقدار مطلق

* `Number.MIN_VALUE` / `Number.MAX_VALUE`: حداقل و حداکثر قابل نمایش توسط نوع `number`

* `Number.NEGATIVE_INFINITY` / `Number.POSITIVE_INFINITY`: همان `-Infinity` و `Infinity` سراسری

### کمک‌کننده‌های استاتیک `Number`

* `Number.isFinite(..)`: بولی برمی‌گرداند که آیا مقدار محدود است

* `Number.isInteger(..)` / `Number.isSafeInteger(..)`: هر دو بولی برمی‌گردانند که آیا مقدار عدد صحیح کامل است و در محدودهٔ *امن* integerهاست

* `Number.isNaN(..)`: نسخهٔ باگ‌رفتهٔ ابزار سراسری `isNaN(..)` که مشخص می‌کند آیا آرگومان مقدار ویژهٔ `NaN` است

* `Number.parseFloat(..)` / `Number.parseInt(..)`: ابزارهایی برای تجزیهٔ مقادیر رشته برای ارقام عددی، چپ به راست

### فضای نام استاتیک `Math`

چون کاربرد اصلی مقادیر `number` انجام عملیات ریاضی است، JS ثابت‌ها و ابزارهای عملیات ریاضی استاندارد زیادی در فضای نام `Math` شامل می‌کند.

تعداد زیادی از این‌ها هست، پس از فهرست کردن تک‌تک آن‌ها صرف‌نظر می‌کنم. اما چند تا برای مثال:

```js
Math.PI;                        // 3.141592653589793

// absolute value
Math.abs(-32.6);                // 32.6

// rounding
Math.round(-32.6);              // -33

// min/max selection
Math.min(100,Math.max(0,42));   // 42
```

برخلاف `Number` که تابع `Number(..)` هم هست (برای coercion عددی)، `Math` فقط شیءای است که این ویژگی‌ها و توابع کمکی استاتیک را نگه می‌دارد؛ نمی‌توان آن را به‌عنوان تابع فراخوانی کرد.

| WARNING: |
| :--- |
| یکی از اعضای عجیب فضای نام `Math` عبارت است از `Math.random()` برای تولید مقدار نقطه‌شناور تصادفی بین `0` و `1.0`. غیرمعمول است تولید عدد تصادفی — کاری که ذاتاً stateful/دارای اثر جانبی است — را عملیات ریاضی در نظر بگیریم. از نظر امنیتی هم مدتها footgun بوده، چون مولد عدد شبه‌تصادفی (PRNG) که JS استفاده می‌کند از نظر رمزنگاری *امن* نیست (قابل پیش‌بینی). پلتفرم وب چند سال پیش با API امن‌تر `crypto.getRandomValues(..)` وارد شد. استفاده از `Math.random()` الان به‌طور جهانی منع شده. |

### BigIntها و Numberها ترکیب نمی‌شوند

همان‌طور که در فصل ۱ پوشش دادیم، مقادیر نوع `number` و `bigint` نمی‌توانند در همان عملیات ترکیب شوند. این می‌تواند حتی با افزایش سادهٔ مقدار (مثل در حلقه) شما را به دام بیندازد:

```js
myAge = 42n;

myAge + 1;                  // TypeError thrown!
myAge += 1;                 // TypeError thrown!

myAge + 1n;                 // 43n
myAge += 1n;                // 43n

myAge++;
myAge;                      // 44n
```

بنابراین، اگر هم مقادیر `number` و هم `bigint` در برنامه‌هایتان استفاده می‌کنید، باید به‌طور منظم یکی را به دیگری اجبار کنید. تابع `BigInt(..)` (بدون کلمهٔ کلیدی `new`) می‌تواند مقدار `number` را به `bigint` اجبار کند. برعکس، برای جهت دیگر از `bigint` به `number`، از تابع `Number(..)` استفاده کنید (دوباره، بدون کلمهٔ کلیدی `new`):

```js
BigInt(42);                 // 42n

Number(42n);                // 42
```

به یاد داشته باشید: اجبار بین این نوع‌ها خطراتی دارد:

```js
BigInt(4.2);                // RangeError thrown!
BigInt(NaN);                // RangeError thrown!
BigInt(Infinity);           // RangeError thrown!

Number(2n ** 1024n);        // Infinity
```
