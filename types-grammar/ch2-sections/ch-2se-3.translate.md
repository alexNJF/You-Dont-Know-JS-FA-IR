## رفتارهای رشته

مقادیر رشته رفتارهای خاصی دارند که هر توسعه‌دهندهٔ JS باید از آن‌ها آگاه باشد.

### دسترسی به کاراکتر رشته

اگرچه رشته‌ها در واقع آرایه نیستند، JS اجازهٔ دسترسی سبک آرایهٔ `[ .. ]` به کاراکتر در ایندکس عددی (بر پایهٔ `0`) را می‌دهد:

```js
greeting = "Hello!";

greeting[4];            // "o"
```

اگر مقدار/عبارت بین `[ .. ]` به عدد حل نشود، مقدار به‌طور ضمنی به نمایش عددی صحیح/کل آن تبدیل می‌شود (در صورت امکان).

```js
greeting["4"];          // "o"
```

اگر مقدار/عبارت به عددی خارج از محدودهٔ صحیح `0` - `length - 1` (یا `NaN`) حل شود، یا اگر نوع مقدار `number` نباشد، دسترسی به‌جای آن به‌عنوان دسترسی ویژگی با نام ویژگی معادل رشته رفتار می‌شود. اگر دسترسی ویژگی شکست بخورد، نتیجه `undefined` است.

| NOTE: |
| :--- |
| coercion را بعداً در کتاب به‌تفصیل پوشش می‌دهیم. |

### تکرار کاراکتر

رشته‌ها آرایه نیستند، اما قطعاً در بسیاری جهات آرایه‌ها را تقلید می‌کنند. یکی از این رفتارها این است که، مثل آرایه‌ها، رشته‌ها iterable هستند. یعنی کاراکترهای (code-unitهای) رشته را می‌توان به‌صورت جداگانه تکرار کرد:

```js
myName = "Kyle";

for (let char of myName) {
    console.log(char);
}
// K
// y
// l
// e

chars = [ ...myName ];
chars;
// [ "K", "y", "l", "e" ]
```

مقادیری مثل رشته‌ها و آرایه‌ها iterable هستند (از طریق `...`، `for..of` و `Array.from(..)`)، اگر متد تولیدکنندهٔ iterator را در محل ویژگی symbol ویژهٔ `Symbol.iterator` افشا کنند (ببینید «Well-Known Symbols» در فصل ۱):

```js
myName = "Kyle";
it = myName[Symbol.iterator]();

it.next();      // { value: "K", done: false }
it.next();      // { value: "y", done: false }
it.next();      // { value: "l", done: false }
it.next();      // { value: "e", done: false }
it.next();      // { value: undefined, done: true }
```

| NOTE: |
| :--- |
| جزئیات پروتکل iterator، از جمله اینکه نتیجهٔ `{ value: "e" .. }` هنوز `done: false` نشان می‌دهد، به‌تفصیل در عنوان «Sync & Async» این مجموعه پوشش داده شده. |

### محاسبهٔ طول

همان‌طور که در فصل ۱ ذکر شد، مقادیر رشته ویژگی `length` دارند که به‌طور خودکار طول رشته را نشان می‌دهد؛ این ویژگی فقط قابل دسترسی است؛ تلاش برای تنظیم آن ساکتانه نادیده گرفته می‌شود.

مقدار `length` گزارش‌شده تا حدی با تعداد کاراکترها در رشته (در واقع، code-unitها) مطابقت دارد، اما همان‌طور که در فصل ۱ دیدیم، وقتی کاراکترهای Unicode درگیر هستند پیچیده‌تر است.

اکثر مردم نمادها را به‌صورت بصری به‌عنوان کاراکترهای جدا تشخیص می‌دهند؛ این مفهوم نماد بصری مستقل *grapheme* یا *grapheme cluster* نامیده می‌شود. پس هنگام شمارش «طول» رشته، معمولاً منظورمان شمارش تعداد graphemeهاست.

اما کامپیوتر این‌طور با کاراکترها برخورد نمی‌کند.

در JS، هر *کاراکتر* یک code-unit (۱۶ بیت) است، با مقدار code-point در یا زیر `65535`. ویژگی `length` رشته همیشه تعداد code-unitها در مقدار رشته را می‌شمارد، نه code-pointها. یک code-unit ممکن است خودش یک کاراکتر تکی را نشان دهد، یا بخشی از surrogate pair باشد، یا با نماد *combining* مجاور ترکیب شود، یا بخشی از grapheme cluster باشد. بنابراین، `length` با مفهوم معمول شمارش کاراکترها/graphemeهای بصری مطابقت ندارد.

برای نزدیک‌تر شدن به *grapheme length* مورد انتظار/شهودی برای رشته، مقدار رشته ابتدا باید با `normalize("NFC")` نرمال شود (ببینید «Normalizing Unicode» در فصل ۱) تا هر code-unit *composed* (در صورت امکان) تولید شود، در صورتی که کاراکترها در اصل *decomposed* به‌صورت code-unitهای جدا ذخیره شده باشند.

مثلاً:

```js
favoriteItem = "teléfono";
favoriteItem.length;            // 9 -- uh oh!

favoriteItem = favoriteItem.normalize("NFC");
favoriteItem.length;            // 8 -- phew!
```

متأسفانه، همان‌طور که در فصل ۱ دیدیم، هنوز امکان کاراکترهای با code-point بزرگ‌تر از `65535` داریم و بنابراین به surrogate pair برای نمایش نیاز است. چنین کاراکترهایی در `length` دو برابر شمارش می‌شوند:

```js
// "☎" === "\u260E"
oldTelephone = "☎";
oldTelephone.length;            // 1

// "📱" === "\u{1F4F1}" === "\uD83D\uDCF1"
cellphone = "📱";
cellphone.length;               // 2 -- oops!
```

پس چه کنیم؟

یک راه‌حل استفاده از تکرار کاراکتر (از طریق عملگر `...`) است همان‌طور که در بخش قبلی دیدیم، چون به‌طور خودکار هر کاراکتر ترکیب‌شده از surrogate pair را برمی‌گرداند:

```js
cellphone = "📱";
cellphone.length;               // 2 -- oops!
[ ...cellphone ].length;        // 1 -- phew!
```

اما متأسفانه، grapheme clusterها (همان‌طور که در فصل ۱ توضیح داده شد) چرخ دیگری به محاسبهٔ طول رشته می‌اندازند. مثلاً، اگر emoji thumbs down (`"\u{1F44E}"`) را بگیریم و modifier رنگ پوست medium-dark (`"\u{1F3FE}"`) را به آن اضافه کنیم:

```js
// "👎🏾" = "\u{1F44E}\u{1F3FE}"
thumbsDown = "👎🏾";

thumbsDown.length;              // 4 -- oops!
[ ...thumbsDown ].length;       // 2 -- oops!
```

همان‌طور که می‌بینید، این‌ها دو code-point متمایز (نه surrogate pair) هستند که به‌خاطر ترتیب و مجاورتشان، رندر Unicode کامپیوتر نماد thumbs-down را با رنگ پوست تیره‌تر از پیش‌فرض ترسیم می‌کند. طول رشتهٔ محاسبه‌شده بنابراین `2` است.

تکرار اکثر منطق رندر Unicode پیچیدهٔ پلتفرم برای تشخیص چنین خوشه‌هایی از code-pointها به‌عنوان یک «کاراکتر» برای شمارش طول لازم است. کتابخانه‌هایی وجود دارند که ادعا می‌کنند این کار را می‌کنند، اما لزوماً کامل نیستند و هزینهٔ سنگینی از نظر کد اضافی دارند.

| :--- |
| به‌عنوان کاربر توییتر، ممکن است انتظار داشته باشید بتوانید ۲۸۰ emoji thumbs-down را در یک توییت قرار دهید، چون مثل یک کاراکتر به‌نظر می‌رسد. توییتر `"👎"` (thumbs-down پیش‌فرض)، `"👎🏾"` (thumbs-down با رنگ پوست medium-dark) و حتی `"👩‍👩‍👦‍👦"` (grapheme cluster emoji خانوادگی) را هر کدام ۲ کاراکتر می‌شمارد، حتی اگر طول‌های رشتهٔ مربوطه (از نظر JS) `2`، `4` و `7` باشند؛ بنابراین، فقط نیمی از تعداد emojiها (۱۴۰ به‌جای ۲۸۰) در یک توییت جا می‌گیرند. در واقع، توییتر این تغییر را در ۲۰۱۸ برای یکسان‌سازی شمارش همهٔ کاراکترهای Unicode، با ۲ کاراکتر به ازای هر نماد، پیاده‌سازی کرد. [^TwitterUnicode] این تغییر خوشایندی برای کاربران توییتر بود، به‌ویژه کسانی که می‌خواهند از کاراکترهای emoji نمایندهٔ جنسیت، رنگ پوست و غیره استفاده کنند. با این حال، *کنجکاو* است که توییتر همهٔ نمادهای Unicode/emoji را هر کدام ۲ کاراکتر شمارش کرد، به‌جای شهودی‌تر ۱ کاراکتر (grapheme) هر کدام. |

شمارش *طول* رشته برای مطابقت با شهود انسانی ما کاری به‌طور قابل‌توجهی چالش‌برانگیز است، شاید بیشتر هنر تا علم. در بسیاری موارد می‌توانیم تقریب‌های قابل قبول بگیریم، اما موارد زیادی دیگر ممکن است برنامه‌هایمان را گیج کنند.

### بین‌المللی‌سازی (i18n) و بومی‌سازی (l10n)

برای پاسخ به نیاز فزایندهٔ برنامه‌های JS به عملکرد مطابق انتظار در هر زمینهٔ زبان/فرهنگ بین‌المللی، کمیتهٔ ECMAScript همچنین ECMAScript Internationalization API را منتشر می‌کند. [^INTLAPI]

برنامهٔ JS به‌طور پیش‌فرض بر اساس محیط اجرای برنامه (صفحهٔ مرورگر وب، نمونهٔ Node و غیره) به locale/زبان پیش‌فرض می‌رود. locale مؤثر بر مرتب‌سازی (و مقایسهٔ مقادیر)، قالب‌بندی و چند رفتار فرض‌شدهٔ دیگر تأثیر می‌گذارد. چنین رفتارهای تغییر‌یافته شاید با رشته‌ها کمی واضح‌تر باشند، اما با اعداد (و تاریخ‌ها!) هم دیده می‌شوند.

اما کاراکترهای رشته هم می‌توانند اطلاعات زبان/locale در خود داشته باشند که بر پیش‌فرض محیط اولویت دارد. اگر کاراکتر رشته از نظر زبان/locale مبهم/مشترک باشد (مثل `"a"`)، تنظیم پیش‌فرض محیط استفاده می‌شود.

بسته به محتوای رشته، ممکن است از چپ‌به‌راست (LTR) یا راست‌به‌چپ (RTL) تفسیر شود. بنابراین، بسیاری از متدهای رشته که بعداً پوشش می‌دهیم از توصیف‌گرهای منطقی در نام‌هایشان استفاده می‌کنند، مثل «start»، «end»، «begin»، «last»، به‌جای اصطلاحات جهت‌دار مثل «left» و «right».

مثلاً، عبری و عربی هر دو زبان‌های RTL رایج هستند:

```js
hebrewHello = "\u{5e9}\u{5dc}\u{5d5}\u{5dd}";

console.log(hebrewHello);                       // שלום
```

توجه کنید اولین کاراکتر فهرست‌شده در string literal (`"\u{5e9}"`) در واقع راست‌ترین کاراکتر هنگام رندر رشته است؟

حتی اگر عبری زبان RTL است، کاراکترها را در string literal به ترتیب معکوس (RTL) آن‌طور که باید رندر شوند تایپ نمی‌کنید. کاراکترها را به ترتیب منطقی وارد می‌کنید، جایی که موقعیت `0` اولین کاراکتر، موقعیت `1` دومین کاراکتر و غیره است. لایهٔ رندر جایی است که کاراکترهای RTL معکوس می‌شوند تا به ترتیب صحیح نشان داده شوند.

این یعنی اگر `hebrewHello[0]` (یا `hebrewHello.charAt(0)`) را دسترسی کنید — برای گرفتن کاراکتر در موقعیت `0` — `"ש"` می‌گیرید چون منطقاً اولین کاراکتر رشته است، نه `"ם"` (منطقاً آخرین کاراکتر رشته). دسترسی ایندکس-موقعیتی ترتیب منطقی را دنبال می‌کند، نه موقعیت رندر‌شده.

همان مثال در زبان RTL دیگر، عربی:

```js
arabicHello = "\u{631}\u{62d}\u{628}\u{627}";

console.log(arabicHello);                       // رحبا

console.log(arabicHello[0]);                    // ر
```

برنامه‌های JS می‌توانند با APIهای مختلف `Intl` مثل `Intl.Collator` زبان/locale خاصی را اعمال کنند: [^INTLCollator]

```js
germanStringSorter = new Intl.Collator("de");

listOfGermanWords = [ /* .. */ ];

germanStringSorter.compare("Hallo","Welt");
// -1 (or negative number)

// examples adapted from MDN:
//
germanStringSorter.compare("Z","z");
// 1 (or positive number)

caseFirstSorter = new Intl.Collator("de",{ caseFirst: "upper", });
caseFirstSorter.compare("Z","z");
// -1 (or negative number)
```

رشته‌های چندکلمه‌ای را می‌توان با `Intl.Segmenter` تقسیم کرد: [^INTLSegmenter]

```js
arabicHelloWorld = "\u{645}\u{631}\u{62d}\u{628}\u{627} \
\u{628}\u{627}\u{644}\u{639}\u{627}\u{644}\u{645}";

console.log(arabicHelloWorld);      // مرحبا بالعالم

arabicSegmenter = new Intl.Segmenter("ar",{ granularity: "word" });

for (
    let { segment: word, isWordLike } of
    arabicSegmenter.segment(arabicHelloWorld)
) {
    if (isWordLike) {
        console.log(word);
    }
}
// مرحبا
//لعالم
```

| NOTE: |
| :--- |
| متد `segment(..)` (از نمونه‌های `Intl.Segmenter`) یک iterator استاندارد JS برمی‌گرداند که حلقهٔ `for..of` اینجا مصرف می‌کند. بیشتر دربارهٔ پروتکل‌های تکرار در عنوان «Sync & Async» این مجموعه. |

### مقایسهٔ رشته

مقادیر رشته را می‌توان با مقادیر رشتهٔ دیگر مقایسه کرد (هم برای برابری و هم ترتیب رابطه‌ای)، با استفاده از عملگرهای داخلی مختلف. مهم است به یاد داشته باشید چنین مقایسه‌هایی به محتوای واقعی رشته حساس هستند، از جمله به‌ویژه code-pointهای زیربنایی از کاراکترهای Unicode غیر-BMP.

هم مقایسهٔ برابری و هم رابطه‌ای برای هر کاراکتری که حروف بزرگ و کوچک به‌خوبی تعریف شده‌اند حساس به حروف هستند. برای مقایسهٔ بدون حساسیت به حروف، ابتدا حروف هر دو مقدار را نرمال کنید (با `toUpperCase()` یا `toLowerCase()`).

#### برابری رشته

عملگرهای `===` و `==` (همراه با معکوس‌هایشان `!==` و `!=`) رایج‌ترین راه مقایسهٔ برابری برای مقادیر اولیه، از جمله مقادیر رشته، هستند:

```js
"my name" === "my n\x61me";               // true

"my name" !== String.raw`my n\x61me`;     // true
```

عملگر `===`[^StrictEquality] — که اغلب «strict equality» نامیده می‌شود — ابتدا بررسی می‌کند آیا نوع‌ها مطابقت دارند، و اگر نه، بلافاصله `false` برمی‌گرداند. اگر نوع‌ها مطابقت کنند، بررسی می‌کند آیا مقادیر یکسان هستند؛ برای رشته‌ها، این مقایسهٔ هر-code-unit از ابتدا تا انتها است.

علیرغم نام «strict»، ظرافت‌هایی در `===` وجود دارد (مثل رفتار `-0` و `NaN`)، اما بعداً پوشش می‌دهیم.

##### برابری اجباری

در مقابل، عملگر `==`[^LooseEquality] — که اغلب «loose equality» نامیده می‌شود — *coercive equality* انجام می‌دهد: اگر نوع‌های مقدار دو عملوند مطابقت نکنند، `==` ابتدا یک یا هر دو عملوند را تا وقتی نوع‌های مقدار *مطابقت کنند* اجبار می‌کند، و سپس مقایسه را به‌صورت داخلی به `===` می‌سپارد.

Coercion موضوعی بسیار مهم است — بخش ذاتی سیستم انواع JS، یکی از سه ستون زبان — اما اینجا در این فصل فقط به‌طور خلاصه معرفی می‌کنیم و بعداً به‌تفصیل دوباره بررسی می‌کنیم.

| NOTE: |
| :--- |
| ممکن است توضیح نقل‌شده اما نادرست شنیده باشید که تفاوت `==` و `===` این است که `==` مقادیر را مقایسه می‌کند در حالی که `===` هم مقادیر و هم نوع‌ها را مقایسه می‌کند. درست نیست، و می‌توانید خودتان مشخصات را بخوانید تا تأیید کنید — هر دو الگوریتم مشخصات `isStrictlyEqual(..)` و `isLooselyEqual(..)` به‌عنوان پاورقی در پاراگراف‌های قبلی لینک شده‌اند. خلاصه: هر دو `==` و `===` از نوع عملوندها آگاه و به آن حساس هستند. اگر نوع عملوندها یکسان باشد، هر دو عملگر دقیقاً همان کار را می‌کنند؛ اگر نوع‌ها متفاوت باشند، `==` coercion را تا مطابقت نوع‌ها اعمال می‌کند، در حالی که `===` بلافاصله `false` برمی‌گرداند. |

برای توسعه‌دهندگان بسیار رایج است که ادعا کنند عملگر `==` گیج‌کننده و بدون غافلگیری سخت استفاده است (بنابراین ترجیح تقریباً جهانی برای `===`). فکر می‌کنم کاملاً بی‌اساس است، و در واقع، توسعه‌دهندگان JS باید به `==` پیش‌فرض کنند (و در صورت امکان از `===` اجتناب کنند). اما برای پشتیبانی از چنین ادعای بحث‌برانگیزی به بحث بیشتری نیاز داریم؛ اعتراضات خود را تا دوباره بررسی نگه دارید.

فعلاً، برای کسب شهود دربارهٔ ماهیت اجباری `==`، روشن‌کننده‌ترین مشاهده این است که اگر نوع‌ها مطابقت نکنند، `==` *ترجیح می‌دهد* مقایسهٔ عددی. یعنی سعی می‌کند هر دو عملوند را به عدد تبدیل کند و سپس بررسی برابری انجام دهد (مثل `===`).

پس، در ارتباط با بحث فعلی ما، برابری رشتهٔ واقعی *فقط* قابل بررسی است اگر هر دو عملوند از قبل رشته باشند:

```js
// actual string equality check (via === internally):
"42" == "42";           // true
```

`==` واقعاً خودش بررسی برابری رشته انجام نمی‌دهد. اگر نوع‌های مقدار عملوند هر دو رشته باشند، `==` فقط مقایسه را به `===` می‌سپارد. اگر هر دو رشته نباشند، مراحل اجباری در `==` مقایسه را به عددی به‌جای رشته کاهش می‌دهد:

```js
// numeric (not string!) equality check:
42 == "42";             // true
```

برابری عددی را بعداً در این فصل پوشش می‌دهیم.

##### برابری *واقعاً* Strict

علاوه بر `==` و `===`، JS ابزار `Object.is(..)` را ارائه می‌دهد که اگر هر دو آرگومان *دقیقاً یکسان* باشند `true` برمی‌گرداند و در غیر این صورت `false` (بدون استثنا یا ظرافت):

```js
Object.is("42",42);             // false

Object.is("42","\x34\x32");     // true
```

چون `===` یک `=` به انتهای `==` اضافه می‌کند تا رفتارش strict‌تر شود، نیم‌شوخی می‌گویم ابزار `Object.is(..)` مثل عملگر `====` (یک `=` چهارم اضافه‌شده) است، برای نوع بررسی برابری واقعاً-واقعاً-strict-بدون-استثنا!

با این حال، `===` (و `==` به‌خاطر تفویض داخلی‌اش به `===`) *بسیار قابل‌پیش‌بینی* هستند، بدون استثناهای عجیب، وقتی نوبت به مقایسهٔ دو مقدار واقعاً-از-قبل-رشته می‌رسد. به‌شدت توصیه می‌کنم برای چنین بررسی‌هایی از `==` (یا `===`) استفاده کنید و `Object.is(..)` را برای موارد خاص (که عددی هستند) نگه دارید.

#### مقایسه‌های رابطه‌ای رشته

علاوه بر بررسی برابری بین رشته‌ها، JS مقایسه‌های رابطه‌ای بین مقادیر اولیه مثل رشته‌ها را پشتیبانی می‌کند: `<`، `<=`، `>` و `>=`.

عملیات `<` (کمتر از) و `>` (بیشتر از) دو مقدار رشته را به‌صورت واژه‌نامه‌ای مقایسه می‌کنند — مثل مرتب‌سازی کلمات در فرهنگ لغت — و بنابراین باید نسبتاً خودتوضیح باشند:

```js
"hello" < "world";          // true
```

| NOTE: |
| :--- |
| همان‌طور که قبلاً ذکر شد، برنامهٔ JS در حال اجرا locale پیش‌فرض دارد و این عملگرها طبق آن locale مقایسه می‌کنند. |

مثل `==`، عملگرهای `<` و `>` از نظر عددی اجباری هستند. هر مقدار غیرعددی به عدد اجبار می‌شود. پس تنها راه انجام مقایسهٔ رابطه‌ای با رشته‌ها اطمینان از این است که هر دو عملوند از قبل مقادیر رشته باشند.

شاید کمی غافل‌گیرکننده، `<` و `>` معادل strict-comparison ندارند، آن‌طور که `===` از coercion `==` اجتناب می‌کند. این عملگرها همیشه اجباری هستند (وقتی نوع‌ها مطابقت نکنند) و در JS راهی برای اجتناب از آن نیست.

پس وقتی هر دو مقدار رشته‌های *به‌ظاهر عددی* باشند چه می‌شود؟

```js
"100" < "11";               // true
```

از نظر عددی، البته، `100` *نباید* کمتر از `11` باشد.

اما مقایسه‌های رابطه‌ای بین دو رشته از ترتیب واژه‌نامه‌ای استفاده می‌کنند. پس کاراکتر دوم `"0"` (در `"100"`) کمتر از کاراکتر دوم `"1"` (در `"11"`) است، و بنابراین `"100"` در *فرهنگ لغت* قبل از `"11"` مرتب می‌شود. عملگرهای رابطه‌ای فقط اگر نوع عملوندها از قبل رشته نباشند به عدد اجبار می‌کنند.

عملگرهای `<=` (کمتر-یا-مساوی) و `>=` (بیشتر-یا-مساوی) در واقع میانبری برای بررسی مرکب هستند.

```js
"hello" <= "hello";                             // true
("hello" < "hello") || ("hello" == "hello");    // true

"hello" >= "hello";                             // true
("hello" > "hello") || ("hello" == "hello");    // true
```

| NOTE: |
| :--- |
| ظرافت جالب مشخصات: JS در واقع عملیات بیشتر-از (برای `>`) یا بیشتر-یا-مساوی (برای `>=`) زیربنایی را تعریف نمی‌کند. در عوض، آن‌ها را با معکوس کردن آرگومان‌ها به معکوس‌های کمتر-از تعریف می‌کند. پس `x > y` توسط JS اساساً به‌عنوان `y <= x` و `x >= y` اساساً به‌عنوان `y < x` رفتار می‌شود. پس JS فقط باید مشخص کند `<` و `==` چطور کار می‌کنند و بنابراین `>` و `>=` را رایگان می‌گیرد! |

##### مقایسه‌های رابطه‌ای آگاه از Locale

همان‌طور که لحظه‌ای پیش ذکر کردم، عملگرهای رابطه‌ای locale مؤثر فعلی را فرض و استفاده می‌کنند. با این حال، گاهی می‌تواند مفید باشد locale خاصی را برای مقایسه‌ها اعمال کنیم (مثل هنگام مرتب‌سازی لیست رشته‌ها).

JS متد `localeCompare(..)` روی رشته‌های JS برای این منظور ارائه می‌دهد:

```js
"hello".localeCompare("world");
// -1 (or negative number)

"world".localeCompare("hello","en");
// 1 (or positive number)

"hello".localeCompare("hello","en",{ ignorePunctuation: true });
// 0

// examples from MDN:
//
// in German, ä sorts before z
"ä".localeCompare("z","de");
// -1 (or negative number) // a negative value

// in Swedish, ä sorts after z
"ä".localeCompare("z","sv");
// 1 (or positive number)
```

آرگومان‌های دوم و سوم اختیاری `localeCompare(..)` کنترل می‌کنند کدام locale استفاده شود، از طریق APIٔ `Intl.Collator`[^INTLCollatorApi]، همان‌طور که قبلاً پوشش داده شد.

ممکن است هنگام مرتب‌سازی آرایهٔ رشته‌ها از `localeCompare(..)` استفاده کنید:

```js
studentNames = [
    "Lisa",
    "Kyle",
    "Jason"
];

// Array::sort() mutates the array in place
studentNames.sort(function alphabetizeNames(name1,name2){
    return name1.localeCompare(name2);
});

studentNames;
// [ "Jason", "Kyle", "Lisa" ]
```

اما همان‌طور که قبلاً بحث شد، راه ساده‌تر (و کمی کارآمدتر هنگام مرتب‌سازی رشته‌های زیاد) استفادهٔ مستقیم از `Intl.Collator` است:

```js
studentNames = [
    "Lisa",
    "Kyle",
    "Jason"
];

nameSorter = new Intl.Collator("en");

// Array::sort() mutates the array in place
studentNames.sort(nameSorter.compare);

studentNames;
// [ "Jason", "Kyle", "Lisa" ]
```

### الحاق رشته

دو یا چند مقدار رشته را می‌توان با عملگر `+` به مقدار رشتهٔ جدید الحاق (ترکیب) کرد:

```js
greeting = "Hello, " + "Kyle!";

greeting;               // Hello, Kyle!
```

عملگر `+` اگر هر یک از دو عملوند (مقادیر در سمت چپ یا راست عملگر) از قبل رشته باشد (حتی رشتهٔ خالی `""`) به‌عنوان الحاق رشته عمل می‌کند.

اگر یک عملوند رشته و دیگری نباشد، آن که رشته نیست برای الحاق به نمایش رشته‌اش اجبار می‌شود:

```js
userCount = 7;

status = "There are " + userCount + " users online";

status;         // There are 7 users online
```

الحاق رشته از این نوع اساساً درج داده در رشته است، که هدف اصلی template literalهاست (ببینید فصل ۱). پس کد زیر نتیجهٔ یکسان دارد اما عموماً رویکرد ترجیح‌داده‌شده‌تر است:

```js
userCount = 7;

status = `There are ${userCount} users online`;

status;         // There are 7 users online
```

گزینه‌های دیگر برای الحاق رشته شامل `"one".concat("two","three")` و `[ "one", "two", "three" ].join("")` هستند، اما این رویکردها فقط وقتی ترجیح‌داده می‌شوند که تعداد رشته‌های الحاق‌شونده به شرایط/محاسبهٔ زمان اجرا وابسته باشد. اگر رشته مجموعهٔ ثابت/شناخته‌شدهٔ محتوا دارد، مثل بالا، template literalها گزینهٔ بهتر هستند.

### متدهای مقدار رشته

مقادیر رشته مجموعهٔ زیادی متدهای خاص رشته (به‌عنوان ویژگی) ارائه می‌دهند:

* `charAt(..)`: مقدار رشتهٔ جدید در ایندکس عددی تولید می‌کند، شبیه `[ .. ]`؛ برخلاف `[ .. ]`، نتیجه همیشه رشته است، یا کاراکتر در موقعیت `0` (اگر عدد معتبر خارج از محدودهٔ ایندکس‌ها) یا رشتهٔ خالی `""` (اگر ایندکس گم/نامعتبر باشد)

* `at(..)` شبیه `charAt(..)` است، اما ایندکس‌های منفی از انتهای رشته به عقب می‌شمارند

* `charCodeAt(..)`: code-unit عددی (ببینید «JS Character Encodings» در فصل ۱) در ایندکس مشخص‌شده را برمی‌گرداند

* `codePointAt(..)`: کل code-point شروع‌شده در ایندکس مشخص‌شده را برمی‌گرداند؛ اگر surrogate pair آنجا پیدا شود، کل کاراکتر (code-point) برگردانده می‌شود

* `substr(..)` / `substring(..)` / `slice(..)`: مقدار رشتهٔ جدیدی تولید می‌کنند که محدوده‌ای از کاراکترها از رشتهٔ اصلی را نشان می‌دهد؛ در نحوهٔ مشخص یا تعیین ایندکس‌های شروع/پایان محدوده تفاوت دارند

* `toUpperCase()`: مقدار رشتهٔ جدیدی تولید می‌کند که همهٔ کاراکترها بزرگ هستند

* `toLowerCase()`: مقدار رشتهٔ جدیدی تولید می‌کند که همهٔ کاراکترها کوچک هستند

* `toLocaleUpperCase()` / `toLocaleLowerCase()`: از نگاشت‌های locale برای عملیات بزرگ یا کوچک استفاده می‌کنند

* `concat(..)`: مقدار رشتهٔ جدیدی تولید می‌کند که الحاق رشتهٔ اصلی و همهٔ آرگومان‌های مقدار رشتهٔ فرستاده‌شده است

* `indexOf(..)`: آرگومان مقدار رشته را در رشتهٔ اصلی جستجو می‌کند، اختیاری از موقعیت مشخص‌شده در آرگومان دوم؛ ایندکس موقعیت بر پایهٔ `0` اگر پیدا شود برمی‌گرداند، یا `-1` اگر پیدا نشود

* `lastIndexOf(..)`: مثل `indexOf(..)` اما از انتهای رشته (راست در localeهای LTR، چپ در localeهای RTL)

* `includes(..)`: شبیه `indexOf(..)` اما نتیجهٔ بولی برمی‌گرداند

* `search(..)`: شبیه `indexOf(..)` اما با تطابق regular-expression مشخص‌شده

* `trimStart()` / `trimEnd()` / `trim()`: مقدار رشتهٔ جدیدی با حذف فاصلهٔ خالی از ابتدا (چپ در LTR، راست در RTL)، یا انتها (راست در LTR، چپ در RTL)، یا هر دو تولید می‌کند

* `repeat(..)`: رشتهٔ جدیدی با تکرار مقدار رشتهٔ اصلی به تعداد مشخص‌شده تولید می‌کند

* `split(..)`: آرایه‌ای از مقادیر رشته به‌صورت تقسیم در مرزهای رشته یا regular-expression مشخص‌شده تولید می‌کند

* `padStart(..)` / `padEnd(..)`: مقدار رشتهٔ جدیدی با padding (پیش‌فرض فاصلهٔ خالی `" "`، اما قابل بازنویسی) اعمال‌شده به ابتدا یا انتها تولید می‌کند، طوری که نتیجهٔ رشتهٔ نهایی حداقل طول مشخص‌شده باشد

* `startsWith(..)` / `endsWith(..)`: ابتدا یا انتهای رشتهٔ اصلی را برای آرگومان مقدار رشته بررسی می‌کند؛ نتیجهٔ بولی برمی‌گرداند

* `match(..)` / `matchAll(..)`: نتیجهٔ تطابق regular-expression شبیه آرایه علیه رشتهٔ اصلی برمی‌گرداند

* `replace(..)`: رشتهٔ جدیدی با جایگزینی از رشتهٔ اصلی، یک یا چند رخداد تطابق regular-expression مشخص‌شده برمی‌گرداند

* `normalize(..)`: رشتهٔ جدیدی با نرمال‌سازی Unicode (ببینید «Unicode Normalization» در فصل ۱) انجام‌شده روی محتوا تولید می‌کند

* `localeCompare(..)`: تابعی که دو رشته را طبق locale فعلی مقایسه می‌کند (مفید برای مرتب‌سازی)؛ عدد منفی (معمولاً `-1` اما تضمین‌نشده) اگر مقدار رشتهٔ اصلی واژه‌نامه‌ای قبل از مقدار رشتهٔ آرگومان بیاید، عدد مثبت (معمولاً `1` اما تضمین‌نشده) اگر بعد بیاید، و `0` اگر دو رشته یکسان باشند برمی‌گرداند

* `anchor()`، `big()`، `blink()`، `bold()`، `fixed()`، `fontcolor()`، `fontsize()`، `italics()`، `link()`، `small()`، `strike()`، `sub()` و `sup()`: از نظر تاریخی برای تولید قطعات رشتهٔ HTML مفید بودند؛ الان منسوخ شده و باید اجتناب شوند

| WARNING: |
| :--- |
| بسیاری از متدهای توصیف‌شدهٔ بالا به ایندکس‌های موقعیت تکیه می‌کنند. همان‌طور که قبلاً در بخش «Length Computation» ذکر شد، این موقعیت‌ها به محتوای داخلی مقدار رشته وابسته‌اند، یعنی اگر کاراکتر Unicode گسترش‌یافته وجود داشته باشد و دو اسلات code-unit اشغال کند، دو موقعیت ایندکس به‌جای یکی شمارش می‌شود. عدم توجه به code-unitهای *decomposed*، surrogate pairها و grapheme clusterها منبع رایج باگ در پردازش رشتهٔ JS است. |

این متدهای رشته را می‌توان مستقیماً روی مقدار literal یا متغیر/ویژگی نگه‌دارندهٔ مقدار رشته فراخوانی کرد. در صورت امکان، مقدار رشتهٔ جدید تولید می‌کنند به‌جای تغییر مقدار رشتهٔ موجود (چون رشته‌ها immutable هستند):

```js
"all these letters".toUpperCase();      // ALL THESE LETTERS

greeting = "Hello!";
greeting.repeat(2);                     // Hello!Hello!
greeting;                               // Hello!
```

### کمک‌کننده‌های استاتیک `String`

توابع کمکی رشتهٔ زیر مستقیماً روی شیء `String` ارائه می‌شوند، به‌جای به‌عنوان متد روی مقادیر رشتهٔ تکی:

* `String.fromCharCode(..)` / `String.fromCodePoint(..)`: رشته از یک یا چند آرگومان نشان‌دهندهٔ code-unitها (`fromCharCode(..)`) یا کل code-pointها (`fromCodePoint(..)`) تولید می‌کنند

* `String.raw(..)`: تابع template-tag پیش‌فرض که اجازهٔ درج روی template literal می‌دهد اما از تجزیهٔ character escape sequenceها جلوگیری می‌کند، پس در کاراکترهای ورودی *raw* جداگانه از literal باقی می‌مانند

علاوه بر این، اکثر مقادیر (به‌ویژه primitives) را می‌توان با فرستادن به تابع `String(..)` (بدون کلمهٔ کلیدی `new`) صریح به معادل رشته‌شان اجبار کرد. مثلاً:

```js
String(true);           // "true"
String(42);             // "42"
String(Infinity);       // "Infinity"
String(undefined);      // "undefined"
```

جزئیات بسیار بیشتری دربارهٔ چنین type coercionها در فصل بعدی پوشش می‌دهیم.
