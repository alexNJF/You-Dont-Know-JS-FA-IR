## مقادیر رشته

نوع `string` هر مقداری را شامل می‌شود که مجموعه‌ای از یک یا چند کاراکتر است، محدودشده (از هر دو طرف) با کاراکترهای نقل‌قول:

```js
myName = "Kyle";
```

JS یک کاراکتر تکی را به‌عنوان نوع متفاوت متمایز نمی‌کند؛ `"a"` رشته است درست مثل `"abc"`.

رشته‌ها می‌توانند با نقل‌قول دوتایی (`"`)، نقل‌قول تکی (`'`) یا بک‌تیک (`` ` ``) محدود شوند. محدودکنندهٔ پایانی باید همیشه با محدودکنندهٔ شروع مطابقت کند.

رشته‌ها طول ذاتی دارند که با تعداد code-pointها — در واقع code-unitها، بیشتر در این مورد — مطابقت دارد.

```js
myName = "Kyle";

myName.length;      // 4
```

این لزوماً با تعداد کاراکترهای قابل‌مشاهده بین محدودکننده‌های شروع و پایان (یعنی string literal) مطابقت ندارد. گاهی می‌تواند کمی گیج‌کننده باشد تفاوت بین string literal و مقدار رشتهٔ زیربنایی را روشن نگه دارید، پس دقت کنید.

| NOTE: |
| :--- |
| محاسبهٔ طول رشته‌ها را به‌تفصیل در فصل ۲ پوشش می‌دهیم. |

### رمزگذاری کاراکتر JS

JS از چه نوع رمزگذاری کاراکتری برای کاراکترهای رشته استفاده می‌کند؟

احتمالاً از «Unicode» شنیده‌اید و شاید حتی «UTF-8» (۸ بیتی) یا «UTF-16» (۱۶ بیتی). اگر مثل من هستید (قبل از تحقیقی که برای نوشتن این متن انجام دادم)، شاید فقط دست تکان داده و تصمیم گرفته‌اید همین کافی است دربارهٔ رمزگذاری کاراکتر در رشته‌های JS.

اما... نیست. حتی نزدیک هم نیست.

معلوم می‌شود باید نحوهٔ کار جنبه‌های مختلف Unicode را درک کنید، و حتی مفاهیم UCS-2 (مجموعه کاراکتر جهانی ۲ بایتی) را در نظر بگیرید که شبیه UTF-16 است اما کاملاً یکی نیست. [^UTFUCS]

Unicode تمام «کاراکتر»هایی را که می‌توانیم به‌طور جهانی در برنامه‌های کامپیوتری نمایش دهیم تعریف می‌کند، با اختصاص عدد مشخصی به هر کدام به‌نام code-pointها. این اعداد از `0` تا حداکثر `1114111` (`10FFFF` در هگزادسیمال) هستند.

نماد استاندارد برای کاراکترهای Unicode `U+` به‌دنبال ۴ تا ۶ کاراکتر هگزادسیمال است. مثلاً، `❤` (نماد قلب) code-point `10084` (`2764` در هگزادسیمال) است و بنابراین با `U+2764` نشان داده می‌شود.

اولین گروه ۶۵٬۵۳۵ code point در Unicode BMP (صفحهٔ چندزبانهٔ پایه) نامیده می‌شود. همهٔ آن‌ها را می‌توان با ۱۶ بیت (۲ بایت) نمایش داد. هنگام نمایش کاراکترهای Unicode از BMP، نسبتاً ساده است چون می‌توانند *جور* در کاراکترهای UTF-16 تکی JS قرار بگیرند.

بقیهٔ code pointها در ۱۶ صفحهٔ به‌اصطلاح «مکمل» یا «آسمانی» گروه‌بندی شده‌اند. این code-pointها برای نمایش به بیش از ۱۶ بیت نیاز دارند — دقیقاً ۲۱ بیت — پس هنگام نمایش کاراکترهای گسترش‌یافته/مکمل بالای BMP، JS در واقع این code-pointها را به‌صورت جفت دو code unit مجاور ۱۶ بیتی ذخیره می‌کند، به‌نام *surrogate halves* (یا *surrogate pairs*).

مثلاً، code point یونیکد `127878` (هگزادسیمال `1F386`) `🎆` (نماد آتش‌بازی) است. JS این را در مقدار رشته به‌صورت دو code unit surrogate-halve ذخیره می‌کند: `U+D83C` و `U+DF86`. به خاطر داشته باشید این دو بخش کاراکتر کل *به‌تنهایی* معتبر نیستند؛ فقط وقتی معتبر/معنادار هستند که بلافاصله کنار هم قرار بگیرند.

این بر طول رشته‌ها تأثیر دارد، چون یک کاراکتر قابل‌مشاهده مثل نماد آتش‌بازی `🎆`، وقتی در رشتهٔ JS است، برای طول رشته به‌عنوان ۲ کاراکتر شمارش می‌شود!

دوباره به کاراکترهای Unicode می‌پردازیم و چالش‌های محاسبهٔ طول رشته را در فصل ۲ پوشش می‌دهیم.

### توالی‌های فرار

اگر `"` یا `'` برای محدود کردن string literal استفاده شود، محتوا فقط برای *character-escape sequences* تجزیه می‌شود: `\` به‌دنبال یک یا چند کاراکتری که JS با معنای ویژه تشخیص و تجزیه می‌کند. هر کاراکتر دیگر در رشته که به‌عنوان escape-sequence تجزیه نشود (تک‌کاراکتری یا چندکاراکتری)، همان‌طور که هست در مقدار رشته درج می‌شود.

برای توالی‌های فرار تک‌کاراکتری، کاراکترهای زیر بعد از `\` شناخته می‌شوند: `b`، `f`، `n`، `r`، `t`، `v`، `0`، `'`، `"` و `\`. مثلاً `\n` یعنی خط جدید، `\t` یعنی تب، و غیره.

اگر `\` با کاراکتر دیگری (به‌جز `x` و `u` — در پایین توضیح داده شده) همراه شود، مثلاً `\k`، آن توالی به‌عنوان `\` فرار غیرضروری تفسیر می‌شود که حذف می‌شود و فقط خود کاراکتر تحت‌اللفظی (`k`) می‌ماند.

برای قرار دادن `"` در وسط string literal محدودشده با `"`، از توالی فرار `\"` استفاده کنید. به‌طور مشابه، اگر کاراکتر `'` را در وسط string literal محدودشده با `'` قرار می‌دهید، از توالی فرار `\'` استفاده کنید. در مقابل، `'` *نیازی* به فرار داخل رشتهٔ محدودشده با `"` ندارد، و برعکس.

```js
myTitle = "Kyle Simpson (aka, \"getify\"), former O'Reilly author";

console.log(myTitle);
// Kyle Simpson (aka, "getify"), former O'Reilly author
```

در متن، اسلش رو به جلو `/` رایج‌تر است. اما گاهی به اسلش رو به عقب `\` نیاز دارید. برای قرار دادن کاراکتر تحت‌اللفظی `\` بدون اینکه به‌عنوان شروع character-escape sequence عمل کند، از `\\` (دو بک‌اسلش) استفاده کنید.

پس... `\\\` (سه بک‌اسلش) در رشته چطور تجزیه می‌شود؟ دو `\` اول یک توالی فرار `\\` می‌شوند و در نتیجه فقط یک کاراکتر `\` در مقدار رشته درج می‌شود، و `\` باقی‌مانده هر کاراکتری که بلافاصله بعدش می‌آید را فرار می‌کند.

یک جا که بک‌اسلش‌ها رایج ظاهر می‌شوند مسیرهای فایل ویندوز است که از جداکنندهٔ `\` به‌جای `/` سبک linux/unix استفاده می‌کنند:

```js
windowsFontsPath =
    "C:\\Windows\\Fonts\\";

console.log(windowsFontsPath);
// C:\Windows\Fonts\"
```

| TIP: |
| :--- |
| چهار بک‌اسلش `\\\\` در string literal چطور؟ خب، فقط دو توالی فرار `\\` کنار هم است، پس دو بک‌اسلش مجاور (`\\`) در مقدار رشتهٔ زیربنایی نتیجه می‌دهد. شاید الگوی قانون فرد/زوج را تشخیص دهید. پس باید بتوانید هر تعداد فرد (`\\\\\`، `\\\\\\\\\`، و غیره) یا زوج (`\\\\\\`، `\\\\\\\\\\`، و غیره) بک‌اسلش در string literal را رمزگشایی کنید. |

#### ادامهٔ خط

کاراکتر `\` به‌دنبال کاراکتر خط جدید واقعی (نه فقط تحت‌اللفظی `n`) حالت خاصی است و چیزی به‌نام line-continuation ایجاد می‌کند:

```js
greeting = "Hello \
Friends!";

console.log(greeting);
// Hello Friends!
```

همان‌طور که می‌بینید، خط جدید در انتهای خط `greeting = ` بلافاصله با `\` قبلش است که اجازه می‌دهد این string literal به خط بعدی ادامه یابد. بدون `\` فرارکننده قبلش، خط جدید — خط جدید واقعی، نه توالی فرار کاراکتر `\n` — ظاهر شدن در string literal محدودشده با `"` یا `'` در واقع خطای تجزیهٔ نحو JS ایجاد می‌کند.

چون `\` انتهای خط خط جدید را به line continuation تبدیل می‌کند، کاراکتر خط جدید از رشته حذف می‌شود، همان‌طور که خروجی `console.log(..)` نشان می‌دهد.

| NOTE: |
| :--- |
| این ویژگی line-continuation اغلب «multi-line strings» نامیده می‌شود، اما فکر می‌کنم برچسب گیج‌کننده‌ای است. همان‌طور که می‌بینید، خود مقدار رشته چند خط ندارد، فقط از طریق line continuationها در چند خط تعریف شده. رشتهٔ چندخطی واقعاً چند خط در مقدار زیربنایی دارد. این موضوع را بعداً در این فصل هنگام پوشش Template Literals دوباره بررسی می‌کنیم. |

### فرارهای چندکاراکتری

توالی‌های فرار چندکاراکتری ممکن است هگزادسیمال یا یونیکد باشند.

توالی‌های فرار هگزادسیمال برای رمزگذاری هر یک از کاراکترهای پایهٔ ASCII (کدهای ۰–۲۵۵) استفاده می‌شوند و شبیه `\x` به‌دنبال دقیقاً دو کاراکتر هگزادسیمال (`0-9` و `a-f` / `A-F` — بدون حساسیت به حروف) هستند. مثلاً، `A9` یا `a9` مقدار اعشاری `169` است که مطابق است با:

```js
copyright = "\xA9";  // or "\xa9"

console.log(copyright);     // ©
```

برای هر کاراکتر معمولی که می‌توان با صفحه‌کلید تایپ کرد، مثل `"a"`، معمولاً خوانا‌تر است خود کاراکتر تحت‌اللفظی را مشخص کنید، به‌جای نمایش هگزادسیمال مبهم‌تر:

```js
"a" === "\x61";             // true
```

#### یونیکد در رشته‌ها

توالی‌های فرار یونیکد به‌تنهایی می‌توانند هر کاراکتر از Unicode BMP را رمزگذاری کنند. شبیه `\u` به‌دنبال دقیقاً چهار کاراکتر هگزادسیمال هستند.

مثلاً، توالی فرار `\u00A9` (یا `\u00a9`) با همان نماد `©` مطابقت دارد، در حالی که `\u263A` (یا `\u263a`) با کاراکتر یونیکد با code-point `9786` مطابقت دارد: `☺` (نماد صورت خندان).

وقتی هر توالی فرار کاراکتر (صرف‌نظر از طول) تشخیص داده می‌شود، کاراکتر تکی که نشان می‌دهد در رشته درج می‌شود، نه کاراکترهای جداگانهٔ اصلی. پس در رشتهٔ `"\u263A"` فقط یک کاراکتر (خندان) هست، نه شش کاراکتر جداگانه.

اما همان‌طور که قبلاً توضیح داده شد، بسیاری از code-pointهای یونیکد بالای `65535` هستند. مثلاً، `1F4A9` (یا `1f4a9`) code-point اعشاری `128169` است که با نماد خنده‌دار `💩` (نماد مدفوع) مطابقت دارد.

اما `\u1F4A9` برای قرار دادن این کاراکتر در رشته کار نمی‌کند، چون به‌عنوان توالی فرار یونیکد `\u1F4A` تجزیه می‌شود، به‌دنبال کاراکتر تحت‌اللفظی `9`. برای رفع این محدودیت، تنوعی از توالی‌های فرار یونیکد معرفی شد که اجازهٔ تعداد دلخواه کاراکتر هگزادسیمال بعد از `\u` را می‌دهد، با احاطه کردن آن‌ها با آکلاد `{ .. }`:

```js
myReaction = "\u{1F4A9}";

console.log(myReaction);
// 💩
```

بحث قبلی کاراکترهای یونیکد گسترش‌یافته (غیر BMP) و *surrogate halves* را به یاد دارید؟ همان `💩` را می‌توان با دو code-unit صریح تعریف کرد که surrogate pair تشکیل می‌دهند:

```js
myReaction = "\uD83D\uDCA9";

console.log(myReaction);
// 💩
```

هر سه نمایش این کاراکتر یکسان به‌طور داخلی توسط JS یکسان ذخیره می‌شوند و غیرقابل تشخیص هستند:

```js
"💩" === "\u{1F4A9}";                // true
"\u{1F4A9}" === "\uD83D\uDCA9";     // true
```

اگرچه JS اهمیتی نمی‌دهد چنین کاراکتری در برنامهٔ شما چطور نمایش داده شود، هنگام نوشتن کد به تفاوت‌های خوانایی دقت کنید.

| NOTE: |
| :--- |
| اگرچه `💩` مثل یک کاراکتر به‌نظر می‌رسد، نمایش داخلی آن بر چیزهایی مثل محاسبهٔ طول رشته با آن کاراکتر تأثیر می‌گذارد. محاسبهٔ طول رشته‌ها را در فصل ۲ پوشش می‌دهیم. |

##### نرمال‌سازی یونیکد

چین دیگری در پردازش رشتهٔ یونیکد این است که حتی برخی کاراکترهای BMP تکی می‌توانند به روش‌های مختلف نمایش داده شوند.

مثلاً، کاراکتر `"é"` می‌تواند یا خودش (code-point `233`، یعنی `\xe9` یا `\u00e9` یا `\u{e9}`) یا ترکیب دو code-point: کاراکتر `"e"` (code-point `101`، یعنی `\x65`، `\u0065`، `\u{65}`) و *combining tilde* (code-point `769`، یعنی `\u0301`، `\u{301}`) نمایش داده شود.

در نظر بگیرید:

```js
eTilde1 = "é";
eTilde2 = "\u00e9";
eTilde3 = "\u0065\u0301";

console.log(eTilde1);       // é
console.log(eTilde2);       // é
console.log(eTilde3);       // é
```

string literal اختصاص‌داده‌شده به `eTilde3` در این قطعه علامت اکسنت را به‌عنوان نماد *combining mark* جداگانه ذخیره می‌کند. مثل surrogate pairs، combining mark فقط در ارتباط با نمادی که کنارش است (معمولاً بعد) معنا دارد.

رندر نماد یونیکد باید در هر صورت یکسان باشد، اما نحوهٔ ذخیرهٔ داخلی کاراکتر `"é"` بر چیزهایی مثل محاسبهٔ `length` رشتهٔ حاوی، و مقایسهٔ برابری و رابطه‌ای تأثیر می‌گذارد (بیشتر در فصل ۲):

```js
eTilde1.length;             // 2
eTilde2.length;             // 1
eTilde3.length;             // 2

eTilde1 === eTilde2;        // false
eTilde1 === eTilde3;        // true
```

چالش خاص این است که ممکن است رشته‌ای با کاراکتر `"é"` قابل‌مشاهده کپی‌پیست کنید و آن کاراکتری که کپی کردید ممکن است به شکل *composed* یا *decomposed* بوده باشد. اما راه بصری برای تشخیص نیست، و با این حال مقدار رشتهٔ زیربنایی در literal متفاوت خواهد بود:

```js
"é" === "é";           // false!!
```

این تفاوت نمایش داخلی می‌تواند اگر با دقت برنامه‌ریزی نشود چالش‌برانگیز باشد. خوشبختانه، JS متد کمکی `normalize(..)` روی رشته‌ها ارائه می‌دهد:

```js
eTilde1 = "é";
eTilde2 = "\u{e9}";
eTilde3 = "\u{65}\u{301}";

eTilde1.normalize("NFC") === eTilde2;
eTilde2.normalize("NFD") === eTilde3;
```

حالت نرمال‌سازی `"NFC"` code-pointهای مجاور را در code-point *composed* ترکیب می‌کند (در صورت امکان)، در حالی که حالت `"NFD"` یک code-point را به code-pointهای *decomposed* تقسیم می‌کند (در صورت امکان).

و در واقع می‌تواند بیش از دو code-point *decomposed* جداگانه باشد که یک code-point *composed* را تشکیل می‌دهند — مثلاً، یک کاراکتر می‌تواند چند علامت اعرابی داشته باشد.

هنگام کار با رشته‌های یونیکد که مقایسه، مرتب‌سازی یا تحلیل طول می‌شوند، بسیار مهم است نرمال‌سازی یونیکد را در نظر داشته باشید و در صورت نیاز استفاده کنید.

##### خوشه‌های گرافیم یونیکد

پیچیدگی نهایی پردازش رشتهٔ یونیکد پشتیبانی از خوشه‌بندی چند code-point مجاور در یک نماد بصری متمایز است، به‌نام *grapheme* (یا *grapheme cluster*).

مثال emoji خانوادگی مثل `"👩‍👩‍👦‍👦"` است که در واقع از ۷ code-point تشکیل شده که همگی خوشه/گروه می‌شوند در یک نماد بصری واحد.

در نظر بگیرید:

```js
familyEmoji = "\u{1f469}\u{200d}\u{1f469}\u{200d}\u{1f466}\u{200d}\u{1f466}";

familyEmoji;            // 👩‍👩‍👦‍👦
```

این emoji *یک* code-point یونیکد ثبت‌شده نیست، و بنابراین هیچ *نرمال‌سازی* نمی‌تواند این ۷ code-point جدا را در یک موجودیت واحد ترکیب کند. منطق رندر بصری برای چنین نمادهای ترکیبی کاملاً پیچیده است، فراتر از آنچه بیشتر توسعه‌دهندگان JS می‌خواهند در برنامه‌هایمان جاسازی کنیم. کتابخانه‌هایی برای پردازش بخشی از این منطق وجود دارند، اما اغلب بزرگ هستند و هنوز لزوماً همهٔ ظرافت‌ها/تنوع‌ها را پوشش نمی‌دهند.

برخلاف surrogate pairs و combining marks، نمادها در grapheme clusters در واقع می‌توانند به‌عنوان کاراکترهای مستقل عمل کنند، اما رفتار ترکیبی ویژه هنگام قرار گرفتن کنار هم دارند.

این نوع پیچیدگی به‌طور قابل‌توجهی بر محاسبات طول، مقایسه، مرتب‌سازی و بسیاری عملیات رایج رشته‌محور دیگر تأثیر می‌گذارد.

### Template Literals

قبلاً گفتم رشته‌ها می‌توانند با بک‌تیک `` `..` `` محدود شوند:

```js
myName = `Kyle`;
```

همهٔ قوانین رمزگذاری کاراکتر، توالی‌های فرار کاراکتر و طول‌ها برای این نوع رشته‌ها اعمال می‌شود.

با این حال، محتوای این template (string) literalها علاوه بر آن برای توالی جداکنندهٔ ویژهٔ `${ .. }` تجزیه می‌شود که عبارتی را برای ارزیابی و درج در مقدار رشته در آن مکان مشخص می‌کند:

```js
myName = `Kyle`;

greeting = `Hello, ${myName}!`;

console.log(greeting);      // Hello, Kyle!
```

هر چیزی بین `{ .. }` در چنین template literal عبارت دلخواه JS است. می‌تواند متغیرهای ساده مثل `myName`، یا برنامه‌های JS پیچیده، یا هر چیزی بین آن‌ها باشد (حتی عبارت template literal دیگر!).

| TIP: |
| :--- |
| این ویژگی معمولاً «template literals» یا «template strings» نامیده می‌شود، اما فکر می‌کنم گیج‌کننده است. «Template» معمولاً در زمینهٔ برنامه‌نویسی یعنی مجموعهٔ متنی قابل استفادهٔ مجدد که می‌توان با دادهٔ متفاوت دوباره ارزیابی کرد. مثلاً، *template engines* برای صفحات، قالب‌های ایمیل برای کمپین‌های خبرنامه، و غیره. این ویژگی JS قابل استفادهٔ مجدد نیست. literal است و یک مقدار فوری واحد تولید می‌کند (معمولاً رشته). می‌توانید چنین مقداری را در تابع قرار دهید و تابع را چند بار فراخوانی کنید. اما آنگاه تابع نقش template را دارد، نه خود literal. من ترجیح می‌دهم به‌جای آن به این ویژگی *interpolated literals* بگویم، یا به‌طور کوتاه: *interpoliterals*. فکر می‌کنم آن نام دقیق‌تر توصیفی است. |

Template literalها همچنین رفتار جالب متفاوتی نسبت به خطوط جدید دارند، در مقایسه با رشته‌های کلاسیک محدودشده با `"` یا `'`. به یاد دارید برای آن رشته‌ها، line-continuation به `\` در انتهای هر خط، درست قبل از خط جدید نیاز داشت. با template literalها نه!

```js
myPoem = `
Roses are red
Violets are blue
C3PO's a funny robot
and so R2.`;

console.log(myPoem);
//
// Roses are red
// Violets are blue
// C3PO's a funny robot
// and so R2.
```

Line-continuationها با template literalها *نیازی* به فرار ندارند. با این حال، یعنی خط جدید بخشی از رشته است، حتی اولین خط جدید بالا. به عبارت دیگر، `myPoem` بالا رشتهٔ *چندخطی* واقعی نگه می‌دارد، همان‌طور که نشان داده شد. با این حال، اگر انتهای هر خطی در template literal را با `\` فرار کنید، خط جدید حذف می‌شود، درست مثل رشته‌های غیر template literal.

Template literalها معمولاً به مقدار رشته منجر می‌شوند، اما همیشه نه. شکلی از template literal که ممکن است کمی عجیب به‌نظر برسد *tagged template literal* نامیده می‌شود:

```js
price = formatCurrency`The cost is: ${totalCost}`;
```

اینجا، `formatCurrency` تگی است که به مقدار template literal اعمال شده، که در واقع `formatCurrency(..)` را به‌عنوان تابع فراخوانی می‌کند و string literalها و عبارات درج‌شده تجزیه‌شده از مقدار را به آن می‌فرستد. این تابع می‌تواند آن‌ها را به هر نحوی که مناسب می‌بیند مونتاژ کند — مثل قالب‌بندی مقدار `number` به‌عنوان ارز در locale فعلی — و هر مقداری، رشته یا غیره، که می‌خواهد برگرداند.

پس tagged template literalها همیشه رشته نیستند؛ می‌توانند هر مقداری باشند. اما untagged template literalها *همیشه* رشته خواهند بود.

برخی توسعه‌دهندگان JS معتقدند untagged template literal stringها بهترین استفاده برای *همه* رشته‌ها هستند، حتی اگر از درج عبارت یا چند خط استفاده نکنند. من مخالفم. فکر می‌کنم فقط وقتی باید استفاده شوند که درج (یا چندخطی) لازم است.

| TIP: |
| :--- |
| اصل همیشگی من در چنین تصمیم‌گیری‌هایی: برای هر کار، نزدیک‌ترین و کم‌توان‌ترین ویژگی/ابزار را استفاده کن. |

علاوه بر این، چند جا وجود دارد که رشته‌های سبک `` `..` `` ممنوع هستند. مثلاً، pragmaٔ `"use strict"` نمی‌تواند از بک‌تیک استفاده کند، وگرنه pragma ساکتانه نادیده گرفته می‌شود (و در نتیجه برنامه تصادفاً در حالت غیر strict اجرا می‌شود). همچنین، این سبک رشته‌ها نمی‌توانند در نام‌های ویژگی نقل‌قول‌شدهٔ object literalها، الگوهای destructuring، یا بند ES Module `import .. from ..` module-specifier استفاده شوند.

نظر من: از رشته‌های محدودشده با `` `..` `` جایی که مجاز است استفاده کنید، اما فقط وقتی درج/چندخطی لازم است؛ و برای بقیه از رشته‌های محدودشده با `".."` یا `'..'` استفاده کنید.
