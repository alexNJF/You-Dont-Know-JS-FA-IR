## مقادیر عددی

نوع `number` هر مقدار عددی (عدد صحیح یا اعشاری) را شامل می‌شود، مثل `-42` یا `3.1415926`. این مقادیر توسط موتور JS به‌صورت مقادیر نقطه‌شناور دودویی دقت دوگانهٔ ۶۴ بیتی IEEE-754 نمایش داده می‌شوند. [^IEEE754]

`number`های JS همیشه اعشاری هستند؛ اعداد صحیح (یعنی «integers») به روش متفاوت/ویژه ذخیره نمی‌شوند. «integer» ذخیره‌شده به‌عنوان مقدار `number` فقط بخش کسری غیرصفر ندارد؛ `42` بنابراین در JS از `42.0` و `42.000000` غیرقابل تشخیص است.

می‌توانیم از `Number.isInteger(..)` برای تعیین اینکه آیا مقدار `number` بخش کسری غیرصفر دارد یا نه استفاده کنیم:

```js
Number.isInteger(42);           // true
Number.isInteger(42.0);         // true
Number.isInteger(42.000000);    // true

Number.isInteger(42.0000001);   // false
```

### تجزیه در مقابل اجبار

اگر مقدار رشته محتوای به‌ظاهر عددی دارد، ممکن است برای اهداف عملیات ریاضی نیاز به تبدیل از آن مقدار رشته به `number` داشته باشید.

با این حال، تمایز بین تبدیل تجزیه‌ای و تبدیل اجباری بسیار مهم است.

می‌توانیم با ابزارهای داخلی `parseInt(..)` یا `parseFloat(..)` تبدیل تجزیه‌ای انجام دهیم:

```js
someNumericText = "123.456";

parseInt(someNumericText,10);               // 123
parseFloat(someNumericText);                // 123.456

parseInt("42",10) === parseFloat("42");     // true

parseInt("512px");                          // 512
```

| NOTE: |
| :--- |
| تجزیه فقط برای مقادیر رشته مرتبط است، چون عملیات کاراکتربه‌کاراکتر (چپ به راست) است. تجزیهٔ محتوای `boolean` معنا ندارد، نه محتوای `number` یا `null`؛ چیزی برای تجزیه نیست. اگر چیزی غیر از مقدار رشته به `parseInt(..)` / `parseFloat(..)` بفرستید، آن ابزارها ابتدا آن مقدار را به رشته تبدیل می‌کنند و سپس سعی می‌کنند تجزیه کنند. این تقریباً قطعاً مشکل‌ساز (منجر به باگ) یا اتلافی است — `parseInt(42)` احمقانه است و `parseInt(42.3)` سوءاستفاده از `parseInt(..)` برای انجام کار `Math.floor(..)` است. |

تجزیه کاراکترهای به‌ظاهر عددی را از مقدار رشته بیرون می‌کشد و در مقدار `number` قرار می‌دهد، و با مواجهه با کاراکتر غیرعددی (مثلاً نه `-`، `.` یا `0`-`9`) متوقف می‌شود. اگر تجزیه در اولین کاراکتر شکست بخورد، هر دو ابزار مقدار ویژهٔ `NaN` را برمی‌گردانند (ببینید «عدد نامعتبر» در پایین)، که نشان می‌دهد عملیات نامعتبر و شکست‌خورده بود.

وقتی `parseInt(..)` به `.` در `"123.456"` می‌رسد، متوقف می‌شود و فقط `123` را در مقدار `number` نتیجه استفاده می‌کند. `parseFloat(..)` در مقابل این کاراکتر `.` را می‌پذیرد و به تجزیهٔ float با هر رقم اعشاری بعد از `.` ادامه می‌دهد.

ابزار `parseInt(..)` به‌طور خاص آرگومان دوم اختیاری — اما *در واقع*، نسبتاً ضروری — `radix` می‌گیرد: پایهٔ عددی برای تفسیر کاراکترهای رشته برای `number` (محدودهٔ `2` - `36`). `10` برای اعداد پایهٔ ۱۰ استاندارد، `2` برای دودویی، `8` برای هشت‌تایی و `16` برای هگزادسیمال است. هر `radix` غیرمعمول دیگر، مثل `23`، ارقام به ترتیب `0` - `9` به‌دنبال ترتیب کاراکتر `a` - `z` (بدون حساسیت به حروف) فرض می‌کند. اگر radix مشخص‌شده خارج از محدودهٔ `2` - `36` باشد، `parseInt(..)` به‌عنوان نامعتبر شکست می‌خورد و مقدار `NaN` برمی‌گرداند.

اگر `radix` حذف شود، رفتار `parseInt(..)` نسبتاً پیچیده و گیج‌کننده است، چون سعی می‌کند حدس بهترین برای radix بر اساس آنچه در اولین کاراکتر می‌بیند بزند. این تاریخی منجر به باگ‌های ظریف زیادی شده، پس هرگز به حدس خودکار پیش‌فرض تکیه نکنید؛ همیشه radix صریح (مثل `10` در فراخوانی‌های بالا) مشخص کنید.

`parseFloat(..)` همیشه با radix `10` تجزیه می‌کند، پس آرگومان دوم پذیرفته نمی‌شود.

| WARNING: |
| :--- |
| یک تفاوت غافل‌گیرکننده بین `parseInt(..)` و `parseFloat(..)` این است که `parseInt(..)` نماد علمی (مثلاً `"1.23e+5"`) را کامل تجزیه نمی‌کند، بلکه در `.` متوقف می‌شود چون برای integers معتبر نیست؛ در واقع، حتی `"1e+5"` در `"e"` متوقف می‌شود. `parseFloat(..)` از طرف دیگر نماد علمی را کامل تجزیه می‌کند. |

در مقابل تبدیل تجزیه‌ای، تبدیل اجباری عملیات همه‌یاهیچ است. یا کل محتوای رشته به‌عنوان عددی (صحیح یا نقطه‌شناور) شناخته می‌شود، یا کل تبدیل شکست می‌خورد (منجر به `NaN` — دوباره، ببینید «عدد نامعتبر» بعداً در این فصل).

تبدیل اجباری را می‌توان صریح با تابع `Number(..)` (بدون کلمهٔ کلیدی `new`) یا عملگر یکانی `+` جلوی مقدار انجام داد:

```js
someNumericText = "123.456";

Number(someNumericText);        // 123.456
+someNumericText;               // 123.456

Number("512px");                // NaN
+"512px";                       // NaN
```

### نمایش‌های عددی دیگر

علاوه بر تعریف اعداد با ارقام پایهٔ ۱۰ سنتی (`0`-`9`)، JS تعریف literalهای عددی فقط عدد صحیح در سه پایهٔ دیگر را پشتیبانی می‌کند: دودویی (پایهٔ ۲)، هشت‌تایی (پایهٔ ۸) و هگزادسیمال (پایهٔ ۱۶).

```js
// binary
myAge = 0b101010;
myAge;              // 42

// octal
myAge = 0o52;
myAge;              // 42

// hexadecimal
myAge = 0x2a;
myAge;              // 42
```

همان‌طور که می‌بینید، پیشوندهای `0b` (دودویی)، `0o` (هشت‌تایی) و `0x` (هگزادسیمال) تعریف اعداد در پایه‌های مختلف را نشان می‌دهند، اما اعشار روی این literalهای عددی مجاز نیست.

| NOTE: |
| :--- |
| نحو JS پیشوندهای `0B`، `0O` و `0X` را هم اجازه می‌دهد. با این حال، لطفاً هرگز از آن اشکال پیشوند بزرگ استفاده نکنید. فکر می‌کنم هر شخص معقولی موافق است: `0O` در نگاه اول بسیار راحت‌تر با `0o` اشتباه گرفته می‌شود (که خودش کمی از نظر بصری مبهم است). همیشه به اشکال پیشوند کوچک پایبند باشید! |

مهم است بدانید که *عدد متفاوت* تعریف نمی‌کنید، فقط از شکلی متفاوت برای تولید همان مقدار عددی زیربنایی استفاده می‌کنید.

به‌طور پیش‌فرض، JS مقدار عددی زیربنایی را در خروجی/رشته به‌صورت فرم پایهٔ ۱۰ استاندارد نمایش می‌دهد. با این حال، مقادیر `number` متد داخلی `toString(..)` دارند که نمایش رشته در هر پایه/radix مشخص‌شده تولید می‌کند (مثل `parseInt(..)`، در محدودهٔ `2` - `36`):

```js
myAge = 42;

myAge.toString(2);          // "101010"
myAge.toString(8);          // "52"
myAge.toString(16);         // "2a"
myAge.toString(23);         // "1j"
myAge.toString(36);         // "16"
```

می‌توانید هر نمایش رشتهٔ radix دلخواه را با `parseInt(..)` و radix مناسب دوباره به `number` تبدیل کنید:

```js
myAge = 42;

parseInt(myAge.toString("23"),23);      // 42
```

شکل مجاز دیگر برای مشخص کردن literalهای عددی استفاده از نماد علمی است:

```js
myAge = 4.2E1;      // or 4.2e1 or 4.2e+1

myAge;              // 42
```

`4.2E1` (یا `4.2e1`) یعنی `4.2 * (10 ** 1)` (`10` به توان `1`). توان می‌تواند اختیاری علامت `+` یا `-` داشته باشد. اگر علامت حذف شود، `+` فرض می‌شود. توان منفی عدد را کوچک‌تر می‌کند (اعشار را به چپ می‌برد) به‌جای بزرگ‌تر (اعشار را به راست می‌برد):

```js
4.2E-3;             // 0.0042
```

این شکل نماد علمی به‌ویژه برای خوانایی هنگام مشخص کردن توان‌های بزرگ‌تر `10` مفید است:

```js
someBigPowerOf10 = 1000000000;

// vs:

someBigPowerOf10 = 1e9;
```

به‌طور پیش‌فرض، JS اعداد بسیار بزرگ یا بسیار کوچک را — به‌طور خاص، اگر مقادیر به بیش از ۲۱ رقم دقت نیاز دارند — با همین نماد علمی نمایش می‌دهد:

```js
ratherBigNumber = 123 ** 11;
ratherBigNumber.toString();     // "9.748913698143826e+22"

prettySmallNumber = 123 ** -11;
prettySmallNumber.toString();   // "1.0257553107587752e-23"
```

اعداد با مقادیر مطلق کوچک‌تر (نزدیک‌تر به `0`) از این آستانه‌ها هنوز می‌توانند به شکل نماد علمی (به‌صورت رشته) اجباری شوند:

```js
plainBoringNumber = 42;

plainBoringNumber.toExponential();      // "4.2e+1"
plainBoringNumber.toExponential(0);     // "4e+1"
plainBoringNumber.toExponential(4);     // "4.2000e+1"
```

آرگومان اختیاری `toExponential(..)` تعداد ارقام اعشاری برای گنجاندن در نمایش رشته را مشخص می‌کند.

امکانات خوانایی دیگر برای مشخص کردن literalهای عددی در کد توانایی درج `_` به‌عنوان جداکنندهٔ رقم هر جا مناسب/معنادار است. مثلاً:

```js
someBigPowerOf10 = 1_000_000_000;

totalCostInPennies = 123_45;  // vs 12_345
```

تصمیم استفاده از `12345` (بدون جداکننده)، `12_345` (مثل «۱۲٬۳۴۵») یا `123_45` (مثل «۱۲۳.۴۵») کاملاً به نویسندهٔ کد بستگی دارد؛ JS جداکننده‌ها را نادیده می‌گیرد. اما بسته به زمینه، `123_45` می‌تواند از نظر خوانایی معنادارتر از سبک سنتی‌تر گروه‌بندی سه‌رقمی‌ازراست‌با-کاما با `12_345` باشد.

### نمایش‌های دودویی بیتی IEEE-754

IEEE-754[^IEEE754] استاندارد فنی برای نمایش دودویی اعداد اعشاری است. توسط اکثر زبان‌های برنامه‌نویسی از جمله JS، Python، Ruby و غیره به‌طور گسترده استفاده می‌شود.

آن را به‌طور جامع پوشش نمی‌دهم، اما فکر می‌کنم مقدمهٔ کوتاهی دربارهٔ نحوهٔ کار اعداد در زبان‌هایی مثل JS بیش از حد توجیه‌شده است، با توجه به اینکه چند برنامه‌نویس *هیچ* آشنایی با آن دارند.

در IEEE-754 ۶۴ بیتی — به‌اصطلاح «دقت دوگانه»، چون originally IEEE-754 ۳۲ بیتی بود و الان دو برابر شده! — ۶۴ بیت به سه بخش تقسیم می‌شوند: ۵۲ بیت برای مقدار پایهٔ عدد (یعنی «fraction»، «mantissa» یا «significand»)، ۱۱ بیت برای توان برای بالا بردن `2` قبل از ضرب، و ۱ بیت برای علامت مقدار نهایی.

| NOTE: |
| :--- |
| چون فقط ۵۲ از ۶۴ بیت واقعاً برای نمایش مقدار پایه استفاده می‌شوند، `number` در واقع `2^64` مقدار ندارد. طبق مشخصات نوع `number`[^NumberType]، تعداد مقادیر دقیقاً `2^64 - 2^53 + 3` است، یا حدود ۱۸ کوینتیلیون، تقریباً به‌طور مساوی بین اعداد مثبت و منفی تقسیم شده. |

این بیت‌ها از چپ به راست چیده شده‌اند، به این شکل (S = بیت علامت، E = بیت توان، M = بیت مانتیسا):

```js
SEEEEEEEEEEEMMMMMMMMMMMMMMMMMMMM
MMMMMMMMMMMMMMMMMMMMMMMMMMMMMMMM
```

پس عدد `42` (یا `42.000000`) با این بیت‌ها نمایش داده می‌شود:

```
// 42:
01000000010001010000000000000000
00000000000000000000000000000000
```

بیت علامت `0` است، یعنی عدد مثبت است (`1` یعنی منفی).

توان ۱۱ بیتی دودویی `10000000100` است که در پایهٔ ۱۰ برابر `1028` است. اما در IEEE-754، این مقدار به‌عنوان ذخیره‌شده بدون علامت با «exponent bias» برابر `1023` تفسیر می‌شود، یعنی محدودهٔ توان را از `-1022:1023` به `1:2046` جابه‌جا می‌کنیم (جایی که `0` و `2047` برای نمایش‌های ویژه رزرو شده‌اند). پس `1028` را بگیرید و bias `1023` را کم کنید که توان مؤثر `5` می‌دهد. `2` را به آن مقدار (`2^5`) می‌رسانیم که `32` می‌دهد.

| NOTE: |
| :--- |
| اگر کم کردن `1023` از مقدار توان منفی بدهد (مثلاً `-3`)، همچنان به‌عنوان توان `2` تفسیر می‌شود؛ بالا بردن `2` به اعداد منفی فقط مقادیر کوچک‌تر و کوچک‌تر تولید می‌کند. |

۵۲ بیت باقی‌مانده مقدار پایهٔ `01010000...` را می‌دهند، به‌عنوان اعشار دودویی `1.0101000...` (با همهٔ صفرهای دنباله‌دار) تفسیر می‌شود. تبدیل *آن* به پایهٔ ۱۰، `1.3125000...` می‌دهد. در نهایت، آن را در `32` که قبلاً از توان محاسبه شد ضرب کنید. نتیجه: `42`.

همان‌طور که الان می‌توانید بگویید، این استاندارد نمایش عدد IEEE-754 «floating point» نامیده می‌شود چون نقطهٔ اعشار «شناور» جلو و عقب در امتداد بیت‌ها است، بسته به مقدار توان مشخص‌شده.

عدد `42.0000001` که فقط با `0.0000001` از `42.000000` متفاوت است با این بیت‌ها نمایش داده می‌شود:

```
// 42.0000001:
01000000010001010000000000000000
00000000110101101011111110010101
```

توجه کنید الگوی بیتی قبلی و این یکی در موقعیت‌های دنباله‌دار با چند بیت تفاوت دارند! کسر اعشاری دودویی حاوی همهٔ آن بیت‌های `1` اضافی (`1.010100000000...01011111110010101`) به پایهٔ ۱۰ به‌عنوان `1.31250000312500003652` تبدیل می‌شود که در `32` ضرب شده دقیقاً `42.0000001` می‌دهد.

جزئیات بیشتر دربارهٔ (عدم)دقت نقطه‌شناور را در فصل ۲ دوباره بررسی می‌کنیم. اما الان *کمی بیشتر* دربارهٔ نحوهٔ کار IEEE-754 می‌فهمید!

### محدودیت‌های عددی

همان‌طور که الان که نحوهٔ کار IEEE-754 را دیده‌اید ممکن است واضح باشد، ۵۲ بیت مقدار پایهٔ عدد باید مشترک باشند، هم بخش عدد صحیح (در صورت وجود) و هم بخش اعشاری (در صورت وجود) مقدار `number` مورد نظر را نمایش می‌دهند. اساساً، هرچه بخش عدد صحیح بزرگ‌تر باشد، بیت‌های کمتری برای بخش اعشاری موجود است و برعکس.

بزرگ‌ترین مقداری که می‌تواند دقیق در نوع `number` ذخیره شود به‌عنوان `Number.MAX_VALUE` در دسترس است:

```js
Number.MAX_VALUE;           // 1.7976931348623157e+308
```

ممکن است انتظار داشته باشید آن مقدار اعشاری باشد با توجه به نمایش. اما با بررسی دقیق‌تر، `1.79E308` (تقریباً) `2^1024 - 1` است. به‌نظر خیلی بیشتر شبیه integer است، درست است؟ می‌توانیم تأیید کنیم:

```js
Number.isInteger(Number.MAX_VALUE);         // true
```

اما اگر از مقدار حداکثر بالاتر بروید چه می‌شود؟

```js
Number.MAX_VALUE === (Number.MAX_VALUE + 1);
// true -- اوه!

Number.MAX_VALUE === (Number.MAX_VALUE + 10000000);
// true
```

پس آیا `Number.MAX_VALUE` واقعاً بزرگ‌ترین مقدار قابل نمایش در JS است؟ قطعاً بزرگ‌ترین مقدار *محدود* `number` است.

IEEE-754 مقدار بی‌نهایت ویژه تعریف می‌کند که JS به‌عنوان `Infinity` در دسترس می‌گذارد؛ همچنین `-Infinity` در انتهای دیگر خط اعداد وجود دارد. مقادیر را می‌توان برای محدود یا نامحدود بودن آزمایش کرد:

```js
Number.isFinite(Number.MAX_VALUE);  // true

Number.isFinite(Infinity);          // false
Number.isFinite(-Infinity);         // false
```

هرگز نمی‌توانید با `+ 1` از `Number.MAX_VALUE` به `Infinity` بالا بروید، هر قدر هم برنامه را اجرا کنید، چون عملیات `+ 1` واقعاً فراتر از مقدار بالای `Number.MAX_VALUE` افزایش نمی‌دهد.

با این حال، عملیات حسابی JS (`+`، `*` و حتی `/`) قطعاً می‌توانند نوع `number` را در انتهای بالا سرریز کنند، که در آن صورت `Infinity` نتیجه است:

```js
Number.MAX_VALUE + 1E291;           // 1.7976931348623157e+308
Number.MAX_VALUE + 1E292;           // Infinity

Number.MAX_VALUE * 1.0000000001;    // Infinity

1 / 1E-308;                         // 1e+308
1 / 1E-309;                         // Infinity
```

| TIP: |
| :--- |
| برعکس درست نیست: عملیات حسابی روی مقدار نامحدود *هرگز* مقدار محدود تولید نمی‌کند. |

از خیلی بزرگ به خیلی خیلی کوچک — در واقع، نزدیک‌ترین به صفر، که با خیلی خیلی منفی یکی نیست! — کوچک‌ترین مقدار اعشاری مطلق که به‌طور نظری می‌توانید در نوع `number` ذخیره کنید `2^-1022` خواهد بود (محدودهٔ توان IEEE-754 را به یاد دارید؟)، یا حدود `2E-308`. با این حال، موتورهای JS طبق مشخصات اجازه دارند در نمایش‌های داخلی این حد پایین متفاوت باشند. هرچه حد پایین مؤثر موتور باشد، به‌عنوان `Number.MIN_VALUE` در دسترس خواهد بود:

```js
Number.MIN_VALUE;               // 5e-324 <-- معمولاً!
```

اکثر موتورهای JS به‌نظر حداقل مقدار قابل نمایش حدود `5E-324` (حدود `2^-1074`) دارند. بسته به موتور و/یا پلتفرم، مقدار متفاوتی ممکن است در دسترس باشد. دربارهٔ هر منطق برنامه که به چنین مقادیر وابسته به پیاده‌سازی تکیه می‌کند محتاط باشید.

### محدودیت‌های Integer امن

چون `Number.MAX_VALUE` integer است، ممکن است فرض کنید بزرگ‌ترین integer در زبان است. اما واقعاً دقیق نیست.

بزرگ‌ترین integer که می‌توانید دقیق در نوع `number` ذخیره کنید `2^53 - 1` است، یا `9007199254740991`، که *خیلی کوچک‌تر* از `Number.MAX_VALUE` (حدود `2^1024 - 1`) است. این مقدار امن‌تر ویژه به‌عنوان `Number.MAX_SAFE_INTEGER` در دسترس است:

```js
maxInt = Number.MAX_SAFE_INTEGER;

maxInt;             // 9007199254740991

maxInt + 1;         // 9007199254740992

maxInt + 2;         // 9007199254740992
```

دیده‌ایم که integerهای بزرگ‌تر از `9007199254740991` می‌توانند ظاهر شوند. با این حال، آن integerهای بزرگ‌تر «امن» نیستند، چون دقت/صحت هنگام انجام عملیات با آن‌ها شروع به خراب شدن می‌کند. همان‌طور که بالا نشان داده شد، عبارات `maxInt + 1` و `maxInt + 2` هر دو اشتباهاً همان نتیجه را می‌دهند، که خطر فراتر رفتن از حد `Number.MAX_SAFE_INTEGER` را نشان می‌دهد.

اما کوچک‌ترین integer امن چیست؟

بسته به تفسیر «کوچک‌ترین»، می‌توانید یا `0` پاسخ دهید یا... `Number.MIN_SAFE_INTEGER`:

```js
Number.MIN_SAFE_INTEGER;    // -9007199254740991
```

و JS ابزاری برای تعیین اینکه آیا مقدار در این محدودهٔ امن (`-2^53 + 1` - `2^53 - 1`) integer است ارائه می‌دهد:

```js
Number.isSafeInteger(2 ** 53);      // false
Number.isSafeInteger(2 ** 53 - 1);  // true
```

### دو صفر

ممکن است تعجب کنید که JS دو صفر دارد: `0` و `-0` (صفر منفی). اما «صفر منفی» چیست؟ [^SignedZero] یک ریاضیدان قطعاً از چنین مفهومی امتناع می‌ورزد.

این فقط یک عجیب‌بودن خنده‌دار JS نیست؛ توسط مشخصات IEEE-754[^IEEE754] الزامی است. همهٔ اعداد نقطه‌شناور علامت‌دار هستند، از جمله صفر. و اگرچه JS وجود `-0` را نوعی پنهان می‌کند، کاملاً ممکن است تولید و تشخیصش دهیم:

```js
function isNegZero(v) {
    return v == 0 && (1 / v) == -Infinity;
}

regZero = 0 / 1;
negZero = 0 / -1;

regZero === negZero;        // true -- اوه!
Object.is(-0,regZero);      // false -- پhew!
Object.is(-0,negZero);      // true

isNegZero(regZero);         // false
isNegZero(negZero);         // true
```

شاید تعجب کنید چرا به چیزی مثل `-0` نیاز داریم. می‌تواند هنگام استفاده از اعداد برای نمایش هم بزرگی حرکت (سرعت) یک آیتم (مثل شخصیت بازی یا انیمیشن) و هم جهتش (مثلاً منفی = چپ، مثبت = راست) مفید باشد.

بدون داشتن مقدار صفر علامت‌دار، نمی‌توانستید بگویید چنین آیتمی در لحظهٔ توقف به کدام جهت اشاره می‌کرد.

| NOTE: |
| :--- |
| در حالی که JS صفر علامت‌دار را در نوع `number` تعریف می‌کند، صفر علامت‌دار متناظری در نوع عددی `bigint` وجود ندارد. بنابراین `-0n` فقط به‌عنوان `0n` تفسیر می‌شود و آن دو غیرقابل تشخیص هستند. |

### عدد نامعتبر

عملیات ریاضی گاهی می‌توانند نتیجهٔ نامعتبر تولید کنند. مثلاً:

```js
42 / "Kyle";            // NaN
```

احتمالاً واضح است، اما اگر سعی کنید عدد را بر رشته تقسیم کنید، عملیات ریاضی نامعتبر است.

نوع دیگر عملیات عددی نامعتبر تلاش برای تبدیل اجباری مقدار شبیه غیرعددی به `number` است. همان‌طور که قبلاً بحث شد، می‌توانیم با تابع `Number(..)` یا عملگر یکانی `+` انجام دهیم:

```js
myAge = Number("just a number");

myAge;                  // NaN

+undefined;             // NaN
```

همهٔ چنین عملیات‌های نامعتبر (ریاضی یا اجباری/عددی) مقدار ویژهٔ `number` به‌نام `NaN` تولید می‌کنند.

ریشهٔ تاریخی «NaN» (از مشخصات IEEE-754[^IEEE754]) به‌عنوان مخفف «Not a Number» است. از نظر فنی، حدود ۹ کوادریلیون مقدار در فضای عدد ۶۴ بیتی IEEE-754 به‌عنوان «NaN» تعیین شده‌اند، اما JS همهٔ آن‌ها را به‌طور غیرقابل تشخیص به‌عنوان مقدار واحد `NaN` رفتار می‌کند.

متأسفانه، آن معنای *عدد نیست* سردرگمی ایجاد می‌کند، چون `NaN` *قطعاً* یک `number` است.

| TIP: |
| :--- |
| چرا `NaN` یک `number` است?!? برعکس را فکر کنید: اگر عملیات ریاضی/عددی مثل `+` یا `/` مقدار غیر`number` (مثل `null`، `undefined` و غیره) تولید می‌کرد چه؟ آیا واقعاً عجیب و غیرمنتظره نبود؟ اگر استثنا پرتاب می‌کردند و مجبور بودید همهٔ ریاضیات را `try..catch` کنید چه؟ تنها رفتار منطقی این است که عملیات عددی/ریاضی باید *همیشه* `number` تولید کنند، حتی اگر آن مقدار به‌خاطر عملیات نامعتبر نامعتبر باشد. |

برای جلوگیری از چنین سردرگمی، من ترجیح می‌دهم «NaN» را به‌عنوان هر یک از موارد زیر تعریف کنم:

* «iNvalid Number» (عدد نامعتبر)
* «Not actual Number» (عدد واقعی نیست)
* «Not available Number» (عدد در دسترس نیست)
* «Not applicable Number» (عدد قابل اعمال نیست)

`NaN` مقدار ویژه‌ای در JS است، چون تنها مقداری در زبان است که فاقد *ویژگی هویت* است — هرگز با خودش برابر نیست.

```js
NaN === NaN;            // false
```

پس متأسفانه عملگر `===` نمی‌تواند مقدار را برای `NaN` بودن بررسی کند. اما راه‌هایی وجود دارد:

```js
politicianIQ = "nothing" / Infinity;

Number.isNaN(politicianIQ);         // true

Object.is(NaN,politicianIQ);        // true
[ NaN ].includes(politicianIQ);     // true
```

واقعیتی دربارهٔ تقریباً همهٔ برنامه‌های JS، چه متوجه باشید چه نه: `NaN` اتفاق می‌افتد. جداً، تقریباً همهٔ برنامه‌هایی که هر ریاضی یا تبدیل عددی انجام می‌دهند در معرض ظاهر شدن `NaN` هستند.

اگر در برنامه‌هایتان جایی که ریاضی یا تبدیل عددی انجام می‌دهید به‌درستی برای `NaN` بررسی نمی‌کنید، می‌توانم با درجه‌ای از قطعیت بگویم: احتمالاً باگ عددی جایی در برنامه دارید و هنوز شما را نگرفته (که بدانید!).

| WARNING: |
| :--- |
| JS در اصل تابع سراسری به‌نام `isNaN(..)` برای بررسی `NaN` ارائه داد، اما متأسفانه باگ اجبار دیرپایی دارد. `isNaN("Kyle")` مقدار `true` برمی‌گرداند، حتی اگر مقدار رشتهٔ `"Kyle"` قطعاً *نه* مقدار `NaN` است. این به‌خاطر آن است که تابع سراسری `isNaN(..)` هر آرگومان غیر`number` را مجبور می‌کند ابتدا به `number` تبدیل شود، قبل از بررسی `NaN`. تبدیل اجباری `"Kyle"` به `number` مقدار `NaN` تولید می‌کند، پس الان تابع `NaN` می‌بیند و `true` برمی‌گرداند! این تابع سراسری باگ‌دار `isNaN(..)` هنوز در JS وجود دارد، اما هرگز نباید استفاده شود. هنگام بررسی `NaN`، همیشه از `Number.isNaN(..)`، `Object.is(..)` و غیره استفاده کنید. |
