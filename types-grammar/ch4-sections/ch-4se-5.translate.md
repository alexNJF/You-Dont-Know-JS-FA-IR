## آگاهی از نوع

اکنون coercion را از هر زاویهٔ قابل تصوری برش دادیم و بررسی کردیم، از abstractهای داخلی مشخصات شروع کردیم، سپس به عبارت‌ها و عبارات عینی‌ای رفتیم که واقعاً coercionها را trigger می‌کنند.

اما هدف همهٔ این چیست؟ آیا جزئیات این فصل، و در واقع این کل کتاب تا این نقطه، بیشتر فقط trivia است؟ اِه، فکر نمی‌کنم.

بیایید به مشاهدات/سؤال‌هایی که در ابتدای این فصل طولانی مطرح کردم برگردیم.

کمبود نظر (به‌ویژه منفی) دربارهٔ coercion وجود ندارد. موضع تقریباً به‌طور جهانی نگه‌داشته‌شده این است که coercion بیشتر/کاملاً *بخش بد* طراحی زبان JS است. اما علیرغم آن واقعیت، تقریباً هر توسعه‌دهنده، در تقریباً هر برنامهٔ JS که تاکنون نوشته شده، با واقعیت مواجه می‌شود که coercion نمی‌تواند اجتناب شود.

به عبارت دیگر، هر چه بکنید، نمی‌توانید از نیاز به آگاهی، فهم و مدیریت value-types و تبدیل‌های آن‌ها فرار کنید. برخلاف فرض‌های رایج، پذیرش زبانی با نوع پویا (یا حتی ضعیف‌تایپ‌شده) به‌معنی بی‌دقتی یا ناآگاهی از نوع‌ها *نیست*.

برنامه‌نویسی آگاه از نوع همیشه، همیشه بهتر از برنامه‌نویسی ناآگاه/غافل از نوع است.

### اِه... TypeScript؟

قطعاً الان فکر می‌کنید: «چرا نمی‌توانم فقط از TypeScript استفاده کنم و همهٔ نوع‌هایم را به‌طور statically اعلام کنم و از همهٔ سردرگمی نوع پویا و coercion اجتناب کنم؟»

| NOTE: |
| :--- |
| نظرهای جزئی‌تر زیادی دربارهٔ TypeScript و نقش بزرگ‌تری که در اکوسیستم ما بازی می‌کند دارم؛ آن نظرها را برای ضمیمه («Thoughts on TypeScript») نگه می‌دارم. |

بیایید ابتدا مستقیم به روش‌هایی که TypeScript به برنامه‌نویسی آگاه از نوع کمک می‌کند و نمی‌کند بپردازیم، همان‌طور که من دفاع می‌کنم.

TypeScript هم **statically-typed** است (یعنی نوع‌ها در زمان نویسنده اعلام و در زمان compile بررسی می‌شوند) و **strongly-typed** (یعنی متغیرها/کانتینرها typed هستند و این ارتباط‌ها اعمال می‌شوند؛ سیستم‌های strongly-typed همچنین coercion *implicit* را ممنوع می‌کنند). بزرگ‌ترین قدرت TypeScript این است که معمولاً هم نویسندهٔ کد و هم خوانندهٔ کد را مجبور می‌کند با نوع‌های تشکیل‌دهندهٔ بیشتر (ایده‌آل، همه!) یک برنامه مواجه شوند. قطعاً چیز خوبی است.

در مقابل، JS **dynamically-typed** است (یعنی نوع‌ها در زمان اجرا کشف و مدیریت می‌شوند) و **weakly-typed** (یعنی متغیرها/کانتینرها typed نیستند، پس ارتباطی برای اعمال نیست و متغیرها می‌توانند هر value-type را نگه دارند؛ سیستم‌های weakly-typed هر شکل coercion را اجازه می‌دهند).

| NOTE: |
| :--- |
| اینجا در سطح نسبتاً بالایی hand-waving می‌کنم و عمداً عمیق در nuanceهای زیاد روی طیف‌های static/dynamic و strong/weak dive نمی‌کنم. اگر الان میل به «خب، در واقع...» دارید، لطفاً کمی صبر کنید و بگذارید استدلال‌هایم را بیان کنم. |

### آگاهی از نوع *بدون* TypeScript

آیا سیستم به‌طور پویا typed به‌طور خودکار یعنی با آگاهی کمتر از نوع برنامه‌نویسی می‌کنید؟ بسیاری استدلال می‌کنند، اما مخالفم.

اصلاً فکر نمی‌کنم اعلام نوع‌های static (annotationها، مثل TypeScript) تنها راه دستیابی به آگاهی مؤثر از نوع است. واضح است، که طرفداران static-typing معتقدند آن *بهترین* راه است.

اجازه دهید آگاهی از نوع بدون static typing TypeScript را نشان دهم. این تعریف متغیر را در نظر بگیرید:

```js
let API_BASE_URL = "https://some.tld/api/2";
```

آیا آن عبارت به هیچ وجه *آگاه از نوع* است؟ مطمئناً، هیچ annotation `: string` بعد از `API_BASE_URL` نیست. اما قطعاً فکر می‌کنم *هنوز* آگاه از نوع است! به‌وضوح value-type (`string`) مقدار assign‌شده به `API_BASE_URL` را می‌بینیم.

| WARNING: |
| :--- |
| با تعریف `let` که قابل reassign است (در مقابل `const`) حواس‌تان پرت نشود. `const` در JS ویژگی first-class سیستم نوع آن نیست. واقعاً آگاهی از نوع بیشتری به‌صرف اینکه می‌دانیم reassignment متغیر `const` توسط موتور JS ممنوع است به دست نمی‌آوریم. اگر کد به‌خوبی ساختار یافته باشد — اِه، با آگاهی از نوع به‌عنوان اولویت ساختار یافته باشد — می‌توانیم فقط کد را بخوانیم و به‌وضوح ببینیم که `API_BASE_URL` *reassign* نمی‌شود و بنابراین همچنان value-type است که قبلاً assign شده بود. از نظر آگاهی از نوع، این effectively همان است که انگار *نمی‌توانست* reassign شود. |

اگر بعداً بخواهم کاری مثل این انجام دهم:

```js
// آیا از URL امن API استفاده می‌کنیم؟
isSecureAPI = /^https/.test(API_BASE_URL);
```

می‌دانم متد `test(..)` عبارت منظم انتظار رشته دارد، و چون می‌دانم `API_BASE_URL` رشته نگه می‌دارد، می‌دانم آن عملیات type-safe است.

به‌طور مشابه، چون قوانین سادهٔ coercion `ToBoolean()` را در رابطه با مقادیر رشته می‌دانم، می‌دانم این نوع عبارت هم type-safe است:

```js
// آیا هنوز URLی API تعیین کرده‌ایم؟
if (API_BASE_URL) {
    // ..
}
```

اما اگر بعداً، شروع به تایپ چیزی مثل این کنم:

```js
APIVersion = Number(API_BASE_URL);
```

آژیر هشدار در سرم trigger می‌شود. چون قوانین بسیار خاصی دربارهٔ نحوهٔ اجبار مقادیر رشته به عدد می‌دانم، تشخیص می‌دهم که این عملیات **type-safe نیست**. پس به‌جای آن متفاوت نزدیک می‌شوم:

```js
// عدد نسخه را از URL API بیرون بکش
versionDigit = API_BASE_URL.match(/\/api\/(\d+)$/)[1];

// مطمئن شو نسخه واقعاً عدد است
APIVersion = Number(versionDigit);
```

می‌دانم که `API_BASE_URL` رشته است و further می‌دانم فرمت محتوای آن شامل `".../api/{digits}"` در انتهاست. پس می‌دانم match عبارت منظم موفق می‌شود و دسترسی آرایهٔ `[1]` type-safe است.

همچنین می‌دانم که `versionDigit` رشته نگه می‌دارد، چون matchهای عبارت منظم آن را برمی‌گردانند. حالا می‌دانم امن است که آن رشتهٔ رقم عددی را با `Number(..)` به عدد اجبار کنم.

طبق تعریف من، آن نوع فکر کردن و آن سبک کدنویسی، آگاه از نوع است. آگاهی از نوع در کدنویسی یعنی فکر دقیق‌تر به اینکه آیا چنین چیزهایی برای خوانندهٔ کد *واضح* و *آشکار* خواهند بود یا نه.

### آگاهی از نوع *با* TypeScript

طرفداران TypeScript اشاره می‌کنند که TypeScript می‌تواند، از طریق type inference، static typing (اعمال) را بدون نیاز به حتی یک type annotation در برنامه انجام دهد. پس همهٔ نمونه‌های کد که در بخش قبلی به اشتراک گذاشتم، TypeScript هم می‌تواند handle کند و نوع بررسی static خودش را ارائه دهد.

به عبارت دیگر، TypeScript همان نوع مزیت را در type checking به ما می‌دهد، هر کدام از این دو را بنویسیم:

```ts
let API_BASE_URL: string = "https://some.tld/api/2";

// در مقابل:

let API_BASE_URL = "https://some.tld/api/2";
```

اما ناهار رایگان نیست. مسائلی داریم که باید با آن‌ها مواجه شویم. اول از همه، TypeScript اینجا خطا trigger نمی‌کند:

```js
API_BASE_URL = "https://some.tld/api/2";

APIVersion = Number(API_BASE_URL);
// NaN
```

به‌طور شهودی، *من* می‌خواهم سیستم آگاه از نوع بفهمد چرا این ناامن است. اما شاید این خیلی زیاد است. یا شاید اگر واقعاً نوع باریک‌تر/خاص‌تری برای آن متغیر `API_BASE_URL` تعریف کنیم، نه صرفاً `string`، کمک کند؟ می‌توانیم از ترفند TypeScript به نام «Template Literal Types» استفاده کنیم: [^TSLiteralTypes]

```ts
type VersionedURL = `https://some.tld/api/${number}`;

API_BASE_URL: VersionedURL = "https://some.tld/api/2";

APIVersion = Number(API_BASE_URL);
// NaN
```

نه، TypeScript هنوز هم مشکلی با آن نمی‌بیند. بله، می‌دانم توضیحی برای چرا وجود دارد (نحوهٔ typing خود `Number(..)`).

| NOTE: |
| :--- |
| تصور می‌کنم افراد واقعاً باهوش که *خوب* TypeScript را می‌شناسند ایده‌های خلاقانه‌ای برای contort کردن خودمان برای بالا آوردن خطا آنجا دارند. شاید حتی ده‌ها راه مختلف برای force کردن TypeScript به trigger روی آن کد وجود دارد. اما واقعاً نکته نیست. |

نکتهٔ من این است که نمی‌توانیم کاملاً به نوع‌های TypeScript برای حل همهٔ مشکلاتمان تکیه کنیم، و اجازه دهیم checkout کنیم و blissfully از nuanceهای نوع‌ها و در این مورد، رفتارهای coercion ناآگاه بمانیم.

اما! قطعاً به این خط استدلال اعتراض می‌کنید، با desperation برای ادعا که حتی اگر TypeScript نتواند برخی موقعیت‌های خاص را بفهمد، قطعاً استفاده از TypeScript آن را *بدتر* نمی‌کند! درست!؟

بیایید ببینیم TypeScript چه می‌گوید[^TSExample1] دربارهٔ این خط:

```ts
type VersionedURL = `https://some.tld/api/${number}`;

let API_BASE_URL: VersionedURL = "https://some.tld/api/2";

let versionDigit = API_BASE_URL.match(/\/api\/(\d+)$/)[1];
// Object is possibly 'null'.
```

خطا نشان می‌دهد که دسترسی `[1]` type-safe نیست، چون اگر عبارت منظم موفق به پیدا کردن هیچ match نباشد، `match(..)` مقدار `null` برمی‌گرداند.

می‌بینید، حتی اگر *من* بتوانم دربارهٔ محتوای رشته در مقایسه با نحوهٔ نوشتن عبارت منظم استدلال کنم، و حتی اگر *من* زحمت super clear کردن برای TypeScript دقیقاً آن محتوای رشتهٔ خاص را کشیدم، آنقدر باهوش نیست که آن دو را به هم وصل کند تا ببیند در واقع فرض match کاملاً type-safe است.

| TIP: |
| :--- |
| آیا واقعاً کار و بهترین استفاده از ابزار آگاه از نوع است که contort شود تا هر nuance ممکن type-safety را بیان کند؟ به ابزارهای کامل و جهانی برای derive کردن مزایای عظیم از چیزهایی که *می‌توانند* انجام دهند نیاز نداریم. |

علاوه بر این، مقایسهٔ سبک کد در بخش قبلی با کد در این بخش (با یا بدون annotationها)، آیا TypeScript واقعاً کدنویسی ما را آگاه‌تر از نوع می‌کند؟

مثلاً، آیا آن `type VersionedURL = ..` و `API_BASE_URL: VersionedURL` واقعاً کد ما را واضح‌تر آگاه از نوع می‌کند؟ لزوماً فکر نمی‌کنم.

### هوش TypeScript

بله، می‌شنوم شما را از طریق صفحهٔ کامپیوتر فریاد می‌زنید. بله، می‌دانم TypeScript آنچه اطلاعات نوع را پیدا می‌کند (یا infer می‌کند) به ویرایشگر کد شما ارائه می‌دهد که به شکل autocompleteهای هوشمند، نشانگرهای هشدار inline مفید و غیره می‌آید.

اما استدلال می‌کنم که حتی *آن‌ها* به خودی خود شما را به‌عنوان توسعه‌دهنده آگاه‌تر از نوع نمی‌کنند.

چرا؟ چون آگاهی از نوع *فقط* دربارهٔ تجربهٔ نویسندگی نیست. همچنین دربارهٔ تجربهٔ خواندن است، شاید حتی بیشتر. و همهٔ مکان‌ها/مکانیزم‌هایی که کد خوانده می‌شود، دسترسی به بهره‌گیری از همهٔ هوش اضافی را ندارند.

ببینید، جادوی language-server که هوش را به ویرایشگر کد شما پمپ می‌کند بدون شک شگفت‌انگیز است. باحال و super مفید است.

و از TypeScript به‌عنوان ابزاری که چیزهایی دربارهٔ **کد JS** من infer می‌کند و از طریق integrationهای دلپذیر ویرایشگر کد به من hints و پیشنهادات می‌دهد کینه‌ای ندارم. فقط لزوماً نمی‌خواهم *مجبور* به annotate کردن اطلاعات نوع به روشی بسیار خاص باشم فقط برای ساکت کردن شکایت‌های ابزار.

### نوار بالای TypeScript

اما حتی اگر همهٔ آن را داشتم/می‌داشتم، هنوز ***کافی*** نیست برای fully آگاه از نوع بودن، هم به‌عنوان code-author و هم به‌عنوان code-reader.

این ابزارها هر خطای نوعی که می‌تواند رخ دهد را catch نمی‌کنند، هر چقدر می‌خواهیم به خودمان بگوییم می‌توانند، و هر چقدر hoop و contortion تحمل می‌کنیم تا آرزو کنیم چنین شود. همهٔ تلاش‌ها برای coax و *coerce* کردن ابزار به catch کردن آن خطاهای nuanced، از طریق پیچیدگی بی‌پایان افزایش‌یابندهٔ ترفندهای سینتکس نوع،... در بهترین حالت، effort misplaced است.

علاوه بر این، هیچ ابزار چنینی مصون از false positive نیست، شکایت از چیزهایی که در واقع خطا نیستند؛ این ابزارها هرگز به اندازهٔ ما به‌عنوان انسان باهوش نخواهند بود. واقعاً وقتتان را تلف می‌کنید در دنبال کردن ترفند سینتکس quirky برای ساکت کردن شکایت‌های ابزار.

فقط جایگزینی وجود ندارد، اگر می‌خواهید واقعاً code-author و code-reader آگاه از نوع باشید، از یادگیری نحوهٔ کار سیستم نوع built-in زبان. و بله، یعنی هر توسعه‌دهندهٔ تیمتان باید effort یادگیری آن را صرف کند. نمی‌توانید این چیزها را برای attainable‌تر بودن برای توسعه‌دهندگان کم‌تجربه‌تر پروژه/تیم رقیق کنید.

حتی اگر فرض کنیم می‌توانید از ۱۰۰٪ همهٔ coercionهای *implicit* اجتناب کنید — نمی‌توانید — قطعاً با نیاز به coercionهای *explicit* مواجه خواهید شد — همهٔ برنامه‌ها می‌کنند!

و اگر پاسخ شما به آن واقعیت این است که پیشنهاد دهید فقط بار ذهنی فهمیدن آن‌ها را به ابزاری مثل TypeScript offload کنید... پس متأسفانه باید به شما بگویم که plainly و painfully از نوار *آگاه از نوع* که همهٔ توسعه‌دهندگان را به strive برای آن challenge می‌کنم کوتاه می‌آیید.

اینجا برای شما advocate نمی‌کنم که TypeScript را ditch کنید. اگر دوست دارید، اشکالی ندارد. اما بسیار واضح و passionately شما را challenge می‌کنم: استفاده از TypeScript به‌عنوان crutch را متوقف کنید. prostrating خود به appease کردن موتور overlordهای TypeScript را متوقف کنید. chasing احمقانهٔ هر type rabbit در هر syntactic hole را متوقف کنید.

از نظر من، رابطهٔ غم‌انگیز معکوسی بین استفاده از ابزارهای آگاه از نوع (مثل TypeScript) و desire/effort برای pursue کردن آگاهی واقعی از نوع به‌عنوان code-author و code-reader وجود دارد. هر چه بیشتر به TypeScript تکیه کنید، به‌نظر می‌رسد بیشتر وسوسه و تشویق می‌شوید توجه خود را از سیستم نوع JS (و به‌ویژه، از coercion) به سیستم نوع جایگزین TypeScript منتقل کنید.

متأسفانه، TypeScript هرگز نمی‌تواند کاملاً از سیستم نوع JS فرار کند، چون نوع‌های TypeScript توسط کامپایلر *erase* می‌شوند و آنچه باقی می‌ماند فقط JS است که موتور JS باید با آن contend کند.

### برابری آگاه از نوع

این فصل طولانی و پرپیچ‌وخم را با یک نمونهٔ نهایی دیگر بسته می‌کنم، مدل‌سازی نحوهٔ فکر من که توسعه‌دهندگان باید — مسلح به تفکر انتقادی بیشتر از conformism bandwagon — به برنامه‌نویسی آگاه از نوع نزدیک شوند، چه از ابزاری مثل TypeScript استفاده کنید یا نه.

دوباره مقایسه‌های برابری (`==` در مقابل `===`) را از نظر آگاهی از نوع بررسی می‌کنیم. قبلاً در این فصل قول دادم موردی برای `==` بر `===` بسازم، پس اینجاست.

بیایید آنچه دربارهٔ `==` و `===` تا الان می‌دانیم را دوباره بیان/خلاصه کنیم:

۱. اگر نوع‌های عملوندهای `==` مطابقت کنند، *دقیقاً همان* رفتار `===` را دارد.

۲. اگر نوع‌های عملوندهای `===` مطابقت نکنند، همیشه `false` برمی‌گرداند.

۳. اگر نوع‌های عملوندهای `==` مطابقت نکنند، اجازهٔ coercion هر عملوند (معمولاً ترجیح مقادیر نوع عددی) را می‌دهد تا نوع‌ها بالاخره مطابقت کنند؛ وقتی مطابقت کردند، (۱) را ببینید.

خب، بیایید آن واقعیت‌ها را بگیریم و تحلیل کنیم چطور ممکن است در برنامهٔ ما تعامل کنند.

اگر مقایسهٔ برابری `x` و `y` را مثل این انجام می‌دهید:

```js
if ( /* آیا x و y برابرند */ ) {
    // ..
}
```

شرایط ممکنی که ممکن است در آن باشیم، با توجه به نوع‌های `x` و `y`، چیست؟

۱. ممکن است دقیقاً بدانیم چه نوع (هایی) `x` و `y` می‌توانند باشند، چون می‌دانیم آن متغیرها چطور assign می‌شوند.

۲. یا ممکن است نتوانیم بگوییم آن نوع‌ها چه می‌توانند باشند. ممکن است `x` یا `y` هر نوعی باشد، یا حداقل هر کدام از چند نوع مختلف، طوری که ترکیب‌های ممکن نوع‌ها در مقایسه برای فهم/پیش‌بینی خیلی پیچیده است.

آیا می‌توانیم موافق باشیم که (۱) بسیار ترجیح‌داده‌شده‌تر از (۲) است؟ آیا می‌توانیم further موافق باشیم که (۱) نشان‌دهندهٔ نوشتن کد با شیوهٔ آگاه از نوع است، در حالی که (۲) نشان‌دهندهٔ کدی است که نوعاً *ناآگاه* از نوع است؟

اگر از TypeScript استفاده می‌کنید، بسیار احتمالاً از نوع‌های `x` و `y` آگاهید، درست؟ حتی اگر از TypeScript استفاده نمی‌کنید، قبلاً نشان دادیم که می‌توانید قدم‌های عمدی برای نوشتن کد به‌گونه‌ای بردارید که نوع‌های `x` و `y` شناخته و آشکار باشند.

#### (۲) نوع‌های نامعلوم

اگر در سناریوی (۲) هستید، ادعا می‌کنم کد شما در وضعیت مشکل است. کد شما کمتر از ایده‌آل است. کد شما نیاز به refactor دارد. بهترین کار، اگر کدی در این وضعیت پیدا کردید، این است... fix کنید!

کد را تغییر دهید تا آگاه از نوع شود. اگر یعنی استفاده از TypeScript و حتی insert کردن برخی type annotationها، انجام دهید. یا اگر احساس می‌کنید می‌توانید با *فقط JS* به وضعیت آگاه از نوع برسید، آن را انجام دهید. به هر حال، هر کاری می‌توانید برای رسیدن به سناریوی (۱) انجام دهید.

اگر نمی‌توانید از type-aware بودن کدی که این مقایسهٔ برابری بین `x` و `y` را انجام می‌دهد اطمینان حاصل کنید، و گزینهٔ دیگری ندارید، پس قطعاً *باید* از عملگر strict-equality `===` استفاده کنید. انجام ندادن این کار supremely irresponsible خواهد بود.

```js
if (x === y) {
    // ..
}
```

اگر دربارهٔ نوع‌ها چیزی نمی‌دانید، چطور می‌توانید (یا هر خوانندهٔ آیندهٔ کد) ایده‌ای از نحوهٔ رفتار مراحل coercive در `==` داشته باشید!؟ نمی‌توانید.

تنها کار مسئولانه استفاده از `===` و اجتناب از coercion است.

اما این واقعیت را از دست ندهید: فقط وقتی `===` را انتخاب می‌کنید که به‌عنوان آخرین راه‌حل، وقتی کدتان آنقدر type-unaware — اِه، type-broken! — است که انتخاب دیگری ندارد.

#### (۱) نوع‌های شناخته‌شده

خب، فرض کنیم به‌جای آن در سناریوی (۱) هستید. نوع‌های `x` و `y` را می‌دانید. در کد بسیار واضح است این مجموعهٔ باریک نوع‌های شرکت‌کننده در بررسی برابری چه می‌توانند باشند.

عالی!

اما هنوز دو sub-condition ممکن ممکن است در آن باشید:

* (۱a): `x` و `y` ممکن است از قبل از همان نوع باشند، چه هر دو `string` باشند، `number` باشند و غیره.

* (۱b): `x` و `y` ممکن است از نوع‌های متفاوت باشند.

هر یک از این موارد را جداگانه در نظر بگیریم.

##### (۱a) نوع‌های شناخته‌شدهٔ مطابق

اگر نوع‌ها در مقایسهٔ برابری مطابقت کنند (هر چه باشند)، از قبل می‌دانیم که `==` و `===` دقیقاً همان کار را می‌کنند. مطلقاً تفاوتی نیست.

جز اینکه `==` *یک کاراکتر* کوتاه‌تر است. بیشتر توسعه‌دهندگان به‌طور غریزی احساس می‌کنند که terse‌ترین اما معادل نسخهٔ چیزی اغلب ترجیح‌داده‌شده باشد. البته جهانی نیست، اما حداقل ترجیح کلی است.

```js
// این بهترین است
if (x == y) {
    // ..
}
```

در این مورد خاص، یک `=` اضافی هیچ کاری برای واضح‌تر کردن کد برای ما نمی‌کند. در واقع، این مقایسه را بدتر می‌کند!

```js
// این strictly بدتر اینجاست!
if (x === y) {
    // ..
}
```

چرا بدتر است؟

چون در سناریوی (۲)، از قبل ثابت کردیم که `===` برای last-resort وقتی استفاده می‌شود که به اندازهٔ کافی/چیزی دربارهٔ نوع‌ها نمی‌دانیم تا بتوانیم نتیجه را پیش‌بینی کنیم. وقتی از `===` استفاده می‌کنیم که مطمئن شویم از coercion اجتناب می‌کنیم وقتی می‌دانیم coercion می‌تواند رخ دهد.

اما اینجا اعمال نمی‌شود! از قبل می‌دانیم که coercion رخ نمی‌دهد. دلیلی برای گیج کردن خواننده با `===` اینجا نیست. اگر در جایی که از قبل *می‌دانید* نوع‌ها — و علاوه بر این، مطابقت دارند! — از `===` استفاده کنید، در واقع ممکن است سیگنال mixed به خواننده بفرستد. ممکن است فرض کرده بودند می‌دانند چه اتفاقی در بررسی برابری می‌افتد، اما بعد `===` را می‌بینند و خودشان را second guess می‌کنند!

دوباره، برای بیان واضح، اگر نوع‌های مقایسهٔ برابری را می‌دانید و می‌دانید مطابقت دارند، فقط یک انتخاب درست وجود دارد: `==`.

```js
// به این گزینه بچسبید
if (x == y) {
    // ..
}
```

##### (۱b) نوع‌های شناخته‌شدهٔ نامطابق

خب، در سناریوی نهایی هستیم. باید `x` و `y` را مقایسه کنیم و نوع‌هایشان را می‌دانیم، اما همچنین می‌دانیم نوع‌هایشان **یکسان نیستند**.

کدام عملگر باید اینجا استفاده کنیم؟

اگر `===` را انتخاب کنید، اشتباه بزرگی کرده‌اید. چرا!؟ چون `===` با نوع‌های نامطابق شناخته‌شده هرگز، هرگز، هرگز `true` برنمی‌گرداند. همیشه شکست می‌خورد.

```js
// `x` و `y` نوع‌های متفاوت دارند؟
if (x === y) {
    // تبریک، این کد اینجا هرگز اجرا نخواهد شد
}
```

خب. پس `===` وقتی نوع‌ها شناخته‌شده و نامطابق‌اند حذف می‌شود. تنها انتخاب دیگرمان چیست؟

خب، در واقع دوباره دو گزینه داریم. می‌توانیم تصمیم بگیریم:

* (۱b-۱): بیایید کد را طوری تغییر دهیم که سعی در انجام بررسی برابری با نوع‌های شناخته‌شدهٔ نامطابق نکنیم؛ این می‌تواند شامل اجبار صریح یک یا هر دو مقدار باشد تا نوع‌ها الان مطابقت کنند، در آن صورت به سناریوی (۱a) برگردید.

* (۱b-۲): اگر می‌خواهیم نوع‌های شناخته‌شدهٔ نامطابق را برای برابری مقایسه کنیم و می‌خواهیم به هر امیدی که آن بررسی عبور کند، *باید* از `==` استفاده کنیم، چون تنها یکی از عملگرهای برابری است که می‌تواند یک یا هر دو عملوند را تا مطابقت نوع‌ها اجبار کند.

```js
// `x` و `y` نوع‌های متفاوت دارند،
// پس بگذاریم JS آن‌ها را برای مقایسهٔ برابری اجبار کند
if (x == y) {
    // .. (پس، می‌گویید شانسی هست؟)
}
```

همین. تمام شد. هر شرایط ممکن مقایسهٔ برابری حساس به نوع (بین `x` و `y`) را بررسی کردیم.

#### خلاصهٔ مقایسهٔ برابری حساس به نوع

مورد برای همیشه ترجیح دادن `==` بر `===` به‌شرح زیر است:

۱. چه از TypeScript استفاده کنید یا نه — اما به‌ویژه اگر *از* TypeScript استفاده می‌کنید — هدف باید این باشد که هر قسمت از کد، از جمله همهٔ مقایسه‌های برابری، *آگاه از نوع* باشد.

۲. اگر نوع‌ها را می‌دانید، همیشه باید `==` را ترجیح دهید.

    - در موردی که نوع‌ها مطابقت دارند، `==` هم کوتاه‌تر و هم مناسب‌تر برای بررسی است.

    - در موردی که نوع‌ها مطابقت ندارند، `==` تنها عملگری است که می‌تواند عملوند(ها) را تا مطابقت نوع‌ها اجبار کند، پس تنها راهی است که چنین بررسی‌ای می‌تواند امید عبور داشته باشد.

۳. در نهایت، فقط اگر *نمی‌توانید* نوع‌ها را بدانید/پیش‌بینی کنید، به دلایلی ناامیدکننده، و گزینهٔ دیگری ندارید، به استفاده از `===` به‌عنوان last resort fallback کنید. و احتمالاً یک comment کد آنجا اضافه کنید که چرا `===` استفاده می‌شود را بپذیرد و شاید prompt کند که توسعه‌دهندهٔ آینده بعداً کد را برای fix کردن آن کمبود و حذف crutch `===` تغییر دهد.

#### مشکل ناسازگاری TypeScript

بگذارید super واضح باشم: اگر از TypeScript به‌درستی استفاده می‌کنید و نوع‌های مقایسهٔ برابری را می‌دانید، استفاده از `===` برای آن مقایسه فقط plain *اشتباه* است! نقطه.

مشکل این است که TypeScript به‌طور عجیب و ناامیدکننده هنوز از شما می‌خواهد از `===` استفاده کنید، مگر اینکه از قبل بداند نوع‌ها مطابقت دارند.

این به این دلیل است که TypeScript یا fully آگاهی از نوع و coercion را نمی‌فهمد، یا — و این حتی بیشتر خشم‌آور است! — fully می‌فهمد اما همچنان سیستم نوع JS را آنقدر despise می‌کند که حتی basic‌ترین نوع استدلال آگاه از نوع را eschew کند.

باور نمی‌کنید؟ فکر می‌کنید خیلی سخت‌گیرانه‌ام؟ این را در TypeScript امتحان کنید: [^TSExample2]

```js
let result = (42 == "42");
// This condition will always return 'false' since
// the types 'number' and 'string' have no overlap.
```

برای توصیف چقدر آن آزاردهنده است برای من کلمات کم دارم. اگر به این فصل طولانی و سنگین توجه کرده‌اید، می‌دانید که TypeScript اساساً به اینجا دروغ می‌گوید. البته `42 == "42"` در JS مقدار `true` تولید می‌کند.

خب، دروغ نیست، اما fundamental truth را افشا می‌کند که بسیاری هنوز fully appreciate نمی‌کنند: TypeScript کاملاً قوانین عادی سیستم نوع JS را دور می‌ریزد، چون موضع TypeScript این است که سیستم نوع JS — و به‌ویژه، coercion implicit — بد هستند و باید جایگزین شوند.

در دنیای TypeScript، `42` و `"42"` هرگز نمی‌توانند با یکدیگر برابر باشند. از این رو پیام خطا. اما در سرزمین JS، `42` و `"42"` قطعاً با یکدیگر coercively برابرند. و معتقدم مورد قوی‌ای اینجا ساختم که آن‌ها *باید* به‌عنوان coercively equivalent امن فرض شوند.

چیزی که حتی بیشتر آزارم می‌دهد این است که TypeScript انواع ناسازگاری‌ها در این respect دارد. TypeScript کاملاً با coercion *implicit* در این کد مشکلی ندارد:

```js
irony = `The value '42' and ${42} are coercively equal.`;
```

`42` وقتی در جمله interpolate می‌شود به‌طور implicit به رشته اجبار می‌شود. چرا TypeScript با این coercion implicit مشکلی ندارد، اما با coercion implicit `42 == "42"` دارد؟

TypeScript شکایتی از این کد هم ندارد:

```js
API_BASE_URL = "https://some.tld/api/2";
if (API_BASE_URL) {
    // ..
}
```

چرا `ToBoolean()` coercion implicit OK است، اما `ToNumber()` در الگوریتم `==` نیست؟

شما را به تفکر می‌گذارم: آیا واقعاً فکر می‌کنید ایدهٔ خوبی است کدی بنویسید که در نهایت در موتور JS اجرا می‌شود، اما از ابزار و سبک کدی استفاده کنید که عمداً بیشتر یک ستون کامل زبان JS را eject کرده است؟ علاوه بر این، آیا اشکالی ندارد که با انواع استثناهای ناسازگار flip-flop هم کرده، صرفاً برای cater کردن به عادات قدیمی توسعه‌دهندگان JS؟
