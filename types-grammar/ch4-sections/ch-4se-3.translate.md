## Coercionهای عینی

اکنون که همهٔ عملیات abstractای را که JS برای مدیریت coercionهای مختلف تعریف می‌کند پوشش دادیم، وقت آن است توجه خود را به عبارت‌ها/عبارات عینی‌ای معطوف کنیم که در برنامه‌هایمان می‌توانیم استفاده کنیم و این عملیات را فعال می‌کنند.

### To Boolean

برای اجبار مقداری که از نوع `boolean` نیست به آن نوع، به عملیات abstract `ToBoolean()` نیاز داریم، همان‌طور که قبلاً در این فصل توضیح داده شد.

قبل از اینکه بررسی کنیم *چطور* آن را فعال کنیم، بیایید دربارهٔ *چرایی* اجبار `ToBoolean()` بحث کنیم.

از نظر خوانایی کد، *صریح* بودن دربارهٔ coercionهای نوع می‌تواند ترجیح‌داده‌شده باشد (اگرچه نه به‌طور جهانی). اما از نظر عملکردی، رایج‌ترین دلیل اجبار `boolean` وقتی است که داده را به منبع خارجی ارسال می‌کنید — مثلاً ارسال داده به‌صورت JSON به endpointی API — و آن مکان انتظار `true` / `false` را دارد بدون نیاز به انجام coercion.

چندین راه برای فعال‌سازی `ToBoolean()` وجود دارد. شاید *صریح‌ترین* (واضح‌ترین) تابع `Boolean(..)` باشد:

```js
Boolean("hello");               // true
Boolean(42);                    // true

Boolean("");                    // false
Boolean(0);                     // false
```

همان‌طور که در فصل ۳ ذکر شد، به خاطر داشته باشید که `Boolean(..)` بدون کلیدواژهٔ `new` فراخوانی می‌شود تا عملیات abstract `ToBoolean()` را فعال کند.

چندان رایج نیست که توسعه‌دهندگان JS از تابع `Boolean(..)` برای چنین coercionهای صریحی استفاده کنند. اغلب، توسعه‌دهندگان از اصطلاح دوبل‌`!` استفاده می‌کنند:

```js
!!"hello";                      // true
!!42;                           // true

!!"";                           // false
!!0;                            // false
```

`!!` عملگر خودش نیست، حتی اگر این‌طور به‌نظر برسد. در واقع دو بار استفاده از عملگر یکانی `!` است. این عملگر ابتدا هر مقدار غیربولی را اجبار می‌کند، سپس آن را نفی می‌کند. برای خنثی کردن نفی، دومین `!` آن را برمی‌گرداند.

پس... کدام از این دو، `Boolean(..)` یا `!!`، را بیشتر coercion صریح می‌دانید؟

با توجه به برگرداندنی که `!` انجام می‌دهد و باید با `!` دیگر خنثی شود، می‌گویم `Boolean(..)` *صریح‌تر* است — در کار اجبار غیربولی به بولی — تا `!!`. اما در بررسی کد JS متن‌باز، `!!` بسیار بیشتر استفاده می‌شود.

اگر *explicit* را به‌عنوان «مستقیماً و آشکارا انجام‌دهندهٔ یک عمل» تعریف کنیم، `Boolean(..)` از `!!` جلو می‌زند. اما اگر *explicit* را به‌عنوان «به‌طور قابل‌تشخیص انجام‌دهندهٔ یک عمل» تعریف کنیم، `!!` ممکن است جلوتر باشد. آیا پاسخ قطعی اینجا هست؟

در حالی که آن سؤال را در نظر می‌گیرید، بیایید به مکانیزم دیگر JS نگاه کنیم که `ToBoolean()` را زیرپوستی فعال می‌کند:

```js
specialNumber = 42;

if (specialNumber) {
    // ..
}
```

عبارت `if` به `boolean` برای شرط نیاز دارد تا تصمیم کنترل جریان را بگیرد. اگر غیربولی به آن بدهید، coercion `ToBoolean()` انجام می‌شود.

برخلاف عبارت‌های coercion `ToBoolean()` قبلی، مثل `Boolean(..)` یا `!!`، این coercion `if` زودگذر است، چون برنامهٔ JS ما هرگز نتیجهٔ coercion را نمی‌بیند؛ فقط داخلی توسط `if` استفاده می‌شود. برخی ممکن است احساس کنند اگر برنامه مقدار را حفظ/استفاده نکند *واقعاً* coercion نیست. اما شدیداً مخالفم، چون coercion قطعاً بر رفتار برنامه تأثیر می‌گذارد.

بسیاری از انواع عبارت دیگر هم coercion `ToBoolean()` را فعال می‌کنند، از جمله شرط سه‌تایی `? :` و حلقه‌های `for` / `while`. همچنین عملگرهای `&&` (منطقی-AND) و `||` (منطقی-OR) را داریم. مثلاً:

```js
isLoggedIn = user.sessionID || req.cookie["Session-ID"];

isAdmin = isLoggedIn && ("admin" in user.permissions);
```

برای هر دو عملگر، عبارت سمت چپ ابتدا ارزیابی می‌شود؛ اگر از قبل `boolean` نباشد، coercion `ToBoolean()` برای تولید مقدار برای تصمیم شرطی فعال می‌شود.

| NOTE: |
| :--- |
| برای توضیح مختصر این عملگرها: برای `||`، اگر مقدار عبارت سمت چپ (پس از coercion در صورت نیاز) `true` باشد، مقدار پیش‌coercion برگردانده می‌شود؛ در غیر این صورت عبارت سمت راست ارزیابی و برگردانده می‌شود (بدون coercion). برای `&&`، اگر مقدار عبارت سمت چپ (پس از coercion در صورت نیاز) `false` باشد، مقدار پیش‌coercion برگردانده می‌شود؛ در غیر این صورت عبارت سمت راست ارزیابی و برگردانده می‌شود (بدون coercion). به عبارت دیگر، هر دو `&&` و `||` coercion `ToBoolean()` عملوند سمت چپ را برای تصمیم‌گیری اجبار می‌کنند، اما نتیجهٔ نهایی هیچ‌کدام از عملگرها در واقع به `boolean` اجبار نمی‌شود. |

در قطعهٔ قبلی، علیرغم دلالت‌های نام‌گذاری، بعید است `isLoggedIn` واقعاً `boolean` باشد؛ و اگر truthy باشد، `isAdmin` هم `boolean` نخواهد بود. آن نوع کد کاملاً رایج است، اما قطعاً خطرناک است که انواع `boolean` فرض‌شدهٔ نتیجه واقعاً آنجا نیستند. این مثال و این عملگرها را در فصل بعد دوباره بررسی می‌کنیم.

آیا این انواع عبارت‌ها/عبارات (مثلاً `if (..)`، `||`، `&&` و غیره) coercion *explicit* یا *implicit* را در تصمیم‌گیری شرطی خود نشان می‌دهند؟

دوباره فکر می‌کنم بستگی به دیدگاه شما دارد. مشخصات به‌طور نسبتاً صریح دیکته می‌کند که آن‌ها فقط با مقادیر شرطی `boolean` تصمیم می‌گیرند و در صورت دریافت غیربولی coercion می‌خواهند. از سوی دیگر، استدلال قوی هم می‌تواند مطرح شود که هر coercion داخلی اثری ثانویه (implicit) به کار اصلی `if` / `&&` / و غیره است.

علاوه بر این، همان‌طور که قبلاً در بحث `ToBoolean()` ذکر شد، برخی افراد هیچ فعال‌سازی `ToBoolean()` را coercion نمی‌دانند.

فکر می‌کنم این کشش زیادی است. نظر من: `Boolean(..)` مطلوب‌ترین شکل coercion *explicit* است. فکر می‌کنم `!!`، `if`، `for`، `while`، `&&` و `||` همگی *به‌طور ضمنی* غیربولی‌ها را اجبار می‌کنند، اما با آن مشکلی ندارم.

از آنجا که بیشتر توسعه‌دهندگان، از جمله نام‌های معروف مثل داگ کروفورد، در عمل از coercionهای implicit (بولی) در کدشان استفاده می‌کنند[^CrockfordIfs]، فکر می‌کنم بتوانیم بگوییم که حداقل *برخی اشکال* coercion *implicit* به‌طور گسترده قابل قبول‌اند، صرف‌نظر از بلاغت فراگیر خلاف آن.

### To String

همانند `ToBoolean()`، چندین راه برای فعال‌سازی coercion `ToString()` وجود دارد (همان‌طور که قبلاً در فصل بحث شد). تصمیم کدام رویکرد به‌طور مشابه ذهنی است.

مثل تابع `Boolean(..)`، تابع `String(..)` (بدون کلیدواژهٔ `new`) راه اصلی فعال‌سازی coercion *explicit* `ToString()` است:

```js
String(true);                   // "true"
String(42);                     // "42"
String(-0);                     // "0"
String(Infinity);               // "Infinity"

String(null);                   // "null"
String(undefined);              // "undefined"
```

با این حال، `String(..)` بیش از *فقط* فعال‌سازی `ToString()` است. مثلاً:

```js
String(Symbol("ok"));           // "Symbol(ok)"
```

این کار می‌کند، چون coercion *explicit* مقادیر `symbol` مجاز است. اما در مواردی که symbol *به‌طور ضمنی* به رشته اجبار می‌شود (مثلاً `Symbol("ok") + ""`)، عملیات زیربنایی `ToString()` استثنا پرتاب می‌کند. این ثابت می‌کند که `String(..)` بیش از فقط فعال‌سازی `ToString()` است. بیشتر دربارهٔ coercion *implicit* رشتهٔ symbol در ادامه.

اگر `String(..)` را با مقدار شیء (مثلاً آرایه و غیره) فراخوانی کنید، عملیات `ToPrimitive()` را فعال می‌کند (از طریق عملیات `ToString()`)، که سپس به دنبال متد `toString()` آن مقدار می‌گردد و آن را فراخوانی می‌کند:

```js
String([1,2,3]);                // "1,2,3"

String(x => x + 1);             // "x => x + 1"
```

علاوه بر `String(..)`، هر مقدار primitive غیر nullish (نه `null` و نه `undefined`) می‌تواند در wrapper شیء مربوطش auto-box شود (فصل ۳ را ببینید)، و متد قابل‌فراخوانی `toString()` را فراهم کند.

```js
true.toString();                // "true"
42..toString();                 // "42"
-0..toString();                 // "0"
Infinity.toString();            // "Infinity"
Symbol("ok").toString();        // "Symbol(ok)"
```

| NOTE: |
| :--- |
| به خاطر داشته باشید، این متدهای `toString()` لزوماً عملیات `ToString()` را فعال نمی‌کنند، آن‌ها فقط قوانین خودشان را برای نحوهٔ نمایش مقدار به‌صورت رشته تعریف می‌کنند. |

همان‌طور که با `String(..)` لحظه‌ای پیش نشان داده شد، انواع فرعی شیء مختلف — مثل آرایه‌ها، توابع، عبارات منظم، نمونه‌های `Date` و `Error` و غیره — همگی متدهای `toString()` خاص خودشان را تعریف می‌کنند که می‌توان مستقیماً فراخوانی کرد:

```js
[1,2,3].toString();             // "1,2,3"

(x => x + 1).toString();        // "x => x + 1"
```

علاوه بر این، هر plain object که (به‌طور پیش‌فرض) به `Object.prototype` با `[[Prototype]]` لینک شده متد پیش‌فرض `toString()` در دسترس دارد:

```js
({ a : 1 }).toString();         // "[object Object]"
```

آیا رویکرد `toString()` به coercion *explicit* است یا *implicit*؟ دوباره بستگی دارد. قطعاً مکانیزمی خودتوضیحی است که به سمت *explicit* متمایل است. اما اغلب به auto-boxing متکی است که خودش coercion نسبتاً *implicit* است.

بیایید به اصطلاح رایج دیگر — و مشهوراً تأییدشده! — برای اجبار مقدار به رشته نگاه کنیم. از «String Concatenation» در فصل ۲ به یاد دارید، عملگر `+` overload شده تا در صورت رشته بودن هر یک از عملوندها ترجیح concatenation رشته بدهد، و بنابراین در صورت نیاز عملوند غیررشته را به رشته اجبار می‌کند.

در نظر بگیرید:

```js
true + "";                      // "true"
42 + "";                        // "42"
null + "";                      // "null"
undefined + "";                 // "undefined"
```

اصطلاح `+ ""` برای coercion رشته از overload شدن `+` استفاده می‌کند، بدون تغییر مقدار رشتهٔ اجبارشدهٔ نهایی. به هر حال، همهٔ این‌ها با عملوندهای معکوس هم یکسان کار می‌کنند (یعنی `"" + ..`).

| WARNING: |
| :--- |
| تصور غلط بسیار رایج این است که `String(x)` و `x + ""` اساساً coercionهای معادل‌اند، به‌ترتیب فقط *explicit* در مقابل *implicit* در شکل. اما، کاملاً درست نیست! این را در بخش «To Primitive» بعداً در این فصل دوباره بررسی می‌کنیم. |

برخی این را coercion *explicit* می‌دانند، اما فکر می‌کنم واضحاً *implicit*‌تر است، چون از overload شدن `+` استفاده می‌کند؛ علاوه بر این، `""` به‌طور غیرمستقیم برای فعال‌سازی coercion بدون تغییر آن استفاده می‌شود. علاوه بر این، در نظر بگیرید وقتی این اصطلاح با مقدار symbol اعمال می‌شود چه اتفاقی می‌افتد:

```js
Symbol("ok") + "";              // TypeError exception thrown
```

| WARNING: |
| :--- |
| مجاز کردن coercion *explicit* symbolها (`String(Symbol("ok"))`)، اما ممنوع کردن coercion *implicit* (`Symbol("ok") + ""`)، کاملاً عمدی توسط TC39 است. [^SymbolString] احساس شد که symbolها، به‌عنوان primitiveهایی که اغلب در مکان‌هایی استفاده می‌شوند که رشته‌ها در غیر این صورت استفاده می‌شوند، می‌توانند به‌راحتی با رشته‌ها اشتباه گرفته شوند. بنابراین، می‌خواستند مطمئن شوند توسعه‌دهندگان قصد اجبار symbol به رشته را بیان می‌کنند، امیدوارانه از بسیاری از آن سردرگمی‌های پیش‌بینی‌شده اجتناب کنند. این یکی از موارد *بسیار نادر* است که طراحی زبان نظر خود را دربارهٔ coercionهای *explicit* در مقابل *implicit* ابراز می‌کند و در واقع بین آن‌ها تبعیض قائل می‌شود. |

چرا استثنا؟ JS، `+ ""` را coercion *implicit* می‌داند، به همین دلیل وقتی با symbol فعال می‌شود استثنا پرتاب می‌شود. فکر می‌کنم این اثباتی نسبتاً محکم است.

با این حال، همان‌طور که در ابتدای این فصل ذکر کردم، برندان آیک از `+ ""`[^BrendanToString] به‌عنوان *بهترین* راه اجبار مقادیر به رشته حمایت می‌کند. فکر می‌کنم این وزن زیادی دارد، از نظر حمایت او از حداقل زیرمجموعه‌ای از شیوه‌های coercion *implicit*. نظر او دربارهٔ coercion *implicit* باید کمی ظریف‌تر از «همه بد است» باشد.

### To Number

coercionهای عددی کمی پیچیده‌تر از coercionهای رشته‌اند، چون می‌توانیم دربارهٔ `number` یا `bigint` به‌عنوان نوع هدف صحبت کنیم. همچنین مجموعهٔ بسیار کوچک‌تری از مقادیری وجود دارد که می‌توانند به‌طور معتبر به‌صورت عددی نمایش داده شوند (هر چیز دیگر `NaN` می‌شود).

بیایید با توابع `Number(..)` و `BigInt(..)` شروع کنیم (بدون کلیدواژهٔ `new`):

```js
Number("42");                   // 42
Number("-3.141596");            // -3.141596
Number("-0");                   // -0

BigInt("42");                   // 42n
BigInt("-0");                   // 0n
```

coercion `Number` که شکست می‌خورد (شناخته‌نشده) منجر به `NaN` می‌شود («Invalid Number» در فصل ۱ را ببینید)، در حالی که `BigInt` استثنا پرتاب می‌کند:

```js
Number("123px");                // NaN

BigInt("123px");
// SyntaxError: Cannot convert 123px to a BigInt
```

علاوه بر این، حتی اگر `42n` به‌عنوان literal `bigint` سینتکس معتبر است، رشتهٔ `"42n"` هرگز نمایش رشتهٔ شناخته‌شدهٔ `bigint` نیست، نه با هیچ‌کدام از اشکال تابع coercive:

```js
Number("42n");                  // NaN

BigInt("42n");
// SyntaxError: Cannot convert 42n to a BigInt
```

با این حال، می‌توانیم رشته‌های عددی با نمایش‌های دیگر اعداد به‌جای اعشار معمول base-10 را اجبار کنیم (فصل ۱ را برای اطلاعات بیشتر ببینید):

```js
Number("0b101010");             // 42

BigInt("0b101010");             // 42n
```

معمولاً `Number(..)` و `BigInt(..)` مقادیر رشته دریافت می‌کنند، اما در واقع لازم نیست. مثلاً، `true` و `false` به معادل‌های عددی معمولشان اجبار می‌شوند:

```js
Number(true);                   // 1
Number(false);                  // 0

BigInt(true);                   // 1n
BigInt(false);                  // 0n
```

همچنین به‌طور کلی می‌توانید بین انواع `number` و `bigint` اجبار کنید:

```js
Number(42n);                    // 42
Number(42n ** 1000n);           // Infinity

BigInt(42);                     // 42n
```

همچنین می‌توانیم از عملگر یکانی `+` استفاده کنیم که معمولاً فرض می‌شود مثل تابع `Number(..)` اجبار می‌کند:

```js
+"42";                          // 42
+"0b101010";                    // 42
```

اما مراقب باشید. اگر coercionها به روش‌های خاص ناامن/نامعتبر باشند، استثنا پرتاب می‌شود:

```js
BigInt(3.141596);
// RangeError: The number 3.141596 cannot be converted to a BigInt

+42n;
// TypeError: Cannot convert a BigInt value to a number
```

واضح است که `3.141596` به امنیت به عدد صحیح اجبار نمی‌شود، چه رسد به `bigint`.

اما پرتاب استثنا توسط `+42n` مورد جالبی است. در مقابل، `Number(42n)` خوب کار می‌کند، پس کمی تعجب‌آور است که `+42n` شکست می‌خورد.

| آن تعجب به‌ویژه محسوس است چون معمولاً فرض می‌شود قرار دادن `+` جلوی عدد فقط یعنی «عدد مثبت»، همان‌طور که `-` جلوی عدد فرض می‌شود یعنی «عدد منفی». اما همان‌طور که در فصل ۱ توضیح داده شد، سینتکس عددی JS (`number` و `bigint`) هیچ سینتکسی برای «مقادیر منفی» نمی‌شناسد. همهٔ literalهای عددی به‌طور پیش‌فرض به‌عنوان «مثبت» parse می‌شوند. اگر `+` یا `-` جلوی آن قرار گیرد، آن‌ها به‌عنوان عملگرهای یکانی اعمال‌شده علیه عدد parse‌شده (مثبت) تلقی می‌شوند. |

خب، پس `+42n` به‌عنوان `+(42n)` parse می‌شود. اما هنوز... چرا `+` اینجا استثنا پرتاب می‌کند؟

ممکن است به یاد داشته باشید وقتی قبلاً نشان دادیم JS اجبار *explicit* رشتهٔ مقادیر symbol را مجاز می‌کند، اما اجبار *implicit* رشته را ممنوع می‌کند؟ همان اتفاق اینجا می‌افتد. طراحی زبان JS عملگر یکانی `+` جلوی مقدار `bigint` را به‌عنوان coercion *implicit* `ToNumber()` تفسیر می‌کند (بنابراین ممنوع!)، اما `Number(..)` به‌عنوان coercion *explicit* `ToNumber()` تفسیر می‌شود (بنابراین مجاز!).

به عبارت دیگر، برخلاف فرض/ادعای رایج، `Number(..)` و `+` قابل تعویض نیستند. فکر می‌کنم `Number(..)` شکل امن‌تر/قابل‌اعتمادتر است.

#### عملیات ریاضی

عملگرهای ریاضی (مثلاً `+`، `-`، `*`، `/`، `%` و `**`) انتظار دارند عملوندهایشان عددی باشند. اگر با آن‌ها غیر`number` استفاده کنید، آن مقدار برای اهداف محاسبهٔ ریاضی به `number` اجبار می‌شود.

مشابه نحوهٔ `x + ""` که اصطلاحی برای اجبار `x` به رشته است، عبارتی مثل `x - 0` به‌طور امن `x` را به عدد اجبار می‌کند.

| WARNING: |
| :--- |
| `x + 0` چندان امن نیست، چون عملگر `+` overload شده تا در صورت رشته بودن هر یک از عملوندها concatenation رشته انجام دهد. عملگر `-` minus مثل آن overload نشده، پس تنها coercion به `number` خواهد بود. البته، `x * 1`، `x / 1` و حتی `x ** 1` هم به‌طور کلی از نظر ریاضی معادل می‌شدند، اما آن‌ها بسیار کمتر رایج‌اند و احتمالاً باید به‌عنوان احتمالاً گیج‌کننده برای خوانندگان کدتان اجتناب شوند. حتی `x % 1` به‌نظر امن می‌رسد، اما می‌تواند skew نقطه‌شناور را معرفی کند («Floating Point Imprecision» در فصل ۲ را ببینید). |

صرف‌نظر از اینکه کدام عملگر ریاضی استفاده شود، اگر coercion شکست بخورد، `NaN` نتیجه است و همهٔ این عملگرها `NaN` را به‌عنوان نتیجهٔ خود منتشر می‌کنند.

#### عملیات بیتی

عملگرهای بیتی (مثلاً `|`، `&`، `^`، `>>`، `<<` و `<<<`) همگی انتظار عملوندهای عددی دارند، اما به‌طور خاص این مقادیر را به اعداد صحیح ۳۲‌بیتی clamp می‌کنند.

اگر مطمئن هستید اعدادی که با آن‌ها سروکار دارید به‌طور امن در محدودهٔ عدد صحیح ۳۲‌بیتی هستند، `x | 0` اصطلاح رایج دیگر است که در صورت نیاز اثر اجبار `x` به `number` را دارد.

علاوه بر این، چون موتورهای JS می‌دانند این مقادیر اعداد صحیح خواهند بود، پتانسیل بهینه‌سازی برای ریاضی فقط عدد صحیح در صورت دیدن `x | 0` وجود دارد. این یکی از چندین «type annotation» توصیه‌شده از تلاش‌های ASM.js[^ASMjs] سال‌ها پیش است.

#### دسترسی به Property

دسترسی به property اشیاء (و دسترسی index آرایه‌ها) جای دیگری است که coercion implicit می‌تواند رخ دهد.

در نظر بگیرید:

```js
myObj = {};

myObj[3] = "hello";
myObj["3"] = "world";

console.log( myObj );
```

از محتوای این شیء چه انتظاری دارید؟ آیا انتظار دو property متفاوت دارید، `3` عددی (نگه‌دارندهٔ `"hello"`) و `"3"` رشته (نگه‌دارندهٔ `"world"`)؟ یا فکر می‌کنید هر دو property در همان مکان هستند؟

اگر آن کد را امتحان کنید، می‌بینید که در واقع شیء با یک property می‌گیریم و `"world"` را نگه می‌دارد. یعنی JS داخلی یا `3` را به `"3"` اجبار می‌کند یا برعکس، وقتی آن دسترسی‌های property انجام می‌شوند.

جالبی، کنسول توسعه‌دهنده ممکن است شیء را تقریباً این‌طور نمایش دهد:

```js
console.log( myObj );
// {3: 'world'}
```

آیا آن `3` آنجا نشان می‌دهد property عددی `3` است؟ نه کاملاً. سعی کنید property دیگری به `myObj` اضافه کنید:

```js
myObj.something = 42;

console.log( myObj )
// {3: 'world', something: 42}
```

می‌بینیم که این کنسول توسعه‌دهنده کلیدهای property رشته را quote نمی‌کند، پس نمی‌توانیم از `3` در مقابل اینکه کنسول `"3"` برای نام کلید استفاده کرده چیزی استنباط کنیم.

بیایید به‌جای آن مشخصات مقدار شیء[^ObjectValue] را بررسی کنیم، جایی که می‌یابیم:

> A property key value is either an ECMAScript String value or a Symbol value. All String and Symbol values, including the empty String, are valid as property keys. A property name is a property key that is a String value.

خب! پس در JS، اشیاء فقط propertyهای رشته (یا symbol) نگه می‌دارند. یعنی باید `3` عددی به رشتهٔ `"3"` اجبار شود، درست؟

در همان بخش مشخصات، بیشتر می‌خوانیم:

> An integer index is a String-valued property key that is a canonical numeric String (see 7.1.21) and whose numeric value is either +0𝔽 or a positive integral Number ≤ 𝔽(253 - 1). An array index is an integer index whose numeric value i is in the range +0𝔽 ≤ i < 𝔽(232 - 1).

اگر کلید property (مثل `"3"`) *شبیه* عدد به‌نظر برسد، به‌عنوان integer index تلقی می‌شود. هوم... این تقریباً به‌نظر برعکس آنچه تازه فرض کردیم می‌رسد، درست؟

با این حال، از نقل‌قول قبلی می‌دانیم که کلیدهای property *فقط* رشته (یا symbol) هستند. پس باید «integer index» اینجا مکان واقعی را توصیف نکند، بلکه استفادهٔ عمدی از `3` در کد JS را به‌عنوان «integer index» بیان‌شده توسط توسعه‌دهنده؛ JS باید همچنان آن را در مکان «canonical numeric String» ذخیره کند.

تلاش‌های استفاده از انواع مقدار دیگر، مثل `true`، `null`، `undefined` یا حتی غیرprimitives (اشیاء دیگر) را در نظر بگیرید:

```js
myObj[true] = 100;
myObj[null] = 200;
myObj[undefined] = 300;
myObj[ {a:1} ] = 400;

console.log(myObj);
// {3: 'world', something: 42, true: 100, null: 200,
// undefined: 300, [object Object]: 400}
```

همان‌طور که می‌بینید، همهٔ آن انواع مقدار دیگر برای اهداف نام property شیء به رشته اجبار شدند.

اما قبل از اینکه خودمان را از این تفسیر که همه چیز (حتی اعداد) به رشته اجبار می‌شود متقاعد کنیم، بیایید به مثال آرایه نگاه کنیم:

```js
myArr = [];

myArr[3] = "hello";
myArr["3"] = "world";

console.log( myArr );
// [empty × 3, 'world']
```

کنسول توسعه‌دهنده احتمالاً آرایه را کمی متفاوت از plain object نمایش می‌دهد. با این حال، همچنان می‌بینیم که این آرایه فقط مقدار واحد `"world"` را در خود دارد، در موقعیت index عددی متناظر با `3`.

آن نوع خروجی به‌نوعی برعکس تفسیر قبلی ما را دلالت می‌کند: که مقادیر آرایه فقط در موقعیت‌های عددی ذخیره می‌شوند. اگر property-name رشتهٔ دیگری به `myArr` اضافه کنیم:

```js
myArr.something = 42;
console.log( myArr );
// [empty × 3, 'world', something: 42]
```

حالا می‌بینیم که این کنسول توسعه‌دهنده موقعیت‌های index عددی در آرایه را *بدون* نام propertyها (مکان‌ها) نمایش می‌دهد، اما property `something` در خروجی نامیده شده است.

همچنین درست است که موتورهای JS مثل v8 تمایل دارند، به دلایل بهینه‌سازی عملکرد، به‌طور خاص propertyهای شیء که رشته‌های شبیه عدد هستند را به‌عنوان ذخیره‌شده در موقعیت‌های عددی مثل آرایه‌ها special-case کنند. پس حتی اگر برنامهٔ JS طوری عمل کند که انگار نام property `"3"` است، در واقع زیرپوست، v8 ممکن است آن را مثل اجبار به `3` رفتار کند!

از همهٔ این چه می‌گیریم؟

مشخصات به‌وضوح به ما می‌گوید که رفتار propertyهای شیء این است که مثل رشته (یا symbol) تلقی شوند. یعنی می‌توانیم فرض کنیم استفاده از `3` برای دسترسی به مکان روی شیء اثر داخلی اجبار آن نام property به `"3"` را خواهد داشت.

اما با آرایه‌ها، معنایی نوعاً معکوس مشاهده می‌کنیم: استفاده از `"3"` به‌عنوان نام property اثر دسترسی به موقعیت index عددی `3` را دارد، انگار رشته به عدد اجبار شده. اما این بیشتر فقط نتیجهٔ این واقعیت است که آرایه‌ها همیشه تمایل به رفتار به‌عنوان index عددی دارند، و/یا شاید بازتابی از جزئیات پیاده‌سازی/بهینه‌سازی زیربنایی در موتور JS.

قسمت مهم این است که باید تشخیص دهیم اشیاء نمی‌توانند به‌سادگی هر مقداری را به‌عنوان نام property استفاده کنند. اگر چیزی غیر از رشته یا عدد باشد، می‌توانیم انتظار داشته باشیم که coercion آن مقدار *رخ خواهد داد*.

باید انتظار داشته باشیم و برای آن برنامه‌ریزی کنیم تا اجازه ندهیم با باگ‌ها در راه ما را غافلگیر کند!

### To Primitive

بیشتر عملگرها در JS، از جمله آن‌هایی که با coercion به `string` و `number` دیدیم، برای اجرا علیه مقادیر primitive طراحی شده‌اند. وقتی هر یک از این عملگرها به‌جای آن علیه مقدار شیء استفاده شود، الگوریتم abstract `ToPrimitive` (همان‌طور که قبلاً توضیح داده شد) برای اجبار شیء به primitive فعال می‌شود.

بیایید شیءای تنظیم کنیم که بتوانیم برای بررسی نحوهٔ رفتار عملیات مختلف از آن استفاده کنیم:

```js
spyObject = {
    toString() {
        console.log("toString() invoked!");
        return "10";
    },
    valueOf() {
        console.log("valueOf() invoked!");
        return 42;
    },
};
```

این شیء هر دو متد `toString()` و `valueOf()` را تعریف می‌کند و هر کدام مقدار نوع متفاوتی برمی‌گردانند (`string` در مقابل `number`).

بیایید برخی از عملیات coercion که قبلاً دیدیم را امتحان کنیم:

```js
String(spyObject);
// toString() invoked!
// "10"

spyObject + "";
// valueOf() invoked!
// "42"
```

واو! شرط می‌بندم چند نفر از شما خوانندگان تعجب کردید؛ قطعاً من کردم. بسیار رایج است که مردم ادعا کنند `String(..)` و `+ ""` اشکال معادل فعال‌سازی عملیات `ToString()` هستند. اما واضحاً نیستند!

تفاوت به *hint*‌ای برمی‌گردد که هر عملیات به `ToPrimitive()` می‌دهد. `String(..)` واضحاً `"string"` را به‌عنوان *hint* می‌دهد، در حالی که اصطلاح `+ ""` *hint* نمی‌دهد (مشابه *hinting* `"number"`). اما این جزئیات را از دست ندهید: حتی اگر `+ ""` فراخوانی `valueOf()` کند، وقتی مقدار primitive عددی `42` برمی‌گرداند، آن مقدار سپس به رشته اجبار می‌شود (از طریق `ToString()`)، پس `"42"` به‌جای `42` می‌گیریم.

ادامه بدهیم:

```js
Number(spyObject);
// valueOf() invoked!
// 42

+spyObject;
// valueOf() invoked!
// 42
```

این مثال دلالت می‌کند که `Number(..)` و عملگر یکانی `+` هر دو coercion `ToPrimitive()` یکسان را انجام می‌دهند (با *hint* `"number"`)، که در مورد ما `42` برمی‌گرداند. چون آن از قبل `number` درخواست‌شده است، مقدار بدون ado بیشتر بیرون می‌آید.

اما اگر `valueOf()` یک `bigint` برگرداند چه؟

```js
spyObject2 = {
    valueOf() {
        console.log("valueOf() invoked!");
        return 42n;  // bigint!
    }
};

Number(spyObject2);
// valueOf() invoked!
// 42     <--- ببین، bigint نیست!

+spyObject2;
// valueOf() invoked!
// TypeError: Cannot convert a BigInt value to a number
```

این تفاوت را قبلاً در بخش «To Number» دیدیم. JS اجبار *explicit* مقدار `42n` bigint به مقدار `42` number را مجاز می‌کند، اما آنچه coercion *implicit* می‌داند را ممنوع می‌کند.

تابع coercion `BigInt(..)` (بدون کلیدواژهٔ `new`) چطور؟

```js
BigInt(spyObject);
// valueOf() invoked!
// 42n    <--- ببین، bigint!

BigInt(spyObject2);
// valueOf() invoked!
// 42n

// *******************************

spyObject3 = {
    valueOf() {
        console.log("valueOf() invoked!");
        return 42.3;
    }
};

BigInt(spyObject3);
// valueOf() invoked!
// RangeError: The number 42.3 cannot be converted to a BigInt
```

دوباره، همان‌طور که در بخش «To Number» دیدیم، `42` می‌تواند به‌طور امن به `42n` اجبار شود. از سوی دیگر، `42.3` نمی‌تواند به‌طور امن به `bigint` اجبار شود.

دیدیم که `toString()` و `valueOf()` به‌طور مختلف فراخوانی می‌شوند، چون coercionهای خاص `string` و `number` / `bigint` انجام می‌شوند.

#### Primitive پیدا نشد؟

اگر `ToPrimitive()` نتواند مقدار primitive تولید کند، استثنا پرتاب می‌شود:

```js
spyObject4 = {
    toString() {
        console.log("toString() invoked!");
        return [];
    },
    valueOf() {
        console.log("valueOf() invoked!");
        return {};
    }
};

String(spyObject4);
// toString() invoked!
// valueOf() invoked!
// TypeError: Cannot convert object to primitive value

Number(spyObject4);
// valueOf() invoked!
// toString() invoked!
// TypeError: Cannot convert object to primitive value
```

اگر می‌خواهید coercionهای to-primitive سفارشی را از طریق `toString()` / `valueOf()` تعریف کنید، مطمئن شوید حداقل از یکی از آن‌ها primitive برگردانید!

#### Object To Boolean

coercionهای `boolean` اشیاء چطور؟

```js
Boolean(spyObject);
// true

!spyObject;
// false

if (spyObject) {
    console.log("if!");
}
// if!

result = spyObject ? "ternary!" : "nope";
// "ternary!"

while (spyObject) {
    console.log("while!");
    break;
}
// while!
```

هر یک از این‌ها `ToBoolean()` را فعال می‌کنند. اما اگر از قبل به یاد دارید، آن الگوریتم هرگز به `ToPrimitive()` تفویض نمی‌کند؛ بنابراین، «valueOf() invoked!» را در خروجی log نمی‌بینیم.

#### Unboxing: Wrapper To Primitive

شکل خاصی از اشیاء که اغلب coercion `ToPrimitive()` می‌شوند: primitiveهای boxed/wrapped (فصل ۳ را ببینید). این coercion خاص شیء-به-primitive اغلب *unboxing* نامیده می‌شود.

در نظر بگیرید:

```js
hello = new String("hello");
String(hello);                  // "hello"
hello + "";                     // "hello"

fortyOne = new Number(41);
Number(fortyOne);               // 41
fortyOne + 1;                   // 42
```

wrapperهای شیء `hello` و `fortyOne` بالا متدهای `toString()` و `valueOf()` پیکربندی‌شده روی خودشان دارند تا مشابه اشیاء `spyObject` / و غیره از مثال‌های قبلی ما رفتار کنند.

مورد خاصی که باید با primitiveهای wrapped-object مراقبش باشیم با `Boolean()` است:

```js
nope = new Boolean(false);
Boolean(nope);                  // true   <--- اوه!
!!nope;                         // true   <--- اوه!
```

به یاد داشته باشید، این به این دلیل است که `ToBoolean()` شیء را با `ToPrimitive` به شکل primitive کاهش *نمی‌دهد*؛ صرفاً مقدار را در جدول داخلی خود جستجو می‌کند، و چون اشیاء عادی (غیر-exotic[^ExoticFalsyObjects]) همیشه truthy‌اند، `true` بیرون می‌آید.

| NOTE: |
| :--- |
| یک gotcha کوچک و زشت است. قطعاً می‌توان استدلال کرد که `new Boolean(false)` باید خود را داخلی به‌عنوان «exotic falsy object» پیکربندی کند. [^ExoticFalsyObjects] متأسفانه، آن تغییر الان، ۲۵ سال در تاریخ JS، به‌راحتی می‌تواند breakage در برنامه‌ها ایجاد کند. بنابراین، JS این gotcha را دست‌نخورده گذاشته است. |

#### Override کردن `toString()` پیش‌فرض

همان‌طور که دیدیم، همیشه می‌توانید `toString()` را روی شیء تعریف کنید تا coercion `ToPrimitive()` مناسب آن را فراخوانی کند. اما گزینهٔ دیگر override کردن `Symbol.toStringTag` است:

```js
spyObject5a = {};
String(spyObject5a);
// "[object Object]"
spyObject5a.toString();
// "[object Object]"

spyObject5b = {
    [Symbol.toStringTag]: "my-spy-object"
};
String(spyObject5b);
// "[object my-spy-object]"
spyObject5b.toString();
// "[object my-spy-object]"

spyObject5c = {
    get [Symbol.toStringTag]() {
        return `myValue:${this.myValue}`;
    },
    myValue: 42
};
String(spyObject5c);
// "[object myValue:42]"
spyObject5c.toString();
// "[object myValue:42]"
```

`Symbol.toStringTag` برای تعریف مقدار رشتهٔ سفارشی برای توصیف شیء در هر بار فراخوانی مستقیم یا ضمنی عملیات پیش‌فرض `toString()` آن از طریق coercion در نظر گرفته شده؛ در غیاب آن، مقدار استفاده‌شده `"Object"` در خروجی رایج `"[object Object]"` است.

سینتکس `get ..` در `spyObject5c` یک *getter* تعریف می‌کند. یعنی وقتی JS سعی می‌کند به این `Symbol.toStringTag` به‌عنوان property دسترسی پیدا کند (به‌طور عادی)، این کد getter باعث می‌شود تابع مشخص‌شدهٔ ما برای محاسبهٔ نتیجه فراخوانی شود. می‌توانیم هر منطق دلخواهی داخل این getter برای تعیین پویای رشتهٔ *tag* برای استفاده توسط متد پیش‌فرض `toString()` اجرا کنیم.

#### Override کردن `ToPrimitive`

می‌توانید به‌طور متناوب کل عملیات پیش‌فرض `ToPrimitive()` را برای هر شیء override کنید، با تنظیم property نماد خاص `Symbol.toPrimitive` برای نگه‌داشتن یک تابع:

```js
spyObject6 = {
    [Symbol.toPrimitive](hint) {
        console.log(`toPrimitive(${hint}) invoked!`);
        return 25;
    },
    toString() {
        console.log("toString() invoked!");
        return "10";
    },
    valueOf() {
        console.log("valueOf() invoked!");
        return 42;
    },
};

String(spyObject6);
// toPrimitive(string) invoked!
// "25"   <--- نه "10"

spyObject6 + "";
// toPrimitive(default) invoked!
// "25"   <--- نه "42"

Number(spyObject6);
// toPrimitive(number) invoked!
// 25     <--- نه 42 یا "25"

+spyObject6;
// toPrimitive(number) invoked!
// 25
```

همان‌طور که می‌بینید، اگر این تابع را روی شیء تعریف کنید، به‌طور کامل جایگزین عملیات abstract پیش‌فرض `ToPrimitive()` استفاده می‌شود. چون `hint` همچنان به این تابع فراخوانی‌شده (`[Symbol.toPrimitive](..)`) داده می‌شود، می‌توانید در تئوری نسخهٔ خودتان از الگوریتم را پیاده‌سازی کنید، با فراخوانی `toString()`، `valueOf()` یا هر متد دیگر روی شیء (مرجع context `this`).

یا می‌توانید فقط به‌صورت دستی مقدار برگشتی را همان‌طور که بالا نشان داده شد تعریف کنید. به هر حال، JS به‌طور خودکار هیچ‌کدام از متدهای `toString()` یا `valueOf()` را فراخوانی *نمی‌کند*.

| WARNING: |
| :--- |
| همان‌طور که قبلاً در «No Primitive Found?» بحث شد، اگر تابع تعریف‌شدهٔ `Symbol.toPrimitive` در واقع مقداری که primitive است برنگرداند، استثنا دربارهٔ ناتوانی در «...convert object to primitive value» پرتاب می‌شود. مطمئن شوید همیشه مقدار primitive واقعی از چنین تابعی برگردانید! |

### Equality

تا الان، coercionهایی که دیدیم روی مقادیر تکی متمرکز بوده‌اند. اکنون توجه خود را به مقایسه‌های برابری معطوف می‌کنیم که ذاتاً دو مقدار را شامل می‌شوند، که هر یک یا هر دو ممکن است مشمول coercion باشند.

قبلاً در این فصل دربارهٔ چند عملیات abstract برای مقایسهٔ برابری مقدار صحبت کردیم.

مثلاً، عملیات `SameValue()`[^SameValue] سخت‌گیرانه‌ترین مقایسه‌های برابری است، با مطلقاً بدون coercion. واضح‌ترین عملیات JS که به `SameValue()` متکی است:

```js
Object.is(42,42);                   // true
Object.is(-0,-0);                   // true
Object.is(NaN,NaN);                 // true

Object.is(0,-0);                    // false
```

عملیات `SameValueZero()` — به یاد دارید، فقط با تلقی `-0` و `0` به‌عنوان غیرقابل تشخیص از `SameValue()` متفاوت است — در چندین مکان دیگر استفاده می‌شود، از جمله:

```js
[ 1, 2, NaN ].includes(NaN);        // true
```

می‌توانیم انحراف `0` / `-0` از `SameValueZero()` را اینجا ببینیم:

```js
[ 1, 2, -0 ].includes(0);           // true  <--- اوه!

(new Set([ 1, 2, 0 ])).has(-0);     // true  <--- اوف

(new Map([[ 0, "ok" ]])).has(-0);   // true  <--- :(
```

در این موارد، *coercion* (از نوعی!) وجود دارد که `-0` و `0` را غیرقابل تشخیص تلقی می‌کند. نه، این از نظر فنی «coercion» نیست که نوع تغییر می‌کند، اما به‌نوعی تعریف را فریب می‌دهم تا *این* مورد را در بحث گسترده‌تر coercion اینجا *شامل* کنم.

مقایسه کنید متدهای `includes()` / `has()` اینجا که `SameValueZero()` را فعال می‌کنند با utility آرایهٔ قدیمی خوب `indexOf(..)` که به‌جای آن `IsStrictlyEqual()` را فعال می‌کند. این الگوریتم کمی «coercive»‌تر از `SameValueZero()` است، چون مانع می‌شود مقادیر `NaN` هرگز با یکدیگر برابر تلقی شوند:

```js
[ 1, 2, NaN ].indexOf(NaN);         // -1  <--- پیدا نشد
```

اگر این quirks ظریف `includes(..)` و `indexOf(..)` شما را آزار می‌دهد، هنگام جستجو — دنبال تطابق برابری در — برای مقداری در آرایه، می‌توانید از هر «coercive» quicks اجتناب کنید و *اجباراً* سخت‌گیرانه‌ترین تطابق برابری `SameValue()` را از طریق `Object.is(..)` انجام دهید:

```js
vals = [ 0, 1, 2, -0, NaN ];

vals.find(v => Object.is(v,-0));            // -0
vals.find(v => Object.is(v,NaN));           // NaN

vals.findIndex(v => Object.is(v,-0));       // 3
vals.findIndex(v => Object.is(v,NaN));      // 4
```

#### عملگرهای برابری: `==` در مقابل `===`

واضح‌ترین جایی که *coercion* در بررسی‌های برابری دخیل است با عملگر `==` است. صرف‌نظر از هر تصور از پیش‌ساخته‌ای که دربارهٔ `==` دارید، به‌طور بسیار قابل پیش‌بینی رفتار می‌کند و اطمینان می‌دهد هر دو عملوند قبل از انجام بررسی برابری‌اش با نوع‌ها مطابقت دارند.

برای بیان چیزی که ممکن است فوق‌العاده واضح باشد یا نباشد: عملگرهای `==` (و `===`) همیشه یک `boolean` (`true` یا `false`) برمی‌گردانند که نتیجهٔ بررسی برابری را نشان می‌دهد؛ هرگز چیز دیگری برنمی‌گردانند، صرف‌نظر از هر coercion که ممکن است رخ دهد.

حالا، مراحل بحث‌شدهٔ قبلی در فصل برای عملیات `IsLooselyEqual()` را به یاد آورید و مرور کنید. [^LooseEquality] رفتار آن، و بنابراین نحوهٔ عمل `==`، می‌تواند به‌طور عملی با فقط این دو واقعیت در ذهن شهودی شود:

۱. اگر نوع‌های هر دو عملوند یکسان باشند، `==` دقیقاً همان رفتار `===` را دارد — `IsLooselyEqual()` بلافاصله به `IsStrictlyEqual()` تفویض می‌کند. [^StrictEquality]

    مثلاً، وقتی هر دو عملوند مراجع شیء هستند:

    ```js
    myObj = { a: 1 };
    anotherObj = myObj;

    myObj == anotherObj;                // true
    myObj === anotherObj;               // true
    ```

    اینجا، `==` و `===` تعیین می‌کنند که هر دو عملوند مربوطهٔ آن‌ها از نوع مرجع `object` هستند، پس هر دو بررسی برابری یکسان رفتار می‌کنند؛ مراجع شیء را برای برابری مقایسه می‌کنند.

۲. اما اگر نوع‌های عملوند متفاوت باشند، `==` اجازهٔ coercion تا مطابقت را می‌دهد و مقایسهٔ عددی را ترجیح می‌دهد؛ در صورت امکان سعی می‌کند هر دو عملوند را به عدد اجبار کند:

    ```js
    42 == "42";                         // true
    ```

    اینجا، رشتهٔ `"42"` به عدد `42` اجبار می‌شود (نه برعکس)، و بنابراین مقایسه سپس `42 == 42` است و قطعاً باید `true` برگرداند.

مسلح به این دانش، اکنون افسانهٔ رایج را رد می‌کنیم که فقط `===` نوع و مقدار را بررسی می‌کند، در حالی که `==` فقط مقدار را بررسی می‌کند. درست نیست!

در واقع، `==` و `===` هر دو به نوع حساس‌اند، هر کدام نوع‌های عملوندهایشان را بررسی می‌کنند. عملگر `==` اجازهٔ coercion نوع‌های نامطابق را می‌دهد، در حالی که `===` هر coercion را ممنوع می‌کند.

نظر تقریباً به‌طور جهانی نگه‌داشته‌شده این است که باید از `==` به نفع `===` اجتناب کرد. ممکن است یکی از معدود توسعه‌دهندگانی باشم که به‌طور عمومی موردی واضح و صریح برای عکس آن دفاع می‌کنم. فکر می‌کنم دلیل اصلی ترجیح مردم به `===`، فراتر از صرفاً conforming به status quo، عدم صرف زمان برای واقعاً فهمیدن `==` است.

این موضوع را برای ساختن مورد ترجیح `==` بر `===` دوباره بررسی می‌کنم، بعداً در این فصل، در «Type Aware Equality». فقط می‌خواهم، صرف‌نظر از اینکه چقدر الان با من مخالفید، سعی کنید ذهن باز نگه دارید.

#### Nullish Coercion

قبلاً چند عملیات JS را دیدیم که nullish هستند — `null` و `undefined` را به‌طور coercive با یکدیگر برابر تلقی می‌کنند، از جمله عملگر optional-chaining `?.` و عملگر nullish-coalescing `??` («Null'ish» در فصل ۱ را ببینید).

اما `==` واضح‌ترین جایی است که JS برابری coercive nullish را افشا می‌کند:

```js
null == undefined;              // true
```

نه `null` و نه `undefined` هرگز با هیچ مقدار دیگر در زبان به‌طور coercive برابر نخواهند بود، مگر با یکدیگر. یعنی `==` ergonomic می‌کند که این دو مقدار را غیرقابل تشخیص تلقی کنیم.

ممکن است از این قابلیت این‌طور استفاده کنید:

```js
if (someData == null) {
    // `someData` «تنظیم‌نشده» است (یا null یا undefined)،
    // پس آن را به مقداری پیش‌فرض تنظیم کنید
}

// یا:

if (someData != null) {
    // `someData` تنظیم شده است (نه null و نه undefined)،
    // پس به نحوی از آن استفاده کنید
}
```

به یاد داشته باشید که `!=` نفی `==` است، در حالی که `!==` نفی `===` است. تعداد `=`ها را مطابقت ندهید مگر اینکه بخواهید خودتان را گیج کنید!

این دو رویکرد را مقایسه کنید:

```js
if (someData == null) {
    // ..
}

// در مقابل:

if (someData === null || someData === undefined) {
    // ..
}
```

هر دو عبارت `if` دقیقاً یکسان رفتار می‌کنند. کدام را ترجیح می‌دهید بنویسید و کدام را ترجیح می‌دهید بعداً بخوانید؟

منصفانه بگویم، برخی از شما نسخهٔ verbose‌تر معادل `===` را ترجیح می‌دهید. و اشکالی ندارد. مخالفم، فکر می‌کنم نسخهٔ `==` این بررسی *خیلی* بهتر است. و همچنین حفظ می‌کنم که نسخهٔ `==` از نظر روح سبکی با نحوهٔ عمل عملگرهای nullish دیگر مثل `?.` و `??` سازگارتر است.

اما واقعیت جزئی دیگر که ممکن است در نظر بگیرید: در benchmarkهای عملکردی که بارها اجرا کرده‌ام، موتورهای JS می‌توانند بررسی واحد `== null` نشان‌داده‌شده را *کمی سریع‌تر* از ترکیب دو بررسی `===` انجام دهند. به عبارت دیگر، مزیت کوچک اما قابل اندازه‌گیری برای اجازه دادن به `==` JS برای انجام coercion *implicit* nullish نسبت به تلاش برای *explicit* لیست کردن هر دو بررسی خودتان وجود دارد.

متوجه می‌شوم که حتی بسیاری از طرفداران سرسخت `===` تمایل دارند قبول کنند که `== null` حداقل یکی از چنین مواردی است که `==` ترجیح‌داده‌شده است.

#### `==` Boolean Gotcha

علاوه بر برخی coercive corner caseهایی که در بخش بعد به آن‌ها می‌پردازیم، احتمالاً بزرگ‌ترین gotcha که باید با `==` از آن آگاه باشید مربوط به booleanهاست.

خیلی دقیق توجه کنید، چون یکی از بزرگ‌ترین دلایلی است که مردم توسط آن گزیده می‌شوند و سپس از `==` متنفر می‌شوند. اگر توصیهٔ سادهٔ من را (در پایان این بخش) بگیرید، هرگز قربانی نخواهید شد!

عبارت زیر را در نظر بگیرید و فرض کنیم برای یک دقیقه که `isLoggedIn` مقدار `boolean` (`true` یا `false`) نگه *نمی‌دارد*:

```js
if (isLoggedIn) {
    // ..
}

// در مقابل:

if (isLoggedIn == true) {
    // ..
}
```

قبلاً شکل اول عبارت `if` را پوشش دادیم. می‌دانیم `if` به `boolean` برای شرط نیاز دارد، پس در این مورد `isLoggedIn` با جدول جستجو در عملیات abstract `ToBoolean()` به `boolean` اجبار می‌شود. نسبتاً قابل پیش‌بینی است، درست؟

اما به عبارت `isLoggedIn == true` نگاه کنید. فکر می‌کنید همان‌طور رفتار می‌کند؟

اگر غریزهٔ شما *بله* بود، تازه در تلهٔ کوچک حیله‌آمیزی افتادید. به یاد آورید اوایل این فصل وقتی هشدار دادم که قوانین coercion `ToBoolean()` فقط وقتی اعمال می‌شوند که عملیات JS واقعاً آن الگوریتم را فعال کند. اینجا، به‌نظر می‌رسد JS باید این کار را بکند، چون `== true` به‌وضوح نوع مقایسهٔ «مربوط به boolean» به‌نظر می‌رسد.

اما نه. بروید الگوریتم `IsLooselyEqual()` (برای `==`) را اوایل فصل دوباره بخوانید. بروید، صبر می‌کنم. اگر خلاصهٔ من را دوست ندارید، خود الگوریتم مشخصات[^LooseEquality] را بخوانید.

خب، آیا چیزی در آنجا می‌بینید که تحت هر شرایطی فراخوانی `ToBoolean()` را ذکر کند؟

نه!

به یاد داشته باشید: وقتی نوع‌های دو عملوند `==` یکسان نیستند، ترجیح می‌دهد هر دو را به عدد اجبار کند.

`isLoggedIn` ممکن است چه چیزی داشته باشد، اگر `boolean` نباشد؟ خب، می‌تواند مقدار رشته مثل `"yes"` باشد، مثلاً. در آن شکل، `if ("yes") { .. }` واضحاً شرط را عبور می‌دهد و بلوک را اجرا می‌کند.

اما چه اتفاقی با شکل `==` شرط `if` می‌افتد؟ این‌طور عمل می‌کند:

```js
// (1)
"yes" == true

// (2)
"yes" == 1

// (3)
NaN == 1

// (4)
NaN === 1           // false
```

پس به عبارت دیگر، اگر `isLoggedIn` مقداری مثل `"yes"` نگه دارد، بلوک `if (isLoggedIn) { .. }` شرط را عبور می‌دهد، اما بررسی `if (isLoggedIn == true)` عبور نمی‌کند. اوف!

اگر `isLoggedIn` رشتهٔ `"true"` را نگه می‌داشت چه؟

```js
// (1)
"true" == true

// (2)
"true" == 1

// (3)
NaN == 1

// (4)
NaN === 1           // false
```

Facepalm.

اینجا یک پاپ کوییز: `isLoggedIn` چه مقداری باید نگه دارد تا هر دو شکل شرط عبارت `if` عبور کنند؟

...

...

...

...

اگر `isLoggedIn` عدد `1` را نگه می‌داشت چه؟ `1` truthy است، پس شکل `if (isLoggedIn)` عبور می‌کند. و شکل دیگر `==` که coercion را شامل می‌شود:

```js
// (1)
1 == true

// (2)
1 == 1

// (3)
1 === 1             // true
```

اما اگر `isLoggedIn` به‌جای آن رشتهٔ `"1"` را نگه می‌داشت؟ دوباره، `"1"` truthy است، اما coercion `==` چطور؟

```js
// (1)
"1" == true

// (2)
"1" == 1

// (3)
1 == 1

// (4)
1 === 1             // true
```

خب، پس `1` و `"1"` دو مقداری هستند که `isLoggedIn` می‌تواند نگه دارد و برای اجبار همراه با `true` در بررسی برابری `==` امن‌اند. اما اساساً تقریباً هیچ مقدار دیگری برای نگه‌داشتن توسط `isLoggedIn` امن نیست.

اگر بررسی `== false` باشد gotcha مشابهی داریم. چه مقادیری در چنین مقایسه‌ای امن‌اند؟ `""` و `0` کار می‌کنند. اما:

```js
if ([] == false) {
    // این اجرا می‌شود!
}
```

`[]` مقدار truthy است، اما با `false` هم coercively برابر است!؟ اوه.

از این gotchaها با بررسی‌های `== true` و `== false` چه بسازیم؟ پاسخ ساده و روشنی دارم.

هرگز، هرگز، تحت هیچ شرایطی، بررسی `==` انجام ندهید اگر هر طرف مقایسه مقدار `true` یا `false` باشد. به‌نظر می‌رسد مثل coercion خوب `ToBoolean()` رفتار می‌کند، اما حیله‌آمیزانه نمی‌کند و در عوض در انواع coercion corner caseها گرفتار می‌شود (در بخش بعد به آن‌ها می‌پردازیم). و از اشکال `===` هم اجتناب کنید.

وقتی با booleanها سروکار دارید، به اشکال implicitly coercive که واقعاً `ToBoolean()` را فعال می‌کنند بچسبید، مثل `if (isLoggedIn)`، و از اشکال `==` / `===` دور بمانید.
