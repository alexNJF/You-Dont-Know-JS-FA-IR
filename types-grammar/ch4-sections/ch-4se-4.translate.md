## موارد خاص Coercion

تا الان در بیان نظر موافق coercion خود روشن بوده‌ام. و این *فقط* یک نظر است، اگرچه بر اساس تفسیر حقایق حاصل از مطالعهٔ مشخصات زبان و رفتارهای قابل مشاهدهٔ JS است.

این به معنای کامل بودن coercion نیست. چند مورد خاص ناامیدکننده وجود دارد که باید از آن‌ها آگاه باشیم تا در آن چاله‌ها نیفتیم. در صورتی که واضح نباشد، توصیف‌های بعدی من از این موارد خاص فقط نظرهای بیشتر من هستند. نتیجهٔ شما ممکن است متفاوت باشد.

### رشته‌ها

قبلاً دیدیم coercion رشتهٔ آرایه این‌طور به‌نظر می‌رسد:

```js
String([ 1, 2, 3 ]);                // "1,2,3"
```

شخصاً این را بسیار آزاردهنده می‌دانم که `[ ]` اطراف را شامل نمی‌شود. به‌طور خاص، این به این پوچی منجر می‌شود:

```js
String([]);                         // ""
```

پس نمی‌توانیم بگوییم حتی آرایه است، چون فقط رشتهٔ خالی می‌گیریم؟ عالی، JS. این فقط احمقانه است. متأسفم، اما هست. و بدتر می‌شود:

```js
String([ null, undefined ]);        // ","
```

چی!؟ می‌دانیم که `null` به رشتهٔ `"null"` و `undefined` به رشتهٔ `"undefined"` اجبار می‌شوند. اما اگر آن مقادیر در آرایه باشند، به‌طور جادویی فقط به‌عنوان رشته‌های خالی در coercion آرایه-به-رشته *ناپدید* می‌شوند. فقط `","` باقی می‌ماند تا حتی به ما اشاره کند چیزی در آرایه بود! این فقط احمقانه است، همین‌جا.

اشیاء چطور؟ تقریباً به همان اندازه آزاردهنده، اما در جهت مخالف:

```js
String({});                         // "[object Object]"

String({ a: 1 });                   // "[object Object]"
```

اوم... اوکی. حتماً، ممنون JS برای هیچ کمکی در فهمیدن مقدار شیء.

### اعداد

می‌خواهم بدترین ریشهٔ شر coercion corner case را فاش کنم. آماده‌اید!؟

```js
Number("");                         // 0
Number("       ");                  // 0
```

هنوز سرم را از این تکان می‌دهم، و نزدیک به ۲۰ سال است که می‌دانم. هنوز نمی‌فهمم برندان با این چه فکری می‌کرد.

رشتهٔ خالی از هر محتوایی خالی است؛ چیزی برای تعیین نمایش عددی ندارد. `0` قطعاً ***نه*** معادل عددی مقدار عددی گم/نامعتبر است. می‌دانید چه مقدار عددی داریم که برای انتقال آن مناسب است؟ `NaN`. حتی مرا به این نکته نرسانید که فاصلهٔ خالی از رشته‌ها هنگام coercion به عدد حذف می‌شود، پس رشتهٔ خیلی-نه-خالی `"       "` هنوز مثل `""` برای اهداف coercion عددی رفتار می‌شود.

بدتر، به یاد دارید `[]` چطور به رشتهٔ `""` اجبار می‌شود؟ با گسترش:

```js
Number([]);                         // 0
```

اوه! اگر `""` به `0` اجبار نمی‌شد — به یاد دارید، این ریشهٔ همهٔ شر coercion است! — آنگاه `[]` هم به `0` اجبار نمی‌شد.

این فقط پوچ، قلمرو جهان وارونه است.

خیلی رام‌تر، اما هنوز کمی آزاردهنده:

```js
Number("NaN");                      // NaN  <--- accidental!

Number("Infinity");                 // Infinity
Number("infinity");                 // NaN  <--- oops, watch case!
```

رشتهٔ `"NaN"` به‌عنوان مقدار عددی قابل تشخیص تجزیه نمی‌شود، پس coercion شکست می‌خورد و (تصادفاً!) مقدار `NaN` تولید می‌کند. `"Infinity"` صریحاً برای coercion قابل تجزیه است، اما هر casing دیگر، از جمله `"infinity"`، شکست می‌خورد و دوباره `NaN` تولید می‌کند.

این مثال بعدی، شاید اصلاً corner case ندانید:

```js
Number(false);                      // 0
Number(true);                       // 1
```

فقط قرارداد برنامه‌نویس است، legacy از زبان‌هایی که در اصل مقادیر بولی `true` و `false` نداشتند، که `0` را `false` و `1` را `true` رفتار می‌کنیم. اما آیا *واقعاً* منطقی است جهت مخالف برویم؟

این‌طور فکر کنید:

```js
false + true + false + false + true;        // 2
```

واقعاً؟ فکر نمی‌کنم هیچ موردی باشد که رفتار `boolean` به‌عنوان معادل `number` آن در برنامه منطقی باشد. می‌فهمم برعکس، به دلایل تاریخی: `Boolean(0)` و `Boolean(1)`.

اما искренاً فکر می‌کنم `Number(false)` و `Number(true)` (و همچنین اشکال implicit coercion) باید `NaN` تولید کنند، نه `0` / `1`.

### پوچی Coercion

برای اثبات نظر من، پوچی را به سطح ۱۱ ببریم:

```js
[] == ![];                          // true
```

چطور!؟ به‌نظر باورنکردنی است که مقداری بتواند برابر اجباری نفی خودش باشد، درست!؟

اما در چاه coercion پایین بروید:

۱. `[] == ![]`
۲. `[] == false`
۳. `"" == false`
۴. `0 == false`
۵. `0 == 0`
۶. `0 === 0`  ->  `true`

سه پوچی متفاوت علیه ما توطئه کرده‌اند: `String([])`، `Number("")` و `Number(false)`؛ اگر هر یک از این‌ها درست نبود، این نتیجهٔ corner case بی‌معنا رخ نمی‌داد.

اما چیزی را کاملاً روشن می‌کنم: هیچ‌کدام از این‌ها تقصیر `==` نیست. البته اینجا مقصر شناخته می‌شود. اما مقصران واقعی corner caseهای زیربنایی `string` و `number` هستند.
