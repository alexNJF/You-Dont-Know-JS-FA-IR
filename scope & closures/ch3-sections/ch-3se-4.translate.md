# بلوک‌ها به‌عنوان Scope

در حالی که توابع رایج‌ترین واحد scope هستند و قطعاً گسترده‌ترین رویکرد طراحی در اکثریت JS در گردش است، واحدهای دیگر scope ممکن هستند، و استفاده از این واحدهای scope دیگر می‌تواند به کد حتی بهتر و تمیزتر برای نگهداری منجر شود.

بسیاری زبان‌های غیر از JavaScript از Block Scope پشتیبانی می‌کنند، پس توسعه‌دهندگان آن زبان‌ها به ذهنیت عادت دارند، در حالی که کسانی که عمدتاً فقط با JavaScript کار کرده‌اند ممکن است مفهوم را کمی غریب بیابند.

اما حتی اگر هرگز یک خط کد به سبک block-scoped ننوشته باشید، احتمالاً هنوز با این idiom فوق‌العاده رایج در JavaScript آشنا هستید:

```js
for (var i=0; i<10; i++) {
	console.log( i );
}
```

متغیر `i` را مستقیماً داخل سر حلقهٔ for اعلام می‌کنیم، احتمالاً چون *قصد* ما استفاده از `i` فقط در زمینهٔ آن حلقهٔ for است، و اساساً این واقعیت را نادیده می‌گیریم که متغیر در واقع خودش را به scope محصور (تابع یا global) scope می‌کند.

همین است block-scoping. اعلام متغیرها تا حد امکان نزدیک، تا حد امکان محلی، به جایی که استفاده می‌شوند. مثال دیگر:

```js
var foo = true;

if (foo) {
	var bar = foo * 2;
	bar = something( bar );
	console.log( bar );
}
```

فقط در زمینهٔ دستور if از متغیر `bar` استفاده می‌کنیم، پس نوعی منطق دارد که آن را داخل بلوک if اعلام کنیم. با این حال، جایی که متغیرها را اعلام می‌کنیم با `var` مرتبط نیست، چون همیشه به scope محصور تعلق خواهند داشت. این تکه اساساً block-scoping «جعلی» است، به دلایل سبکی، و متکی بر self-enforcement برای استفادهٔ تصادفی نکردن از `bar` در جای دیگر آن scope.

Block scope ابزاری برای گسترش «اصل حداقل ~~امتیاز~~ افشا» [^note-leastprivilege] قبلی از پنهان کردن اطلاعات در توابع به پنهان کردن اطلاعات در بلوک‌های کدمان است.

مثال حلقهٔ for را دوباره در نظر بگیرید:

```js
for (var i=0; i<10; i++) {
	console.log( i );
}
```

چرا کل scope تابع را با متغیر `i` که فقط برای (یا فقط *باید* برای) حلقهٔ for استفاده می‌شود آلوده کنیم؟

اما مهم‌تر، توسعه‌دهندگان ممکن است ترجیح دهند *خودشان* را در برابر استفادهٔ تصادفی (مجدد) از متغیرها خارج از هدف مورد نظرشان چک کنند، مثل صدور خطا دربارهٔ متغیر ناشناخته اگر سعی کنید در جای اشتباه استفاده کنید. Block-scoping (اگر ممکن بود) برای متغیر `i` باعث می‌شد `i` فقط برای حلقهٔ for در دسترس باشد و در صورت دسترسی به `i` در جای دیگر تابع خطا ایجاد کند. این کمک می‌کند متغیرها به روش‌های گیج‌کننده یا سخت‌برای-نگهداری استفادهٔ مجدد نشوند.

اما واقعیت غم‌انگیز این است که، در سطح، JavaScript هیچ تسهیلاتی برای block scope ندارد.

یعنی تا کمی عمیق‌تر کاوش کنید.

### `with`

دربارهٔ `with` در فصل ۲ یاد گرفتیم. در حالی که ساختار مذمومی است، *مثالی* از (شکلی از) block scope است، چون scope ایجادشده از شیء فقط برای طول عمر آن دستور `with` وجود دارد و در scope محصور نیست.

### `try/catch`

واقعیت *بسیار* کم‌شناخته این است که JavaScript در ES3 اعلام متغیر در بند `catch` یک `try/catch` را block-scoped به بلوک `catch` مشخص کرد.

مثلاً:

```js
try {
	undefined(); // illegal operation to force an exception!
}
catch (err) {
	console.log( err ); // works!
}

console.log( err ); // ReferenceError: `err` not found
```

همان‌طور که می‌بینید، `err` فقط در بند `catch` وجود دارد و وقتی سعی می‌کنید جای دیگر ارجاع دهید خطا پرتاب می‌کند.

**توجه:** در حالی که این رفتار مشخص شده و در practically تمام محیط‌های استاندارد JS (شاید به‌جز IE قدیمی) درست است، بسیاری linterها به نظر می‌رسد هنوز شکایت می‌کنند اگر دو یا چند بند `catch` در همان scope داشته باشید که هر کدام متغیر خطای خود را با همان نام شناسه اعلام می‌کنند. این در واقع re-definition نیست، چون متغیرها به‌طور امن block-scoped هستند، اما linterها به نظر می‌رسد هنوز، آزاردهنده، از این واقعیت شکایت می‌کنند.

برای اجتناب از این هشدارهای غیرضروری، برخی devها متغیرهای `catch` خود را `err1`، `err2` و غیره می‌نامند. devهای دیگر به‌سادگی چک linting برای نام‌های متغیر تکراری را خاموش می‌کنند.

طبیعت block-scoping مربوط به `catch` ممکن است واقعیت آکادمیک بی‌فایده به نظر برسد، اما پیوست ب را برای اطلاعات بیشتر دربارهٔ چقدر مفید می‌تواند باشد ببینید.

### `let`

تا اینجا دیدیم که JavaScript فقط برخی رفتارهای طاقچهٔ عجیب دارد که قابلیت block scope را افشا می‌کنند. اگر فقط همین را داشتیم، و *برای سال‌ها همین بود*، آنگاه block scoping برای توسعه‌دهندهٔ JavaScript چندان مفید نمی‌بود.

خوشبختانه، ES6 آن را تغییر می‌دهد و کلمهٔ کلیدی جدید `let` را معرفی می‌کند که کنار `var` به‌عنوان راه دیگری برای اعلام متغیرها قرار می‌گیرد.

کلمهٔ کلیدی `let` اعلام متغیر را به scope هر بلوکی (معمولاً جفت `{ .. }`) که در آن قرار دارد متصل می‌کند. به عبارت دیگر، `let` به‌طور ضمنی scope هر بلوکی را برای اعلام متغیرش hijack می‌کند.

```js
var foo = true;

if (foo) {
	let bar = foo * 2;
	bar = something( bar );
	console.log( bar );
}

console.log( bar ); // ReferenceError
```

استفاده از `let` برای متصل کردن متغیر به بلوک موجود تا حدی ضمنی است. می‌تواند گیج‌کننده باشد اگر به بلوک‌هایی که متغیرها به آن‌ها scope شده‌اند و عادت جابه‌جایی بلوک‌ها، پیچیدن آن‌ها در بلوک‌های دیگر و غیره در حین توسعه و تکامل کد توجه نکنید.

ایجاد بلوک‌های صریح برای block-scoping می‌تواند برخی از این نگرانی‌ها را برطرف کند و واضح‌تر کند کجا متغیرها متصل هستند و کجا نه. معمولاً کد صریح بر کد ضمنی یا ظریف ترجیح دارد. این سبک block-scoping صریح به‌راحتی قابل دستیابی است و طبیعی‌تر با نحوهٔ کار block-scoping در زبان‌های دیگر هماهنگ است:

```js
var foo = true;

if (foo) {
	{ // <-- explicit block
		let bar = foo * 2;
		bar = something( bar );
		console.log( bar );
	}
}

console.log( bar ); // ReferenceError
```

می‌توانیم بلوک دلخواهی برای bind کردن `let` با به‌سادگی شامل کردن جفت `{ .. }` هرکجا که دستور دستور معتبر است ایجاد کنیم. در این مورد، بلوک صریحی *داخل* دستور if ساختیم که ممکن است به‌عنوان کل بلوک برای جابه‌جایی بعداً در refactoring آسان‌تر باشد، بدون تأثیر بر موقعیت و معناشناسی دستور if محصور.

**توجه:** برای راه دیگر بیان block scopeهای صریح، پیوست ب را ببینید.

در فصل ۴ به hoisting می‌پردازیم که دربارهٔ اعلام‌هایی صحبت می‌کند که برای کل scope که در آن رخ می‌دهند موجود در نظر گرفته می‌شوند.

با این حال، اعلام‌های انجام‌شده با `let` *به* کل scope بلوکی که در آن ظاهر می‌شوند hoist نمی‌شوند. چنین اعلام‌هایی تا دستور اعلام به‌طور قابل مشاهده در بلوک «موجود» نخواهند بود.

```js
{
   console.log( bar ); // ReferenceError!
   let bar = 2;
}
```

#### Garbage Collection

دلیل دیگر مفید بودن block-scoping مربوط به closureها و garbage collection برای reclaim کردن حافظه است. اینجا به‌طور خلاصه نشان می‌دهیم، اما مکانیزم closure در فصل ۵ به‌تفصیل توضیح داده می‌شود.

در نظر بگیرید:

```js
function process(data) {
	// do something interesting
}

var someReallyBigData = { .. };

process( someReallyBigData );

var btn = document.getElementById( "my_button" );

btn.addEventListener( "click", function click(evt){
	console.log("button clicked");
}, /*capturingPhase=*/false );
```

تابع callback handler کلیک `click` اصلاً به متغیر `someReallyBigData` نیاز ندارد. یعنی، از نظر تئوری، بعد از اجرای `process(..)`، ساختار دادهٔ بزرگ و سنگین حافظه می‌توانست garbage collected شود. با این حال، کاملاً محتمل است (هرچند وابسته به پیاده‌سازی) که موتور JS هنوز مجبور به نگه داشتن ساختار باشد، چون تابع `click` closure روی کل scope دارد.

Block-scoping می‌تواند به این نگرانی بپردازد و واضح‌تر به موتور بگوید نیازی به نگه داشتن `someReallyBigData` ندارد:

```js
function process(data) {
	// do something interesting
}

// anything declared inside this block can go away after!
{
	let someReallyBigData = { .. };

	process( someReallyBigData );
}

var btn = document.getElementById( "my_button" );

btn.addEventListener( "click", function click(evt){
	console.log("button clicked");
}, /*capturingPhase=*/false );
```

اعلام بلوک‌های صریح برای bind محلی متغیرها ابزار قدرتمندی است که می‌توانید به جعبه ابزار کد خود اضافه کنید.

#### حلقه‌های `let`

مورد خاصی که `let` در آن می‌درخشد در مورد حلقهٔ for است که قبلاً بحث کردیم.

```js
for (let i=0; i<10; i++) {
	console.log( i );
}

console.log( i ); // ReferenceError
```

نه تنها `let` در سر حلقهٔ for `i` را به بدنهٔ حلقهٔ for bind می‌کند، بلکه در واقع آن را به هر *تکرار* حلقه **دوباره bind** می‌کند و مطمئن می‌شود مقدار از انتهای تکرار قبلی حلقه دوباره انتساب یابد.

راه دیگر نشان دادن رفتار binding هر-تکرار که رخ می‌دهد:

```js
{
	let j;
	for (j=0; j<10; j++) {
		let i = j; // re-bound for each iteration!
		console.log( i );
	}
}
```

دلیل جالب بودن این binding هر-تکرار در فصل ۵ هنگام بحث closureها روشن می‌شود.

چون اعلام‌های `let` به بلوک‌های دلخواه متصل می‌شوند نه به scope تابع محصور (یا global)، gotchaهایی وجود دارد که کد موجود وابستگی پنهان به اعلام‌های `var` function-scoped دارد، و جایگزینی `var` با `let` ممکن است هنگام refactoring کد احتیاط اضافی بخواهد.

در نظر بگیرید:

```js
var foo = true, baz = 10;

if (foo) {
	var bar = 3;

	if (baz > bar) {
		console.log( baz );
	}

	// ...
}
```

این کد به‌راحتی re-factor می‌شود به:

```js
var foo = true, baz = 10;

if (foo) {
	var bar = 3;

	// ...
}

if (baz > bar) {
	console.log( baz );
}
```

اما هنگام استفاده از متغیرهای block-scoped مراقب چنین تغییراتی باشید:

```js
var foo = true, baz = 10;

if (foo) {
	let bar = 3;

	if (baz > bar) { // <-- don't forget `bar` when moving!
		console.log( baz );
	}
}
```

پیوست ب را برای سبک جایگزین (صریح‌تر) block-scoping ببینید که ممکن است کد نگهداری/refactor آسان‌تر و قوی‌تر در این سناریوها ارائه دهد.

### `const`

علاوه بر `let`، ES6 `const` را معرفی می‌کند که متغیر block-scoped هم ایجاد می‌کند، اما مقدارش ثابت است. هر تلاشی برای تغییر آن مقدار در زمان بعد منجر به خطا می‌شود.

```js
var foo = true;

if (foo) {
	var a = 2;
	const b = 3; // block-scoped to the containing `if`

	a = 3; // just fine!
	b = 4; // error!
}

console.log( a ); // 3
console.log( b ); // ReferenceError!
```
