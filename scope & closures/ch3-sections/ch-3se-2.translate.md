# پنهان‌سازی در Scope

روش سنتی فکر کردن دربارهٔ توابع این است که تابعی اعلام می‌کنید و سپس کد داخلش اضافه می‌کنید. اما فکر معکوس به‌همان اندازه قدرتمند و مفید است: هر بخش دلخواهی از کدی که نوشته‌اید بردارید و اعلام تابعی دور آن بپیچید، که در عمل کد را «پنهان» می‌کند.

نتیجهٔ عملی ایجاد حباب scope دور کد مورد نظر است، یعنی هر اعلامی (متغیر یا تابع) در آن کد اکنون به scope تابع پوشانندهٔ جدید وابسته می‌شود، نه scope محصور قبلی. به عبارت دیگر، می‌توانید متغیرها و توابع را با محصور کردن آن‌ها در scope یک تابع «پنهان» کنید.

چرا «پنهان» کردن متغیرها و توابع تکنیک مفیدی است؟

دلایل متنوعی برای این پنهان‌سازی مبتنی بر scope وجود دارد. معمولاً از اصل طراحی نرم‌افزار «اصل حداقل امتیاز» [^note-leastprivilege] ناشی می‌شوند، که گاهی «حداقل اقتدار» یا «حداقل افشا» هم نامیده می‌شود. این اصل می‌گوید در طراحی نرم‌افزار، مثل API برای ماژول/شیء، باید فقط حداقل لازم را افشا کنید و بقیه را «پنهان» کنید.

این اصل به انتخاب scope برای محصور کردن متغیرها و توابع گسترش می‌یابد. اگر تمام متغیرها و توابع در global scope بودند، قطعاً برای هر scope تو در تو قابل دسترسی می‌بودند. اما این اصل «حداقل...» را نقض می‌کرد چون (احتمالاً) بسیاری متغیرها یا توابعی را افشا می‌کنید که باید خصوصی نگه دارید، چون استفادهٔ صحیح از کد دسترسی به آن متغیرها/توابع را دلسرد می‌کند.

مثلاً:

```js
function doSomething(a) {
	b = a + doSomethingElse( a * 2 );

	console.log( b * 3 );
}

function doSomethingElse(a) {
	return a - 1;
}

var b;

doSomething( 2 ); // 15
```

در این تکه، متغیر `b` و تابع `doSomethingElse(..)` احتمالاً جزئیات «خصوصی» نحوهٔ کار `doSomething(..)` هستند. دادن «دسترسی» scope محصور به `b` و `doSomethingElse(..)` نه تنها غیرضروری است بلکه احتمالاً «خطرناک» است، چون ممکن است به روش‌های غیرمنتظره، عمدی یا نه، استفاده شوند و این ممکن است فرض‌های پیش‌شرط `doSomething(..)` را نقض کند.

طراحی «صحیح‌تر» این جزئیات خصوصی را داخل scope مربوط به `doSomething(..)` پنهان می‌کند، مثل:

```js
function doSomething(a) {
	function doSomethingElse(a) {
		return a - 1;
	}

	var b;

	b = a + doSomethingElse( a * 2 );

	console.log( b * 3 );
}

doSomething( 2 ); // 15
```

حالا `b` و `doSomethingElse(..)` برای هیچ تأثیر بیرونی قابل دسترسی نیستند، بلکه فقط توسط `doSomething(..)` کنترل می‌شوند. عملکرد و نتیجهٔ نهایی تحت تأثیر قرار نگرفته، اما طراحی جزئیات خصوصی را خصوصی نگه می‌دارد، که معمولاً نرم‌افزار بهتری در نظر گرفته می‌شود.

### اجتناب از برخورد

فایدهٔ دیگر «پنهان» کردن متغیرها و توابع داخل scope اجتناب از برخورد ناخواسته بین دو شناسهٔ مختلف با همان نام اما کاربردهای مورد نظر متفاوت است. برخورد اغلب منجر به بازنویسی غیرمنتظرهٔ مقادیر می‌شود.

مثلاً:

```js
function foo() {
	function bar(a) {
		i = 3; // changing the `i` in the enclosing scope's for-loop
		console.log( a + i );
	}

	for (var i=0; i<10; i++) {
		bar( i * 2 ); // oops, infinite loop ahead!
	}
}

foo();
```

انتساب `i = 3` داخل `bar(..)` به‌طور غیرمنتظره `i` اعلام‌شده در `foo(..)` در حلقهٔ for را بازنویسی می‌کند. در این مورد، منجر به حلقهٔ بی‌نهایت می‌شود، چون `i` به مقدار ثابت `3` تنظیم می‌شود و برای همیشه `< 10` می‌ماند.

انتساب داخل `bar(..)` باید متغیر محلی برای استفاده اعلام کند، صرف‌نظر از نام شناسهٔ انتخاب‌شده. `var i = 3;` مشکل را حل می‌کرد (و اعلام «متغیر shadowed» قبلاً ذکر‌شده برای `i` ایجاد می‌کرد). گزینهٔ *اضافی*، نه جایگزین، انتخاب نام شناسهٔ کاملاً دیگر است، مثل `var j = 3;`. اما طراحی نرم‌افزار شما ممکن است طبیعتاً همان نام شناسه را بخواهد، پس استفاده از scope برای «پنهان» کردن اعلام درونی بهترین/تنها گزینهٔ شما در آن مورد است.

#### Global «Namespaces»

مثال به‌طور خاص قوی از (احتمالی) برخورد متغیر در global scope رخ می‌دهد. کتابخانه‌های متعددی که در برنامهٔ شما بارگذاری می‌شوند به‌راحتی می‌توانند با هم برخورد کنند اگر توابع و متغیرهای داخلی/خصوصی خود را به‌درستی پنهان نکنند.

چنین کتابخانه‌هایی معمولاً یک اعلام متغیر، اغلب یک شیء، با نامی به‌اندازهٔ کافی یکتا در global scope ایجاد می‌کنند. این شیء سپس به‌عنوان «namespace» برای آن کتابخانه استفاده می‌شود، جایی که تمام افشاهای خاص عملکرد به‌عنوان ویژگی‌های آن شیء (namespace) انجام می‌شوند، نه به‌عنوان شناسه‌های lexically scoped سطح بالا خودشان.

مثلاً:

```js
var MyReallyCoolLibrary = {
	awesome: "stuff",
	doSomething: function() {
		// ...
	},
	doAnotherThing: function() {
		// ...
	}
};
```

#### مدیریت ماژول

گزینهٔ دیگر برای اجتناب از برخورد رویکرد «ماژول» مدرن‌تر است، با استفاده از هر یک از مدیران وابستگی مختلف. با این ابزارها، هیچ کتابخانه‌ای هرگز هیچ شناسه‌ای به global scope اضافه نمی‌کند، بلکه باید شناسه(های) آن‌ها به‌طور صریح از طریق مکانیزم‌های مختلف مدیر وابستگی به scope خاص دیگری import شوند.

باید توجه کرد که این ابزارها قابلیت «جادویی» ندارند که از قوانین lexical scoping معاف باشند. آن‌ها به‌سادگی از قوانین scoping توضیح‌داده‌شدهٔ اینجا استفاده می‌کنند تا هیچ شناسه‌ای به هیچ scope مشترکی inject نشود، و در عوض در scopeهای خصوصی و غیرمستعد برخورد نگه داشته شوند، که از هر برخورد scope تصادفی جلوگیری می‌کند.

به این ترتیب، می‌توانید دفاعی کدنویسی کنید و همان نتایج مدیران وابستگی را بدون نیاز واقعی به استفاده از آن‌ها به دست آورید، اگر بخواهید. برای اطلاعات بیشتر دربارهٔ الگوی ماژول فصل ۵ را ببینید.
