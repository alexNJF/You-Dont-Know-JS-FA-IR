# دور زدن Lexical

اگر lexical scope فقط با جایی که تابع اعلام شده تعریف می‌شود، که کاملاً تصمیم زمان نوشتن است، چگونه ممکن است راهی برای «تغییر» (یعنی دور زدن) lexical scope در زمان اجرا وجود داشته باشد؟

JavaScript دو مکانیزم از این دست دارد. هر دو به‌طور یکسان در جامعهٔ گسترده‌تر به‌عنوان روش‌های بد برای استفاده در کدتان مذموم هستند. اما استدلال‌های معمول علیه آن‌ها اغلب مهم‌ترین نکته را از دست می‌دهند: **دور زدن lexical scope منجر به کارایی ضعیف‌تر می‌شود.**

قبل از توضیح مسئلهٔ کارایی، بیایید ببینیم این دو مکانیزم چگونه کار می‌کنند.

### `eval`

تابع `eval(..)` در JavaScript رشته‌ای را به‌عنوان آرگومان می‌گیرد و محتوای رشته را طوری برخورد می‌کند که انگار واقعاً کد نوشته‌شده در آن نقطهٔ برنامه بوده است. به عبارت دیگر، می‌توانید به‌صورت برنامه‌ای کد داخل کد نوشته‌شدهٔ خود تولید کنید و کد تولیدشده را طوری اجرا کنید که انگار از زمان نوشتن آنجا بوده است.

با ارزیابی `eval(..)` در آن نور، باید واضح باشد که `eval(..)` چگونه به شما اجازه می‌دهد محیط lexical scope را با دور زدن و وانمود کردن اینکه کد زمان نوشتن (یعنی lexical) از همان اول آنجا بوده تغییر دهید.

در خطوط بعدی کد بعد از اجرای `eval(..)`، *Engine* «نمی‌داند» یا «اهمیت نمی‌دهد» که کد قبلی به‌صورت پویا تفسیر شد و در نتیجه محیط lexical scope را تغییر داد. *Engine* به‌سادگی جستجوهای lexical scope خود را مثل همیشه انجام می‌دهد.

این کد را در نظر بگیرید:

```js
function foo(str, a) {
	eval( str ); // cheating!
	console.log( a, b );
}

var b = 2;

foo( "var b = 3;", 1 ); // 1 3
```

رشتهٔ `"var b = 3;"` در نقطهٔ فراخوانی `eval(..)` طوری برخورد می‌شود که انگار کدی بوده که از همان اول آنجا بوده. چون آن کد اتفاقاً متغیر جدید `b` را اعلام می‌کند، lexical scope موجود `foo(..)` را تغییر می‌دهد. در واقع، همان‌طور که بالا ذکر شد، این کد واقعاً متغیر `b` را داخل `foo(..)` ایجاد می‌کند که `b` اعلام‌شده در scope بیرونی (global) را shadow می‌کند.

وقتی فراخوانی `console.log(..)` رخ می‌دهد، هر دو `a` و `b` را در scope مربوط به `foo(..)` پیدا می‌کند و هرگز `b` بیرونی را پیدا نمی‌کند. پس به‌جای «۱ ۲» که در حالت عادی بود، «۱ ۳» چاپ می‌کنیم.

**توجه:** در این مثال، برای سادگی، رشتهٔ «کد» که منتقل می‌کنیم یک literal ثابت بود. اما به‌راحتی می‌توانست به‌صورت برنامه‌ای با اضافه کردن کاراکترها بر اساس منطق برنامهٔ شما ایجاد شود. `eval(..)` معمولاً برای اجرای کد ایجادشدهٔ پویا استفاده می‌شود، چون ارزیابی پویای کد اساساً ثابت از رشته literal فایدهٔ واقعی نسبت به نوشتن مستقیم کد ندارد.

به‌طور پیش‌فرض، اگر رشتهٔ کدی که `eval(..)` اجرا می‌کند یک یا چند اعلام (متغیر یا تابع) داشته باشد، این عمل lexical scope موجودی که `eval(..)` در آن قرار دارد را تغییر می‌دهد. از نظر فنی، `eval(..)` می‌تواند «غیرمستقیم» فراخوانی شود، از طریق ترفندهای مختلف (فراتر از بحث ما)، که باعث می‌شود به‌جای آن در زمینهٔ global scope اجرا شود و در نتیجه آن را تغییر دهد. اما در هر دو مورد، `eval(..)` می‌تواند در زمان اجرا lexical scope زمان نوشتن را تغییر دهد.

**توجه:** وقتی `eval(..)` در برنامهٔ strict-mode استفاده می‌شود در lexical scope خودش عمل می‌کند، یعنی اعلام‌های داخل `eval()` در واقع scope محصور را تغییر نمی‌دهند.

```js
function foo(str) {
   "use strict";
   eval( str );
   console.log( a ); // ReferenceError: a is not defined
}

foo( "var a = 2" );
```

تسهیلات دیگری در JavaScript وجود دارد که اثری بسیار مشابه `eval(..)` دارند. `setTimeout(..)` و `setInterval(..)` *می‌توانند* رشته‌ای را برای آرگومان اول مربوطه بگیرند که محتوایش به‌عنوان کد تابع تولیدشدهٔ پویا `eval` می‌شود. این رفتار قدیمی و legacy است و مدتهاست منسوخ شده. این کار را نکنید!

سازندهٔ تابع `new Function(..)` به‌طور مشابه رشته‌ای از کد را در آرگومان **آخر** خود می‌گیرد تا به تابع تولیدشدهٔ پویا تبدیل کند (آرگومان(های) اول، در صورت وجود، پارامترهای نام‌دار برای تابع جدید هستند). این نحو سازندهٔ تابع کمی امن‌تر از `eval(..)` است، اما باز هم باید در کدتان از آن اجتناب کنید.

موارد استفاده برای تولید پویای کد داخل برنامهٔ شما به‌طور باورنکردنی نادر است، چون کاهش کارایی تقریباً هرگز ارزش قابلیت را ندارد.

### `with`

ویژگی دیگر مذموم (و اکنون منسوخ!) در JavaScript که lexical scope را دور می‌زند کلمهٔ کلیدی `with` است. راه‌های معتبر متعددی برای توضیح `with` وجود دارد، اما اینجا از منظر تعامل و تأثیر آن بر lexical scope توضیح می‌دهم.

`with` معمولاً به‌عنوان میانبر برای ارجاع‌های متعدد ویژگی علیه یک شیء *بدون* تکرار ارجاع خود شیء هر بار توضیح داده می‌شود.

مثلاً:

```js
var obj = {
	a: 1,
	b: 2,
	c: 3
};

// more "tedious" to repeat "obj"
obj.a = 2;
obj.b = 3;
obj.c = 4;

// "easier" short-hand
with (obj) {
	a = 3;
	b = 4;
	c = 5;
}
```

با این حال، اینجا بیش از فقط یک میانبر مناسب برای دسترسی ویژگی شیء در کار است. در نظر بگیرید:

```js
function foo(obj) {
	with (obj) {
		a = 2;
	}
}

var o1 = {
	a: 3
};

var o2 = {
	b: 3
};

foo( o1 );
console.log( o1.a ); // 2

foo( o2 );
console.log( o2.a ); // undefined
console.log( a ); // 2 -- Oops, leaked global!
```

در این مثال کد، دو شیء `o1` و `o2` ایجاد می‌شوند. یکی ویژگی `a` دارد و دیگری ندارد. تابع `foo(..)` ارجاع شیء `obj` را به‌عنوان آرگومان می‌گیرد و `with (obj) { .. }` را روی ارجاع فراخوانی می‌کند. داخل بلوک `with`، ارجاع lexical عادی به متغیر `a` می‌کنیم، در واقع ارجاع LHS (فصل ۱ را ببینید)، برای انتساب مقدار `2` به آن.

وقتی `o1` را منتقل می‌کنیم، انتساب `a = 2` ویژگی `o1.a` را پیدا می‌کند و مقدار `2` را به آن انتساب می‌دهد، همان‌طور که در دستور بعدی `console.log(o1.a)` منعکس است. با این حال، وقتی `o2` را منتقل می‌کنیم، چون ویژگی `a` ندارد، چنین ویژگی‌ای ایجاد نمی‌شود و `o2.a` همچنان `undefined` می‌ماند.

اما سپس یک اثر جانبی عجیب را می‌بینیم، اینکه متغیر global `a` توسط انتساب `a = 2` ایجاد شد. چطور ممکن است؟

دستور `with` یک شیء می‌گیرد که صفر یا چند ویژگی دارد، و **آن شیء را طوری برخورد می‌کند انگار *خودش* یک lexical scope کاملاً مجزا است**، و بنابراین ویژگی‌های شیء به‌عنوان شناسه‌های تعریف‌شدهٔ lexical در آن «scope» برخورد می‌شوند.

**توجه:** حتی اگر بلوک `with` شیء را مثل lexical scope برخورد می‌کند، اعلام عادی `var` داخل آن بلوک `with` به آن بلوک `with` scope نمی‌شود، بلکه به scope تابع محصور.

در حالی که تابع `eval(..)` می‌تواند lexical scope موجود را تغییر دهد اگر رشتهٔ کدی با یک یا چند اعلام بگیرد، دستور `with` در واقع یک **lexical scope کاملاً جدید** از هیچ ایجاد می‌کند، از شیءای که به آن منتقل می‌کنید.

با این فهم، «scope» اعلام‌شده توسط دستور `with` وقتی `o1` را منتقل کردیم `o1` بود، و آن «scope» یک «شناسه» داشت که با ویژگی `o1.a` مطابقت دارد. اما وقتی از `o2` به‌عنوان «scope» استفاده کردیم، چنین «شناسه»ٔ `a` در آن نبود، و بنابراین قوانین عادی جستجوی شناسهٔ LHS (فصل ۱ را ببینید) رخ داد.

نه «scope» مربوط به `o2`، نه scope مربوط به `foo(..)`، و نه حتی global scope، شناسهٔ `a` برای یافتن ندارند، پس وقتی `a = 2` اجرا می‌شود، منجر به ایجاد automatic-global می‌شود (چون در حالت non-strict هستیم).

یک نوع فکر عجیب و ذهن‌پیچ است که ببینیم `with` در زمان اجرا یک شیء و ویژگی‌هایش را به «scope»ای *با* «شناسه»ها تبدیل می‌کند. اما این واضح‌ترین توضیحی است که می‌توانم برای نتایجی که می‌بینیم بدهم.

**توجه:** علاوه بر ایدهٔ بد بودن استفاده، هر دو `eval(..)` و `with` تحت تأثیر (محدودیت) Strict Mode هستند. `with` کاملاً ممنوع است، در حالی که اشکال مختلف `eval(..)` غیرمستقیم یا ناامن ممنوع هستند در حالی که عملکرد اصلی حفظ می‌شود.

### کارایی

هر دو `eval(..)` و `with` lexical scope تعریف‌شدهٔ زمان نوشتن را با تغییر یا ایجاد lexical scope جدید در زمان اجرا دور می‌زنند.

پس مشکل بزرگ چیست، می‌پرسید؟ اگر قابلیت پیچیده‌تر و انعطاف کدنویسی بیشتری ارائه می‌دهند، آیا این‌ها ویژگی‌های *خوب* نیستند؟ **نه.**

*Engine* JavaScript تعدادی بهینه‌سازی کارایی دارد که در فاز کامپایل انجام می‌دهد. برخی از این‌ها به توانایی تحلیل اساساً ایستای کد هنگام lex کردن و پیش‌تعیین کردن محل تمام اعلام‌های متغیر و تابع خلاصه می‌شوند، تا حل شناسه‌ها در حین اجرا کمتر effort بخواهد.

اما اگر *Engine* `eval(..)` یا `with` در کد پیدا کند، اساساً باید *فرض* کند که تمام آگاهی‌اش از محل شناسه ممکن است نامعتبر باشد، چون نمی‌تواند در زمان lex دقیقاً بداند چه کدی ممکن است به `eval(..)` برای تغییر lexical scope منتقل کنید، یا محتوای شیءای که ممکن است به `with` برای ایجاد lexical scope جدید برای مشورت منتقل کنید.

به عبارت دیگر، به‌معنای بدبینانه، اکثر آن بهینه‌سازی‌هایی که *می‌کرد* اگر `eval(..)` یا `with` حضور داشته باشند بی‌فایده است، پس اصلاً آن بهینه‌سازی‌ها را انجام نمی‌دهد.

کد شما تقریباً قطعاً تمایل به کندتر اجرا شدن دارد صرفاً به‌خاطر اینکه `eval(..)` یا `with` را هرکجا در کد قرار دهید. صرف‌نظر از اینکه *Engine* چقدر باهوش باشد در تلاش برای محدود کردن اثرات جانبی این فرض‌های بدبینانه، **راهی برای دور زدن این واقعیت نیست که بدون بهینه‌سازی‌ها، کد کندتر اجرا می‌شود.**
