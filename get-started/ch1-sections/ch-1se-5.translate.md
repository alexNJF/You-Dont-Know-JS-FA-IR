# عقب و جلو

یکی از اصول بنیادین که جاوااسکریپت را هدایت می‌کند حفظ *سازگاری با نسخه‌های قبلی* (backwards compatibility) است. بسیاری از پیامدهای این اصطلاح سردرگم می‌شوند، و اغلب آن را با اصطلاح مرتبط اما متفاوت اشتباه می‌گیرند: *سازگاری با نسخه‌های بعدی* (forwards compatibility).

بیایید روشن کنیم.

سازگاری با نسخه‌های قبلی یعنی وقتی چیزی به‌عنوان جاوااسکریپت معتبر پذیرفته شد، تغییری در آیندهٔ زبان نخواهد بود که آن کد را جاوااسکریپت نامعتبر کند. کدی که در ۱۹۹۵ نوشته شده—هرچقدر هم اولیه یا محدود بوده باشد!—باید امروز هم کار کند. همان‌طور که اعضای TC39 اغلب اعلام می‌کنند، «وب را خراب نمی‌کنیم!»

ایده این است که توسعه‌دهندگان جاوااسکریپت بتوانند با اطمینان کد بنویسند که کدشان به‌خاطر انتشار به‌روزرسانی مرورگر به‌طور غیرقابل‌پیش‌بینی کار نکند. این انتخاب جاوااسکریپت برای یک برنامه را سرمایه‌گذاری عاقلانه‌تر و امن‌تر می‌کند، برای سال‌های آینده.

آن «تضمین» چیز کمی نیست. حفظ سازگاری با نسخه‌های قبلی، در طول تقریباً ۲۵ سال تاریخ زبان، بار عظیمی و مجموعه‌ای از چالش‌های منحصربه‌فرد ایجاد می‌کند. پیدا کردن نمونه‌های زیاد دیگری در محاسبات از چنین تعهدی به سازگاری با نسخه‌های قبلی سخت است.

هزینه‌های پایبندی به این اصل نباید به‌سادگی نادیده گرفته شوند. لزوماً مانع بسیار بالایی برای گنجاندن تغییر یا گسترش زبان ایجاد می‌کند؛ هر تصمیمی به‌طور مؤثر دائمی می‌شود، اشتباهات و همه. وقتی در جاوااسکریپت است، نمی‌توان آن را بیرون آورد چون ممکن است برنامه‌ها را خراب کند، حتی اگر واقعاً، واقعاً دوست داشته باشیم آن را حذف کنیم!

استثناهای کوچکی برای این قانون وجود دارد. جاوااسکریپت تغییرات ناسازگار با نسخه‌های قبلی داشته، اما TC39 در انجام آن بسیار محتاط است. آن‌ها کد موجود در وب را (از طریق جمع‌آوری دادهٔ مرورگر) مطالعه می‌کنند تا تأثیر چنین خرابی را تخمین بزنند، و مرورگرها در نهایت تصمیم می‌گیرند و رأی می‌دهند که آیا مایل‌اند فشار کاربران را برای خرابی بسیار کوچک در مقابل مزایای اصلاح یا بهبود جنبه‌ای از زبان برای سایت‌ها و کاربران بسیار بیشتر بپذیرند.

این نوع تغییرات نادرند، و تقریباً همیشه در موارد حاشیه‌ای استفاده‌اند که بعید است در بسیاری سایت‌ها به‌طور قابل‌مشاهده خرابی ایجاد کنند.

*سازگاری با نسخه‌های قبلی* را با همتای آن، *سازگاری با نسخه‌های بعدی* مقایسه کنید. forwards-compatible بودن یعنی گنجاندن افزودنی جدید به زبان در یک برنامه باعث خرابی آن برنامه نشود اگر در موتور جاوااسکریپت قدیمی‌تری اجرا شود. **جاوااسکریپت forwards-compatible نیست**، علیرغم آرزوی بسیاری، و حتی باور نادرست افسانهٔ اینکه هست.

HTML و CSS، در contrast، forwards-compatible هستند اما backwards-compatible نیستند. اگر HTML یا CSS نوشته‌شده در ۱۹۹۵ را بیرون بیاورید، کاملاً ممکن است امروز کار نکند (یا همان‌طور کار کند). اما اگر از ویژگی جدید ۲۰۱۹ در مرورگری از ۲۰۱۰ استفاده کنید، صفحه «خراب» نیست—CSS/HTML ناشناخته رد می‌شود، در حالی که بقیهٔ CSS/HTML بر همین اساس پردازش می‌شود.

شاید مطلوب به نظر برسد که forwards-compatibility در طراحی زبان برنامه‌نویسی گنجانده شود، اما به‌طور کلی عملی نیست. Markup (HTML) یا styling (CSS) ماهیتاً declarative هستند، پس «رد کردن» اعلان‌های ناشناخته با حداقل تأثیر بر اعلان‌های شناخته‌شده بسیار آسان‌تر است.

اما آشفتگی و non-determinism رخ می‌دهد اگر موتور زبان برنامه‌نویسی به‌طور انتخابی دستورات (یا حتی expressionها!) را که نمی‌فهمد رد کند، چون غیرممکن است اطمینان حاصل شود که بخش بعدی برنامه انتظار نداشته بخش ردشده پردازش شده باشد.

هرچند جاوااسکریپت forwards-compatible نیست و نمی‌تواند باشد، شناخت backwards compatibility جاوااسکریپت، از جمله مزایای پایدار برای وب و محدودیت‌ها و دشواری‌هایی که در نتیجه بر جاوااسکریپت می‌گذارد، حیاتی است.

## پریدن از شکاف‌ها

از آنجا که جاوااسکریپت forwards-compatible نیست، یعنی همیشه پتانسیل شکافی بین کدی که می‌توانید بنویسید و معتبر جاوااسکریپت است، و قدیمی‌ترین موتوری که سایت یا اپلیکیشن شما باید پشتیبانی کند وجود دارد. اگر برنامه‌ای که از ویژگی ES2019 استفاده می‌کند را در موتوری از ۲۰۱۶ اجرا کنید، به احتمال زیاد برنامه خراب و crash می‌شود.

اگر ویژگی نحو جدید باشد، برنامه به‌طور کلی کاملاً از compile و اجرا بازمی‌ماند، معمولاً syntax error پرتاب می‌کند. اگر ویژگی یک API باشد (مثل `Object.is(..)` در ES6)، برنامه ممکن است تا نقطه‌ای اجرا شود اما سپس runtime exception پرتاب کند و با برخورد به ارجاع به API ناشناخته متوقف شود.

آیا یعنی توسعه‌دهندگان جاوااسکریپت باید همیشه عقب‌تر از سرعت پیشرفت بمانند، فقط از کدی استفاده کنند که در لبهٔ عقب قدیمی‌ترین محیط‌های موتور جاوااسکریپتی که باید پشتیبانی کنند است؟ نه!

اما یعنی توسعه‌دهندگان جاوااسکریپت باید مراقبت ویژه برای رفع این شکاف داشته باشند.

برای نحو جدید و ناسازگار، راه‌حل transpiling است. Transpiling اصطلاح ساختگی و ابداع‌شدهٔ جامعه برای توصیف استفاده از ابزاری برای تبدیل کد منبع برنامه از یک شکل به شکل دیگر (اما هنوز به‌عنوان کد منبع متنی) است. معمولاً مشکلات forwards-compatibility مربوط به نحو با استفاده از transpiler (رایج‌ترین آن Babel (https://babeljs.io)) برای تبدیل از آن نسخهٔ نحو جاوااسکریپت جدیدتر به نحو قدیمی معادل حل می‌شود.

مثلاً یک توسعه‌دهنده ممکن است تکه‌ای کد مثل این بنویسد:

```js
if (something) {
    let x = 3;
    console.log(x);
}
else {
    let x = 4;
    console.log(x);
}
```

این شکلی است که کد در درخت کد منبع آن اپلیکیشن به نظر می‌رسد. اما هنگام تولید فایل(ها) برای deploy به وب‌سایت عمومی، transpiler Babel ممکن است آن کد را به این شکل تبدیل کند:

```js
var x$0, x$1;
if (something) {
    x$0 = 3;
    console.log(x$0);
}
else {
    x$1 = 4;
    console.log(x$1);
}
```

تکهٔ اصلی به `let` تکیه داشت تا متغیرهای `x` با block-scope در هر دو clauseهای `if` و `else` ایجاد کند که با هم تداخل نداشتند. برنامهٔ معادل (با بازکاری حداقلی) که Babel می‌تواند تولید کند فقط دو متغیر متفاوت با نام‌های یکتا انتخاب می‌کند، همان نتیجهٔ عدم تداخل را تولید می‌کند.

| نکته: |
| :--- |
| کلمهٔ کلیدی `let` در ES6 (۲۰۱۵) اضافه شد. مثال قبلی transpiling فقط در صورتی لازم است که اپلیکیشن نیاز به اجرا در محیط موتور جاوااسکریپت pre-ES6 داشته باشد. مثال اینجا فقط برای سادگی توضیح است. وقتی ES6 جدید بود، نیاز به چنین transpilation کاملاً رایج بود، اما در ۲۰۲۰ کمتر رایج است که نیاز به پشتیبانی محیط‌های pre-ES6 باشد. «target» استفاده‌شده برای transpilation پس یک پنجرهٔ لغزنده است که فقط با تصمیم‌گیری برای توقف پشتیبانی از مرورگر/موتور قدیمی توسط سایت/اپلیکیشن به بالا می‌لغزد. |

شاید بپرسید: چرا زحمت استفاده از ابزار برای تبدیل از نسخهٔ نحو جدیدتر به قدیمی‌تر؟ نمی‌توانستیم فقط دو متغیر بنویسیم و از کلمهٔ کلیدی `let` صرف‌نظر کنیم؟ دلیل این است که به شدت توصیه می‌شود توسعه‌دهندگان از آخرین نسخهٔ جاوااسکریپت استفاده کنند تا کدشان تمیز باشد و ایده‌هایش را به مؤثرترین شکل منتقل کند.

توسعه‌دهندگان باید روی نوشتن شکل‌های تمیز و جدید نحو تمرکز کنند، و بگذارند ابزارها نسخهٔ forwards-compatible آن کد را که مناسب deploy و اجرا در قدیمی‌ترین محیط‌های موتور جاوااسکریپت پشتیبانی‌شده است تولید کنند.

## پر کردن شکاف‌ها

اگر مسئلهٔ forwards-compatibility مربوط به نحو جدید نباشد، بلکه به متد API گمشده‌ای باشد که تازه اضافه شده، رایج‌ترین راه‌حل ارائهٔ تعریفی برای آن متد API گمشده است که جایگزین می‌شود و طوری عمل می‌کند انگار محیط قدیمی از قبل آن را به‌صورت native تعریف کرده بود. این الگو polyfill (با نام مستعار «shim») نامیده می‌شود.

این کد را در نظر بگیرید:

```js
// getSomeRecords() یک promise برای داده‌ای که
// fetch می‌کند برمی‌گرداند
var pr = getSomeRecords();

// اسپینر UI را هنگام گرفتن داده نشان بده
startSpinner();

pr
.then(renderRecords)   // در صورت موفقیت رندر کن
.catch(showError)      // در صورت خطا نشان بده
.finally(hideSpinner)  // همیشه اسپینر را مخفی کن
```

این کد از ویژگی ES2019 استفاده می‌کند، متد `finally(..)` روی prototype promise. اگر این کد در محیط pre-ES2019 استفاده شود، متد `finally(..)` وجود نخواهد داشت و خطا رخ می‌دهد.

یک polyfill برای `finally(..)` در محیط‌های pre-ES2019 می‌تواند این شکلی باشد:

```js
if (!Promise.prototype.finally) {
    Promise.prototype.finally = function f(fn){
        return this.then(
            function t(v){
                return Promise.resolve( fn() )
                    .then(function t(){
                        return v;
                    });
            },
            function c(e){
                return Promise.resolve( fn() )
                    .then(function t(){
                        throw e;
                    });
            }
        );
    };
}
```

| هشدار: |
| :--- |
| این فقط یک توضیح ساده از یک polyfill پایه (نه کاملاً spec-compliant) برای `finally(..)` است. از این polyfill در کد خود استفاده نکنید؛ همیشه از polyfill قوی و رسمی استفاده کنید هر جا ممکن است، مثل مجموعه polyfillها/shimها در ES-Shim. |

دستور `if` تعریف polyfill را با جلوگیری از اجرا در هر محیطی که موتور جاوااسکریپت از قبل آن متد را تعریف کرده محافظت می‌کند. در محیط‌های قدیمی، polyfill تعریف می‌شود، اما در محیط‌های جدید دستور `if` به‌سادگی رد می‌شود.

Transpilerهایی مثل Babel معمولاً تشخیص می‌دهند کدام polyfillها را کد شما نیاز دارد و آن‌ها را خودکار برای شما فراهم می‌کنند. اما گاهی ممکن است نیاز باشد آن‌ها را صریحاً include/define کنید، که مشابه تکه‌ای که تازه دیدیم کار می‌کند.

همیشه کد را با مناسب‌ترین ویژگی‌ها برای انتقال مؤثر ایده‌ها و قصدش بنویسید. به‌طور کلی، یعنی استفاده از آخرین نسخهٔ پایدار جاوااسکریپت. از تأثیر منفی بر خوانایی کد با تلاش برای تنظیم دستی برای شکاف‌های نحو/API اجتناب کنید. ابزارها برای همین هستند!

Transpilation و polyfilling دو تکنیک بسیار مؤثر برای رفع آن شکاف بین کدی که از آخرین ویژگی‌های پایدار زبان استفاده می‌کند و محیط‌های قدیمی که سایت یا اپلیکیشن هنوز باید پشتیبانی کند هستند. از آنجا که جاوااسکریپت قرار نیست بهبود را متوقف کند، شکاف هرگز از بین نمی‌رود. هر دو تکنیک باید به‌عنوان بخش استاندارد زنجیرهٔ تولید هر پروژهٔ جاوااسکریپت پذیرفته شوند.
