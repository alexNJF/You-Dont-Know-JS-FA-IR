# به‌طور *سخت‌گیرانه* صحبت کنیم

در ۲۰۰۹ با انتشار ES5، جاوااسکریپت *حالت strict* را به‌عنوان مکانیزم opt-in برای تشویق برنامه‌های بهتر جاوااسکریپت اضافه کرد.

مزایای حالت strict بسیار بیشتر از هزینه‌هاست، اما عادت‌های قدیمی سخت می‌میرند و اینرسی پایگاه‌های کد موجود (با نام مستعار «legacy») واقعاً سخت جابه‌جا می‌شود. پس متأسفانه، بیش از ۱۰ سال بعد، *اختیاری بودن* حالت strict یعنی هنوز لزوماً پیش‌فرض برای برنامه‌نویسان جاوااسکریپت نیست.

چرا حالت strict؟ حالت strict نباید به‌عنوان محدودیت بر آنچه نمی‌توانید انجام دهید فکر شود، بلکه راهنمایی به بهترین روش انجام کارهاست تا موتور جاوااسکریپت بهترین شانس بهینه‌سازی و اجرای کارآمد کد را داشته باشد. بیشتر کد جاوااسکریپت توسط تیم‌های توسعه‌دهنده کار می‌شود، پس *سخت‌گیری* حالت strict (همراه با ابزارهایی مثل linter!) اغلب به همکاری روی کد با اجتناب از برخی اشتباهات مشکل‌دارتر که در حالت non-strict رد می‌شوند کمک می‌کند.

بیشتر کنترل‌های حالت strict به شکل *early errors* هستند، یعنی خطاهایی که به‌طور سخت‌گیرانه خطای نحو نیستند اما هنوز در زمان compile (قبل از اجرای کد) پرتاب می‌شوند. مثلاً حالت strict نام‌گذاری دو پارامتر تابع با نام یکسان را ممنوع می‌کند و منجر به early error می‌شود. برخی کنترل‌های دیگر حالت strict فقط در runtime قابل‌مشاهده‌اند، مثل اینکه `this` به‌جای شیء سراسری به `undefined` پیش‌فرض می‌شود.

به‌جای جنگیدن و بحث با حالت strict، مثل بچه‌ای که فقط می‌خواهد هر چه والدینش می‌گویند نکند را انجام ندهد، بهترین ذهنیت این است که حالت strict مثل یک linter است که یادآوری می‌کند جاوااسکریپت *باید* چطور نوشته شود تا بالاترین کیفیت و بهترین شانس عملکرد را داشته باشد. اگر احساس می‌کنید دست‌بسته‌اید، سعی می‌کنید دور حالت strict کار کنید، آن باید پرچم قرمز هشداردهنده باشد که باید عقب بروید و کل رویکرد را بازاندیشی کنید.

حالت strict با یک pragma خاص به‌ازای هر فایل روشن می‌شود (هیچ چیز قبل از آن مجاز نیست مگر کامنت/whitespace):

```js
// فقط whitespace و کامنت مجاز است
// قبل از pragma use-strict
"use strict";
// بقیهٔ فایل در حالت strict اجرا می‌شود
```

| :--- |
| چیزی که باید بدانید این است که حتی یک `;` سرگردان به تنهایی قبل از pragma حالت strict ظاهر شود pragma را بی‌فایده می‌کند؛ هیچ خطایی پرتاب نمی‌شود چون داشتن string literal expression در موقعیت statement جاوااسکریپت معتبر است، اما همچنین به‌طور silent حالت strict را روشن *نمی‌کند*! |

حالت strict می‌تواند به‌طور جایگزین به‌ازای scope تابع روشن شود، با دقیقاً همان قوانین دربارهٔ اطرافش:

```js
function someOperations() {
    // whitespace و کامنت اینجا مشکلی ندارد
    "use strict";

    // همهٔ این کد در حالت strict اجرا می‌شود
}
```

جالبه که اگر فایلی حالت strict روشن داشته باشد، pragmaهای حالت strict سطح تابع ممنوع‌اند. پس باید یکی یا دیگری را انتخاب کنید.

**تنها** دلیل معتبر استفاده از رویکرد به‌ازای تابع برای حالت strict وقتی است که در حال تبدیل یک فایل برنامهٔ حالت non-strict موجود هستید و نیاز دارید تغییرات را کم‌کم در طول زمان انجام دهید. در غیر این صورت، به مراتب بهتر است به سادگی حالت strict را برای کل فایل/برنامه روشن کنید.

بسیاری پرسیده‌اند آیا زمانی خواهد بود که جاوااسکریپت حالت strict را پیش‌فرض کند؟ پاسخ این است، تقریباً قطعاً نه. همان‌طور که قبلاً دربارهٔ سازگاری با نسخه‌های قبلی بحث کردیم، اگر به‌روزرسانی موتور جاوااسکریپت فرض کند کد حالت strict است حتی اگر به‌عنوان چنین علامت‌گذاری نشده، ممکن است آن کد در نتیجهٔ کنترل‌های حالت strict خراب شود.

با این حال، چند عامل تأثیر آیندهٔ این «ابهام» غیرپیش‌فرض حالت strict را کاهش می‌دهند.

یکی اینکه، تقریباً همهٔ کد transpile‌شده در نهایت در حالت strict است حتی اگر کد منبع اصلی چنین نوشته نشده باشد. بیشتر کد جاوااسکریپت در production transpile شده، پس یعنی بیشتر جاوااسکریپت از قبل به حالت strict پایبند است. ممکن است آن فرض را برگردانید، اما واقعاً باید از راه خود خارج شوید تا چنین کنید، پس بسیار بعید است.

علاوه بر آن، جابه‌جایی گسترده‌ای به سمت نوشتن بیشتر/بیشتر کد جاوااسکریپت جدید با قالب ماژول ES6 در حال وقوع است. ماژول‌های ES6 حالت strict را فرض می‌کنند، پس همهٔ کد در چنین فایل‌هایی به‌طور خودکار به حالت strict پیش‌فرض می‌شود.

در مجموع، حالت strict تا حد زیادی de facto پیش‌فرض است حتی اگر از نظر فنی واقعاً پیش‌فرض نباشد.
