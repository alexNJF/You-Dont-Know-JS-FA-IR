# رفتار خصوصی کلاس

همهٔ آنچه تا الان به‌عنوان بخشی از تعریف `class` بحث کردیم به‌صورت عمومی قابل مشاهده/دسترسی است، چه به‌عنوان ویژگی‌ها/توابع استاتیک روی کلاس، متدها روی `prototype` constructor، یا ویژگی‌های member روی نمونه.

اما چطور اطلاعاتی را ذخیره کنید که از بیرون کلاس قابل مشاهده نباشد؟ این یکی از پرتقاضاترین ویژگی‌ها و بزرگ‌ترین شکایات از `class` جاوااسکریپت بود، تا اینکه سرانجام در ES2022 برطرف شد.

`class` اکنون سینتکس جدیدی برای اعلام فیلدهای خصوصی (memberهای نمونه) و متدهای خصوصی پشتیبانی می‌کند. علاوه بر این، ویژگی‌ها/توابع استاتیک خصوصی هم ممکن است.

### انگیزه؟

قبل از نشان دادن نحوهٔ انجام privates کلاس، ارزش تأمل دارد چرا این ویژگی مفید است؟

با الگوهای طراحی جهت‌یافته به closure (دوباره، کتاب «Scope & Closures» این سری را ببینید)، به‌طور خودکار «privacy» داخلی داریم. وقتی متغیری داخل scope اعلام می‌کنید، از بیرون آن scope قابل مشاهده نیست. نقطه. کاهش visibility scope اعلام به جلوگیری از برخورد namespace (نام‌های متغیر یکسان) کمک می‌کند.

اما حتی مهم‌تر اطمینان از طراحی «دفاعی» صحیح نرم‌افزار است، به اصطلاح «Principle of Least Privilege» [^POLP]. POLP می‌گوید باید فقط یک قطعه اطلاعات یا قابلیت را در نرم‌افزارمان به کوچک‌ترین سطح لازم expose کنیم.

over-exposure نرم‌افزارمان را در معرض چند مسئله قرار می‌دهد که امنیت/نگهداری نرم‌افزار را پیچیده می‌کنند، از جمله کد دیگر که به‌طور مخرب کاری انجام دهد که کد ما انتظار یا قصد نداشت. علاوه بر این، نگرانی کمتر حیاتی اما همچنان مشکل‌ساز این است که بخش‌های دیگر نرم‌افزارمان به بخش‌هایی از کدمان وابسته شوند (استفاده کنند) که باید به‌عنوان جزئیات پیاده‌سازی مخفی رزرو کرده باشیم. وقتی کد دیگر به جزئیات پیاده‌سازی کدمان وابسته شود، دیگر نمی‌توانیم کدمان را refactor کنیم بدون اینکه احتمالاً بخش‌های دیگر برنامه را بشکنیم.

پس، خلاصه، *باید* جزئیات پیاده‌سازی را مخفی کنیم اگر لازم به expose نیستند. از این نظر، سیستم `class` جاوااسکریپت کمی بیش از حد permissive به نظر می‌رسد چون همه چیز به‌طور پیش‌فرض عمومی است. ویژگی‌های class-private افزودنی خوشایندی برای طراحی نرم‌افزار صحیح‌تر هستند.

#### بیش از حد خصوصی؟

با همهٔ اینها، باید کمی روی جشن class-private سایه بیندازم.

قویاً پیشنهاد کرده‌ام که فقط وقتی از `class` استفاده کنید که واقعاً از اکثر یا همهٔ آنچه جهت‌گیری کلاسی می‌دهد بهره ببرید. در غیر این صورت، بهتر است از ویژگی‌های ستون اصلی دیگر JS برای سازماندهی کد استفاده کنید، مثل الگوی closure.

یکی از مهم‌ترین جنبه‌های جهت‌گیری کلاسی inheritance زیرکلاس است، همان‌طور که بارها در این فصل تصویرسازی کرده‌ایم. حدس بزنید وقتی member/متد خصوصی در کلاس پایه توسط زیرکلاس extend می‌شود چه اتفاقی می‌افتد؟

Memberها/متدهای خصوصی **فقط برای کلاسی که در آن تعریف شده‌اند** خصوصی هستند، و **به هیچ وجه** توسط زیرکلاس به ارث برده نمی‌شوند. اوه اوه.

شاید نگرانی خیلی بزرگی به نظر نرسد، تا وقتی با `class` و memberها/متدهای خصوصی در نرم‌افزار واقعی کار کنید. ممکن است خیلی سریع به وضعیتی برخورد کنید که نیاز به دسترسی به متد خصوصی، یا حتی بیشتر، فقط member خصوصی، از زیرکلاس دارید، تا زیرکلاس بتواند رفتار کلاس پایه را طبق میل extend/augment کند. و ممکن است خیلی سریع وقتی متوجه شوید این ممکن نیست فریاد بزنید.

آنچه بعد می‌آید اجتناب‌ناپذیراً تصمیم awkward است: آیا فقط آن را عمومی کنید تا زیرکلاس دسترسی داشته باشد؟ اوه. یا بدتر، آیا سعی می‌کنید کلاس پایه را طوری بازطراحی کنید که طراحی memberها/متدهایش را contort کند تا کمبود دسترسی تا حدی دور زده شود؟ آن اغلب شامل over-parameterization خسته‌کننده (با privates به‌عنوان مقادیر پیش‌فرض پارامتر) متدها و ترفندهای دیگر است. دوبرابر اوه.

صادقانه بگویم، پاسخ خاصاً عالی اینجا نیست. اگر با جهت‌گیری کلاسی در زبان‌های کلاسی سنتی‌تر مثل Java یا C++ تجربه دارید، احتمالاً تردید دارید چرا *protected* visibility بین *public* و *private* نداریم. دقیقاً *protected* برای همین است: خصوصی نگه داشتن چیزی برای کلاس و هر زیرکلاسش. آن زبان‌ها ویژگی *friend* هم دارند، اما فراتر از محدودهٔ بحث ماست.

متأسفانه، نه تنها JS *protected* visibility ندارد، به نظر می‌رسد (حتی با مفید بودنش!) بعید است به عنوان ویژگی JS باشد. بیش از یک دهه با جزئیات زیاد بحث شده (قبل از اینکه ES6 حتی چیزی باشد)، و پیشنهادهای متعددی برایش بوده.

نباید بگویم *هرگز* اتفاق نمی‌افتد، چون در هر نرم‌افزاری زمین محکمی برای شرط بستن نیست. اما بسیار بعید است، چون در واقع ستونی که `class` روی آن ساخته شده را خیانت می‌کند. اگر کنجکاوید، یا (محتمل‌تر) مطمئنید که *حتماً راهی هست*، incompatibility *protected* visibility با مکانیزم‌های JS را در ضمیمه پوشش می‌دهم.

نکتهٔ اینجا این است، تا الان، JS *protected* visibility ندارد، و به این زودی هم نخواهد داشت. و *protected* visibility در عمل واقعاً مفیدتر از *private* visibility است.

پس به سؤال برمی‌گردیم: **چرا باید به خصوصی کردن محتوای `class` اهمیت دهید؟**

صادقانه بگویم: شاید نباید. یا شاید باید. به عهدهٔ شماست. فقط با آگاهی از موانع وارد شوید.

### Memberها/متدهای خصوصی

هیجان‌زده‌اید بالاخره سینتکس visibility جادویی *private* را ببینید؟ لطفاً اگر از آنچه می‌خواهید ببینید عصبانی یا ناراحت شدید messenger را شلیک نکنید.

```js
class Point2d {
    // statics
    static samePoint(point1,point2) {
        return point1.#ID === point2.#ID;
    }

    // privates
    #ID = null
    #assignID() {
        this.#ID = Math.round(Math.random() * 1e9);
    }

    // publics
    x
    y
    constructor(x,y) {
        this.#assignID();
        this.x = x;
        this.y = y;
    }
}

var one = new Point2d(3,4);
var two = new Point2d(3,4);

Point2d.samePoint(one,two);         // false
Point2d.samePoint(one,one);         // true
```

نه، جاوااسکریپت کار منطقی نکرد و کلمهٔ کلیدی `private` مثل `static` معرفی نکرد. به‌جای آن، `#` را معرفی کرد. (جوک بی‌مزه دربارهٔ millennials شبکه‌های اجتماعی که hashtag دوست دارند، یا چیزی شبیهش)

| :--- |

سینتکس `#whatever` (از جمله شکل `this.#whatever`) فقط داخل بدنهٔ `class` معتبر است. اگر خارج از `class` استفاده شود خطای syntax پرتاب می‌کند.

برخلاف فیلدها/memberهای نمونهٔ عمومی، فیلدها/memberهای نمونهٔ خصوصی *باید* در بدنهٔ `class` اعلام شوند. نمی‌توانید member خصوصی را به‌طور پویا در متد constructor به تعریف کلاس اضافه کنید؛ انتساب‌های نوع `this.#whatever = ..` فقط کار می‌کنند اگر فیلد خصوصی `#whatever` در بدنهٔ کلاس اعلام شده باشد. علاوه بر این، هرچند فیلدهای خصوصی می‌توانند دوباره انتساب شوند، نمی‌توان آن‌ها را مثل فیلد/member کلاس عمومی از نمونه `delete` کرد.

#### Subclassing + Privates

قبلاً هشدار دادم که subclassing با کلاس‌هایی که memberها/متدهای خصوصی دارند می‌تواند تلهٔ محدودکننده باشد. اما این یعنی نمی‌توان با هم استفاده شوند.

چون «inheritance» در JS اشتراک است (از طریق زنجیرهٔ `[[Prototype]]`)، اگر متد به‌ارث‌برده را در زیرکلاس فراخوانی کنید، و آن متد به‌ارث‌برده به نوبهٔ خود به privates در کلاس میزبان (پایه) دسترسی/فراخوانی کند، درست کار می‌کند:

```js
class Point2d { /* .. */ }

class Point3d extends Point2d {
    z
    constructor(x,y,z) {
        super(x,y);
        this.z = z;
    }
}

var one = new Point3d(3,4,5);
```

فراخوانی `super(x,y)` در این constructor متد constructor کلاس پایهٔ به‌ارث‌برده (`Point2d(..)`) را فراخوانی می‌کند، که خودش به متد خصوصی `#assignID()` مربوط به `Point2d` دسترسی دارد (snippet قبلی را ببینید). حتی با اینکه `Point3d` نمی‌تواند مستقیماً privates مربوط به `#ID` / `#assignID()` را ببیند یا دسترسی داشته باشد که واقعاً روی نمونه ذخیره شده‌اند (اینجا `one` نامیده شده)، استثناء پرتاب نمی‌شود.

در واقع، حتی تابع `static samePoint(..)` به‌ارث‌برده از هر دو `Point3d` یا `Point2d` کار می‌کند:

```js
Point2d.samePoint(one,one);         // true
Point3d.samePoint(one,one);         // true
```

در واقع، نباید خیلی تعجب‌آور باشد، چون:

```js
Point2d.samePoint === Point3d.samePoint;
```

ارجاع تابع به‌ارث‌برده *دقیقاً همان تابع* است که ارجاع تابع پایه است؛ کپی تابع نیست. چون تابع مورد نظر هیچ ارجاع `this` در خودش ندارد، مهم نیست از کجا فراخوانی شود، باید همان نتیجه را بدهد.

هنوز تأسف‌بار است که `Point3d` هیچ راهی برای دسترسی/تأثیرگذاری، یا حتی آگاهی از privates مربوط به `#ID` / `#assignID()` از `Point2d` ندارد:

```js
class Point2d { /* .. */ }

class Point3d extends Point2d {
    z
    constructor(x,y,z) {
        super(x,y);
        this.z = z;

        console.log(this.#ID);      // will throw!
    }
}
```

| :--- |
| توجه کنید که این snippet در زمان تعریف کلاس `Point3d`، قبل از حتی فرصت ساختن نمونهٔ کلاس، خطای syntax استاتیک زودهنگام پرتاب می‌کند. همان استثناء پرتاب می‌شد اگر ارجاع `super.#ID` به‌جای `this.#ID` بود. |

#### بررسی وجود

به خاطر داشته باشید که فقط خود `class` از چنین فیلد/متد خصوصی می‌داند و بنابراین می‌تواند بررسی کند.

ممکن است بخواهید بررسی کنید آیا فیلد/متد خصوصی روی نمونهٔ شیء وجود دارد. مثلاً (همان‌طور که پایین نشان داده شده)، ممکن است تابع استاتیک یا متدی در کلاس داشته باشید که ارجاع شیء خارجی passed-in دریافت می‌کند. برای بررسی اینکه آیا ارجاع شیء passed-in از همین کلاس است (و بنابراین همان memberها/متدهای خصوصی را دارد)، اساساً باید «brand check» علیه شیء انجام دهید.

چنین بررسی‌ای می‌تواند نسبتاً پیچیده باشد، چون اگر به فیلد خصوصی که قبلاً روی شیء وجود ندارد دسترسی کنید، استثناء JS پرتاب می‌شود و به منطق `try..catch` زشت نیاز است.

اما رویکرد تمیزتری هست، به اصطلاح «ergonomic brand check»، با کلمهٔ کلیدی `in`:

```js
class Point2d {
    // statics
    static samePoint(point1,point2) {
        // "ergonomic brand checks"
        if (#ID in point1 && #ID in point2) {
            return point1.#ID === point2.#ID;
        }
        return false;
    }

    // privates
    #ID = null
    #assignID() {
        this.#ID = Math.round(Math.random() * 1e9);
    }

    // publics
    x
    y
    constructor(x,y) {
        this.#assignID();
        this.x = x;
        this.y = y;
    }
}

var one = new Point2d(3,4);
var two = new Point2d(3,4);

Point2d.samePoint(one,two);         // false
Point2d.samePoint(one,one);         // true
```

بررسی `#privateField in someObject` اگر فیلد پیدا نشود استثناء پرتاب نمی‌کند، پس استفادهٔ امن بدون `try..catch` و نتیجهٔ boolean سادهٔ آن ممکن است.

#### Exfiltration

حتی با اینکه member/متد ممکن است با visibility *private* اعلام شده باشد، هنوز می‌تواند از نمونهٔ کلاس exfiltrate (استخراج) شود:

```js
var id, func;

class Point2d {
    // privates
    #ID = null
    #assignID() {
        this.#ID = Math.round(Math.random() * 1e9);
    }

    // publics
    x
    y
    constructor(x,y) {
        this.#assignID();
        this.x = x;
        this.y = y;

        // exfiltration
        id = this.#ID;
        func = this.#assignID;
    }
}

var point = new Point2d(3,4);

id;                     // 7392851012 (...for example)

func;                   // function #assignID() { .. }
func.call(point,42);

func.call({},100);
// TypeError: Cannot write private member #ID to an
// object whose class did not declare it
```

نگرانی اصلی اینجا احتیاط هنگام passing متدهای خصوصی به‌عنوان callback (یا هرگونه expose کردن privates به بخش‌های دیگر برنامه) است. چیزی جلوی شما را نمی‌گیرد، که می‌تواند کمی افشای ناخواستهٔ privacy ایجاد کند.

### استاتیک‌های خصوصی

ویژگی‌ها و توابع استاتیک هم می‌توانند از `#` برای علامت‌گذاری به‌عنوان خصوصی استفاده کنند:

```js
class Point2d {
    static #errorMsg = "Out of bounds."
    static #printError() {
        console.log(`Error: ${this.#errorMsg}`);
    }

    // publics
    x
    y
    constructor(x,y) {
        if (x > 100 || y > 100) {
            Point2d.#printError();
        }
        this.x = x;
        this.y = y;
    }
}

var one = new Point2d(30,400);
// Error: Out of bounds.
```

تابع استاتیک خصوصی `#printError()` اینجا `this` دارد، اما به کلاس `Point2d` اشاره می‌کند، نه نمونه. بنابراین، `#errorMsg` و `#printError()` مستقل از نمونه‌ها هستند و بنابراین بهترین حالت به‌عنوان استاتیک هستند. علاوه بر این، دلیلی برای دسترسی‌پذیر بودن از بیرون کلاس نیست، پس خصوصی علامت‌گذاری شده‌اند.

به خاطر داشته باشید: استاتیک‌های خصوصی به همین ترتیب مثل memberها/متدهای خصوصی توسط زیرکلاس‌ها به ارث برده نمی‌شوند.

#### Gotcha: Subclassing با استاتیک‌های خصوصی و `this`

به خاطر بیاورید که متدهای به‌ارث‌برده، فراخوانی‌شده از زیرکلاس، برای دسترسی (از طریق ارجاعات سبک `this.#whatever`) به هر private از کلاس پایهٔ خودشان مشکلی ندارند:

```js
class Point2d {
    // ..

    getID() {
        return this.#ID;
    }

    // ..
}

class Point3d extends Point2d {
    // ..

    printID() {
        console.log(`ID: ${this.getID()}`);
    }
}

var point = new Point3d(3,4,5);
point.printID();
// ID: ..
```

درست کار می‌کند.

متأسفانه، و (برای من) کاملاً غیرمنتظره/ناسازگار، همین‌طور برای استاتیک‌های خصوصی دسترسی‌یافته از توابع استاتیک عمومی به‌ارث‌برده صادق نیست:

```js
class Point2d {
    static #errorMsg = "Out of bounds."
    static printError() {
        console.log(`Error: ${this.#errorMsg}`);
    }

    // ..
}

class Point3d extends Point2d {
    // ..
}

Point2d.printError();
// Error: Out of bounds.

Point3d.printError === Point2d.printError;
// true

Point3d.printError();
// TypeError: Cannot read private member #errorMsg
// from an object whose class did not declare it
```

استاتیک `printError()` از `Point2d` به `Point3d` به‌درستی به ارث برده می‌شود (اشتراک از طریق `[[Prototype]]`)، به همین دلیل ارجاعات تابع یکسان‌اند. مثل snippet غیراستاتیک بالا، ممکن بود انتظار داشته باشید فراخوانی استاتیک `Point3d.printError()` از طریق زنجیرهٔ `[[Prototype]]` به مکان کلاس پایهٔ اصلیش (`Point2d`) resolve شود، و بدین ترتیب به استاتیک خصوصی `#errorMsg` کلاس پایه دسترسی داشته باشد.

اما شکست می‌خورد، همان‌طور که آخرین statement در آن snippet نشان می‌دهد. دلیل شکست اینجا، اما نه با snippet قبلی، یک brain twister پیچیده است. نمی‌خواهم به توضیح *چرا* اینجا بپردازم، صادقانه چون خونم را به جوش می‌آورد.

*راه‌حلی* هست، هرچند. در تابع استاتیک، به‌جای `this.#errorMsg`، آن را با `Point2d.#errorMsg` عوض کنید، و اکنون کار می‌کند:

```js
class Point2d {
    static #errorMsg = "Out of bounds."
    static printError() {
        // the fixed reference vvvvvv
        console.log(`Error: ${Point2d.#errorMsg}`);
    }

    // ..
}

class Point3d extends Point2d {
    // ..
}

Point2d.printError();
// Error: Out of bounds.

Point3d.printError();
// Error: Out of bounds.  <-- phew, it works now!
```

اگر توابع استاتیک عمومی به ارث برده می‌شوند، از نام کلاس برای دسترسی به هر استاتیک خصوصی به‌جای ارجاعات `this.` استفاده کنید. مراقب آن gotcha باشید!
