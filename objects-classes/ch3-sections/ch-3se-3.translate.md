# `this` نمونهٔ کلاس

کلمهٔ کلیدی `this` را در فصل بعد با جزئیات بیشتر پوشش می‌دهیم. اما در ارتباط با کد جهت‌یافته به کلاس، `this` به‌طور کلی به نمونهٔ فعلی که context هر فراخوانی متد است اشاره می‌کند.

در constructor و همچنین هر متدی، می‌توانید از `this.` برای اضافه کردن یا دسترسی به ویژگی‌ها روی نمونهٔ فعلی استفاده کنید:

```js
class Point2d {
    constructor(x,y) {
        // add properties to the current instance
        this.x = x;
        this.y = y;
    }
    toString() {
        // access the properties from the current instance
        console.log(`(${this.x},${this.y})`);
    }
}

var point = new Point2d(3,4);

point.x;                // 3
point.y;                // 4

point.toString();       // (3,4)
```

هر ویژگی که مقدار تابع نگه نمی‌دارد و به نمونهٔ کلاس اضافه می‌شود (معمولاً از طریق constructor)، *member* نامیده می‌شود، در مقابل اصطلاح *method* برای توابع قابل اجرا.

وقتی متد `point.toString()` در حال اجراست، ارجاع `this` آن به همان شیء‌ای اشاره می‌کند که `point` به آن اشاره می‌کند. به همین دلیل هم `point.x` و هم `this.x` همان مقدار `3` را نشان می‌دهند که constructor با عملیات `this.x = x` تنظیم کرد.

### فیلدهای عمومی

به‌جای تعریف member نمونهٔ کلاس به‌صورت دستوری با `this.` در constructor یا متد، کلاس‌ها می‌توانند *field*ها را به‌صورت اعلانی در بدنهٔ `class` تعریف کنند، که مستقیماً با memberهایی که روی هر نمونه ساخته می‌شوند مطابقت دارند:

```js
class Point2d {
    // these are public fields
    x = 0
    y = 0

    constructor(x,y) {
        // set properties (fields) on the current instance
        this.x = x;
        this.y = y;
    }
    toString() {
        // access the properties from the current instance
        console.log(`(${this.x},${this.y})`);
    }
}
```

فیلدهای عمومی می‌توانند مقداردهی اولیه داشته باشند، همان‌طور که بالا نشان داده شد، اما الزامی نیست. اگر فیلدی را در تعریف کلاس مقداردهی نکنید، تقریباً همیشه باید آن را در constructor مقداردهی کنید.

فیلدها همچنین می‌توانند با سینتکس دسترسی طبیعی `this.` به هم ارجاع دهند:

```js
class Point3d {
    // these are public fields
    x
    y = 4
    z = this.y * 5

    // ..
}
```

درست مثل نام‌های ویژگی محاسبه‌شده (فصل ۱ را ببینید)، نام فیلدها می‌توانند محاسبه‌شده باشند:

```js
var coordName = "x";

class Point2d {
    // computed public field
    [coordName.toUpperCase()] = 42

    // ..
}

var point = new Point2d(3,4);

point.x;        // 3
point.y;        // 4

point.X;        // 42
```

#### از این اجتناب کنید

الگویی که ظهور کرده و بسیار محبوب شده، اما که من قویاً معتقدم anti-pattern برای `class` است، این‌طور به نظر می‌رسد:

```js
class Point2d {
    x = null
    y = null
    getDoubleX = () => this.x * 2

    constructor(x,y) {
        this.x = x;
        this.y = y;
    }
    toString() { /* .. */ }
}

var point = new Point2d(3,4);

point.getDoubleX();    // 6
```

فیلد نگه‌دارندهٔ تابع `=>` را می‌بینید؟ می‌گویم این ممنوع است. اما چرا؟ بیایید ببینیم چه اتفاقی می‌افتد.

اول، چرا این کار را بکنیم؟ چون به نظر می‌رسد توسعه‌دهندگان JS دائماً از قوانین binding پویای `this` (فصل ۴ را ببینید) ناامیدند، پس binding `this` را با تابع `=>` اعمال می‌کنند. بدین ترتیب، مهم نیست `getDoubleX()` چطور فراخوانی شود، همیشه به نمونهٔ خاص `this`-bound است. این راحتی قابل فهمی است که بخواهند، اما... ماهیت ستون `this` / `[[Prototype]]` زبان را خیانت می‌کند. چطور؟

کد معادل snippet قبلی را در نظر بگیرید:

```js
class Point2d {
    constructor(x,y) {
        this.x = null;
        this.y = null;
        this.getDoubleX = () => this.x * 2;

        this.x = x;
        this.y = y;
    }
    toString() { /* .. */ }
}

var point = new Point2d(3,4);

point.getDoubleX();    // 6
```

مشکل را می‌بینید؟ دقیق نگاه کنید. صبر می‌کنم.

...

تا الان بارها واضح کرده‌ایم که تعاریف `class` متدهایشان را روی شیء `prototype` constructor کلاس قرار می‌دهند — جایشان همانجاست! — طوری که فقط یکی از هر تابع هست و توسط همهٔ نمونه‌ها به ارث برده (اشتراک) می‌شود. این اتفاقی است که با `toString()` در snippet بالا می‌افتد.

اما `getDoubleX()` چطور؟ این اساساً یک متد کلاس است، اما JS آن را کاملاً مثل `toString()` handle نمی‌کند. در نظر بگیرید:

```js
Object.hasOwn(point,"x");               // true -- good
Object.hasOwn(point,"toString");        // false -- good
Object.hasOwn(point,"getDoubleX");      // true -- oops :(
```

حالا می‌بینید؟ با تعریف مقدار تابع و اتصال آن به‌عنوان ویژگی field/member، ماهیت متد پروتوتایپی اشتراکی تابع را از دست می‌دهیم، و مثل هر ویژگی per-instance می‌شود. یعنی برای **هر نمونه** یک ویژگی تابع جدید می‌سازیم، به‌جای اینکه فقط یک بار روی `prototype` constructor کلاس ساخته شود.

این از نظر عملکرد و حافظه اتلاف است، حتی اگر کمی باشد. همین باید برای اجتناب کافی باشد.

اما استدلال می‌کنم که مهم‌تر، کاری که با این الگو کرده‌اید بی‌اعتبار کردن دلیلی است که چرا استفاده از `class` و متدهای `this`-aware حتی تا حدی مفید/قدرتمند است!

اگر زحمت تعریف متدهای کلاس با ارجاعات `this.` در سراسرشان را می‌کشید، اما بعد اکثر یا همهٔ آن متدها را به یک نمونهٔ شیء خاص lock/bind می‌کنید، اساساً دور دنیا رفته‌اید تا کنار در بروید.

اگر فقط می‌خواهید تابع‌هایی که به یک «context» خاص ثابت هستند و به هیچ پویایی یا اشتراکی نیاز ندارند، آنچه می‌خواهید... **closure** است. و خوش‌شانسید: یک کتاب کامل در این سری («Scope & Closures») دربارهٔ استفاده از closure نوشتم تا توابع scope (یعنی context) تعریف‌شدهٔ استاتیک را به خاطر بسپارند/دسترسی داشته باشند. این رویکرد مناسب‌تر و ساده‌تر برای کدنویسی برای رسیدن به آنچه می‌خواهید است.

`class` را سوءاستفاده/استفادهٔ نادرست نکنید و آن را به مجموعهٔ closure بیش‌ازحد تبلیغ‌شده و glorified تبدیل نکنید.

واضح بگویم، *نمی‌گویم*: هرگز از توابع `=>` داخل کلاس‌ها استفاده نکنید.

*می‌گویم*: هرگز تابع `=>` را به‌عنوان ویژگی نمونه به‌جای متد کلاس پروتوتایپی پویا attach نکنید، چه از روی عادت بی‌فکر، چه تنبلی در تایپ کمتر کاراکتر، چه راحتی binding اشتباه `this`.

در فصل بعد، عمیقاً به نحوهٔ درک و استفادهٔ صحیح از قدرت کامل مکانیزم پویای `this` می‌پردازیم.
