# فلش به جایی اشاره می‌کند

همهٔ آنچه تا الان دربارهٔ `this` در توابع و نحوهٔ تعیینش بر اساس call-site گفته‌ام یک فرض غول‌پیکر دارد: که با تابع (یا متد) *معمولی* سروکار دارید.

پس تابع *غیرمعمولی* چیست؟!؟ این‌طور به نظر می‌رسد:

```js
const x = x => x <= x;
```

| NOTE: |
| :--- |
| بله، کمی طعنه‌آمیز و ناعادلانه است که تابع فلش را «غیرمعمولی» بنامم و از چنین مثال contrived استفاده کنم. شوخی است، اوکی؟ |

یک مثال واقعی از تابع فلش `=>`:

```js
const clickHandler = evt =>
    evt.target.matches("button") ?
        this.theFormElem.submit() :
        evt.stopPropagation();
```

برای مقایسه، معادل غیرفلش را هم نشان می‌دهم:

```js
const clickHandler = function(evt) {
    evt.target.matches("button") ?
        this.theFormElem.submit() :
        evt.stopPropagation();
};
```

یا اگر کمی old-school برویم — این jam من است! — می‌توانیم شکل اعلام تابع standalone را امتحان کنیم:

```js
function clickHandler(evt) {
    evt.target.matches("button") ?
        this.theFormElem.submit() :
        evt.stopPropagation();
}
```

یا اگر تابع به‌عنوان متد در تعریف `class` یا concise method در object literal ظاهر شود، این‌طور به نظر می‌رسد:

```js
// ..
clickHandler(evt) {
    evt.target.matches("button") ?
        this.theFormElem.submit() :
        evt.stopPropagation();
}
```

چیزی که واقعاً می‌خواهم رویش تمرکز کنم نحوهٔ رفتار هر کدام از این اشکال تابع نسبت به ارجاع `this`شان است، و آیا شکل اول `=>` با بقیه فرق دارد (hint: دارد!). اما بیایید با یک quiz کوچک ببینیم آیا توجه کرده‌اید.

برای هر کدام از اشکال تابعی که نشان داده شد، چطور می‌دانیم هر `this` به چه چیزی اشاره می‌کند؟

### Call-site کجاست؟

امیدوارم پاسخی شبیه این داده باشید: «اول باید ببینیم توابع چطور فراخوانی می‌شوند.»

منصفانه است.

فرض کنیم برنامهٔ ما این‌طور است:

```js
var infoForm = {
    theFormElem: null,
    theSubmitBtn: null,

    init() {
        this.theFormElem =
            document.getElementById("the-info-form");
        this.theSubmitBtn =
            theFormElem.querySelector("button[type=submit]");

        // is *this* the call-site?
        this.theSubmitBtn.addEventListener(
            "click",
            this.clickHandler,
            false
        );
    },

    // ..
}
```

آه، جالب. نیمی از خوانندگان هرگز کد واقعی DOM API مثل `getElementById(..)`، `querySelector(..)` و `addEventListener(..)` ندیده‌اند. الان صدای زنگ سردرگمی را شنیدم!

| NOTE: |
| :--- |
| ببخشید، دارم سنم را لو می‌دهم. آنقدر این کارها را کرده‌ام که یادم می‌آید وقتی آن نوع کد را قبل از utilities مثل jQuery که همه جا کد را با `$` شلوغ می‌کرد می‌نوشتیم. و بعد سال‌ها تکامل front-end، به نظر می‌رسد جایی «مدرن‌تر» فرود آمده‌ایم — حداقل، این فرض غالب است. |

حدس می‌زنم خیلی‌هایتان این روزها به دیدن کد component-framework (React و غیره) شبیه این عادت کرده‌اید:

```jsx
// ..

infoForm(props) {
    return (
        <form ref={this.theFormElem}>
            <button type=submit onClick=this.clickHandler>
                Click Me
            </button>
        </form>
    );
}

// ..
```

البته، بسته به framework و غیره، راه‌های زیادی برای شکل‌گیری کد هست.

یا شاید دیگر از componentهای سبک `class` / `this` استفاده نمی‌کنید، چون همه چیز را به hooks و closure منتقل کرده‌اید. در هر صورت، برای اهداف بحث ما، *این* فصل همه دربارهٔ `this` است، پس باید به سبک کدنویسی مثل بالا پایبند بمانیم تا کد مرتبط با بحث داشته باشیم.

و هیچ‌کدام از آن دو snippet قبلی تعریف تابع `clickHandler` را نشان نمی‌دهند. اما بارها گفته‌ام، مهم نیست؛ آنچه مهم است... چیست؟ با من بگویید... آنچه مهم است *نحوهٔ* فراخوانی تابع است.

پس `clickHandler` چطور فراخوانی می‌شود؟ call-site چیست، و کدام قانون انتساب context تطابق دارد؟

### مخفی از دید

اگر گیر کرده‌اید، نگران نباشید. عمداً سخت می‌کنم تا نکتهٔ خیلی مهمی را نشان دهم.

وقتی bindingهای event handler مربوط به `"click"` یا `onClick=` اتفاق می‌افتند، در هر دو مورد `this.clickHandler` را مشخص کردیم، که دلالت دارد شیء context `this` با ویژگی به نام `clickHandler` رویش هست که تعریف تابع ما را نگه می‌دارد.

پس آیا `this.clickHandler` call-site است؟ اگر بود، کدام قانون انتساب اعمال می‌شود؟ قانون *context ضمنی* (#۳)؟

متأسفانه نه.

مشکل این است که **واقعاً نمی‌توانیم call-site را در این برنامه ببینیم**. اوه اوه.

اگر call-site را نمی‌بینیم، چطور می‌دانیم تابع *واقعاً* چطور فراخوانی می‌شود؟

*همین* نکتهٔ من است.

مهم نیست که `this.clickHandler` را pass کردیم. آن صرفاً ارجاعی به مقدار شیء تابع است. call-site نیست.

زیر پوشش، جایی داخل framework، کتابخانه، یا حتی خود محیط JS، وقتی کاربر دکمه را کلیک می‌کند، ارجاع به تابع `clickHandler(..)` فراخوانی می‌شود. و همان‌طور که implied کردیم، آن call-site حتی شیء رویداد DOM را به‌عنوان آرگومان `evt` pass می‌کند.

چون call-site را نمی‌بینیم، باید *تصور* کنیم. شاید شبیه این باشد...؟

```js
// ..
eventCallback( domEventObj );
// ..
```

اگر بود، کدام قانون `this` اعمال می‌شد؟ قانون *context پیش‌فرض* (#۴)؟

یا، اگر call-site این‌طور بود...؟

```js
// ..
eventCallback.call( domElement, domEventObj );
```

حالا کدام قانون `this` اعمال می‌شد؟ قانون *context صریح* (#۲)؟

مگر اینکه کد منبع framework/کتابخانه را باز کنید و ببینید، یا مستندات/مشخصات را بخوانید، *نمی‌دانید* از آن call-site چه انتظاری داشته باشید. یعنی پیش‌بینی نهایی اینکه `this` در تابع `clickHandler` که می‌نویسید به چه چیزی اشاره می‌کند... به بیان ملایم... کمی پیچیده است.

### *This* اشتباه است

برای رهایی از درد بیشتر، مستقیم به اصل مطلب می‌روم.

تقریباً همهٔ پیاده‌سازی‌های مکانیزم click-handler کاری شبیه `.call(..)` می‌کنند، و المان DOM (مثلاً دکمه) که event listener به آن bind شده را به‌عنوان *context صریح* برای فراخوانی تنظیم می‌کنند.

هممم... اوکی است یا مشکل می‌شود؟

به خاطر بیاورید تابع `clickHandler(..)` ما `this`-aware است، و ارجاع `this.theFormElem` آن دلالت بر ارجاع به شیء با ویژگی `theFormElem` دارد، که به نوبهٔ خود به المان والد `<form>` اشاره می‌کند. دکمه‌های DOM به‌طور پیش‌فرض ویژگی `theFormElem` رویشان ندارند.

به عبارت دیگر، ارجاع `this` که event handler ما برایش تنظیم می‌شود تقریباً قطعاً اشتباه است. اوه.

مگر اینکه بخواهیم تابع `clickHandler` را بازنویسی کنیم، باید آن را اصلاح کنیم.

### اصلاح `this`

چند گزینه برای رفع mis-assignment در نظر بگیریم. برای تمرکز، به این سبک event binding برای بحث پایبند می‌مانم:

```js
this.submitBtn.addEventListener(
    "click",
    this.clickHandler,
    false
);
```

یک راه برای رفعش:

```js
// store a fixed reference to the current
// `this` context
var context = this;

this.submitBtn.addEventListener(
    "click",
    function handler(evt){
        return context.clickHandler(evt);
    },
    false
);
```

| TIP: |
| :--- |
| اکثر کد JS قدیمی‌تر که از این رویکرد استفاده می‌کند چیزی مثل `var self = this` می‌گوید به‌جای نام `context` که اینجا می‌دهم. «Self» کلمهٔ کوتاه‌تری است و cooler به نظر می‌رسد. اما معنای semantic کاملاً اشتباه است. کلمهٔ کلیدی `this` ارجاع «self» به تابع نیست، بلکه context آن فراخوانی تابع فعلی است. ممکن است در نگاه اول یکی به نظر برسند، اما مفاهیم کاملاً متفاوتی‌اند، به متفاوتی سیب و آهنگ بیتلز. پس... paraphrase کنم، «هی developer، بدش نکن. یک `self` غمگین بگیر و `context` بهتری بساز.» |

چه اتفاقی می‌افتد؟ تشخیص دادم کد محصورکننده، جایی که فراخوانی `addEventListener` اجرا می‌شود، context `this` فعلی صحیحی دارد، و باید مطمئن شویم همان context `this` هنگام فراخوانی `clickHandler(..)` اعمال شود.

تابع محصورکننده (`handler(..)`) تعریف کردم و سپس call-site را مجبور کردم این‌طور باشد:

```js
context.clickHandler(evt);
```

| TIP: |
| :--- |
| کدام قانون انتساب context `this` اینجا اعمال می‌شود؟ درست است، قانون *context ضمنی* (#۳). |

حالا مهم نیست call-site داخلی کتابخانه/framework/محیط چه شکلی دارد. اما چرا؟

چون اکنون *واقعاً* کنترل call-site را داریم. مهم نیست `handler(..)` چطور فراخوانی شود یا `this` آن چه چیزی انتساب شود. فقط مهم است وقتی `clickHandler(..)` فراخوانی می‌شود، context `this` به آنچه می‌خواستیم تنظیم شود.

آن ترفند را نه فقط با تعریف تابع محصورکننده (`handler(..)`) تا call-site را کنترل کنم انجام دادم، بلکه... و این مهم است، پس از دست ندهید... `handler(..)` را به‌عنوان تابع NON-`this`-aware تعریف کردم! هیچ کلمهٔ کلیدی `this` داخل `handler(..)` نیست، پس هر `this`ی که توسط کتابخانه/framework/محیط تنظیم (یا نشود) کاملاً نامربوط است.

خط `var context = this` برای ترفند حیاتی است. متغیر واژگانی `context` را تعریف می‌کند، که کلمهٔ کلیدی خاصی نیست، و snapshot مقدار `this` بیرونی را نگه می‌دارد. سپس داخل `clickHandler`، صرفاً به متغیر واژگانی (`context`) ارجاع می‌دهیم، نه کلمهٔ کلیدی نسبی/جادویی `this`.

### Lexical This

نام این الگو، به هر حال، «lexical this» است، یعنی `this`ی که مثل متغیر lexical scope رفتار می‌کند به‌جای binding context پویا.

اما معلوم می‌شود JS راه ساده‌تری برای انجام ترفند جادویی «lexical this» دارد. آمادهٔ افشای ترفند هستید؟!

...

تابع فلش `=>`! تادا!

درست است، تابع `=>` برخلاف همهٔ اشکال دیگر تابع خاص است، به این معنا که اصلاً خاص نیست. یا بهتر، هیچ چیز خاصی برای رفتار `this` تعریف نمی‌کند.

در تابع `=>`، کلمهٔ کلیدی `this`... **کلمهٔ کلیدی نیست**. مطلقاً مثل هر متغیر دیگری است، مثل `context` یا `happyFace` یا `foobarbaz`.

بگذارید *این* نکته را مستقیم‌تر تصویرسازی کنم:

```js
function outer() {
    console.log(this.value);

    // define a return an "inner"
    // function
    var inner = () => {
        console.log(this.value);
    };

    return inner;
}

var one = {
    value: 42,
};
var two = {
    value: "sad face",
};

var innerFn = outer.call(one);
// 42

innerFn.call(two);
// 42   <-- not "sad face"
```

`innerFn.call(two)` برای هر تعریف تابع *معمولی* نتیجهٔ `"sad face"` می‌داد. اما چون تابع `inner` که تعریف و برگرداندیم (و به `innerFn` انتساب دادیم) تابع *غیرمعمولی* `=>` بود، رفتار خاص `this` ندارد، بلکه رفتار «lexical this» دارد.

وقتی تابع `innerFn(..)` (یعنی `inner(..)`) فراخوانی می‌شود، حتی با انتساب *context صریح* از طریق `.call(..)`، آن انتساب نادیده گرفته می‌شود.

| NOTE: |
| :--- |
| مطمئن نیستم چرا توابع فلش `=>` حتی `call(..)` / `apply(..)` رویشان دارند، چون توابع no-op ساکت هستند. حدس می‌زنم برای سازگاری با توابع معمولی است. اما همان‌طور که بعداً می‌بینیم، ناسازگاری‌های دیگری بین توابع *معمولی* و توابع *غیرمعمولی* `=>` هست. |

وقتی `this` (`this.value`) داخل تابع فلش `=>` مواجه می‌شود، `this` مثل متغیر lexical معمولی رفتار می‌شود، نه کلمهٔ کلیدی خاص. و چون متغیر `this` در خود آن تابع نیست، JS همان کاری را می‌کند که همیشه با متغیرهای lexical: یک سطح lexical scope بالا می‌رود — در این مورد، به تابع محصورکنندهٔ `outer(..)` — و بررسی می‌کند آیا `this` ثبت‌شده‌ای در آن scope هست.

خوشبختانه، `outer(..)` تابع *معمولی* است، یعنی کلمهٔ کلیدی `this` معمولی دارد. و فراخوانی `outer.call(one)` مقدار `one` را به `this` آن انتساب داد.

پس، `innerFn.call(two)` دارد `inner()` را فراخوانی می‌کند، اما وقتی `inner()` برای `this` مقدار جستجو می‌کند، می‌گیرد... `one`، نه `two`.

#### برگشت به... دکمه

فکر کردید می‌خواهم جوک pun بزنم و «future» بگویم، درست؟!

راه مستقیم‌تر و مناسب‌تر برای حل مسئلهٔ قبلی، جایی که `var context = this` کرده بودیم تا نوعی رفتار «lexical this» جعلی بگیریم، استفاده از تابع فلش `=>` است، چون ویژگی طراحی اصلیش... «lexical this» است.

```js
this.submitBtn.addEventListener(
    "click",
    evt => this.clickHandler(evt),
    false
);
```

بوم! مشکل حل شد! Mic drop!

در *این* حرفم را بشنوید: تابع فلش `=>` *نه* — تکرار می‌کنم، *نه* — دربارهٔ تایپ کمتر کاراکتر است. نکتهٔ اصلی اضافه شدن تابع `=>` به JS دادن رفتار «lexical this» بدون توسل به hackهای سبک `var context = this` (یا بدتر، `var self = this`) بود.

| TIP: |
| :--- |
| اگر به «lexical this» نیاز دارید، همیشه تابع فلش `=>` را ترجیح دهید. اگر به «lexical this» نیاز ندارید، خب... تابع فلش `=>` ممکن است بهترین ابزار برای کار نباشد. |

#### زمان اعتراف

در سراسر این فصل گفته‌ام که نحوهٔ نوشتن تابع و جایی که تابع را می‌نویسید *هیچ ربطی* به نحوهٔ انتساب `this` آن ندارد.

برای توابع معمولی، درست است. اما وقتی تابع *غیرمعمولی* فلش `=>` را در نظر می‌گیریم، دیگر کاملاً دقیق نیست.

شکل اصلی `=>` مربوط به `clickHandler` از اوایل فصل را به خاطر دارید؟

```js
const clickHandler = evt =>
    evt.target.matches("button") ?
        this.theFormElem.submit() :
        evt.stopPropagation();
```

اگر آن شکل را در همان context event bindingمان استفاده کنیم، می‌تواند این‌طور باشد:

```js
const clickHandler = evt =>
    evt.target.matches("button") ?
        this.theFormElem.submit() :
        evt.stopPropagation();

this.submitBtn.addEventListener("click",clickHandler,false);
```

خیلی توسعه‌دهندگان ترجیح می‌دهند حتی بیشتر کاهشش دهند، به تابع فلش `=>` inline:

```js
this.submitBtn.addEventListener(
    "click",
    evt => evt.target.matches("button") ?
        this.theFormElem.submit() :
        evt.stopPropagation(),
    false
);
```

وقتی تابع فلش `=>` می‌نویسیم، مطمئنیم binding `this` آن دقیقاً binding `this` فعلی هر تابع محصورکنندهٔ در حال اجرا خواهد بود، صرف نظر از call-site تابع فلش `=>`. پس به عبارت دیگر، *نحوهٔ* نوشتن تابع فلش `=>` و *جایی* که نوشتیم مهم است.

این سؤال `this` را کاملاً پاسخ نمی‌دهد. فقط سؤال را به *نحوهٔ فراخوانی تابع محصورکننده* منتقل می‌کند. در واقع، تمرکز روی call-site هنوز تنها چیز مهم است.

اما nuanceای که اعتراف می‌کنم تا *این* لحظه حذف کرده بودم این است: مهم است *کدام* call-site را در نظر بگیریم، نه فقط *هر* call-site در call stack فعلی. call-site مهم، نزدیک‌ترین فراخوانی تابع در call stack فعلی است ***که واقعاً context `this` انتساب می‌دهد***.

چون تابع فلش `=>` هرگز call-site انتساب‌دهندهٔ `this` ندارد (مهم نیست چه)، آن call-site برای سؤال ما نامربوط است. باید call stack را بالا برویم تا فراخوانی تابعی پیدا کنیم که *هست* انتساب‌دهندهٔ `this` — حتی اگر آن تابع فراخوانی‌شده خودش `this`-aware نباشد.

**آن** تنها call-site مهم است.

#### Call-site درست را پیدا کنید

با یک آشفتگی پیچیده از توابع/فراخوانی‌های تو در تو تصویرسازی می‌کنم:

```js
globalThis.value = { result: "Sad face" };

function one() {
    function two() {
        var three = {
            value: { result: "Hmmm" },

            fn: () => {
                const four = () => this.value;
                return four.call({
                    value: { result: "OK", },
                });
            },
        };
        return three.fn();
    };
    return two();
}

new one();          // ???
```

می‌توانید آن (کابوس) را در ذهنتان طی کنید و تعیین کنید چه چیزی از فراخوانی `new one()` برگردانده می‌شود؟

می‌تواند هر کدام از این‌ها باشد:

```js
// from `four.call(..)`:
{ result: "OK" }

// or, from `three` object:
{ result: "Hmmm" }

// or, from the `globalThis.value`:
{ result: "Sad face" }

// or, empty object from the `new` call:
{}
```

call-stack برای آن فراخوانی `new one()`:

```
four         |
three.fn     |
two          | (this = globalThis)
one          | (this = {})
[ global ]   | (this = globalThis)
```

چون `four()` و `fn()` هر دو توابع فلش `=>` هستند، call-siteهای `three.fn()` و `four.call(..)` انتساب‌دهندهٔ `this` نیستند؛ پس برای سؤال ما نامربوط‌اند. فراخوانی بعدی برای در نظر گرفتن در call stack چیست؟ `two()`. آن تابع معمولی است (می‌تواند انتساب `this` بپذیرد)، و call-site با قانون انتساب *context پیش‌فرض* (#۴) تطابق دارد. چون در strict-mode نیستیم، `this` به `globalThis` انتساب می‌شود.

وقتی `four()` در حال اجراست، `this` فقط متغیر معمولی است. پس به تابع حاویش (`three.fn()`) نگاه می‌کند، اما دوباره تابعی بدون `this` پیدا می‌کند. پس یک سطح دیگر بالا می‌رود و تابع *معمولی* `two()` را پیدا می‌کند که `this` تعریف شده دارد. و آن `this` همان `globalThis` است. پس عبارت `this.value` به `globalThis.value` resolve می‌شود، که برمی‌گرداند... `{ result: "Sad face" }`.

...

نفس عمیق بکشید. می‌دانم ذهنی زیاد است. و منصفانه بگویم، مثال super contrived است. تقریباً هرگز آن پیچیدگی را در یک call stack مخلوط نمی‌بینید.

اما قطعاً call stackهای مخلوط در برنامه‌های واقعی پیدا می‌کنید. باید با تحلیلی که تصویرسازی کردم راحت شوید تا بتوانید call stack را باز کنید تا recentترین call-site انتساب‌دهندهٔ `this` را پیدا کنید.

ضرب‌المثل قبلی را به خاطر بیاورید: «با قدرت بزرگ مسئولیت بزرگ می‌آید». انتخاب کد جهت‌یافته به `this` (حتی `class`ها) یعنی انتخاب هم انعطافش و هم نیاز به راحتی در پیمایش call stack برای فهم نحوهٔ رفتارش.

این تنها راه نوشتن (و بعد خواندن!) مؤثر کد `this`-aware است.

### This حتماً پیش می‌آید

کمی عقب‌تر، گزینهٔ دیگری هست اگر نخواهید از رفتار «lexical this» تابع فلش `=>` برای رفع عملکرد button event handler استفاده کنید.

علاوه بر `call(..)` / `apply(..)` — این‌ها توابع را فراخوانی می‌کنند، به خاطر داشته باشید! — توابع JS utility سومی به نام `bind(..)` هم دارند — که تابع را فراخوانی *نمی‌کند*، فقط واضح بگویم.

utility `bind(..)` نسخهٔ *جدید* wrapped/bound تابع را تعریف می‌کند، جایی که `this` آن از پیش تنظیم و ثابت است، و نمی‌توان با `call(..)` یا `apply(..)` یا حتی شیء *context ضمنی* در call-site override کرد:

```js
this.submitBtn.addEventListener(
    "click",
    this.clickHandler.bind(this),
    false
);
```

چون تابع `this`-bound را به‌عنوان event handler pass می‌کنم، به همین ترتیب مهم نیست آن utility چطور سعی می‌کند `this` تنظیم کند، چون قبلاً `this` را به آنچه می‌خواستم مجبور کرده‌ام: مقدار `this` از context فراخوانی تابع محصورکننده.

#### به‌زحمت New

این الگو اغلب «hard binding» نامیده می‌شود، چون ارجاع تابعی می‌سازیم که به `this` خاصی قویاً bound است. خیلی نوشته‌های JS ادعا کرده‌اند تابع فلش `=>` اساساً فقط syntax برای hard-binding مربوط به `bind(this)` است. نیست. بیایید عمیق شویم.

اگر می‌خواستید utility `bind(..)` بسازید، شاید این‌طور به نظر برسد:

```js
function bind(fn,context) {
    return function bound(...args){
        return fn.apply(context,args);
    };
}
```

| NOTE: |
| :--- |
| این واقعاً نحوهٔ پیاده‌سازی `bind(..)` نیست. رفتار پیچیده‌تر و nuancedتر است. فقط بخشی از رفتارش را در این snippet تصویرسازی می‌کنم. |

آشنا به نظر می‌رسد؟ از hack قدیمی «lexical this» جعلی استفاده می‌کند. و زیر پوشش، انتساب *context صریح* است، در این مورد از طریق `apply(..)`.

پس صبر کنید... یعنی می‌توانستیم با تابع فلش `=>` انجامش دهیم؟

```js
function bind(fn,context) {
    return (...args) => fn.apply(context,args);
}
```

اه... نه کاملاً. مثل اکثر چیزها در JS، کمی nuance هست. تصویرسازی می‌کنم:

```js
// candidate implementation, for comparison
function fakeBind(fn,context) {
    return (...args) => fn.apply(context,args);
}

// test subject
function thisAwareFn() {
    console.log(`Value: ${this.value}`);
}

// control data
var obj = {
    value: 42,
};

// experiment
var f = thisAwareFn.bind(obj);
var g = fakeBind(thisAwareFn,obj);

f();            // Value: 42
g();            // Value: 42

new f();        // Value: undefined
new g();        // <--- ???
```

اول، به فراخوانی `new f()` نگاه کنید. استفادهٔ عجیبی است، فراخوانی `new` روی تابع hard-bound. احتمالاً به‌ندرت چنین کاری می‌کنید. اما چیز جالبی نشان می‌دهد. حتی با اینکه `f()` به context `this` مربوط به `obj` hard-bound بود، عملگر `new` توانست `this` تابع hard-bound را hijack کند و دوباره به شیء خالی تازه‌ساخته bind کند. آن شیء ویژگی `value` ندارد، به همین دلیل `"Value: undefined"` چاپ می‌شود.

اگر عجیب به نظر می‌رسد، موافقم. nuance گوشهٔ عجیبی است. چیزی نیست که احتمالاً exploit کنید. اما فقط برای trivia اشاره نمی‌کنم. به چهار قانون ارائه‌شدهٔ قبلی در این فصل برگردید. به خاطر دارید چطور order-of-precedence را گفتم و `new` در بالا (#۱) بود، جلوتر از قانون انتساب *صریح* `call(..)` / `apply(..)` (#۲)؟

چون می‌توانیم `bind(..)` را نوعی variation آن قانون تصور کنیم، اکنون آن order-of-precedence ثابت شده را می‌بینیم. `new` precedentتر است و حتی می‌تواند تابع hard-bound را override کند. کمی فکر می‌کنید تابع hard-bound شاید آنقدرها «hard»-bound نیست، ها؟!

اما... با فراخوانی `new g()` چه می‌شود، که `new` را روی تابع فلش `=>` برگردانده‌شده فراخوانی می‌کند؟ آیا همان نتیجهٔ `new f()` را پیش‌بینی می‌کنید؟

متأسفم که ناامید می‌کنم.

آن خط واقعاً استثناء پرتاب می‌کند، چون تابع `=>` نمی‌تواند با کلمهٔ کلیدی `new` استفاده شود.

اما چرا؟ بهترین پاسخ من، بدون اینکه خودم در TC39 معتبر باشم، این است که از نظر مفهومی و واقعی، تابع فلش `=>` تابعی با `this` hard-bound نیست، تابعی است که اصلاً `this` ندارد. به همین دلیل، `new` علیه چنین تابعی معنا ندارد، پس JS فقط آن را disallow می‌کند.

| NOTE: |
| :--- |
| قبلاً به خاطر بیاورید وقتی گفتم توابع فلش `=>` دارای `call(..)`، `apply(..)` و حتی `bind(..)` هستند. اما دیدیم چنین توابعی اساساً این utilityها را به‌عنوان no-op نادیده می‌گیرند. کمی عجیب است، به نظر من، که توابع فلش `=>` همهٔ آن utilityها را به‌عنوان pass-through no-op دارند، اما برای کلمهٔ کلیدی `new`، دوباره فقط no-op pass-through نیست، بلکه با استثناء disallowed است. |

اما نکتهٔ اصلی این است: تابع فلش `=>` *شکل syntactic* مربوط به `bind(this)` نیست.

### از دست دادن این نبرد

یک بار دیگر به مثال button event handler برمی‌گردیم:

```js
this.submitBtn.addEventListener(
    "click",
    this.clickHandler,
    false
);
```

نگرانی عمیق‌تری هست که هنوز به آن نپرداخته‌ایم.

چند رویکرد مختلف برای ساخت ارجاع تابع callback متفاوت برای pass کردن به‌جای `this.clickHandler` دیدیم.

اما هر کدام از آن روش‌ها را انتخاب کنیم، به‌طور تحت‌اللفظی تابع متفاوتی تولید می‌کنند، نه فقط تغییر in-place در تابع `clickHandler` موجودمان.

چرا مهم است؟

خب، اولاً هرچه توابع بیشتری می‌سازیم (و دوباره می‌سازیم)، زمان پردازش بیشتر (خیلی کم) و حافظهٔ بیشتر (معمولاً نسبتاً کم) مصرف می‌کنیم. و وقتی ارجاع تابع را دوباره می‌سازیم و قدیمی را دور می‌ریزیم، حافظهٔ un-reclaimed هم می‌ماند، که به GC فشار می‌آورد تا بیشتر، لحظه‌ای universe برنامهٔ ما را متوقف کند تا پاک کند و آن حافظه را reclaim کند.

اگر hook کردن این event listening عملیات یک‌باره باشد، مشکلی نیست. اما اگر بارها و بارها اتفاق بیفتد، اثرات عملکرد سطح سیستم *می‌تواند* جمع شود. آیا animation صاف دیگری jitter داشته؟ احتمالاً GC بود که وارد شد و یک دسته حافظهٔ reclaimable را پاک کرد.

اما نگرانی دیگر این است که برای چیزهایی مثل event handlerها، اگر قرار است event listener را زمانی بعد حذف کنیم، باید ارجاعی به همان تابع دقیقی که originally attach کردیم نگه داریم. اگر از کتابخانه/framework استفاده می‌کنیم، اغلب (اما نه همیشه!) آن جزئیات dirty-work کوچک را برایتان انجام می‌دهند. در غیر این صورت، بر عهدهٔ ماست مطمئن شویم هر تابعی که قصد attach داریم، ارجاعی نگه داریم در صورت نیاز بعداً.

پس نکتهٔ من این است: preset کردن انتساب `this`، مهم نیست چطور انجامش دهید، تا قابل پیش‌بینی باشد، هزینه دارد. هزینهٔ سطح سیستم و هزینهٔ نگهداری/پیچیدگی برنامه. *هرگز* رایگان نیست.

یک واکنش به آن واقعیت این است که تصمیم بگیریم، اوکی، فقط همهٔ آن ارجاعات تابع انتساب‌یافتهٔ `this` را یک بار، از قبل، up-front تولید می‌کنیم. بدین ترتیب مطمئن می‌شویم هم فشار سیستم و هم فشار کد را به حداقل برسانیم.

منطقی به نظر می‌رسد، درست؟ نه اینقدر سریع.

#### Pre-Binding کردن Contextهای تابع

اگر ارجاع تابع یک‌باره دارید که باید `this`-bound باشد، و از فلش `=>` یا فراخوانی `bind(this)` استفاده می‌کنید، مشکلی نمی‌بینم.

اما اگر اکثر یا همهٔ توابع `this`-aware در بخشی از کدتان به روش‌هایی فراخوانی می‌شوند که `this` context قابل پیش‌بینی مورد انتظارتان نیست، و پس تصمیم می‌گیرید باید همه را hard-bind کنید... فکر می‌کنم سیگنال هشدار بزرگی است که دارید اشتباه پیش می‌روید.

لطفاً بحث بخش «Avoid This» از فصل ۳ را به خاطر بیاورید، که با این snippet کد شروع شد:

```js
class Point2d {
    x = null
    getDoubleX = () => this.x * 2

    constructor(x,y) {
        this.x = x;
        this.y = y;
    }
    toString() { /* .. */ }
}

var point = new Point2d(3,4);
```

حالا تصور کنید با آن کد این کار را کردیم:

```js
const getX = point.getDoubleX;

// later, elsewhere

getX();         // 6
```

همان‌طور که می‌بینید، مشکلی که سعی در حلش داشتیم همان است که در این فصل با آن سروکار داریم. می‌خواستیم بتوانیم ارجاع تابعی مثل `getX()` فراخوانی کنیم و *معنی* و *رفتار* آن مثل `point.getDoubleX()` باشد. اما قوانین `this` روی توابع *معمولی* اینطور کار نمی‌کنند.

پس از تابع فلش `=>` استفاده کردیم. مشکلی نیست، درست؟!

اشتباه.

مشکل ریشهٔ واقعی این است که *دو چیز متضاد* از کدمان می‌خواهیم، و سعی می‌کنیم همان *چکش* را برای هر دو *میخ* استفاده کنیم.

می‌خواهیم متد `this`-aware روی prototype کلاس ذخیره داشته باشیم، تا فقط یک تعریف برای تابع باشد و همهٔ زیرکلاس‌ها و نمونه‌هایمان آن تابع را به خوبی share کنند. و نحوهٔ share همه از طریق قدرت binding پویای `this` است.

اما همزمان، *همچنین* می‌خواهیم آن ارجاعات تابع وقتی آن‌ها را pass می‌کنیم و کد دیگر مسئول call-site است به‌طور جادویی `this`-assigned به نمونهٔ ما بمانند.

به عبارت دیگر، گاهی می‌خواهیم چیزی مثل `point.getDoubleX` یعنی «ارجاعی بده که به `point` `this`-assigned است»، و گاهی می‌خواهیم همان عبارت `point.getDoubleX` یعنی ارجاع تابع `this`-assignable پویا بدهد تا context مورد نیازم را در این لحظه درست بگیرد.

شاید JS بتواند عملگر دیگری غیر از `.` ارائه دهد، مثل `::` یا `->` یا چیزی شبیه، که بتوانید نوع ارجاع تابع مورد نظرتان را تشخیص دهید. در واقع، پیشنهاد دیرپایی برای عملگر `this`-binding (`::`) هست که گاه توجه می‌گیرد و بعد به نظر می‌رسد متوقف می‌شود. چه کسی می‌داند، شاید روزی چنین عملگری بالاخره land شود و گزینه‌های بهتری داشته باشیم.

اما قویاً suspect می‌کنم حتی اگر روزی land شود، ارجاع تابع کاملاً جدیدی vend می‌کند، دقیقاً مثل رویکردهای `=>` یا `bind(this)` که قبلاً گفتیم. به‌عنوان راه‌حل رایگان و کامل نمی‌آید. همیشه تنشی بین خواستن همان تابع برای گاهی `this`-flexible و گاهی `this`-predictable بودن خواهد بود.

نویسندگان کد جهت‌یافته به `class` در JS اغلب دیر یا زود به این تنش دقیق برخورد می‌کنند. و می‌دانید چه می‌کنند؟

هزینه‌های pre-binding سادهٔ همهٔ متدهای `this`-aware کلاس به‌عنوان توابع فلش `=>` در ویژگی‌های member را در نظر نمی‌گیرند. متوجه نمی‌شوند که کاملاً هدف کل زنجیرهٔ `[[Prototype]]` را شکست داده. و متوجه نمی‌شوند اگر fixed-context آن چیزی است که *واقعاً* نیاز دارند، مکانیزم کاملاً متفاوتی در JS هست که برای آن هدف مناسب‌تر است.

#### نگاه انتقادی‌تر بیندازید

پس وقتی این کار را می‌کنید:

```js
class Point2d {
    x = null
    y = null
    getDoubleX = () => this.x * 2
    toString = () => `(${this.x},${this.y})`

    constructor(x,y) {
        this.x = x;
        this.y = y;
    }
}

var point = new Point2d(3,4);
var anotherPoint = new Point2d(5,6);

var f = point.getDoubleX;
var g = anotherPoint.toString;

f();            // 6
g();            // (5,6)
```

می‌گویم «ick!» به متدهای `this`-aware hard-bound یعنی `getDoubleX()` و `toString()` آنجا. برای من، code smell است. اما رویکرد حتی *بدتر* که بسیاری توسعه‌دهندگان در گذشته ترجیح داده‌اند:

```js
class Point2d {
    x = null
    y = null

    constructor(x,y) {
        this.x = x;
        this.y = y;
        this.getDoubleX = this.getDoubleX.bind(this);
        this.toString = this.toString.bind(this);
    }
    getDoubleX() { return this.x * 2; }
    toString() { return `(${this.x},${this.y})`; }
}

var point = new Point2d(3,4);
var anotherPoint = new Point2d(5,6);

var f = point.getDoubleX;
var g = anotherPoint.toString;

f();            // 6
g();            // (5,6)
```

Double ick.

در هر دو مورد، از مکانیزم `this` استفاده می‌کنید اما کاملاً خیانت/خنثی‌اش می‌کنید، با گرفتن همهٔ dynamicism قدرتمند `this`.

واقعاً باید حداقل این رویکرد جایگزین را در نظر بگیرید، که کل مکانیزم `this` را رد می‌کند:

```js
function Point2d(px,py) {
    var x = px;
    var y = py;

    return {
        getDoubleX() { return x * 2; },
        toString() { return `(${x},${y})`; }
    };
}

var point = Point2d(3,4);
var anotherPoint = Point2d(5,6);

var f = point.getDoubleX;
var g = anotherPoint.toString;

f();            // 6
g();            // (5,6)
```

می‌بینید؟ هیچ `this` زشت یا پیچیده‌ای برای شلوغ کردن آن کد یا نگرانی از corner caseها. Lexical scope فوق‌العاده سرراست و شهودی است.

وقتی فقط می‌خواهیم اکثر/همهٔ رفتارهای تابعمان context ثابت و قابل پیش‌بینی داشته باشند، مناسب‌ترین راه‌حل، سرراست‌ترین و حتی performantترین راه‌حل، متغیرهای lexical و scope closure است.

وقتی زحمت پاشیدن ارجاعات `this` در سراسر قطعه‌ای کد را می‌کشید، و بعد کل مکانیزم را با «lexical this» مربوط به `=>` یا `bind(this)` از پا درمی‌آورید، انتخاب کرده‌اید کد را verboseتر، پیچیده‌تر، overwroughtتر کنید. و چیزی مفیدتر از آن نگرفتید، مگر پیروی از bandwagon مربوط به `this` (و `class`).
