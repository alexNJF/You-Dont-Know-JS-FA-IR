# دام‌های `class` (`class` Gotchas)

اما همه چیز bubblegum و roses نیست. هنوز مسائل عمیق و به‌شدت نگران‌کننده دربارهٔ استفاده از «class»ها به‌عنوان الگوی طراحی در JS وجود دارد.

اول، نحو `class` ممکن است شما را متقاعد کند که مکانیزم «class» جدیدی از ES6 در JS وجود دارد. **چنین نیست.** `class` عمدتاً فقط syntactic sugar روی مکانیزم `[[Prototype]]` (delegation!) موجود است.

یعنی `class` در زمان اعلام به‌صورت استاتیک تعریف‌ها را کپی نمی‌کند آن‌طور که در زبان‌های class-oriented سنتی می‌کند. اگر متدی روی «class» والد را (عمداً یا تصادفی) تغییر/جایگزین کنید، «class» فرزند و/یا instanceها هنوز «تحت تأثیر» قرار می‌گیرند، به این معنا که در زمان اعلام کپی نگرفتند و همه هنوز از مدل live-delegation مبتنی بر `[[Prototype]]` استفاده می‌کنند:

```js
class C {
	constructor() {
		this.num = Math.random();
	}
	rand() {
		console.log( "Random: " + this.num );
	}
}

var c1 = new C();
c1.rand(); // "Random: 0.4324299..."

C.prototype.rand = function() {
	console.log( "Random: " + Math.round( this.num * 1000 ));
};

var c2 = new C();
c2.rand(); // "Random: 867"

c1.rand(); // "Random: 432" -- oops!!!
```

این فقط در صورت *از قبل دانستن* طبیعت delegation چیزها رفتار معقول به نظر می‌رسد، به‌جای انتظار *کپی* از «classهای واقعی». پس سؤالی که باید از خود بپرسید این است: چرا برای چیزی اساساً متفاوت از classها نحو `class` را انتخاب می‌کنید؟

آیا نحو `class` مربوط به ES6 **فقط** دیدن و فهم تفاوت بین classهای سنتی و objectهای delegate‌شده را *سخت‌تر* نمی‌کند؟

نحو `class` *راهی* برای اعلام propertyهای عضو class (فقط متدها) فراهم نمی‌کند. پس اگر برای دنبال کردن state مشترک بین instanceها به آن نیاز دارید، به نحو زشت `.prototype` برمی‌گردید، مثل این:

```js
class C {
	constructor() {
		// make sure to modify the shared state,
		// not set a shadowed property on the
		// instances!
		C.prototype.count++;

		// here, `this.count` works as expected
		// via delegation
		console.log( "Hello: " + this.count );
	}
}

// add a property for shared state directly to
// prototype object
C.prototype.count = 0;

var c1 = new C();
// Hello: 1

var c2 = new C();
// Hello: 2

c1.count === 2; // true
c1.count === c2.count; // true
```

بزرگترین مشکل اینجا این است که نحو `class` را خیانت می‌کند با افشای (نشت!) `.prototype` به‌عنوان جزئیات پیاده‌سازی.

اما همچنین هنوز غافل‌گیری gotcha را داریم که `this.count++` به‌طور ضمنی property جدا shadowشدهٔ `.count` روی هر دو object مربوط به `c1` و `c2` می‌سازد، به‌جای به‌روزرسانی state مشترک. `class` برای آن موضوع هیچ تسلیتی به ما نمی‌دهد، مگر (احتمالاً) با عدم پشتیبانی نحوی دلالت کند که اصلاً نباید آن کار را بکنید.

علاوه بر این، shadowing تصادفی هنوز خطر است:

```js
class C {
	constructor(id) {
		// oops, gotcha, we're shadowing `id()` method
		// with a property value on the instance
		this.id = id;
	}
	id() {
		console.log( "Id: " + this.id );
	}
}

var c1 = new C( "c1" );
c1.id(); // TypeError -- `c1.id` is now the string "c1"
```

همچنین مسائل ظریف و nuanceشدهٔ بسیار با نحوهٔ کار `super` وجود دارد. ممکن است فرض کنید `super` به‌طور مشابه با نحوهٔ bind شدن `this` (فصل ۲ را ببینید) bind می‌شود، یعنی `super` همیشه به یک سطح بالاتر از هرچه موقعیت فعلی متد در زنجیرهٔ `[[Prototype]]` است bind شود.

با این حال، به‌خاطر دلایل عملکرد (binding مربوط به `this` از قبل گران است)، `super` به‌صورت داینامیک bind نمی‌شود. به‌نوعی «استاتیک» در زمان اعلام bind می‌شود. مهم نیست، درست؟

اه... شاید، شاید نه. اگر مثل بیشتر توسعه‌دهندگان JS شروع کنید توابع را به objectهای مختلف (که از تعاریف `class` آمده‌اند) به روش‌های مختلف انتساب دهید، احتمالاً خیلی از این آگاه نخواهید بود که در همهٔ آن موارد مکانیزم `super` زیر پرده باید هر بار دوباره bind شود.

و بسته به اینکه چه رویکردهای نحوی برای این انتساب‌ها برمی‌گزینید، ممکن است مواردی باشد که `super` نتواند درست bind شود (حداقل نه جایی که حدس می‌زنید)، پس ممکن است (در زمان نگارش، بحث TC39 ادامه دارد) مجبور شوید `super` را دستی با `toMethod(..)` bind کنید (نوعی مثل اینکه برای `this` باید `bind(..)` بکنید — فصل ۲ را ببینید).

عادت دارید بتوانید متدها را به objectهای مختلف انتساب دهید تا *به‌طور خودکار* از پویایی `this` از طریق قانون *implicit binding* (فصل ۲ را ببینید) بهره ببرید. اما احتمالاً همین برای متدهایی که از `super` استفاده می‌کنند درست نخواهد بود.

در نظر بگیرید `super` اینجا (علیه `D` و `E`) چه باید بکند:

```js
class P {
	foo() { console.log( "P.foo" ); }
}

class C extends P {
	foo() {
		super();
	}
}

var c1 = new C();
c1.foo(); // "P.foo"

var D = {
	foo: function() { console.log( "D.foo" ); }
};

var E = {
	foo: C.prototype.foo
};

// Link E to D for delegation
Object.setPrototypeOf( E, D );

E.foo(); // "P.foo"
```

اگر فکر می‌کردید (کاملاً معقول!) که `super` در زمان فراخوانی به‌صورت داینامیک bind می‌شود، ممکن بود انتظار داشته باشید `super()` به‌طور خودکار تشخیص دهد که `E` به `D` delegate می‌کند، پس `E.foo()` با `super()` باید به `D.foo()` فراخوانی کند.

**چنین نیست.** به‌خاطر دلایل عمل‌گرایی عملکرد، `super` *late bound* (یعنی به‌صورت داینامیک bind‌شده) مثل `this` نیست. به‌جای آن در زمان فراخوانی از `[[HomeObject]].[[Prototype]]` به‌دست می‌آید، که `[[HomeObject]]` در زمان ساخت به‌صورت استاتیک bind شده است.

در این مورد خاص، `super()` هنوز به `P.foo()` resolve می‌شود، چون `[[HomeObject]]` متد هنوز `C` است و `C.[[Prototype]]` برابر `P` است.

*احتمالاً* راه‌هایی برای رسیدگی دستی به چنین gotchaهایی خواهد بود. استفاده از `toMethod(..)` برای bind/rebind کردن `[[HomeObject]]` یک متد (همراه با تنظیم `[[Prototype]]` آن object!) در این سناریو به نظر کار می‌کند:

```js
var D = {
	foo: function() { console.log( "D.foo" ); }
};

// Link E to D for delegation
var E = Object.create( D );

// manually bind `foo`s `[[HomeObject]]` as
// `E`, and `E.[[Prototype]]` is `D`, so thus
// `super()` is `D.foo()`
E.foo = C.prototype.foo.toMethod( E, "foo" );

E.foo(); // "D.foo"
```

**یادداشت:** `toMethod(..)` متد را clone می‌کند و `homeObject` را به‌عنوان پارامتر اول می‌گیرد (به‌همین‌دلیل `E` را پاس می‌دهیم) و پارامتر دوم (اختیاری) نامی برای متد جدید تنظیم می‌کند (که روی «foo» نگه می‌داریم).

هنوز باید دید آیا gotchaهای corner case دیگری هست که توسعه‌دهندگان به آن برخورد کنند. به‌هرحال باید دقیق باشید و آگاه بمانید engine در کجاها خودکار `super` را برای شما پیدا می‌کند و در کجاها باید خودتان رسیدگی کنید. **اف!**

# استاتیک > داینامیک؟

اما بزرگترین مشکل از همه دربارهٔ `class` مربوط به ES6 این است که همهٔ این gotchaهای مختلف یعنی `class` نوعی شما را به نحوی می‌کشاند که به نظر دلالت می‌کند (مثل classهای سنتی) وقتی یک `class` اعلام کردید تعریف استاتیک یک چیز (instantiate‌شده در آینده) است. کاملاً از نظر دور می‌کنید که `C` یک object است، یک چیز مشخص، که می‌توانید مستقیماً با آن تعامل کنید.

در زبان‌های class-oriented سنتی هرگز تعریف یک class را بعداً تنظیم نمی‌کنید، پس الگوی طراحی class چنین قابلیت‌هایی را پیشنهاد نمی‌کند. اما **یکی از قدرتمندترین بخش‌های** JS این است که *داینامیک* است و تعریف هر object (مگر اینکه immutable کنید) چیز سیال و قابل تغییر است.

`class` به نظر دلالت می‌کند نباید چنین کارهایی بکنید، با وادار کردن شما به نحو زشت‌تر `.prototype` برای انجام آن، یا وادار کردن شما به فکر کردن به gotchaهای `super` و غیره. همچنین *پشتیبانی خیلی کمی* برای هر یک از pitfalls که این پویایی می‌تواند بیاورد ارائه می‌دهد.

به عبارت دیگر، گویی `class` می‌گوید: «داینامیک خیلی سخت است، پس احتمالاً ایدهٔ خوبی نیست. اینجا نحو به‌ظاهر استاتیک است، پس چیزهایتان را استاتیک کد کنید.»

چه تفسیر غم‌انگیزی از جاوااسکریپت: **داینامیک خیلی سخت است، بیایید تظاهر کنیم (اما واقعاً نباشیم!) استاتیک.**

این‌ها دلایلی هستند که `class` مربوط به ES6 خود را به‌عنوان راه‌حل خوب برای سردردهای نحوی ماسک می‌زند، اما در واقع آب را بیشتر گل‌آلود می‌کند و برای JS و فهم روشن و مختصر وضع را بدتر می‌کند.

**یادداشت:** اگر از utility مربوط به `.bind(..)` برای ساختن تابع hard-bound استفاده کنید (فصل ۲ را ببینید)، تابع ساخته‌شده با `extend` مربوط به ES6 مثل توابع معمولی subclassable نیست.
