# به سوی طراحی مبتنی بر delegation

برای آن که بتوانیم به‌درستی بر نحوهٔ استفاده از `[[Prototype]]` به ساده‌ترین شکل تمرکز کنیم، باید درک کنیم که این مکانیزم نمایندهٔ الگوی طراحی‌ای اساساً متفاوت از classهاست (فصل ۴ را ببینید).

**یادداشت:** برخی اصول طراحی class-oriented همچنان معتبرند؛ پس هر آنچه می‌دانید را دور نریزید (فقط بیشترش را!). مثلاً *encapsulation* بسیار قدرتمند است و با delegation سازگار است (هرچند به‌اندازهٔ class رایج نیست).

باید سعی کنیم نگرش خود را از الگوی طراحی class/inheritance به الگوی طراحی behavior delegation تغییر دهیم. اگر در تحصیل یا حرفهٔ خود بیشتر برنامه‌نویسی را با تفکر class-based انجام داده‌اید، این تغییر ممکن است ناراحت‌کننده یا غیرطبیعی به‌نظر برسد. شاید لازم باشد این تمرین ذهنی را چندین بار تکرار کنید تا به این شیوهٔ بسیار متفاوت فکر کردن عادت کنید.

ابتدا چند تمرین نظری را با هم مرور می‌کنیم، سپس نمونهٔ عینی‌تری را در کنار هم می‌بینیم تا زمینهٔ عملی برای کد خودتان فراهم شود.

### Class Theory

فرض کنید چند «وظیفه» مشابه («XYZ»، «ABC» و غیره) داریم که باید در نرم‌افزار مدل کنیم.

در رویکرد class، سناریو را این‌طور طراحی می‌کنید: یک parent (پایه) class کلی مثل `Task` تعریف می‌کنید که رفتار مشترک همهٔ وظایف «مشابه» را مشخص می‌کند. سپس child classهای `XYZ` و `ABC` را تعریف می‌کنید که هر دو از `Task` ارث می‌برند و هر کدام رفتار تخصصی خود را برای انجام وظیفهٔ مربوطه اضافه می‌کنند.

**نکتهٔ مهم:** الگوی طراحی class شما را ترغیب می‌کند که برای بهرهٔ بیشتر از inheritance از method overriding (و polymorphism) استفاده کنید؛ یعنی تعریف متدی کلی از `Task` را در وظیفهٔ `XYZ` خود override کنید و شاید از `super` برای فراخوانی نسخهٔ پایهٔ آن متد و افزودن رفتار بیشتر استفاده کنید. **احتمالاً جاهای زیادی** پیدا می‌کنید که بتوانید رفتار کلی را به parent class «abstract» کنید و در child classها آن را تخصصی (override) کنید.

یک pseudo-code تقریبی برای این سناریو:

```js
class Task {
	id;

	// constructor `Task()`
	Task(ID) { id = ID; }
	outputTask() { output( id ); }
}

class XYZ inherits Task {
	label;

	// constructor `XYZ()`
	XYZ(ID,Label) { super( ID ); label = Label; }
	outputTask() { super(); output( label ); }
}

class ABC inherits Task {
	// ...
}
```

حالا می‌توانید یک یا چند **کپی** از child classِ `XYZ` instantiate کنید و از آن instanceها برای انجام وظیفهٔ «XYZ» استفاده کنید. این instanceها **هم** رفتار تعریف‌شدهٔ کلی در `Task` و **هم** رفتار تعریف‌شدهٔ خاص `XYZ` را به‌صورت کپی دارند. به‌همین‌ترتیب، instanceهای classِ `ABC` کپی رفتار `Task` و رفتار خاص `ABC` را دارند. پس از construction، عموماً فقط با این instanceها تعامل می‌کنید (و نه با classها)، چون هر instance کپی همهٔ رفتاری را دارد که برای انجام وظیفهٔ مورد نظر لازم است.

### Delegation Theory

اما حالا همان حوزهٔ مسئله را با *behavior delegation* به‌جای *class*ها در نظر بگیریم.

ابتدا یک **object** تعریف می‌کنید (نه class و نه `function` آن‌طور که بسیاری از JSکارها القا می‌کنند) به نام `Task` که روی آن رفتار عینی وجود دارد، از جمله متدهای کمکی که وظایف مختلف می‌توانند استفاده کنند (یعنی به آن *delegate* کنند!). سپس برای هر وظیفه («XYZ»، «ABC») یک **object** تعریف می‌کنید تا داده/رفتار خاص آن وظیفه را نگه دارد. object(های) خاص وظیفه را به object کمکی `Task` **link** می‌کنید تا در صورت نیاز بتوانند به آن delegate کنند.

در اصل، انجام وظیفهٔ «XYZ» را به‌عنوان نیاز به رفتار دو object هم‌سطح (sibling/peer) یعنی `XYZ` و `Task` در نظر می‌گیرید. اما به‌جای ترکیب آن‌ها از طریق کپی class، می‌توانیم آن‌ها را در objectهای جدا نگه داریم و به objectِ `XYZ` اجازه دهیم در صورت نیاز به `Task` **delegate** کند.

کد سادهٔ زیر نحوهٔ انجام این کار را پیشنهاد می‌کند:

```js
var Task = {
	setID: function(ID) { this.id = ID; },
	outputID: function() { console.log( this.id ); }
};

// make `XYZ` delegate to `Task`
var XYZ = Object.create( Task );

XYZ.prepareTask = function(ID,Label) {
	this.setID( ID );
	this.label = Label;
};

XYZ.outputTaskDetails = function() {
	this.outputID();
	console.log( this.label );
};

// ABC = Object.create( Task );
// ABC ... = ...
```

در این کد، `Task` و `XYZ` class (یا function) نیستند، **صرفاً object** هستند. `XYZ` با `Object.create(..)` طوری تنظیم شده که به objectِ `Task` **[[Prototype]] delegate** کند (فصل ۵ را ببینید).

در مقایسه با class-orientation (که OO — object-oriented — هم گفته می‌شود)، این سبک کد را **«OLOO»** (objects-linked-to-other-objects) می‌نامم. آنچه *واقعاً* برایمان مهم است این است که objectِ `XYZ` به objectِ `Task` delegate می‌کند (و objectِ `ABC` هم همین‌طور).

در JavaScript، مکانیزم `[[Prototype]]` **object**ها را به **object**های دیگر link می‌کند. هیچ مکانیزم انتزاعی مثل «class» وجود ندارد، هرچقدر هم خودتان را متقاعد کنید. مثل پارو زدن قایق در خلاف جهت جریان است: *می‌توانید* انجامش دهید، اما *دارید* بر خلاف جریان طبیعی حرکت می‌کنید، پس واضح است که **رسیدن به مقصد سخت‌تر خواهد بود.**

چند تفاوت دیگر در **کد سبک OLOO**:

1. هر دو عضو دادهٔ `id` و `label` از مثال class قبلی، اکنون propertyهای داده به‌طور مستقیم روی `XYZ` هستند (هیچ‌کدام روی `Task` نیست). به‌طور کلی، با حضور delegationِ `[[Prototype]]`، **می‌خواهید state روی delegatorها** (`XYZ`، `ABC`) باشد، نه روی delegate (`Task`).
2. در الگوی طراحی class، عمداً هر دو را در parent (`Task`) و child (`XYZ`) با نام `outputTask` نام‌گذاری کردیم تا از overriding (polymorphism) بهره ببریم. در behavior delegation برعکس عمل می‌کنیم: **در حد امکان از نام‌گذاری یکسان** در سطوح مختلف زنجیرهٔ `[[Prototype]]` پرهیز می‌کنیم (که shadowing نامیده می‌شود — فصل ۵ را ببینید)، چون برخورد آن نام‌ها سینتکس ناخوشایند/شکننده برای رفع ابهام ارجاعات ایجاد می‌کند (فصل ۴ را ببینید) و می‌خواهیم در حد امکان از آن دوری کنیم.

   این الگوی طراحی به نام‌های متد کلی کمتر که مستعد overriding هستند و در عوض به نام‌های توصیفی‌تر و *خاص* نوع رفتاری که هر object انجام می‌دهد نیاز دارد. **این در واقع می‌تواند کد قابل‌فهم‌تر/قابل‌نگهداری‌تر ایجاد کند**، چون نام متدها (نه فقط در محل تعریف بلکه در سراسر کد دیگر) واضح‌تر (self documenting) هستند.
3. `this.setID(ID);` داخل متدی روی objectِ `XYZ` ابتدا روی `XYZ` به دنبال `setID(..)` می‌گردد، اما چون متدی با آن نام روی `XYZ` پیدا نمی‌کند، *delegation*ِ `[[Prototype]]` یعنی می‌تواند link را تا `Task` دنبال کند و `setID(..)` را جستجو کند که البته پیدا می‌کند. افزون بر این، به‌خاطر قواعد implicit call-site `this` binding (فصل ۲ را ببینید)، وقتی `setID(..)` اجرا می‌شود، حتی با وجود اینکه متد روی `Task` پیدا شد، bindingِ `this` برای آن فراخوانی تابع دقیقاً `XYZ` است، همان‌طور که انتظار و میل داریم. همان را با `this.outputID()` بعدتر در لیست کد می‌بینیم.

   به‌عبارت دیگر، متدهای کمکی کلی که روی `Task` هستند هنگام تعامل با `XYZ` در دسترس ما هستند، چون `XYZ` می‌تواند به `Task` delegate کند.

**Behavior Delegation** یعنی: اجازه دادن به objectی (مثل `XYZ`) که در صورت پیدا نشدن property یا متد روی آن object (`XYZ`)، یک delegation (به `Task`) برای ارجاعات property یا method فراهم کند.

این الگوی طراحی *به‌غایت قدرتمند* است و با ایدهٔ parent و child class، inheritance، polymorphism و غیره بسیار متمایز است. به‌جای سازمان‌دهی objectها در ذهن به‌صورت عمودی با جریان از Parent به Child، objectها را در کنار هم، به‌عنوان هم‌سطح، با هر جهت linkهای delegation بین objectها که لازم است تصور کنید.

**یادداشت:** Delegation درست‌تر آن است که به‌عنوان جزئی از پیاده‌سازی داخلی استفاده شود تا اینکه مستقیماً در طراحی API در معرض دید قرار گیرد. در مثال بالا، لزوماً در طراحی API قصد نداریم توسعه‌دهندگان `XYZ.setID()` را فراخوانی کنند (هرچند البته می‌توانیم!). delegation را تا حدی به‌عنوان جزئی داخلی از API *پنهان* می‌کنیم؛ جایی که `XYZ.prepareTask(..)` به `Task.setID(..)` delegate می‌کند. برای جزئیات بیشتر بحث «Links As Fallbacks?» در فصل ۵ را ببینید.

#### Mutual Delegation (Disallowed)

نمی‌توانید *چرخه‌ای* ایجاد کنید که دو یا چند object به‌صورت متقابل (دوطرفه) به یکدیگر delegate شده باشند. اگر `B` را به `A` link کنید و بعد بخواهید `A` را به `B` link کنید، خطا خواهید گرفت.

این که این کار ممنوع است تأسف‌بار است (خیلی غافل‌گیرکننده نیست، اما کمی آزاردهنده). اگر به property/methodی ارجاع می‌دادید که در هیچ‌کدام وجود نداشت، یک بازگشت بی‌نهایت روی حلقهٔ `[[Prototype]]` داشتید. اما اگر همهٔ ارجاعات دقیقاً موجود بودند، آنگاه `B` می‌توانست به `A` delegate کند و بالعکس، و *می‌توانست* کار کند. یعنی می‌توانستید از هر دو object برای delegate کردن به دیگری برای وظایف مختلف استفاده کنید. چند use-case خاص هست که این ممکن است مفید باشد.

اما به‌این دلیل ممنوع است که پیاده‌سازان موتور مشاهده کرده‌اند که بررسی (و رد!) ارجاع دایره‌ای بی‌نهایت یک‌بار در زمان set از نظر کارایی بهتر است تا اینکه در هر بار lookup کردن property روی یک object هزینهٔ آن بررسی را پرداخت کنید.

#### Debugged

جزئی ظریف را به‌طور خلاصه پوشش می‌دهیم که می‌تواند برای توسعه‌دهندگان گیج‌کننده باشد. به‌طور کلی، مشخصات JS چگونگی نمایش مقادیر/ساختارهای خاص به توسعه‌دهنده توسط ابزارهای توسعهٔ مرورگر را کنترل نمی‌کند؛ پس هر مرورگر/موتور آزاد است چنین چیزهایی را آن‌طور که مناسب می‌بیند تفسیر کند. بنابراین مرورگرها/ابزارها *همیشه توافق ندارند*. به‌طور مشخص، رفتاری که اکنون بررسی می‌کنیم در حال حاضر فقط در Chrome Developer Tools مشاهده می‌شود.

این کد JS سبک سنتی «class constructor» را در نظر بگیرید، آن‌طور که در *console* ابزار توسعهٔ Chrome نمایش داده می‌شود:

```js
function Foo() {}

var a1 = new Foo();

a1; // Foo {}
```

به خط آخر آن قطعه نگاه کنیم: خروجی ارزیابی عبارت `a1` که `Foo {}` را چاپ می‌کند. اگر همین کد را در Firefox امتحان کنید، احتمالاً `Object {}` می‌بینید. چرا این تفاوت؟ این خروجی‌ها چه معنایی دارند؟

Chrome در اصل می‌گوید «{} یک object خالی است که توسط تابعی با نام 'Foo' ساخته شده». Firefox می‌گوید «{} یک object خالی با ساخت کلی از Object است». تفاوت ظریف این است که Chrome به‌صورت *internal property* نام تابع واقعی که construction را انجام داده را فعالانه ردیابی می‌کند، در حالی که سایر مرورگرها آن اطلاعات اضافی را ردیابی نمی‌کنند.

وسوسه‌انگیز است که بخواهیم این را با مکانیزم‌های JavaScript توضیح دهیم:

```js
function Foo() {}

var a1 = new Foo();

a1.constructor; // Foo(){}
a1.constructor.name; // "Foo"
```

پس آیا Chrome با بررسی سادهٔ `.constructor.name` object خروجی «Foo» را می‌دهد؟ به‌طور گیج‌کننده، پاسخ هم «بله» است هم «خیر».

این کد را در نظر بگیرید:

```js
function Foo() {}

var a1 = new Foo();

Foo.prototype.constructor = function Gotcha(){};

a1.constructor; // Gotcha(){}
a1.constructor.name; // "Gotcha"

a1; // Foo {}
```

حتی با تغییر `a1.constructor.name` به چیز دیگری به‌درستی («Gotcha»)، consoleِ Chrome هنوز از نام «Foo» استفاده می‌کند.

پس به‌نظر می‌رسد پاسخ پرسش قبلی (آیا از `.constructor.name` استفاده می‌کند؟) **خیر** است؛ باید آن را جای دیگری، به‌صورت داخلی، ردیابی کند.

اما صبر کنید! ببینیم این رفتار با کد سبک OLOO چطور کار می‌کند:

```js
var Foo = {};

var a1 = Object.create( Foo );

a1; // Object {}

Object.defineProperty( Foo, "constructor", {
	enumerable: false,
	value: function Gotcha(){}
});

a1; // Gotcha {}
```

آها! **Gotcha!** اینجا consoleِ Chrome **در واقع** `.constructor.name` را پیدا کرد و استفاده کرد. در واقع، هنگام نوشتن این کتاب، این رفتار دقیق به‌عنوان باگ در Chrome شناسایی شد و تا وقتی این را می‌خوانید ممکن است اصلاح شده باشد. پس شاید به‌جای آن خروجی اصلاح‌شدهٔ `a1; // Object {}` را دیده باشید.

گذشته از آن باگ، ردیابی داخلی (ظاهراً فقط برای هدف خروجی debug) «نام constructor» که Chrome انجام می‌دهد (در قطعات قبلی نشان داده شد) یک گسترش عمدی فقط-Chrome برای رفتار فراتر از آنچه مشخصات JS می‌طلبد است.

اگر از «constructor» برای ساخت objectهای خود استفاده نکنید، همان‌طور که در این فصل در کد سبک OLOO توصیه کرده‌ایم، objectهایی خواهید داشت که Chrome برای آن‌ها نام داخلی «constructor» را ردیابی *نمی‌کند* و چنین objectهایی درست فقط به‌صورت «Object {}» خروجی داده می‌شوند؛ یعنی «object تولیدشده از constructionِ Object()».

**فکر نکنید** این نشان‌دهندهٔ نقطهٔ ضعف کدنویسی سبک OLOO است. وقتی با OLOO و behavior delegation به‌عنوان الگوی طراحی کد می‌نویسید، *چه کسی* «ساخت» (یعنی *کدام function* با `new` فراخوانی شد؟) objectی را انجام داده جزئی نامربوط است. ردیابی داخلی خاص Chrome برای «نام constructor» واقعاً فقط وقتی مفید است که کاملاً کدنویسی «سبک class» را بپذیرید، اما در پذیرش delegationِ OLOO بی‌اثر است.

### Mental Models Compared

حالا که تفاوت الگوهای طراحی «class» و «delegation» را حداقل به‌صورت نظری می‌بینید، ببینیم این الگوها چه تأثیری بر mental modelهایی که برای استدلال دربارهٔ کدمان استفاده می‌کنیم دارند.

کد نظری بیشتری («Foo»، «Bar») را بررسی می‌کنیم و هر دو شیوه (OO در برابر OLOO) پیاده‌سازی را مقایسه می‌کنیم. قطعهٔ اول از سبک کلاسیک OO («prototypal») استفاده می‌کند:

```js
function Foo(who) {
	this.me = who;
}
Foo.prototype.identify = function() {
	return "I am " + this.me;
};

function Bar(who) {
	Foo.call( this, who );
}
Bar.prototype = Object.create( Foo.prototype );

Bar.prototype.speak = function() {
	alert( "Hello, " + this.identify() + "." );
};

var b1 = new Bar( "b1" );
var b2 = new Bar( "b2" );

b1.speak();
b2.speak();
```

Parent classِ `Foo`، که child classِ `Bar` از آن ارث برده، و سپس دو بار به‌صورت `b1` و `b2` instantiate شده. آنچه داریم این است: `b1` به `Bar.prototype` delegate می‌کند که به `Foo.prototype` delegate می‌کند. در این مرحله باید نسبتاً آشنا به‌نظر برسد. چیز خیلی انقلابی در کار نیست.

حالا **دقیقاً همان عملکرد** را با کد سبک *OLOO* پیاده‌سازی می‌کنیم:

```js
var Foo = {
	init: function(who) {
		this.me = who;
	},
	identify: function() {
		return "I am " + this.me;
	}
};

var Bar = Object.create( Foo );

Bar.speak = function() {
	alert( "Hello, " + this.identify() + "." );
};

var b1 = Object.create( Bar );
b1.init( "b1" );
var b2 = Object.create( Bar );
b2.init( "b2" );

b1.speak();
b2.speak();
```

دقیقاً همان مزیت delegationِ `[[Prototype]]` را از `b1` به `Bar` به `Foo` می‌گیریم که در قطعهٔ قبلی بین `b1`، `Bar.prototype` و `Foo.prototype` داشتیم. **همچنان همان ۳ object را به‌هم link شده داریم**.

اما مهم این است که *همهٔ چیزهای دیگر* را به‌شدت ساده کرده‌ایم، چون اکنون فقط **object**هایی را به‌هم link شده تنظیم کرده‌ایم، بدون نیاز به تمام آشغال و سردرگمی چیزهایی که شبیه (اما رفتار نمی‌کنند!) class هستند، با constructorها و prototypeها و فراخوانی‌های `new`.

از خود بپرسید: اگر با کد سبک OLOO همان عملکرد کد سبک «class» را داشته باشم، اما OLOO ساده‌تر است و چیزهای کمتری برای فکر کردن دارد، **آیا OLOO بهتر نیست؟**

mental modelهای این دو قطعه را بررسی کنیم.

در واقع، کمی ناعادلانه/گمراه‌کننده است، چون جزئیات زیادی نشان می‌دهد که *از نظر فنی* همیشه لازم نیست بدانید (هرچند *باید* درکش کنید!). یک برداشت این است که سری رابطه‌ای نسبتاً پیچیده است. برداشت دیگر: اگر وقت بگذارید و آن فلش‌های رابطه را دنبال کنید، **ثبات داخلی شگفت‌انگیزی** در مکانیزم‌های JS وجود دارد.

مثلاً، دسترسی تابع JS به `call(..)`، `apply(..)` و `bind(..)` (فصل ۲ را ببینید) به‌این‌دلیل است که خود functionها object هستند و function-objectها هم یک linkِ `[[Prototype]]` به objectِ `Function.prototype` دارند که آن متدهای پیش‌فرضی را تعریف می‌کند که هر function-object می‌تواند به آن‌ها delegate کند. JS می‌تواند آن کارها را انجام دهد، *و شما هم می‌توانید!*
