# مکانیک کلاس

در بسیاری از زبان‌های مبتنی بر class، «کتابخانهٔ استاندارد» یک ساختار دادهٔ «stack» (push، pop و غیره) به‌عنوان class یعنی `Stack` فراهم می‌کند. این class مجموعه‌ای داخلی از متغیرها برای ذخیرهٔ داده و مجموعه‌ای از رفتارهای قابل دسترسی عمومی («method»ها) فراهم‌شده توسط class دارد که به کد شما توانایی تعامل با دادهٔ (پنهان) (اضافه و حذف داده و غیره) می‌دهد.

اما در چنین زبان‌هایی، واقعاً مستقیماً روی `Stack` عمل نمی‌کنید (مگر ارجاع عضو **Static** class، که خارج از محدودهٔ بحث ماست). class یعنی `Stack` فقط توضیح انتزاعی از آنچه *هر* «stack» باید انجام دهد است، اما خودش *یک* «stack» نیست. باید class یعنی `Stack` را **instantiate** کنید قبل از داشتن ساختار دادهٔ *چیز* مشخص برای عمل کردن علیه آن.

### ساختن

استعارهٔ سنتی برای تفکر مبتنی بر «class» و «instance» از ساخت‌وساز ساختمان می‌آید.

معمار همهٔ ویژگی‌های ساختمان را برنامه‌ریزی می‌کند: چقدر عریض، چقدر بلند، چند پنجره و در چه محل‌هایی، حتی چه نوع مصالحی برای دیوارها و سقف. در این مرحله لزوماً *کجا* ساختمان ساخته می‌شود یا *چند* کپی از آن ساختمان ساخته می‌شود برایش مهم نیست.

همچنین به محتوای ساختمان — مبلمان، کاغذ دیواری، پنکهٔ سقفی و غیره — خیلی اهمیت نمی‌دهد، فقط چه نوع ساختاری آن‌ها را در بر می‌گیرد.

نقشه‌های معماری که تولید می‌کند فقط *طرح* یک ساختمان‌اند. در واقع ساختمانی که بتوانیم واردش شویم و بنشینیم تشکیل نمی‌دهند. برای آن کار به سازنده نیاز داریم. سازنده آن طرح‌ها را می‌گیرد و دقیقاً دنبال می‌کند، همان‌طور که ساختمان را *می‌سازد*. به معنای بسیار واقعی، *کپی* ویژگی‌های مورد نظر از طرح‌ها به ساختمان فیزیکی است.

وقتی تمام شد، ساختمان instantiation فیزیکی طرح‌های نقشه است، امیدواریم *کپی*ای اساساً کامل. و بعد سازنده می‌تواند به زمین خالی کنار برود و همه را تکرار کند و *کپی* دیگری بسازد.

رابطهٔ بین ساختمان و نقشه غیرمستقیم است. می‌توانید نقشه را بررسی کنید تا بفهمید ساختمان چطور ساختار یافته، برای هر بخشی که بازرسی مستقیم خود ساختمان کافی نبود. اما اگر بخواهید در را باز کنید، باید به خود ساختمان بروید — نقشه فقط خطوطی روی صفحه دارد که *نماینده* محل در هستند.

یک class یک نقشه است. برای *داشتن* واقعی objectی که بتوانیم با آن تعامل کنیم، باید چیزی از class بسازیم (به‌اصطلاح «instantiate» کنیم). نتیجهٔ نهایی چنین «ساخت»ی یک object است، معمولاً «instance» نامیده می‌شود، که می‌توانیم مستقیماً متدها را روی آن فراخوانی کنیم و در صورت نیاز به هر property دادهٔ عمومی دسترسی پیدا کنیم.

**این object *کپی*ی** همهٔ ویژگی‌های توصیف‌شده توسط class است.

احتمالاً انتظار ندارید وارد ساختمانی شوید و کپی نقشه‌های استفاده‌شده برای برنامه‌ریزی ساختمان را قاب‌شده و روی دیوار آویزان پیدا کنید، هرچند نقشه‌ها احتمالاً در پروندهٔ ادارهٔ سوابق عمومی هستند. به‌طور مشابه، عموماً از instance یک object برای دسترسی و دستکاری مستقیم classش استفاده نمی‌کنید، اما معمولاً حداقل ممکن است تعیین کنید instance یک object *از کدام class* می‌آید.

مفیدتر است رابطهٔ مستقیم class با instance یک object را در نظر بگیرید، نه هر رابطهٔ غیرمستقیم بین instance یک object و classی که از آن آمده. **یک class با عملیات کپی به شکل object instantiate می‌شود.**

### Constructor

Instanceهای classها توسط متد خاصی از class ساخته می‌شوند، معمولاً با همان نام class، که *constructor* نامیده می‌شود. کار صریح این متد مقداردهی اولیهٔ هر اطلاعات (state) مورد نیاز instance است.

مثلاً این شبه‌کد آزاد (نحو ابداعی) را برای classها در نظر بگیرید:

```js
class CoolGuy {
	specialTrick = nothing

	CoolGuy( trick ) {
		specialTrick = trick
	}

	showOff() {
		output( "Here's my trick: ", specialTrick )
	}
}
```

برای *ساختن* یک instance یعنی `CoolGuy`، constructor کلاس را فراخوانی می‌کردیم:

```js
Joe = new CoolGuy( "jumping rope" )

Joe.showOff() // Here's my trick: jumping rope
```

توجه کنید class یعنی `CoolGuy` constructor یعنی `CoolGuy()` دارد که در واقع وقتی می‌گوییم `new CoolGuy(..)` فراخوانی می‌شود. از constructor objectی برمی‌گیریم (instance از classمان) و می‌توانیم متد `showOff()` را فراخوانی کنیم که ترفند خاص آن `CoolGuy` را چاپ می‌کند.

*واضح است، طناب‌بازی جو را آدم خیلی باحالی می‌کند.*

Constructor یک class *به* class تعلق دارد، تقریباً همیشه با همان نام class. همچنین، constructorها تقریباً همیشه باید با `new` فراخوانی شوند تا به engine زبان بفهمانند می‌خواهید instance *جدید* class بسازید.
