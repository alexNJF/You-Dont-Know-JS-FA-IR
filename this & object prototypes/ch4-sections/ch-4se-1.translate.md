# نظریهٔ کلاس

«Class/Inheritance» شکلی خاص از سازماندهی و معماری کد را توصیف می‌کند — روشی برای مدل‌سازی حوزه‌های مسئلهٔ واقعی در نرم‌افزارمان.

برنامه‌نویسی OO یا مبتنی بر class تأکید می‌کند که داده ذاتاً رفتار مرتبط دارد (البته بسته به نوع و ماهیت داده متفاوت!) که روی آن عمل می‌کند، پس طراحی درست بسته‌بندی (به‌اصطلاح encapsulate) داده و رفتار با هم است. این گاهی در علوم رایانهٔ رسمی «ساختارهای داده» نامیده می‌شود.

مثلاً، رشته‌ای از کاراکترها که کلمه یا عبارت را نشان می‌دهد معمولاً «string» نامیده می‌شود. کاراکترها داده‌اند. اما تقریباً هرگز فقط به داده اهمیت نمی‌دهید، معمولاً می‌خواهید *کارهایی* با داده انجام دهید، پس رفتارهایی که می‌توانند *روی* آن داده اعمال شوند (محاسبهٔ طولش، الحاق داده، جستجو و غیره) همگی به‌عنوان متدهای class یعنی `String` طراحی شده‌اند.

هر رشتهٔ داده‌شده فقط یک instance از این class است، یعنی بسته‌بندی مرتبی از هم دادهٔ کاراکتر و هم قابلیتی که می‌توانیم روی آن انجام دهیم.

Classها همچنین روشی برای *دسته‌بندی* یک ساختار دادهٔ خاص دلالت می‌کنند. روشش این است که هر ساختار داده‌شده را به‌عنوان گونهٔ خاصی از تعریف پایهٔ کلی‌تر در نظر بگیریم.

بیایید این فرایند دسته‌بندی را با نگاه به مثال رایجی بررسی کنیم. یک *ماشین* می‌تواند به‌عنوان پیاده‌سازی خاصی از «class» کلی‌تر چیز به‌نام *وسیلهٔ نقلیه* توصیف شود.

این رابطه را در نرم‌افزار با classها با تعریف class یعنی `Vehicle` و class یعنی `Car` مدل می‌کنیم.

تعریف `Vehicle` ممکن است چیزهایی مثل پیشرانه (موتورها و غیره)، توانایی حمل افراد و غیره را شامل شود که همگی رفتارها هستند. آنچه در `Vehicle` تعریف می‌کنیم همهٔ چیزهایی است که برای همه (یا بیشتر) انواع وسایل نقلیه («هواپیماها، قطارها و خودروها») مشترک است.

در نرم‌افزارمان معقول نیست ماهیت پایهٔ «توانایی حمل افراد» را بارها برای هر نوع وسیلهٔ متفاوت بازتعریف کنیم. به‌جای آن، آن قابلیت را یک بار در `Vehicle` تعریف می‌کنیم، و بعد وقتی `Car` را تعریف می‌کنیم، به‌سادگی نشان می‌دهیم که از تعریف پایهٔ `Vehicle` «ارث می‌برد» (یا «گسترش می‌دهد»). گفته می‌شود تعریف `Car` تعریف کلی `Vehicle` را تخصصی می‌کند.

در حالی که `Vehicle` و `Car` با هم رفتار را از طریق متدها تعریف می‌کنند، داده در یک instance چیزهایی مثل VIN یکتای یک ماشین خاص و غیره خواهد بود.

**و بدین‌سان classها، inheritance و instantiation پدیدار می‌شوند.**

مفهوم کلیدی دیگر با classها «polymorphism» است، که ایدهٔ اینکه رفتار کلی از class والد می‌تواند در class فرزند override شود تا جزئیات بیشتری به آن بدهد را توصیف می‌کند. در واقع، relative polymorphism به ما اجازه می‌دهد از رفتار overrideشده به رفتار پایه ارجاع دهیم.

نظریهٔ class به‌شدت پیشنهاد می‌کند که class والد و class فرزند برای رفتار خاص همان نام متد را دارند، تا فرزند والد را (به‌صورت تفاضلی) override کند. همان‌طور که بعداً خواهیم دید، انجام این کار در کد جاوااسکریپت شما یعنی opting into ناامیدی و شکنندگی کد.

### الگوی طراحی «Class»

شاید هرگز به classها به‌عنوان «الگوی طراحی» فکر نکرده باشید، چون رایج‌تر است بحث «الگوهای طراحی OO» محبوب مثل «Iterator»، «Observer»، «Factory»، «Singleton» و غیره دیده شود. با این ارائه، تقریباً فرض است که classهای OO مکانیک سطح پایین‌تری هستند که با آن همهٔ (سطح بالاتر) الگوهای طراحی را پیاده می‌کنیم، گویی OO بنیاد داده‌شده برای *همهٔ* کد (درست) است.

بسته به سطح تحصیلات رسمی شما در برنامه‌نویسی، ممکن است «برنامه‌نویسی رویه‌ای» را به‌عنوان روشی برای توصیف کدی که فقط از رویه‌ها (به‌اصطلاح توابع) فراخوانی‌کنندهٔ توابع دیگر تشکیل شده، بدون هیچ انتزاع بالاتر، شنیده باشید. ممکن است به شما آموخته شده باشد که classها روش *درست* تبدیل «کد اسپاگتی» به سبک رویه‌ای به کد خوش‌شکل و خوش‌سازمان بودند.

البته، اگر با «برنامه‌نویسی تابعی» (Monadها و غیره) تجربه دارید، خوب می‌دانید classها فقط یکی از چند الگوی طراحی رایج‌اند. اما برای بقیه، شاید اولین بار باشد از خود می‌پرسید آیا classها واقعاً بنیاد اساسی کد هستند، یا انتزاع اختیاری روی کد.

بعضی زبان‌ها (مثل جاوا) انتخاب به شما نمی‌دهند، پس اصلاً *اختیاری* نیست — همه‌چیز یک class است. زبان‌های دیگر مثل C/C++ یا PHP هم نحو رویه‌ای و هم مبتنی بر class به شما می‌دهند، و بیشتر به انتخاب توسعه‌دهنده گذاشته شده کدام سبک یا ترکیب سبک‌ها مناسب است.

### «Class»های جاوااسکریپت

جاوااسکریپت در این مورد کجا قرار می‌گیرد؟ JS مدتی است *چند* عنصر نحوی شبیه class (مثل `new` و `instanceof`) دارد، و اخیراً در ES6 چند افزودنی مثل واژه‌کلیدی `class` (ضمیمهٔ A را ببینید).

اما آیا یعنی جاوااسکریپت واقعاً *class* دارد؟ ساده و روشن: **نه.**

چون classها یک الگوی طراحی‌اند، *می‌توانید* با تلاش قابل توجه (همان‌طور که در بقیهٔ این فصل خواهیم دید) تقریب‌هایی برای بخش زیادی از قابلیت class سنتی پیاده کنید. JS سعی می‌کند *میل* به‌شدت فراگیر طراحی با class را با فراهم کردن نحو به‌ظاهر شبیه class ارضا کند.

در حالی که ممکن است نحوی داشته باشیم که شبیه class به نظر برسد، گویی مکانیزم‌های جاوااسکریپت علیه استفادهٔ شما از *الگوی طراحی class* می‌جنگند، چون پشت پرده مکانیزم‌هایی که روی آن‌ها می‌سازید کاملاً متفاوت عمل می‌کنند. Syntactic sugar و کتابخانه‌های (به‌شدت پرکاربرد) «Class» JS راه درازی برای پنهان کردن این واقعیت از شما می‌پیمایند، اما دیر یا زود با این واقعیت روبرو می‌شوید که *class*هایی که در زبان‌های دیگر دارید مثل «class»هایی که در JS جعل می‌کنید نیستند.

نتیجهٔ نهایی این است که classها الگویی اختیاری در طراحی نرم‌افزار هستند، و در جاوااسکریپت انتخاب دارید از آن‌ها استفاده کنید یا نه. چون بسیاری از توسعه‌دهندگان تمایل قوی به طراحی نرم‌افزار مبتنی بر class دارند، بقیهٔ این فصل را صرف بررسی آنچه برای حفظ توهم class با آنچه JS فراهم می‌کند لازم است، و نقاط دردمان می‌کنیم.
