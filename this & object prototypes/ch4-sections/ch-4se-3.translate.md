# وراثت کلاس

در زبان‌های مبتنی بر class، نه فقط می‌توانید classی تعریف کنید که خودش قابل instantiate باشد، بلکه می‌توانید class دیگری تعریف کنید که از class اول **ارث می‌برد**.

اغلب گفته می‌شود class دوم «child class» است در حالی که اولی «parent class» است. این اصطلاحات واضحاً از استعارهٔ والد و فرزند می‌آیند، هرچند استعاره‌ها اینجا کمی کش می‌خورند، همان‌طور که به‌زودی خواهید دید.

وقتی والد فرزند زیستی دارد، ویژگی‌های ژنتیکی والد در فرزند کپی می‌شوند. واضح است در بیشتر سیستم‌های تولیدمثل زیستی دو والد هستند که به‌طور برابر ژن به مخلوط می‌دهند. اما برای هدف استعاره، فرض می‌کنیم فقط یک والد داریم.

وقتی فرزند وجود دارد، از والد جدا است. فرزند تحت تأثیر شدید inheritance از والدش بود، اما یکتا و متمایز است. اگر فرزند موی قرمز داشته باشد، یعنی موی والد *بود* یا خودکار *قرمز نمی‌شود*.

به‌طور مشابه، وقتی child class تعریف شد، از parent class جدا و متمایز است. child class کپی اولیهٔ رفتار از parent را دارد، اما می‌تواند هر رفتار به‌ارث‌برده را override کند و حتی رفتار جدید تعریف کند.

مهم است به یاد داشته باشیم دربارهٔ **class**های والد و فرزند حرف می‌زنیم که چیزهای فیزیکی نیستند. اینجاست که استعارهٔ والد و فرزند کمی گیج‌کننده می‌شود، چون در واقع باید بگوییم parent class مثل DNA والد و child class مثل DNA فرزند است. باید از هر مجموعه DNA شخصی بسازیم (به‌اصطلاح «instantiate») تا واقعاً شخص فیزیکی برای گفتگو داشته باشیم.

بیایید والد و فرزند زیستی را کنار بگذاریم و inheritance را از دریچهٔ کمی متفاوت ببینیم: انواع مختلف وسایل نقلیه. این یکی از استعاره‌های کانونی‌ترین (و اغلب ناله‌برانگیز) برای فهم inheritance است.

بیایید بحث `Vehicle` و `Car` از اوایل این فصل را بازبینیم. این شبه‌کد آزاد (نحو ابداعی) را برای classهای به‌ارث‌برده در نظر بگیرید:

```js
class Vehicle {
	engines = 1

	ignition() {
		output( "Turning on my engine." )
	}

	drive() {
		ignition()
		output( "Steering and moving forward!" )
	}
}

class Car inherits Vehicle {
	wheels = 4

	drive() {
		inherited:drive()
		output( "Rolling on all ", wheels, " wheels!" )
	}
}

class SpeedBoat inherits Vehicle {
	engines = 2

	ignition() {
		output( "Turning on my ", engines, " engines." )
	}

	pilot() {
		inherited:drive()
		output( "Speeding through the water with ease!" )
	}
}
```

**یادداشت:** برای وضوح و اختصار، constructorهای این classها حذف شده‌اند.

class یعنی `Vehicle` را طوری تعریف می‌کنیم که یک موتور، روش روشن کردن احتراق و روش رانندگی فرض کند. اما هرگز فقط یک «وسیلهٔ نقلیه» کلی تولید نمی‌کنید، پس در این مرحله واقعاً فقط یک مفهوم انتزاعی است.

پس دو نوع خاص وسیلهٔ نقلیه را تعریف می‌کنیم: `Car` و `SpeedBoat`. هر کدام ویژگی‌های کلی `Vehicle` را به ارث می‌برند، اما بعد ویژگی‌ها را مناسب هر نوع تخصصی می‌کنند. ماشین به ۴ چرخ و قایق تندرو به ۲ موتور نیاز دارد، یعنی نیاز به توجه اضافه برای روشن کردن احتراق هر دو موتور دارد.

### Polymorphism

`Car` متد `drive()` خودش را تعریف می‌کند که متد هم‌نام به‌ارث‌برده از `Vehicle` را override می‌کند. اما بعد، متد `drive()` یعنی `Car` فراخوانی `inherited:drive()` می‌کند که نشان می‌دهد `Car` می‌تواند به `drive()` اصلی پیش از override که به ارث برده ارجاع دهد. متد `pilot()` یعنی `SpeedBoat` هم به کپی به‌ارث‌بردهٔ `drive()` ارجاع می‌دهد.

این تکنیک «polymorphism» یا «virtual polymorphism» نامیده می‌شود. مشخص‌تر برای نقطهٔ فعلی ما، آن را «relative polymorphism» می‌نامیم.

Polymorphism موضوعی بسیار گسترده‌تر از آن است که اینجا تمام کنیم، اما معناشناسی «relative» فعلی ما به یک جنبهٔ خاص اشاره می‌کند: ایدهٔ اینکه هر متدی می‌تواند به متد دیگری (با همان نام یا نام متفاوت) در سطح بالاتر سلسله‌مراتب inheritance ارجاع دهد. «relative» می‌گوییم چون مطلقاً تعریف نمی‌کنیم می‌خواهیم به کدام سطح inheritance (به‌اصطلاح class) دسترسی داشته باشیم، بلکه با اساساً گفتن «یک سطح بالا نگاه کن» نسبتاً ارجاع می‌دهیم.

در بسیاری زبان‌ها، واژه‌کلیدی `super` به‌جای `inherited:` این مثال استفاده می‌شود، که بر ایدهٔ اینکه «super class» والد/نیای class فعلی است تکیه می‌کند.

جنبهٔ دیگر polymorphism این است که نام یک متد می‌تواند چند تعریف در سطوح مختلف زنجیرهٔ inheritance داشته باشد، و این تعریف‌ها به‌طور خودکار هنگام حل کردن کدام متدها فراخوانی می‌شوند مناسب انتخاب می‌شوند.

دو وقوع آن رفتار را در مثال بالا می‌بینیم: `drive()` هم در `Vehicle` و هم در `Car` تعریف شده، و `ignition()` هم در `Vehicle` و هم در `SpeedBoat`.

**یادداشت:** چیز دیگر که زبان‌های سنتی مبتنی بر class از طریق `super` به شما می‌دهند راه مستقیم برای constructor یک child class برای ارجاع به constructor والدش است. این تا حد زیادی درست است چون با classهای واقعی، constructor به class تعلق دارد. با این حال در JS برعکس است — در واقع مناسب‌تر است فکر کنیم «class» به constructor تعلق دارد (ارجاع‌های نوع `Foo.prototype...`). چون در JS رابطهٔ بین فرزند و والد فقط بین دو object یعنی `.prototype` constructorهای مربوط وجود دارد، خود constructorها مستقیماً مرتبط نیستند و بنابراین راه ساده‌ای برای ارجاع نسبی یکی از دیگری وجود ندارد (ضمیمهٔ A را برای `class` ES6 که این را با `super` «حل» می‌کند ببینید).

دلالت جالب polymorphism را مشخصاً با `ignition()` می‌توان دید. داخل `pilot()` ارجاع relative-polymorphic به نسخهٔ (به‌ارث‌بردهٔ) `drive()` یعنی `Vehicle` شده. اما آن `drive()` فقط با نام (بدون ارجاع نسبی) به متد `ignition()` ارجاع می‌دهد.

کدام نسخهٔ `ignition()` را engine زبان استفاده می‌کند، آن از `Vehicle` یا آن از `SpeedBoat`? **نسخهٔ `SpeedBoat` یعنی `ignition()` را استفاده می‌کند.** اگر *خود* class یعنی `Vehicle` را instantiate می‌کردید و بعد `drive()` آن را فراخوانی می‌کردید، engine زبان به‌جای آن فقط تعریف متد `ignition()` یعنی `Vehicle` را استفاده می‌کرد.

به بیان دیگر، تعریف متد `ignition()` *polymorph* می‌شود (تغییر می‌کند) بسته به اینکه به instance کدام class (سطح inheritance) ارجاع می‌دهید.

شاید جزئیات آکادمیک بیش از حد عمیق به نظر برسد. اما فهم این جزئیات برای مقایسهٔ درست رفتارهای مشابه (اما متمایز) در مکانیزم `[[Prototype]]` جاوااسکریپت لازم است.

وقتی classها به ارث برده می‌شوند، راهی **برای خود classها** (نه instanceهای object ساخته‌شده از آن‌ها!) برای ارجاع *نسبی* به class به‌ارث‌برده وجود دارد، و این ارجاع نسبی معمولاً `super` نامیده می‌شود.

نگذارید polymorphism شما را گیج کند که فکر کنید child class به parent class لینک است. به‌جای آن child class کپی آنچه از parent class نیاز دارد را می‌گیرد. **وراثت class دلالت بر کپی دارد.**

### Multiple Inheritance

بحث قبلی والد(ها) و فرزندان و DNA را به یاد دارید؟ گفتیم استعاره کمی عجیب بود چون از نظر زیستی بیشتر فرزندان از دو والد می‌آیند. اگر یک class بتواند از دو class دیگر ارث ببرد، بیشتر با استعارهٔ والد/فرزند جور می‌شد.

بعضی زبان‌های مبتنی بر class به شما اجازه می‌دهند بیش از یک class «والد» برای «ارث‌بردن» مشخص کنید. Multiple-inheritance یعنی تعریف هر parent class در child class کپی می‌شود.

در ظاهر، این به‌نظر افزودنی قدرتمند به class-orientation می‌رسد و توانایی ترکیب قابلیت بیشتر با هم را می‌دهد. با این حال قطعاً سؤال‌های پیچیده‌ای پیش می‌آید. اگر هر دو parent class متدی به نام `drive()` فراهم کنند، ارجاع `drive()` در فرزند به کدام نسخه resolve می‌شود؟ آیا همیشه باید دستی مشخص کنید منظورتان `drive()` کدام والد است و بنابراین بخشی از ظرافت inheritance polymorphic را از دست بدهید؟

گونهٔ دیگری هست، به‌اصطلاح «مسئلهٔ الماس»، که به سناریویی اشاره می‌کند که child class یعنی «D» از دو parent class («B» و «C») ارث می‌برد و هر کدام به نوبهٔ خود از parent مشترک «A» ارث می‌برند. اگر «A» متد `drive()` فراهم کند و هر دو «B» و «C» آن متد را override (polymorph) کنند، وقتی `D` به `drive()` ارجاع می‌دهد کدام نسخه را باید استفاده کند (`B:drive()` یا `C:drive()`)?
