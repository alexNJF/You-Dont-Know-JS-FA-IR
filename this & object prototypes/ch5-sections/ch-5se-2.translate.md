# «کلاس»

در این نقطه ممکن است بپرسید: «*چرا* یک object باید به object دیگر لینک شود؟» فایدهٔ واقعی چیست؟ سؤال بسیار مناسبی است، اما اول باید بفهمیم `[[Prototype]]` **چیست نیست** قبل از فهم و قدردانی کامل از آنچه *هست* و چطور مفید است.

همان‌طور که در فصل ۴ توضیح دادیم، در جاوااسکریپت الگو/نقشهٔ انتزاعی برای objectها به نام «class» مثل زبان‌های مبتنی بر class وجود ندارد. جاوااسکریپت **فقط** object دارد.

در واقع، جاوااسکریپت **تقریباً یکتا** در بین زبان‌هاست به‌عنوان شاید تنها زبانی با حق استفاده از برچسب «object oriented»، چون یکی از فهرست کوتاه زبان‌هایی است که object می‌تواند مستقیماً، بدون هیچ class، ساخته شود.

در جاوااسکریپت، classها نمی‌توانند (چون وجود ندارند!) آنچه object می‌تواند انجام دهد را توصیف کنند. object رفتار خود را مستقیماً تعریف می‌کند. **فقط *همان* object است.**

### توابع «Class»

نوع خاصی از رفتار در جاوااسکریپت هست که سال‌ها بی‌پرده برای *هک* چیزی که *شبیه* «class» به نظر می‌رسد سوءاستفاده شده. این رویکرد را به‌تفصیل بررسی می‌کنیم.

رفتار عجیب «نوعی class» به ویژگی غریب توابع وابسته است: همهٔ توابع به‌طور پیش‌فرض یک property عمومی و non-enumerable (فصل ۳ را ببینید) به نام `prototype` روی خود می‌گیرند که به objectی در غیر این صورت دلخواه اشاره می‌کند.

```js
function Foo() {
	// ...
}

Foo.prototype; // { }
```

این object اغلب «prototype یعنی Foo» نامیده می‌شود چون از طریق ارجاع property با نام بدشانسی یعنی `Foo.prototype` به آن دسترسی داریم. با این حال آن اصطلاح‌شناسی محکوم به سردرگمی ماست، همان‌طور که به‌زودی می‌بینیم. به‌جای آن آن را «object معروف به prototype یعنی Foo» می‌نامم. شوخی. چطور است: «object با برچسب دلخواه 'Foo dot prototype'»؟

هرچه بنامیم، این object دقیقاً چیست؟

مستقیم‌ترین توضیح این است که هر object ساخته‌شده از فراخوانی `new Foo()` (فصل ۲ را ببینید) در نهایت (تا حدی دلخواه) به این object «Foo dot prototype» با `[[Prototype]]` لینک می‌شود.

بیایید نشان دهیم:

```js
function Foo() {
	// ...
}

var a = new Foo();

Object.getPrototypeOf( a ) === Foo.prototype; // true
```

وقتی `a` با فراخوانی `new Foo()` ساخته می‌شود، یکی از کارها (فصل ۲ را برای هر *چهار* قدم ببینید) این است که `a` لینک داخلی `[[Prototype]]` به objectی که `Foo.prototype` به آن اشاره می‌کند می‌گیرد.

لحظه‌ای درنگ کنید و دلالت آن جمله را در نظر بگیرید.

در زبان‌های مبتنی بر class، **کپی**های متعدد (به‌اصطلاح «instance») از یک class می‌توان ساخته، مثل قالب‌زدن چیزی از قالب. همان‌طور که در فصل ۴ دیدیم، این چون فرایند instantiate کردن (یا ارث‌بردن از) یک class یعنی «طرح رفتار را از آن class به object فیزیکی کپی کن» اتفاق می‌افتد، و برای هر instance جدید دوباره انجام می‌شود.

اما در جاوااسکریپت چنین عملیات‌های کپی انجام نمی‌شوند. instanceهای متعدد یک class نمی‌سازید. می‌توانید objectهای متعددی بسازید که با `[[Prototype]]` به object مشترک *لینک* می‌شوند. اما به‌طور پیش‌فرض کپی اتفاق نمی‌افتد، و بنابراین این objectها کاملاً جدا و قطع‌شده از هم نمی‌شوند، بلکه ***لینک*** می‌شوند.

`new Foo()` به object جدیدی (آن را `a` نامیدیم) منجر می‌شود، و **همان** object جدید یعنی `a` درونی به object یعنی `Foo.prototype` با `[[Prototype]]` لینک است.

**در نهایت دو object داریم که به هم لینک‌اند.** همین. class را instantiate نکردیم. قطعاً هیچ کپی رفتار از «class» به object مشخص نکردیم. فقط دو object را به هم لینک کردیم.

در واقع، رازی که از بیشتر توسعه‌دهندگان JS پنهان می‌ماند این است که فراخوانی تابع `new Foo()` واقعاً تقریباً هیچ ارتباط *مستقیمی* با فرایند ساخت لینک نداشت. **نوعی اثر جانبی تصادفی بود.** `new Foo()` راه غیرمستقیم و دور برای رسیدن به آنچه می‌خواهیم است: **object جدید لینک‌شده به object دیگر**.

می‌توانیم آنچه می‌خواهیم به روش *مستقیم‌تر* بگیریم؟ **بله!** قهرمان `Object.create(..)` است. اما به‌زودی می‌رسیم.

#### چه چیزی در یک نام؟

در جاوااسکریپت از یک object («class») به دیگری («instance») *کپی* نمی‌گیریم. بین objectها *لینک* می‌سازیم. برای مکانیزم `[[Prototype]]`، از نظر بصری فلش‌ها از راست به چپ و از پایین به بالا حرکت می‌کنند.

این مکانیزم اغلب «prototypal inheritance» نامیده می‌شود (به‌زودی کد را به‌تفصیل بررسی می‌کنیم)، که معمولاً نسخهٔ زبان پویا از «classical inheritance» گفته می‌شود. تلاشی است برای سوار شدن بر فهم رایج از معنای «inheritance» در دنیای مبتنی بر class، اما *تغییر* (**یعنی پوشاندن**) معناشناسی فهمیده‌شده برای جا دادن در اسکریپت پویا.

واژهٔ «inheritance» معنای خیلی قوی دارد (فصل ۴ را ببینید)، با پیشینهٔ ذهنی زیاد. فقط اضافه کردن «prototypal» جلو برای تمایز رفتار *واقعاً تقریباً متضاد* در جاوااسکریپت نزدیک به دو دهه سردرگمی گلی به جا گذاشته.

دوست دارم بگویم چسباندن «prototypal» جلو «inheritance» برای معکوس کردن شدید معنای واقعی مثل نگه داشتن پرتقال در یک دست و سیب در دست دیگر و اصرار بر نامیدن سیب «پرتقال قرمز» است. هر برچسب گیج‌کننده‌ای جلو بگذارم *واقعیت* را که یکی سیب و دیگری پرتقال است عوض نمی‌کند.

رویکرد بهتر صریحاً سیب را سیب نامیدن است — استفاده از دقیق‌ترین و مستقیم‌ترین اصطلاحات. این فهم هر دو شباهت و **تفاوت‌های زیاد** را آسان‌تر می‌کند، چون همه فهم ساده و مشترکی از معنای «سیب» داریم.

به‌خاطر سردرگمی و درهم‌آمیختگی اصطلاحات، معتقدم برچسب «prototypal inheritance» خودش (و تلاش برای اعمال نادرست همهٔ اصطلاحات مرتبط class-orientation مثل «class»، «constructor»، «instance»، «polymorphism» و غیره) **بیشتر ضرر کرده تا فایده** در توضیح نحوهٔ *واقعی* کار مکانیزم جاوااسکریپت.

«Inheritance» دلالت بر عملیات *کپی* دارد، و جاوااسکریپت propertyهای object را کپی نمی‌کند (به‌طور بومی و پیش‌فرض). به‌جای آن JS لینکی بین دو object می‌سازد که یک object می‌تواند اساساً دسترسی property/تابع را به object دیگر *delegate* کند. «Delegation» (فصل ۶ را ببینید) اصطلاح بسیار دقیق‌تر برای مکانیزم object-linking جاوااسکریپت است.

اصطلاح دیگر که گاهی در جاوااسکریپت پرتاب می‌شود «differential inheritance» است. ایده این است که رفتار object را بر اساس آنچه *متفاوت* از توصیف‌گر کلی‌تر است توصیف می‌کنیم. مثلاً توضیح می‌دهید ماشین نوعی وسیلهٔ نقلیه است اما با دقیقاً ۴ چرخ، به‌جای بازتوصیف همهٔ جزئیات تشکیل‌دهندهٔ وسیلهٔ نقلیهٔ کلی (موتور و غیره).

اگر سعی کنید هر object داده‌شده در JS را به‌عنوان مجموع کل رفتاری که *از طریق delegation در دسترس* است در نظر بگیرید، و **در ذهن همهٔ آن رفتار را در یک *چیز* ملموس صاف کنید**، آنگاه می‌توانید (نوعاً) ببینید «differential inheritance» چطور می‌تواند جور شود.

اما مثل «prototypal inheritance»، «differential inheritance» وانمود می‌کند مدل ذهنی شما مهم‌تر از آنچه فیزیکی در زبان اتفاق می‌افتد است. این واقعیت را نادیده می‌گیرد که object یعنی `B` واقعاً به‌صورت تفاضلی ساخته نشده، بلکه با ویژگی‌های مشخص تعریف‌شده ساخته شده، در کنار «سوراخ»هایی که چیزی تعریف نشده. در این «سوراخ»ها (فاصله یا فقدان تعریف) است که delegation *می‌تواند*接手 شود و روی پرواز آن‌ها را با رفتار delegate‌شده «پر کند».

object به‌طور پیش‌فرض بومی، **از طریق کپی**، به آن object تفاضلی تکی که مدل ذهنی «differential inheritance» دلالت می‌کند صاف نمی‌شود. به‌همین دلیل «differential inheritance» برای توصیف نحوهٔ واقعی کار مکانیزم `[[Prototype]]` جاوااسکریپت به‌طور طبیعی جور نمی‌شود.

*می‌توانید* اصطلاحات و مدل ذهنی «differential inheritance» را ترجیح دهید، به سلیقه، اما انکار این واقعیت نیست که *فقط* با حرکات آکروباتیک ذهنی در ذهن شما جور می‌شود، نه رفتار فیزیکی در engine.

### «Constructor»ها

برگردیم به کد قبلی:

```js
function Foo() {
	// ...
}

var a = new Foo();
```

دقیقاً چه چیزی ما را وادار می‌کند فکر کنیم `Foo` یک «class» است؟

اول، استفاده از واژه‌کلیدی `new` را می‌بینیم، درست مثل زبان‌های مبتنی بر class وقتی instanceهای class را می‌سازند. دوم، به نظر می‌رسد در واقع متد *constructor* یک class را اجرا می‌کنیم، چون `Foo()` در واقع متدی است که فراخوانی می‌شود، درست مثل فراخوانی constructor یک class واقعی وقتی آن class را instantiate می‌کنید.

برای تشدید سردرگمی معناشناسی «constructor»، object با برچسب دلخواه یعنی `Foo.prototype` ترفند دیگری در آستین دارد. این کد را در نظر بگیرید:

```js
function Foo() {
	// ...
}

Foo.prototype.constructor === Foo; // true

var a = new Foo();
a.constructor === Foo; // true
```

object یعنی `Foo.prototype` به‌طور پیش‌فرض (در زمان اعلان در خط ۱ قطعه!) property عمومی و non-enumerable (فصل ۳ را ببینید) به نام `.constructor` می‌گیرد، و این property ارجاعی برگشتی به تابع (`Foo` در این مورد) است که object به آن وابسته است. علاوه بر این می‌بینیم object یعنی `a` ساخته‌شده توسط فراخوانی «constructor» یعنی `new Foo()` *به نظر* propertyی به نام `.constructor` رویش دارد که به‌طور مشابه به «تابعی که آن را ساخته» اشاره می‌کند.

**یادداشت:** این در واقع درست نیست. `a` property یعنی `.constructor` رویش ندارد، و هرچند `a.constructor` در واقع به تابع `Foo` resolve می‌شود، «constructor» **واقعاً به معنای** «ساخته‌شده توسط» نیست، آن‌طور که به نظر می‌رسد. به‌زودی این عجیب‌بودن را توضیح می‌دهیم.

آها، بله، همچنین... بر اساس قرارداد در دنیای جاوااسکریپت، «class»ها با حرف بزرگ نام‌گذاری می‌شوند، پس اینکه `Foo` به‌جای `foo` است نشانهٔ قوی است که قصد داریم «class» باشد. برای شما کاملاً واضح است، درست!؟

**یادداشت:** این قرارداد آن‌قدر قوی است که بسیاری linterهای JS در واقع *شکایت* می‌کنند اگر `new` را روی متدی با نام کوچک فراخوانی کنید، یا اگر روی تابعی که با حرف بزرگ شروع می‌شود `new` فراخوانی نکنیم. عجیب است که این‌قدر برای *درست* کردن (جعلی) «class-orientation» در جاوااسکریپت تقلا می‌کنیم که قانون linter می‌سازیم تا مطمئن شویم حرف بزرگ استفاده می‌کنیم، حتی با اینکه حرف بزرگ ***هیچ* معنایی** برای engine جاوااسکریپت ندارد.

#### Constructor یا فراخوانی؟

در قطعهٔ بالا، وسوسه‌انگیز است فکر کنیم `Foo` یک «constructor» است، چون با `new` فراخوانی می‌کنیم و مشاهده می‌کنیم که object را «construct» می‌کند.

در واقع، `Foo` بیشتر از هر تابع دیگر در برنامهٔ شما «constructor» نیست. خود توابع **constructor نیستند**. با این حال وقتی واژه‌کلیدی `new` را جلوی فراخوانی تابع معمولی می‌گذارید، آن فراخوانی تابع را به «constructor call» تبدیل می‌کند. در واقع `new` نوعاً هر تابع معمولی را می‌رباید و به صورتی فراخوانی می‌کند که object می‌سازد، **علاوه بر هر کار دیگری که قرار بود انجام دهد**.

مثلاً:

```js
function NothingSpecial() {
	console.log( "Don't mind me!" );
}

var a = new NothingSpecial();
// "Don't mind me!"

a; // {}
```

`NothingSpecial` فقط یک تابع معمولی قدیمی است، اما وقتی با `new` فراخوانی می‌شود object *می‌سازد*، تقریباً به‌عنوان اثر جانبی، که اتفاقاً به `a` انتساب می‌دهیم. **فراخوانی** یک *constructor call* بود، اما `NothingSpecial` به خودی خود *constructor* نیست.

به بیان دیگر، در جاوااسکریپت مناسب‌ترین گفته این است که «constructor» **هر تابعی است که با واژه‌کلیدی `new` جلوش فراخوانی شود**.

توابع constructor نیستند، اما فراخوانی‌های تابع «constructor call» هستند اگر و فقط اگر `new` استفاده شود.

### مکانیک

آیا *آن‌ها* تنها محرک‌های رایج بحث‌های «class» بدفرجام در جاوااسکریپت‌اند؟

**نه دقیقاً.** توسعه‌دهندگان JS برای شبیه‌سازی هرچه می‌توانند از class-orientation تلاش کرده‌اند:

```js
function Foo(name) {
	this.name = name;
}

Foo.prototype.myName = function() {
	return this.name;
};

var a = new Foo( "a" );
var b = new Foo( "b" );

a.myName(); // "a"
b.myName(); // "b"
```

این قطعه دو «class-orientation» ترفند اضافی در حال اجرا نشان می‌دهد:

1. `this.name = name`: property یعنی `.name` را روی هر object (`a` و `b` به‌ترتیب؛ فصل ۲ را دربارهٔ binding مربوط به `this` ببینید) اضافه می‌کند، مشابه نحوهٔ encapsulate کردن مقادیر داده توسط instanceهای class.

2. `Foo.prototype.myName = ...`: شاید تکنیک جالب‌تر، این property (تابع) را به object یعنی `Foo.prototype` اضافه می‌کند. حالا `a.myName()` کار می‌کند، اما شاید غافل‌گیرانه. چطور؟

در قطعهٔ بالا، وسوسه‌انگیز است فکر کنیم وقتی `a` و `b` ساخته می‌شوند، propertyها/توابع روی object یعنی `Foo.prototype` *کپی* می‌شوند به هر یک از objectهای `a` و `b`. **با این حال این اتفاق نمی‌افتد.**

در ابتدای این فصل، لینک `[[Prototype]]` و نحوهٔ فراهم کردن قدم‌های fall-back جستجو اگر ارجاع property مستقیماً روی object پیدا نشود را به‌عنوان بخشی از الگوریتم پیش‌فرض `[[Get]]` توضیح دادیم.

پس به‌خاطر نحوهٔ ساخته‌شدن، `a` و `b` هر کدام در نهایت لینک داخلی `[[Prototype]]` به `Foo.prototype` دارند. وقتی `myName` روی `a` یا `b` به‌ترتیب پیدا نمی‌شود، به‌جای آن (از طریق delegation، فصل ۶ را ببینید) روی `Foo.prototype` پیدا می‌شود.

#### بازبینی «Constructor»

بحث قبلی دربارهٔ property یعنی `.constructor` و اینکه *به نظر* می‌رسد `a.constructor === Foo` درست بودن یعنی `a` property واقعی `.constructor` رویش دارد که به `Foo` اشاره می‌کند را به یاد دارید؟ **درست نیست.**

این فقط سردرگمی بدشانسی است. در واقع، ارجاع `.constructor` هم *delegate* می‌شود به `Foo.prototype` که **اتفاقاً** به‌طور پیش‌فرض `.constructor` دارد که به `Foo` اشاره می‌کند.

*به نظر* خیلی راحت می‌رسد که object یعنی `a` «ساخته‌شده توسط» `Foo` به property یعنی `.constructor` که به `Foo` اشاره می‌کند دسترسی داشته باشد. اما این چیزی بیش از حس امنیت کاذب نیست. تصادف خوشایندی است، تقریباً مماس، که `a.constructor` *اتفاقاً* از طریق این delegation پیش‌فرض `[[Prototype]]` به `Foo` اشاره می‌کند. در واقع چند راه هست که فرض بدفرجام معنای «ساخته‌شده توسط» برای `.constructor` می‌تواند برگردد و شما را گاز بگیرد.

اول، property یعنی `.constructor` روی `Foo.prototype` فقط به‌طور پیش‌فرض روی object ساخته‌شده وقتی تابع یعنی `Foo` اعلان می‌شود هست. اگر object جدیدی بسازید و ارجاع object پیش‌فرض یعنی `.prototype` یک تابع را جایگزین کنید، object جدید به‌طور پیش‌فرض به‌طور جادویی `.constructor` رویش نمی‌گیرد.

در نظر بگیرید:

```js
function Foo() { /* .. */ }

Foo.prototype = { /* .. */ }; // create a new prototype object

var a1 = new Foo();
a1.constructor === Foo; // false!
a1.constructor === Object; // true!
```

`Object(..)` `a1` را «construct» نکرد، درست است؟ قطعاً به نظر می‌رسد `Foo()` آن را «construct» کرده. بسیاری توسعه‌دهندگان `Foo()` را سازنده می‌دانند، اما جایی که همه‌چیز از هم می‌پاشد وقتی است که فکر کنید «constructor» یعنی «ساخته‌شده توسط»، چون با آن استدلال `a1.constructor` باید `Foo` باشد، اما نیست!

چه اتفاقی می‌افتد؟ `a1` property یعنی `.constructor` ندارد، پس به زنجیرهٔ `[[Prototype]]` به `Foo.prototype` delegate می‌کند. اما آن object هم `.constructor` ندارد (مثل object پیش‌فرض `Foo.prototype` که داشت!)، پس به delegate کردن ادامه می‌دهد، این بار به `Object.prototype`، بالای زنجیرهٔ delegation. *آن* object در واقع `.constructor` رویش دارد که به تابع داخلی `Object(..)` اشاره می‌کند.

**تصور غلط، رد شد.**

البته می‌توانید `.constructor` را به object یعنی `Foo.prototype` برگردانید، اما این کار دستی می‌خواهد، به‌ویژه اگر بخواهید با رفتار بومی مطابقت داشته باشد و non-enumerable باشد (فصل ۳ را ببینید).

مثلاً:

```js
function Foo() { /* .. */ }

Foo.prototype = { /* .. */ }; // create a new prototype object

// Need to properly "fix" the missing `.constructor`
// property on the new object serving as `Foo.prototype`.
// See Chapter 3 for `defineProperty(..)`.
Object.defineProperty( Foo.prototype, "constructor" , {
	enumerable: false,
	writable: true,
	configurable: true,
	value: Foo    // point `.constructor` at `Foo`
} );
```

کار دستی زیادی برای درست کردن `.constructor`. علاوه بر این، واقعاً فقط تصور غلط اینکه «constructor» یعنی «ساخته‌شده توسط» را جاودانه می‌کنیم. توهم *گران*ی است.

واقعیت این است که `.constructor` روی object به‌طور پیش‌فرض دلخواه به تابعی اشاره می‌کند که متقابلاً ارجاعی برگشتی به object دارد — ارجاعی که آن را `.prototype` می‌نامد. واژه‌های «constructor» و «prototype» فقط معنای پیش‌فرض شلی دارند که ممکن است بعداً درست باشد یا نباشد. بهترین کار یادآوری به خود است: «constructor یعنی ساخته‌شده توسط نیست».

`.constructor` property جادویی تغییرناپذیر نیست. *non-enumerable* است (قطعهٔ بالا را ببینید)، اما مقدارش قابل نوشتن است (قابل تغییر)، و علاوه بر این می‌توانید property با نام `constructor` را روی هر object در هر زنجیرهٔ `[[Prototype]]` اضافه یا بازنویسی کنید (عمداً یا تصادفی)، با هر مقداری که مناسب دیدید.

به‌خاطر نحوهٔ پیمایش الگوریتم `[[Get]]` در زنجیرهٔ `[[Prototype]]`، ارجاع property یعنی `.constructor` پیدا شده در هر جا ممکن است کاملاً متفاوت از انتظار شما resolve شود.

می‌بینید معنایش چقدر دلخواه است؟

نتیجه؟ ارجاع دلخواه object-property مثل `a1.constructor` را نمی‌توان *اعتماد* کرد که ارجاع تابع فرض‌شدهٔ پیش‌فرض باشد. علاوه بر این، همان‌طور که به‌زودی می‌بینیم، فقط با حذف ساده، `a1.constructor` حتی می‌تواند به جایی کاملاً غافل‌گیرکننده و نامعقول اشاره کند.

`.constructor` به‌شدت غیرقابل اعتماد است و ارجاع ناامنی برای تکیه در کد شما. **به‌طور کلی چنین ارجاع‌هایی در صورت امکان باید اجتناب شوند.**
